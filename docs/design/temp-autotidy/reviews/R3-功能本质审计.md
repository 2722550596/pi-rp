## §1 独立作答：只为达成 E1-E9，我的最优架构

### 1.0 从效果倒推的硬约束

先把 E1-E9 翻译成架构约束，再谈组件：

| 约束 | 来源 | 推论 |
|---|---|---|
| 全程无角色 turn 参与 | E1 | 触发必须是宿主的确定性代码（计数器/阈值），不能是角色 agent 自己调工具或被提示词引导去做 |
| 不打断、不阻塞、不污染上下文；tidy 对话不进角色 transcript/raw_log | E2 | 整理必须运行在**独立的对话/循环**里，有自己的消息史（或无消息史），与角色 session 的持久化通道物理隔离 |
| 无记忆工具的 preset 也能整理 | E3 | 整理执行者不能是角色 agent，也不能复用角色 agent 的工具策略；它必须自带独立的工具集与提示词 |
| 简报下 turn 自然可见，不唤醒新 turn | E4 | 需要宿主已有的"排队注入"类机制（把一条消息放进角色会话，下次组装上下文时带上），而不是发起一次新的模型调用 |
| preset 可整体覆写 tidy 提示词，与 compaction 同惯例 | E5 | 提示词装配走 preset 的覆写通道，tidy 不自创第二套配置惯例 |
| 失败/禁用/未配置回退现有手动通知 | E6 | 整理路径是**叠加**在现有手动通知之上，通知代码一个字不改，只把"总是通知"改成"整理失败才通知" |
| 简报无废话 | E7 | 默认提示词内写死风格禁令；这是提示词工程问题，不需要机制 |
| 任意草稿类型 | E8 | 提示词的判断框架必须内容中立（"逐条判断去留"而非"判断是否为反思笔记"）；去留判断是语义任务，LLM 合理 |
| 可整体关闭，关闭后与现状一致 | E9 | 一个总开关 + 关闭时触发钩子直接 no-op；不引入"半开"状态 |

核心推论一句话：**E1+E2+E3 三条合起来，唯一可行的形态是"宿主自有的、与角色循环解耦的第二个 agent 循环（side loop）"，其定位 analogous to compaction——compaction 本来就是平台里"自动、异步、独立对话、不进角色上下文"的先例，tidy 是同一形态减去上下文替换、加上记忆写工具与简报注入。**

### 1.1 组件清单（五个，个个有 E 编号背书）

1. **触发器（确定性代码，零 LLM）**：宿主在 TEMP 写入路径上维护计数（条数或字节数，阈值可配）。在角色 turn 收尾的安全点检查阈值，越线则入队一个整理任务并清零计数。纯 if 语句。E1 由它达成，E9 的开关也装在这里（关 = 检查直接 return，现状逐字节不变）。
2. **任务队列/单飞控制（确定性代码）**：每会话至多一个在途 tidy 任务；角色 turn 正在跑时延迟到 turn 边界再启动，避免读写竞争。fire-and-forget，不 await 进回复路径。E2 的"不阻塞"由它达成。
3. **TidyRunner（唯一的 LLM 环节）**：复用平台已有的 agent loop 装配（与 compaction/subagent 同一层的循环原语），自带三样东西：
   - **输入**：TEMP 快照**直接注入**提示词（TEMP 本来就是宿主手里的一块 buffer，不需要给模型任何"翻找"工具——数据就在手边，拼进 prompt 是最短路径）。
   - **工具**：仅记忆读写 + 一个"提交 TEMP 残留"工具（决定哪些条目留下）。不给角色 preset 的工具，不给检索类工具。E3 由"工具集独立于角色 preset"达成。
   - **消息史**：runner 的对话落在独立的 tidy 日志（或干脆不落盘），绝不 append 到角色 session。E2 的"不污染、不进 transcript/raw_log"由存储通道隔离达成。
4. **简报注入器（确定性代码）**：截取 runner 的最终输出文本，经宿主已有的"自定义消息/排队消息"通道塞进角色会话，标记为下 turn 组装上下文时可见、不触发新调用。E4 达成。简报内容就是 runner 的收尾文本本身，宿主不做二次加工。
5. **兜底（确定性代码）**：整个 tidy 任务包在 try/catch 里；任何失败（模型错误、超时、禁用、未配置）→ 调现有的手动 TEMP 通知函数发通知。E6 达成，且现有通知路径零修改。

数据流一行：`角色 turn 写 TEMP → 计数越线 → 入队 → runner（TEMP 注入 + 记忆工具 + 残留提交）→ 成功：提交残留 + 简报入队；失败：手动通知`。

竞争处理：TEMP 带单调版本号；runner 基于快照 vN 工作，提交时若版本已前进（整理期间角色又写了），简单策略是把残留提交作废、重新计数（下个周期再来一轮）——宁可多整理一次，不做合并逻辑。

### 1.2 提示词策略要点（默认模板）

- **任务定义内容中立**（E8）："TEMP 是通用缓冲区，逐条判断：写入记忆 / 丢弃 / 留守"，全篇不出现任何内容类型名词。
- **风格禁令前置且具体**（E7）：明令禁止"好了/完成/这是简报/以下是"类元话语；要求输出即简报本体，无变化时输出一行事实（如"本次无写入"）。
- **无交互**：禁止提问、禁止请求确认——runner 是无人值守循环，问了也没人答。
- **覆写语义**（E5）：preset 字段 = 整体替换默认模板（与 compaction 提示词覆写同一语义），不做模板拼接，避免"覆写了一半"的语义泥潭。

### 1.3 我会刻意**不做**的事

- 不让角色 agent 感知 tidy 的存在（提示词里不提）——E1 要求"无角色动作"，任何"提醒角色配合"的设计都在制造反面。
- 不给 runner 检索/搜索工具——TEMP 全量在手，检索是伪需求。
- 不做整理结果的 diff 审计/回滚 UI——E1-E9 没要。
- 不为 tidy 单独建配置体系——挂在现有 preset + settings 两级上，一个开关一个阈值一个覆写字段，到此为止。

### 1.4 复杂度自检（对照 1.1 的每个组件问：删掉会丢哪个 E？）

触发器→E1/E9；单飞→E2/E1（防风暴）；runner→E3/E8（语义任务）；注入器→E4；兜底→E6。五个组件无冗余。LLM 只出现在"判断去留"这一语义必要点上，其余全部确定性代码。

## §3 无道理复杂度清单（逐项：质疑在先，判定在后）

判定标准：一个环节若可用更简单的**确定性**机制替代且效果不减 = 无道理复杂度。LLM 调用仅"去留判断/归位选址/简报撰写"三个语义必要点为合法。

**a) D10 载体：agentLoop 自建 runner，否决 runSubagent —— 历史决策审计：简单且必要，PASS。**
质疑：runSubagent 是现成子代理设施，为何重造？核查结论：否决依据成立且最终形态更简。`run.ts:146` inMemory / `:157` noTools:"builtin" / `:167` resourceLoader 空壳（零扩展发现）已核实——记忆工具唯一提供方是 memory module（`module.ts:682-691` 经 registerTool），不挂 module 就没工具、挂了就 autoretain/raw_log 双重污染（`:4766` 无条件挂载已核实）。修 guard 只治污染，工具注入仍需新机制；且触发点在 memory 包，headless 禁 import coding-agent（§5.5）——走 runSubagent 要么违反硬边界，要么把编排搬进 host，接口从"注入一个 StreamFn"膨胀成"传工具+提示词+收简报"。最终形态（memory 侧 loop + host 闭包）接口最窄、复用既有传输层（`Models.streamSimple` satisfies StreamFn，`CHANGELOG.md:155` 已核实）。**零新传输机制，唯一新造物是"把闭包交出去"。**

**b) §2.9 v2 导航修复 N1-N4 —— 历史决策审计：用户命令范围内、最终形态最小，PASS。**
质疑：{temp_list} SQL 直出已给 tidy 底册，修复对 E1-E9 是否必需？判定：就 E1-E9 单独论**非必需**（S14 复核是兜底眼，主账是底册回执，03 §6 自认）；但系明月明拍板必修（"怎么可能会绕过啊……严重 bug"，初版绕过被推翻），且修复同步救活 E6 手动路径与角色自查——`buildTempNotifyContent` 的 `MEM://recent/20` 指引在嵌套草稿下实测拿不全（`temp-notify.ts:46` 已核实）。最终形态审计：虚拟域根零迁移（对照"物理根行三连爆炸"论证成立；`store.ts:470-485` scheme 永不建行已核实）、includeStubs 默认 false 保既有渲染字节不漂、index 单趟计数。**非"复刻主代理研究路径"，系用户明令 + 最小实现。**

**c) 跨进程互斥锁全家桶（锁 + 心跳 + 僵死回收 + fencing + 冷却 + last-finish）—— 必要，PASS。**
质疑：单进程单飞不够吗？判定：WAL + busy_timeout=5000 是 README §3 明文的多进程契约——同库多进程是受支持部署；无锁则两个 tidy 交错 consolidate/forget 同批节点（读-改-写竞态、重复归档/误删）。设计里每个齿轮都有"漏了会怎样"且逐一成立（假死→心跳；死亡→僵死回收；回收后原主苏醒→fencing lock-lost；D3 不清空使命→冷却防多会话空转）。已是最小正确形态。fencing 可辩但僵尸写污染真实，保留。

**d) TIDY_MODEL_STUB 占位模型 —— 唯一可避免复杂度，要求显性化处理。**
质疑：`AgentLoopConfig.model` 必填（`types.ts:168` 已核实）而模型解析在 host 闭包 → memory 侧传 `as unknown as Model` 假对象，依赖"loop 只转发不解引用"（`agent-loop.ts:319`：getApiKey 未提供时短路 `.provider`，已核实），代价：① 类型系统里留一个文书化谎言；② AgentEvent 快照 model 字段显示假值 → 需要跨文档纪律"落账禁止依赖事件 model 字段"（01 §5）来对冲。**确定性更简替代存在**：`sideStreamFn` 返回 `{ streamFn, model }`（或伴生 getter），stub、观测面谎言、跨文档纪律三者全消，代价仅修订契约 §2.3 冻结形状。判定：运行时无害（seam 已验证），不构成 veto，但属"为冻结形状付长期税"。**要求：实现前修订 §2.3 形状，或书面接受该税并写入 01 §5——二选一显性化，不许默认滑过。**

**e) S14 模型 recall 复核 —— 可接受，PASS。**
质疑：引擎已确定性重数 afterCount（01 §3.3），为何让模型再遍历？判定：afterCount 是审计对账（03 §5），复核服务于"简报 R 如实"（快照陈旧窗口内漏掉的草稿只有模型自己知道）；一次 recall 在 maxTurns 预算内，且 S14 明文"复核是兜底眼，主账是底册回执"。非"SQL 可直出让模型翻找"哨兵——底册直出恰是该哨兵的正确反面的示范。

**f) 其余清点（均 PASS）**：{max_turns} 变量 + replace-if-present（给 S9/T3 诚实判断供数，微成本）；02 每轮 registerSideRequest/unregister（防 controller 泄漏）；缺省补全 `{triggerTurn:true}` 补在 host 层（防手动通知静默降级，论证经引擎四象限核实成立）；pull getter（热切换唯一正确解）；冷却/last-finish 双 key（§7-01 备案）。
