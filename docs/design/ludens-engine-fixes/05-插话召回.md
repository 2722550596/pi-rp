## 1. 定位与范围

**做什么**：`steer()` 插入的用户消息，在进入上下文时触发和 `prompt()` 相同的记忆自动召回；召回结果（`rp-memories`）位于这批插话之后、下一次 LLM 调用之前。两条进入路径都覆盖：

- 路径 A：agent loop 在运行中注入；
- 路径 B：一轮结束后，`continue()` 把插话队列当作新一轮输入。

**不做什么**（对应 01 §2.8 的范围排除项）：

- followUp 队列的消息不触发召回（需求只提了插话，维持现状）；
- 被新召回取代的旧召回仍可能注入降级结果（`recall.ts:630-635`、`module.ts:532`）：`prompt()` 路径原有行为，不改；
- `abort()` 不清插话队列，之后自动续跑会把插话送进新一轮并召回：不改，要丢弃的宿主自己 `clearQueue()`；
- 召回没有总超时，与 `prompt()` 路径一致（收口裁决 C16 维持）；要加另行立项。

另外不改：`steer()`、`_queueSteer` 的入队逻辑（`agent-session.ts:3283-3286`、`:3304-3321`）；记忆召回算法、去重规则、`rp-memories` 形状（T6）。

**接线（收口裁决 C4、C21）**：agent 包新增 `AgentLoopConfig.onSteeringBatch` 钩子；会话新增事件 `steering_injected`（ludens 依赖，见 PE14）；会话直接调用 `MemoryModule.onSteeringMessages`，沿用 `onTurnEnd`、`onLeafChange` 的模块方法调用模式（`agent-session.ts:1426`、`:3750`），**不经扩展 runner**。不新增扩展事件，`steering_context` 作废。

**涉及文件**：`packages/agent/src/types.ts`、`packages/agent/src/agent.ts`、`packages/agent/src/agent-loop.ts`、`packages/coding-agent/src/core/agent-session.ts`（steer 路径、`steering_injected`、调用记忆模块方法）、`packages/memory/src/module.ts`（`MemoryModule` 接口与返回对象、召回逻辑抽取）。文档：`rpc.md`、`json.md`、各包 `CHANGELOG.md`（§6）。

## 4. 行为契约

### 4.1 端到端流程

**路径 A（轮中）**，按顺序：

1. agent-loop 的轮询拿到非空批次 `batch`（`agent-loop.ts:284/311/386`）。
2. 循环调用 `config.onSteeringBatch(batch)`（NEW，§5）。循环在此 `await`，下一步要等它完成。
   - 会话实现 `_handleSteeringBatch` 先发 `steering_injected`（会话事件，§4.4），再调用 `const result = await this._memoryModule?.onSteeringMessages(batch)`。
   - `MemoryModule.onSteeringMessages` 对 `batch` 做召回与去重，返回单个 `{ message: Record<string, unknown> }` 或 `undefined`。会话读取 `result?.message`，转换成 0 或 1 条 custom 消息作为 `extras: AgentMessage[]`（§5）。
3. 循环对 `[...batch, ...extras]` 逐条 `message_start`、`message_end`，再 push 进 `currentContext.messages` 与 `newMessages`（`agent-loop.ts:316-324` 改写）。`message_end` 经会话处理函数持久化，`rp-memories` 因此成为 `rebuildInjectedFromEntries` 可见的条目。
4. 进入 `streamAssistantResponse`：下一次 LLM 调用，此时 `rp-memories` 已在上下文中。

**路径 B（run 边界）**，按顺序：

1. `_runAgentPrompt` 循环：`_handlePostAgentRun()` 返回 true（`agent-session.ts:2900-2901`），调用 `agent.continue()`（`:2917`）。
2. `continue()`：最后一条是 assistant，`drain()` 得到 `batch`（`agent.ts:410`）。
3. 调用 `this.onSteeringBatch(batch)`（同一个会话实现，同样先发 `steering_injected`）。
4. `runPromptMessages([...batch, ...extras], {skipInitialSteeringPoll: true})`（`agent.ts:412` 改写）。这些消息作为新一轮 prompts 发 `message_start`、`message_end`，然后进入 LLM 调用。

### 4.3 召回规则（记忆侧）

1. **过滤**：只取 `role === "user"` 的消息。取文本规则与 `prompt()` 路径相同：去首尾空白，空文本跳过，`/` 或 `\` 开头跳过（`module.ts:570-571` 的规则）。图片不参与召回（`prompt()` 路径也只用文本）。
2. **合并**：过滤后的文本按队列顺序用 `"\n"` 拼成一个字符串，作为 `queries[0]`。没有可用文本直接返回 `undefined`，不发起召回。
3. **双查询**：与 `prompt()` 相同，`queries = [merged, "Prior context:\n…"]`（prior 为空时只有一条）。prior 由 `collectPriorContext(snapshot.entries)` 取得（`module.ts:269`）。
4. **去重与注入**：与 `prompt()` 路径同一个函数 `recallInjection`（§5），按 uri+md5 去重，只注入新内容，返回 `rp-memories` 消息（`display:false`）。
5. **失败**：`recallInjection` 不捕获异常。`handleSteeringMessages` 包装层捕获后记一条 warn 并返回 `undefined`，注入照常进行。warn 走记忆包的通道 `process.stderr.write("[memory] …\n")`（收口 C3，与 `packages/memory/src/schema.ts:235` 相同）。`handleBeforeAgentStart` 的静默捕获保持不变（`module.ts:590-596` 的行为）。

### 4.4 ludens 可依赖的事件（PE14，回答 ludens 01 §2.9）

事件名已定稿：`steering_injected`（会话事件）。`steering_context` 已作废（收口裁决 C4）。

`steering_injected` 只通过 `this._emit` 发给会话的本地监听器（`session.subscribe` 的订阅者），不镜像给扩展，因此不走 `_emitSessionEvent`。ludens 02 通过 `session.subscribe` 收到它。

每个注入批次按固定顺序发出：

| 顺序 | 事件 | 何时 | 载荷与保证 |
|---|---|---|---|
| 1 | `steering_injected`（会话事件） | 批次确定注入、尚未进入上下文时；**每个注入批次恰好发一次** | `{type:"steering_injected", messages: AgentMessage[]}`；`messages` 是这批插话（队列顺序，与入队顺序相同，可能含自定义消息，宿主按 `role` 过滤）。路径 A 与 B 都发 |
| 2 | `message_start`/`message_end`（role=user） | 每条插话进入上下文时 | 与今天相同（`agent-loop.ts:319-320`）。`prompt()` 的用户消息也会发它，宿主需按 steer 记录的文本匹配 |
| 3 | `message_start`/`message_end`（customType=`rp-memories`） | 召回有新内容时 | 与 `prompt()` 路径相同；只在本批插话之后出现 |
| 4 | 下一次 LLM 调用 | 之后 | 上下文已含 2 和 3 |

**对 LudBrain 的直接结论**：要标记已注入，用 `steering_injected`。它在 `message_start` 之前发，所以会话订阅监听器里的上下文**还不含**这批插话；插话的 `message_start` 在召回结束后发出。`clearQueue()` 取走的插话不发 `steering_injected`，也没有 `message_start`，宿主需要用 `queue_update` 或 `clearQueue()` 的返回值清理自己的记录。

### 4.5 漏掉某一步的后果

| 漏掉 | 后果 |
|---|---|
| 不在路径 B 调用钩子 | 压缩期间或运行最后一次轮询之后到达的插话，经路径 B 投递，没有召回，违反 PE10 |
| 钩子不 `await` | 召回结果来不及进入下一次 LLM 调用，违反 §2.8 最后一条 |
| 不把结果做成 `message_start`/`message_end` | 结果进了 `currentContext` 却不进会话条目：下次去重读不到，同一条记忆反复注入；预设编译也读不到 |
| 结果不放在批次之后 | 模型先看到召回再看到插话，与 `prompt()` 顺序不一致 |
| 召回不做去重 | 同一条记忆在每个插话批次里重复注入 |

### 4.6 超时（收口裁决 C16）

本设计不新增总超时，插话路径与 `prompt()` 路径一致（§3.9）。下一次 LLM 调用可能等 20 秒以上（embedding + rerank），这是已知现状；要加另行立项。

| 记忆模块未挂载 | `this._memoryModule` 为 `undefined`（包括未启用、初始化失败、reload 或重建期间）时，`this._memoryModule?.onSteeringMessages(batch)` 不执行召回，`extras = []`；`steering_injected` 照常发出 |

| 批次里没有用户文本（只有图片、只有自定义消息、或 `/` 开头） | 不召回；`steering_injected` 照常发出 |
| `abort()` 发生在钩子 `await` 期间 | `abort()` 不清队列（`agent-session.ts:3887-3893`）；钩子结束后批次照常注入，之后 LLM 调用因 signal 中止。与现在的插话注入一致 |
| `abort()` 之后队列仍有插话 | `_handlePostAgentRun` 返回 true，`continue()` 走路径 B，插话送入新一轮，有召回。要丢弃的宿主自己 `clearQueue()`（01 §2.8 裁决） |
| `clearQueue()` | 取走的插话从 `_steeringMessages` 与 agent 队列移除，没有注入、没有召回、没有 `steering_injected`（`agent-session.ts:3852-3863`） |
| `steeringMode: "one-at-a-time"` | 每批一条，每条各召回一次（`drain()` 只取第一条，`agent.ts:171-`）。只有 `"all"` 才合并 |
| 召回进行中出现 `/tree`、`/fork`、leaf 变化 | `onLeafChange` 取消旧召回（`module.ts:821`；新召回也在 `:532` 取消前次）；`search()` 在 signal 中止时可降级为关键词结果返回（`recall.ts:630-635`）。旧结果仍可能注入，这是 `prompt()` 路径原有行为（01 §2.8 不在范围内） |
| 召回进行中模块被 dispose | `module.ts:876-881` 设置 `disposed`、中止并清空 `recallAbort`，也中止 autoretain/tidy；现有召回返回链（`:529-627`）没有 `disposed` 后置检查，signal 中止时 `search()` 仍可能返回关键词降级结果（`recall.ts:630-635`），Jev 请求失败也会 fail-open（`module.ts:500-501`）。所以在途结果仍可能返回并注入，不能承诺 dispose 后必为 `undefined`；若最终抛异常，插话包装层 warn 后返回 `undefined`，`prompt()` 包装层静默返回。两条路径沿用同一召回取消行为，不新增 stale-result 丢弃逻辑；后续批次则由已清空的 `_memoryModule` 阻止调用旧模块 |
| 召回耗时长（Jev 无超时） | 循环在钩子处等待，下一次 LLM 调用也等待（§4.6，C16 维持） |
| 同一记忆在 `prompt()` 与插话中都命中 | `rebuildInjectedFromEntries` 读到前一次注入的 md5，不重复注入（路径 A 中 `rp-memories` 在 `message_end` 时持久化，早于下一批） |
