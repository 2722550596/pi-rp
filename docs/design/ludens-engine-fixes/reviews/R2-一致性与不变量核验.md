## 7. 发现

### F1（高）— 03 的 `MemoryMacroDefinition` 偏离契约 §2.2 / §2.5

- 证据：
  - 契约 `01:111–115`：宿主接口 `registerMacro(definition: MemoryMacroDefinition)`，"字段与 §2.2 的 `MacroDefinition` 联合类型完全一致"。
  - 契约 `01:66–68`：联合类型的两个分支，`render` 分别是 `MacroRenderer`（同步 `string`）和 `AsyncMacroRenderer`（`Promise<string>`），且异步分支要求 `static: true; async: true` 字面量。
  - 03:234–243：`MemoryMacroRenderContext` 是新名字（契约里没有）；`render` 返回 `string | Promise<string>`；`async?: boolean`（不是字面量）；`runtime: unknown`。
  - 03:403（§9 冲突 1）声称"原样转交"。但 `string | Promise<string>` 的函数不能赋给 §2.2 的任一分支，所以转交处必须有 cast 或适配器。
- 影响：违反契约"字段完全一致"；转交代码无法类型通过，或只能靠 cast 绕过。
- 修复方向：
  - 03 §4.8 改为 §2.2 联合类型的字面镜像：异步分支 `render: (ctx) => Promise<string>`、`static: true`、`async: true`，同步分支保持 `render: (ctx) => string`。
  - `runtime` 的类型：契约 `MacroRenderContext.runtime` 是 `PromptRuntime`，memory 无法 import。这里需要决定：要么 memory 侧用 `unknown` 并把 `MacroRenderContext` 的 `runtime` 字段改宽（需要升级拍板，改 01 §2.2），要么 coding-agent 侧在转交时包一层适配器（不改形状，但需要 cast）。
  - 升级拍板：`runtime` 的类型策略。我的建议是适配器方案，因为它不改冻结契约。
