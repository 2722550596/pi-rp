### 1.2 关键策略

**（1）"静态宏一段时期内只算一次"的最简可靠形态。**
三个候选：
- 形态一：缓存**展开产物**（静态宏的字符串结果），失效时清空。
- 形态二：缓存**整份编译结果**，每轮只拼接 history。不可行：编译输出混着 `{{lastUserMessage}}` 与动态 slot，整体冻结必然出错；拆分编译器内部又会伤筋动骨。
- 形态三：宏引擎里给每个静态宏加全局 memo。改动最小，但失效事件分散在会话层各处，容易漏。

选**形态一**。依据：宏引擎已支持 `mode: "all" | "static" | "dynamic"`（macro-engine.ts:191-201），现有静态系统提示路径就用 `mode: "static"`（agent-session.ts:2504）。做法：静态部分命中缓存则直接替换为字面量，未命中（时期开始）则现算并写缓存；动态部分照常每轮展开。这样 PE3 的逐字节相同是天然的（同一字符串被复用），PE4 的五个事件只改"缓存键/清缓存"这一个点。

注意 `{{setvar}}/{{addvar}}` 有副作用且要求串行（compiler.ts:410 `itemsHaveSideEffectMacros`），缓存层必须保持现有顺序语义，只替换命中的静态片段，不改变副作用宏的执行次序。

**（2）PE4 失效事件挂在已有钩子上。**
- 会话开始：缓存初始为空。
- 换预设：`preset_activated`（agent-session.ts:2670）。
- 工具集、模型：与 `_staticPromptCache` 同键（agent-session.ts:2472-2487 的 `toolNamesKey`、`model`）。
- 换气（压缩）：`compaction_end` 三处 emit（agent-session.ts:4370、4382、4532）之后清缓存。压缩发生在 `_compactBeforeNextAssistantResponse`（agent-session.ts:1108，经 1143 调用），时序上先于下一次编译，不会读到旧值。

不发明新事件系统。

**（3）PE6 静态 slot 宏的取值时点。**
slot 是 `async: true`，宏 render 是同步签名（types.ts:487 `MacroDefinition`）。方案：时期开始后的第一次异步编译（`compileMessages` 的 async 路径，live 路径本来就走它）顺带把三个 slot 的渲染文本写入快照；静态宏 render 只读快照。下一个时期才更新。这样不新增 LLM 调用，也不单独发起渲染。`awaken` 里的"当前时间"行（slots.ts:65-102）会一起被冻结，这正是 PE6 要的。

**（4）PE9 断点怎么打。**
Anthropic 缓存要求前缀逐字节一致。现状：`convertMessages`（anthropic-messages.ts:1134）只在"最后一条消息且 role 为 user"上打断点（1274-1296）。预设在 history 之后放 user 块时（prompt-presets.md:169 的范例），断点落在这个块上。这个块每轮变化，history 末尾不是断点，history 前缀无法独立命中。

最简形态：断点打在**history 末尾**。需要的信息只有一个整数：编译器知道 history 结束的消息索引（`compileMessages` 的 source 已区分 chat-history 与 preset-item），把它随编译结果传给适配器；适配器在该消息最后一个 block 上打 `cache_control`，system 断点保持现状。没有 history 后置块时，history 末尾即最后一条消息，与现状一致。Anthropic 最多 4 个断点：system、tools、history 末尾、最后一条，正好 4 个——这是硬上限，不能再加。

PE9 验收"第二轮 cacheRead 覆盖上一轮 history 末尾"成立的前提：history 末尾之前的内容两轮之间逐字节不变。PE3 的静态冻结保证了 history 之前的前缀稳定；history 本身只增不改，前缀天然成立。

**（5）PE10 steer 召回的接入点。**
现状召回链：`before_agent_start` 注册（module.ts:810）→ `handleBeforeAgentStart`（module.ts:566）→ 读 `event.prompt`（:567）→ 双 query 召回 → 去重（:606）→ 返回 `rp-memories`。`prompt()` 发此事件（agent-session.ts:3070）；steer 不发。
agent-loop 轮询 steer 的位置是 `getSteeringMessages`（agent-loop.ts:284、311、386），消息在那里被 push 进 context。接入点应为这些轮询点的会话侧包装：拿到新到的 steer 后，对其文本执行与 `handleBeforeAgentStart` 相同的召回，把结果与 steer 消息一起进入 context，保证 LLM 调用时召回已就绪。去重逻辑（module.ts:606 的 hash 对照）天然支持多次触发，不重复注入同一版本内容。

不做成新事件类型：复用 `handleBeforeAgentStart` 的管线，只补一个触发点。

**（6）PE1 时钟切换的最小切口。**
所有"现在"取值点（实际核对过）：
- 世界钟读取回退：`store.getWorldTime() ?? new Date().toISOString()`，出现在 slots.ts:65、memory-views.ts:134、module.ts:536（后者是 `.slice(0, 10)` 的日期版本）。
- raw_log 写入：module.ts:830、852 取 `store.getWorldTime()`；`memorize` 默认值 store.ts:425 `input.world_ts ?? this.getWorldTime()`。
- 真实墙钟（已存在，不属于世界钟）：memory-views.ts:97、250 用 `new Date().toISOString()` 计算沉睡天数，注释明确"世界钟绝不能当现在"（memory-views.ts:93-96）。

最简可靠：在记忆包内放一个时钟策略对象，`now()`（参照时间）与 `write()`（写入时间戳）两个方法。世界模式下两者分别返回现状的值（`getWorldTime() ?? new Date().toISOString()` 与 `getWorldTime()`，逐点等价）；真实模式下两者都返回本地带偏移 ISO。memory-views.ts:97、250 已经是真实墙钟，**不需要改**——真实模式下它们的行为天然正确，这也证实两种时钟并存在本代码库里已有先例。

`set_time` 在真实模式下不注册（A1）。`toEpochDays`（recall.ts:228）只取字符串前 10 字符，真实模式写入的本地 ISO 前 10 字符就是本地日期，"按本地日期分天"自动成立。

**（7）失败处理。**
- 召回失败静默跳过是现状（module.ts:592 `catch`），steer 路径沿用。
- 静态缓存 miss 的代价等于现状每轮求值，不会比现在差。
- Anthropic 断点索引缺失时回退到现有"最后一条消息"逻辑。

### 1.3 我会刻意不做的事

1. **不做整份编译结果缓存**（形态二）。
2. **不为 `{{date}}/{{time}}` 发明"半静态"第三态**：静态集合就是 `static: true` 的那几个宏；缓存是否命中由静态集合决定，不由新标记决定。
3. **不动 slot 注册和渲染路径**。PE6 的三个宏是新增，不是改 slot。
4. **不新增 steer 专用事件**：复用 `handleBeforeAgentStart`，只补触发点。
5. **不动 splitSystemMessages、不动酒馆预设**（PE11、PE12）。
6. **不伪造"世界时间"**：真实模式不打印"当前世界时间"，不提供 `set_time`，不把本地时间写进 `world_time` 键值。两种时钟是并列模式。
7. **不做 squash 合并策略配置**：只修"丢非文本块"这一个 bug。
8. **不为 steer 召回设独立开关**：清单没有要求，默认行为对齐 `prompt()`。

### 1.5 效果之间的冲突，以及现有平台做不到的效果

**冲突 1（PE3 vs PE5，同一个 `static` 标记语义冲突）。** 现状 `static: true` 名为"编译时展开一次"（prompt-presets.md:432），实际每轮编译都重新求值（agent-session.ts:2839、2861 每轮传新的 `now`）。PE3 要的是"时期内冻结"，PE5 要的是三个宏每轮新值。裁决：`static` 布尔只决定"进不进缓存"，date/time/lastUserMessage 退出集合（PE5 优先）。文档与代码的错位（PE7）正是因为这个标记语义从未真正生效。

**冲突 2（PE4 的"换气"与 PE9 的"history 前缀稳定"）。** 压缩替换 history 后前缀必然失效，这与 PE4 的"换气后刷新"一致，属于预期，不是缺陷。需要在文档里写清：缓存命中以"时期"为单位，换气是时期边界。

**冲突 3（PE10 与 PE5 对 `{{lastUserMessage}}` 的取值时点）。** steer 进入 context 后，`deriveLatestUserMessage`（compiler.ts:646）取的是最后一条 user 消息，插话会改变下一轮的 `{{lastUserMessage}}`。这是正确语义，不构成冲突；实现时不要为 steer 特判宏取值。

**冲突 4（PE2 与 "墙钟"已有两种用法）。** 当前代码里真实墙钟（memory-views.ts:97、250 的沉睡天数）与世界钟（slots.ts:65、module.ts:536、memory-views.ts:134）已并存，且注释明确二者不能混用（memory-views.ts:93-96）。PE1 真实模式的改动面因此小于直觉：沉睡计算不动，只替换世界钟回退点。

**现有平台做不到，或需要新代码的点：**
1. **PE9 不能只靠改适配器做到**：`convertMessages`（anthropic-messages.ts:1134）看到的是 transform 之后的扁平数组，分不清 history 末尾与预设尾块。必须由上层编译产物传一个边界索引——这是跨包（coding-agent → ai）的新接口，清单里唯一需要动公共类型的地方。[推断] 若不传，任何启发式（如"最后一条 toolResult"）在无工具会话里都会失效。
2. **PE1 的时间文案**：`formatRelativeWorldTime` 的输出（"昨天"等）与 slot 的"（发生于: …）"文案是给角色看的故事内时间（slots.ts:65-102；memory-views.ts:134）。PE1 只说"按本地日期分天"，我按"只换时间来源、文案结构不变"处理。若设计认为文案也要改，是合理延伸。[推断]
3. **PE10 的纯图片插话**：`handleBeforeAgentStart` 对空 prompt 直接返回（module.ts:571 `if (!trimmed ...) return`）。纯图片插话不触发召回是合理边界，不需要为它扩召回。[推断]
4. **PE4 与 resume**：resume 旧会话时，"会话代次开始"与首轮压缩（`_compactBeforeNextAssistantResponse`，agent-session.ts:1143）可能同时发生。两个清缓存动作幂等，无需专门处理。[推断]

### 1.6 我预计设计最容易出错或过度设计的地方（第二阶段重点查）

1. **`static` 标记语义重构。** 最容易出错：沿用"static = 缓存"的直线思路，把 date/time 也缓存住（直接违反 PE5）；或把三个宏的标记全删、改由缓存键区分，导致缓存键设计复杂化。检查：静态集合与"进缓存"是否为同一决定，宏定义里的布尔是否只有一个含义。
2. **PE9 的边界传递。** 最容易过度设计：给 AgentMessage 加通用 tag/注解协议。只需一个可选整数索引从编译产物流到适配器。检查：sync/async 两条编译路径与 implicit-history 回退（compiler.ts:369）下索引都正确——implicit history 时 history 在数组中段，索引要指向 history 末尾而非数组末尾。

5. **PE2 的回归面。** 真实时钟若与 `getWorldTime() ?? new Date()` 散点纠缠，极易在"顺手统一"时改掉世界模式的行为。现状两处 fallback 格式就不同：slots.ts:65 用完整 ISO，module.ts:536 用 `.slice(0, 10)` 日期前缀。切换逻辑必须保留这个差异，不能顺手统一。
6. **PE8 的合并语义。** 最容易顺手做"智能合并"（去重、重排 text/image）。最小修复：text 块按现规则连接，其余块原样保序；纯 text 消息输出保持逐字节不变；toolResult 永不合并（compiler.ts:429 的保护必须原样保留）。
7. **过度设计高发区。** 给静态缓存加 LRU/TTL（不需要，时期由显式事件界定）；给时钟做"混合/回拨"模式（清单只要两种）；给 steer 召回做独立配置开关（清单无此要求）；给 PE9 做多于一个边界的断点策略（Anthropic 上限 4 个，已用满）。凡是为"将来可能"预留的旋钮，第二阶段应打回。

### §1 补：PE13（盲判）

> 效果行：会话主循环的模型请求可以通过 settings 设置 cacheRetention；不设置时行为不变。settings 写 "long" 后，经 SDK 发出的 Anthropic 请求，缓存断点带 ttl "1h"（模型支持长保留时）；不写时请求字节与现在相同。

**先给结论：这条效果的管线在代码里已经端到端存在，缺的只是"settings → 主循环 streamFn"的最后一跳，一个设置项 + 一行注入。**

现状证据：
- 选项类型已有：`cacheRetention?: CacheRetention` 是 `SimpleStreamOptions` 的标准字段（ai/src/types.ts:206-209）。
- 适配器已实现完整解析：`resolveCacheRetention`（anthropic-messages.ts:50-57）——显式传入优先，否则回退环境变量 `PI_CACHE_RETENTION`，否则 `"short"`；`getCacheControl`（anthropic-messages.ts:62-73）在 `retention === "long"` 且 `getAnthropicCompat(model).supportsLongCacheRetention`（ai/src/types.ts:652）时才给 `cache_control` 加 `ttl: "1h"`。
- 主循环的流入口把外部 options 原样透传：`sdk.ts:474-475` `gateway.streamSimple(model, context, { ...options, ... })`——但**没有任何调用方给主循环设置 `cacheRetention`**（全 coding-agent 包 grep 只有 compaction.ts:647 显式设 `"none"`，那是压缩路径，与本效果无关）。
- 未设置时的字节不变性天然成立：`resolveCacheRetention` 无显式值且无 env 时返回 `"short"`，`getCacheControl` 生成的 `cacheControl` 是 `{ type: "ephemeral" }`，**不含 `ttl` 键**——与今天发出的请求逐字节相同（除非用户环境里已设 `PI_CACHE_RETENTION=long`，那属于既有环境行为，不是本效果的回归）。

我的最简做法：
1. settingsManager 增加一个读取项（如 `cacheRetention`，取值 `"short" | "long" | "none"`，缺省 undefined）。
2. 在 `sdk.ts` 的 `streamFn`（465 行附近，settingsManager 已在作用域内）里把该项并入 options：`cacheRetention: options?.cacheRetention ?? settingsManager.getCacheRetention()`。放在 `...options` 之后、与 `maxRetries` 等现有注入并列，不新开通道。
3. 不改适配器、不改类型、不加事件。Anthropic 之外的适配器对不认识的 retention 自然走各自的映射或忽略——这不是本效果的验收范围。

三处刻意不做：
- **不动 compaction 的 `cacheRetention: "none"`**（compaction.ts:647）：压缩请求是独立短任务，效果行只说"会话主循环"，把它一起染上 "long" 反而是行为外溢。
- **不做按模型/按 provider 的细分配置**：模型支持性已有 `supportsLongCacheRetention` 兜底（不支持时 ttl 自动省略，请求仍合法），settings 只需要一个全局值。
- **不在会话层缓存这个值**：每次流调用读一次 settings 的开销可忽略，缓存反而引入"改设置后何时生效"的新问题。

最容易做错的地方：把 "long" 的裁剪逻辑（模型支持与否）写进 settings 读取层或 sdk 层——那是适配器 `getCacheControl` 的职责，sdk 层只传值。第二层错误是给 `"none"` 也走 sessionId 逻辑——适配器已处理（anthropic-messages.ts:543 `cacheSessionId` 在 "none" 时为 undefined），上层别碰。

## §3 无道理的复杂度

> 每项：是什么、在哪、比 §1 独立架构多出什么、为何不必要、更简替代。共 5 项，按严重度排序。另有 2 项"确定性代码交给 LLM 去猜"类问题。

### 3.1 【复杂度】volatile 标记穿 7 层转换链的改型成本 vs 一个整数索引

- **是什么**：04 §4.1 给 pi-ai `UserMessage`/`AssistantMessage` 加 `volatile?: true` 字段，要求标记从编译器穿过 `squashMessages` → `applyRegexRulesToMessages` → `emitContext`（structuredClone）→ `convertToLlm`（custom 分支**必须加透传代码**，messages.ts:283-297）→ SDK 图片过滤 → `splitSystemMessages` → `transformMessages` → 适配器，共 8 个环节，04 §3.2 用一整张表核实"哪一环会丢"。其中 custom 分支是必须改代码的点位，`branchSummary`/`compactionSummary` 分支是"丢了也行但要论证为什么行"的点位。
- **比 §1 多出什么**：我的盲判是"编译产物上带一个可选的 history 边界索引，随编译结果传给适配器"（§1.1 D、§1.2(4)）。多出的是：一个公共类型字段、一条消息级标记的**生命周期论证**（04 §4.1 第 5 点专门论证"会话里永远不会有带 volatile 的消息被持久化"——这正是字段方案的固有负担）、custom 分支的透传代码、以及 `squashMessages` 里新加的"volatile 与非 volatile 永不合并"规则（04 §4.2 规则 2）。
- **为何不必要**：T4（01 §1）说"下标不可靠，因为消息会被过滤、合并"——但**过滤和合并都发生在编译器内部**（squash 在 compileMessages 尾部，compiler.ts:182-184/281-283），编译器自己知道 history 边界在哪里；适配器需要的只是"history 之后的块从第几条开始"这一个数。04 的转换链表恰好证明了字段方案的成本：8 个环节里只有 1 个环节真正需要字段（适配器消费点），其余 7 个环节都在论证"别把它弄丢"。索引方案下这些环节**全部零改动**——数组长度在过滤后变化确实存在（如 toolResult 归一化、空内容 continue），但适配器在 `convertMessages` 里逐条重建 `params` 时**本来就有源消息数组**，一个 `historyEnd: number`（语义：transformedMessages 中索引 < historyEnd 的消息属于缓存前缀）在 `splitSystemMessages` 之后按"移除了几条 system"偏移一次即可。
- **更简替代**：`CompileMessagesResult`（prompt-preset/types.ts:420-424）加一个 `volatileFrom?: number`；`transformContext`（sdk.ts:530-544）把它与消息数组一起传给适配器 options（`streamSimple` 的 options 已是自由形状，ai/src/types.ts:190 起）；适配器读 options 而非消息字段。custom 分支、squash 规则 2、7 层链路论证全部消失。
- **保留项**：04 的 squash 规则 2（volatile/非 volatile 不合并）在索引方案下不需要——squash 可以照旧把尾块并进 history 末尾的 user，只要适配器知道 history 边界，断点照样打对。**这同时消掉一个行为变化**：现有 25 个 `{{lastUserMessage}}` 预设的请求体从"两条 user"变回"一条 user"（04 §6 自己承认"多一条消息、内容不变"，04 §6 兼容性第 1 行），请求体逐字节与现状一致，T5 的"现有预设请求前缀不应变化"得到更完整的满足。**注意**：连续 user 消息经 Anthropic API 是合法的（convertMessages 逐条 push，anthropic-messages.ts:1150-1183 无交替校验），04 方案不会 400——我否定的只是它的改型成本，不是合法性。
- **何时 04 方案反而更好**：若扩展 `emitContext`（runner.ts:1296-1318）替换整个数组（04 §4.4 承认这种情形），索引会失效（第三方数组没有边界信息）。字段方案下第三方数组同样不带 volatile，断点回现状——**两种方案在同一边界上降级行为相同**，不构成取舍理由。

### 3.2 【复杂度】02 的异步宏机器（`presetHasAsyncMacros` + `fillStaticMacros` 双模式 + MacroDefinition 联合类型）超出效果要求

- **是什么**：02 §2.2 把 `MacroDefinition` 从 interface 改为联合类型、强制 `async:true ⟹ static:true`（契约 §2.2）；02 §4.1 新增 `fillStaticMacros(text, runtime, diagnostics, mode)` 在 `renderItemTextSync/Async` 里补齐快照；02 §4.3 新增 `presetHasAsyncMacros` 路由函数；02 §5.1 给 `_rebuildSystemPrompt` 的预设门加宏检查。
- **比 §1 多出什么**：我的盲判是"静态宏的缓存挂编译入口，B2 快照搭每轮编译的顺风车"（§1.2(1)(3)），宏定义形状不动。02 多出了：类型系统的联合化（影响所有 `MacroDefinition` 引用方）、一个新扫描函数的两种模式、一个新路由谓词、静态路径的占位符语义（§5.3 整节在论证 `mode:"static"` 是空操作）。
- **为何不必要**：PE6 只要求"三个内置记忆 slot 有宏形式且是静态宏"（消息 2）。三个记忆 slot 的 render 函数（slots.ts:61-137）**实际上是同步的**——我读了全文：`render` 里没有 `await`，`async: true` 只是 slot 定义上的标记，函数体全部是同步的 store 调用（`getAwakenUris`、`store.listRecentNodes`、`store.listNodes`）。也就是说，`memory.*` 宏的 render 用同步签名就能实现（读 store 是同步 API，`listNodes(): MemoryNode[]`，store.ts:1740）。**整个异步宏机器（联合类型、双模式 fillStaticMacros、presetHasAsyncMacros、异步路由）服务的输入在当下不存在**。契约 §2.2 的"异步静态宏"是为"记忆宏要读库"设计的（T2 理由），但读库不需要 await。
- **更简替代**：`memory.*` 三个宏用**同步 render** 实现（03 的 `createMemoryMacros` 返回的 render 签名本来就可以是同步的——03 §4.8 的 `MemoryMacroDefinition.render: (context) => string | Promise<string>` 已兼容同步）；静态快照机制保留（PE3/PE4 仍需），但 `fillStaticMacros` 退化为"快照里有值用值、没值现算存入"的同步逻辑，不需要 mode 参数、不需要 `presetHasAsyncMacros`、不需要联合类型。02 §5.1 的"`[object Promise]` 拼进字符串"问题随 async 消失。02 §4.6 的"预扫描会导致 slot 渲染两次"论证随之简化（同步 render 下重复渲染无害且成本低，但仍应保留"渲染点补齐"以避免双渲染）。
- **何时 02 方案反而更好**：未来若有真正异步的宏（网络调用）。但效果清单没有这个要求；契约 §2.2 是把"将来可能"做成了类型系统承诺——正是我在 §1.3.7 警告的过度设计模式。

### 3.3 【复杂度】03 的 `dayNumber`/`formatStamp`/`resolveMemoryClock` 新文件 + 时区参数化超出 PE1 的验收

- **是什么**：03 §4.1–4.2 新建 `clock.ts`，含 `resolveMemoryClock`（带 warning 通道）、`formatStamp`（`Intl.DateTimeFormat` + `formatToParts` + `longOffset` 解析，手动处理 `hour === "24"`）、`dayNumber`。
- **比 §1 多出什么**：我的盲判（§1.2(6)）是"真实模式 = `now()`/`write()` 返回本地带偏移 ISO"，用 `Intl.DateTimeFormat(...).format(date)` 一行得到偏移 ISO（`2026-10-16T05:31:07+08:00`）。03 多出了：独立文件、时区校验器、`timezone` 可配置项（契约 §2.1）、`hour24` 归一化等边界处理。
- **为何部分不必要**：PE1 的验收只要求"带时区偏移的真实时间"与"按本地日期分天"，**没有要求时区可配置**——进程本地时区已满足"本地"语义（用户原话："参照时间是本地当前时间"，00 §1 消息 1）。`timezone` 字段与 `resolveMemoryClock` 的校验容错是效果清单外的能力。`formatStamp` 的 `formatToParts` + `longOffset` 手工解析是为了支持**任意 IANA 时区**，若 `timezone` 缺省即进程本地，则 `Intl.DateTimeFormat().resolvedOptions().timeZone` 之外的时区支持整体不必要。
- **更简替代**：`clock.ts` 缩为 `nowStamp()`/`referenceNow()` 两个函数（或直接挂 store），real 模式用 `new Date().toLocaleString("sv-SE", { timeZone: undefined })` 风格的本地偏移 ISO（或保留 `Intl` 但去掉 `timezone` 参数化——直接用进程默认）。03 §10.5 自己承认"WSL 上进程本地时区可能是 UTC"，而 ludens 宿主显式配 `Asia/Shanghai`——**ludens 的真实诉求是"宿主显式指定时区"**，这只需要 `timezone` 字段存在（一行 `options.timeZone = cfg.timezone`），不需要校验器 + warning 通道 + world/real 分叉的 `ResolvedMemoryClock` 对象。校验可缩为"try/catch 构造 formatter，失败回退本地"。
- **何时 03 方案反而更好**：若未来多用户/多部署环境需要每库不同时区。效果清单没有此要求。

### 3.4 【复杂度】05 的 `steering_injected` 会话事件 + `steering_context` 扩展事件双层事件

- **是什么**：05 §4.4/§5 同时新增两个事件：会话事件 `steering_injected`（只 `_emit` 给本地监听器）和扩展事件 `steering_context`（走 runner 分发、有返回值）。记忆模块订阅 `steering_context`（05 §5 module.ts 行）。
- **比 §1 多出什么**：我的盲判（§1.2(5)）是"放宽 `before_agent_start` 的触发时机，让记忆模块复用同一 handler"。05 多出了：`AgentLoopConfig.onSteeringBatch` 钩子（agent 包新字段）、`Agent.onSteeringBatch`（agent 包新公开字段）、`AgentSessionEvent` 新变体、扩展事件类型 + runner 专用发送器 + `RunnerEmitEvent` 排除项 + `ExtensionAPI.on` 重载 + 文档同步（rpc.md/json.md/extensions.md/CHANGELOG/memory-system.md/README，05 §6 共 6 处）。
- **为何部分不必要**：PE10 只要求"插话触发记忆召回"。记忆召回需要的是：在批次进入上下文前拿到批次文本、产出 `rp-memories`。这只需要**一个**钩子。`steering_injected` 是给 ludens 宿主看的（05 §2 引 ludens 01 §2.9"注入后记为 seen"）——**这个需求来自 ludens 的设计文档而非 pi-rp 的效果清单**。检查效果清单：PE10 原文与验收都不含"宿主可见事件"。`steering_context` 扩展事件同理：记忆模块不是扩展 runner 的注册方，它走的是 memory 宿主 `on()`（module.ts:101）——为它建一套扩展事件类型 + runner 发送器，是把记忆模块当成通用扩展来服务，而事实上它已通过专用宿主接口接入。
- **更简替代**：只做 `AgentLoopConfig.onSteeringBatch`（05 §5 的第一行，这个钩子本身是必要的）；记忆模块侧新增宿主回调 `onSteeringBatch`（module.ts 宿主接口，与 `registerSlot` 同层），`_handleSteeringBatch` 直接调它，跳过扩展 runner 的类型/发送器/排除项/重载/6 处文档。ludens 需要的 `steering_injected` 若确需，保留（它便宜，一个 `_emit` 变体）；`steering_context` 整个砍掉。
- **何时 05 方案反而更好**：若"插话召回"要开放给任意扩展（不止记忆模块）。效果清单只有记忆召回一个消费者。

### 3.5 【复杂度】03 的 7 工具提示句追加（"等下次压缩才生效"）违反 PE2 的验收口径

- **是什么**：03 §5（tools.ts:1521 行）、03 §7"提示句（追加到 7 个工具说明，NEW 文本，逐字）"，并声明"这会改变所有模式的工具描述字节（一次性 prompt 变化）…契约 §2.4 明确要求补这段说明，因此接受。见 9.7"。
- **比 §1 多出什么**：我的盲判没有这项——PE1/PE2 的验收是"记忆行为和测试结果与修复前一致"（PE2），工具描述字节变化直接影响所有项目的 prompt。
- **为何不必要**：契约 §2.4 要求"会改变这三项内容的记忆工具，说明文字里要写清楚"，但**这句说明的正确位置是文档（prompt-presets.md / memory-system.md），不是发给模型的工具描述**。发给模型的工具描述是 prompt 的一部分：7 个工具各加一句，每次请求 7 处重复，所有 pi-rp 用户（不只 ludens）的 prompt 字节变化、token 成本增加，换取的信息"静态宏要等压缩才刷新"——**只有用了 `{{memory.*}}` 宏的预设才需要知道**，而用宏的预设作者已从文档读到这条（02 §7.6 也有同样文字）。模型侧不需要知道：模型调用 `memorize` 时关心的是写入成功，不关心预设怎么渲染。
- **更简替代**：提示句只写进文档（02 §7.6 已有）；工具描述不动，world 模式字节零变化，PE2 验收干净。若坚持要模型侧知情，只在 `memorize`/`revise`（真正改变内容的两个）加一句，而非 7 个。
- **裁决依据**：这条是契约层决策（§2.4 明文）而非 03 自作主张，但契约把"写清楚"的位置错误地定在了工具描述上。建议主代理重裁。

### 3.6 【交给 LLM 猜】03 的工具描述按 mode 选词（memorize/revise 时间措辞）

- **是什么**：03 §4.5/§5：memorize/revise 的时间描述按 mode 选词（world"缺省用当前世界时间"/real"缺省用当前真实时间（带时区偏移）"）。
- **为何列为问题**：工具描述是确定性代码的输出，两个模式各写死一句即可（if/else），03 也确实是这么写的——**这项本身没问题**。列出是因为它和 3.5 同源：这类"模式差异通知"被放进了 prompt 面。若 3.5 被打回，此项随之消失。单独保留会导致 mode 差异仍在 prompt 字节里（world 用户也吃到 if/else 的分支结构）。

### 3.7 【交给 LLM 猜】02 §7.1 的文档改写把"OpenAI 原样传"删掉后没有替代句

### 3.8 【复杂度】03 §5 的 `logAudit` 改写

- **是什么**：03 §5 表：`store.ts:1956` `logAudit` 的 `this.getWorldTime()` → `this.nowStamp()`，依据"01:47 裁决"。
- **比 §1 多出什么**：我的盲判（§1.1 A2）只覆盖节点与 raw_log 写入。audit_log 是审计面，非模型可见面。
- **为何列为低危复杂度而非打回**：real 模式下 audit 的 world_ts 从 NULL 变真实时间，**world 模式逐字节相同**（`nowStamp()` world = `getWorldTime()`）。它扩大了 real 模式的行为面（PE1 只提节点与 raw_log），但方向正确（audit 记 NULL 时间无意义）、成本一行、有专测（03 §8.2a）。**保留**，不算打回项；列出供主代理知情。

## §4 结论

**fix-then-go。**

必修项（按优先级）：

1. **§3.2：砍掉异步宏机器**。三个记忆 slot 的渲染函数是同步的（slots.ts:61-137，`render` 无 `await`），`memory.*` 宏用同步 render 即可；`MacroDefinition` 保持 interface，不引入联合类型与 `async`/`static` 联动校验；`fillStaticMacros` 退化为同步"缺值现算、有值用值"；删除 `presetHasAsyncMacros` 与异步编译路由。保留：静态纪元快照、五边界、`_staticPromptCache` 带纪元号（02 §3.3）。PE3/PE4/PE6 全部效果不变，实现面缩小约一半。
2. **§3.4：砍掉 `steering_context` 扩展事件层**。保留 `AgentLoopConfig.onSteeringBatch` 钩子 + `steering_injected` 会话事件（ludens 依赖后者）；记忆模块的召回接线改为宿主回调（module.ts 宿主接口新增 `onSteeringBatch`），不经过扩展 runner。6 处文档同步随之减少到 2 处（rpc.md、memory-system.md）。PE10 效果不变。
3. **§3.5：工具描述提示句回退为文档-only**。7 个工具描述不动，"静态宏等压缩刷新"只写进 prompt-presets.md（02 §7.6）与 memory-system.md。PE2 的"记忆行为和测试结果与修复前一致"验收恢复干净；memorize/revise 的按 mode 选词（§3.6）随本项一并回退。
4. **§3.1：volatile 字段方案降级为二选一**（不算必修，主代理裁决）：保留 04 方案（字段 + 8 环节链路 + squash 规则 2 + custom 分支透传），或改用索引方案（`CompileMessagesResult.volatileFrom` 经 stream options 传入适配器，squash 不加规则 2，现有 25 个预设请求体逐字节不变）。若选字段方案，04 的 squash 规则 2 与 custom 透传**不可再省**；若选索引方案，04 §4.1/§4.2 规则 2 删除。
5. **§3.3：`timezone` 配置保留，校验器与 `formatToParts` 手工解析缩水**。real 模式实现允许直接用进程本地时区 + 可选 `timeZone` 覆盖一行；`resolveMemoryClock` 的 warning 通道可保留（便宜），`hour===24` 归一化等边界保留（便宜且必要）。此项是"缩水"不是"砍"——ludens 显式配 `Asia/Shanghai` 的需求必须满足。

无 veto。设计整体与我的 §1 盲判方向一致（快照缓存、五边界、volatile 断点、set_time 裁剪、steer 钩子），分歧集中在**改型成本**（3.1/3.2/3.4）与**prompt 面污染**（3.5/3.6）。上述必修项全部有更简替代且不损失任何 PE 效果。

### D. 唯一剩余项 R3-R2-1：heading/ending 静态宏补齐规则矛盾

**定位：02-宏与静态纪元.md:187–197，尤其 :190、:197。**
