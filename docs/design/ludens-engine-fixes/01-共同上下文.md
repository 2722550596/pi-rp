## §1 已拍板决策

明月拍板的见 `00-需求原话.md` §4（D1–D9）。下面是主代理补充的技术决策，设计代理可以申报异议，但不得自行推翻。

| # | 决策 | 理由 |
|---|---|---|
| T1 | 静态宏的"一段时期"（下称**静态纪元**）在以下事件后结束，下一次请求前重新计算：会话运行时就绪（新建、恢复、`/reload`）、切换活动预设、活动工具集变化、模型变化、压缩完成（手动和自动都算）。改变这些状态的任何代码路径都算，不限于公开的 setter（2026-10-16 收口补：`cycleModel` 系列、`_refreshCurrentModelFromRegistry`、`reloadPresets` 和 `_activePreset` 的各处直接赋值都要覆盖，见 R1 V-2、R2 F2/F14） | 这些事件发生时，静态宏描述的东西（预设、工具、模型、记忆快照）可能已经变了；而且这些事件本来就会让缓存前缀失效，在这时刷新不增加额外的缓存损失 |
| T2 | 宏渲染一律同步：静态宏和动态宏都用同步 `render`，不引入异步宏（2026-10-16 收口改，原"静态宏允许异步渲染"作废） | 三个记忆 slot 只是标了 `async`，渲染函数体里没有 await（`packages/memory/src/slots.ts:62-137`），读 store 是同步 API（`store.ts:1740`），记忆宏同步读库就行；异步宏机制服务的输入不存在（R3 3.2，02、03 确认） |
| T3 | 记忆宏的内容和对应 slot 用同一个渲染函数，但快照形式不同：第一行是快照时间，正文全部用绝对日期，不写"昨天"这类相对时间 | 静态内容会在一个纪元里保留很久，相对时间过几个小时就错了 |
| T4 | B 修复用编译结果上的一个下标（`volatileFrom`）传递 history 边界，不给消息加字段（2026-10-16 收口改，取代"逐条消息标记"） | 过滤和合并都发生在编译器内部，编译器知道边界在哪，下游只需要一个数；字段方案要在 7 个中间环节论证不丢、还要改 custom 分支和合并规则（R3 3.1）；04 确认两种方案缓存覆盖等效 |
| T5 | A 修复只改合并逻辑本身：保留非文本内容；纯文本合并的输出必须和现在逐字节相同；不新增"不跨 history 边界合并"的规则（2026-10-16 收口改） | 现有预设的请求体不应因为这次修复而变化：加"不跨边界合并"会让 25 个用 `{{lastUserMessage}}` 的预设多出一条 user 消息（R1 V-4），Bedrock 还会拒绝连续 user 消息 |
| T6 | 插话召回复用记忆模块现有的召回、去重和 `rp-memories` 注入逻辑，不另写一套 | 召回结果的形状和去重状态必须与 `prompt()` 路径一致 |
| T7 | 实现必须收敛到已有机制：静态纪元的触发点要和 `runtimeContextSlots`（"只渲染一次、压缩后刷新"的现成先例）对齐；能复用就复用它的生命周期，不能复用要在设计文档里写明理由 | 避免出现第二套"何时刷新"的机制 |
| T8 | 会话主循环的模型请求支持 `cacheRetention` 设置（§2.10）：settings 新增可选顶层字段，由 SDK 的 streamFn 每次请求时读取；请求自己带了 `cacheRetention` 时以请求为准；不设置时行为不变（2026-10-16 按 ludens 02 C-1 申报补入） | ludens 的 D18 要求 `cacheRetention` 做成配置项，供以后换 Anthropic / OpenAI 时用（`~/projects/ludens/docs/design/00-需求原话.md` D18），而 SDK 现在没有入口（`sdk.ts:464-498` 不设这个字段）；streamFn 本来就在每次请求时读 settings 里的超时和重试（`:465-466`），沿用同一机制，不另开 SDK 选项 |

## §2 冻结契约（共享形状：各设计文档 MUST 原样引用，MUST NOT 改名或改形）

### §2.1 记忆时钟设置 `settings.memory.clock`

```jsonc
"memory": {
  "clock": {
    "mode": "world",          // "world" | "real"。缺省 "world"，即现有行为
    "timezone": "Asia/Shanghai" // 可选，IANA 时区名，只在 "real" 模式下使用；缺省取进程本地时区
  }
}
```

- `MemorySettings`（`packages/memory/src/config.ts:24`）新增可选字段 `clock?: { mode?: "world" | "real"; timezone?: string }`。
- 解析容错：非法 `mode` 按 `"world"` 处理；非法 `timezone`（构造 `Intl.DateTimeFormat` 时抛错）按进程本地时区处理；都用 `process.stderr.write` 记一条带 `[memory]` 前缀的 warn（与 `packages/memory/src/schema.ts:235` 的迁移提示同一通道），不另设 warning 返回通道，不 throw（2026-10-16 收口，按 R3 3.3 缩减；第二轮按 R1 M-1 写定通道）。
- **`world` 模式**：与修复前逐行为一致（PE2）。包括钟未设置时的回退、UTC 分天等现有行为，本次都不改。
- **`real` 模式**：
  1. 参照时间（"现在"）取 `new Date()`，按 `timezone` 呈现；
  2. 新写入的节点时间、raw_log 时间、audit_log 的 `world_ts` 都写真实时间，格式为带时区偏移的 ISO 8601，例如 `2026-10-16T05:31:07+08:00`；不再出现因"钟未设置"而写 NULL 的情况。模型显式清除时间（`revise` 传 `time: ""`，`tools.ts:860`）仍写 NULL：这是显式动作，不是回退（2026-10-16 按 03 申报补入）；
  3. 不注册 `set_time` 工具；`memory_kv["world_time"]` 不读也不写；
  4. awaken slot 和 `MEM://wakeup` 视图不打印"当前世界时间"那一行；`/memories` 概览里的世界时间行改为真实时钟（同一个"现在"在不同渲染面上不能互相矛盾，2026-10-16 按 03 申报补入）；
  5. 相对时间标注（今天、昨天……）和 recency 分档，按 `timezone` 的本地日期分天。
- 时钟挂在 store 上（autoretain、tidy、seed、import 都经 `store.put` 写入，不传时间）：store 新增公开方法 `setClock`、`getClock`、`nowStamp`、`referenceNow`（03 §4.3）。world 模式下 `nowStamp()` 等于 `getWorldTime()`，`referenceNow()` 等于 `getWorldTime() ?? new Date().toISOString()`，与现有表达式逐字节相同。
- 记忆 web 服务（2026-10-16 第二轮，C19）：它由 `/memories` 以独立进程启动（`packages/coding-agent/src/extensions/memories/web-launcher.ts:103-104`），按 TEMP 阈值的同一来源（`packages/memory/src/web/cli.ts:82-99`）读 `memory.clock`，对本进程打开的每个 store 调 `setClock`。`real` 模式下第 3 条同样约束 web：不读 `memory_kv["world_time"]`，对外给出的"当前时间"用真实时钟；POST 世界时间不写钟。宿主的时钟配置不在这两个 settings 文件里时（自定义 agentDir，如 ludens 的 `data/brain/agent/`；或只在内存 settings 里），web 进程读不到，按 settings 文件取值。

### §2.3 静态纪元语义

- 一个静态纪元内，编译出的预设内容里所有静态宏的展开结果，在每次请求中逐字节相同。
- 每个静态宏调用（宏名加参数串，即 `{{name:params}}` 的完整内容）在一个纪元里只渲染一次：纪元内第一次用到时渲染，结果存进快照，此后本纪元一直用快照值。通常第一次用到就是边界之后的第一次请求；纪元中途才注册的宏，在注册后第一次用到时渲染，同样只渲染一次。用到时还没注册的宏，按现有的未知宏规则处理，不进快照。
- 快照在宏展开处同步补齐：快照里有值就用，没有就当场渲染并存入（2026-10-16 收口改：宏一律同步后，不再需要"先 await 补齐"的步骤）。每次请求的编译路径（`getPresetInjectMessages` → `compileMessages`）和 `_rebuildSystemPrompt` 的 static 模式用同一份快照，后者的细节由 02 定义。
- 纪元边界见 §1 T1。02 可以增加边界（必须写理由），不能减少。
- 动态宏（包括改成动态后的 `lastUserMessage`、`date`、`time`）每次请求照常展开。
- slot（包括记忆的三个 async slot）每次请求照常渲染，行为不变。
- 快照只在内存里，不落盘；进程重启算新纪元。
- 纪元快照 MUST 作用在每次请求的编译路径上（`getPresetInjectMessages` → `compileMessages`），不能只靠 `_rebuildSystemPrompt`：用了记忆 slot 的预设在后者直接返回 `""`（见 §3），而 ludens 的大脑预设正是这种。
- 静态宏出现在 history 之前还是之后都按同一语义处理。
- 参数里含 `{{` 的静态宏调用（如 `{{memory.recent:rawCount={{getvar::x}}}}`）不支持：不进快照，原样保留，并记 warn 诊断（2026-10-16 裁决；各项目的预设目录里没有这种写法）。
- 内置宏的静态标记，改完后是：
  - 静态：`cwd`、`tools`、`selectedTools`、`activeModel`，以及 §2.4 的三个记忆宏；
  - 动态：`date`、`time`、`lastUserMessage`、`setvar`、`addvar`、`getvar`、`trim`、`user`。

### §2.6 history 边界与 Anthropic 断点（B）（2026-10-16 收口改：编译结果带下标，取代消息字段）

- `CompileMessagesResult`（`prompt-preset/types.ts:420-424`）新增可选字段：

```ts
/**
 * Index of the first compiled message that carries content placed after chat
 * history (compiled fresh for every request). Providers with explicit cache
 * breakpoints anchor the conversation breakpoint before this message.
 * Undefined when nothing follows history.
 */
volatileFrom?: number;
```

- 在合并（§2.7）之后计算。history 末尾那条 user 消息和尾块合并成一条时，`volatileFrom` 指向合并后的这一条。
- pi-ai 的消息类型不加字段；`convertToLlm` 的 custom 分支不改。
- 下标随这次请求传到适配器：SDK 的 `transformContext`（`sdk.ts:530-544`）拿到编译结果，经 stream options 交给适配器（`ProviderStreamOptions` 是 `StreamOptions & Record<string, unknown>`，`packages/ai/src/types.ts:230`）。选项名和传递路径由 04 定。
- 编译结果到适配器之间，凡是会改变消息条数或顺序的环节（`ExtensionRunner.emitContext`（`extensions/runner.ts:1296`）、`convertToLlm`（`core/messages.ts:233`）、SDK 图片过滤（`sdk.ts:391-397`）、`splitSystemMessages`、`transformMessages` 等），04 逐个给出下标怎么换算并带 file:line。换算建立不起来时（例如扩展的 context 处理器换掉了整个数组），按没有下标处理，即现状断点规则。
- Anthropic 适配器（`packages/ai/src/api/anthropic-messages.ts:1274-1296`）的消息断点规则改为：
  - 有下标时，断点打在下标之前最后一条消息的最后一个可缓存块上（包括 tool_result 块）；
  - 没有下标时，行为与现在完全相同；
  - 下标之前没有可缓存的块时，不打消息断点。
- 断点总数不变（OAuth 模式下已经用满 4 个：system 2 个、tools 1 个、消息 1 个），只移动消息断点的位置。
- Bedrock 适配器同一规则：system 后面打一个 `cachePoint`（`bedrock-converse-stream.ts:793-795`），消息部分现在是"最后一条消息是 user 时"往它末尾加 `cachePoint`（`:995-1001`）。其他自己打断点的地方（`openai-completions.ts` 的 Anthropic 兼容格式）也按同一规则修。
- 按前缀自动缓存的 provider（OpenAI、Gemini 等）忽略下标。
- 现有预设的请求体，除消息断点的位置外逐字节不变：不新增消息，也不拆分消息（T5）。

### §2.8 插话召回

- 由 `steer()` 插入的用户消息进入上下文时，触发和 `prompt()` 路径相同的记忆自动召回。进入上下文有两条路：agent loop 在运行中注入（轮询在 `agent-loop.ts:284/311/386`，注入块在 `:316-324`）；或者一轮结束后，`continue()` 把插话队列当作新一轮的输入（`agent.ts:409-413`，由 `agent-session.ts:2900-2917` 的自动续跑触发）。两条都要覆盖（2026-10-16 按 05 申报补入，行号按 05 复核更正）。
- 召回结果是同一个 `rp-memories` 自定义消息（自定义类型策略：进上下文、以 user 角色发给模型、压缩时排除，`module.ts:795-798`），放在这批插话之后、下一次 LLM 调用之前；与 `prompt()` 路径共用去重状态。
- `steeringMode: "all"` 一次注入多条插话时，把这批插话的文本合起来做一次召回。
- 只有用户插话触发召回；经 `sendCustomMessage` 等途径进入 steer 队列的自定义消息不触发。
- 召回失败不能阻止插话注入：插话路径记 warning，照常继续。`prompt()` 路径现在是静默吞掉错误（`module.ts:590-596`），保持不变。
- 召回是异步的，下一次 LLM 调用要等它完成。
