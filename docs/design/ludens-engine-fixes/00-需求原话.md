# 需求原话：ludens 引出的 pi-rp 引擎修复

> 本文是本次需求的第一手档案。§1 是明月原话，逐字照录；§2 起是注释和清单，**不是原文**，与原文严格分开。设计、评审、实现代理 MUST 以 §1 为对照基准，并在自己的设计文档里单列「需求对照」一节。
>
> 背景（注释）：明月新建项目 ludens（`~/projects/ludens`），是一个角色陪伴聊天产品。大脑层是嵌在 Node 服务端里的 pi-rp AgentSession，用户看不到；输出层是一次单独的 LLM 调用。ludens 自己的需求档案在 `~/projects/ludens/docs/design/00-需求原话.md`。讨论 ludens 时暴露出几处 pi-rp 的通用问题，本文只收这部分。

## 1. 明月原话（2026-10-15 会话，逐字）

### 消息 1（记忆时间戳：双时钟）

> 关于你刚才提的那些问题，比较大的一个问题应该是记忆的时间戳，那个确实是个问题
>
> 那玩意设计出来的时候，其实应该有两种功能：一种是用世界时间，另一种模式是同步真实时间。但是派尔皮那边当时可能偷工减料了，没有做真实时间那种
>
> 所以这个你到时候看着办吧
> 1. 要么先修pi rp那边，让派子代理去搞，应该也很容易
> 2. 要么像 Prime Agent 这边一样，在服务端主动帮它同步一下，其实都可以

（注释："派尔皮"是语音转写，指 pi-rp。助手选了方案 1，明月未反对。）

### 消息 2（记忆 slot 与缓存：给内置记忆 slot 加静态宏形式）

> 至于你说的这个 Slot 对缓存命中不友好，这个确实是问题。但这东西其实也挺难弄的。有时候有些场景又需要它能够刷新；如果不刷新的话，就会比较麻烦。不过预设中除了 slot 本来也有 macro 这个机制。
>
> 所以我觉得，也许 Slot 那边你可以先不管静态动态，保持动态，但是你可以看一下能不能让这几个内置记忆 slot 有宏的形式，并且是静态宏，这样应该能解决你的顾虑。

### 消息 3（双时间的出处；静态宏的正确含义）

> pi-memory的始祖是 @../nocturne_memory/ 这里有双时间设计  对于静态宏，正确的表述应该就是保持静态，那个lastUserMessage本来就应该是非静态的，字面上就是动态的啊，不知道文档发什么神经乱写

### 消息 4（时间宏改动态，但要放在 history 之后）

> 这个时间可以改成动态。只是说这种东西如果改成动态，你就把它放在预设 Items 数组的最下方，也就是在 History 的后面。因为如果放在上面的话，它每回合都变，那缓存命中要见鬼了

（注释："这个时间"指 `{{date}}` / `{{time}}` 两个宏。）

### 消息 5（ask 答复：丢图与 Anthropic 断点）

> A+B 都加

（注释，非原文。问题：「丢图（A）和 Anthropic 断点（B）这两项，要加进 pi-rp 的待改清单吗？都等你说动手后再派子代理。」选项：A+B 都加 / 只加 A / 都先不加。
- A：预设编译把相邻同角色消息压成一段纯文本，图片会丢（`compiler.ts:439-453`）。用 bun 跑真实编译器实测过：用户消息"文字 + 图片"和 history 后面的 user 块合并后，图片没了。
- B：Anthropic 适配器把消息部分的缓存断点打在"最后一条 user 消息的最后一块"（`anthropic-messages.ts:1274-1296`）。history 后面只要有块，断点就落在这个块上，聊天记录永远读不到缓存。）

### 消息 6（system 角色：尾部块用 user，系统性质用 XML 标签表达）

> system 消息的拼装很正常。正常来说，哪有那么多 system 消息？哪有那么多 system role？没有那么多这样的，一般用 user role 就够了
>
> 如果你想表明它属于系统提示，就用 XML 标签包着，比如<system-reminder>，没必要在末尾还用一个 system role，没有必要这样
>
> 那个设计是因为，派原本没有预设这一套机制。它当时很简单，就像所有其他的 agent handler 一样，用的都是 system prompt，只有这么一个东西。再加上有些 provider 天生不支持 system role 出现在一些奇奇怪怪的地方，比如 anthropic provider，所以它就搞了这么一套转换
>
> 这也是为什么现在这个预设如果要启用，必须先显式地把 system prompt 设成空，要不然根本用不了。其实也是为了兼容之前那种形式

（注释：这条消息明月连发了两次，内容完全相同，只收一次。）

### 消息 7（chaoxi 预设不在本次范围）

> chaoxi那个算是特殊情况，它本来就是不太重视缓存命中的，那些world info  depth已经每次都重新刷新了。而且理论上确实应该把尾巴改成user role会好一些。它本来就是酒馆风格的一个预设，这种预设在缓存命中优化上基本算是教科书般的反例了

### 消息 8（顺序安排）

> 这些你也用ask工具问完吧，之后没什么问题可以写文档了，然后我们先修pi-rp的问题

### 消息 9（ask 答复：插话的记忆召回）

> pi-rp 补上

（注释，非原文。问题：「大脑忙的时候，用 steer 插进来的消息不会触发自动记忆召回。怎么补？」选项：pi-rp 补上（steer 插进用户消息时也自动召回一次，其他项目也能用上）/ ludens 宿主补 / 只靠提示词。）

## 2. 效果清单（注释，非原文）

| # | 效果 | 验收口径 | 依据 |
|---|---|---|---|
| PE1 | 记忆有两种时钟：世界时间（现有行为）和真实时间。真实时间模式下，参照时间是本地当前时间，节点和 raw_log 写入带时区的真实时间，不提供"设置世界时间"的能力，不打印"当前世界时间"，按本地日期分天 | 设成真实时间后，新写入的节点和 raw_log 都有带时区偏移的真实时间；没有 `set_time` 工具；相对时间（"昨天"）按本地日期算 | 消息 1、3 |
| PE2 | 默认仍是世界时间，现有项目行为不变 | 不加配置的项目，记忆行为和测试结果与修复前一致 | 消息 1 |
| PE3 | 静态宏真正静态：同一段时期内只算一次，之后每次请求都用同一份结果，不再每轮重算 | 一段时期内，相邻两次请求里静态宏展开出的文字逐字节相同 | 消息 3 |
| PE4 | 静态宏在需要的时候刷新：会话开始、换预设、工具集变化、模型变化、压缩（换气）之后 | 上述任一事件之后的下一次请求，静态宏按新状态重新计算 | 消息 2（"有时候有些场景又需要它能够刷新"） |
| PE5 | `{{lastUserMessage}}`、`{{date}}`、`{{time}}` 是动态宏，每次请求都按当时的值展开 | 改完后这三个宏每轮都是新值；依赖 `lastUserMessage` 的 25 个现有预设行为不变 | 消息 3、4 |
| PE6 | 三个内置记忆 slot 各有一个对应的静态宏形式；slot 本身保持动态 | 预设里用 `{{memory.awaken}}` 等宏时，内容在一段时期内固定、换气后刷新；用 slot 时行为和现在一样 | 消息 2 |
| PE7 | 文档写对：静态就是静态；每轮变化的内容放在 history 之后、role 用 user，需要系统性质时用 XML 标签包裹 | `prompt-presets.md` 的宏表、摆放规则、role 说明与代码行为一致 | 消息 3、4、6 |
| PE8 | 预设编译不再丢图：相邻同角色消息合并时，图片等非文本内容保留 | "文字 + 图片"的用户消息后面跟着 user 块时，发给模型的请求里图片还在 | 消息 5（A） |
| PE9 | Anthropic 上，history 后面有块时，聊天记录部分仍能命中缓存 | 连续两轮请求，第二轮的 cacheRead 覆盖到上一轮写下的消息断点。history 末尾那条 user 消息和尾块合并成一条时，断点落在它前一条消息上，即只少缓存最后一条用户消息（2026-10-16 收口细化，见 01 T4、§2.6） | 消息 5（B） |
| PE10 | 大脑忙时用 steer 插进来的用户消息，也会像 `prompt()` 一样触发记忆自动召回 | 插话提到一个记忆里的话题，召回结果在下一次 LLM 调用前进入上下文 | 消息 9 |
| PE11 | system 角色提升（`splitSystemMessages`）保持现状，不改 | 兼容旧写法；本次不动这段逻辑 | 消息 6 |
| PE12 | chaoxi 等酒馆风格预设不在本次修改范围 | 本次不改 STpreset / pi-sillytavern-bridge 里的预设 | 消息 7 |
