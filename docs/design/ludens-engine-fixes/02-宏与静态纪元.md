## 0. 结论

1. 宏渲染一律同步（01 T2）。`MacroDefinition` 保持现有 interface，不改联合类型，不加 `async` 字段（C1）。
2. 静态宏调用（`{{name}}` 或 `{{name:params}}`）在一个纪元里只渲染一次，结果存进快照（01 §2.3）。同一纪元内每次请求的静态宏输出逐字节相同。
3. 快照由 `expandMacros` 的静态分支就地读写：命中就用，未命中只渲染一次并存入（C18）。不增加预扫描或第二次展开。`date`、`time`、`lastUserMessage` 改为动态，每次请求现算。
4. 纪元判定用键比对（C6，§3.3）：三个编译入口在展开前检查纪元键，变化就开新纪元。
5. `_rebuildSystemPrompt` 的 static 模式与请求编译路径共用同一份快照；static 模式不调用任何异步渲染（本来就是同步的），`{{memory.*}}` 在其中按未知宏规则留占位符（§5）。
6. 落地第一步是 PE5 单独成步（§8，C11）。

## 2. 宏定义与快照形状

### 2.1 现有宏定义原样保留（C1，01 §2.2）

```ts

	runtime: PromptRuntime;
	variables: Record<string, string>;
	/** Optional parameter string from {{name:params}} syntax. */
	params?: string;

export type MacroRenderer = (context: MacroRenderContext) => string;

export interface MacroDefinition {
	name: string;
	description: string;
	render: MacroRenderer;
```

### 2.2 快照类型（02 新增形状，非契约冻结）

```ts
/** Per-epoch cache of rendered static macro calls. NEW (02). */
export interface MacroSnapshotTable {
	readonly epochId: number;
	readonly entries: Map<string, string>;

```

- 字段（NEW，挂 `PromptRuntime`，`types.ts:354` 起）：`macroSnapshot?: MacroSnapshotTable`。

### 2.4 未知宏（现有规则，本文不改）

1. 注册表里有该宏 → 同步调用 `macro.render`（`:262`）。
2. 没有 → 若 `name in variables`，取变量值。
3. 都没有 → 按 `unresolvedMacroPolicy`（`keep`/`warn`/`error`）保留占位符或记诊断。

未注册的宏不进快照；之后注册的宏，在下一次用到时按第 1 条渲染（§4.4）。

## 3. 快照存放与纪元（点 1、点 2）

### 3.1 存放位置

- 有 scope 时快照存 `AgentSessionScope`（NEW 字段 `macroSnapshot`）；无 scope 时存 AgentSession 的 NEW 字段 `_localMacroSnapshot: MacroSnapshotTable`。SDK 没有收到 `scope`/`runtimeContextSlots` 时不创建 scope（`sdk.ts:446–450`），无 scope 也必须缓存，不能退回每轮现算。
- scope 上 NEW 方法 `invalidateMacroEpoch(): void` 仿照 `invalidateRuntimeContext()`（`session-scope.ts:281`）递增 epochId、清表；`dispose()`（`:417`）同点清空。AgentSession 的 NEW 方法 `_getMacroSnapshot(): MacroSnapshotTable` 统一返回 scope 表或本地表。
- 三个编译入口统一传 `_getMacroSnapshot()`：`getPresetInjectMessages`（`agent-session.ts:2829`）、`_rebuildSystemPrompt`（`:2395`）、`compileSystemPrompt`（`:2854`）。
- `_agentSessionScope` 仅在构造赋值（`:921`）；`_ownsAgentSessionScope` 只控制 dispose（`:926,1564`），不控制纪元判定。上一键存 AgentSession，不在 scope 上共享。

### 3.2 纪元边界清单（C6 MUST 覆盖项 → 键组件）

C6 的状态变化由纪元键捕捉；会话就绪另由 runtime 成功提交代数捕捉（同一 scope 原地 reload 也会变化）。

| `cycleModel` 直接写 `agent.state.model` | `agent-session.ts:4052`、`:4080` | 模型 provider+id |
| `setModel` 写 `agent.state.model` | `:4000` | 模型 provider+id |

### 3.3 纪元键比对（C6 推荐方案，本文采纳）

NEW 字段均存 **AgentSession 实例**：`_macroRuntimeGeneration: number = 0`、`_macroCompactionId: string = ""`、`_lastMacroEpochKey`（类型见下）。新实例不继承旧实例的键；共用 scope 也不共用“上一次的键”。

纪元键（NEW 私有结构，不拼成字符串）：`{ runtimeGeneration: number; preset: PromptPreset; tools: string; model: string; compactionId: string }`。NEW 方法 `_macroEpochKey()` 返回该结构；逐字段比较，预设用对象引用比较，工具名排序后序列化为字符串，模型用 provider+id，避免对象引用转字符串丢失身份。

`_buildRuntime`（`agent-session.ts:5331–5345`）在 `update?.commit()`（`:5339`）之后、与现有 `_staticPromptCache = undefined`（`:5341`）同一成功分支递增 `_macroRuntimeGeneration`；无 `update` 的首次构建也递增。失败 rollback 不递增。选择代数而非只比较 scope：reload 在同一 scope 上 `beginUpdate/commit`，scope 和 readonly registry 的身份均不变（`session-scope.ts:244,354–357`），代数明确表达一次成功就绪。

压缩 id 不在请求里扫描：把手动、自动两处 `sessionManager.appendCompaction(...)`（`agent-session.ts:4322,4702`）的返回值直接保存到 `_macroCompactionId`。`appendCompaction` 返回 `string` id（`session-manager.ts:1320–1328`）；`getEntries()` 会调用 `filter` 复制数组（`:1550–1551`），因此纪元键不调用它。恢复时无需查找历史压缩 id：新 runtime 代数已经保证新纪元，字段初始空串即可，后续每次新压缩换 id。每次请求只读上述字段，不复制或扫描会话数组。

NEW 方法 `_ensureMacroEpoch(): void`：与实例上一键逐字段比较，变化则使 `_getMacroSnapshot()` 开新纪元并存新键。无 scope 的本地表同样清空并递增 epochId。调用点三处：`getPresetInjectMessages`（`:2829`）构造 runtime 前、`_rebuildSystemPrompt`（`:2395`）缓存判断前、`compileSystemPrompt`（`:2854`）构造 runtime 前。

键对比只读实例字段和当前预设、工具、模型；runtime 提交与压缩落盘两处更新对应字段。不是通过 scope 身份推断 reload。

### 3.4 `_staticPromptCache` 与纪元（点 ④）

- 缓存键加纪元号：`_rebuildSystemPrompt` 命中判断（`:2472` 起）新增 `cache.macroEpoch === this._getMacroSnapshot().epochId`。失效后 epochId 变，旧缓存自然不命中。
- 现状缺口：压缩不清 `_staticPromptCache`（`:4340`、`:4721` 处无清空）。键方案下不需要显式清：压缩条目 id 变 → epochId 变 → 缓存不命中。

## 4. 每次请求的编译路径（点 3）

### 4.1 在 `expandMacros` 静态分支就地缓存（C18）

唯一改动入口是 `macro-engine.ts:253–262`：`:255` 判断静态，`:262` 原为直接渲染。条件同时满足时查写快照：`macro.static === true`、`shouldExpand` 为真、`runtime.macroSnapshot` 存在、调用参数里没有嵌套 `{{`。

- 键沿用 01 §2.3：宏名加参数串，按 §2.2 的完整内层调用文本区分调用；无参数与空参数按原语法保留区别。
- 用 `entries.has(key)` 判断命中（空字符串也是有效值）；命中直接拼接缓存值。未命中同步调用一次 `macro.render({ runtime, variables, params })`，写入同一快照，再拼接结果。
- §2.2 的快照形状是 02 新增而非冻结契约；`entries` 明确用 `Map<string, string>`，表引用只读、内容可写，此分支直接 `entries.set(key, value)`，不新增写入接口或模块、不复制表。
- 参数含嵌套宏：在递归展开参数前识别静态调用，原样保留整段、记 warn、不渲染、不进快照（01 §2.3）。
- 动态宏照常渲染；`mode: "dynamic"` 中不展开的静态宏仍保留占位符；`skipMacroExpansion` 路径不进入宏引擎，保持不变。
- `compiler.ts` 的 `renderItemTextSync/Async`、`finalizeItemText` 和 `slot-renderers.ts:461` 都不用改。没有预补齐函数、没有未命中后不写缓存的回退。

### 4.2 覆盖范围：凡经过 `expandMacros` 的文本都覆盖

1. heading、raw（block 文本或 slot 结果）、ending：`compiler.ts:518–529` 的 `finalizeItemText` 调用。
2. slot 选项字符串：`slot-renderers.ts:461` 的 `expandSlotOptions` 调用。
3. static 系统提示：`agent-session.ts:2504` 的 `expandMacros(..., { mode: "static" })` 调用。
4. message content：`macro-engine.ts:309,311` 的 `expandContentMacros` 转调。

缓存逻辑与现有解析在同一次遍历执行，不先替换 raw 再展开，保留有副作用宏的原顺序。

其余核对结论：
- 宏输出不回头展开（`macro-engine.ts:262` 直接拼接），无需二次扫描。
- `//…` 注释跳过（`processText` 的 `startsWith("//")` 分支）。
- **参数含 `{{` 的静态宏调用**（如 `{{memory.recent:rawCount={{getvar::x}}}}`）：不支持，不进快照，原样保留，记 warn 诊断（01 §2.3 冻结；主代理已核查各项目预设无此写法）。

### 4.3 无异步路由

C1 删除异步宏路由。`compileMessages`（`compiler.ts:94`）仅按 async slot/historyOps 选择路径（`:385,389`）；两条编译路径最终都进入 `expandMacros`，由其静态分支渲染并写入快照（§4.1），不需要改变编译路由。

### 4.4 晚注册的宏

- `registerMacro`（`registry-scope.ts:81–84`）注册不触发纪元失效。
- 注册后第一次用到时由 `expandMacros` 的静态分支渲染并写入快照（一次，01 §2.3）。
- 注册前用到的是未知宏（§2.4），不进快照。

## 5. `_rebuildSystemPrompt` static 模式（点 4、点 5）

### 5.1 与请求路径共用同一份快照（01 §2.3）

- `_rebuildSystemPrompt` 的 `staticRuntime`（`:2490–2499`）新增 `macroSnapshot: this._getMacroSnapshot()`；构造前 `_ensureMacroEpoch()`，与请求、`/prompt` 路径共享当前表。
- `expandMacros(..., { mode: "static" })`（`:2504`）：静态宏已在编译期展开（`finalizeItemText` 的 `expand` 默认 `mode: "all"`，`macro-engine.ts:215`），此调用实际无静态宏可匹配，保留原样。[推断：现行为即如此]
- `{{memory.*}}` 在 static 模式的结果：原稿 `staticRuntime.promptRegistry` 为空，记忆宏经 scope 注册、不在全局 `customMacros`，走未知宏规则留占位符（§2.4）。实现期偏差 6 让无 scope 会话把记忆宏注册到进程级 `customMacros`；registry 为空的 static 路径会在有 scope 的会话里查到别的会话的宏，并写进本会话共用的快照，请求路径随后复用。因此实现时 `staticRuntime` 带上 `this._agentSessionScope?.promptRegistry`，与请求路径查同一个注册表（偏差 7，收口裁决 §7）。记忆宏发布前的 rebuild 仍留占位符。该输出只喂给扩展可见的 `systemPrompt`（§5.2），不进 LLM 默认载荷。static 路径的 diagnostics 无人消费，保持静默。
- 同步性：static 模式全程同步（`compileMessagesSync`，`compiler.ts:109`），宏全同步后不存在"异步宏被同步调用"的问题（C1 删除该论证与门检查）。

- `_baseSystemPrompt` 的用途：
  1. `before_agent_start` 事件参数（`:3074`）；
  2. 下一轮 systemPrompt（`:1150`）：`_systemPromptOverride ?? (hasCustomPrompt ? _baseSystemPrompt : "")`。预设模式无自定义 prompt，仅当扩展在 `before_agent_start` 返回 `systemPrompt`（`:3081–3085` 写 `_systemPromptOverride`）时，这段文字才进 LLM。
- 结论：预设启用时 static 路径输出**默认不进 LLM 请求**；LLM 的预设内容走 `getPresetInjectMessages`（`:2829`，§4）。
- `/prompt`：`compileSystemPrompt`（`agent-session.ts:2854–2872`）await 编译器同名函数；`compiler.ts:25–39` await `compileMessages` 再 `deriveSystemPrompt`。该入口不是 static 模式；新增 `_ensureMacroEpoch()` 与同一快照参数，保证显示和请求编译一致。

### 5.3 date/time/lastUserMessage 动态后各路径的值（点 ⑤）

前提（本轮复核）：`{{date}}` 等在 `compileMessagesSync` 里被 `expandMacros`（默认 `mode: "all"`）展开，取值 `staticRuntime.now`（rebuild 时刻的 `new Date()`，`:2492`）；`:2504` 的 `mode: "static"` 不产生占位符。改动态后同理：static 模式里它们是 **rebuild 时刻的值**，不是占位符。

## 6. T7：与 `runtimeContextSlots` 对照

| 项 | `runtimeContextSlots`（`session-scope.ts`） | 静态宏快照（本文） | 对齐 |
|---|---|---|---|
| 存放 | `runtimeContextContents`、`runtimeSlots` | `macroSnapshot`（NEW） | 对齐 |
| 失效方法 | `invalidateRuntimeContext()`（`:281`） | `invalidateMacroEpoch()`（NEW，同形） | 对齐 |
| 生命周期 | `dispose()`（`:417`）清空 | 同点清空 | 对齐 |
| 会话就绪 | 随 scope 的生命周期；reload 为原地更新 | runtime 成功提交代数进入纪元键（§3.3），无 scope 用实例本地表 | 生命周期对齐；reload 不依赖 scope 身份 |
| 压缩刷新 | 钩子 `session_compact` 带回 `replaceContextSlots`，经 `replaceRuntimeContextSlots`（`agent-session.ts:4353–4355`、`:4729–4731`）写入预渲染内容 | 压缩条目 id 进纪元键，失效后由宏渲染器重算 | 时机对齐，方式不同 |

不对齐的理由（供评审）：
- 压缩刷新方式：runtime slot 的新内容只能由压缩摘要产生（经钩子带回）；宏内容由宏渲染器自己读库，失效后重算即可，不需要 payload。
- 额外状态：静态宏依赖预设/工具/模型（`cwd`、`tools`、`activeModel`），runtime slot 没有这类依赖，所以纪元键比 `invalidateRuntimeContext` 的触发面宽。这不是第二套"何时刷新"机制：失效函数、存放位置、生命周期都收敛在同一 scope 上（T7 的要求），只是触发判定从事件挂载改为键比对（C6 推荐方案）。

### 7.3 静态与动态（`:432` 段替换）

> **Static vs Dynamic**: A `static` macro produces one value per static epoch. Within an epoch, every request sees the same text for it. The epoch ends when the session is (re)started, the active preset changes, the active tool set changes, the model changes, or a compaction completes. A dynamic macro (no `static: true`) is rendered on every request, for example `{{roll:1d100}}` or `{{date}}`.

### 7.4 放置与角色（新增段；C8 核对：显式写 `role: user`）

> **Placement**: Put static content (such as static memory macros) anywhere in the item list; it does not change between turns. Put content that changes every turn (such as `{{date}}`, `{{time}}`, `{{lastUserMessage}}`) after the `history` item. Items after `history` MUST explicitly set `"role": "user"` (or `"assistant"` where appropriate): the default is `system` (`compiler.ts:589`), and every `system` message is pulled back to the top of the request by `splitSystemMessages` (`packages/ai/src/api/transform-messages.ts:19`), which defeats the placement. To mark content as system-type, wrap it in an XML tag such as `<system-reminder>` instead of using the `system` role.

（C8 裁决：不改 role 默认值；规则写明显式写。D5 的提升逻辑不变由此段覆盖。）

### 7.5 history 之后的缓存行为（新增段；内容来自 04，措辞 02 定稿）

> **Items after history**: The compiler records the first message containing content after history as the `volatileFrom` boundary. Cache-aware adapters anchor the conversation breakpoint on the last cacheable block before that boundary. Normal text merging is unchanged: if a tail item merges into the last history message, the boundary points to that merged message and the cached prefix ends before it. Without a boundary, existing provider behavior is unchanged; if no cacheable block precedes it, no conversation breakpoint is added.

（已复核 04 §4.1–4.3：使用编译结果下标，不给消息加字段，不禁止纯文本跨边界合并，消息布局保持不变。）

### 7.6 静态记忆宏（新增段；来自 03 附录 A，措辞按本文统一）

> **Static memory macros** (`memory.awaken`, `memory.recent`, `memory.index`)
>
> These three macros render the same content as the matching memory slots, but they are static: each renders once per static epoch and every request sees the same text. The epoch ends at the events listed under "Static vs Dynamic".
>
> The first line is `> 快照时间: <时间>（此后新写入的记忆不在这份快照里，需要时用 recall 或 retrieve 查）`; the body uses absolute dates only. Slot form (`"kind": "slot"`) still renders on every request, unchanged.
>
> | Macro | Parameters | Description |
> |---|---|---|
> | `{{memory.awaken}}` | none | Full awaken list |
> | `{{memory.recent}}` | `rawCount=N,snippetCount=M`, defaults 1 and 4 | Latest N entries in full, then M snippets |
> | `{{memory.index}}` | none | Snippets of each domain root node |
>
> Parameters are comma-separated `key=value`; unknown keys are ignored and invalid values fall back to the defaults. Macro parameters must not contain nested `{{...}}` macros; a static macro call with nested macros is kept as-is and reported with a warning.
>
> Memory writes do not immediately refresh static macros. The first use in the next epoch (including one started after compaction) reads the current content. Use `recall` or `retrieve` for current memory; slot form reflects current content every request.

（C5 首行及刷新时机已按 03:201,447–459 定稿合入。）
