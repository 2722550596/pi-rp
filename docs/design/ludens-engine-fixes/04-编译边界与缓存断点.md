# 04 编译边界与缓存断点

> 本文范围：pi-rp 修复契约（`01-共同上下文.md`，下称"契约"）§2.6（history 边界下标 `volatileFrom` + Anthropic / Bedrock 消息断点）和 §2.7（`squashMessages` 不丢图、纯文本逐字节不变）。含主代理裁决 D10 / 效果 PE13（会话请求的 `cacheRetention` 设置）。
>
> 路径约定：不写前缀的路径相对 pi-rp 仓库根目录。`NEW` 标记本文新引入的符号（含签名），其余符号均能在现有代码或契约里找到。

## 1. 定位与范围

改三件事，都是为了让"history 之后每轮变化的内容"这一玩法成立：

1. **A（丢图）**：预设编译把相邻同角色消息压成一段纯文本，图片会丢（`compiler.ts:439-453`）。用 bun 跑真实编译器实测过：用户消息"文字 + 图片"和 history 后面的 user 块合并后，图片没了（契约 §2.7，效果 PE8）。
2. **B（断点）**：Anthropic 适配器把消息部分的缓存断点打在"最后一条 user 消息的最后一块"（`anthropic-messages.ts:1274-1296`）。history 后面只要有块，断点就落在这个块上，聊天记录永远读不到缓存（契约 §2.6，效果 PE9）。Bedrock 同理。
3. **T8（会话请求的 `cacheRetention` 设置）**：settings 新增可选顶层字段 `cacheRetention`，SDK 的 streamFn 每次请求时读取；请求自带值优先；不设置时请求字节与现在相同（契约 T8 + §2.10，效果 PE13，主代理裁决 D10）。

主要文件：`packages/coding-agent/src/core/prompt-preset/compiler.ts`（合并与下标）、`packages/coding-agent/src/core/prompt-preset/types.ts`（`CompileMessagesResult.volatileFrom`）、`packages/ai/src/api/anthropic-messages.ts`、`packages/ai/src/api/bedrock-converse-stream.ts`、`packages/coding-agent/src/core/sdk.ts`（streamFn、下标传递）、`packages/coding-agent/src/core/settings-manager.ts`（T8）。

**不做的**（契约 §1 T5、§8）：不改 `splitSystemMessages` 的提升逻辑；不改宏展开（归 02）；不改 chaoxi 等酒馆预设（D8）；不动按前缀自动缓存的 provider（OpenAI / Gemini 等）；pi-ai 的消息类型不加字段；`convertToLlm` 的 custom 分支不改、不透传消息字段；不新增“history 边界两侧不合并”的合并规则（契约 §2.7 第 4 条）。

## 3. 现状

### 3.1 编译路径

- 每次请求前 `getPresetInjectMessages`（`agent-session.ts:2829-2849`）调 `compileMessages`（`prompt-preset/compiler.ts:94`）重新编译整套预设，产出 `CompileMessagesResult { messages, sources, diagnostics }`（`prompt-preset/types.ts:420-424`）。
- 编译产出 `AgentMessage[]`（`packages/agent/src/types.ts:385`，= pi-ai `Message` ∪ 自定义角色消息）。history 之前的条目和 history 之后的条目都经 `addSyntheticMessage`（`compiler.ts:582-601`）变成 `{ role, content: [{type:"text",text}], timestamp }`；role 缺省是 `system`（`compiler.ts:588`）。
- 编译末尾：`result = squashMessages(result)` → `applyRegexRulesToMessages`（sync 路径 `compiler.ts:182-184`；async 路径 `:281-283`）。
- `squashMessages`（`compiler.ts:418-460`）：相邻同角色且双方 content 都是数组时，取出双方的 text 块拼成 `${lastText}\n\n${msgText}`，**替换整个 content 数组**，其余块（图片、thinking、toolCall…）全部丢弃（`:439-453`）。toolResult 永不合并（`:429-437`）。
- 实测复现（2026-10-16，bun 跑真实编译器，脚本已删）：preset `[block(system) "SYS", history, block(tail) role=user "TAIL"]`，history 是一条"文字 + 图片"的用户消息 → 编译结果只有一条 user 消息 `"看看这张图\n\nTAIL"`，图片块数为 0。同 preset 纯文本时，system 合并为 `"SYS\n\nSYS2"`、user 尾块保持独立（history 末尾是 assistant 时）或被并进 history 末尾的 user（history 末尾是 user 时）。这就是契约 §3 记录的实测结论，本次复核一致。

### 3.2 下标换算表：编译结果到适配器，条数/顺序在哪变

`volatileFrom` 是"history 之后第一条消息在编译产物 `messages` 数组里的下标"。适配器拿到的是转换后的消息序列，所以每个会改变条数或顺序的环节都要回答："转换后的第 N 条，对应编译产物的第 M 条？换算方法是什么？"以下按实际调用顺序（`packages/agent/src/agent-loop.ts:416-431` 组装请求）逐环核实：

1. **`compileMessages` 产出**（`compiler.ts:94`）：`volatileFrom` 的**计算点**，在 squash（§2.7 合并）之后、返回之前。取值：history 之后第一条消息的下标；history 之后的块与 history 末尾同角色消息合并成一条时，指向合并后的那一条（契约 §2.6）；history 之后没有条目时 `undefined`。
2. **`applyRegexRulesToMessages`**（sync `compiler.ts:182-184`；async `:281-283`；`regex-engine.ts:399-421`）：只改 content，不改条数或顺序。squash 得到的下标在 regex 后不变，作为编译返回值输出。
3. **`ExtensionRunner.emitContext`**（`extensions/runner.ts:1296-1318`）：扩展可以改 content（条数不变，下标不变）也可以**替换整个数组**（`replaceMessages` 情形）。条数变了下标就失效。**换算建立不起来 → 按"没有下标"处理**（契约 §2.6 明文）。实现上用"下标溯源失败检测"判定，见 §4.1 第 3 步与 §7。
4. **`convertToLlm`**（`core/messages.ts:233-335`）：跳过 bashExecution 的 `excludeFromContext`（`:255`）、custom 的 context/compaction 排除策略（`:265-268`）和未知角色（`:316-317`）；custom/summary 转换会重建对象（`:283-307`）。custom 在工具调用未完成时进入 `held`，等 `flush` 才输出（`:239-247, :320-333`），所以不仅可能减少条数，还可能改变顺序。
   换算：新增可选第 4 参数 `sourceIndices?: number[]`（NEW；完整签名 `convertToLlm(messages: AgentMessage[], resolveCustomType?: CustomTypeResolver, forSummarization?: boolean, sourceIndices?: number[]): Message[]`）。仅在现有 `out.push`、`held.push`、`flush` 处同步记录源下标：`held` 旁保留同序下标队列，flush 时一起移入输出映射。custom 的转换分支保持原样，不给消息加字段；现有调用方不传第 4 参数时返回值和行为不变。SDK 在转换时提供本次请求专用的空数组，转换结束后其第 k 项就是输出第 k 条的编译源下标。
5. **SDK 图片过滤**（`convertToLlmWithBlockImages` 内，`sdk.ts:402-424`）：只改 content（`{ ...msg, content: filteredContent }`，`:424`），不改条数。换算：下标不变；`sourceIndices` 数组原样传递。
6. **`splitSystemMessages`**（`packages/ai/src/api/transform-messages.ts:19-44`）：仅当传入 systemPrompt 为空时移除 system（`:23-28, :42`），预设路径满足该条件。各适配器在调用处保留过滤前的 systemPrompt 真值，用相同条件过滤本地 sourceIndices 副本；systemPrompt 非空则映射原样保留，不改提升逻辑。边界仍用编译坐标，不把 volatileFrom 指向的 system 当成 provider 消息；候选只取源下标位于边界前的剩余消息。无法对应输出条数时丢弃边界选项，按无下标处理。
7. **`transformMessages`**（`transform-messages.ts:98-257`）：第一轮 map 不改条数；第二轮会为孤立工具调用插入合成 toolResult（`:192-214, :253-254`），并跳过 error/aborted assistant（`:223-230`）。新增可选第 4 参数 `sourceIndices?: number[]`（NEW，前 3 参数与返回 `Message[]` 保持原样），调用时传当前映射的副本；第二轮 push 真实消息时记录输入的源下标，跳过时不记录，合成结果记录 `-1`；返回前用最终映射覆盖该参数。各适配器后续只使用换算后的映射；`-1` 表示无来源，禁止成为缓存候选。无下标时不传参数，现状行为不变。
8. **适配器 `convertMessages`**：Anthropic（`anthropic-messages.ts:1134-1296`）、Bedrock（`bedrock-converse-stream.ts:843-1001`）、openai-completions（`:1095-1230`）会新建 provider 格式对象；Anthropic 空串 user 不 push（`:1150-1155`），连续 toolResult 合并（`:1244-1273`）；Bedrock assistant 空内容跳过（`:885-888`），连续 toolResult 合并（`:951-964`）。构建 provider 消息时同步记录其全部源下标。候选必须有来源，且每个来源均满足 `0 <= sourceIndex < volatileFrom`；跨边界合并的整条消息和含 -1 的合成组排除。倒序找最后一条满足条件且具有可缓存块的消息。断点还会覆盖它前面的全部 provider 消息，因此其前缀中若已有边界后来源，候选必须继续前移到该来源之前；不能因 custom 重排把边界后内容纳入缓存。没有安全候选则不打。不能用 provider 数组位置直接索引上游 sourceIndices。
9. **`openai-completions` 的 `requiresAssistantAfterToolResult` 合成消息**（`openai-completions.ts:1118, :1319`，`:1556` 主路径为 false）：插入合成 assistant 会增加条数。其来源集合为空，不作为缓存候选；源消息输出仍使用自身源下标，不向合成消息借用前驱下标。

**传递路径**（下标怎么到适配器）：`CompileMessagesResult.volatileFrom` → SDK 的 `transformContext`（`sdk.ts:528-544`：它拿到编译结果）→ streamFn（`sdk.ts:464-498`）把它放进 `gateway.streamSimple` 的选项 → `ProviderStreamOptions = StreamOptions & Record<string, unknown>`（`packages/ai/src/types.ts:230`）携带任意附加键 → 适配器 `stream()` 入口读。选项名定为 **`volatileFrom?: number`**（NEW，约定见 §4.1）。[推断] 适配器间透传：`transformMessages`/`splitSystemMessages` 不动 options 对象，附加键原样到达 `convertMessages`。

**逐环结论表**：

### 3.3 现有断点规则

- **Anthropic**：system 2 个断点（OAuth 模式，`anthropic-messages.ts:999, 1006`；非 OAuth 1 个 `:1015`），tools 1 个（最后一个工具，`:1339`），消息 1 个——"最后一条消息若是 user，打在它最后一个可缓存块上"（`:1274-1296`；可缓存块 = text / image / tool_result，`:1280-1282`）。`getCacheControl`（`:60-74`）：`cacheRetention === "none"` 时无断点，`short` → `{type:"ephemeral"}`，`long` → 加 `ttl:"1h"`。
- **Bedrock**：system 后一个 `cachePoint`（`bedrock-converse-stream.ts:789-796`，仅 Claude 系模型），最后一条消息是 user 时往它 content 末尾 push 一个 `cachePoint`（`:995-1001`）。
- **其他适配器**：全仓 grep `cache_control|cachePoint`，只有 `anthropic-messages.ts`、`bedrock-converse-stream.ts`、`openai-completions.ts` 三处。`openai-completions.ts` 的 `applyAnthropicCacheControl`（`:965-1010`）只在 Anthropic 兼容格式（OpenRouter 的 anthropic/ 模型，`:1545`）下生效，往"最后一条 user/assistant/tool 消息的最后一个 text 块"打（`:987-1008`）；其余适配器（openai-responses、google-*、mistral、pi-messages、cloudflare、azure）无显式断点，靠前缀自动缓存。核查结论：需要改的是 Anthropic、Bedrock、openai-completions（Anthropic 兼容格式）三处；后者与 Anthropic 同构，一并修（§4.3）。

### 3.4 `cacheRetention` 现在传不进会话请求

- pi-ai 的流式选项本来就有 `cacheRetention?: CacheRetention`（`packages/ai/src/types.ts:209`，`CacheRetention = "none" | "short" | "long"` 在 `:104`），适配器都读它（§3.3）。
- 但 SDK 的 streamFn（`sdk.ts:464-498`）组装请求选项时只透传 `...options` 并补 `timeoutMs`、`websocketConnectTimeoutMs`、`maxRetries`、`maxRetryDelayMs`，不设置 `cacheRetention`。调用方（agent 主循环）不传这个字段，settings 里也没有对应字段（`Settings` 接口 `settings-manager.ts:141-193` 无 cacheRetention）。所以 ludens 的 `brain.cacheRetention` 配置传不进大脑会话。
- 缺省值事实（契约 §3 :221）：显式打断点的适配器缺省都是 `"short"`，环境变量 `PI_CACHE_RETENTION=long` 可改为 long（`anthropic-messages.ts:50-57`、`bedrock-converse-stream.ts:709-716`、`openai-completions.ts:190-197`、`openai-responses.ts:57-64`）；google-* 适配器不读这个字段（Gemini 隐式缓存）。
- 现有的"settings 每请求现读"先例：streamFn 在 `:465-466` 每次请求调 `settingsManager.getProviderRetrySettings()` 和 `getHttpIdleTimeoutMs()`。T8 沿用同一机制。
- 作用范围核查：
  - **在范围内**：agent 主循环（`agent-loop.ts` 经 `config.streamFunction` = SDK streamFn）；分支摘要（`agent-session.ts:6227` 传 `streamFn: this.agent.streamFunction`）；压缩（`compaction/compaction.ts:647` 显式传 `cacheRetention: "none"`——请求自带值，按 T8 优先级它赢，行为不变）。
  - **不在范围内**：`completeSideRequest`（`agent-session.ts:5131-5140`）和 auto-tidy 的 sideStreamFn（`:5741-5758`）都直接调 `this._requestGateway.streamSimple` / `gateway.streamSimple`，绕过 SDK streamFn，settings 值对它们无效（现状也不该有副作用：side request 本来就不追求缓存）。

## 4. 行为契约

### 4.1 `volatileFrom` 的计算与传递（契约 §2.6）

逐步行为：

1. **类型**：`CompileMessagesResult`（`prompt-preset/types.ts:420-424`）新增可选字段（契约 §2.6 给定形状原样落地）：

```ts
/**
 * Index of the first compiled message that carries content placed after chat
 * history (compiled fresh for every request). Providers with explicit cache
 * breakpoints anchor the conversation breakpoint before this message.
 * Undefined when nothing follows history.
 */
volatileFrom?: number;
```

2. **计算时机**：sync（`compiler.ts:182-184`）、async（`:281-283`）均在 squash 之后、编译返回之前产出下标。处理 afterItems 前记录 `messages.length` 为 `trackedFrom`；只有 afterItems 实际追加了消息才传入，否则传 `undefined`（空 slot 或空 block 不构成尾部消息）。squash 每处理一条输入时记录它将进入的输出位置：合并到 last 时是 `squashed.length`，开启新消息时是 push 前驱后的 `squashed.length`。当前输入下标等于 `trackedFrom` 时记下这个位置；之后不再改动。因此尾块并进 history 末尾 user 时，下标指向合并后的那一条。regex 只改 content，不再换算。
3. **`undefined` 条件**：history 后没有实际产出消息，或下游无法建立来源对应关系。编译器本身不负责判断扩展降级；该判断发生在 SDK/runner 接口处（§7）。
4. **传递**：选项名 `volatileFrom?: number`、`sourceIndices?: number[]`（均 NEW），前者始终使用编译产物坐标，后者把当前请求消息映射回该坐标。`getPresetInjectMessages` 现签名返回 `AgentMessage[]`，`:2849` 会丢编译元数据：新增可选参数 `onCompiled?: (result: CompileMessagesResult) => void`（NEW；完整签名 `getPresetInjectMessages(onCompiled?: (result: CompileMessagesResult) => void): Promise<AgentMessage[]>`），编译后、返回 messages 前调用。SDK transformContext 用回调接收边界；custom prompt 的早返回不调用，SDK 已先清空元数据。convertToLlmWithBlockImages 在有边界时传 sourceIndices 给 convertToLlm；streamFn 只在边界有效时条件展开两个选项。splitSystemMessages 和 transformMessages 各用本地副本同步换算，不能修改请求 options 中的原数组。映射未提供时 pi-ai 直接调用者按输入位置建立恒等映射；提供了但不合法时按无下标降级。
5. **换算失败降级**：`emitContext` 在 runner 内检查扩展是否换数组、增删或重排元素（§7），SDK 收到失效通知后丢弃本次 `volatileFrom`/`sourceIndices`；适配器收不到下标选项，走现状断点规则。每次 transformContext 开始先清空上次请求元数据，避免重试或其他请求继承旧边界。

**漏掉某一步的后果**：漏第 2 步的 squash 校准 → 下标指向被合并掉的位置，断点打错块（可能打进 history 更早的消息，缓存前缀被截短）；漏第 4 步条件展开 → 无下标的请求多一个字段，违反"逐字节不变"；漏第 5 步 → 扩展换数组后下标指向错误消息，断点位置随机。

### 4.2 合并规则（契约 §2.7）与 squash 中的下标跟踪

`squashMessages`（`compiler.ts:418-460`）改为：

1. **保留全部非文本内容且保持顺序**：合并双方 content 数组按原顺序拼接；两个 text 块相邻时才合成一个 `${lastText}\n\n${msgText}` 块（保证纯文本情形逐字节不变）。
2. **纯文本合并输出逐字节不变**：双方 content 都只有 text 块时，结果和现在一样是单个 `{type:"text", text: lastText + "\n\n" + msgText}` 块。
3. **toolResult 永不合并**：不变（`:429-437`）。
4. **不加边界规则**（契约 §2.7 第 4 条）：history 末尾的 user 与尾块照常合并（现状行为）。

函数签名（NEW）：

```ts
function squashMessages(
	messages: AgentMessage[],
	trackedFrom?: number,   // NEW：after 首条在输入数组中的下标；undefined 表示本路径无 after 条目
): { messages: AgentMessage[]; volatileFrom?: number }
```

下标跟踪规则（NEW 局部变量 `outputIndex: number`、`volatileFrom: number | undefined`）：

1. 输入循环保留当前 `idx`。先沿用现有条件判断本条是跳过、并入 last，还是开启新消息。
2. 跳过时不记录；若被跳过的是 trackedFrom，继续把下一条实际保留的尾部消息当作边界。尾部全部跳过则结果为 undefined。
3. 并入 last 时，`outputIndex = squashed.length`；不合并时先把已有 last push，再令 `outputIndex = squashed.length`。
4. 第一次处理 `idx >= trackedFrom` 的保留消息时，记录 `volatileFrom = outputIndex`。用独立的“已记录”布尔值区分 0 和未记录；后续消息不覆盖。
5. 结束后输出 last 并返回 `{ messages: squashed, volatileFrom }`。此法只记最终输出位置，不使用对象引用继承，不受 `{ ...last }` 重建对象影响。

非文本合并保留现有“双方都有非空 text 才合并”条件。双方纯文本时沿用现有 filter/map/join 后的拼接算法；含非文本时按 `[...last.content, ...msg.content]` 顺序遍历，仅把相邻 text 合成一个块，所有非文本块原样保留。不要修改输入块（合并 text 时新建块）。

注意点：

- 规则 1 的分支只在"至少一方 content 里有非 text 块、且双方都有 text"时到达。双方都有 text 是进入合并的前提（现有代码 `:443` 的 `if (lastText && msgText)`），所以"图片 + 纯空文本"这类组合维持现状（不合并、两条都保留）——现有行为如此，不在本次范围。
- **合并方向与 PE9 的关系**：squash 保持现状的合并（尾块并进 history 末尾 user）→ writer.json 型预设请求体逐字节不变（除断点位置外），这正是收口裁决 C2 消解 R1 V-4 的机制。下标指向合并后的那一条 → Anthropic 断点打在它**前一条**消息上 → "只少缓存最后一条用户消息"（PE9 收口后的验收口径，`00-需求原话.md` :85）。
- 顺序：merge 保留 `[...lastArr, ...msgArr]` 原顺序，图片在合并结果中的位置与合并前一致。

**漏掉某一步的后果**：漏规则 1 → PE8 不成立，图片继续丢；漏下标跟踪 → `volatileFrom` 指向被合并掉的旧位置或根本没算，PE9 失效或断点错位；漏规则 2 → 现有预设请求前缀字节变化，违反 T5。

### 4.3 断点规则（契约 §2.6）

统一规则（三个适配器共用语义）：

- **规则一（有下标）**：适配器收到 `volatileFrom` 时，消息断点打在**下标之前最后一条消息的最后一个可缓存块**上（包括 tool_result 块）。可缓存块：Anthropic 为 text / image / tool_result（现判定 `:1280-1282`，tool_result 块来自 toolResult 分支 `:1247-1273`）；Bedrock 为 content 数组末尾追加 `cachePoint`（现状做法 `:995-1001`，天然追加在最后一块之后，等价于"最后一个块"）。
- **规则二（无下标）**：没有 `volatileFrom` 选项时，行为与现在完全相同（不打新断点，现有"最后一条 user 消息最后一块"逻辑照旧）。
- **规则三（无可缓存块）**：下标之前没有任何可缓存的消息/块（消息数组以下标处开头，或之前的消息都被跳过/无内容）时，**不打消息断点**（system / tools 的断点照旧）。不打的理由：Anthropic 官方规则是缓存只在断点处写入、回看只找以前写入过的缓存（契约 §3）；没有可锚定的内容时打在下标处只会每轮写一个新缓存单元，纯浪费。

实现落点（Anthropic，`anthropic-messages.ts:1274-1296`）：

- Anthropic 构建 `params` 时同步记录每条 provider 消息的全部源下标（§3.2 第 8 环）。有下标时倒序查找所有源下标均小于边界的消息，打在最后一个 text/image/tool_result 块上；找不到可缓存块就继续向前，全部没有则不打。无下标保留现有逻辑。
- Bedrock（`bedrock-converse-stream.ts:995-1001`）使用同一候选判定，追加 `cachePoint`。记录连续 toolResult 的全部来源（`:951-964`），跨边界组排除；跳过的空 assistant（`:885-888`）不产生映射。无下标走现状。
- `openai-completions.ts` 的 Anthropic 兼容格式（`:965-1010`）：有下标时，addCacheControlToLastConversationMessage 按 §3.2 第 8 环的安全前缀条件选择最后一条 user/assistant/tool 消息的可缓存 text 块；排除无源、跨边界与边界之后消息。无下标照旧，仅影响该兼容格式。

按前缀自动缓存的 provider（openai-responses、google-*、mistral、pi-messages 等）：忽略 `volatileFrom` 附加键，零改动。附加键不出现在请求体里（适配器是逐块新建请求对象，见 §3.2 最后一环）。

**断点总数不变**：OAuth 模式 system 2 + tools 1 + messages 1（契约 §2.6）；本次只移动消息断点位置，不新增。

**PE9 落地口径**（契约收口后的验收，`00-需求原话.md` :85）：连续两轮请求，第二轮的 cacheRead 覆盖到上一轮写下的消息断点；history 末尾 user 和尾块合并成一条时，断点落在它前一条消息上，即只少缓存最后一条用户消息。对应实现：合并条的下标 = volatileFrom，规则一锚定"之前最后一条"。

**漏掉某一步的后果**：漏规则一 → PE9 不成立（回到现状）；漏规则二分支保护 → 无下标的现有预设断点位置变化，违反"行为与现在完全相同"；漏规则三 → 每轮多写一个无意义的缓存单元（Anthropic 按 1h/5m 计费写价高于读价）。

## 7. 错误边界与降级

- **扩展替换消息数组**：给 `ExtensionRunner.emitContext` 新增可选第 2 参数 `onMappingInvalidated?: () => void`（NEW，返回类型仍为 `Promise<AgentMessage[]>`）。在 `runner.ts:1298` 的 structuredClone 后，逐个处理器调用前复制当前元素引用列表；调用后若返回另一个数组，或当前数组长度/逐位置引用与快照不同，则调用回调并将本次映射永久标为失效。即使是等长替换或原地重排也能发现；只改原对象的 content 不触发。SDK 传入只清除本次请求元数据的回调。不能在 SDK 外比较原数组与 structuredClone 结果，否则所有请求都会误降级。
- **来源不可建立**：SDK 生成的 `sourceIndices` 长度与发送消息数不一致、索引越界，或扩展已报告失效时，丢弃下标选项、回现状断点规则。可确定映射但边界前没有候选时，不打消息断点；不回退到尾块。toolResult 跨边界合并按 §3.2 第 8 环排除整组。
- **Anthropic 断点合法性**：`cache_control` 打在 text/image/tool_result 块上都是合法位置（现状已在 tool_result 上打，`:1280-1282`）。规则一选中的"最后一个可缓存块"复用同一判定，不引入新块型。
- **Bedrock `cachePoint`**：`CachePointType.DEFAULT` 是现状用的类型（`:794, :998`），规则一沿用，不新增块型。
- **降级总原则**：任何分支找不到预期位置（无可缓存块、消息数组空、换算失败）时不打或按现状，不 throw；与规则三一致。
- **steering 连续 user / Bedrock 400**（存量，C15 不在本次范围）：`steeringMode: "all"` 多批 steer 与用户连发两条 `prompt()` 都会产生连续 user（§4.4 末条），Bedrock Converse 拒绝（`ValidationException`，AWS 官方行为，langchain-aws#192 等复现）。本次修复不加重（下标方案不加合并规则）也不修复。触发时错误信息原样冒泡给调用方（现状行为）。
- **T8 非法值降级**：`cacheRetention` 配了非法字符串（如 `"1h"`、`"Short"` 大小写错）→ getter 记 warning、按未设置处理，会话照常启动。不 throw（契约 §2.10 明文）。非法值 warning 只在读取时记一次即可（[推断] 每次请求现读，若每次都记会产生重复告警——实现可按 settings 值缓存"已告警"标记，或接受重复；不阻塞）。
- **T8 优先级冲突**：压缩显式传 `"none"` 而设置写了 `"long"` → `options?.cacheRetention ?? 设置值` 取 `"none"`，压缩行为不变。这是优先级规则的直接结果，无需特判。
