## 2. 一句话定位

把扩展加载拆成「node 磁盘通道（现状不动）」与「打包通道（全剖面，工厂注册 + ESM 静态 import）」两条腿，两条腿踩在同一块纯 TS 装配核上，产出同一个 `Extension` 形状；`pi.exec` 与 npm-git 包安装作为 Node 能力按 `capabilities.shell` 协商，协商语义与工具协商禁用同构。

## 3. 装配点与签名参数

### 3.1 现状装配链（node 剖面，本设计不改变其行为）

  → new DefaultResourceLoader (agent-session-services.ts:151-156)
  → resourceLoader.reload() (core/resource-loader.ts:395)

      → loadFinalExtensionSet (resource-loader.ts:580)
          → loadExtensionsCached (resource-loader.ts:565,585,605)  ← 磁盘通道：jiti 装载

关键事实：**打包通道在 node 剖面今天已经存在**——`DefaultResourceLoaderOptions.extensionFactories`（resource-loader.ts:169）+ `loadExtensionFromFactory`（core/extensions/loader.ts:583）。本设计不发明新机制，是把这条既有支路升格为 browser/hosted 的主通道。

### 3.2 双通道装配点（设计后）

### 3.3 browser 剖面装配签名（消费面）

browser-engine 入口（命名归 PackF 15-F）向引擎传递的资源清单走既有字段，零新类型：

```ts
// PackF 的入口内部组装（示意）——扩展作者 API 不分叉的关键：作者只写工厂
new DefaultResourceLoader({
  cwd, agentDir,
  settingsManager,                    // B 剖面注入的 SettingsManager（11-B 域）
  eventBus,                           // browser EventBus 实现（§9 缝 2）
  extensionFactories,                 // 组装期显式清单：InlineExtension[]（resource-loader.ts:169）
  noExtensions: true,                 // 关磁盘路径合并（resource-loader.ts:458-460）
  packageManager: nullPackageManager, // 新增注入点（§9 缝 4；node 缺省值不变）
  noSkills: true, noPromptTemplates: true, noThemes: true,   // 磁盘资源归 B/PackF 域，本模块不展开
})
```

`InlineExtension` 形状现状即够用（core/extensions/types.ts:1766-1771）：`ExtensionFactory | { factory, name, hidden }`。异步 chunk（`await import("./ext.js")` 后取 `mod.default`）是**宿主侧**动作——`createAgentSessionServices` 本就是 async，宿主 await 完再把工厂传进来，引擎无需感知加载方式。

### 3.4 runtime 注入签名

`createExtensionRuntime`（loader.ts:175）增可选参数：`createExtensionRuntime(options?: { exec?: ExecImpl; capabilities?: Capabilities })`。`exec` 由**组装点**按 `harnessEnv.capabilities.shell` 位选定后注入（node 组装点维持 `execCommand` 直连；`shell:false` 注入 `refusalExec`；hosted `shell:true` 注入 `shellBridgeExec(env)`——两个纯构造器见 §9 缝 3，共享层无 profile 字符串、无分派函数，「分派」即组装点一行表达式）；`capabilities` 自 `HarnessEnv.capabilities` 原样携带进 runtime，供扩展注册边界做能力声明检查（§4.9）。`loadExtensionsInternal` 已支持外部传入 runtime（loader.ts:601-628 的 `runtime ?? createExtensionRuntime()`），装配核不需要新传参路径。

## 4. 行为契约逐步

### 4.1 步骤一：通道分派总则

装配入口按 capabilities 决定启用哪些通道与实现；分派只发生在组装点，harness 内部无剖面分支：

| 通道/能力 | node {T,T,T} | browser {F,F,F} | hosted {?,F,?} |
|---|---|---|---|
| 磁盘通道（jiti 发现） | ✅ | ❌（`capabilities.diskExtensions=false`） | ❌（同左；升级路径见 §13.4） |
| 打包通道（工厂注册） | ✅（与磁盘通道并存，现状已支持） | ✅（唯一通道） | ✅（唯一通道） |
| `pi.exec` | ✅ execCommand | 结构化失败 `refusalExec`（shell 位分派，§4.5/§9 缝 3） | `shellBridgeExec(env)` 桥接（同上，`env.shell.exec`） |
| npm-git 安装 | ✅ DefaultPackageManager | Null 实现（§4.6） | 宿主注入 PackageManager 实现则可用，未注入则协商禁用 |
| 模块缓存（§4.7） | extensionCache Map | 语言级单例（无 Map） | 同 browser |

**漏了会怎样**：没有这张总则表，各模块会各自探测环境（`typeof process`、UA 嗅探），击穿契约 §4 原则 1「能力有且只有一个来源」。

### 4.2 步骤二：打包通道规范——三方案对照与结论

**方案 (a)：VIRTUAL_MODULES 的 browser 变体（jiti 进浏览器）——否决。**
- jiti@2.7.0 的 exports 无 browser 条件（node_modules/jiti/package.json 实测：仅 `.`/`register`/`native`/`static` 五导出，全部 node 实现），其价值主张是用 babel 在无构建环境转译 TS——浏览器本身就是 ESM 环境，转译与手工模块解析纯属倒退，违反 E5「归化而非绕过」。
- `tryNative: false`（loader.ts:514）要求 jiti 接管全部 import 解析；浏览器里表外 specifier 无处解析，等于要求维护第二张表，而表内内容（typebox、pi-* 包）恰恰是宿主 bundle 原生就有的。
- 打包体积为负收益：babel 运行时全量入包（PackF 实测上游 smoke bundle 已 974KB，见其 15-F）。

**方案 (b)：loadExtensionFromFactory 注册约定——采纳。**
- 复用既有代码路径（loader.ts:583-597 + resource-loader.ts:952-977 + 169 行的 option），两通道共用同一装配核（createExtensionAPI/createExtension/createExtensionRuntime），`Extension` 形状结构性同源——这是 I5 的最强保证，不靠测试追平。
- ESM 静态 import 原生提供方案 (a) 想解决的问题：「无磁盘模块系统运行时」在浏览器 = 语言内置。
- 树摇友好：未 import 的扩展不进包。

**方案 (c)：全局注册表（`window.__piExtensions` 之类）——否决。**
隐式时序依赖（注册必须先于装配）、树摇敌对（副作用模块不能被摇掉）、无类型、无诊断。仓内无任何先例。

**结论**：打包通道 = ESM 模块默认导出工厂 + 宿主经 `extensionFactories` 显式注入。VIRTUAL_MODULES 保持 node/bun 剖面原职责不动（loader.ts:52-80），其 key 集升格为**全剖面「扩展可 import 公共面」契约文档**（§4.3）——同一张表在 node 经 `getAliases()`（loader.ts:87-155）解析、在 bun 经 virtualModules 解析、在 browser 经宿主 bundler 解析，三剖面一份兼容性承诺。

**漏了会怎样**：若选 (a)，浏览器包背上一个 node 装载器且仍跑不通 node: 内置模块；若选 (c)，扩展加载时序变成隐式全局约定，AIRP 下游无法静态审查自己依赖了什么。

### 4.3 步骤三：扩展的 ES 模块静态 import 约定与依赖解析规则

扩展模块形状（两通道同一份源码）：

```ts
// my-extension.ts —— 默认导出工厂（jiti 侧 loader.ts:517 `{ default: true }` 与打包通道一致）
import { Type } from "typebox";            // peer：宿主/引擎提供
import { defineTool } from "@earendil-works/pi-coding-agent";  // peer
import type { ExtensionAPI } from "@earendil-works/pi-coding-agent";  // 类型随意

export default function (pi: ExtensionAPI): void {
  pi.registerTool({ name: "airp_lookup", /* typebox schema + execute */ });
}
```

规则：
1. **默认导出、工厂签名**。非函数默认导出在两通道得到同一错误串：`Extension does not export a valid factory function`（loader.ts:519-521 校验、:564-566 报错）。
2. **peer 约定**：`typebox`（含 `/compile`、`/value`）与 `@earendil-works/pi-*` 五包按 VIRTUAL_MODULES key 清单（loader.ts:53-80，含 `@mariozechner/*` 历史别名）视为运行时提供，扩展 MUST NOT 自带副本——typebox 以 per-copy symbol 做品牌校验 [推断]，双副本会导致 schema 校验静默失败。宿主 bundler 负责把 peer import 去重到引擎同一副本（npm `overrides`/bundler alias 写进 browser-engine 文档）。
3. **非 peer 依赖**：扩展自带并自行打包，但内容必须兼容目标剖面（`node:` 内置导入 = 扩展仅限 node 剖面使用，作者自选目标矩阵）。
4. **pi-tui 纪律**：跨剖面扩展对 `@earendil-works/pi-tui` MUST type-only import。运行时 import（渲染器返回 `Component`）在 browser bundle 会拖入 38 个 tui 模块（PackF 15-F 实测，barrel 击穿 tree-shake）。注册行为不受影响（I5 只要求注册等价），但打包体积由作者纪律决定。
5. **清单**：browser/hosted 的扩展清单 = 组装期显式传入（契约 §7 冻结口径）；`package.json` 的 `pi.extensions` manifest 读取（loader.ts:666-676 `readPiManifest`）属磁盘通道，不进 browser 面。

**漏了会怎样**：不锁 peer 规则，AIRP 扩展自带 typebox 副本会在浏览器里以「schema 全部校验失败」的方式静默炸掉，且这种炸法在 node 单副本环境下测试不出来。

### 4.4 步骤四：`discoverAndLoadExtensions` 的剖面行为

先纠正一个事实（见 §12 冲突 1）：`discoverAndLoadExtensions`（loader.ts:778-826）在生产代码**零调用点**——它只被 `index.ts:173`、`core/index.ts:44`、`extensions/index.ts:9` re-export，消费方全部在 test/。生产主路径是 `packageManager.resolve()` + `loadExtensionsCached`（§3.1）。

| 剖面 | 行为 |
|---|---|
| node | 现状不变：项目 `.pi/extensions` + `agentDir/extensions` + configuredPaths 三路发现（loader.ts:789-825），jiti 装载 |
| browser | 函数**不进入 browser-engine 导出面**。磁盘发现的前提（node:fs、路径解析、pi manifest）在剖面内不成立；扩展清单唯一来源 = 组装期显式传入（§3.3） |
| hosted | 同 browser（v1）。即使宿主注入真 fs（ExecutionEnv.FileSystem），jiti 需要的是 node require 语义而非 FileSystem 接口，fs 注入不自动点亮磁盘通道（`diskExtensions=false`，10-A 定稿） |

**漏了会怎样**：若把该函数带进 browser 导出面，AIRP 下游会在运行时撞 `node:fs` 导入错误，且这种错误出现在打包产物里才暴露，反馈环极长。

### 4.5 步骤五：`pi.exec` 协商语义（结论 + 理由）

**结论：方法保留，永不缺席，永不抛未知异常；browser 返回结构化失败值，hosted 桥接宿主 Shell。**

`pi.exec` 的唯一 API 位点：`ExtensionAPI.exec(command, args, options?): Promise<ExecResult>`（extensions/types.ts:1572-1573；事件 ctx 上没有 exec——brief 里的「ctx.exec」即此方法）。现状实现：loader.ts:388-391 直连 `execCommand`（core/exec.ts:29，node:child_process，exec.ts:5）。

分层语义（与 10-A 定论对齐，两层各守各的契约）：

| 层 | node | browser | hosted |
|---|---|---|---|
| ExecutionEnv（A 域） | NodeExecutionEnv | BrowserExecutionEnv.exec 恒返 `err(ExecutionError("shell_unavailable"))`（harness/types.ts:158-165 既有码） | 宿主 Shell |
| ExtensionAPI（本模块域） | `execCommand` 直连（行为不变） | 桥接 ExecutionEnv，把 `err(ExecutionError)` **映射为 ExecResult**：`{ stdout:"", stderr:"pi.exec unavailable: shell_unavailable (profile: browser)", code:127, killed:false }` | 桥接 `env.shell.exec`，`ok` → ExecResult，`err(timeout/aborted)` → `killed:true`，`err(其余)` → code:127 + stderr |

**理由**：
1. node 剖面的 `pi.exec` 契约是「resolve-oriented」——`execCommand` 连 spawn 失败都 resolve（exec.ts:60-63 catch 分支），从不 reject。若 browser 改为 reject，同一份扩展源码在 browser 多出一条只有 browser 才需要的 try/catch 路径，这正是 E6 要消灭的分叉。`code:127` 是 shell 对「command not found」的本义编码，语义诚实；stderr 前缀消歧「命令跑了但 127」与「没有执行器」。
2. 仓内「能力缺席」的既有表达不是方法缺席，而是**注入结构化失败实现 + 能力探测位**：noOpUIContext（runner.ts:283-287，`setTheme` 返回 `{success:false, error:"UI not available"}`）、`ctx.hasUI`（runner.ts:807-810）。工具协商禁用（ToolE：registry 缺席）与 API 协商（方法保留 + 结构化失败 + `ctx.capabilities` 探测，10-A §3 步骤 6）是同一枚硬币的两面：消费面分别对模型与扩展作者不可见。
3. 方法缺席方案否决理由：ExtensionAPI 类型（types.ts:1572-1573）全剖面同一份，运行时 delete 键会让 TS 类型说谎；`TypeError: pi.exec is not a function` 是无结构信息的崩溃，违背契约 §4 原则 2「不是运行时抛错」。

**hosted 桥接细节**：`ExecOptions.timeout` 是毫秒（exec.ts:15），`ShellExecOptions.timeout` 是秒（harness/types.ts:293-294），桥接换算；`(command, args[])` spawn 语义 → `Shell.exec(command 字符串)` shell 语义需参数 quoting（POSIX 单引号规则 v1，Windows 宿主壳待定，§13.3）。

**探测写法**（扩展作者）：`if (ctx.capabilities.shell) { ... }`（字段名 `capabilities` 已由 10-A §3 步骤 6/§9 定稿，类型 `packages/agent/src/harness/capabilities.ts`）；或检查 `code === 127 && stderr.startsWith("pi.exec unavailable")`。

**漏了会怎样**：若 browser 直接抛/reject，跨剖面扩展必须双路径写；若返回无差别 code:0 假成功，扩展会把「没执行」当「执行了」记录进业务状态——AIRP 场景这是数据损坏。

### 4.6 步骤六：package-manager（扩展 npm-git 安装）协商

npm-git 安装 = `DefaultPackageManager`（core/package-manager.ts）spawn npm/git（:32 `spawnProcess`，:2582-2666 spawn 家族）写安装根目录——纯 Node 能力，扩展作者经 `pi install`/settings packages 间接触达，`ExtensionAPI` 上**没有**安装方法（createExtensionAPI 全量方法面无 install，loader.ts:264-460）。

| 剖面 | 机制 | 行为 |
|---|---|---|
| node | DefaultPackageManager（现状） | 不变 |
| browser | NullPackageManager（注入，§3.3） | `resolve()/resolveExtensionSources()` 返回空集；`install/update*` 返回结构化失败（方法保留，同 §4.5 语义）；配置了 packages 源时经诊断通道输出「N 个源不可用（无 shell）」 |
| hosted | 宿主注入 PackageManager 实现（接口现成，package-manager.ts:102-118） | 注入则可用（契约 §7「经宿主注入可用」的落点）；未注入则协商禁用。`capabilities.shell` 是必要条件而非充分条件——shell:true 不自动等于 package-manager 可用，避免第二真相源 |

ResourceLoader 侧代码路径三剖面统一（reload 硬调 `packageManager.resolve()`，resource-loader.ts:410）——注入 Null 实现而非加剖面分支，这是 E6 的直接应用。

**漏了会怎样**：不加注入缝，browser 装配会在 `resolve()` 内部撞 node:child_process；若改为在 ResourceLoader 里 `if (browser) skip`，就开了 harness 内部剖面分叉的口子。

### 4.7 步骤七：extensionCache 的无磁盘等价物

现状（node 专属语义）：`extensionCache: Map<path, ExtensionFactory>`（loader.ts:147-149）+ cwd 代 token（:151-172 区段），仅 `loadExtensionsCached` 启用；作用是让 jiti（`moduleCache: false`，loader.ts:511）在信任引导双趟（resource-loader.ts:393-405 → :580-621）与 reload 之间不重复转译/重导同一模块；`clearExtensionCache()` 在每次 reload 时调用（resource-loader.ts:397-399），cwd 变化即换代（loader.ts:151-155）。

browser 等价物：**语言级单例，Map 退役**。
- 打包通道的工厂身份 = ESM 模块绑定，per realm 天然单例且不可清除——「同一工厂引用跨多次 reload 稳定」这一缓存目标由语言免费提供。
- 装配核保留 `clearExtensionCache()` 导出为 no-op（签名不动，两剖面调用方零改动——resource-loader.ts:398 与测试都在调它）。

**显式声明的跨剖面语义差异**（I5 不破，注册行为等价）：
- node reload：清缓存 + `moduleCache:false` ⇒ 扩展**模块顶层代码**每次 reload 重跑。
- browser reload：模块顶层代码**每页面生命周期仅跑一次**，工厂函数照常每次重跑（`loadExtensionFromFactory` 每次新建 Extension 对象 + 重执行 factory(api)，loader.ts:583-597），注册集合等价刷新。
- 推论（作者守则，进 browser-engine 文档）：扩展模块顶层不得持有本质状态，状态放闭包/工厂内/`pi` 状态面——这条守则在 node 下本来就隐性成立（顶层代码可能被重跑），browser 只是让它从「可能」变「绝不」。

**漏了会怎样**：若在 browser 仿造一张路径键控 Map，键都没有（工厂没有路径，只有 `<inline:name>` 假路径，resource-loader.ts:959-962）；若不声明顶层语义差异，依赖顶层副作用单次执行的扩展在两剖面行为漂移，I5 验收时表现为「偶发、无法复现」。

### 4.8 步骤八：subagent 扩展浏览器剖面初判

**结论：可行，无 Node 依赖阻断；真正的开口在 preset 供给链与工具集协商透传，均不在扩展装载机制内。**

事实：
1. `core/subagent/extension.ts` 是**命名误导**——它不经扩展 loader 装载，而是核心工具工厂，直接注册进 `_baseToolDefinitions`（agent-session.ts:4713-4715）。
2. `core/subagent/` 五文件（extension/spawn/run/prepare/index）**零 `node:` 导入**（复核 2026-09-30）：子代理是进程内构造——`prepareSubagentConversation` + `runSubagent`（run.ts），消费 `session.modelRuntime`/`requestGateway`（LLM fetch 面，browser 原生可用），`spawnAgent`（spawn.ts:84 起）同样进程内，无 child process。
3. 工具集缺口（ToolE 认领，14-E 落档）：`DEFAULT_SUBAGENT_TOOLS` 含 bash（prepare.ts:26-27），子代理经 run.ts:148-157 `createAgentSession({ tools: effectiveTools })` 构造但**不继承父会话 excludedToolNames**——browser 下父会话无 bash、子代理仍拿到 bash。修法 = 透传协商禁用集并 ∩ 进 effectiveTools（ToolE 定案，agent-session.ts:592/731 加 accessor）。
4. `spawnAgent` 的 `customTools` 通道（spawn.ts:46-49）接受扩展注册工具定义，纯数据传递，剖面无关。
5. **delegatable preset browser 供给链 = v1.x 专项条目（本模块持有，§13.5）**：现状 `prompt-preset/loader.ts:1` 直连 node:fs 读盘；v1 行为 = browser 剖面 `subagent_profiles` 优雅空返回「No delegatable subagent profiles are configured」（extension.ts:44-46 分支现成），该限制在 15-F v1 范围宣言双写；专项关闭条件 = 子代理 preset 在 browser 剖面可实例化（依赖 B 的 OPFS 布局资源扫描与 F 的资产打包，见 §13.5）。

**漏了会怎样**：若按文件名把 subagent 当扩展加载问题处理，会错误地把一套进程内机制做成可卸载扩展，反而制造 I5 分叉。

### 4.9 步骤九：工具能力声明面（`ToolDefinition.requires`，认领 14-E §3 步骤 10 提案）

**结论：采纳并收编**。`ToolDefinition`（extensions/types.ts:517-569 区段，`executionMode` :543 / `deferrable` :546 旁落位）增可选声明字段：

```ts
requires?: Array<"shell" | "diskExtensions" | "concurrentFsAccess">;  // 只引用 10-A 冻结三键，I2 不破
```

语义与检查点：

1. **声明式、缺席即全剖面可用**：不声明 = 工具自证全剖面可用（纯 JS/纯 API 工具的常态，14-E 口径采纳）。
2. **检查点 = 扩展注册边界，不是 isAllowedTool**：`registerTool`（loader.ts:296-303，装配核 api.ts 迁移后）经 runtime 携带的 `capabilities`（§3.4 注入）逐一核对 `requires` 三键；任一不满足 ⇒ **拒绝注册**（不写入 `extension.tools`）+ 诊断条目。`isAllowedTool`（agent-session.ts:4571-4583）与 `_refreshToolRegistry` 保持纯集合逻辑，**AgentSession 全程不接触 capabilities**——14-E 原提案的挂点越界（R2-B2）由此消解，R2-B2 附加条件「capabilities 进入 AgentSession 的通道也须一并设计」整个不再需要。
3. **诊断通道复用冲突诊断先例**：非致命、可见、可聚合——与 `addExtensionConflictDiagnostics` 同通道同形状（push 进 `extensionsResult.errors`；先例即冲突消息也走 error 字段，resource-loader.ts:623-631）。消息格式：`tool "<name>" requires capability "<key>" not available in this profile; registration skipped`。ExtensionRuntimeState 增收集数组 `pendingRegistrationWarnings`（模式对齐既有 `pendingProviderRegistrations`，loader.ts:250-256），`loadExtensionsInternal`/`loadExtensionFactories` 尾部转储进 result。
4. **I5 解读口径（备案）**：注册行为 = 同一确定性函数 f(扩展源码, capabilities) 在各剖面求值——输入不同输出不同是机制的**正确行为**，与 bash 协商禁用造成的模型可见面剖面差异同性质；I5 冻结的是装载机制等价（同一装配核、同一形状、同一注册语义），非无视能力位的字面全等。等价性可审计：每次差异化拒绝都落诊断条目（§11 T8 双向断言）。
5. **扩展作者守则**：内部调用 shell 的自建工具（如 "deploy"）应声明 `requires:["shell"]`；未声明的 shell 依赖工具在 browser 仍会注册并在调用期失败——requires 是声明式门控，不声明不兜底。该边界与 14-E §13-3 的「漏网」表述合并为同一条已知边界，且随本字段进 v1 收窄大半：**声明即被协商**。
6. **执行期第二防线**：工具 execute 收到的 ExtensionContext 有只读 `capabilities`（10-A §3 步骤 6 定稿），运行期分支探测合法（ExtensionContext 属契约 §4.1 允许查询位置），与注册期第一防线互补。

**漏了会怎样**：不落此字段，扩展自建 shell 工具在 browser 注册面漏网——与 bash 禁用同构的洞藏在扩展里（14-E 原话）；若按原提案挂 isAllowedTool，capabilities 渗入 harness 内部注册过滤层，违反契约 §4.1 冻结查询位置，且每次工具过滤都付出能力位比对成本。

## 10. 与现状差异

1. loader.ts 单文件 → 双文件（node 行为零变化；browser 获得可打包的装配核）。
2. EventBus 接口/实现分离（node 行为零变化；browser 获得 EventTarget 实现）。

6. ExtensionContext 增只读 `capabilities` 字段（10-A §3 步骤 6；三剖面一致增，非分叉）。
7. 扩展模块顶层副作用执行次数：node 每次 reload 重跑 → browser 每页面一次（§4.7，显式声明的唯一语义差异）。

10. 扩展工具能力声明面 `ToolDefinition.requires`：注册期协商禁用扩展自建能力依赖工具（三剖面一致生效：声明即被协商，未声明工具行为不变，§4.9）。

## 12. 发现的冲突

1. **事实修正（非契约冲突）**：契约 §2.2 与 P3 前提核查把「jiti + 磁盘发现」读作扩展 loader 主路径；实测生产主路径 = `packageManager.resolve()` + `loadExtensionsCached`（resource-loader.ts:410-413,565），`discoverAndLoadExtensions`（loader.ts:778-826）生产零调用点（仅 re-export 与测试）。影响：浏览器化的实际改动面比契约表述更小——发现/安装本就集中在一条可注入缝上。请契约维护方斟酌 §2.2 措辞（回写走申报，本模块不私改）。
2. **表面张力**：契约 §3 hosted 行「能力等价 node」 vs §7「磁盘通道 node 剖面专属」+ 10-A `diskExtensions: hosted=false`。本设计按 §7+10-A 执行（hosted 的 fs/shell 注入服务工具与存储，不自动点亮 jiti 通道）。建议 §3 hosted 行加半句「（磁盘扩展通道除外，见 §7）」。
3. **组装端前提依赖**（PackF 15-F）：coding-agent tools 层 browser 打包当前失败、pi-tui barrel 击穿 tree-shake。本模块装配核不在失败面（T2 证成后闭环）；工具层归 ToolE。不阻断本设计。
4. **子代理授权继承缺口**（ToolE 14-E）：run.ts:148-157 不继承父 excludedToolNames，browser 下父禁 bash 子代理仍有 bash。认领归 ToolE；本模块 §4.8/T7 引用其结论。
5. 与冻结不变量 I1–I6 核验：无违例。I5 由双通道共用装配核结构性保证（§9 缝 1）；I5 在 requires 场景的解读口径备案见 §4.9 检查点 4。
6. **冲突申报：能力查询位置扩充（R2-B2 处置 a 的契约回写请求）**。契约 §4.1 冻结查询位置为「组装点 + ExtensionContext」；本设计增列第三位置——**扩展注册边界**（`createExtensionAPI.registerTool`，capabilities 经组装点 `createExtensionRuntime({capabilities})` 注入流动至此，§9 缝 6）。申报理由：ExtensionContext 在注册期不存在（`runner.createContext()` 仅事件/工具执行期构造，runner.ts:792-794），能力门控若只能挂 ExtensionContext 则只能运行期拒绝，违反协商禁用语义（❌ = 不进模型工具列表）；检查点物理位置在 loader 装配核内，是组装注入边界的下游延伸，非新探测源——原则 1 不破（capabilities 唯一来源仍是 `HarnessEnv.capabilities`，runtime 只是携带者）。较 R2-B2 建议申报的 `_refreshToolRegistry` 范围更小：AgentSession 不需要 capabilities 传播，R2 附加条件「capabilities 进入 AgentSession 的通道设计」整体消解。请契约维护方回写 §4.1 查询位置清单为：组装点 / ExtensionContext / 扩展注册边界（@ProfileA 会签）。
