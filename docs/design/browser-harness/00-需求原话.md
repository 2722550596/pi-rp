# 需求原话：pi-rp 浏览器化（便携 harness）

> 本文档是本次需求的第一手档案。§1 为明月原话，一字不差；§2 起为注释与清单，**注释非原文**，与原文严格分离。任何设计/评审/实现代理 MUST 以 §1 为对照基准。

## 1. 明月原话（2026-09-30 会话，一字不差）

### 消息 1

> 我现在有一堆项目在用pi-rp作为agent引擎，然后我这里就遇到一个很现实的问题，成本问题。就是你想想，pi这玩意本来就是ts写的，理论上搞成js后浏览器直接import就能在用户local跑了，scale时压根不用占用服务器资源。前提是下游在消费agent时不需要沙箱环境，不需要跑代码/build之类，然而对于airp类产品来说这才是常态啊常态。所以我想你研究一下我们能不能找一个办法，把pi打包成接口，让pi-rp的进程能够以十分便携的形式在各种载体跑。比如理想情况下我觉得拿pi的引擎来做一个纯前端应用应该是理论上是没问题的

### 消息 2

> 我们反正只需要消费它作为harness提供的agent loop整个框架的核心，以及扩展系统，以及其他能力，完全没必要强行依赖沙箱

### 消息 3

> 对了，哪怕有阻碍，比如某些模块依赖node或者不能直接浏览器处理，我相信困难也只是暂时的，只要我们聪明一点改掉，理论上可以local化

### 消息 4

> 阻碍项肯定不是直接砍，因为浏览器化只是一种形式，pi-rp这东西毕竟是agent harness，你要把那些真砍了，它就不叫pi-rp了，而是叫pi-rp-browser。能兼容并且处理得优雅一点吗？

### 消息 5

> 其实我的想法是，真搞纯前端的话，bash 工具可以直接禁用了

### 消息 6（启动设计）

> 开始弄吧，注意我们的核心诉求是浏览器化+兼容，其他的解法如果更优需要考虑，我们刚才想的那些只是临时的说法

### 消息 7-9（设计期间插话，2026-09-30，补录留痕 [注释，非原话档案——R3 审计指认后补]）

> 有两个问题，第一个是grep find这种工具原生是不启用的，那怎么用到？第二个问题是，既然agent都跑在浏览器里了，那文件系统是什么？还有pwd，目录，文件，这种概念吗？

> 那两个工具原生就是不启用的，你自己看清楚。非fork的pi原生只有 write read edit bash 四个工具，pi-rp这个fork加了其他rp用工具，但没碰过那两个

> 那个bash是后来补进去的 / 因为之前不给bash实在太神经了 / 那两个工具以及ls我记得是默认有，但是不用，因为原生有bash，然后有一个启用的方式是子代理会显式启用，因为子代理默认禁用bash。这个思路应该被浏览器本地化学习，因为浏览器化后bash就被禁用了。但是你别以为这几个工具默认启用啊

**注释（拍板留痕）**：消息 9 即「bash 互补开关」原则的出处——grep/find/ls 默认激活状态 = bash 可用性的反函数；该原则已冻结进契约 §5 注记并由 14-E §3 步骤 3A 落实。R3 审计质疑"拍板引文不在 §1 六条消息档案内"成立，本节即为补录。

## 2. 效果清单（用户要的功能效果；注释，非原文）

| # | 效果 | 验收口径 |
|---|---|---|
| E1 | pi-rp 可"打包成接口"，以十分便携的形式在各种载体跑 | 下游能在多种载体（纯浏览器前端为理想情形）import/接入并运行 agent |
| E2 | scale 时基本不占用服务器资源 | agent loop 的计算与内存在用户侧设备上发生，服务器不再为每个会话常驻 agent 进程 |
| E3 | 下游消费无需沙箱环境、无需跑代码/build 类能力也能正常用 | AIRP 类消费形态（工具=业务 API 调用）在无 shell 的载体上开箱即用 |
| E4 | 消费面 = harness 的 agent loop 核心 + 扩展系统 + 其他 harness 能力 | loop、扩展、preset、memory、session 等 harness 能力在浏览器载体上可用 |
| E5 | Node 依赖类阻碍被"聪明地改掉"而非绕过 | 每个阻碍项有明确归化方案（接口化/替换/协商禁用），不做环境 hack |
| E6 | **pi-rp 仍是 pi-rp**：同一物种多运行时形式，不产生被砍能力的"pi-rp-browser"分支物种 | harness 能力面完整保留；浏览器形式下不可用能力走"协商禁用/注入替换"，代码本体不分叉 |
| E7 | 纯前端形式下 bash 工具可直接禁用（用户已拍板的剖面决策） | 纯前端载体下 bash 不进入模型工具列表 |
| E8 | 兼容优先，不锚定临时方案 | 消息 1–5 中讨论的解法均为候选提案；若存在达成 E1–E7 的更优解法，设计须考虑并升级拍板 |

## 3. 解法清单（用户/讨论中提议的做法及其系统能力前提；注释，非原文）

> 依消息 6："我们刚才想的那些只是临时的说法"——以下解法均为**候选提案**，设计阶段以 E1–E8 为准绳重新审视，可推翻。

| # | 提议解法 | 依赖的系统能力前提 | 前提核查（2026-09-30 调研） |
|---|---|---|---|
| P1 | TS 编译成 JS 后浏览器直接 import | 核心链路无 Node-only 运行时依赖 | ✅ 成立。上游 CI `scripts/check-browser-smoke.mjs` 以 `platform:"browser"` 持续守护五入口（agent/ai/compat/protocol/client）；`packages/agent` 主入口 import 链无 node: 运行时导入（仅 `env/nodejs.ts` 与 session/testing 两处，均被子导出隔离） |
| P2 | 拿 pi 引擎做纯前端应用 | session/存储/memory 等可浏览器归化 | ✅ 成立。`JsonlSessionRepoFileSystem` 接口缝（`packages/agent/src/harness/session/jsonl/types.ts:4-19`）；memory `driver.ts:46-51` 为 node:sqlite 单点工厂；`@node-rs/jieba` 为唯一 native 依赖（`packages/memory/package.json`） |
| P3 | 只消费 loop 核心+扩展系统，不依赖沙箱 | 扩展系统可脱离磁盘/Node 模块机制加载 | ✅ 成立。`VIRTUAL_MODULES`（`packages/coding-agent/src/core/extensions/loader.ts:33-55`，为 Bun 单文件二进制设计的先例）+ `loadExtensionFromFactory`（loader.ts，内联工厂注册） |
| P4 | 阻碍项不砍、协商禁用（E6/E7 落地机制候选） | 工具注册可按运行时能力条件化 | ✅ 成立。工具全部为独立工厂 `create*ToolDefinition` + Operations 注入（`packages/coding-agent/src/core/tools/index.ts:81-110`）；`ExecutionEnv = FileSystem + Shell` 接口（`packages/agent/src/harness/types.ts:231-315`） |
| P5 | bash 在纯前端形式下直接禁用 | 同 P4；且禁用后 loop 其余部分不受影响 | ✅ 成立（P4 同源）。grep/find 的 Node 实现 spawn `rg`/`fd`，浏览器形式的归化需设计阶段实测取舍（纯 JS 实现 vs 一并禁用） |

## 4. 待设计阶段回答的开放问题（注释，非原文）

1. 载体谱系的**剖面划分与命名**（node / browser / 宿主壳等）及各剖面能力集——E6 的落地核心。
2. "打包成接口"的**分发形态**：独立 npm 包？coding-agent 的 browser 子导出？入口 API 面是什么样？
3. LLM 请求的 **CORS 与 key 策略**：BYOK 直连 vs 内置 streamProxy 中转 vs 自建网关。
4. grep/find 浏览器形式归化：纯 JS OPFS 实现 vs 剖面禁用，性能/体积实测取舍。
5. memory 分词：`Intl.Segmenter` vs jieba-wasm，检索质量实测取舍。
6. AgentSession 类内焊死的存储/bash/扩展加载如何拆分成注入接口，且**不破坏 Node 剖面现状**。
7. 上游同调策略：本仓偏离集中在外围，设计须声明哪些改动将来可反哺上游、哪些是本仓私有。
