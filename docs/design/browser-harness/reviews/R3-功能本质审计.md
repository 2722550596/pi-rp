## ① 独立架构推导（写于读设计文档之前）

### 0. 从 E1–E8 反推的本质需求

- E1+E8：消费形态是**库/接口**而非"服务"。"打包成接口让 pi-rp 进程便携跑"是候选措辞（E8 明示消息 1–5 均为临时说法），真正被锚定的验收是"下游能在多种载体 import/接入并运行"，理想情形=纯前端应用直接 import 在用户设备上跑。
- E2：计算与内存发生在用户侧；服务器至多保留**无状态**辅助（如 CORS 中转）。
- E3：工具面=业务 API 调用（fetch 级），无 shell/build/沙箱需求。
- E4：消费面是 harness 全能力面（loop/扩展/preset/memory/session），不是阉割版。
- E5：每个 Node 依赖有**接口化/替换/协商禁用**的归化方案；禁止环境 hack（polyfill 假 fs 之类语义说谎物）。
- E6：同一物种多运行时形态。代码本体不分叉；不可用能力走"协商禁用/注入替换"。E6 的反面教材就是"pi-rp-browser"分支物种。
- E7：纯前端下 bash 不进模型工具列表（用户已拍板）。

关键洞察：**E7 不该是 bash 的特例，而是"能力不可用 → 工具不注册"一般规则的特例**。架构的核心是一个能力协商层；bash 只是它的第一个实例。

### 1. 剖面划分（关键决策一）

从零接手，先做依赖审计。本仓（勘察所得）为 pi 的 fork monorepo：`agent`（loop 核心）/`ai`（provider）/`memory`/`protocol`+`client`+`server`（RPC 栈）/`session-backends/sqlite-node`/`tui`/`coding-agent`（产品装配）。`node:` 内建导入分布：coding-agent 62 文件、memory 12、ai 6、agent 仅 2（且已有 `./node` 子导出隔离与 `check:browser-smoke` 守护雏形）——**核心已经很干净，脏的是产品装配层**。

正确的切法是六边形（ports & adapters），且端口必须按**能力粒度**而非运行时粒度切：

1. **核心层（runtime-agnostic）**：agent loop 状态机、消息/事件类型、tool-call 协议、preset 组装、LLM 流式传输（fetch/SSE 是 Web 标准，两个运行时都有）。硬约束：零 `node:` 导入，用构建断言机械守护（上游 browser-smoke 已是这个思路）。
2. **环境端口层**：把 Node 依赖收拢为窄接口——文件存储（限定 harness 实际需要的读写列举面，而非 POSIX 全集）、进程执行、密钥来源、模块加载。fetch 直接用全局。
3. **适配器层**：Node 适配器（现有实现收拢）+ 浏览器适配器（OPFS 等）。
4. **载体装配层**：Node CLI/TUI 与浏览器前端都是"载体"（carrier），各自提供能力并装配 harness。E6 的"同一物种多运行时形式"在结构上就体现为：**两个载体、一个核心**。

否决的替代切法：fork 出 pi-rp-browser 包（违 E6，明示）；给浏览器塞 WASM Node（E3 明示不需要跑代码，复杂度无消费场景）；memfs 类 fs polyfill（语义说谎，违 E5）。

### 2. 能力协商（关键决策二）

- 启动时构造**显式的、类型化的能力清单**（数据，不是散落各处的 `typeof process` 探测）：shell 执行有无、持久存储有无/形态、密钥来源。
- 每个内置工具/扩展声明自己需要什么能力。装配期解析：能力缺失 → 该工具**不注册、不进模型工具列表**，而非注册后运行时报错（浪费上下文、制造必然失败的调用）。禁用事实应当可查询，供载体 UI 呈现。
- E7 由此变为一般规则的实例：纯浏览器无进程执行能力 → bash 不进列表。**不需要任何 bash 专用开关**。
- 能力清单默认值可按运行时派生，载体可显式收窄/覆盖（受限 Node 环境可以只给存储不给 shell）。
- 否决：环境嗅探散落在工具内部（不可测试、不可嵌入）；polyfill 假实现（违 E5）。

### 3. 存储（关键决策三）

- 接口定义在**文档/集合级**（get/put/list/delete + 命名空间），不定义 POSIX 级。session transcript、memory、settings/preset 都是 JSON 文档。
- Node 适配器 → 现有磁盘布局（格式不变）；浏览器适配器 → OPFS（语义最接近文件、worker 内有同步面、受 quota/eviction 管辖需显式声明）。
- **格式跨运行时逐字节一致**：node 导出的会话能被浏览器载入，反之亦然——这是 E6"同一物种"在数据面的兑现，也是 E1"各种载体跑"的状态面。
- read/edit/write 类文件工具：走存储端口的作用域根实现；载体不愿提供文件命名空间时按能力协商禁用。两个运行时都不丢能力面。
- pi 自身状态与 agent 工作区应分属两个命名空间（一个是 harness 的账本，一个是模型操作对象），不混居。
- 本仓 session 已有 backend 抽象苗头（session-backends/sqlite-node、协议栈），浏览器化是**增加一个后端**，不是新造机制。

### 4. 扩展加载（关键决策四）

- 扩展是 TS/JS 模块。抽象"模块解析"这一个缝：Node=磁盘发现+运行时装载（现状）；浏览器=**装配期显式传入的模块清单**（import map/预打包 ESM），浏览器本身就是 ESM 环境+自带沙箱，无需再造模块系统、无需沙箱。
- 扩展 API 本体必须 runtime-agnostic；扩展用了 Node 内建 → 在浏览器加载/运行失败并给出明确诊断，与工具同一协商规则。
- 否决：为扩展造自定义模块系统/运行时转译器（复杂度无收益：浏览器原生 ESM 就是答案）；隐式全局注册表（时序不可控、树摇敌对）。

### 5. 分发形态（关键决策五）

- 形态 = **npm 包 + 唯一工厂入口**（如 `createHarness(env)`）的 headless SDK；单一源码树、双运行时入口。node CLI/TUI 与 browser app 都是它的消费者——这同时是 E6 的结构证明。
- 浏览器侧由任意打包器打包；核心零 node 导入 → tree-shaking 自然丢弃 node-only 实现。
- E8 检查：消息 1 的"打包成接口让进程便携跑"暗含"进程"概念，可能把人引向远程进程协议/容器镜像。但 E1 验收口径与理想情形（纯前端 import 直跑）已把形态钉死为**库内嵌**；进程形态至多是 node 载体的既有事实，不构成架构目标。
- 可选的第二产物（CDN esm/嵌入组件）是发布策略，不是架构承诺。

### 6. LLM 接入（关键决策六）

- 传输统一 fetch/SSE（Web 标准），剔除 undici 等 Node 专属传输件。
- 鉴权：密钥经注入的密钥来源（浏览器=用户输入+本地持久化）；BYOK 是 AIRP 形态的自然默认。
- CORS：允许直连的 provider 直连（用户自己的 key，E2 成立）；不允许直连的 provider 由载体配置**无状态**转发（不跑 loop、不存会话）→ E2 不破。
- 主流 provider 侧：Anthropic 已有官方浏览器直连机制；OpenAI/Google 类待服务端 CORS 核实——设计必须把"待实测"显式留档而非默认承诺。

### 7. 明确不做的事（范围纪律）

不做 WASM Node、不做完整 POSIX fs polyfill、不做 service-worker 文件系统、不做自定义沙箱、不把 RPC 远程进程形态当架构目标（RPC 栈是 node 世界的既有能力，浏览器化不依赖它）。所有端口以现有真实消费者（node CLI 今天就要用）为第一用户，不为假想场景预留重型抽象。

### 8. 最小机制集自检

达成 E1–E8 所需的全部机制：能力清单 + 按能力注册工具 + 存储端口（node=磁盘/浏览器=OPFS，格式一致）+ 模块清单式扩展通道 + 密钥来源 + BYOK 直连/可选无状态中转 + 单包双入口分发。**除此之外的任何机制，都应被要求回答"为什么更简单的确定性代码不够"。**

## ② 对照差异分析

### 2.1 收敛点（独立推导与设计一致的核心决策）

六份设计与 §1 的独立推导在所有关键决策点上**方向一致**，收敛度高到可以互为佐证：

| 决策点 | 独立推导 | 设计 | 判定 |
|---|---|---|---|
| 能力协商 | 启动期类型化能力清单，唯一来源；缺失→不注册 | `Capabilities` 伴生对象 + `negotiate()` 唯一构造点 + 契约 §5 总表 + 协商禁用语义冻结 | 一致 |
| E7 | bash 是"能力缺失→不注册"一般规则的实例 | bash 是唯一以 capability 位为开关依据的内置工具，全链（schema/prompt/指南/子代理/扩展同名覆盖）协商禁用 | 一致，且设计的全链证明（14-E 步骤 2）比推导更完备 |
| 存储 | 文档级端口、OPFS、格式逐字节一致、状态/工作区分居双子树 | StorageBackend 窄面 + `/state`//`/workspace` 双子树 + 跨剖面拷贝即迁移 | 一致（形状分歧见 2.2-b） |
| 扩展 | 显式模块清单通道，不移植 jiti、不造沙箱、否决全局注册表 | 打包通道=既有 `extensionFactories` 升格；jiti 进浏览器被证据否决；全局注册表否决 | 几乎逐条一致 |
| 分发 | 单包 + 唯一工厂入口 + 双载体 | `packages/browser-engine` + `createPiHarness()`；否决 coding-agent 子导出方案（理由充分） | 一致 |
| LLM | BYOK 直连默认 + 无状态中转可选 + 待实测留档 | 三候选对照表、anthropic 直连全链在案、CORS 待实测显式列表、不自建参考 proxy | 一致 |
| 拒绝清单 | 无 WASM Node/无 memfs/无沙箱/进程形态非目标 | 同上全部未出现；remote RPC 明确"加分项非前置" | 一致 |

### 2.2 分歧点及裁决

- **(a) 能力字段集**：独立推导倾向"每工具/扩展声明 requires"的一般化；设计收敛为**三个** capability 位（shell/diskExtensions/concurrentFsAccess）+ 开关总表，其余差异走注入件存在性。设计更简、I2 有机械核验。**采认设计**——一般化 `requires` 只保留为扩展工具的提案（14-E 步骤 10），且 v1 进否未拍板（见 ③-5）。
- **(b) 存储端口形状**：独立推导偏好文档/集合级抽象；设计选择了"与现存 node:fs 同步调用逐一对应的窄面"（StorageBackend 12 方法）。驱动力是独立推导未充分权重的一个真实约束：**本仓是活跃 fork，上游同调（fork-merge 冲突面最小化）是硬工程约束**——`ExecutionEnv` 上游接口零改动、node 剖面逐字节零行为变化、同步签名不变，都由此而来。该约束成立（勘察可证：上游 browser-smoke 守护模式、`packages/agent` 几乎未动），**采认设计**；但它只豁免"接口形状保守"，**不豁免 E6 纪律走样与 ④ 项机制冗余**（见下）。
- **(c) 协商记录落账**：推导建议禁用事实可查询/可呈现；设计裁定 capabilities 不落账、只读展示归载体。设计更简，采认。
- **(d) hosted 剖面**：E1 字面只要求"多载体、纯浏览器理想"；设计增列 hosted（Tauri/Electron 壳）。由于 F 让 hosted 与 browser **共享同一 bundle**、差异只在注入与开关值，增量成本受控且与 E6 同构。采认，但它不是 E1–E8 的字面义务——④ 中两个 capability 位的存废论证都依赖 hosted 场景，审计据此提问。

### 2.3 纪律执行核查（E6 口径的走样）

契约 §3/E6 口径与 10-A 步骤 7 冻结："剖面名不出现在任何 harness 内部函数签名/参数/字段；harness 内部只能问 capabilities 查询"。核查发现两处设计自身违背此纪律：

1. **12-C 缝 3**：`negotiatedExec(profile): ExecImpl`，落点 `core/extensions/exec-impl.ts`——coding-agent core 内部以 profile 字符串为参数的分派函数。exec 的三剖面差异（execCommand/协商失败值/宿主桥接）完全可以在**组装点**选好 ExecImpl 注入（12-C 自己在 §3.4 已有 `createExtensionRuntime(options?: { exec })` 注入缝，二者重复）。`negotiatedExec(profile)` 是同一件事的第二套机制 + profile 名入共享层双重违纪。
2. **13-D §3.2**：`createMemoryTokenizer(profileHint: "node" | "browser")`——memory 共享层按剖面分支。且 13-D 同时已有注入式 `MemoryTokenizer` 接口（§3.2 上半）与 db 级 `fts_tokenizer` 落账，该 profileHint 工厂是第三套表达同一分叉的机制。按契约 §3 口径，分词器选择应在组装点注入，core 只认接口。

10-A 验收测试 7（grep 无 `browser|hosted` 剖面字符串比较）的扫描范围写的是"agent 核心与 coding-agent core"，恰好把 memory 包排除在外——这两处走样说明该验收口径本身需要扩大到全部 harness 共享层。**这不是行为缺陷，是纪律风险**：第一步让 `if (profile)` 合法化，E6 的禁令就退化成自觉。

### 2.4 跨文档一致性核查

- **11-B 与 15-F 的持久化装配矛盾**（升级为 ③-1 主要缺口，证据见彼处）：B 承诺 OPFS 持久化 + 刷新恢复冒烟，F 的入口 API 缺省与字段面都不通往该承诺。
- 11-B 在 F 的包（packages/browser-engine）内规划 `src/state/*` 文件（11-B §8），而 F 的包布局（§5.1）与装配步骤（§4 S1–S9）没有该目录与对应步骤——两份文档对同一个包的内部结构各写各的，未对齐。
- C/E 之间的接口点（子代理排除集透传、`ToolDefinition.requires`）互相引用且认领清晰；A/B 的 HarnessEnv vs HarnessStores 分立经冲突申报定稿。这两处一致性良好。
- F `profile: "browser"|"hosted"` 入口字段与 A 的三入口函数并存：profile 字符串与 env 注入形状信息冗余（见 ④-6），在入口边界使用不违约，但两套入口分类学的关系（谁调用谁）文中未写明。

## ③ 效果未达成项（E1–E8 对照）

判定口径：**未兑现** = 设计无通路；**折扣** = 有通路但留有已声明的洞或押在未定项上。

| # | 效果 | 等级 | 缺口与证据 |
|---|---|---|---|
| 1 | **E1/E4 · 未兑现（主要缺口）** | 高 | **浏览器持久化装配在分发入口缺位，与存储设计的承诺直接矛盾。** 11-B 承诺：OPFS 双子树、settings/auth/sessions 全量落盘、"建 session→写三轮→**刷新页面→session 恢复**；auth 写读"冒烟（11-B 验收 3），并在 F 包内规划 `src/state/*` 装配 provider（11-B §8）。但 15-F 的入口 API：`settings` 缺省 `SettingsManager.inMemory()`（§3.3）、`storage` 面只有 `sessionRepo/credentials/sqliteFactory` 三字段、S3 明写"缺省 inMemory + 注入覆盖"，包布局（§5.1）无 state 目录、S1–S9 无 OPFS 状态装配步骤。结果：**按 15-F 文档化 API 组装的 browser harness，settings/auth/session 全部不持久**，11-B 的刷新恢复冒烟无法通过；而 15-F 自己的冒烟（§11.2）只测 prompt 与工具列表，恰好绕开了持久化。两个验收口径互斥，说明两文档未对齐同一装配真相。修法方向：F 入口补 `state`/stores 装配面（或 profile=browser 时内部缺省走 B 的 OPFS provider）并回写两处缺省值声明。 |
| 2 | **E4 · 折扣** | 中 | **delegatable preset（子代理 profile）浏览器供给链未设计。** 12-C §4.8/§13.5：`prompt-preset/loader.ts` 直连 node:fs，"preset 打包/存储归 B/PackF 域"，专项关闭前 browser 剖面 `subagent_profiles` 优雅返回"无配置"。子代理是 E4"harness 能力面完整"的组成部分；优雅空返回是诚实的降级，但**能力未达成**，须在 v1 范围宣言中显式列为已知缺口（或补设计），不能停留在"待专项"。 |

## ⑤ 总结论

**有条件通过（conditional）。**

理由：六份设计在架构方向上与独立推导高度收敛——能力协商唯一来源、E7 一般规则化、OPFS 存储格式跨剖面一致、扩展工厂通道（拒绝移植 jiti/拒绝沙箱）、独立 npm 包单入口、BYOK 直连+无状态中转、拒绝清单（WASM Node/memfs/进程形态）逐条吻合；且设计在 fork 同调约束、候选对照实证（sqlite/分词/打包体积/grep-find 实测）上比独立推导更扎实。E1–E8 的**架构层通路全部成立**。

放行条件（主代理裁定前须获设计方回应）：

1. **③-1（必须修复）**：11-B 与 15-F 的持久化装配矛盾必须闭环——F 入口补状态装配面或改缺省值，两份文档的缺省声明与冒烟口径对齐；否则 E1/E4 在分发入口上不成立。
2. **③-2/③-3（拍板留痕）**：delegatable preset 缺口与凭据持久化归属，v1 范围宣言显式列明（补设计或显式降级）。
3. **③-4/④-4（归属拍板）**：pi-tui 正解（renderer sidecar）纳入 v1 归属，或显式接受 stub 为 v1 方案并写明风险承担方。
4. **③-6（纪律回正）**：`negotiatedExec(profile)`、`createMemoryTokenizer(profileHint)` 改为组装点注入；10-A 验收 7 的剖面名扫描范围扩大到全部 harness 共享层（含 memory 包）。
5. **④ 各项**：设计方对 6 个问题书面回答后，由主代理逐项裁定去留；③-5（`requires` v1 进否）与 ④-1（互补开关出处）须留痕。

否决理由不成立的底线检查：本审计未发现任何"用复杂机制做确定性代码可完成的事且删除后 E1–E8 崩塌"级别的结构性错误；亦未发现设计偷偷砍能力面（所有降级均显式申报，符合 I6 精神）。故不构成否决。
