## 1. 一句话定位

把 pi 自身状态的全部落盘点从「散落的 node:fs 直调 + proper-lockfile + homedir 推断」收编为四个注入缝——**StorageBackend（同步 fs 面）、ExecutionEnv.FileSystem（异步 fs 面，已存在）、StateLocks（互斥面）、StatePaths（路径解析面）**——node 剖面逐字节零行为变化，browser 剖面以 OPFS 双面实现装配，hosted 剖面复用 node 实现或由宿主注入。

## 2. 签名参数

### 2.1 组装入口（模块 A 冻结版终态对齐）

```ts
// 模块 A 已冻结：HarnessEnv = { env: ExecutionEnv; capabilities: Capabilities }（10-A 终版，types.ts:315 零改动）
// 本模块的存储三件 **不并入 HarnessEnv**，为组装层平行注入缝：
interface HarnessStores {
  storage: StorageBackend;   // 同步面：node:fs 同步调用的逐点替身
  locks: StateLocks;         // 互斥面：proper-lockfile 的接缝
  paths: StatePaths;         // 路径面：getAgentDir() 的接缝
}
// 装配点：coding-agent createAgentSession 选项链（sdk.ts:218-219 一带）与 browser-engine provider；
// 与 HarnessEnv 同点构造、对象分立传递（协商记录见 §11 冲突 3）。
```

能力位消费：本模块**唯一**消费 `capabilities.concurrentFsAccess`（A 冻结三字段集成员；`concurrentFsAccess:false ⇒ locks 整体旁路 no-op` 已写入 10-A §4.1 字段注释）；`shell:false` 只影响工具面（E），`diskExtensions:false` 只影响扩展通道（C），存储面对二者无感。

### 2.2 StorageBackend（同步面）

与现存 node:fs 同步调用**逐一对应**（多一个方法都是死代码，少一个方法都有调用点落空——对照清单见 §8）：

```ts
interface StorageBackend {
  readonly kind: "node-fs" | "opfs" | "host-fs";

  existsSync(path: string): boolean;
  readTextFileSync(path: string): string;
  /** 供 session-manager 头扫描/逐行装载（现 createReadStream+readSync+StringDecoder 流式实现，session-manager.ts:549-560、:601-620） */
  readTextLinesSync(path: string, maxLines?: number): string[];
  /** flag:"wx" = create-exclusive（对应 openSync(p,"wx")，session-manager.ts:1060、:1727） */
  writeTextFileSync(path: string, data: string, opts?: { flag?: "w" | "wx" }): void;
  appendTextFileSync(path: string, data: string): void;
  mkdirSync(path: string, opts?: { recursive?: boolean }): void;
  readdirSync(path: string): Array<{ name: string; isFile: boolean; isDirectory: boolean }>;
  statSync(path: string): { size: number; mtimeMs: number; isFile: boolean; isDirectory: boolean };
  renameSync(source: string, destination: string): void;
  /** node=realpathSync（utils/paths.ts:24-32 现行为）；opfs=字符串规范化（OPFS 无 symlink） */
  canonicalizeSync(path: string): string;
  /** models-store 文件修订号（现 statSync bigint dev:ino:size:mtime:ctime，utils/paths.ts:34-42）；opfs 用 size:mtimeMs 合成 */
  fileRevisionSync?(path: string): string | undefined;
}
```

不进接口：`accessSync/realpathSync`（仅 config.ts 安装方式探测用，node CLI 专属面）、`createReadStream`（被 readTextLinesSync 收编）、Buffer 读写（现存全部状态写入均为 UTF-8 字符串，逐点核实见 §8 清单）。**实现期修订（2026-09-30，StoreB）**：`chmodSync` 以**可选成员**进入 StorageBackend（`chmodSync?(path, mode)`：node 实做真 chmod、OPFS no-op）——auth-storage 收编后需保留 node 0600 语义而又不得直连 node:fs；可选成员不构成死代码（唯一消费方 auth-storage 凭据写入）。`mkdirSync` 选项增 `mode?`（凭据目录 0700 同理，OPFS 忽略）；`readdirSync` 条目增 `isSymbolicLink?`（node 填 dirent 实旗、OPFS 恒缺省——listAll 的 symlink 目录过滤依赖）。

### 2.3 StateLocks（互斥面）

```ts
interface StateLocks {
  /** 返回 release。node=proper-lockfile 包装（三份重复 retry 循环合一）；opfs=同步 no-op */
  lockSync(path: string, opts?: { lockfilePath?: string }): () => void;
  /** auth withLockAsync 专用（现 proper-lockfile lock + stale:30s + signal，auth-storage.ts:120-149） */
  lockAsync(path: string, opts?: { signal?: AbortSignal }): Promise<() => Promise<void>>;
}
```

语义冻结（与 ProfileA capabilities 注释对齐）：`concurrentFsAccess:false ⇒ lockSync/lockAsync 整体 no-op`——JS 单上下文内同步函数天然无交错，no-op 是安全退化而非削弱；同 origin 多 tab 是真实多写者，**v1 不在语义内**（§12 拍板项 2）。no-op 不抛错（契约 §4 原则 2）。**该位 v1 消费者仅 StateLocks 实现选择**（OpfsStateLocks no-op 的唯一依据位；browser 假写单写者）；它是 hosted 宿主申报并发能力的唯一通道（契约 §6「hosted 按宿主能力决定」的落点）——评审门 R3 问 3 裁决保留，不下放。

### 2.4 StatePaths（路径面）

```ts
interface StatePaths {
  /** node=现行 getAgentDir()（config.ts:539-544，env 覆盖 + homedir）；browser=() => "/state/agent" */
  agentDir(): string;
}
```

sessions/models/auth/settings/trust/keybindings/prompts/themes/tools/bin 各派生路径全部经 `join(paths.agentDir(), …)` 得到（config.ts:548-590 现状即如此），不单独进接口——多一个字段就违反契约 I2 精神（死代码）。project 侧 `getProjectConfigDir(cwd, …)`（config.ts，`join(cwd, getProjectConfigDirName(), …)`）不改：cwd 由调用方显式传入，浏览器剖面传工作区虚拟路径。

### 2.5 异步面（零新增）

`JsonlSessionRepoFileSystem`（packages/agent/src/harness/session/jsonl/types.ts:4-19，FileSystem 的 12 方法 Pick 子集）**保持原样**。browser 剖面只补一个实现——**实现期定名 `OpfsFileSystem`**（文档原名 `OpfsExecutionEnv`；落地为完整 `FileSystem` 实现，经 A 冻结的 `HostedExecutionEnv(opfsFs, undefined)` 作 shell 缺席基底，`createBrowserHarnessEnv` 装配，见 10-A §4），装配处：

```ts
new JsonlSessionRepo({ fs: opfsEnv, sessionsRoot: "/state/agent/sessions" })
```

## 3. 行为契约逐步

每步标注「漏了会怎样」。

**步骤 1 · 组装注入与缺省装配契约（与 15-F 对齐，评审门 P1 修订）**。profile provider 构造 `HarnessStores`（平行注入件，不并入 HarnessEnv——§2.1 终版）；browser 剖面 provider 同时确保 OPFS 可用（`navigator.storage.getDirectory()` 探测）并请求持久化（`navigator.storage.persist()`，见 §4）。

**缺省装配契约（B↔F 精确接口）**：
1. `createPiHarness`（packages/browser-engine）在 browser 剖面的**缺省行为 = 持久 OPFS 装配**（主代理裁决，推翻 15-F 原「缺省 inMemory」表述）：装配器内部构造 HarnessStores 三件——`storage = new OpfsStorageBackend()`、`locks = new OpfsStateLocks()`、`paths = { agentDir: () => "/state/agent" }`（实现本体经 packages/agent `./web` 子导出提供，构造权在 F 的装配器，B 供实现与契约）。
2. 15-F §3.3 入口字段缺省值随之反转：`storage.sessionRepo` 缺省 = `new JsonlSessionRepo({ fs: opfsEnv, sessionsRoot: "/state/agent/sessions" })`（非 InMemorySessionRepo）；`settings` 初值写读落 `OpfsSettingsStorage`（`/state/agent/settings.json` + `/workspace/<p>/.pi/settings.json`，字段仍接受 `Partial<Settings>` 初值）；`storage.credentials` OPFS 实现归 B（15-F 待拍板项 4 已留位）；`storage.sqliteFactory` 归 D。
3. F 新增装配字段 **`stores?: StateStores`**（字段名/类型名 F 已定稿回填 15-F §3.3）：缺省 = 上述三件套；下游显式传入 = 整体替换（测试/无持久需求载体可用 inMemory 组合）。**inMemory 自此仅为显式 opt-in，不再是 browser 缺省**。
4. 验收口径统一：11-B §10.3 以「createPiHarness browser 缺省装配」为准；15-F 冒烟（S1-S9）补 OPFS 状态装配步骤后两文档一致（F 已认领补充）。

## 4. 文件与副作用

**物理介质（browser 剖面）**：OPFS = origin 私有、盘上持久（浏览器落盘位置不透明）。MDN 明示：OPFS 与 IndexedDB 同受 quota/eviction 管辖；清除站点数据 = OPFS 全灭；入口 `navigator.storage.getDirectory()`，主线程异步句柄、worker 另有同步句柄（DedicatedWorker 专属）。

**eviction 对策**：组装时调用 `navigator.storage.persist()`（无 prompt 的最佳努力），失败不阻断组装、降级为「可被驱逐」并在 UI 显式提示（对齐 I6「降级必须显式」精神）。配额写满：`QuotaExceededError` → `FileErrorCode "unknown"`（与 node ENOSPC 落点一致，nodejs.ts:97-117 的 case 表无 ENOSPC）→ 由 loop 错误面呈现，不静默。

**文件清单（browser 剖面新建/触碰）**：仅契约 §6 回填布局树内路径。node 剖面：零新文件、零路径变化、零格式变化。

**副作用边界**：本设计不引入任何网络传输、不引入 IndexedDB、不引入 service worker（缓存/离线归 F）；存储 worker 与组装 worker 的关系归 A 的剖面装配（本模块只在 §5 声明同步面的 worker 约束）。

## 7. 错误边界

### 7.1 renameFile 原子写降级策略（逐 API 核实证据链）

**标准现状**：WHATWG File System Standard（2026-03-15 版）三接口全文核实——`FileSystemFileHandle = {getFile, createWritable, createSyncAccessHandle}`（§2.3 IDL 块）、`FileSystemDirectoryHandle = {getFileHandle, getDirectoryHandle, removeEntry, resolve}`（§2.4）、`FileSystemSyncAccessHandle = {read, write, truncate, getSize, flush, close}`（§2.6）。**标准没有任何 rename/move**。

**非标准 `FileSystemFileHandle.move()`**：
- Chromium 官方提案自述：「When launching SyncAccessHandles, we launched `FileSystemFileHandle.move()` for files within the OPFS. Moving of files outside of the OPFS and moving directories at all are not yet supported.」（whatwg/fs `proposals/MovingNonOpfsFiles.md`）——即 move 是随 SyncAccessHandle 发布的 Chromium 扩展、OPFS 文件专属。
- Chrome 102 默认启用（BCD issue mdn/browser-compat-data#20341 引 crbug 40185659 与 chromium commit 链）。
- 引擎分歧：2026-04 实测（同 issue caugner）：`'move' in FileSystemHandle.prototype` Firefox **true** / Chrome false；`'move' in FileSystemFileHandle.prototype` Chrome 与 Firefox 均 true；Chrome 的 DirectoryHandle 无 move。Safari desktop 过 rhashimoto 2023 实测（同 issue）。MDN 已删除 move 页（404）——非标准身份坐实。
- move 的锁语义（提案 Security Considerations）：源/任一持有 exclusive 锁（sync handle 打开中）⇒ move 被拒。

**实现策略（OpfsExecutionEnv.renameFile）**：
1. 首选：`"move" in fileHandle` ⇒ `handle.move(destName)`（本设计 temp 与目标恒同目录，仅需改名形态；move 在 OPFS 内覆盖已存在目标 = 提案明确的目标语义「Emulating POSIX … within the OPFS is a compelling use case」）。
2. 降级（探测为假或 move 拒绝）：读 temp 内容 ⇒ `createWritable(dest)` 写入 ⇒ `close()` ⇒ `removeEntry(temp)`。原子性依据 = spec §2.5 closeAlgorithm 注：「It is expected that this atomically updates the contents of the file on disk being written to」；§2.3.2「typically implemented by writing data to a temporary file, and only replacing … when the writable filestream is closed」。即**浏览器自带的 temp+swap 就是 createWritable 的实现方式**——node 侧自管 `.tmp` 的理由（fs.writeFile 非原子）在 OPFS 不成立。
3. publishFileAtomically（storage.ts:24-46）契约保持：「destination 未提交前不动」由 createWritable close 语义直接满足；「崩溃残留仅 .tmp」由浏览器自管 temp 承担（残留物不再是我们的 `.tmp` 文件，不影响 codec 解析——listDir 过滤 `.jsonl` 后缀，repo.ts:63-67 同构）。

### 7.2 FileError 映射表（DOMException → FileErrorCode，对齐 env/nodejs.ts:97-117 既有 node 侧映射）

| DOMException name | 触发点（spec） | FileErrorCode | node 对位 |
|---|---|---|---|
| NotFoundError | getFile/getFileHandle(create:false)/rename 源缺失 | `not_found` | ENOENT（nodejs.ts:107-108） |
| TypeMismatchError | getFileHandle 撞目录 / getDirectoryHandle 撞文件 | `not_directory` / `is_directory` | ENOTDIR / EISDIR（:112-115） |
| InvalidModificationError | removeEntry 非空目录未递归 | `invalid` | node ENOTEMPTY 落 default ⇒ `unknown`（近似差异，标注） |
| NoModificationAllowedError | 文件锁冲突（createWritable/sync handle 已持锁） | `permission_denied` | 近似（node 无对位；Windows 锁冲突最接近 EPERM） |
| NotAllowedError / SecurityError | 权限/安全拒绝 | `permission_denied` | EACCES/EPERM（:109-111） |
| InvalidStateError | 非 OPFS 上 createSyncAccessHandle、closed handle 复用 | `not_supported` | 无对位（browser 专属情形） |
| NotSupportedError | 引擎能力缺失 | `not_supported` | 无对位 |
| QuotaExceededError | write/truncate 超配额 | `unknown` | ENOSPC 同落 default `unknown`（**一致**） |
| TypeError | 非法文件名 | `invalid` | EINVAL（:116-117） |
| 其余 | — | `unknown` | default |

### 7.3 chmod/0600 语义

auth.json 的 0600（auth-storage.ts:39/:68/:103）目的 = 同机他用户不可读。browser 剖面无该威胁模型（OPFS origin 私有、无同机多用户），`chmodSync` 调用点在 OpfsStorageBackend 为 no-op；hosted 宿主若注入真 fs 则保留原行为。**不做**静默降级提示（无行为差异可提示）。

### 7.4 OPFS 不可用

存储是 harness 存在前提，不属于「协商禁用」范畴（禁用 session 持久化 = 换物种）。OPFS 缺失/被禁 ⇒ **组装期硬错误**，错误信息给出宿主修复指引（如需 HTTPS/secure context）。这与 E7 的 bash 禁用不同类：bash 缺失时 harness 仍成立，存储缺失时不成立。

### 7.5 "wx" TOCTOU

OPFS `getFileHandle(create:true)` 对已存在目标不报错 ⇒ `{flag:"wx"}` 实现为 exists 探测 + 创建两步。竞态窗口仅对跨 tab 写者开放（v1 排除）；单上下文内 sync 队列天然串行。node 实现保持内核级 wx 原子性，零变化。

### 7.6 worker 崩溃

同步面运行于 worker 时（§5 采纳形态），worker 崩溃 ⇒ 组装层重建 worker + 重放内存态（session 内存态 fileEntries 本就是 source of truth，session-manager.ts:928 装载语义）；已 close 的 sync handle 无泄漏（OPFS 锁随上下文终止释放）。

## 11. 发现的冲突
