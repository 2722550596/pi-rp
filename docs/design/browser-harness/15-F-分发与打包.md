## 2. 一句话定位

把 harness（agent loop + 扩展系统 + 工具面 + 存储缝 + LLM 接入）装配为一个可 `npm install` 后在 browser/hosted 剖面直接 ESM import 的独立包 **`packages/browser-engine`**（发布名候选 `@earendil-works/pi-browser`，§13），对外唯一入口 `createPiHarness(options)`；node 剖面不经此包。

**v1 范围宣言（评审门 R1-D2/R3 裁决补录，显式声明非静默缩水）**：

- **v1 交付**：`createPiHarness` browser/hosted 全装配面（S1–S9）、OPFS 缺省持久（含刷新恢复）、工具协商禁用与 bash 互补开关、扩展打包通道、BYOK 直连五家 + 网关形态、CI 守护 A1–A5。
- **v1 已知边界**：
  1. **delegatable subagent preset 的 browser 供给链未归化**——子代理 profile 在 browser 剖面现状为优雅空返回（`extension.ts:44-46` 既有分支）；归化立为 **v1.x 专项，12-C §13.5 持有**，关闭条件 = 子代理 preset 在 browser 剖面可实例化（prepareSubagentConversation→runSubagent 全链），依赖 11-B 的 OPFS 布局资源扫描与 F 的资产打包。
  2. **pi-tui renderer 构建期 stub 为已知临时解**（§5.4 留痕），删除条件 = 正解（renderer sidecar + sideEffects 声明）合入；正解立 v1.x 归属，A5 断言守护 stub 期安全边界。
  3. CDN 附加发布未立项（§13-3 待拍板）；`requires` 扩展能力声明已进 v1（12-C §4.9），未声明 `requires` 的扩展自建 shell 工具调用期失败为残余已知边界（14-E §13-3 合并口径）。

## 3. 签名参数

### 3.1 分发形态候选对照（契约 §9 拍板项）

| 裁决标准 | A. 独立 npm 包（`packages/browser-engine`） | B. coding-agent 的 browser 子导出 | C. 独立构建产物（CDN esm） |
|---|---|---|---|
| **E1 便携性** | ✅ 下游 `npm install @earendil-works/pi-browser`，版本随 monorepo 同发锁定 | ⚠️ 下游被迫安装完整 coding-agent：其 `dependencies` 含 jiti/proper-lockfile/cross-spawn/@silvia-odwyer/photon-node 等纯 Node 件（`packages/coding-agent/package.json` dependencies 实测），浏览器项目安装面被 Node 生态污染；dist 14MB | ⚠️ 免安装，但版本漂移、完整性无锁、无 npm 语义的 peer 协商 |
| **上游同调成本** | ✅ 纯增量新包，上游可整包收编或拒收，fork merge 零冲突 | ❌ 需改上游包的 `exports` 语义与依赖声明；上游 coding-agent `exports` 现仅 `. / ./rpc-entry / ./client`（实测），子导出改造侵入面大 | ⚠️ 构建脚本为本仓私有，上游无对应物，收编需另立 |
| **下游 AIRP 接入摩擦** | ✅ 一个包名一个入口，类型面（d.ts）随包走 | ⚠️ 入口藏于 coding-agent 内，认知负担高；且 `exports` 深导入被封死（实测 `@earendil-works/pi-coding-agent/dist/core/tools/index.js` 解析失败），改造需动上游 exports | ✅ 接入最简但类型/调试体验差 |
| **bundle 排除路径（§5.4）** | ✅ 独立 entry 天然隔离 coding-agent 主 barrel（jiti/interactive 模式永不入包） | ❌ 子导出无法阻止下游或扩展误 import 主出口把 node 依赖拖进浏览器构建 | ✅ 同 A |
| **CI 守护对齐（上游 check-browser-smoke 手法）** | ✅ 新 entry 完全复用上游 metafile 断言手法（§11.1） | ⚠️ 断言对象与上游脚本共享仓库路径，守护边界模糊 | ⚠️ 构建产物断言无法进仓库 CI（产物不在源内） |

**结论（拍板建议）**：**选 A**；C 不作为独立形态，而是 A 的**附加发布产物**（同一 bundle 产物额外投递 CDN esm，发布策略见 §13 待拍板）；**B 否决**，否决理由存档：E1 便携性与排除路径两项硬伤（Node 依赖传染 + 主 barrel 不可隔离）。

契约 §9 的「与上游 browser-smoke 守护模式对齐是硬约束」如何满足：A 形态的构建脚本逐手法复刻 `scripts/check-browser-smoke.mjs`（`platform:"browser"` + `format:"esm"` + metafile 禁止输入断言，实测脚本 :7-103），见 §5.2 与 §11.1。

### 3.2 三剖面 bundle 策略（拍板项）

**结论：browser 与 hosted 共享同一 bundle 产物；node 剖面不消费本 bundle。**

- 依据：契约 E6 口径——剖面差异只允许存在于（a）入口注入的实现（b）能力协商开关值。hosted 与 browser 的全部差异 = `HarnessEnv` 注入物不同（宿主注入真 fs/shell vs OPFS+无 shell）+ capabilities 派生值不同（A 定稿：`hosted.shell=宿主是否注入 Shell` 等）。bundle 代码内零 `if (profile)`。
- **`profile` 字段降级为纯断言（评审门裁决）**：仅用于运行时校验「注入形状与声明剖面一致」（报错可读性）；内部分派与缺省值选择一律只认 `HarnessEnv` 注入形状（capabilities 派生值）——与 10-A 的 negotiate/注入边界衔接。
- node 剖面继续直接消费 `@earendil-works/pi-agent-core` / `@earendil-works/pi-coding-agent` 源码包（现状形态），与上游 browser-smoke 守护的「五入口 browser 可打包性」各司其职：上游守护**可打包性**，本包提供**成品产物**。

### 3.3 入口 API 面：`createPiHarness(options)` 完整草案

下游开发者拿到的 = 一个包、一个工厂函数、一组类型重出口。设计原则：**每个 options 字段都必须映射到一个已存在的注入缝或已冻结的契约形状**；F 不发明新接口语义，只做剖面化预设。

## 4. 行为契约逐步

每步含「漏了会怎样」。

- **S1 剖面校验与能力协商**：校验 `profile ∈ {browser, hosted}` 且**注入形状与声明剖面一致**（profile=纯断言，不一致即组装期报错——报错可读性用途）；冻结 `env.capabilities` 为只读（唯一来源 A 的 `negotiate()`）。后续一切分派只读 capabilities/注入形状，不读 profile。
  漏了 → `typeof process`/UA 嗅探等第二能力来源复活，违反契约 §4 原则 1。
- **S2 ExecutionEnv 绑定**：harness 全部 fs/shell 访问改走 `env.env`；browser 下 `Shell.exec` 恒返回 `ExecutionError("shell_unavailable")`（A 定论；错误码先例 harness/types.ts:158-167、harness/env/nodejs.ts:201,220）。
  漏了 → agent-session.ts:22-23 的 node:fs 用法（建库目录 :238-246 / 读 skill md / 写 session :5728-5752，契约 2.2）在浏览器即崩。

### 5.4 TUI/interactive 组件的 tree-shake 隔离（核实结论 + 排除路径）

**核实结论（实测，颠覆调研单点认知）**：

1. pi-tui 耦合不只在 read.ts：**7 个工具文件全部**静态 import pi-tui 与 interactive 组件——read.ts:4、bash.ts（`Container, Text, truncateToWidth`）、edit.ts（`Box, Container, Spacer, Text`）、find.ts、grep.ts、ls.ts（各 `Text`）、memory-renderers.ts（`Text`）；另有 keybinding-hints（read.ts:9、bash.ts、find.ts、grep.ts、ls.ts）与 `modes/interactive/theme/theme.ts`（read.ts:10、edit.ts、find.ts、grep.ts、ls.ts）。
2. pi-tui 本体是 Node 重依赖包：terminal.ts:1-4（node:fs/module/path/url）+ process.stdout 写入（terminal.ts:174,177,252 等）；native-modifiers.ts:1-3（createRequire + 平台 native prebuilds）；terminal-image.ts:1-4（execSync）；autocomplete.ts:1（child_process）；stdin-buffer.ts:20（events）。
3. **barrel 击穿 tree-shake（实测）**：以 `core/tools/read.ts` 为 entry、platform browser 构建，metafile 显示 **38 个 pi-tui 模块入包**，含 terminal.ts、native-modifiers.ts、terminal-image.ts、autocomplete.ts、stdin-buffer.ts、editor.ts、markdown.ts 等——因为 pi-tui package.json **无 `sideEffects` 声明**（实测 grep 无），esbuild 保守保留 barrel 全部再导出链。结论：指望「只 import Text 就能树掉 terminal」不成立。

**排除路径设计（两阶段）**：

- **短期（本仓私有，bundle 级）**：构建脚本内置 alias 插件，把 `@earendil-works/pi-tui` 与 `…/modes/interactive/*` 在 browser bundle 中替换为 no-op stub 模块（导出同名符号的空组件/恒等函数）。安全性依据：工具文件中这些符号全部只在 renderer/格式化闭包内引用（read.ts:118-267 `formatReadCall`/`formatReadLineRange` 等函数体内），无模块求值期执行；browser 剖面 renderer 永不被宿主调用（渲染由下游 UI 承担）。风险与对策：stub 必须覆盖全部被引符号，漏一个=运行时 undefined 调用——由 §11.1 的 ci-entry 断言「38 模块 0 入包」兜底。
  **留痕（E8，评审门裁决）**：stub 为**已知临时解**；**删除条件 = 正解合入**（renderer sidecar 拆分 + pi-tui `sideEffects` 声明/子导出）。正解立 **v1.x 归属条目**，负责人=上游同调候选/反哺（§6.3 ①②），不阻塞 v1 交付（A5 断言守护其安全边界）。
- **正解（反哺上游候选，归 E/A 协同）**：把 renderer 代码从工具定义模块拆为 sidecar（如 `tools/read.render.ts`），工具核经惰性 accessor 暴露渲染器、宿主按需 import；同时 pi-tui 补 `"sideEffects": false` 或提供子导出（`@earendil-works/pi-tui/components/text`）。这同时消灭 stub 的脆弱性。**E5 归类：这是归化（分离渲染关注点），不是砍除**——node 剖面 interactive 模式行为不变。
- **扩展作者纪律（ExtC 12-C §4.3 规则 4，须写进 browser-engine 作者文档）**：跨剖面扩展对 pi-tui **必须 type-only import**——VIRTUAL_MODULES 含 pi-tui（loader.ts:58），扩展运行时 import pi-tui（渲染器返回 Component）会把本节实测的 38 模块拖进下游 bundle。pi-tui「类型/运行时拆分」列为上游反哺候选（与上条正解同族）。

| 效果 | key 在用户设备，零中转延迟；anthropic 零改动即直连 | key 存服务端；客户端只持短期 authToken | 同②+审计/配额/多租户 |
| key 暴露面 | 用户自己的 key 在浏览器（BYOK 语义下可接受） | key 不下发 ✅ | key 不下发 ✅ |
| CORS | 受各 provider 服务端策略约束（上表） | 无 CORS 问题（代理服务端配 CORS 即可） | 无 |
| 成本 | 平台方零服务器资源（E2 ✅） | **需一个流式代理服务**：协议已定义（POST `{proxyUrl}/api/stream`，Bearer，body `{model, context, options}`，响应 SSE `data: {ProxyAssistantMessageEvent}`，proxy.ts:39-60,166-176），但**全仓无参考服务端实现**（实测 grep `/api/stream` 仅 proxy.ts 一处）——②的「内置」仅指客户端内置 | 自建成本最高 |
| 上游同调 | ✅ 纯上游现状 | ✅ 客户端是上游 API；服务端上游亦未提供 | 上游 pi-messages 协议可承载 |
| 风险 | key 泄漏面=用户设备（BYOK 语义下可接受；CORS 风险已闭案——直连集五家实测全通） | 多一跳运维；无现成 server | 过度设计（对 AIRP 类下游） |

**推荐结论（拍板建议，回写契约 §8）**：

1. **browser 剖面默认 = ① BYOK 直连**。**直连集 = anthropic / openai / google / mistral / openrouter 五家**（2026-09-30 主代理真机 OPTIONS 预检全部通过，契约 §8 已回写）**+ 自定义 baseURL 网关形态**（不受官方 CORS 约束，v1 即支持）；gemini 认证形态约束见表内注记（SDK 默认即正确，零改动）。bedrock/vertex 维持「需网关」，出现即报「该 provider 需网关/代理」错误（§8）。
2. **② streamProxy 为宿主/企业可选项**：`llm.proxyUrl` 一开关切换（§3.3），且**不改**客户端任何代码（上游 API 现成）。不为本仓新建参考服务端（上游未提供、自建属部署文档范畴）——直连集五家已全部实测通过，原「CORS 大面积不通」升级触发条件不再存在。
3. **③ 自建网关 = 部署形态而非本设计产物**：协议即 pi-messages（pi-messages.ts:355-385 裸 fetch Bearer，天然网关友好）；AIRP 类下游已有后端的，推荐走 ③ 复用其网关。
4. 组装规则冻结：`llm.streamFn` > `llm.proxyUrl` > `llm.byok` 三态互斥（§4 S7），缺省无任何一态时报「未配置 LLM 接入」组装错误（§8）。

### 11.1 CI 守护设计（拍板建议）

**结论：本仓独立脚本 `scripts/check-browser-harness.mjs`，不扩展上游 `check-browser-smoke.mjs`。**

理由：① 上游同调最大化的判据是「fork merge 冲突面」——不改上游文件逐字节同调，新脚本纯增量；② 本包断言对象（browser-engine entry）与上游断言对象（agent/ai 五入口）不同源，塞进同一脚本反而模糊守护边界；③ 上游若将来收编 browser-engine 包，本脚本随包整体迁移为上游文件，迁移成本为零（脚本自包含）。

## 12. 发现的冲突

1. **调研事实修正（非契约错误）**：调研称 pi-tui 耦合点为「read.ts:7」单点；实测为 **7 个工具文件全部耦合**（§5.4），且 barrel 击穿 tree-shake（38 模块入包）。影响：模块 E/上游反哺工作量被低估，本档已按实测重列。
2. **契约 2.2「工具全部为独立工厂 + Operations 注入」的隐性前提不成立**：接口缝存在，但**默认实现静态 import node**（read.ts:6 fs/promises、bash.ts:5 child_process、photon 链 read.ts:11→utils/photon.ts:17）——仅靠注入无法通过 browser 构建（§5.5 实测错误清单）。这是对契约事实基座的补充证据，非改道；建议随拍板回写契约 2.2 备注。
3. **session 落盘双实现（StoreB 发现，I4 关联；收编口径已对齐）**：`packages/agent` JsonlSessionRepo（接口驱动）与 `packages/coding-agent/src/core/session-manager.ts`（直连 node:fs 独立实现）并存。收编方案（B 定稿口径）：session-manager 模块本体**留在** browser bundle（AgentSession 构造必选 sessionManager，agent-session.ts:350），其顶层 `import … from "fs"`（session-manager.ts:4-16）整体消失，fs 实现体移入 `./node` 子导出（NodeStorageBackend）。因此本包 CI 断言按**文件级**口径（§11.1 A2 总原则），不按模块级排除；否则 I4 在 browser 剖面形同虚设。
4. **引用精度**：契约/调研引 `rpc-mode.ts:133-137` 为「stdio 传输 Node 专属」证据——`runRpcMode` 定义确在 :133，但 stdio 接线体实际在 :1107-1211（本会话核实）。结论不变，引用应在回写时更新。
