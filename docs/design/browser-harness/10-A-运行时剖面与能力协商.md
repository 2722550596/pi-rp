## 1. 一句话定位

定义 harness 的**唯一能力来源**：一个随环境在组装入口一次性派生的 `Capabilities` 伴生对象 + 三个剖面的组装入口（node/browser/hosted），并给出 BrowserExecutionEnv 骨架与 hosted 宿主注入协议；上游 `ExecutionEnv` 接口保持原样。

## 2. 签名参数

### 2.1 上游不动项（证据）

- `ExecutionEnv extends FileSystem, Shell`（`packages/agent/src/harness/types.ts:315`）：**不增加任何成员**。
- `FileSystem` 18 方法 + `cleanup`（types.ts:231-284）、`ShellExecOptions`（:286）、`Shell`（:304-313）原样。
- `ExecutionErrorCode` 已含 `"shell_unavailable"`（types.ts:158-165；`ExecutionError` 类 :167）；nodejs.ts:201、:220 已在"Windows 无 bash"场景使用该码。
- `NodeExecutionEnv`（`packages/agent/src/harness/env/nodejs.ts:347`，构造 `{ cwd, shellPath?, shellEnv? }` :349-355）：**现状不动**。
- `AgentHarnessOptions`（`packages/agent/src/harness/agent-harness.ts:243-262`）**无 env 字段**——env 经 `toolContext`（`ExecutionToolContext = { env: ExecutionEnv }`，`packages/agent/src/harness/tool-context.ts:4-6`）进入工具执行。本文不改动该结构（理由见 §3 步骤 6）。

### 2.2 新增契约类型（设计形状）

```ts
/** 唯一能力来源。由 negotiate() 在组装入口派生一次，此后只读。 */
export interface Capabilities {
  /** 进程/命令执行能力（真 shell 或宿主等价注入）。
   *  消费者：工具总表 bash 开关（模块 E）、扩展 ctx.exec（types.ts:1573）与 npm-git 安装（模块 C）。 */
  readonly shell: boolean;
  /** 扩展磁盘发现通道（jiti，loader.ts:509-517）可用性。打包通道不受此字段影响。
   *  消费者：模块 C 双通道协商。 */
  readonly diskExtensions: boolean;
  /** 文件系统是否存在本会话之外的并发写者（其他进程/窗口/tab）。
   *  消费者：模块 B 的 proper-lockfile 取舍（契约 §6"hosted 按宿主能力决定"的落点=宿主申报此位）。
   *  语义注记（模块 B 确认）：
   *  (a) false ⇒ 存储类文件锁 MUST 整体旁路（no-op），不是换实现——JS 单上下文内 sync 函数天然无交错，no-op 是安全退化；
   *  (b) browser 的 false 隐含「单 tab 单写者」假设：同 origin 多 tab 经 OPFS 是真实多写者，v1 明确不在此语义内；
   *      升级路径 = Web Locks API（async，与现有 sync withLock 形状不兼容），届时另走拍板，不静默扩义。 */
  readonly concurrentFsAccess: boolean;
}

/** 组装入口的唯一产物：环境 + 能力，二者同源同生命周期。 */
export interface HarnessEnv {
  readonly env: ExecutionEnv;            // 上游接口，原样
  readonly capabilities: Capabilities;   // 唯一能力来源（契约 §4 原则 1）
}
```

### 2.3 三个组装入口（谁 new 谁、配置从哪来）

```ts
// node：薄壳，不改变 createAgentSession 现状
export function createNodeHarnessEnv(options?: { cwd?: string; shellPath?: string; shellEnv?: Record<string,string> }): HarnessEnv;
// 实现：new NodeExecutionEnv({ cwd: options.cwd ?? process.cwd(), ... }) + negotiate

// browser：异步（OPFS 获取是异步）
export async function createBrowserHarnessEnv(options: { root: FileSystemDirectoryHandle; cwd: string }): Promise<BrowserHarnessEnv>;
// root 由入口调用方从 navigator.storage.getDirectory() 及模块 B 的布局解析取得（§12 待 B 定稿）

// hosted：宿主注入
export interface HostContributions {
  fs: FileSystem;              // 必填：宿主真 fs 桥（须遵守 types.ts:225-229 的 never-throw Result 契约）
  shell?: Shell;               // 缺省 ⇒ capabilities.shell = false
  concurrentFsAccess?: boolean; // 缺省 true（保守：宿主不申报就按有并发写者处理）
  cwd: string;
}
export function createHostedHarnessEnv(contributions: HostContributions): HarnessEnv;
```

字面量特化型（仅组装边界可见，供下游静态获知开关，不必运行期再问）：

```ts
export interface NodeHarnessEnv     extends HarnessEnv { capabilities: { shell: true; diskExtensions: true; concurrentFsAccess: true } }
export interface BrowserHarnessEnv  extends HarnessEnv { capabilities: { shell: false; diskExtensions: false; concurrentFsAccess: false } }
// hosted 不特化：能力由宿主注入决定，保持宽型 Capabilities
```

## 3. 行为契约逐步（每步含"漏了会怎样"）

### 步骤 1：negotiate 是唯一构造点

`Capabilities` 只允许在三个入口内由一个纯函数 `negotiate(parts: { shell?: Shell; diskExtensions?: boolean; concurrentFsAccess?: boolean }): Capabilities` 派生；任何其他模块不得 new/字面量拼写 Capabilities。
**漏了会怎样**：出现第二来源（工具自探 `typeof process`、UA 嗅探），契约 §4 原则 1 失守，E6 的"不分叉"退化为口头约定。

### 步骤 2：capabilities 是伴生对象，不是 ExecutionEnv 成员（候选裁定）

三候选评估：

- **候选 1（扩展 ExecutionEnv 加只读能力属性）——推翻**。理由：(a) `ExecutionEnv` 是上游几乎未动的核心接口（契约 §2.4），加成员=核心接口 fork，且把"怎么做事"（exec 方法）与"能不能做"（能力位）焊在一个对象上——`BrowserExecutionEnv.exec` 存在却永远不可用，能力位与方法存在性互为冗余真源，恰是原则 1 要消灭的结构；(b) 一致性维护成本：二者必须人为保持同步；(c) 波及所有 mock/测试 env 字面量。
- **候选 2（伴生对象随环境注入）——采纳**，并以"negotiate 派生 + 只读冻结"强化：能力与实现解耦，`ExecutionEnv` 零改动，能力事实有且只有一个生产者。
- **候选 3a（静态剖面→能力总表）——推翻**：hosted 宿主能力各异，静态表必被宿主覆盖，形成"默认表+覆盖"双源。**候选 3b（从注入件结构派生）——吸收进候选 2**：negotiate 的输入就是注入件本身，能力位=注入件存在性/申报值，结构性防漂移。**候选 3c（env 上烙 profile 判别字段）——推翻**：剖面名进入运行时对象会诱导 harness 内部散落 `if (profile===...)` 分叉，直接违反契约 §3。

**漏了会怎样**：选候选 1 会让上游同调成本翻倍并留下双真源；选 3c 会让 E6 的禁令从"纪律"退化成"靠自觉"。

### 步骤 3：node 入口

`createNodeHarnessEnv` 是 `new NodeExecutionEnv`（nodejs.ts:347）的唯一新调用方；现有 `createAgentSession`（`packages/coding-agent/src/core/sdk.ts:217`）**一行不改**——它继续以 node:fs 直连方式工作（其拆解归模块 B/A 后续边界，见 §9）。配置来源：`cwd` 选项（缺省 `process.cwd()`，同 sdk.ts:218 现状）、可选 `shellPath/shellEnv`（同 NodeExecutionEnv 构造参数 nodejs.ts:349-355）。
**漏了会怎样**：若 node 入口反而改写 createAgentSession，E6"现状不动"前提被自己打破，B 的存储拆解失去稳定基线。

### 步骤 4：browser 入口

`createBrowserHarnessEnv({ root, cwd })`：root 是调用方交入的 `FileSystemDirectoryHandle`（从 `navigator.storage.getDirectory()` 或 B 布局的子树解析而来——子树划分是 B 的 §6 职责，本文只冻结"env 呈现单根 POSIX 风格寻址命名空间"这一约定）；cwd 指向工作区子树根（文件工具的操作对象），由入口调用方从 B 的布局函数取得。OPFS 获取失败（如 Safari 私密模式）**不静默降级**：入口以类型化错误拒绝（`BrowserEnvAcquireError`），由下游决定是否以内存环境重建（那是 B 的存储降级声明范畴，且必须显式）。
**漏了会怎样**：root 获取失败若静默回退内存，会话数据无声蒸发，违反契约 §10 I6 的"降级必须显式"精神；root/cwd 若由 env 自行嗅探，布局知识泄入 A，越界 B 的 §6。

### 步骤 5：hosted 入口

`createHostedHarnessEnv(HostContributions)` 同步派生。宿主要获得**全能力**（等价 node）必须：实现 `FileSystem`（types.ts:231-284 全 18 方法 + cleanup，遵守 never-throw Result 契约）、实现 `Shell`（:304-313）、且 `concurrentFsAccess` 如实申报。只给 fs 不给 shell 的宿主（只读查看器类）得到 `shell:false` 的合法子集。宿主桥的跨语言序列化（Tauri command/postMessage 等）是宿主私有实现，本文只冻结 JS 侧接口形状。

桥接契约注意点（模块 C 实测提示）：扩展侧 `ExecOptions.timeout` 单位为毫秒（`core/exec.ts:15`），而 `ShellExecOptions.timeout` 单位为秒（`harness/types.ts:293-294`）——宿主桥若把 `env.exec` 暴露给扩展 `ctx.exec`，超时单位必须换算，这是 HostContributions 消费方的义务，不属于 capabilities 语义。
**漏了会怎样**：若宿主协议要求"三件套缺一不可"，只读壳被迫伪造 shell；若不要求申报并发位，B 的锁策略在 Electron 多窗口场景失真（契约 §6 hosted 分支落空）。

### 步骤 6：capabilities 的流动位置（三点，R2-B2 会签修订）

1. **组装点**：三入口的调用方（工具总表应用、B 存储装配、D driver 选择、F 入口装配）拿 `HarnessEnv` 整体。
2. **扩展注册边界**：组装点经 `createExtensionRuntime({ capabilities })` 注入运行时，`registerTool` 的 requires 门控（模块 E 提案、C 认领）在注册期据此协商拒绝——`ExtensionContext` 在注册期不存在（`createContext()` 仅事件/工具执行期构造，runner.ts:787，全部调用点为执行期 handler :959/:993/:1035 等），故注册期检查必须以运行时注入为载体；该注入是组装边界的下游延伸，能力值唯一来源仍为 `HarnessEnv.capabilities`，原则 1 不破。
3. **扩展执行上下文**：`ExtensionContext`（`packages/coding-agent/src/core/extensions/types.ts:316`）增加只读 `capabilities` 字段（全量对象零投影，12-C §13.2 拍板），供扩展执行期查询（`exec` types.ts:1573、磁盘通道 API 等）。模块 C 已确认采纳与本文步骤 8 同款的缺席语义：`ctx.exec` 方法保留、协商拒绝返回 `ExecutionError("shell_unavailable")`（否决"方法缺席"——运行时 TypeError 不是协商禁用）；npm-git 安装可用性 = `shell`（必要条件）+ 组装期注入 PackageManager 实现，`shell:true` 不自动等于安装可用，避免第二真源。
4. **不进工具执行上下文与 AgentSession**：`ExecutionToolContext`（tool-context.ts:4-6）与 `AgentSession`/`isAllowedTool`（agent-session.ts:4571-4572）今日均不加/不接触 `capabilities`——内置 7 工具的开关全部发生在注册期（协商禁用，挂点为 excludedToolNames→isAllowedTool，§3 步骤 9；扩展工具的 requires 门控在扩展注册边界，见上第 2 点），工具执行期与 registry 刷新期不存在"按能力分支"的合法消费者；加了就是 I2 意义上的死字段或第二来源。若未来出现真实消费者，走冲突申报加字段（契约 §4.1 已按 R2-B2 显式加码此禁入清单）。

**漏了会怎样**：传进执行上下文 ⇒ 诱导工具内部能力分支（散落分叉）；不传给扩展上下文 ⇒ C 只能嗅探环境，原则 1 破防。

### 步骤 7：剖面名在 harness 内部类型不可见

- `profile` 名（"node"|"browser"|"hosted"）**不出现在**任何 harness 内部函数签名、参数、对象字段中；它只存在于组装入口的函数名与文档。
- harness 内部能问的问题只有 capabilities 查询；三个入口的类型区别仅通过 §2.3 的字面量特化型在**组装边界**表达。
- 契约 §3 的"E6 落地口径（a）入口注入的实现（b）能力协商的开关值"由此获得类型层保障：除这两处外，剖面差异无处存身。
- 边界澄清（非剖面判断的合法存在）：`NodeExecutionEnv` 内部的 `process.platform` win32 分支（nodejs.ts:341 等）是 **node 专属实现内部的平台适配**，该类只在 node 入口被构造，浏览器永远不会 import 它（`./node` 子导出隔离，package.json:13-16），故不违反本步。

**漏了会怎样**：剖面名一旦流入共享层，每个功能都会长出 `if (browser)` 枝，最终必然产出被砍能力的 pi-rp-browser 分支物种——正是消息 4 否定的形态。

### 步骤 8：Browser Shell 缺席的表达（裁定：方法保留 + 恒返回类型化错误）

**结论：接口不分型。** `BrowserExecutionEnv implements ExecutionEnv` 完整实现含 `exec/cleanup`；`exec` 恒同步返回 `err(new ExecutionError("shell_unavailable", "Shell capability not negotiated for browser profile"))`；`cleanup()` 为 no-op。

理由（对照"接口分型"替代方案）：

1. **上游既有语义**：`ExecutionErrorCode.shell_unavailable`（types.ts:158-165 区段）与 nodejs.ts:201、:220（Windows 无 bash）已经确立了"有接口、无实现、返回类型化错误"的库内惯例，browser 只是同一语义的静态化，不是新发明——E5 的"聪明地改掉"。
2. **避免双真源**：接口分型把"无 shell"复制进类型系统，而 `capabilities.shell:false` 已携带该事实；两处必有一处在演进中漂移。伴生对象是唯一事实，exec 错误是防御性深度。
3. **协商禁用使防御永不该触发**：bash 在注册期就不进模型工具列表（E7），会话内没有任何合法路径调用 exec；分型防的是一个不存在的调用路径，付出的却是 tool-context（tool-context.ts:4-6）、prompt-templates、skills、session 存储等全部 ExecutionEnv 消费点的签名翻改，直接冲击上游同调（E6/契约 §2.4）。

**漏了会怎样**：若 exec 抛异常而非返回 Result，违反 types.ts:225-229 契约并可能在扩展误用时炸穿 loop；若接口分型，则如上，签名翻改+双真源。

### 步骤 9：能力→工具开关的唯一映射

总表（契约 §5）中 7 工具的开关依据在本设计下完全派生：

| 工具 | 开关依据 | node | browser | hosted |
|---|---|---|---|---|
| read/write/edit/ls | env 存在（FileSystem 恒在）+ 对应 Operations 注入 | ✅ | ✅（OPFS Operations） | ✅（宿主注入） |
| bash | `capabilities.shell` | ✅ | ❌ 协商禁用 | ✅（宿主注入 shell 时） |
| grep/find | Operations 注入（node 内置 spawn rg/fd；browser 由模块 E 实测决定注入纯 JS OPFS 实现或禁用） | ✅ | ⚠️ 归模块 E | ✅ |

即：**bash 是唯一以 capabilities 字段为开关依据的内置工具**；grep/find 的归化走注入件存在性（fs 恒在，无需新字段）；其余走 env 本身。模块 E 实测后只需改总表 ⚠️ 两格，不产生新能力字段（I2 守恒）。

协商禁用的既有挂点（模块 E 复核、本文独立验证）：开关值的落点不在工具工厂内部，而是组装入口 → `excludedToolNames`（`agent-session.ts:730-731`，配置字段 :373）→ `_refreshToolRegistry` 的 `isAllowedTool` 过滤（:4571-4572，应用于 builtin 注册 :4581/:4584、扩展工具 :4631、活跃名单 :4647）；system prompt 的工具片段/指南自同一 registry 派生——禁用即全链无残留。**该过滤面同时覆盖子代理工具集收窄路径**（`core/subagent/prepare.ts:190-191` 的工具集派生，`DEFAULT_SUBAGENT_TOOLS` 含 bash [转引 ExtC]）——browser 剖面的 bash 禁用必须在子代理会话同样生效，验收测试 §10-5 应含子代理路径。

**hosted 的 grep/find ✅ 语义澄清（模块 E 提请，本文采纳）**：hosted ✅ = 「组装入口注入了 Grep/FindOperations」，**不是**「宿主有 shell 所以工具自动可用」——默认实现直接 `child_process.spawn`（grep.ts:226、find.ts:269），hosted webview JS 上下文没有 child_process；宿主注入了 Shell 只意味着 `env.exec` 可用，不等于 rg/fd 二进制可达。两个 hosted 归化选项：宿主连同一 fs 桥注入 grep/find Operations，或宿主注入的 Shell 足以让默认实现工作（仅当宿主运行时真是 Node 进程而非 webview）。取舍归模块 E 定稿。
**漏了会怎样**：若为 grep/find 增加 `binarySpawn` 之类字段，会造出一个无跨模块消费者的死字段，违反 I2。

### 步骤 10：I2 守恒的执行方式

本文档字段集 = `{ shell, diskExtensions, concurrentFsAccess }`。任何兄弟模块若发现自己需要新位（或发现某位无人消费），**必须**走 hub 广播 + 契约 §4.1 回写，不得私开（私开=第二来源）或留死字段。
**漏了会怎样**：字段集漂移后 I2 机械核验失败，评审门退回。
