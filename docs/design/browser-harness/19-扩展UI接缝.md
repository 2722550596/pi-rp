## 1. 一句话定位

把 Browser/hosted 剖面「扩展已装载但永不绑定」的静默断层——`createPiHarness` 只装配不绑定 ⇒ `session_start` 永不发射、`ctx.ui` 恒为 `noOpUIContext`、`ctx.hasUI` 恒 false、`/opening` 播种器永不触发——收编为**恒执行的扩展绑定装配缝**：`createPiHarness` 在返回前恒执行一次 `session.bindExtensions(...)`（S8.5，C3 裁决），session_start 生命周期事件、opening 播种从此必达；`ui` + `opening` 两个新字段决定绑入的内容（`ui.uiContext` 提供宿主对话框回调即点亮 `ctx.hasUI`，缺省对话框面保持 no-op；`opening` 触发播种）。node 剖面零改动（E6）。并给出与 RPC `extension_ui_request` 逐成员同构的宿主回调形状建议，使 wl 前端 `ExtensionUiHost.svelte` 的消费面零改动复用。

现状断层证据：`packages/browser-engine/src/assemble.ts` 全文无 `bindExtensions` 调用（:232-408 通读核实）；ExtensionRunner 构造即缺省 `noOpUIContext`（`core/extensions/runner.ts:362`）；`bindExtensions` 是 `session_start` 的唯一发射点（`core/agent-session.ts:4278-4282`），node 三模式（interactive/print/rpc）都在装配后绑定，唯独 browser 入口不绑。

绑定规则（2026-09-30 Main 裁决 C3，取代本文原「条件触发」稿）：

```
S8.5 恒执行一次 session.bindExtensions(bindings)   —— browser 装配必走，无「不绑定」分支
bindings.uiContext = options.ui?.uiContext          （缺省 undefined ⇒ runner 保持 noOpUIContext）
bindings.mode      = options.ui?.mode ?? "rpc"      （缺省装配也是 "rpc"，非 print）

```

裁决理由（Main，2026-09-30）：session_start 是 node 不变的生命周期事件，唯一发射点在 `bindExtensions`（agent-session.ts:4280，构造器只存缺省事件 :793；sdk/assemble 现均不调用）；「缺省不绑定」会让宿主 factories 扩展的 session_start 处理器静默死掉——与 E5 反静默目标同类，不允许。E6 约束的是 node 剖面（node 各模式自管绑定，零改动）；空 bindings 的 UI 语义仍是 no-op（noOpUIContext），行为面其余不变。opening 因此不再影响 bindings 组成（其触发经工厂闭包 `getOpeningId`，与绑定与否解耦——但播种依赖恒绑定成立）。原「opening-only 走 print 先例」的精化稿作废。

## 3. 行为契约逐步

**B1 · 恒绑定与缺省 no-op UI 面（C3 裁决，2026-09-30）**。S8.5 **恒执行一次** `bindExtensions`——「无 ui 无 opening」缺省装配也不例外，bindings = `{ uiContext: noOp UIContext, mode: "rpc", onError: 内置记录器 }`。缺省装配的可观测面：`ctx.ui === noOpUIContext`、`ctx.hasUI === false`（runner.ts:535-537、:807-810）、notify/select/confirm/input/editor 仍为 no-op 语义（:256-286）——**但 `session_start`（reason "startup"）发射、用户工厂扩展的生命周期处理器激活、`/opening` 命令注册**。这是 browser 剖面缺省行为对今日的显式变更（session_start 从不发射变为发射），依据：session_start 是 node 不变的生命周期事件，「不绑定 = 处理器静默死掉」正是 E5 要消灭的静默类故障；E6 只约束 node 剖面（node 各模式自管绑定，零改动）。
漏了：保留「缺省不绑定」⇒ 宿主 factories 扩展的 session_start 处理器静默死掉（Main 裁决否决的原稿）；反之若缺省把 mode 定为 "tui" 或注入非 noOp UI ⇒ hasUI 谎报、对话框语义失控。

**B2 · 缺省扩展集并入内建 opening 工厂（仅 opening，对象形 InlineExtension）**。assemble.ts 当前 `extensionFactories` 只包含用户工厂（:311，锚点实现期可能因 A 的字段段位移）。终态：内建在前、用户工厂在后，镜像 node 顺序（`main.ts:595` `[...builtInExtensions, ...用户工厂]`）。`assembleDefaultExtensions` 恒返回 `[createOpeningExtension({ getOpeningId: () => options.opening, configDir: options.configDir ?? ".pi", storage: stores.storage, inline: options.openings })]`；函数本身返回对象形 InlineExtension，不二次包装（DesignReview 条件 3；B4 reject 不在此函数，归 A 资源块）。
llama/memories **不随入**（契约 §3.4 授权本文给建议，建议 = 只入 opening）：
- llama：`extensions/llama/huggingface.ts:1-3` 顶层 `node:fs/promises` + `node:os` homedir，浏览器打包即触 shims 恒空面/直接抛错；其价值面（本地 llama.cpp server）在纯前端剖面也不成立。
- memories：头注自述「TUI mode only (rpc/print intentionally unsupported)」（`extensions/memories/index.ts:2-4`），且 `openStore` 直调 `openMemoryStore(dbPath)`（:29-37）不经 D 的 sqliteFactory 注入缝，浏览器内会落 `node:sqlite` 动态导入；另依赖 `open-browser`/`ensureWebServer`（:15-16，node http server）。三重不兼容。
漏了：opening 不入缺省集 ⇒ 下游必须自己知道要传工厂才能用 opening，E2 的「内建 opening 播种器可用」退化为文档承诺；llama/memories 若一起塞入 ⇒ bundle 拖入 node 面（15-F §5.5 同类实测失败）。

**B3 · opening 触发源参数化（env → 选项）**。现 handler 逐字节：`const id = process.env.PI_OPENING; if (!id) return;`（index.ts:41-42）。终态判定式：`const id = deps.getOpeningId ? deps.getOpeningId() : process.env.PI_OPENING;`——**二选一而非 fallback 叠加**：注入了 `getOpeningId` 就不再读 env（两源叠加会让宿主进程 env 泄漏进 browser 语义，违反契约 §3.4「env 触发通道仅 node」）。node 缺省（无 deps）走 env 分支，逐字节等价（11-B 缺省参数先例）。装载同理：handler 内以 `{ configDir: deps.configDir, storage: deps.storage, inline: deps.inline }` 调 A 的参数化 `loadOpeningPreset(ctx.cwd, id, options)`（现 :47 直调位的参数化替换）；node 无参 deps ⇒ options 全缺省 ⇒ fs/旧项目根分支逐字节等价（等价性承诺在 18 号，回归守卫 T12）。
漏了：直接改读一个全局/新 env ⇒ 剖面判定复活（契约 §4 原则 1 禁第二能力源）；fallback 叠加 ⇒ 同一进程 env 与选项互相干扰，行为不可推理。

**B4a · `configDir` per-harness 项目配置根（17 §3.1/§3.2，Opening 对 A 装载缝的消费）**。`CreatePiHarnessOptions.configDir?: string` 是相对 `cwd` 的配置目录，Browser/hosted 缺省 `.pi`；Browser 装配时将规范化值 `options.configDir ?? ".pi"` 原样传给 opening factory，loader 以 `projectRoot = join(ctx.cwd, configDir)` 后在 `join(projectRoot, "openings")` 查项目级 opening（全局 preset 根 `<agentDir>/prompt-presets` 与此分开）。该值随 harness/session/子代理继承（17 §3.2），不写入 `process.env.PI_PROJECT_CONFIG_DIR`，所以同一 `cwd` 可同时装配不同 IP 的 config roots；SettingsManager 项目设置与 AgentSession 默认 StateStore root 也必须共用该 root（由 A 的 assemble/settings/session seam 负责）。
漏了：用全局 env 或静态 singleton 解析 config root ⇒ 同一 Browser 进程里的两个 IP/harness 串读 openings、settings/state，违反 17 的 per-harness 隔离；忽略 configDir ⇒ wl 的 `--config-dir ipDir` 资产目录不可达。

**B4 · `options.opening` 显式 ID 组装期校验（E5 对齐）**。`options.opening` 未命中合并集 ⇒ createPiHarness 组装期 **reject**，错误信息按契约 §4 格式：请求 ID + 合并集实际 ID（`listOpeningPresets(cwd, { configDir, storage, inline })` 取得）+ 各源摘要（`inline:*` / `opfs:*`）。**归属（A↔B 2026-09-30 定稿）**：reject 机制与错误格式落 A 的资源块（与 preset/`schemas` reject 同一通道、同一格式；位于 stores 装配之后、resourceLoader 构造之前）；本文只持 `opening?` 字段与消费端工厂，不重复实现校验。理由：16 效果清单 E5 是对「显式指定了资源 ID 但资源不存在」的通则，opening ID 同类；node env 通道保持现 `console.warn`（index.ts:49-51），node 零变化。
漏了：只在 session_start 里 warn ⇒ browser 下 console.warn 多数宿主看不见（无终端），又一次「静默回落」；或静默忽略 ⇒ 与 E5 直接冲突。

**B5 · bindExtensions 调用点与时序**。插入位：`const { session } = await createAgentSession(...)`（assemble.ts:357）之后、`execExportTemplateAssets()`（:359）与 PiHarness 返回（:361）之前，编号 **S8.5**（assemble.ts 头注 S1-S9 序列补一步，S9 dispose 不变）；**恒执行，无条件分支**（C3 裁决）。论证链：
1. `createAgentSession` 返回前已 `await session._buildRuntimePromise`（sdk.ts:565-566），`bindExtensions` 首行 `_ensureRuntimeReady()`（agent-session.ts:4248、:822-824）即时决，无二次等待、无竞态窗口。
2. 与 node 三模式完全同时序——都在 `createAgentSession` 完成后绑定：interactive-mode.ts:1784-1787、print-mode.ts:76-79、rpc-mode.ts:477-481。browser 不发明新时序。
3. 此时 `setActivePreset`/`loadSchema`（sdk.ts:570-598）已应用完毕 ⇒ session_start 处理器（含 opening 播种）看到的是 preset/schema 终态的会话，与 node TUI 首帧一致。
漏了：绑定点提前进 S8 之前 ⇒ `_ensureRuntimeReady` 挂起且 preset 播种序倒置；推迟到首次 `prompt()` ⇒ opening 播种晚于宿主首屏渲染，且扩展 session_start 在并发 prompt 下交错，不可复现。

**B6 · session_start 事件语义与 opening 播种就位点**。`bindExtensions` 执行 `_applyExtensionBindings`（:4278→:4338-4356：`runner.setUIContext(this._extensionUIContext, this._extensionMode)` :4339）后，在 `withReloadDeferred` 内发射 `this._sessionStartEvent`（:4280）——browser 未传 `sessionStartEvent` ⇒ 缺省 `{ type: "session_start", reason: "startup" }`（:793）——随后 `extendResourcesFromExtensions("startup")`（:4281）。因此：
- opening 自动播种发生在 `createPiHarness` resolve **之前**：harness 返回时消息/状态已落 session（E2「可达」，不是「参数里有个 ID」）。
- 播种写真实 message entry + `opening` audit entry（index.ts:56 `pi.appendEntry("opening", { name: id, seededAt })`），落账格式见 §5。
- 续档会话：`applyOpeningPreset(preset, { skipIfSeeded: true })`（index.ts:51）的守卫「已有 message entry 则不播」（preset.ts:119-121，函数 :113）保证 restore/reload 不双播——该守卫查 `e.type === "message"`，`opening` audit entry 不触发守卫（语义与 node 一致：audit 不算「已有内容」）。
漏了：若在 bindExtensions 之外另开播种通道 ⇒ 两套 seeding 语义分叉、skipIfSeeded 守卫被绕过；若改守卫判定 ⇒ node 行为漂移（E6）。

**B7 · 组装期 fire-and-forget reload 竞态的两种交错均收敛**。已知：preset 换 memory.dbPath 会触发 `void requestReload()`（sdk.ts:533-559 注释、`_maybeReloadForMemoryDbPathChange`）。S8.5 恒绑定之下，两种交错：
- reload 先完成：S8.5 之前 `_extensionsBound` 尚 false ⇒ `_reloadCore` 的 hasBindings 检查（:5201-5206）不通过 ⇒ reload 不发 session_start；随后 S8.5 在**新 runner**上发 startup（:4280）。终态一次 startup。✓
- reload 后到：S8.5 已绑定（hasBindings true）⇒ reload 在新 runner 上补发 `session_start reason:"reload"`（:5209）+ `extendResourcesFromExtensions("reload")`（:5210）；新 runner 的 UI ctx 已被重建路径的 `_applyExtensionBindings`（:4793）重挂。startup（旧 runner，已 invalidate）+ reload（新 runner）各一次；opening 的 skipIfSeeded 守卫保证已播会话不重播。
两种序终态一致（UI 就位、startup 至少一次、播种至多一次、事件序可解释），无需引擎侧加锁。
漏了：若 bindExtensions 不走 session 存储的 `_extensionUIContext` 而直接改 runner 字段 ⇒ reload 重建 runner 后 UI 丢失（现绑定路径天然免役，:4793 是关键）。

**下游（宿主壳）拿到的新面**：`ui` / `opening` / `configDir` 三个选项；`createHostExtensionUIContext` 工厂；`ExtensionUIContext`/`ExtensionMode`/`RpcExtensionUIRequest`/`RpcExtensionUIResponse` 类型。`configDir` 相对 `cwd`、缺省 `.pi`，允许同 cwd 多 harness 指向不同项目配置根。缺省不传 `ui` = 对话框面仍 no-op（noOpUIContext），但 session_start 生命周期**恒激活**（C3）——要扩展交互必须显式传 `ui`；生命周期事件无需任何选项。

## 7. 错误边界

**E1 · 扩展错误通道（本设计必须补的隐性静默点）**。`emitError` 无监听器时**静默丢弃**（runner.ts:676-680 空 Set 循环），全仓唯一订阅点是 `bindExtensions` 的 `bindings.onError`（agent-session.ts:4353-4355）。现状 browser（永不绑定）⇒ 扩展错误全灭。S8.5 的内部绑定**恒传 onError**：`options.ui?.onError`（U1 采纳的结构化上抛口）?? 内置 `console.error("[pi-extension]", extensionPath, event, error)`（console 在浏览器宿主可用且可见；RPC 模式同权重的 `extension_error` 事件输出，rpc-mode.ts:496-498）。
漏了：只绑 uiContext 不绑 onError ⇒ E4 的「对话框失败」也灭在半路——notify 修好了、错误反而静默，违背 16「不得静默 no-op」的整改精神。

**E2 · 宿主回调异常**。`handlers.request` reject/throw ⇒ 对话框 Promise reject ⇒ 沿扩展 handler 的 try/catch 进 `emitError`（E1 通道）；`handlers.fire` throw ⇒ 工厂边界记录 `console.warn`（fire-and-forget 单程通道不反压扩展事件循环）。request 返回 undefined = cancelled（§2.3），不视为错误。

**E3 · 超时与中止**。`ExtensionUIDialogOptions`（types.ts:105-111）的 `signal`/`timeout` 由工厂在引擎侧兑现：signal 已中止 ⇒ 立即缺省值（rpc-mode.ts:256）；timeout 到期 ⇒ 缺省值（select/input/editor→undefined、confirm→false），宿主迟到的 response 经 Map 未命中自然丢弃（:281-288 的 pendingExtensionRequests 生命周期同构）。

**E4 · `opening` 未命中**。组装期 reject（B4；U6 已裁决 2026-09-30），错误文案含请求 ID / 合并集 ID（可用 opening 清单）/ source 摘要。不允许静默回落；node env 通道维持现 console.warn（node 零变化约束）。

**E5 · 资源发现越界**。绑定后扩展的 `resources_discover` 处理器会经 `extendResourcesFromExtensions`（:4285-4312）把路径注回 resource loader；browser 剖面这些路径的扫描能力取决于 A 的 storage 化扫描器覆盖面（非本文域）。本文只承诺：不阻断绑定、不吞 discover 错误（走 emitError）。

**E6 · theme 求值安全**。`noOpUIContext.theme` 与工厂 `theme` 都引 `modes/interactive/theme/theme.ts` 的 `theme` 对象（runner.ts:8、rpc-mode.ts:31 同源）；browser 构建期该模块被 stub 为 `export const theme: Record<string, unknown> = {}`（`src/stub/interactive.ts:8`，头注明言「浏览器剖面永不求值其字段」）。扩展读 `ctx.ui.theme.xxx` 得 undefined 而非崩溃——与现状（runner 已在打包面内）完全一致，本文零新增风险。

**E7 · 双绑定/迟到绑定**。重复 `bindExtensions` ⇒ session_start 重发（§3 B8，文档级禁令，无运行时守卫——与 node 各模式同水位）；S8.5 之前宿主拿到 session 的窗口不存在（S8.5 与返回同 tick）。

**E8 · `ui.mode:"tui"`**。组装期 reject（B10；U5 已追认 2026-09-30）；文案给出 "rpc" 指引。

## 9. 与现状差异

1. **bindExtensions 从无到有且恒执行**：assemble.ts 现零绑定（通读核实）⇒ S8.5 单点恒绑定（C3 裁决）；ui/opening 只决定绑入内容（uiContext/mode/onError 覆盖 + opening 经工厂闭包触发）。

3. **`ctx.hasUI` 从恒 false 到可选 true**：runner 缺省链不变（noOpUIContext :362），对话框语义仍 opt-in——传 `ui.uiContext` 才 flip（B10 语义表）；缺省 mode 从 runner 内部 "print" 变显式 "rpc"。
4. **内建 opening 工厂首次进 browser 缺省集**：现状 :311 只用户工厂 ⇒ `[内建 opening, ...用户]`（B2）；llama/memories 维持排除并留证据。
5. **opening 触发从 env 单通道到 deps 注入双实现**：node env 路径逐字节保留（无参 default export），browser 走 `options.opening`（B3）；`options.opening` 未命中从「无反馈」变组装期 reject（B4，node env 通道保持 warn）。
