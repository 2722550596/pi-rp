## 1. 一句话定位

把 harness 的 7 个内置工具（`allToolNames` = read/bash/edit/write/grep/find/ls，`packages/coding-agent/src/core/tools/index.ts:85`）在三个剖面上归一：**bash 按能力协商禁用（E7）、grep/find 以纯 JS OPFS 实现实测转正（本模块定案权）、read/write/edit/ls 走现成 Operations 缝注入浏览器实现**，全部差异收敛在组装入口，harness 代码本体零分叉。

## 2. 签名参数（组装入口 API 面）

### 2.1 剖面组装签名（消费 ProfileA 定稿的 HarnessEnv）

```ts
// 组装入口（模块 F 的 browser-engine 包内部；本模块只定义工具面切片）
import type { HarnessEnv } from "pi-agent-core/harness"; // { env: ExecutionEnv; capabilities: Capabilities }（10-A 定稿）
import type { ToolsOptions } from "../core/tools/index.ts";

// browser 剖面工具面：一次调用产出 (a) 全部 Operations 注入 (b) 协商禁用名单
export function createBrowserToolFace(harness: HarnessEnv, workspaceRoot: string): {
  toolsOptions: ToolsOptions;        // read/write/edit/ls/grep/find 的 operations 全部注入
  excludeTools: string[];            // 派生禁用名单，喂给 createAgentSession 的 options.excludeTools
};
```

- 工具面派生规则分两层（都是唯一判断点，harness 内部零分叉）：
  - **协商禁用层（registry）**：`!capabilities.shell → excludeTools 必含 "bash"`；grep/find/ls 不在协商禁用之列（§4 定值 ✅ 注册）；宿主可经同一通道追加（§3 步骤 7 回退）。
  - **激活默认层（initial active set）**：bash 互补开关（§3 步骤 3A）——`capabilities.shell ? [read,bash,edit,write] : [read,edit,write,grep,find,ls]` 作为 grep/find/ls 的默认激活依据；任何显式声明（settings `defaultTools`、SDK `tools`、preset tools、扩展 `setActiveTools`）优先于剖面默认。
- `workspaceRoot`：OPFS 工作区子树根（契约 §6.1 `/workspace/...` 布局，StoreB 11-B 定稿），所有工具路径解析的命名空间。

### 2.2 OPFS Operations 工厂

```ts
export function createOpfsOperations(
  workspaceRoot: string,                     // 虚拟绝对路径前缀（"/workspace/<project>"）
  getDir: (relParts: string[]) => Promise<FileSystemDirectoryHandle>,
): {
  read: ReadOperations; write: WriteOperations; edit: EditOperations; ls: LsOperations;
  grep: GrepOperations & { search: GrepSearchOp };   // search 为 §3 步骤 5 开缝后的新可选成员
  find: FindOperations;
};
```

### 2.3 hosted 剖面签名（同一形状，宿主给实现）

hosted 宿主注入自己的 `{ read, write, edit, ls, grep, find }` Operations（实现桥接宿主真 fs/shell）+ `capabilities = { shell: true, ... }`（宿主申报）。入口派生规则同一份 → bash/grep/find 自动全量恢复。**不需要新 API**：`ToolsOptions`（index.ts:87-95）与 `createAgentSession` 的 `tools/excludeTools`（sdk.ts:303-309）现成。

## 3. 行为契约逐步（每步含"漏了会怎样"）

### 步骤 1：协商禁用挂点定案 = 组装入口，不是工厂内部

**结论：`❌` 的实现挂点是 `createAgentSession(options.excludeTools)` → `AgentSessionConfig.excludedToolNames`（agent-session.ts:730-731）→ `_refreshToolRegistry` 的 `isAllowedTool` 过滤（agent-session.ts:4568-4572），而不是在 `createToolDefinition`/`createCodingTools` 等组合器内部按能力过滤。**

理由（三条，全部源码核实）：

1. **单点已存在且覆盖面正确**。`isAllowedTool`（agent-session.ts:4571-4572）同时过滤 builtin 工具（`_baseToolDefinitions`，4578-4589）与扩展注册工具（`getAllRegisteredTools()`，4574-4583）。在组合器内过滤则只管住 7 个 builtin，扩展同名覆盖/自建工具需要第二套判断——违约契约 §4 原则 3（映射必须一张总表，不允许散落）。
2. **下游全链自动一致**。工具 schema（LLM 可见工具列表）、system prompt 的工具清单与指南，全部从同一个 registry 派生：`_toolPromptSnippets`/`_toolPromptGuidelines` 只从过滤后的 `definitionRegistry` 构建（agent-session.ts:4611-4626）；`_rebuildSystemPrompt` 再按 `validToolNames = toolNames.filter(name => this._toolRegistry.has(name))`（agent-session.ts:1960）取片段。注册层缺席 ⇒ 模型工具列表、prompt 工具行、prompt 指南三处同时无残留（slot-renderers.ts:84-87 `hasBash=false` 时不产出 "Use bash for file operations like ls, rg, find" 指南）。
3. **组合器出口面大且是公共 API**。`createCodingToolDefinitions/createReadOnlyToolDefinitions/createAllToolDefinitions/createCodingTools/createReadOnlyTools/createAllTools` 六个公共出口（index.ts:139-197）+ `createToolDefinition`/`createTool` 两个 switch（index.ts:98-136），共 8 处；SDK 直接消费（index.ts:269-273、sdk.ts:165-169 再导出）。工厂内过滤意味着 8 处各嵌一套能力查询，且 SDK 直连用户（不经 AgentSession）绕不过去；组装入口过滤则是既有参数（`excludeTools`，sdk.ts:305），零新面。

**漏了会怎样**：若改在工厂内过滤，扩展工具与 system prompt 两条链会各自出现第二来源判断；若完全不挂（只在 prompt 层藏 bash），模型仍会收到 bash 工具 schema 并调用，运行时在 browser 报 child_process 不存在——违反契约 §5「❌ = 不注册」与 §4 原则 2。

### 步骤 2：禁用语义全链证明（bash 在 browser 的消失路径）

逐环核实（file:line）：

| 环节 | 机制 | 证据 |
|---|---|---|
| 组装入口 | `options.excludeTools = ["bash"]` → `excludedToolNames` | sdk.ts:305,306,510-512 |
| 会话构造 | `config.excludedToolNames → new Set` | agent-session.ts:731 |
| 注册过滤 | `isAllowedTool` 把 bash 从 builtin 列表剔除 | agent-session.ts:4568-4589 |
| 活跃集 | `_refreshToolRegistry` 产出的 `_toolRegistry` 无 bash；`syncToolSearchState` 收窄活跃名单 | agent-session.ts:4643-4677 |
| LLM 工具列表 | loop 只见活跃 registry | agent-session.ts:1403-1419（`setActiveToolsByName`） |
| system prompt 工具行 | `validToolNames` 过滤 + `_toolPromptSnippets` 无 bash | agent-session.ts:1960-1967 |
| system prompt 指南 | `getToolGuidelines`：`hasBash=false` 不产出 bash 指南 | slot-renderers.ts:75-101 |
| 工具搜索折叠面 | `normalizeDeferrable` 对 7 内置名恒 false（tool-search-policy.ts:27-29），bash 不注册则不进 catalog | agent-session.ts:4610-4626 |

**漏了会怎样**：任一环独立判断（例如 prompt 层单独判）都会出现「prompt 不提 bash 但工具在」的错位，模型照调、运行时炸。

### 步骤 3：bash 开关的唯一依据 = `capabilities.shell`

消费 ProfileA 冻结字段（10-A）：`browser { shell:false }` → 派生必含 `"bash"`；`hosted { shell: 宿主注入 Shell? }` → 宿主注入即自动恢复；`node` 入口不传 excludeTools（现状不变）。契约 §5 bash 行不变。**禁止**任何第二来源（UA 嗅探、`typeof process` 探测）——契约 §4 原则 1。

### 步骤 3A：bash 互补开关（明月 2026-09-30 插话拍板，机制挂点已核实）

**原则**：grep/find/ls 的**默认激活状态 = bash 可用性的反函数**。bash 在场时模型走 bash 万能路线（rg/grep/fd 都是 bash 一行），grep/find/ls 默认不激活；bash 被协商禁用的剖面，bash 替代物默认激活顶上。此机制推广自本仓子代理的既有实践（曾禁 bash + 显式启用 grep/find/ls，prepare.ts:26-27 的七件套是后来补的）。**显式声明（settings `defaultTools`、SDK `options.tools`、preset tools 声明、扩展 `setActiveTools`）永远优先于剖面默认**——两层分离：剖面只定"默认值"，声明随时覆盖。

**机制挂点（源码核实，非新造）**：当前主会话的默认激活链已经就是这个形状——

| 环节 | 事实 | 证据 |
|---|---|---|
| 默认激活名单（SDK 入口） | `defaultActiveToolNames = [read, bash, edit, write, state_update, get_state, subagent_profiles, subagent(, memory...)]`——**grep/find/ls 本就不在默认激活集** | sdk.ts:293-302 |
| settings 覆盖 | `configuredDefaultToolNames = settingsManager.getDefaultTools()`，显式配置优先 | sdk.ts:303、settings-manager.ts:158-159,1540-1543 |
| 初激活推导 | `initialActiveToolNames = (options.tools ?? (noTools ? [] : configured ?? default)).filter(≠excluded)` | sdk.ts:307-309 |
| 注册与激活分离 | registry 恒含 7 件套（createAllToolDefinitions，agent-session.ts:4687）；`activeToolNames` 只决定可见面——**「默认不激活但可显式启用」的机制现状即存在** | agent-session.ts:4749-4757、4645-4677 |
| preset/扩展覆盖 | `applyResourcePolicy(effectiveTools, preset.tools)`（allow/deny）与扩展 `setActiveTools` 均可激活 | prepare.ts:296、agent-session.ts:4414-4417 |
| 会话内 fallback | `_buildRuntime` 无 activeToolNames 时的 default 名单与 SDK 侧重复（agent-session.ts:4749-4751），**两处硬编码需保持同源** | agent-session.ts:4749-4751 |

**归化落点**：互补逻辑只允许写一次——在**组装入口**（sdk.ts 一层，可消费 capabilities 的边界）实现 `bashComplementDefaultTools(capabilities)`：`shell:true → 现状名单（read/bash/edit/write+常驻）`；`shell:false → [read, edit, write, grep, find, ls] + 常驻`。browser 入口经 `initialActiveToolNames`/options.tools 传入；agent-session.ts:4749 的 fallback 名单对齐同源常量（提为共享导出，消双写）。harness 内部（AgentSession 及以下）不出现任何 capability 判断——它只收到一个名单。

**漏了会怎样**：不分离两层，"browser 默认启用 grep/find/ls"会被实现成在工具工厂或 registry 里加 profile 分叉（违约 E6/契约 §3 I1 纪律）；不提共享常量，sdk.ts:293 与 agent-session.ts:4749 两份名单漂移后，直构 AgentSession 的下游与 SDK 下游默认面不一致。

**与子代理的关系**：`DEFAULT_SUBAGENT_TOOLS` 七件套（prepare.ts:26-27）是**显式声明**（子代理机制本来就是 bash 互补开关的 origin），不受此默认值影响；browser 下仍需步骤 8 的排除集透传把 bash 从其名单中协商掉。

### 步骤 4：grep/find browser 定值 ✅（实测定案，数据见 §4）

- **find = ✅（OPFS Operations 注入）**：注入缝**现成零改动**——`customOps.glob` 全绕行 fd（find.ts:168-169 「If custom operations provide glob(), use that instead of fd」），OPFS 实现只需提供 `exists + glob(pattern, searchPath, { ignore, limit })`（FindOperations，find.ts:55-66；ignore 合同 = `["**/node_modules/**","**/.git/**"]` 硬编码于 find.ts:180）。
- **grep = ✅（OPFS Operations 注入）**：注入缝**不完整，需一处 B 级开缝**（步骤 5）。实测典型亚 2s、最坏 10s（2003 文件/16MB），在 tool call 时延预算内（§4 分析）。

### 步骤 5：grep 注入缝开缝设计（唯一必须动 tools 层源码的点）

现状：`GrepOperations = { isDirectory, readFile }`（grep.ts:56-66）只抽象"上下文行读取"，搜索引擎 rg 无条件 spawn（`const rgPath = await ensureTool("rg")`，grep.ts:177；`spawn(rgPath, args, ...)`，grep.ts:226）。对比 find 已有全绕行先例。

开缝方案（对齐 find 语义，可反哺上游）：

```ts
export interface GrepSearchOp {
  /** 全量替代 rg 的搜索；返回 (file, line) 对，早停语义与 limit 一致 */
  (args: { pattern: string; path: string; glob?: string; ignoreCase: boolean; literal: boolean; limit: number; signal?: AbortSignal })
    : Promise<Array<{ filePath: string; lineNumber: number }>>;
}
export interface GrepOperations {
  isDirectory: ...; readFile: ...;
  /** Optional: full search bypass (browser OPFS / SSH delegates). Default: spawn rg. */
  search?: GrepSearchOp;
}
```

- `createGrepToolDefinition` 的 execute 开头（grep.ts:176 前）：`if (customOps?.search) { → 走 search，复用现有 formatBlock/formatGrepResult 渲染 → return }`；未提供则现状逐字不变。
- **漏了会怎样**：不开缝则 browser 的 grep 只能整工具禁用或 fork grep.ts——前者丢能力（违 E6 精神），后者分叉物种（违 I 系列）。
- 反哺上游评估：纯增量可选成员 + 默认路径零改动，符合上游 browser-smoke 守护形态（契约 §2.1），可反哺。

### 步骤 6：read/write/edit/ls 的 OPFS Operations 逐接口映射

现有 Operations 面（全部已核实）与浏览器实现对照：

| 工具 | Operations 接口（现状，file:line） | Node 默认 | browser OPFS 实现 | 语义对齐点 |
|---|---|---|---|---|
| read | `ReadOperations { readFile: (abs) => Promise<Buffer>; access; detectImageMimeType?; stat?; listDirectory? }`（read.ts:77-95） | read.ts:98-107 | `readFile`：`getFile()`→`arrayBuffer()`→Buffer-like（下注）；`access`：getFileHandle 探测（OPFS 无权限位，存在即可读）；`detectImageMimeType`：首 4100 字节魔数嗅探（parity：mime.ts:3 `IMAGE_TYPE_SNIFF_BYTES=4100`）；`stat`：`{ isDirectory: () => handle.kind === "directory" }`；`listDirectory`：`handle.kind` 映射 `ReadDirectoryEntry{name,isDirectory}`（read.ts:72-75） | 目录读取走 listDirectory 分支；缺 stat 时 read.ts 靠 readFile 的 EISDIR 错误降级（read.ts:85-90 注释）——OPFS 实现必须提供 stat，避免靠异常编码目录性 |
| write | `WriteOperations { writeFile(abs, content: string); mkdir(dir) }`（write.ts:31-41） | write.ts:38-41 | `writeFile`：`createWritable()`→write→close（close 即原子替换点，StoreB 11-B §证据链）；`mkdir`：逐级 `getDirectoryHandle(create:true)` | 自动建父目录语义保持（write.ts:216） |
| edit | `EditOperations { readFile: Promise<Buffer>; writeFile(abs, string); access(R_OK\|W_OK) }`（edit.ts:85-98） | edit.ts:94-98 | `readFile` 同 read；`writeFile` 同 write；`access`：存在性探测（无写权限位） | edit.ts:341-342 `buffer.toString("utf-8")` 是 Buffer 专有方法（见下方类型收窄注） |
| ls | `LsOperations { exists; stat: {isDirectory()}; readdir: string[] }`（ls.ts:37-50） | ls.ts:46-50 | `exists`：handle 探测；`stat`：`handle.kind`；`readdir`：`dir.entries()` 的 name 数组 | ls 输出按字母序、目录加 `/` 后缀（ls.ts:108 description），不依赖 mtime——OPFS mtime 不可靠性（11-B §12）不波及 ls |

**Buffer 类型收窄注（上游可反哺的 2 行级改动）**：`ReadOperations.readFile`/`EditOperations.readFile` 声明为 `Promise<Buffer>`（read.ts:79、edit.ts:87），消费点只用了 `buffer.toString("utf-8")`（read.ts:325、edit.ts:342）与图片字节（read.ts:305-306）。归化方案：接口类型放宽为 `Promise<Uint8Array>`，消费点改 `new TextDecoder().decode(buffer)`（Node 语义等价，Buffer extends Uint8Array 故默认实现零改动）；browser 实现直接回 Uint8Array。**若不做此收窄**，browser 实现必须返回带 `toString` 的 Buffer 仿制对象——能跑但把 Node 类型钉死在接口上，违 E5「接口化」精神；本文采收缩窄方案，列为上游同调项。

### 步骤 7：剖面可见性总规则（hosted 恢复机制）

- 总规则：**剖面决定 Operations 的来源与 excludedToolNames 的派生值，其他一切由这两样推导**。
  - `node`：默认 Node Operations（各工具 default*Operations），不传 excludeTools → 全 7 工具。
  - `browser`：OPFS Operations（§2.2）+ `capabilities.shell=false` 派生 `["bash"]` → 6 文件工具。
  - `hosted`：宿主 Operations（桥接宿主 fs/shell）+ 宿主申报 `shell:true` → 全 7 工具。
- hosted 的 grep/find 语义澄清（已与 ProfileA 对齐并留档 10-A）：**✅ = 宿主注入 GrepOperations/FindOperations**。Node 默认实现直接 `child_process.spawn`（grep.ts:5,226；find.ts:4,269），在 hosted 的 webview JS 上下文里没有 child_process——"宿主有 shell"≠"工具自动可用"，宿主必须桥接（如经 Tauri command 调宿主侧 rg/fd，或同样注入 JS 实现）。契约 §5 hosted 列的 ✅ 语义已按此回写。
- 回退通道：任何剖面宿主可用同一 `excludeTools` 通道追加禁用（如超大工作区禁 grep）——机制层统一，无特例代码。

**漏了会怎样**：若 hosted 的 ✅ 被理解成"自动继承 Node 实现"，hosted 包会静默带进 child_process 依赖并在 webview 运行时炸（P5 前提核查的直接坑）。

### 步骤 8：子代理收窄路径（认领自 ExtC 广播，接口点）

`DEFAULT_SUBAGENT_TOOLS` 含全部 7 工具（prepare.ts:26-27）；子代理经 `createAgentSession({ tools: effectiveTools, noTools: "builtin" })` 构造（run.ts:148-157），`effectiveTools = DEFAULT ∪ 扩展工具名`（prepare.ts:189-191）作为 allowlist（sdk.ts:304）。**allowlist 不继承父会话的 excludedToolNames** → browser 剖面父会话禁了 bash、子代理仍拿到 bash。

归化：`run.ts:148` 的 createAgentSession 调用透传父会话的协商禁用集并与 `effectiveTools` 取交。需要 AgentSession 暴露一个只读 accessor（暴露 agent-session.ts:592/731 的 `_excludedToolNames`，一行级 API 增量）；或在 prepare 阶段从父 session 的 HarnessEnv.capabilities 重新派生。两案等价，取 accessor 案（数据单源）。已与 ExtC 对齐（12-C 引用本节）。

**漏了会怎样**：browser 剖面下子代理调用 bash → 运行时 child_process 不存在 → 契约 §4 原则 2 破功（协商禁用漏网）。

### 步骤 9：错误语义对齐（工具层 vs FileSystem 层两条通道）

核实结论：**coding-agent 的 7 个工具不经过 `FileSystem`/`FileError`（`Result<T,FileError>`，types.ts:131-155）通道**。它们的错误通道是：

1. Operations/execute **throw** → agent-loop 统一捕获 → `createErrorToolResult(error.message)` + `isError: true`（agent-loop.ts:739-745、702-704）→ **模型看到的是 message 文本**。
2. 工具自身还会合成文案：grep/find 的 `Path not found: ${searchPath}`（grep.ts:186-190、find.ts:170-172）、read 的 `[Error reading ${path}: ${message}]`（read.ts formatReadFailure，read.ts:290-294）、write 直接抛 ops 错误原文（write.ts:216-231）。

因此 OPFS Operations 的对齐义务是 **throw Error 且 message 措辞与 Node 默认实现对齐**：

| OPFS DOMException | Node 对应 | 抛出措辞（对齐 Node 默认） |
|---|---|---|
| `NotFoundError` | ENOENT | `ENOENT: no such file or directory, ${syscall} '${absPath}'` |
| `TypeMismatchError`（对文件用 getDirectoryHandle 等） | EISDIR/ENOTDIR | `EISDIR: illegal operation on a directory, read` 等 |
| `InvalidModificationError`/quota | ENOSPC/EACCES | 对齐 Node 措辞；结构化映射引用 11-B §7.2（DOMException→FileErrorCode 全表） |
| AbortError | 中止 | `Operation aborted`（与 write.ts:209、grep/find abort 文案一致） |

packages/agent 层（skills/jsonl/memory 走的 `FileSystem`）才用 `Result<FileError{code}>`——那层的 browser 实现是模块 B/宿主桥的职责（11-B 已定），与工具层正交，勿混。

**漏了会怎样**：browser 抛裸 DOMException（"NotFoundError: A requested file or directory..."）给模型——模型收到的错误文本与 Node 剖面措辞不一致，跨剖面 prompt 行为不可复现，且丢失路径上下文。

### 步骤 10：扩展注册工具的边界（协商禁用是否波及扩展）

定案：**波及，且分两层**——

1. **同名覆盖层（现成，零改动）**：`isAllowedTool` 按名字过滤所有注册工具（agent-session.ts:4571-4583）。browser 剖面排除 `"bash"` 时，扩展重新注册的同名 `bash` 工具一并不可见（扩展覆盖 builtin 走同一 `definitionRegistry.set(name, ...)`，agent-session.ts:4585-4588，名字相同命运相同）。这是正确的默认：扩展版 bash 大概率也要 spawn。
2. **能力声明层（已定稿，12-C §4.9）**：`ToolDefinition`（extensions/types.ts:517-569）今天没有能力声明字段；扩展注册一个内部调用 shell 的自建工具（如 "deploy"）无法被协商禁用。定案（ExtC 采纳本模块数组提案，挂点变更）：`ToolDefinition` 增可选 `requires?: Array<"shell" | "diskExtensions" | "concurrentFsAccess">`（**只引用 ProfileA 冻结三键，不新增 capability 字段**，I2 不破），缺席 = 全剖面可用；执行挂点为 **registerTool 注册期拒绝 + 诊断条目**（复用冲突诊断通道，resource-loader.ts:623-631 先例）——capabilities 经组装点 `createExtensionRuntime({ capabilities })` 注入 runtime，**不进 AgentSession**，故本模块 §3 步骤 1-2 的 excludedToolNames→isAllowedTool 链路零改动。扩展作者一份源码三剖面通用（不写 profile 分支），shell 依赖工具在 browser 注册期即被拒并留下诊断。
   - 与同名覆盖层的关系：两机制正交——同名覆盖（isAllowedTool，按名）管 builtin 覆写；`requires`（注册期拒绝，按声明）管扩展自建工具。
   - 默认值语义：不声明 `requires` = 工具自证全剖面可用（纯 JS/纯 API 工具的常态）。
   - 该改动属模块 C 的 API 面，**已定稿落 12-C §4.9**（E 侧消费立场以该节为准；本节保留 E 侧依据与正交性分析）。

**漏了会怎样**：browser 剖面下扩展的 shell 依赖工具进入模型工具列表，调用时炸——与 bash 禁用同构的漏洞，只是藏在扩展里。

### 步骤 11：read 工具图片路径的 browser 降级语义

- 标准类型（png/jpeg/gif/webp，image-process.ts:44-53 的 normalizeSupportedImageMimeType 白名单）**不需要 photon**：normalizeImage 直通（image-process.ts:56-60），browser 可用。
- 非 TUI 必需路径：`autoResizeImages` 走 worker_threads（image-resize.ts:1）+ photon（photon.ts:21-22 createRequire，Node 专属）→ **browser 组装默认 `autoResizeImages: false`**（`autoResizeImages` 本就是 ReadToolOptions/createAllToolDefinitions 选项，agent-session.ts:4688 现成传参）。
- 异常类型降级：photon 加载失败 → `convertImageBytesToPng` null → `processImage ok:false` → read 返回 `[Image omitted: ...]` 文本注记（image-process.ts:84-88、read.ts:307-310）——显式降级非静默（符合 I6 精神）。[推断]：loadPhoton 的 try/catch 返 null 路径（photon.ts:116-131）在 browser import 失败时成立。
- `detectImageMimeType` 由 OPFS ops 提供（首 4100 字节魔数，mime.ts:3 同参）；mime.ts 的判定表建议抽纯函数 `detectSupportedImageMimeTypeFromBytes(bytes)` 供两剖复用（上游同调项，非必须）。

### 步骤 12：model-facing 残留文案的处置（read.ts:351）

全链核查结论：注册层缺席已保证 prompt/schema 无残留（步骤 2），**唯一残留是 read.ts:351 的动态错误文案**：单行超限时建议 `Use bash: sed -n 'N'p ... | head -c ...`——browser 剖面下 bash 不存在，模型照做会失败。

处置（保持剖面逻辑只在注入边界）：`ReadToolOptions` 增可选 `oversizedLineHint?: string`，默认值 = 现文案（Node 剖面逐字不变）；browser/hosted-无-shell 组装传入 bash-free 文案（如 `[Line N is X, exceeds Y limit. The full line cannot be displayed; split the file with edit or use offset/limit around it.]`）。落点：read.ts:348-351 一处 + ReadToolOptions 一成员。同类的 grep/find 错误文案不引用其他工具，无需处理；bash.ts:47 snippet 只在 bash 注册时渲染，无残留。

**漏了会怎样**：模型在 browser 收到"用 bash sed"的指引 → 调用失败重试 → token 浪费 + 行为不可预期。

## 4. grep/find 归化实测（定案数据）

### 4.1 方法

- 三方对照，同一棵合成工作区树（确定性种子生成：src TS / docs MD / json / 带 NUL 的二进制 log / node_modules / .git / 根+.gitignore，gitignore 规则 `node_modules/ dist/ *.log`）：
  1. **browser OPFS 实测**：真实 headless Chromium（Chrome 内核），`navigator.storage.getDirectory()`，`createWritable()` 写树，同一 isomorphic 引擎跑 OPFS 适配器（dir-handle 缓存 + `getFile()` + 首 8KB NUL 嗅探）。
  2. **Node 磁盘对照**：同引擎跑 `node:fs` 适配器（剥离 OPFS 因素的纯 JS 成本）。
  3. **原生基线**：rg/fd 按 pi 工具的真实 spawn 参数跑同一棵磁盘树（grep.ts:220-224 / find.ts:236-268 逐参对齐）。
- 规模：S = 503 文件 / ~4MB，M = 2003 文件 / ~16MB（明月定的百-千量级上探 2 倍）。workload 对齐 pi 工具语义：grep-common（常见词，limit 100 + context 2）、grep-rare（0 命中全扫描，最坏情况）、grep-glob（glob 过滤）、find `*.ts` / full-path / `*.md`（limit 1000）。cold = 建树后首跑，warm = 共享句柄缓存 3 跑取中位。
- 引擎要点（即 14-E 提案的 browser 实现算法）：gitignore 匹配（`ignore@7.0.5` 语义子集，根起逐目录叠加规则）、`.git` 目录跳过（repo 内）、hidden 包含（对齐 rg/fd 的 `--hidden`）、二进制嗅探跳过（对齐 rg）、limit 早停（对齐 rg `killedDueToLimit` 与 find `--max-results`）、find 用 customOps 合同的固定 ignore 表。

### 4.3 读数与定案

1. **find 的成本就是遍历成本**（不读内容）：2000 文件级工作区 warm 280-455ms，比 fd 慢 ~20×但绝对值可忽略 → **browser find = ✅，无争议**。
2. **grep 常见词路径被 limit 早停兜住**：S/M 都在 0.6-1.6s。**最坏情况（罕见词全扫描）M = 10.1s**——这是本定案唯一的痛 点。JS 引擎比 rg 慢 5-100×，但 tool call 的实际体感由 LLM 往返时延（秒级起步）主导；typical 亚 2s、worst 10s（千文件级、16MB 工作区）在 agent 工具预算内。
3. **内存无风险**：≤3MB 增量，无需流式扫描设计（文件级读入 + 行缓存即可，与 Node 版 grep 的 fileCache 同构，grep.ts:212-221）。
4. **对照候选 b（一并禁用）**：禁用省下的是最坏 10s 与 bundle 里 ~几 KB 的 JS 引擎；代价是 browser 模型丧失内容搜索能力，只能 read+ls 盲翻——AIRP 类工作区导航场景（找配置、找定义、找文档）高频受损，且违反 E6「不是砍」的方向。**数据支持保留（候选 a），find 全胜、grep 净收益为正**。
5. **回退阀**：worst-case 对超大工作区（>1 万文件）不可控，故保留宿主经 `excludeTools` 追加禁用 grep 的协商通道（§3 步骤 7）；契约 §5 值仍为 ✅（默认不禁），是否禁属宿主协商，不是代码分叉。
6. 局限声明：headless 桌面级 CPU；移动端预算 ×3-5[推断]；OPFS 句柄开销已含在实测内（dir-handle 缓存 + per-cold 新建 adapter 双口径都测了）；`ignore` 库全语义（如 `**` 中段规则）的成本子集化测量，全量 `ignore@7.0.5` 在 Node 侧 walk 全程 <10ms 量级[推断]，非瓶颈。

## 11. 验收测试

1. **注册表与默认激活面断言**（组装 smoke）：browser 形态 `createAgentSession` 后 registry 无 bash（协商禁用），默认激活集含 grep/find/ls（互补默认）；`excludedToolNames:[]` 的 node 形态 registry = 7 名、默认激活集 = `[read,bash,edit,write+常驻]`（grep/find/ls 注册但默认不激活）；settings `defaultTools:["grep"]` 在 node 可显式激活（覆盖优先断言）。
2. **prompt 残留断言**：browser 形态 `buildSystemPrompt` 产物不含 "bash" 字样（含指南与工具行）；node 形态含。read.ts:351 文案断言双向（默认含 "Use bash:"、browser hint 不含）。
3. **OPFS 行为等价**：同一棵合成树上，JS grep/find 的输出结构（匹配行格式 `path:line: text`、limit 截断通知、find 相对化路径）与 rg/fd 输出经同一 formatter 后逐字段对照（允许顺序差异，须排序归一后比对）。
4. **错误语义**：OPFS 不存在路径的 read/write/edit/ls 错误文本含 `ENOENT` 与路径；与 Node 同场景文本 shape 一致。
5. **子代理继承**：browser 会话 spawn 子代理，其活跃工具集无 bash（步骤 8 回归）。
6. **扩展 requires**：声明 `requires:["shell"]` 的扩展工具在 browser 注册期被拒且产生诊断条目、node 注册成功（12-C §4.9 落地后补；断言走诊断通道而非注册面静默）。
7. 上游守护对齐：新增文件过 `check:browser-smoke` 同款 esbuild `platform:"browser"` 打包（opfs/ 目录零 node: 导入，CI 断言纳入 PackF 的黑名单口径）。

## 12. 发现的冲突（向契约评审申报）

1. **契约 §2.2 表述过强**：「工具全部独立工厂 + Operations 注入（core/tools/index.ts:81-110）」——对 grep **不成立**：GrepOperations 只抽象 isDirectory/readFile，rg spawn 不在 Operations 缝内（grep.ts:56-66,177,226）。本设计以 §3 步骤 5 开缝修复；契约该句建议将来复核时加注（不阻塞，因 P4 的核心主张"工具可条件化注册"仍成立）。
2. **read.ts:351 与契约 §5 禁用语义的隐性冲突**：注册层禁用已冻结为"无残留"，但动态错误文案可绕过 prompt 层清洁性（模型被指引调用已禁用工具）。已在本设计内闭环（步骤 12），申报备案供评审确认处置方向（hint 注入 vs 文案中性化）。
3. **find 双路径语义现状不一致**（非本设计引入）：fd 路径尊重 .gitignore（find.ts:237-241），customOps.glob 路径只硬编码忽略 node_modules/.git（find.ts:180）——即 browser 剖面 find 的 gitignore 语义弱于 node。本设计在 OPFS ops 里补齐 gitignore 匹配（§4.1 引擎要点），但**接口合同本身**未要求 ops 尊重 .gitignore，属 find.ts 的既有语义缝隙，建议 ExtC/上游复核时定夺是否把「尊重 gitignore」写进 FindOperations.glob 合同注释。
