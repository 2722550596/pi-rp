# Pi 浏览器执行会话共享：共同上下文

> 本文是本设计阶段所有模块设计文档的共享契约，所有模块 MUST 遵守；发现错误 MUST 申报冲突并由主设计回写，不得各自改造协议。
> 权威顺序：`00-需求原话.md` 中用户原文及其效果清单 > 本文已核实的现状与范围 > 模块设计文档 > 实现代码。用户原话高于本文；本文的源码事实可以被新证据推翻。

## 1. 效果范围和非目标

唯一产品效果：在 Pi 已能由浏览器本地执行的基础上，让多个参与者能共同参与**同一个 Pi 会话**，同时 Pi-rp 提供平台可复用的通用接缝，而不是要求每个参与者会话都由平台常驻一个 Pi Node 执行进程。

本设计只改进和说明 Pi-rp 自身。平台服务端如何部署、鉴权、授权、保存平台数据、路由浏览器执行者、管理房间成员和实施产品 UI 均不属于 Pi-rp 实现目标。Pi-rp 设计必须说明平台依赖的接口与责任边界，不能把下游平台的实现当作本仓工作。

非目标：多 agent 分布式编排；多个浏览器并发执行或合并同一会话；Pi 托管型房间/认证/授权服务；Amio 或 Worldlines 产品接入实现；参与者 client 另造一套 Pi 会话协议。**按用户 2026-10-01 明确选择，本项目允许并要求研究/设计一套 Pi-rp 通用的浏览器执行者出站通道**；这与已有 PiClient 参与者协议分工不同，不得把两种角色混为一个包或一条消息方向。

## 2. 已核实架构事实（基于当前源码）

### 2.1 远程 Pi 会话已有共享基础

- `packages/protocol/src/schemas.ts:241-256` 定义 `SessionSnapshot`，包括会话 phase/model/revision/transcript/queued steer 等状态；`:291-324` 定义 list/create/attach/detach/prompt/steer/abort/set-model/set-thinking 命令；`:400-410` 定义 server/session snapshot、progress 与 session-removed 事件。
- `packages/server/src/types.ts:36-60` 定义 `PiSessionRuntime` 和 `PiServerService`：runtime 暴露 snapshot/phase、会话命令、事件订阅与 dispose；service 提供持久会话的 list/create/open。
- `packages/server/src/sessions.ts:7-16,42-65,264-309` 中一个 live session 持有多个连接；多个连接可以 attach 同一个 runtime，session snapshot/progress 向已 attach 连接广播，命令要求调用连接已 attach。
- `packages/server/src/listener.ts:1-10` 将 listener 定位为 PiServer 前的授权连接边界。协议握手只有版本协商，未定义应用用户身份或 ACL；平台层负责身份认证和会话授权。
- `packages/client/src/transport.ts:1-18` 提供认证、有序字节通道的 `ByteTransportFactory` 注入。PiClient 是传输无关客户端，并不实现平台网络或认证。
- `packages/client/src/client.ts:381-400` 的 shared/exclusive lease 只在一个 `PiClient` 实例内检查，不是跨设备或跨进程的全局会话所有权。
- Client 断线会使待处理请求失败且清理连接态，不自动重放命令；协议没有事件游标或 progress replay 契约。设计必须明确断线后的现有 snapshot 恢复能保证什么，不得声称已有命令 exactly-once 或事件历史回放。

### 2.2 Browser harness 与 Pi远程服务尚未接通

- `packages/browser-engine/src/assemble.ts:124-184` 定义 `CreatePiHarnessOptions`；`:186-187` 明确写有 “v1 无 remote 入口面”，只重出口 `ByteTransportFactory` 类型作为类型注记；`:189-201` 暴露本地 `AgentSession`、单轮 `prompt`、`abort` 和 `dispose`。
- `createPiHarness` 在 `packages/browser-engine/src/assemble.ts:351-393` 校验浏览器/宿主 profile 并组装本地 stores；它没有创建 `PiServer` 或把 AgentSession 接入远程可调用 runtime。
- `packages/browser-engine/package.json:41-50` 将 `@earendil-works/pi-client` 声明为 peer dependency，但包声明依赖不等于 harness 提供远程执行者通道。
- `packages/coding-agent/src/core/agent-session-runtime.ts:74-90,417-435` 的 `AgentSessionRuntime` 是 coding-agent 内部管理 AgentSession 生命周期/重新创建的对象。它不是 `packages/server/src/types.ts` 的 `PiSessionRuntime`；不得仅凭相似名称假定两者可直接替换。
- `packages/server/src/types.ts:42-60` 的 `PiSessionRuntime` / `PiServerService` 是进程内直接方法调用的 server runtime/service contract；`packages/server/src/sessions.ts:90-117,248-317` 直接调用 runtime、订阅并广播。
- `packages/client/src/connection.ts:101-117,162-204` 的 PiClient 只通过 ByteTransport 向 server 发送 request 并接收响应/事件；`packages/protocol/src/schemas.ts:291-324,391-410` 没有执行者注册/上行 progress/服务端向执行者下发命令的角色。
- 仓内 `PiServerService` 生产实现未在 packages 中找到：`packages/server/README.md:38-40` 要求应用提供具体 service。Pi-rp 提供协议与 runtime proxy/driver 契约；平台实现具体 broker/认证/路由/持久化/部署。

## 3. 共同设计约束

1. **收敛既有参与者协议，单独承载执行者角色**：参与者继续复用 `PiClient` / `pi-protocol` / `PiServerService`；浏览器执行者需要向平台出站连接、接收 runtime 命令、上送 Pi runtime progress/snapshot。是否复用现有 framing/codec，或新增最小 runtime-host messages，由模块设计以证据裁定；不得重复定义已有参与者命令和 transcript 形状。
2. **单一执行者模型**：本阶段一个会话只有一个执行 runtime；多客户端能参与，但全局选择/存活管理、session 与执行者的绑定属于平台服务。Pi-rp 不在多个浏览器间选举或合并状态。
3. **区分会话 transcript 与应用扩展事件**：`pi-protocol` 当前表达标准会话 transcript/progress/命令，不自动等价于所有 `AgentSession` 或 extension 事件。设计必须列明目标效果需要暴露的状态，标明哪些已有契约覆盖、哪些不属于标准远程会话；未有用户证据不得把全部内部事件加入核心 protocol。
4. **身份与授权边界**：Pi transport/server 消费平台提供的已授权连接；Pi-rp 定义执行者 wire contract，但不设计用户、房间、成员权限、host authentication 或凭据策略。
5. **浏览器边界**：纯浏览器只建立 outbound transport；不得假设浏览器可监听公网 socket，也不得为实现效果引入常驻 Node Pi worker。
6. **断线和错误语义诚实**：区分命令响应、session snapshot、live progress 和可恢复事件日志；request ID 不能推导去重/幂等保证。执行者通道若支持 resume/ownership，须显式定义并避免暗示平台级原子性。
7. **依赖/公共 API**：改变导出 API 前先核对所有引用与既有 exports。新增机制必须是跨 Pi 使用方可复用的执行者↔runtime契约，而不是平台 transport/room API 的重复实现。
8. **文档交付**：设计文档须精确标明 Pi 提供的协议/驱动/proxy抽象、平台必需提供的 broker服务、未实现能力与限制；不能把设计提案描述成现状支持。

## 4. 拆分模块的接口问题（供设计，不预先裁定）

- **执行者协议/代理runtime**：平台 broker 如何把经过认证并绑定会话的浏览器执行者通道，映射为 PiServer service 需要的 `PiSessionRuntime`；Pi-rp提供哪些 protocol parser/client/proxy primitives；是否复用 CBOR framing；版本、snapshot bootstrap、progress ordering、命令关联、错误、取消、dispose 和 reconnect语义是什么。
- **浏览器执行端**：如何把 browser-engine 内本地 `AgentSession` 映射到 host command/event contract；model、会话ID、snapshot/transcript映射是否已有可用API；如何确保单一执行和资源生命周期；出站 ByteTransport 由平台注入，auth由平台完成。
- **参与者client**：保留现有 `PiClient` 和 participant wire protocol；标准 WebSocket helper 是否确属 Pi 通用API，仍须按多消费者复用证据论证。
- **恢复/幂等**：执行端掉线时 proxy 对已进行中的 prompt 如何表现；标准 snapshot 能恢复什么；是否足以不增加 event replay 或命令去重协议。

上述问题由模块设计和评审以源码证据论证，已由用户明确选择“Pi-rp定义执行者通道”的范围不再作为待选项；具体通道形状仍开放。
