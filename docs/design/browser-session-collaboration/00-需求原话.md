# 注释（非原文）

## 效果清单

1. Pi 已有浏览器本地运行能力的前提下，支持多人共同参与同一个 Pi 会话。
2. 不要求为每个活跃用户/会话在平台服务器常驻一个 Pi Node 进程；Pi-rp 提供平台可复用的基础设施接缝。
3. 研究并说明 Pi-rp 为达成上述效果需要补齐的能力，形成清楚的设计/使用文档。
4. 工作范围限于 Pi-rp；不实现 Amio、Worldlines 或其他下游平台的服务层、UI、产品权限策略。

## 解法清单（候选，不是已冻结方案）

1. 复用或补强 `@earendil-works/pi-client`、`pi-protocol`、`pi-server`，不要在未核实前新造远程会话协议。
  - 能力前提核验：已有 client/server/protocol 包；PiServer 支持多个连接 attach 同一 live session 并广播 session progress/snapshot（`packages/server/src/sessions.ts:7-15,264-309`）；Client transport 可注入（`packages/client/src/transport.ts:1-18`）。
2. 将 browser-engine 内的本地 `AgentSession` 接到可供平台服务集成的共享会话 runtime/协议接缝。
  - 能力前提核验：browser-engine 当前通过 `createPiHarness()` 创建本地 AgentSession（`packages/browser-engine/src/assemble.ts:124-201,351-393`）；已知入口没有接入 PiClient/PiServer 远程会话协议（`packages/browser-engine/src/assemble.ts:186-201`）。`PiSessionRuntime` 与 `AgentSessionRuntime` 的职责适配关系仍须调查（`packages/server/src/types.ts:42-60`; `packages/coding-agent/src/core/agent-session-runtime.ts:74-90,417-435`）。
3. 核查浏览器端 PiClient transport 和远程协议事件/命令的缺口，只有确认可跨平台复用且确属 Pi 通用职责后才纳入设计。
  - 能力前提核验：ByteTransportFactory 是可注入接口（`packages/client/src/transport.ts:1-18`）；Client 没有为 browser-engine 提供装配路径（`packages/browser-engine/src/assemble.ts:186-201`）。浏览器 WebSocket helper 是否属于 Pi-rp 应提供的通用能力仍待论证。
4. 服务端认证、授权、房间/成员管理、路由、执行者租约、持久化和产品级协作策略由平台实现；Pi-rp 只需定义其依赖的协议/接口契约并写清边界。
  - 能力前提核验：PiServer listener 接收平台预先授权的连接（`packages/server/src/listener.ts:1-10`）；协议握手/请求没有应用用户身份或 ACL 字段（`packages/protocol/src/schemas.ts:354-450`）。

## 用户补充决策（非原文，2026-10-01）

用户在查看“Pi-rp定义执行者通道”选项后选择该方案：Pi-rp 负责定义通用执行者出站通道、浏览器执行端和服务端 proxy/runtime 契约；平台仍负责认证、session/执行者绑定与路由、持久化、部署等服务层。该决策授权 Pi-rp 设计新的执行者通道，但不意味着替平台实现 broker/服务端产品。

决策依据：评审确认 `PiSessionRuntime` 是 PiServer 同进程直接调用的对象（`packages/server/src/types.ts:42-60`; `packages/server/src/sessions.ts:90-117,248-317`）；`PiClient` 的现有消息方向是参与者客户端向服务端发命令（`packages/client/src/connection.ts:101-117,162-204`；`packages/protocol/src/schemas.ts:291-324,391-410`），不含浏览器执行者注册、服务端向浏览器下发运行命令的协议。因此只包一层 `AgentSession -> PiSessionRuntime` 无法建立跨进程闭环。
