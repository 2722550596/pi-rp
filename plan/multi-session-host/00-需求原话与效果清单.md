## 注释（非原文）：已知范围与解释

用户要把 Pi 多 Session 后端能力及可复用的 client/连接能力下沉到 Pi 基础设施，让产品不再重复管理角色进程与会话路由。前端继续连接产品后端；产品是否嵌入 SDK 或连接 Pi Server 是集成决策。100-agent AI Town 是规模动机，不是已经给定的性能数字验收目标。

### 用户拍板（2026-10-02；覆盖下方候选范围）

- 首轮交付为通用 coding-agent Host adapter，不含 Rivet 完整功能迁移；Rivet 保留旧路径，callback/tree protocol 扩展与切换另立范围。
- 首轮正式客户端限现有 Node/TypeScript `PiClient`；不交付第一方 Python SDK、不承诺 NeonRP 可直接接入。
- 默认文件存储仅针对同机本地文件系统设计；用户已明确要求Host root lock支持Linux/macOS/Windows上的本地文件系统；共享/网络文件系统不在v1支持范围，必须fail closed。
- 同一 Host 仅接受产品审核的可信扩展；不承诺隔离任意或不可信 JS 扩展，需隔离者另用 Host/进程。


## 效果清单

1. Pi 的 coding-agent 能在其后端运行时中承载多个独立逻辑 AgentSession，不要求每个角色对应一个 Node/Pi OS 进程。
2. 每个 Session 保持各自的消息/持久化、模型与工具配置、事件、取消和生命周期；不同 Session 之间无消息、状态、事件或 abort 泄漏。
3. 产品能复用 Pi 已提供的多 Session server/protocol/client；不得再造并行协议或要求每个产品手写相同 Pi client/进程管理/事件分流。
4. Pi Host/adapter 可共享适合共享的模型/provider 运行时和请求调度资源，同时确保每个 Session 的扩展、工具权限及运行状态隔离。
5. 产品保留领域对象、权限、角色调度和产品 API；Pi 只管理通用 AgentSession 运行与连接。
6. 后端能控制 Session 与模型请求并发、清理和服务关闭；角色增加时 Pi 进程数不必线性增加。
7. 不强迫所有 Agent 共用一个进程/故障域；隔离要求较高的产品可部署多个 Pi Server/Host。
8. 100-agent 作为候选负载必须通过基准定义 resident-idle 与 concurrent-active 两种场景，不预先许诺具体内存或延迟收益。

## 解法清单（用户提出的候选，不是实现定稿）

1. 在 pi-rp 下沉明确的多 Session 宿主，让多个 coding-agent Session 可由通用 Pi Server 持有；实现应优先检索并复用现有 PiServerService/PiClient/protocol。
   - 现有前提部分满足：`packages/server/src/sessions.ts:39-46,48-146` 已有多 Session LiveSessionManager；`packages/server/src/types.ts:27-60` 已有通用 service/runtime 抽象；`packages/client/README.md:28-34` 明确一条 client connection 可连接多个 sessions。
   - 尚缺的关键前提：当前 `packages/server/README.md:38` 明确该 server 尚无 coding-agent service/adapter；应用仍须自行实现 `PiServerService`。`AgentSessionRuntime` 管一个当前会话并在切换时 teardown，不能直接冒充多 AgentSession Host：`packages/coding-agent/src/core/agent-session-runtime.ts:67-95,171-186,204-231`。
2. 消费方复用标准 Host client/协议，而非手写；本轮不得重新设计与 `@earendil-works/pi-server` / `pi-protocol` / `pi-client` 重复的 transport/session registry。
   - 当前通用协议已有 create/list/attach/detach 与按 sessionId 的命令/事件：`packages/protocol/src/schemas.ts:286-324,391-445`；`PiClient` 有 shared/exclusive lease 与一连接多个 session：`packages/client/src/client.ts:137-177`、README `:28-34`。
   - 未满足：现有 `PiClient` 为 TS/JS client；尚未找到官方 Python client。现有协议是泛化 session snapshot/command 子集，是否覆盖 coding-agent 完整扩展/会话能力须在设计中核对。
3. 让同一 Pi Server 的多个角色共享 Node/Pi runtime，减少 per-role OS process 的基线成本；不得只因 PiServer 自带 LiveSessionManager 就断言 AgentSession 会自动共享 ModelRuntime/RequestGateway。
   - 现有 server 是抽象协议宿主，`PiServerService` 由调用者提供；没有证据证明其当前 runtime adapter 使用 coding-agent AgentSession：`packages/server/README.md:7-40`、`packages/server/src/types.ts:41-60`。
   - Rivet 按角色 ID 懒加载、缓存独立 RpcClient/CLI：`worldlines-rivet/.pi/extensions/handoff.ts:341-342,464-527`。
4. 参考 Rivet 的 Node 多角色和 Amio 的 Writer/角色/side-request 分工；Amio 的浏览器本地模式不作为 Node 子进程成本基线。
5. 现有通用 Server/Protocol/Client 的 identity semantics、运行时映射与生命周期由设计核实；除非确认有缺口，不新增 `hostSessionId` 字段/第二套 RPC。产品前端仍通过自身后端 API。

## 当前已知事实（来源优先于本文件注释）

- `@earendil-works/pi-server` 已是 transport listener + LiveSessionManager 的通用多会话 server；其 `PiServerService` 由应用供给；README 标为 Experimental，明确无 standalone CLI/coding-agent service：`packages/server/README.md:1-40`。
- `@earendil-works/pi-protocol` 有 versioned CBOR framing/schema；server/client 可按 sessionId 路由：`packages/protocol/README.md:1-16`、`packages/server/src/sessions.ts:48-146`。
- `@earendil-works/pi-client` 是 transport-neutral 官方 TS client；一连接可 attach 多 sessions，有 typed SessionLease：`packages/client/README.md:1-42`。
- SDK 可单独创建 coding-agent AgentSession，并注入 ModelRuntime、RequestGateway、ResourceLoader、SessionManager 等：`packages/coding-agent/src/core/sdk.ts:83-180,266-299,422-427`。
- 当前未发现 coding-agent 对 `PiServerService` 的生产实现；PiServer/Client 的“generic multi-session server”与“coding-agent 多 AgentSession 共享装配”是不同层次。
- Amio 的 `completeSideRequest()` 是已有 Session 的 side request，不等于建立一个额外角色/Session：`amio/.pi/extensions/party-shell.ts:180-185,258-265`。
