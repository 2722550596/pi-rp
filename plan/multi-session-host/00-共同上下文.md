- `packages/client` 已有 transport-neutral 官方 `PiClient`；单个连接可 attach 多个 session，支持 create/list/attach、session leases、请求相关性及事件/snapshot 订阅：`packages/client/README.md:1-42`、`packages/client/src/client.ts:51-78,137-207`。因此 MUST NOT 新建一套重复 transport/session protocol 或通用 client。

- `createAgentSession()` 可创建 coding-agent Session，并接受 `modelRuntime`、`requestGateway`、`resourceLoader`、`sessionManager` 等注入：`packages/coding-agent/src/core/sdk.ts:83-180,266-299,422-427`。

- 每个 AgentSession 有独立的 ExtensionRunner、队列/取消状态和 SessionManager；`dispose()` abort 本 Session 的 side requests 并清理监听/资源：`packages/coding-agent/src/core/agent-session.ts:566-614,661-694,1387-1429`。
- `AgentSessionServices` 可注入共享 ModelRuntime，但含 SettingsManager/ResourceLoader；不得假设所有服务可直接跨角色共享：`packages/coding-agent/src/core/agent-session-services.ts:37-92,147-207`。`ResourceLoader.getExtensions()` 返回其所持有的扩展结果对象：`packages/coding-agent/src/core/resource-loader.ts:251-258,323-345`。

- `packages/session-backends/postgres` 与 `sqlite-node` 实现的是 `pi-agent-core` 的 `SessionRepo`，并未替换 coding-agent 仍使用的 JSONL `SessionManager`；Postgres README 明确无 JSONL import/fallback/dual-write：`packages/session-backends/postgres/README.md:1-24`、`packages/session-backends/sqlite-node/README.md:1-22`。设计不得把这些 package 误认为 coding-agent durable session adapter 已存在；若提议迁移存储，必须作为独立范围/成本讨论。

- coding-agent 中还有不可忽略的进程级注册状态：prompt slots 与 macros 使用模块级 Map（`prompt-preset/slot-registry.ts:10-24`、`prompt-preset/macro-engine.ts:8-24`）；Session 的 Memory slot 注册 renderer 会捕获该 Session 的 store（`agent-session.ts:5012-5017,5036-5061`）；不同 Session 可能同名覆盖或跨库读取，不能将“每 Session ExtensionRunner 独立”当成完整隔离证明。
- 扩展 API provider compat registry 也在模块级；`resetApiProviders()` 清空并重建全局 registry（`packages/ai/src/compat.ts:126-158,191-213`），每个 AgentSession reload 会调用它（`agent-session.ts:5339-5342`）。多 Session Host 必须评估这些注册副作用如何隔离/收敛，不能假设共享进程天然安全。用户已确认 v1 仅接受产品审核、符合受支持 Session-scoped API 契约的 trusted extension set；这是一项产品配置/信任边界，不是任意 JS 全局副作用的自动检测或沙箱保证。
- `RequestGateway` 支持 provider 并发闸门与优先级，但 identity.sessionId 当前仍是占位符 `"?"`；SDK 未注入 gateway 时会逐 Session 各建实例：`packages/coding-agent/src/core/request-gateway.ts:12-35,44-48`、`sdk.ts:156-159,422-427`。

- Protocol error codes already include `busy`, and PiServer encodes a caught `PiServerError` with its code/details into the client response: `packages/protocol/src/schemas.ts:269-284`、`packages/server/src/server.ts:380-392`。可复用 `busy` + `details.reason` 表达 Host capacity/root lock busy，不另造协议错误码。
- `proper-lockfile` 已是 coding-agent 直接依赖 (`packages/coding-agent/package.json:45-68`)；Node state store已有 stale/compromised 模式 (`packages/agent/src/harness/env/nodejs-storage.ts:16,19-22,173-194`)，当前 stale threshold 为30s并支持 `onCompromised`。但该库靠 lock mtime判 stale 后删除/重建 lock (`proper-lockfile/lib/lockfile.js:30-67`)，`onCompromised` 是旧owner发现失锁的回调，不构成对 SessionManager 后续写入的原子 fencing。若旧owner被暂停超过 stale 时限后恢复，可能与新owner并写。故 proper-lockfile stale reclaim **不能单独满足 root ownership**；必须选出并验收能阻止 stale/paused owner继续写的机制（例如进程死亡自动释放、无法被超时窃取的同机 OS 锁，或每次写入强制检查的 fencing-capable storage）；机制确定前，crash recovery / file-root exclusivity 为实现阻断项。
- Rivet 的角色池按角色 ID 缓存 RpcClient，按需启动 Pi CLI：`worldlines-rivet/.pi/extensions/handoff.ts:341-342,464-527`。这是本项目最直接的 Node 多角色消费场景；Amio 浏览器 harness 仅作 Agent 能力与调用频率参考，不作为 Node 进程成本基线。

## 2. 目标与边界

目标是让 pi-rp 的 coding-agent 能够复用既有多会话 server/client 栈：**提供 coding-agent-backed PiServerService/PiSessionRuntime（或经证据证明更合适的等价适配），并将共享运行时与逐 Session 状态安全装配起来**。下游产品不再各自实现每角色 Pi 子进程管理、AgentSession registry 和同类 Pi RPC client。

现有协议/client/server 是优先收敛的基础：

- 进程外：复用 `@earendil-works/pi-server`、`@earendil-works/pi-protocol`、`@earendil-works/pi-client`；若某个 coding-agent 能力确实未被协议覆盖，先说明效果缺口，再提出最小扩展，不得另造并行 transport/session 协议。
- 进程内：coding-agent 适配层可被 Node 应用嵌入；是否需要第二种公开 SDK Host façade 由设计论证，不能为重复抽象而抽象。
- 产品前端继续使用产品自己的 HTTP/WebSocket/API 连后端；无需直接依赖 Pi 协议。

**用户已拍板的 v1 范围：**首轮仅交付通用 coding-agent Host adapter，复用 Node/TypeScript `PiClient`；Rivet 暂留旧路径，`context_request`/`orchestration_request`/tree 操作及全功能切换不在本轮，1/10/25/50/100-role 测量只验证 Host adapter/topology，不等同 Rivet migration。首轮不交付 Python SDK、不承诺 NeonRP 直接接入。默认文件 store 只支持同机本地持久文件系统，但 Host lock 必须支持 Linux/macOS/Windows 上受验证的本地文件系统；共享/网络、易失临时卷和unknown FS不支持且必须fail closed。同一进程中的多 Session 扩展限产品审核的 trusted 扩展；未知/不可信扩展须另用 Host/进程。

职责边界：

- Pi Server/adapter 管理通用 AgentSession、可共享运行时、每 Session 生命周期/事件隔离以及所需请求并发。
- 产品仍负责世界/角色/用户领域状态、业务权限、角色调度和将产品实体映射到 Pi server session；Pi 不取代产品后端。
- Host 不代替 TUI/Web UI、产品 API、世界模拟、跨产品身份/计费/存储。
- 一组 session 可以在一个 Pi Server 进程中共享基础设施；消费者仍可部署多个 Pi Server 保持独立故障域。单进程多 Session 不意味着所有产品/角色强制共用一个进程。

## 3. 共享术语与标识契约

- **PiServer sessionId**：现有 Pi protocol/server 的规范 durable-session ID，作为该 server/client 的路由标识。PiServer 在 create 时分配 ID，要求 `PiServerService` 原样持久化；runtime snapshot ID 必须与之吻合：`packages/server/src/types.ts:27-34`、`packages/server/src/sessions.ts:56-65,236-263,303-313`。
- **coding-agent SessionManager ID / session file**：Pi coding-agent 内部持久化会话树身份。它与 PiServer sessionId 可以在严格证明生命周期、fork/new/switch/import 语义相容后映射为同一值；否则 adapter MUST 保留明确映射。不得因两个字段都叫 sessionId 就默认为语义相同，也不得在没有效果需求时新增第二个公开 `hostSessionId` 字段。
- **protocol request `id` / extension requestId**：一条 command/response 或异步 extension request 的相关性标识，不是 session identity。
- 当前协议的 sessionId 是独立 server/session 路由 identity；它不意味着当前 PiServer 已经持有 coding-agent AgentSession。设计必须落清楚 server ID ↔ coding-agent SessionManager/file ↔ AgentSession lifetime 的 mapping、所有权和恢复语义。

现有 PiClient/PiServer 已为 session-scoped request、response、event 携带 session identity。设计应沿用现有 envelope 和 session 归属；只有证明 coding-agent 的具体事件/扩展回调无法用现有标准表达时，才列 protocol delta。

## 4. 共享与隔离不变量

MUST 每个 PiServer live Session / coding-agent runtime 独立拥有：

- Agent 和消息上下文、SessionManager/持久化树、会话级队列与运行/abort 状态；
- ExtensionRunner、扩展上下文、工具权限、事件订阅和 side-request 生命周期；
- Session 专属配置/提示/模型/工具选择（允许继承 Host 默认值，但不得隐式串写角色配置）；
- 其 PiServer durable session identity 到内部 SessionManager 文件/ID 的稳定映射。

MAY 在同一 coding-agent service/Host 级共享经核实安全的基础设施：

- `ModelRuntime`、provider/auth/model registry；
- `RequestGateway`，实现 Host 内所有 AgentSession 的 provider 并发控制；
- 只读/不可变资源、连接池等。

SHOULD 复用共享服务；不得把 `ResourceLoader` 可变 extension runtime、Session 的 ExtensionRunner/context、SessionManager 或 abort controller 无条件共享。不同 Session 的 provider/extension registration MUST 有一次性注册、命名隔离或明确冲突语义；不得每建一个角色就隐式污染共享 ModelRuntime。

现有代码还存在必须在设计中逐项认领的全局可变注册表：`registerSlot()`/`registerMacro()` 写进模块级 Map；Memory slots 的 renderer 捕获当前 session store；`resetApiProviders()` 会清空重置 process-global API provider registry，且某个 AgentSession reload 会触发它。共享 Host 若运行多种 preset/角色或不同 memory DB，必须设计 per-session scope/keying、受限能力或确定性消除这些全局副作用，并给出交叉污染/并发 reload 验收。不能把它标成“将来优化”后仍声称不同 Session 的 prompt/provider 隔离已达标；事实路径在 §1。

PiServer 已对同一 durable session 的 acquire 做单飞并校验 runtime snapshot id；coding-agent adapter 仍需对 session 文件所有权/重复打开负责：同一持久化树在同一进程内最多有一个可写 runtime，Session A abort/error/dispose 不得取消、关闭或改写 Session B。

- **v1 不暴露**同一 PiServer Session 内的 new/fork/switch/import replacement；一 durable protocol ID 始终对应创建时的一个 coding-agent session/file。`ExtensionRunner.bindCommandContext()` 未绑定时这些 handler 会以 `{ cancelled: false }` 成功形状静默返回，而不是拒绝（`packages/coding-agent/src/core/extensions/runner.ts:342-345,484-502`）；因此 adapter MUST 明确绑定拒绝这些 replacement 的 handler，或证明相应扩展面不可达，禁止使用静默 no-op 伪装成功。若后续由实际消费者要求开放 replacement，必须加入目标路径预留/owner claim：在当前 Session teardown 或任何目标文件写入之前取得；claim 失败必须保留当前可用 Session 且不得改目标文件。当前 `AgentSessionRuntime` 不完全提供该原语，未来设计须处理 switch/import 在 teardown 前准备目标、new 先分配目标 manager、fork 在返回前可能已写目标的差异。证据：`packages/coding-agent/src/core/agent-session-runtime.ts:204-231,234-267,270-339,369-403`、`core/session-manager.ts:1474-1552`。若无法安全禁用间接 replacement，则 adapter 不得加载/开放相应能力。

- coding-agent PiServer assembly MUST require a positive finite `maxActiveRuntimes` bound (counts in-memory live AgentSession/PiSessionRuntime, not durable catalog records) and finite positive provider request limits. Saturation rejects new `createSession/openSession` with existing protocol `busy` and `details.reason = "active_runtime_limit"`, before any new durable catalog/JSONL write; no implicit queue or eviction of attached sessions. Session detach + runtime disposal releases one active slot; an existing durable ID can then reopen. These limits are separate. Every effective `RequestGateway` provider limit, including explicit per-provider overrides and the fallback default, MUST be positive finite; `0`, negative, `Infinity`, `NaN`, and omitted limits are not valid Host configuration because they remove the promised concurrency bound.
- `sessionStorageDir` default root MUST 由可证明排他的root ownership机制保护，并在listeners accept requests前取得。用户已明确v1要求同机持久本地文件系统的Linux/macOS/Windows均可用；共享/网络、易失临时卷（如tmpfs）和无法识别的FS MUST fail closed。实现使用进程生命周期SQLite排他写事务：必须在 `BEGIN EXCLUSIVE` 后执行实际未提交写并持有至close/进程死亡，不得仅BEGIN空事务，也不得用stale mtime reclaim。OS/FS识别须按Linux mountinfo、macOS本地卷mount信息、Windows volume/drive type分别验证；不得将路径存在/可写误当本地锁正确。第二个PiServer同root须在暴露listener/触碰catalog/session records前本地失败，typed `busy/root_owned`；正常close在PiServer及sessions退出后释放。设计门已通过，但上线支持三平台前必须分别验证同平台SQLite竞争、暂停旧owner不得被接管、SIGKILL自动释放/重开以及远程/unknown/易失FS拒绝。
- PiServer close MUST close all owned live runtimes; coding-agent assembly MUST provide an owner lifecycle handle whose `close()` awaits `PiServer.close()` and all session runtime disposals before releasing its own Host coordinator/registrations/gateway/storage resources. A caller-injected catalog/store remains caller-owned; the built-in store, if selected, is owned by the assembly. Direct low-level PiServer + service users must follow the same ordering because PiServer has no service close hook. Current `ModelRuntime` has no public dispose API, so do not promise to close an unexposed transport pool; the owner may release its own references.

## 5. Server/Client 集成边界

目标是复用现有 Pi client/server，而非让每产品再手写一套。设计 MUST 明确并区分：

1. PiServer/PiServerService：server 的通用生命周期、协议路由与 session runtime 抽象；
2. coding-agent adapter/service：将 `PiServerService` 的 create/open/list 和 `PiSessionRuntime` 能力映射到独立 AgentSession，管理共享 ModelRuntime/RequestGateway 与 session-owned resources；
3. `PiClient`/protocol transport：消费方的第一方客户端与已定义 wire contract；
4. 产品自己的前端↔产品后端 HTTP/WebSocket/API。

- `packages/server` README 标 experimental；设计需评估正式复用对其 API stability、服务装配与 release 的要求。`PiClient` 当前 TypeScript/JS package transport-neutral，存在 Unix adapter；源码没有证据显示已提供第一方 Python client。用户已拍板首轮不交付 Python SDK/不保证 NeonRP 可直接接入；未来 Python 消费者若纳入范围，需提供第一方 client，不能让每个产品从头逆向 CBOR/schema。协议是语言无关基础，不等于Python SDK已存在。
建议coding-agent包公开`createCodingAgentPiServer(options): Promise<CodingAgentPiServerHandle>`，组合现有PiServer与coding-agent-backed `PiServerService`；调用方不注入store时 MUST 使用以`sessionStorageDir`为根的第一方JSONL兼容文件catalog，避免Node消费方各自实现durable ID→path metadata。v1一个PiServer进程独占一个storage root；产品可注入自有catalog，但业务实体→PiServer ID映射仍由产品负责。当前工作树已实现此接口、默认store与root ownership；真实验证状态见40文档。

不要默认把 legacy `packages/coding-agent/src/modes/rpc/{rpc-mode,rpc-client,rpc-types}.ts` 作为新 Host 的 route/server/client 复用面：它当前是单活跃 `AgentSessionRuntime` 的 stdio JSONL RPC（`rpc-mode.ts:372-380,498-562,592-617`; `rpc-types.ts:21-75`），和现有 PiServer CBOR session protocol 是两条不同栈。若要让旧 CLI RPC 也承载 PiServer Host，需另外证明为何必须，不把它变为前置条件。

## 6. 验收必须覆盖的行为

完整验收设计至少包含以下类别；各模块可扩展，不得删减：

- 一个 `PiClient` connection attach/创建多个 coding-agent runtime 时，消息、工具执行、session file、extension context、state/event 均严格隔离。
- V1 fixed protocol ID/file mapping survives close/reopen and server restart; same-session new/fork/switch/import are not exposed.
- 一个 Session abort/dispose/error 不影响另一个；PiServer close 对全部自有运行时完整清理。
- 同一 durable ID 的重复/并发 create/open 不造成多个 runtime 同时写同一 session tree；符合现有 PiServer acquire/lease semantics。
- Active runtime cap is an admission limit, not silent eviction: filling `maxActiveRuntimes` causes next create/open to return `busy` before persistence, doesn't disturb attached sessions, and detaching/disposal allows reopen; enforce no orphan metadata/file on rejected create.
- 共享 RequestGateway 的 provider 限流确实约束同一 adapter/Host 内所有 Session；request identity 不再是无信息占位值，队列/优先级不会让主要角色无限饥饿。
- 产品可通过现有 `PiClient` 复用 server，不需要复制 Pi protocol/client/角色级 process manager；本轮正式支持消费方为 Node/TypeScript；产品领域逻辑仍由产品实现。Rivet 是首个迁移候选但本轮暂留 legacy path；完整 Rivet cutover 需另立范围。
- 角色规模增加时 Pi 子进程数不必按角色数线性增长；分别记录 1/10/25/50/100 roles 的 resident-idle 与 concurrent-active 负载下的进程数、RSS/heap、创建/启动成本、event loop lag、排队和模型请求时延。该基准只用于通用 Host adapter/topology 验证，不构成性能承诺或 Rivet 全功能迁移验收；100-agent 仍是候选基准，不是已测性能承诺。
- File-root exclusivity acceptance uses two host processes and必须覆盖paused/stale owner split-brain: live/paused owner阻止第二writer；进程死亡后新PiServer可安全恢复同一session；任何旧owner在ownership失效后恢复都不得写catalog/JSONL。若使用不可窃取的进程生命周期OS锁，验证pause期间拒绝竞争者、kill后自动释放；若用fencing storage，验证每次catalog及SessionManager JSONL write都强制检查有效fencing token。未选并证明其中一种机制前，该验收仍为阻断项。Lock compromise in a still-live host is fail-closed.
- 需要独立故障域的角色仍可运行在独立 PiServer/进程。

## 7. 既有方案冲突与收敛要求

1. `plan/multi-agent-infrastructure.md:15-18,40-46,111-133` 判断 daemon/单 Host 多会话“无消费者，不做”，并以 Rivet 进程簇为生产形态。本次用户已明确要求将多 Session/客户端复用下沉到 Pi，Rivet 大量角色是目标消费者，故“无消费者”前提已变。新设计必须保留异构角色进程隔离的价值，同时调查是否用现有 `PiServer` + coding-agent adapter 满足同世界多角色；不能照旧计划否决，也不能假定所有 session 强制同进程。
