## 2. pico 去留决策

### 2.1 结论:删除 `vendor/pico.min.css` 与 `pico.LICENSE`,自建 token + reset

00-context §1 给的倾向是"去掉,自建 token;若保留必须说明理由"。本节给出的是**论证**,不是执行默认。

### 2.2 为什么"保留 pico + 写覆盖"是坏选项

1. **本次重设计的本质是换设计语言,而 pico 的产出物就是设计语言本身。** 保留它意味着每个视觉决定都要先问"pico 默认是什么",再写一条覆盖。现状 app.css 已经证明了这条路的天花板:257 行里相当比例是"反 pico"补丁——横向滚动 hack(app.css:10-18,抵消 pico nav 负 margin 的 10px 溢出)、caret/↗ 按钮还原(43-49,抵消 pico 全局按钮样式)、`#mw-db` 尺寸补丁(244-248)、nav select 首帧假控件补丁。重写后这些补丁的目标(pico 的行为)消失,补丁也必须消失,等于重写但继续背 83KB 包袱。
2. **双主题体系必然漂移。** 52 处 `var(--pico-*)` 意味着我们的颜色语义寄生于 pico 的变量集;设计系统要的语义(面层/边框/语义色/域色板)pico 大半没有(琥珀警示三值就是被迫自建的先例,app.css:7),最终会形成"pico 变量 + 自建变量"两套并行,auto/light/dark 三态 × 两套 = 六条覆盖路径,和 app.css:72-76 注释里已经踩过的"漏一条路径就错配"问题同源。
3. **首帧与控件控制权。** 零构建下 `color-scheme`、表单控件暗色外观、滚动条、`::backdrop` 全部要和 pico 的选择器打架。拿到完全控制权后这些都是十几行的事(§6)。
4. **83KB 常驻下载换 0 收益。** 被消费子集(§1.5)折算约 150-180 行 CSS;自建后全站样式总量预计 700-900 行(可读、带注释),比 83KB minified 黑盒小一个数量级且可维护。

## 3. 文件架构

```
assets/
  tokens.css    # 新增:全部 --mw-* 变量(light 在 :root,dark 在双轨选择器),~130 行
  app.css       # 重写:reset/base + 组件层,只准引用 var(--mw-*),禁止任何第三方变量
  index.html    # 调整:去 pico link、加 boot script、加 tokens link、nav 类名(§7.2)
  app.js        # 主题代码零改动;仅 §8 的类名字符串替换
  vendor/       # 整目录删除(pico.min.css + pico.LICENSE)
```

- **为什么拆 tokens.css**:暗色 token 块因选择器双轨必须字面写两份(§5.1),独立文件让它自成一个"调色板章节",改色不翻 700 行组件规则;实现时也方便对 token 表逐格校对。
- **为什么不用 `@import`**:多一次串行请求且失败模式差;index.html 两个 `<link>` 即可,顺序 `tokens.css` → `app.css`(var 解析虽与顺序无关,但 reset→组件的 cascade 顺序必须保证)。
- 注释纪律:沿用现状 app.css 的 ⭐ 惯例——凡是"看起来多余但实际承重"的规则(min-width:0、flex:0 1 auto、双轨暗色)必须写为什么;这是这份 CSS 六个月后还能改的前提。

## 5. 主题机制

### 5.1 选择器策略(三态;与现有 applyTheme 协议逐字兼容)

```css
/* tokens.css —— light 是默认(:root),dark 走双轨。
   ⚠️ 双轨是硬要求,不是风格:app.js:82-84 的 applyTheme 在 auto 时"移除"
   data-theme(交给 prefers-color-scheme),在 light/dark 时设属性值。
   两条路径任何一条漏写 dark 值,就会出现 app.css:72-76 注释记载过的
   「跟随系统是 A、手动切过去是 B」的错配。 */
:root {
  color-scheme: light;
  /* …… §4 全部 light 值 …… */
  --mw-disc-fg: #8a5a00; --mw-disc-bg: #fdf3dd; --mw-disc-bd: #e6c982;
}
:root[data-theme="dark"] {
  color-scheme: dark;
  /* …… §4 全部 dark 值 + 琥珀 dark 三值(第一份)…… */
}
@media (prefers-color-scheme: dark) {
  :root:not([data-theme="light"]) {
    color-scheme: dark;
    /* …… §4 全部 dark 值 + 琥珀 dark 三值(第二份)…… */
  }
}
```

- 三态行为:auto → 无属性,media query 生效;light → `[data-theme="light"]` 同时**关掉** dark 双轨(`:not([data-theme="light"])`);dark → 属性选择器命中。与现状 `--mw-disc-*` 的处理(app.css:74-76)同构,推广到全部 token。
- 两份 dark 块在文件内**必须物理相邻**(media 块在上、属性块在下),块间注释互指;实现校验:两块的声明列表逐行 diff 为空。
- `color-scheme` 进 token 层的原因:它决定原生控件、滚动条、`::backdrop` 之外的 UA 默认色,必须和变量同生共死;index.html 的 `<meta name="color-scheme" content="light dark">`(L6)保留,负责 CSS 加载前的 UA 缺省。

### 5.2 首帧无闪白(契约 §2.11 的落实)

根因:主题唯一应用点是 `applyTheme`,它在 `app.js`(module → defer)模块顶层执行(app.js:89-90);defer 脚本晚于首次绘制,手动 dark 用户 + 光亮系统 = 首帧光亮闪白。pico 时代靠 media query 蒙对 auto 用户,手动档一直是闪的。

修法:index.html `<head>` 内、任何 `<link rel="stylesheet">` **之前**插入:

```html
<script>
/* 主题首帧自举:绘制前把持久化主题写到 <html>,消灭闪白(00-context §2.11)。
   与 app.js readTheme/applyTheme(app.js:69-90)同用 localStorage key "mw:theme";
   auto(缺省/值非法)时不设属性,交给 CSS 的 prefers-color-scheme 双轨。 */
try {
  var m = localStorage.getItem("mw:theme");
  if (m === "dark" || m === "light") document.documentElement.setAttribute("data-theme", m);
} catch (e) { /* 隐私模式:localStorage 不可读 → 跟随系统,可接受 */ }
</script>
```

- 内联(而非外链)的理由:零额外请求、同步执行保证在首帧前;服务端响应头只有 `X-Content-Type-Options: nosniff`(routes.ts:1373),**没有 CSP**,内联脚本可执行;若未来加 CSP,需为这段配 hash——已在此记录,不是现在的约束。
- 与 `applyTheme` 的关系:boot 脚本只负责"首帧前落属性";点击切换仍走 `applyTheme`(app.js:767-778),两者读写同一个 key、同一个属性,协议无第二真相源。

### 5.3 主题切换的通知面(canvas 重绘)

04 的图谱在 canvas 上画域色,主题切换后必须重读 token 重绘。**推荐 04 用 MutationObserver 自持**,不新增壳的职责:

```js
const mo = new MutationObserver(() => scheduleRedraw());
mo.observe(document.documentElement, { attributes: true, attributeFilter: ["data-theme"] });
// dispose() 里 mo.disconnect()(契约 §4 的 dispose 纪律)
```

可选增强(归 02,非本次必需):`applyTheme` 末尾派发 `mw:themechange` CustomEvent(契约 §2.9 只冻结既有事件不删,**新增**合法)。04 若用 observer 则与该事件无关,两案不互斥但只取其一,避免双重重绘。
