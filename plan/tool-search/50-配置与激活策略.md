# M5 · 配置与激活策略

## 1. 一句话定位

本模块把 `toolSearch` 的 settings / preset / CLI 配置归一为激活策略，按注册工具集与当前模型上下文窗口计算是否折叠，并把折叠类别段接入默认与 preset 两条系统提示路径；它不拥有 discovered 状态，也不根据 provider compat 标志改变是否折叠。

## 2. 签名参数

M1 已定稿的交界（D2：接口名以 M1 为准；M5 只组装输入，不重复定义）：

```ts
// M1 侧定稿（10-*.md §2）
export interface ToolSearchEntry {
  name: string;
  description: string;
  promptSnippet?: string;
  parameters: TSchema;
  deferrable: boolean; // 已由 normalizeDeferrable 归一化
}

export interface ToolSearchManagerInput {
  /** allow/deny 后仍可见的注册工具；不得传入 deny 工具。 */
  tools: readonly ToolSearchEntry[];
  /** R5 已由 M5 判定的激活结果；manager 不重复实现 token 估算。 */
  active: boolean;
  reservedTools?: readonly string[];
}

// M1 seam（D2）；返回值中的 activeToolNames 必须保留 discovered 工具。
recompute(input: ToolSearchManagerInput): {
  activeToolNames: readonly string[];
  activated: boolean;
  changed: boolean;
};
```

M5 不拥有 `discovered`；`recompute` 的实现由 M1 维护 discovered 并遵守 active→inactive 保留规则。M5 的职责 = 判定 `active`（下方纯函数）+ 组装 `ToolSearchManagerInput`（含归一化后的 `ToolSearchEntry` 视图），由 M4 定稿的 `syncToolSearchState()` 统一编排调用（D4）。M5 自身的判定输入与 NEW 纯函数：

```ts
// M5 判定输入；tools 为归一化后的 allow/deny 可见视图（形状同 ToolSearchEntry）。
export interface ToolSearchActivationInput {
  enabled: boolean;
  mode: "on" | "off" | "auto";
  thresholdPercent: number;
  contextWindow: number;
  reservedTools: readonly string[];
  tools: readonly ToolSearchEntry[];
}

// NEW；M5 纯判定，结果作为 ToolSearchManagerInput.active 传入。
export function shouldActivateToolSearch(input: ToolSearchActivationInput): boolean;
```

注册构建点先完成 deferrable 归一化，manager 不读取 `SourceInfo`：

```ts
import type { SourceInfo } from "../source-info.ts";
import type { ToolDefinition } from "../extensions/types.ts";

// NEW；调用顺序定稿见下（D8）；reservedTools 不参与归一化。
export function normalizeDeferrable(
  definition: ToolDefinition,
  sourceInfo: SourceInfo,
): boolean;
```

原生 7 工具始终归一化为 `false`；扩展/SDK 工具缺省归一化为 `true`，作者显式声明优先。**调用顺序（D8 定稿）**：落点函数为 `_refreshToolRegistry`（`agent-session.ts:4084`）；在该函数内 registry 最终覆盖合并完成之后（built-in + 扩展 + SDK customTools 的同名覆盖已在 `definitionRegistry` 决出唯一 definition+sourceInfo 对，`this._toolDefinitions` 赋值于 `:4117`）、`wrapRegisteredTools`（`:4135-4143`，内部走 `wrapToolDefinition` 白名单转发）之前调用一次；布尔结果写入 manager entry（M1 `ToolSearchEntry.deferrable`）；`wrapToolDefinition` 同步把 `deferrable` 加入白名单透传到 `AgentTool`（I4，落点归 M1）。每个工具名只归一化一次，manager/recompute/搜索路径不得重复判定。漏了归一化会令 manager 依赖 sourceInfo，或因误标折叠原生工具。

`estimateToolsTokens` 现状签名为 `(tools: readonly Tool[] | undefined): number`（`packages/ai/src/utils/estimate.ts:109-111`，私有），M5 负责去私有导出、算法保持原样（I3）；策略对经过 allow/deny 的、实际可见的 deferrable 工具全集估算，而不是对 registry 中被 deny 的工具估算。估算输入由 `ToolSearchEntry` 视图映射为 wire 上真实存在的 `Tool` 形状（name/description/parameters 三元组）后传入：不新造估算器，也不把 `promptSnippet`/`deferrable` 等非请求字段计入 token 负担。

`contextWindow` 取**当前会话实际 model 的 `contextWindow`**，不是 settings 中的历史值，也不是上一模型缓存值。窗口无效（缺失或 ≤0）时 `auto` 保守不激活并记录诊断（R5；C3 已裁决采纳本方案），实现中保持这一条单一规则。

## 3. 行为契约逐步（每步写「漏了会怎样」）

1. 读取有效 settings：`enabled` 缺省 `true`、`mode` 缺省 `"auto"`、`thresholdPercent` 缺省 `10`、`reservedTools` 缺省 `[]`（R4）。漏了默认值会导致旧配置无法启动，或小工具集意外产生额外 `tool_search`。
2. 先做现有 allow/deny 过滤，再做折叠过滤（R7；现状 `isAllowedTool` 在 `agent-session.ts:317-322,658-661,4084-4157`）。漏了顺序会让 deny 工具出现在目录/类别段，违反 deny 封闭性。
3. 强制 eager 集合 = 原生 `read/bash/edit/write/grep/find/ls`（`packages/coding-agent/src/core/tools/index.ts:37-58`）+ `tool_search` + `reservedTools` + `deferrable:false` 工具 + `tools.allow` 白名单工具（R5）。漏了原生兜底会因作者误标而折叠核心工具；漏了 reserved/allow 会使用户明确指定的工具延迟可用。
4. `mode="off"` 或 `enabled=false` 时不激活，不加入合成工具；保留现有 active 工具构造逐字节路径。漏了短路会让关闭配置仍改变请求。
5. `mode="on"` 且总开关开启时激活，不受 token 阈值影响。漏了强制分支会使 on 仍表现成 auto。
6. `mode="auto"` 时计算 `estimateToolsTokens(deferrable 工具全集) >= thresholdPercent / 100 * contextWindow`。阈值使用 `>=`；漏了边界会使恰好达到阈值的会话行为不稳定。contextWindow 无效（缺失或 ≤0）时不进入本比较，直接判定不激活并记录诊断（R5/C3，见 §7）。
7. `reservedTools` 只从折叠候选中移除，不减少阈值估算的全集（R5 的“叠加”语义）：用户保留工具仍计入“工具总负担”，但不会被折叠。漏了计入会因 reserved 越多而错误关闭 tool search，或反之改变 auto 的目的。
8. allow 白名单中的工具按显式列名解释为用户明确要随时可用，**强制 eager**；但仍受 `deferrable:false`/原生规则和 deny 语义约束。漏了这条会使 `tools.allow` 与用户预期冲突。本条已由 R5 冻结（allow 白名单一律强制 eager、不参与折叠），不再是待裁定建议。
9. 激活状态在工具注册刷新、allow/deny 或 preset policy 刷新、模型切换时重算；全部触发器统一调用 M4 定稿的 `syncToolSearchState()`（D4），M5 只在该编排内提供配置面输入（settings 有效值、当前模型 `contextWindow`、`reservedTools`、归一化后的 deferrable 视图），不另设第二编排入口。模型切换必须读取新模型的 `contextWindow`。漏了刷新会让旧模型窗口或旧工具集污染 auto 判定。
10. 运行中**进程内** settings 修改（setter/`/settings`/SDK）在**下一次请求前动态读取**，并触发一次策略重算（D14 的验收范围）；沿用 settings manager 现有读取/保存模型，不要求文件监听。settings **文件外部编辑**属无 watcher 的已知限制（§12），不触发重算、不作为验收目标。漏了重算会让用户改配置后要重启，违反热生效预期。
11. 激活→非激活时保留 discovered 名单及已发现工具 active，移除的只有合成 `tool_search`（R5）；非激活→激活时恢复 manager 计算的未发现折叠集合。漏了保留会抽走模型已经知道的 schema；漏了重新折叠会使关闭后再开启失去节省效果。
12. 激活时 R9 类别段只列仍可搜索的折叠工具（名称 + description 首句，同 `promptSnippet` 来源）；deny 工具不列。工具集变化随 `_rebuildSystemPrompt` 重建。漏了刷新会让模型目录与实际搜索集不一致。
13. `Model.compat.supportsToolReferences`、`supportsAdditionalTools`、`supportsToolSearch`、`deferredToolsMode` 只选择 provider 通道表现（R2 表；字段在 `packages/ai/src/types.ts:604-606,626-628,681-686`），不得影响客户端“是否折叠”的判定。漏了分层会让非兼容 provider 退化成全量，违背 provider 无关目标。

## 4. 文件与副作用

- `packages/ai/src/utils/estimate.ts`：仅导出 `estimateToolsTokens`，不改 4 chars/token 算法（现状 `:109-111`）。
- `packages/coding-agent/src/core/settings-manager.ts`：新增 `ToolSearchSettings` 接口与四个 getter/setter（键为 R4 的 `enabled/mode/thresholdPercent/reservedTools`）。写 setter 时复用 `markModified` + `save`，参照 `compaction.enabled`（`:28-34,908-919`）。
- `packages/coding-agent/src/core/agent-session.ts`：请求/注册刷新/模型切换策略同步（统一经 `syncToolSearchState()`，D4）；类别段输入经 `_rebuildSystemPrompt` 传参扩展写入 `_baseSystemPromptOptions`（组装点 `:1555-1565`），并确保 `_staticPromptCache` 指纹（`:1595-1611` 比对、`:1625-1636` 写入）包含类别段或其工具集 key。
- `packages/coding-agent/src/core/prompt-preset/compiler.ts` 与 `slot-renderers.ts`：preset 的 tools slot 编译时接入类别段，不绕过 preset 的消息编译与 regex 阶段（compiler `:22-54`；slot tools 事实见 `slot-renderers.ts:83-132`）。
- `packages/coding-agent/src/cli/args.ts`：新增显式 flags，沿用 `--tools` 的值解析模式（`:129-142`）；最终写入本次会话 overlay，而不是静默改全局 settings。
- `docs/settings.md`：按第 12 节回写。

副作用是 active tools 列表和系统提示类别段可能变化，从而改变下一请求 payload；策略计算本身不得执行工具、写 session entry 或改变 provider adapter。

## 5. 落账

settings 三层仍是 overlay > project > global（`settings-manager.ts:182-203,368-371`）。建议配置形状：

```json
{
  "toolSearch": {
    "enabled": true,
    "mode": "auto",
    "thresholdPercent": 10,
    "reservedTools": ["my_frequently_used_tool"]
  }
}
```

setter 应分别标记 `toolSearch.enabled`、`toolSearch.mode`、`toolSearch.thresholdPercent`、`toolSearch.reservedTools`。`reservedTools` setter 应复制输入并校验字符串；阈值必须是有限的 `>= 0` 数值，非法值拒绝保存或回退默认，不能把 NaN 带入策略。

preset 的 `tools.allow` / `tools.deny` 保持既有互斥与语义（`prompt-preset/types.ts:31-35`）；allow 作为强制 eager 叠加层，不改 allow/deny 本身的 registry 可见性。

## 6. 前端或 RPC 可见性

CLI 建议提供：

- `--tool-search on|off|auto`：覆盖 `toolSearch.mode`；
- `--tool-search-threshold <percent>`：覆盖 `thresholdPercent`；
- `--reserve-tools <name,...>`：**覆盖**本次会话 `reservedTools`（D9 定稿：语义对齐 `--tools`，显式给定完整列表，非追加）；
- `--no-tool-search`：等价本次会话 `enabled=false`。

flag 名称若与现有命令约定冲突，应在 args parser 中发诊断而非静默忽略。现有 `--no-tools/-nt` 是禁用全部工具（`args.ts:129-132`），不得把它误作 tool search off。

`/settings` 展示四个键及有效来源层级；修改后从下一请求生效。无须新增 RPC 方法；若 settings UI 有 schema 白名单，必须同步加入。

## 7. 错误边界

- `mode` 非 `on|off|auto`、阈值非有限非负数、reservedTools 含非字符串：给配置诊断并使用安全默认，不得崩溃 agent loop。
- `contextWindow <= 0` 或缺失：`auto` 保守不激活并记录可诊断原因（R5，C3 裁决）。
- `reservedTools` 中不存在/被 deny 的名称：不加入 active；不应出现在 tool_search 目录或 R9 类别段。
- `supportsToolReferences` 等为 false 不是错误，也不是关闭折叠条件；provider 仍收到普通工具 schema（R2）。
- preset 编译失败沿用 preset diagnostics；类别段不得绕过诊断直接拼入另一条系统消息。

## 8. 代码落点（精确到文件与函数）

1. `estimate.ts:109`：现状 `estimateToolsTokens(tools: readonly Tool[] | undefined): number` 去私有导出，算法不变。
2. `settings-manager.ts`：`CompactionSettings` 附近新增 `ToolSearchSettings`；在 `getCompactionEnabled` 附近新增 `getToolSearchEnabled/Mode/ThresholdPercent/ReservedTools` 与 setter。
3. `agent-session.ts`：`_refreshToolRegistry`（`:4084`）为 registry 构建/归一化落点（D8：归一化调用插在 `:4117` 的 `this._toolDefinitions` 赋值之后、`:4135` 的 `wrapRegisteredTools` 之前）；策略同步与 `_syncActiveToolPolicy`（现状 `:1860-1872`）、`setActiveToolsByName`（现状 `:1331-1346`）相衔接，统一经 `syncToolSearchState()`（D4，M4 所有）；`_rebuildSystemPrompt` 实际签名为 `(toolNames: string[])`（`:1524`），**不存在** `BuildSystemPromptOptions` 输入参数形态（D12）；静态 cache fingerprint 比对在 `:1595-1611`、写入在 `:1625-1636`，需纳入类别段 key。
4. 默认模式（D12 接线方案）：NEW 向 `_rebuildSystemPrompt` 增加可选第二参数 `toolSearchCategories?: readonly { name: string; description: string }[]`，由 `setActiveToolsByName`/`syncToolSearchState` 调用时传入，函数内写入 `_baseSystemPromptOptions.toolSearchCategories`（组装点 `:1555-1565`）。该 options 对象是三条渲染路径的统一输入：custom prompt 模式的 `buildSystemPrompt(options)`（`:1567`）、preset 静态编译的 `staticRuntime.options`（`:1612`）、per-turn preset 编译的 `getPresetInjectMessages`/`compileSystemPrompt`（`:1927,1947`），单点扩展即覆盖全部路径；类别段文本由 `buildSystemPrompt` 与 tools slot renderer 各自在所属路径渲染。类别段为空时不输出，保证 off/小工具集零开销。
5. preset 模式：类别段写入 `_baseSystemPromptOptions` 后自动进入全部 `PromptRuntime.options`（静态 `:1612`、per-turn `:1927,1947`，`PromptRuntime.options` 与其同型，`prompt-preset/types.ts:276`），无需另设运行时字段；`tools` slot renderer（`slot-renderers.ts:83-132`）从 `runtime.options.toolSearchCategories` 读取并渲染；`compileSystemPrompt` 继续从编译消息派生，不在 compiler 外追加旁路文本。这样 async slot 与静态 slot 行为一致。
6. 模型切换回调/设置同步点统一调用 `syncToolSearchState()`（D4，M4 所有）；其内部以 M5 判定的 `active` 组装 M1 `ToolSearchManagerInput` 调用 `manager.recompute`，M1 维护 discovered；M5 不新增第二编排路径。

## 9. 与现状差异

现状没有 `ToolSearchSettings` 或 `deferrable` 字段；settings 只有三层 deep merge（`settings-manager.ts:182-203,368-371`）。现状 `estimateToolsTokens` 私有（`estimate.ts:109-111`，I3）。现状 `_rebuildSystemPrompt(toolNames: string[])`（`agent-session.ts:1524`）内部从 `toolNames` 派生 `selectedTools/toolSnippets/promptGuidelines` 并组装 `_baseSystemPromptOptions`（类型定义于 `system-prompt.ts:9`，仅是内部 memo 字段，不是 `_rebuildSystemPrompt` 的输入参数形态，D12）；preset 的 system 内容经 compiler（`compiler.ts:22-54`），静态编译结果按输入指纹缓存于 `_staticPromptCache`（`:1595-1636`）。现状 blockImages 是请求动态读取 getter 的先例（`sdk.ts:319-324`），tool search 将采用同样的请求前读值，但新增一次策略重算。

## 10. 验收测试

- 默认值：空 settings 得到 enabled=true、mode=auto、threshold=10、reserved=[]。
- settings 三层覆盖与 setter：overlay/project/global 顺序正确，四个 setter 持久化且下一请求可见。
- `estimateToolsTokens` 导出结果与现有算法快照相同。
- auto 边界：估算值 `<`、`=`、`>` 阈值分别得到 false/true/true；模型 contextWindow 切换后结果按新值变化。
- on/off/enabled：on 无视阈值，off 与 enabled=false 无 tool_search 且工具列表等价现状。
- reserved/allow：reserved 与 allow 工具均 eager；reserved 仍计入阈值全集；deny 工具不出目录、类别段、搜索结果；CLI `--reserve-tools` 给定的列表完全**替换**本次会话 `reservedTools`（覆盖语义，D9），先前的 reserved 列表不残留。

- R9 默认与 preset：同一类别集合在两种模式均出现；空集合不出现；工具集变更重建且 cache 不复用旧类别段。
- compat：对 compat 四种组合，激活判定相同；仅 provider payload 通道不同（详细 12 格由 M6 验收）。
- 动态设置（D14 收窄）：进程内 setter/`/settings` 修改 → 下一请求重算，无需重启；settings 文件外部编辑（无 watcher）明确不列入验收（见 §12）。[推断] `/settings` 的具体调用测试应接已有命令测试 harness。
- 退化：激活后改 off，已 discovered 工具仍 active，`tool_search` 消失。
## 11. 发现的冲突

未发现必须偏离冻结契约的冲突。allow 白名单强制 eager、`--reserve-tools` 覆盖语义、无效 `contextWindow` 时 auto 不激活并诊断均已由主代理裁决并写入 R5。C1/C2 仅影响 M1/M4 的 discovered 恢复与通知；本模块要求类别段对 available（registry ∩ allow/deny）求交，不泄漏恢复中已卸载或 deny 的名称。

## 12. 仍未知待拍板
1. `/settings` 当前实现是否有命令级 schema/枚举白名单，需要将 toolSearch 四键注册到哪里。
2. preset tools slot 是否已有可复用的动态变量名；若没有，在 `system-prompt.ts` 的 `BuildSystemPromptOptions` 上新增 `toolSearchCategories` 字段（`PromptRuntime.options` 同型，经 `_baseSystemPromptOptions` 自动可见，见 §8.4/§8.5）。
3. settings 文件外部编辑：现状无文件 watcher，本设计不新增 watcher（D14 定稿）。**已知限制**：外部编辑在下次进程内 setter 写入或会话重启前不生效、不触发重算；这不是本期验收目标。进程内 setter 修改仍按 §3 步骤 10 在下一请求前读取 getter 并重算。
