# 30 · 搜索实现

## 1. 一句话定位

本模块定义合成工具 `tool_search.execute` 的纯检索算法：从 M1 提供的**已允许且未发现的折叠工具快照**中，以正则/关键词混合匹配返回可解释的短目录，并把本次首次发现的工具名写入 `addedToolNames`。它不执行真实工具，也不改变 provider adapter wire 格式。

## 2. 签名参数

M1 的 `ToolSearchManager`（落点 `packages/coding-agent/src/core/tool-search/`）向合成工具提供只读快照；搜索执行器不直接读取 registry，避免绕过 allow/deny。建议接口如下（`NEW`）：

```ts
export interface SearchableToolParameter {
  name: string;
  description?: string;
}
export interface SearchableTool {
  name: string;
  description: string;
  promptSnippet?: string;
  parameters: readonly SearchableToolParameter[];
  deferrable: boolean;
}
export interface ToolSearchRequest {
  pattern?: string;
  keywords?: string[];
  limit?: number;
}
export interface ToolSearchDetails {
  matchedToolNames: string[];
  addedToolNames: string[];
}
```

M1 的正式 seam 是 `getSearchableTools(): readonly SearchableTool[]`（不可变快照），其结果已完成 allow/deny、折叠资格和 discovered 过滤；条目形状为上面的 `SearchableTool`。execute 完成匹配后调用 `filterNewNames(names: readonly string[])`，仅返回尚未发现的名称；登记与 active 刷新由批次完成回调统一处理。M1 同时提供 `getGuidance`、`isFolded`、`isDiscovered`、`discoveredSnapshot`，但搜索算法不绕过快照重复过滤。

参数 schema 的唯一真相由 M1 工具定义 owner 维护；本节只引用该 schema，不定义第二份。其参数语义为 `{ pattern?: string, keywords?: string[], limit?: number }`，其中 `keywords` 严格为 `Type.Array(Type.String())`；非法类型交给参数校验自纠。`pattern` 最大 200 字符、`limit` 为 1–100，具体完整 TypeBox 定义见 M1 文档 §3.4。

`pattern` 与 `keywords` 至少提供一个；空对象由 schema/执行器返回参数错误，不执行全目录枚举。`keywords` 是可选结构化补充，不能把一个含空格的自然语言 query 强行拆成不可控 regex；若只需一个查询，调用方传 `keywords: ["database", "migration"]`。
当 foldedNames 非空时 tool_search 进入 active 广告集；无折叠工具、mode=off 或全部已发现时不进入 active，但仍保留可执行入口。后者的幻觉重调返回 `All folded tools are already loaded.`，不报 Unknown tool；热加载产生新折叠工具时由 `syncToolSearchState` 重新广告。

## 3. 行为契约逐步


1. **取得快照**：execute 开始时调用 M1 的 `getSearchableTools()`，并固定本次不可变快照。快照只含 R7 过滤后的可搜工具；deny 工具不应进入快照（00 §5 不变量 3）。漏了会怎样：直接从 registry 搜索会让 deny 工具泄露。
2. **规范化查询**：匹配大小写不敏感，并用 Unicode `toLocaleLowerCase("en-US")` 的稳定 ASCII 风格比较；不移除标点、不做模糊拼写纠正。工具名保持原始大小写返回。漏了会怎样：同一个 MCP 名称会因大小写造成不可重复发现，或误命中相似名称。
3. **校验 pattern**：长度超过 200 个 UTF-16 code units 视为 `invalid_tool_input`；空 pattern 等同未提供。使用 `new RegExp(pattern, "iu")`，捕获 `SyntaxError` 返回结构化 invalid input，而不是抛出 execute 异常。为防灾难回溯，禁止带潜在高成本结构：拒绝 pattern 中 lookbehind、backreference、以及量词上界超过 100；并将正则测试包在一次轻量预算内。JS 没有可靠的原生 regex timeout，长度/结构拒绝是硬防线，不能声称任意 regex 可被超时中断。漏了会怎样：模型生成的非法或恶意 pattern 会中断 agent loop，或在 200 个描述上长时间占用事件循环。
4. **构造搜索文本**：每工具四类字段分别检索：`name`、`description`、`promptSnippet`（若有）、参数 `name` 与参数 `description`。参数名/描述按参数边界拼接但评分保留字段命中信息。四处范围与 Anthropic 对齐（01 §2）。漏了会怎样：用户只能记住参数名或 prompt 指引时会找不到工具。
5. **正则匹配**：有合法 pattern 时，只要四类任一字段匹配即产生 regex 命中。regex 是精确检索通道，不要求整字段匹配。
6. **关键词匹配**：每个 keyword trim 后转小写；工具须满足所有关键词（AND）。一个 keyword 在任一四类字段命中即满足（OR across fields）；关键词使用 `includes`，不是隐式 regex。漏了会怎样：AND/OR 颠倒会返回大量无关工具或漏掉组合意图。
7. **混合条件**：pattern 与 keywords 同时提供时采用 AND：工具必须 regex 命中且所有 keyword 命中。仅提供其中一种时按该通道筛选。漏了会怎样：用户明确给出两种约束却得到只满足一半的结果。
8. **相关度排序**：不引入 BM25。按以下可解释分数降序：name 精确（归一化后等于完整 pattern/keyword）= 100；name 前缀 = 70；name 子串 = 50；description/promptSnippet 子串 = 30；参数名 = 25；参数描述 = 15；每个匹配查询 token 只计最高字段分，多个关键词分数相加；regex 额外 +20（只加一次）。同分按原始工具名 Unicode 字典序，最后按快照顺序稳定兜底。漏了会怎样：仅按注册顺序返回会让结果不可解释且 MCP 前缀工具常挤掉真正相关项。
9. **limit**：默认 5（对齐 Anthropic，01 §2），接受 1–100；超界由 TypeBox 拒绝，内部仍 clamp 以防非 schema 调用。排序在截断前完成。漏了会怎样：先截断再排序会丢失高相关结果。
10. **生成返回值**：正文只列每个命中工具的 `name — description 首句`，description 首句取第一个句号/问号/感叹号后的非空前缀，若无标点则整段 trim，长度最多 240 字符。不得返回完整 JSON schema；下一轮真实工具注入 schema（R3）。漏了会怎样：把 schema 重复放进上下文，抵消折叠收益。
11. **筛选新增工具**：对截断后的结果按排序顺序调用 M1 `filterNewNames(names: readonly string[])`，仅计算本次尚未 discovered 的名称；execute 不调用 `discover`，也不直接刷新 active 集合。登记、`addedToolNames` 生成和下一轮刷新由唯一的 `onToolBatchCompleted` 批次回调完成。R3 配对要求：`addedToolNames ⊆ 正文列出 ∩ 折叠集合`，且等于下一轮 active 集合增量。漏了会怎样：execute 内登记会与批次并发交错，造成重复 added 名称或 active 集合中途缩减。
12. **空结果**：合法查询但零命中，返回成功的空结果正文：`No matching tools found. Try different keywords or a broader pattern.`，`addedToolNames: []`，details 记录空数组；不抛异常。全部候选已 discovered 时快照为空，同样返回：`No undiscovered matching tools found. All matching tools are already loaded.`（M1 可提供 `hasDiscoveredMatches` 仅用于提示；不得泄露 deny 名称）。漏了会怎样：把正常搜索失败变成 loop 异常，模型无法自纠。

## 4. 文件与副作用

建议实现为 `packages/coding-agent/src/core/tool-search/search.ts` 的纯函数 `searchTools(snapshot, request): SearchResult`，以及 M1 合成工具适配器中的薄 execute。纯函数无 IO、无全局缓存、无 registry mutation；execute 只通过 M1 `filterNewNames` 计算候选，不登记 discovered。`AgentToolResult` 字段已存在于 `packages/agent/src/types.ts:362-376`，并由 agent-loop 传播（00 §3.2）。快照不得被 execute 原地修改。

## 5. 落账

搜索本身不新增 session entry；通过现有 ToolResult 的 `addedToolNames` 落账，字段实际定义见 `packages/agent/src/types.ts:362-370`，历史传播见 `packages/agent/src/agent-loop.ts:784-788`。M4 负责完整 branch/compaction 恢复。`details` 仅供日志/UI，建议保存 `matchedToolNames` 与 `addedToolNames`，不保存参数 schema。

## 6. 前端或 RPC 可见性
`tool_search` 是模型可见的合成工具；搜索结果正文是模型可见文本，details 可供 UI/日志但不应成为另一套模型协议。无新的前端 RPC、无 npm 依赖。目录只暴露允许且尚未发现的工具；R7 的 allow/deny 顺序来自 `packages/coding-agent/src/core/agent-session.ts:4084-4157`（00 §3.1），无 namespace 机制、工具名是纯字符串（`packages/coding-agent/src/core/extensions/loader.ts:278-285`），故不得按 server namespace 过滤。

## 7. 错误边界

- schema 验证失败、pattern 非法/过长、keyword 空/过长：返回现有工具参数错误语义（`invalid_tool_input`），不得部分执行。
- 合法查询无命中：成功空结果，不是异常。
- 原生 7 工具、allow 白名单中的工具、`tool_search` 和 `reservedTools` 属于强制 eager（00 §2 R5），即使工具作者声明可折叠也不可搜；否则会破坏 eager 语义。
- M1 `filterNewNames` 失败：execute 返回工具执行错误；登记与刷新仍不得在 execute 内完成。
- regex 防护是风险缓解而非强制 timeout：采用 200 字符上限、拒绝危险结构（lookbehind、backreference、量词上界超过 100），并以 adversarial 样本集验证；不得使用未验证的第三方 regex 包，也不得声称 JS RegExp 可被强制中断。

## 9. 与现状差异

现状只有全量注册/active 工具集与 deferred 结果传播：工具 registry 合并及 allow/deny 在 `packages/coding-agent/src/core/agent-session.ts:4084-4157`，`setActiveToolsByName` 下一轮生效并重建 prompt 在 `packages/coding-agent/src/core/agent-session.ts:1310-1345`；没有 tool_search 入口。`ToolDefinition` 当前字段清单见 `packages/coding-agent/src/core/extensions/types.ts:516-562`，作者标记与透传由 M1 处理。本文新增纯检索与合成 execute 适配，不改变上述 provider 通道。

单次搜索性能预算：折叠 200 工具、平均每工具 1 个描述/promptSnippet、8 个参数、总文本约 200k UTF-16 字符时，目标 p95 ≤ 5 ms、硬预算 ≤ 20 ms（Node/Bun 单线程，regex 预编译一次、每字段最多一次测试）；若超预算应降低目录文本或拒绝查询，而不是异步改变结果顺序。[推断] 具体机器 p95 需 M6 基准实测，本文只给算法预算。

## 10. 验收测试

- `search.test.ts`：四类字段各自命中；参数名与参数描述分别命中；promptSnippet 缺省不崩。
- 混合查询：pattern+keywords 为 AND，关键词内部为 AND、字段之间为 OR；大小写不敏感。
- 排序/limit：默认 5、显式 1/100、同分名字稳定；先排序后截断。
- 输入边界：非法 regex、201 字符 regex、空 keywords、危险 backreference/lookbehind 得 `invalid_tool_input`；合法普通 regex 得结果。
- R3：首次命中 added 与正文一致；二次相同查询 added 为空；`addedToolNames` 不含 eager/deny/正文外工具。
- 空快照分别验证“无匹配”和“全部已加载”提示不泄露 deny 名称。
- 200 工具基准验证 p95 ≤ 5 ms、硬预算 ≤ 20 ms（基准结果由 M6/主代理记录）。

## 11. 发现的冲突

1. JavaScript 原生 `RegExp` 没有可取消的 per-match timeout；契约要求正则注入/灾难回溯防护。本文采用长度 200、危险结构拒绝、固定字段扫描预算，这是无 npm 依赖下可实施的保守防线；若主代理要求任意正则强制中断，需引入 worker/新依赖或改为受限 regex 子集，属于超出当前冻结契约的决策。
2. 00 §2 R3 要求返回 description 首句，而 R9 又提到与 `promptSnippet` 同源。本文严格按 R3 使用 description 首句；promptSnippet 只参与检索。若 M1 将 promptSnippet 视作展示优先级，需主代理回写裁定，本文不私自改口径。
3. 接口方法名现已按裁决统一为 `getSearchableTools`、`getGuidance`、`filterNewNames`；登记入口由 D1 批次回调调用 manager `discover`，搜索 execute 不调用 discover。
