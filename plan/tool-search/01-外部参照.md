## 1. 两条技术路线

| 维度 | A. Provider 服务端原生 | B. 客户端合成工具 |
|---|---|---|
| 代表 | Anthropic `defer_loading` + `tool_search_tool_regex/bm25` | TanStack `lazy: true`；Claude Code 的 fallback 路径 |
| 机制 | 模型调 search 工具 → API 服务端检索 → `tool_reference` 块自动展开进上下文 | 引擎注册一个合成 tool_search 元工具 → 命中后引擎改写**下一轮请求**的 tools 列表 |
| 请求内容 | 全量工具仍随请求发送（服务端检索需要），但 deferred 工具不进模型上下文 | 只发 eager + 已发现 + search 工具本身 |
| provider 依赖 | 仅 Anthropic（beta header）；代理普遍不转发 `tool_reference`，Azure Foundry 直接拒绝 | 无，任何 provider |
| 缓存影响 | 前缀不含 deferred 工具 → 缓存稳定；命中后内联追加 | 每轮 tools 列表按需变化，缓存策略需引擎自行设计 |
| Claude Code 的选择 | 主路径用 A；**非第一方 endpoint 自动降级为全量加载** | — |

**pi-rp 已拍板走路线 B**（明月 2026-09-25）。本文以下按"可抄的设计决策"组织，不再论证路线选择。

## 2. Anthropic 原生机制要点（抄设计思路）

- 搜索范围：**name、description、参数名、参数描述**四处。
- 两个变体：regex（模式 ≤200 字符，大小写不敏感）与 BM25（自然语言 ≤500 字符）。
- 默认每次返回 5 个结果；模型可在调用时给 `limit`（1–10000）。
- 全 defer 直接 400：至少一个工具（通常是 search 工具自己）必须保持加载。
- 命中零成本复用：`tool_reference` 在整个对话历史里持续展开，后续轮不需要重新搜索。
- 官方启用判据：**≥10 个工具**、定义 **>10K tokens**、或 **30–50 个工具**以上选择准确率明显劣化。反向判据：<10 个工具、每个工具每轮都用、定义紧凑 → 不要开。

## 3. Claude Code 的产品化决策（最值得抄的工程决策）

1. **两分法**：核心高频工具（Bash/Read/Edit/Write/Glob/Grep/Agent/ToolSearch/Skill）永远全量加载；WebSearch、TodoWrite、全部 MCP 工具等 deferred。启发式 = **第一轮就可能用到的留下，整场可能用不到的折叠**。ToolSearch 自己必须 always-loaded（它是折叠工具的入口）。
2. **自适应激活**：`auto` 模式统计全部可折叠工具定义的 token 量，**超过上下文窗口 10% 才激活**，否则全量内联（小项目零开销）。阈值可调（`auto:5` = 5%）。取值：开/关/auto/auto:N。
3. **compaction 恢复**：压缩边界消息里记录已发现工具清单（`preCompactDiscoveredTools`），压缩后据此恢复状态；另外**每轮开始前对比"已告知模型的工具集"与当前实际工具集**，有变化（MCP server 连接/断开）就注入一条通知，防止模型对可用工具的认知过期。
4. **兼容性 fallback**：非第一方 base URL / 不支持的模型 / 服务端拒绝 → 自动退回全量加载。判据是**可检测的失败**（SDK 检测拒绝），不是配置猜测。
5. **系统提示补丁**：官方建议在系统提示追加一段"可用工具类别"清单（如"你可以搜索 Slack/GitHub/Jira 相关工具"），弥补折叠后模型不知道该搜什么。工具描述质量决定搜索命中率。
6. 单次搜索成本 ~200 token；一次性 30+ 工具定义 >10K token → 净收益极高。
7. 已加载的工具**跨轮保持加载**，直到 compaction 把发现它的消息压掉（压掉后靠恢复机制重建）。

## 4. TanStack 客户端实现（源码级，pi-rp 直接可抄的结构）

核心类 `LazyToolManager`（`packages/ai/src/activities/chat/tools/lazy-tool-manager.ts`，全文已读）：

1. **标记**：工具定义加 `lazy: true`，其余 eager。构造时分离为 `eagerTools` + `lazyToolMap`。
2. **合成 discovery 工具**：名字 `__lazy__tool__discovery__`；description 里**列出全部 lazy 工具名**（目录），可配 `includeDescription: 'none' | 'first-sentence' | 'full'` 控制目录条目带多少描述（`lazy-tools.ts` 的 `renderLazyCatalogEntry`）。入参 `{ toolNames: string[] }`；**execute 的返回值就是这些工具的完整 name + description + JSON Schema**。
3. **active 集合**：`getActiveTools()` = eager + 已发现 lazy + discovery 工具（仅当还有未发现的）。全部发现完毕后 discovery 工具退出广告集。
4. **可执行集合与广告集分离**（`getExecutableTools`）：discovery 工具退出广告集后，若模型仍调用它（幻觉/长上下文），执行查找放宽让它**可执行**——再拿一次 schema 而不是报 Unknown tool。**广告集不变，只放宽执行查找**；且绝不能在执行期调 `getActiveTools()`（会重置 `hasNewDiscoveries` 标志，破坏 agent loop 的刷新判定）。
5. **多轮状态恢复**：构造时 `scanMessageHistory` 扫历史里的 discovery 调用及其 tool result（按 toolCallId 配对、解析 result JSON 里的 `tools[].name`），恢复 `discoveredTools` 集合 → **resume 与 compaction 天然正确**，不需要额外持久化状态。
6. **自纠错**：模型调用未发现的 lazy 工具 → 不报 Unknown tool，返回 `"Tool 'x' must be discovered first. Call __lazy__tool__discovery__ with toolNames: ['x'] to discover it."`，模型下一轮自我修正。这是**正常控制流**，不是错误路径。
7. **刷新时机**：一批工具执行完后，若 `hasNewlyDiscoveredTools()` 为真 → 重新取 active 集合并继续 agent loop。只有**真正新发现**才置位标志（重复请求已发现的工具不触发无谓刷新）。
8. **零开销 opt-in**：没有任何 lazy 工具时不创建 discovery 工具，行为与原来逐字节一致。
9. 未知工具名处理：discovery 调用里给 `errors: ["Unknown tool: 'x'. Available tools: [...未发现清单...]"]`——**把可用清单塞进错误信息**，模型自纠。

## 5. 其他实现（一笔带过）

- **Mastra**：`ToolSearchProcessor` 中间件形态，官方宣称上下文缩减 84–94%。
- **mcp-shark/lazy-tool**：Go 单二进制 + SQLite 目录的 MCP 透明代理，外挂思路，对引擎内实现无参考价值。
- **agentic-patterns** 归纳的变体：LRU 缓存最近用过的工具、渐进式加载（常用留全量、长尾进搜索）、强制开关（测试用）。阈值选 10% 是 Claude Code 实测值。

## 6. 共同设计决策点（任何实现都要回答）

| # | 决策点 | 业界答案分布 |
|---|---|---|
| D1 | 哪些工具折叠 | 按频率两分：核心 3–5 个留全量；MCP/扩展工具是天然折叠对象 |
| D2 | 何时激活 | 固定开关 vs token 阈值自动（共识 ~10% 上下文窗口）；auto:N 可调 |
| D3 | 搜索怎么做 | 正则/关键词匹配（目录 <100 个足够）vs BM25/embeddings 语义检索 |
| D4 | 命中后如何注入 | 服务端展开（A）vs 客户端改写下一轮 tools 列表（B） |
| D5 | 状态生命周期 | 已发现跨轮保留；compaction 后恢复（边界记录 or 历史扫描）；工具集变化时增量通知 |
| D6 | 防呆 | 调未加载工具 → 引导性报错（自纠错），不失败；search 工具永远可执行 |

## 7. 对 pi-rp 的映射判断（主 agent 初步裁定，设计期可反驳）

- **可整体照抄结构**：TanStack 的 LazyToolManager（分离/合成工具/active 集合/历史扫描恢复/自纠错/刷新时机）。
- **值得吸收**：Claude Code 的 10% 自适应阈值、系统提示"工具类别"补丁、每轮工具集变化通知。
- **不可抄**：`tool_reference`/`defer_loading` 一切服务端机制（provider 绑定）。
- **pi-rp 特有约束**：多 provider；工具 schema 用 TypeBox 时含 array 的 Union **array 分支必须放第一位**（Gemini/Vertex 校验会 400，`packages/coding-agent/src/core/tools/read.ts:22-26` 有约定注释原文，已核实）——tool_search 工具自己的入参 schema 必须遵守。
- **待 scout 事实校准后定**：工具分类的配置面（谁决定哪些工具折叠）、与 MCP 工具生命周期的接缝、与 compaction 的接缝。
