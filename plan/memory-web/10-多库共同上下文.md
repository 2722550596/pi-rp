## 1. 目标与非目标

### 1.1 预期效果（明月 2026-09-16 定）

前端能**选择任意一个记忆库**，选中后全部读视图与写操作都作用于该库 —— 等价于一个面向使用者的记忆库编辑器。使用场景：一个 world 下有多个库（world 级 + 每个角色一个），需要在不重启 web、不换端口的前提下逐个查看与修正。

### 1.2 已拍板决策（MUST NOT 重新论证）

| # | 决策 | 出处 |
|---|---|---|
| M1 | **库的来源 = 自动发现 + 手动输入兜底** | 明月 2026-09-16 选（本轮） |
| M2 | **支持新建空记忆库，但必须显式确认** | 明月 2026-09-16 选（本轮） |
| M3 | web 是独立进程，多库功能**不改这一点** | 上一轮 2026-09-16 已定：`/memories web` 是启动器不是服务 |
| M4 | 不开新包、零 npm 依赖、零构建、客户端纯 ESM JS | 沿用 `00-共同上下文.md` §2.1 |
| M5 | 本地单用户工具，**不引入 token / session / 登录** | 沿用 `00` §5 |

### 1.3 非目标（MUST NOT 出现在本期实现）

- **不做跨库合并 / 迁移 / 复制节点**。
- **不做库级别的删除 / 重命名 / 移动**。
- **不做 schema 迁移**（`schema.ts:131` 的"无就地迁移"立场不变）。
- **不做多库并发写的事务协调**：两个库是两份完全独立的 SQLite，没有跨库事务这个概念。
- **不做远程 / 网络多用户**：多库功能在非回环绑定下**整体禁用**（见 §5）。
- **不重做导航**：库选择器是**增量**，不改现有 9 条路由的语义。

### 1.4 术语（冻结，MUST 全文一致）

| 术语 | 含义 | 禁用同义词 |
|---|---|---|
| **记忆库 / DB** | 一个 `memory.db` 文件 | "数据库实例"、"connection" |

## 2. 现状事实（实测，2026-09-16）

子文档 MUST 引用这些事实，MUST NOT 凭印象重述。

### 2.1 服务端是「一进程一库」

- `ServerContext`（`src/web/server.ts:18-25`）持有**单个** `store: MemoryStore` 与 `dbPath: string`。
- `dispatch`（`src/web/routes.ts:878`）收到这个 `ctx`，全部 handler 通过 `rc.ctx.store` 取库 —— **共 16 处** `ctx.store` 引用。
- `ctx.dbPath` 只在 `getMeta` 用了一次（`routes.ts:177`，填 `MetaDTO.db_path`）。
- 启动时**只打开一个库**（`cli.ts:163`），失败则 `exit(1)`。
- `startServer` 的 `close()` 直接 `ctx.store.db.close()`（`server.ts:130`）。

### 2.2 三处「per-connection」状态（多库下必须逐库持有）

| 状态 | 现状 | 多库影响 |
|---|---|---|
| `ChangeDetector` | `runtime.ts:15` `WeakMap<MemoryStore, ChangeDetector>` | ⭐ 本来就是 per-store 的，**天然支持多库**，只需保证每库一个连接 |
| `PRAGMA data_version` | 每连接计数器（`runtime.ts:4-6` 注释） | 每库必须复用**同一个**连接，否则 `changed` 恒 false |
| `visibility` | `runtime.ts:33` 每请求 `createVisibility(ctx.store)` 重建 | 跟着目标库走即可 |

### 2.3 ⚠️ 关键危险：`openMemoryStore` 对陌生 SQLite 文件**不校验、直接灌表**

实测（`/tmp/victim.db`，一张 `users` 表）：

```
调用 openMemoryStore('/tmp/victim.db')
→ 成功返回，victim.db 被加进 **23 张** memory 相关表（`sqlite_master` 计数 1 → 24，含 `users` 与 FTS 影子表）；users 数据未丢但文件被污染。主文件 mtime 变，并生成 `-wal`/`-shm`。
```

根因：`schema.ts:131` `createSchema` 只在 `memory_kv.schema_version` **存在且不匹配**时才拒绝；普通 SQLite 文件该表不存在 → `readSchemaVersion` 返回 `null` → 一路建表。
（`index.ts:123-127` `openMemoryStore` = `openDatabase` + `createSchema` + `new MemoryStore`。）

**这是本功能最严重的风险**：选错一个路径（笔记库、别的应用的数据文件）就会**污染用户的文件**。§5.2 的强制探测就是为它立的。

### 2.4 ⭐ 只读探测可行，但「零副作用」有边界（实测，见 §2.4b 修正）

```
new DatabaseSync(path, { readOnly: true })          → 成功
读一个普通库                                        → 事实可读
查询 memory_kv（普通库）                             → 抛 "no such table: memory_kv"
```

即：**可以安全地先验后开**。`node:sqlite` 的 `DatabaseSync` 支持 `{ readOnly: true }`（Node v26.8.1 实测）。
⚠️ 但现有 `driver.ts:14` `openDatabase` **不暴露 readOnly 开关**（`driver.ts:28` 只有 `new DatabaseSync(resolved)`）→ §4.4 要求新增一个**只读探测专用**入口。

### 2.4b ⚠️⚠️ 修正：「零副作用」只对**非 WAL** 库成立（实测，D1 报告后复核）

初版契约写「未新建 `-wal` / `-shm`」—— 那是对 `journal_mode=delete` 的普通文件测的结论，**对 WAL 库不成立**。逐项实测：

| 被探测的文件 | 主文件 md5 | 新建 `-wal`/`-shm` |
|---|---|---|
| 非 WAL 普通库 | 不变 | **否** |
| WAL 模式的普通库 | 不变 | ⚠️ **是**（`-shm` 32 KB、`-wal` 0 B） |
| **真实 memory 库**（WAL） | **不变**（md5 逐字节相同） | ⚠️ **是** |

**三条结论（都要落进实现）**：
1. ⭐ **主库文件本体永不被改**（md5 逐字节相同，实测）。这才是「先验后开」安全的**真正依据**。
2. ⚠️ 但会留下 `-wal` / `-shm` 附属文件 —— 不改变主文件，是任何只读客户端读 WAL 库的正常行为，删除安全（下次打开重建）。
3. ⭐ **§5.2 的安全判据 MUST 表述为「主库文件的表集合 + md5/mtime 不变」，MUST NOT 断言「文件列表不变」** —— 后者对本功能自己的库都不成立。

**对 D2 / D5 的直接影响**（已广播）：
- D2：威胁分析 MUST 区分「改主文件」（**不发生**，要防的就是它）与「留 WAL 附属文件」（**发生**，无害但如实记录）。
- D5：V2 的断言 MUST 用**主文件 md5 + 表集合**，**MUST NOT** 用 `readdir` 比文件列表（会对 memory 库误报失败）。

补充（D1 实测）：
- `{readOnly:true}` 打开**不存在的文件**抛 `ERR_SQLITE_ERROR "unable to open database file"` 且**不创建文件**；目录抛 "disk I/O error"；文本文件 open 成功但 `prepare` 抛 "file is not a database"；0 字节文件 open 成功且大小不变。
- ⭐ **只读连接上执行 `PRAGMA journal_mode = WAL` 会抛 `attempt to write a readonly database`** —— 这是「`openDatabaseReadonly` MUST NOT 复用 `openDatabase`」的**硬证据**（比「改写文件头」的说法更直接、更可测）。
- 只读连接上 `PRAGMA busy_timeout` 与 `BEGIN`/`COMMIT` **不抛**；`INSERT`/`CREATE TABLE` 抛 `attempt to write a readonly database`。
- `-wal`/`-shm` 在连接 `close()` 之后**仍留在磁盘上**（实测 `-shm` 32 KB + `-wal` 0 B 关闭后仍在）→ 进一步说明 D5 的断言只能对**主库**成立。

### 2.5 前端取数只有一个入口

`app.js:101-124` 的 `get(path, query)` / `post(path, body)` 是**全站唯一** HTTP 层（`edit.js:38` 另有一处 `fetch`，见 §7.1）。
`app.js:104` / `app.js:115` 是加 `?db=` 的**仅有两个**注入口。

### 2.6 机器上的真实库分布（39 个，实测）

```
/home/yoshix7ti/projects/hackathon/worlds/<world>/.pi/memory.db                     ← world 级
/home/yoshix7ti/projects/hackathon/worlds/<world>/characters/<char>/.pi/memory.db  ← 角色级
共 39 个 memory.db；其中**只有 4 个** nodes > 0（其余为空库）
```

→ 选择器**必须显示节点数**，否则 39 个库无法辨认（§6.2 强制）。
⚠️ **`39` / `4` 都不是不变量**（D1 复核，2026-09-16）：该数字是当时按 `~/projects` 整体降的；D3 全量 `find` 得 **41 个**（还含 `~/world/...` 与 `~/projects/pi-rp/packages/coding-agent/.pi/`）。任何文档/测试 MUST NOT 写死这两个数（§7.5 已禁止测试依赖真机库路径）。它们只用来说明**量级**：库多、且绝大多数是空库。

### 2.8 ⚠️ 并发写：pi 会话与 web 同时写同一库会 `database is locked`（实测）

`MemoryStore` 用 `busy_timeout = 5000`（`driver.ts:30`）。实测两个连接交错写 WAL 库：

```
a 开 BEGIN IMMEDIATE 并写 → b 尝试写
  → b 等满 5011ms，抛 "database is locked"
a COMMIT 后 → b 再写成功  ✅（冲突是暂时的，非永久）
```

**为什么这对多库更重要**：切库功能让用户**更容易**切到一个正被 pi 会话写着的库（那正是他关心的库）。
现有映射（`routes.ts:112-137`）**没有** `database is locked` 分支 → 落 `internal`(500) → 前端 `app.js:280` 显示「服务可能未启动，或已退出」——**把「等一下再试」误报成「服务挂了」**。
D3 MUST 为它加映射与文案（建议 `conflict` 409 + 「记忆库正被另一个进程写入，请稍后重试」）。

### 2.7 现有路由表（**21 条**，`routes.ts:834-854`）

11 条 `GET`（`meta/tree/node/search/temp/view/audit/revisions/raw/sessions/events`）+ 10 条 `POST`。
多库只在其中**注入 `?db=`**，不新增语义。新增 3 条库管理路由（§4.3）。

## 3. 架构（冻结）

### 3.1 一句话

> 把「一进程一库」放宽为「**一进程 N 库**」：进程持有一个**注册表**（路径 → 懒打开的 store），每个请求从 `?db=` 解析目标库，其余 handler 代码**不动**。

### 3.2 StoreRegistry（新增，归 D1）

```ts
interface RegisteredDb {
  /** 绝对路径，同时是库 id（§4.2）。 */
  path: string;
  /** 已打开的库；未打开为 null（懒加载）。 */
  entry: StoreEntry | null;
}

interface StoreEntry {
  store: MemoryStore;
  /** 与 store 一一对应的连接，供 ChangeDetector 使用（§2.2）。 */
  openedAt: string;
  lastUsedAt: number;
}
```

MUST 成立的语义：

1. **懒打开**：注册 ≠ 打开。只有被请求命中才 `openMemoryStore`。理由：机器上有 39 个空库，全开会浪费 fd 且拖慢启动。
2. **同库同连接**：同一个路径在进程内 MUST 只有一个 `StoreEntry`（`PRAGMA data_version` 依赖此，§2.2）。
3. **LRU 上限**：同时打开的库数上限 **8**；超限时关闭最久未用的**且不是当前请求目标**的库。驱逐 MUST 发生在 `dispatch` 拿到目标库**之前**，且 MUST 从 `runtime.ts` 的 detector `WeakMap` 中一并失效（`weakMap.delete(store)`）。
4. **关闭失败不致命**：`db.close()` 抛错时 MUST 记录并继续注册表清理，MUST NOT 让驱逐失败拖垮请求。
5. **文件消失不静默**：已注册库的文件被外部删除 → 请求报错（`invalid_db`），**MUST NOT 静默从注册表移除**（用户需要知道库不见了）。

### 3.3 请求如何找到目标库（冻结的顺序）

```
dispatch(req, res, ctx)
  ├─ S2 Host 检查（不变）
  ├─ S3 Origin 检查（不变）
  ├─ ★ 解析目标库：url.searchParams.get("db")
  │     ├─ 缺省 → 进程库（ctx 自带的那个）           ← 保住 /api/meta 的 launcher 探测（§4.5）
  │     ├─ 是已注册路径 → 取该库（必要时懒打开）
  │     └─ 否则 → 404 not_found，错误信息含该值
  ├─ ★ 驱逐（§3.2#3）
  └─ route.handler  ← 此后 ctx.store 即目标库
```

⭐ **实现要点（避免大改）**：MUST 以**构造一个新的 `ServerContext`**（store/dbPath 换成目标库）的方式传给 handler，而不是改 20 个 handler 的签名。`ServerContext` 是普通 interface，复制成本可忽略。

### 3.4 库管理路由（新增 3 条，归 D3）

| 方法 | 路径 | 作用 |
|---|---|---|
| `GET` | `/api/databases` | 列出已注册库 + 发现结果（含 `node_count`、`world_time`，§6.2） |
| `POST` | `/api/databases/open` | 注册并打开一个**手动输入**的路径（需通过 §5.2 探测） |
| `POST` | `/api/databases/create` | 新建空库（**必须**带 `confirm: true`，§5.3） |

⚠️ **这三条 MUST NOT 接受 `?db=` 参数**（它们是"关于库"的操作，不是"在库里"的操作）。

### 3.5 不做的事（防止子文档自行发散）

- 不做 `/api/databases/close`、`/api/databases/remove`：注册表随进程消亡，用户重启即可。
- 不做库级别的权限区分：全部注册库读写能力相同。
- 不做"最近使用"持久化到磁盘：localStorage 在前端（§6.3）。

## 4. 接口契约（冻结）

### 4.1 `?db=` 参数（全站唯一的多库开关）

- 名称：**`db`**（禁用 `database`、`dbPath`、`path`）。
- 值：**库的绝对路径**（即库 id，§4.2）。**不做 URL 编码之外的处理**。
- 缺省：等价于**进程库**。
- 出现在：全部 21 条数据路由（11 GET + 10 POST）。**不出现在** `GET /` 与 `/assets/*`（静态）。

### 4.2 ⚠️ 库 id = 绝对路径，且**只接受已注册的值**

这是本设计的安全核心，MUST 逐字实现：

1. `?db=<值>` 经 `path.resolve` 归一后，MUST 与注册表中某个 `path` **全等**才被接受。
2. **MUST NOT** 把 `?db=` 直接当路径去 `openMemoryStore` —— 否则等于把"读任意文件"暴露给任何本机网页（CSRF）+ 任意 UA。
3. 未注册的值 → `404 not_found`，**MUST NOT** 顺手注册并打开。（注册的唯一入口是 `/api/databases/open`，它带 §5.2 探测。）
4. 用绝对路径而非 hash 作 id 的理由：可读、可调试、`/api/meta` 的 `db_path` 天然一致（§4.5 的 launcher 探测依赖此）。

### 4.3 `/api/databases` 响应（冻结形状）

```jsonc
{
  "current": "/abs/path/to/current.db",     // 进程库（不是选择状态；选择状态在前端 §6.3）
  "databases": [
    {
      "path": "/abs/path/world/.pi/memory.db",
      "label": "fpal-9cdfb1dc",              // 供 UI 显示的短名（D3 定生成规则）
      "registered": true,                     // 是否已在注册表（false = 发现到但未打开）
      "reachable": true,                      // 文件当前存在且可探测为记忆库
      "node_count": 73,                       // 见 §6.2；不可达时为 null
      "world_time": "2020-09-28",             // 同上
      "error": null                            // 不可达时的原因（人话）
    }
  ],
  "roots": ["/home/yoshix7ti/projects/hackathon/worlds"],
  "discovery": { "enabled": true, "scanned": 1824, "errors": [] }   // scanned = **实际 readdir 过的目录数**，不是库数（库数见 databases.length）
}
```

- `databases` MUST 是**注册库 ∪ 发现库**的并集，按 `path` 去重。
- 排序：`registered` 优先，其次 `node_count` 降序，再次 `path` 升序（**确定性**，测试依赖）。

### 4.4 只读探测（新增引擎入口，归 D1）

`driver.ts` MUST 新增只读打开能力（**不破坏** `openDatabase` 现有语义）：

```ts
/** 只读打开，供多库探测使用；MUST NOT 建表、MUST NOT 改文件。 */
export async function openDatabaseReadonly(path: string): Promise<MemoryDatabase>;
```

⚠️ 实现 MUST 传 `readOnly: true`（§2.4 实测支持）。**MUST NOT** 用 `openDatabase` 冒充只读 —— 它会 `PRAGMA journal_mode = WAL`（`driver.ts:29`）、建 `-wal` 文件并**改写文件头**。
⚠️ 探测函数 MUST 自己 `close()`，不得泄漏连接。

### 4.5 与 `/memories web` 启动器的兼容（**不能破坏**）

`web-launcher.ts` 用 `GET /api/meta` 的 `db_path` 判断"端口上是否已有服务本库的实例"（上一轮实现）。
因此：**不带 `?db=` 的 `/api/meta` MUST 返回进程库的 `db_path`**，语义与现在**逐字不变**。
（`probePort` 比较的是 `db_path === dbPath`，见 `web-launcher.ts`。）

### 4.6 错误码（沿用 `routes.ts:71` 的七码闭集，新增 0 个）

多库场景的映射（**不得自造第八个码**）：

| 场景 | 码 | HTTP |
|---|---|---|
| `?db=` 未注册 | `not_found` | 404 |
| 已注册但文件消失 / schema 不兼容 | `invalid_db` | **409** |
| 手动路径不在允许 roots 内 | `bad_request` | 400 |
| 手动路径不是记忆库 | `bad_request` | 400 |
| 非回环绑定下调多库端点 | `forbidden_origin` | 403 |
| 新建库缺 `confirm: true` | `bad_request` | 400 |

⭐ **更正（D3 报告，2026-09-16）**：初版写 `invalid_db` → **500 是错的**。既有实现是 **409**（`routes.ts:116-118` 三处 `fail(409, "invalid_db")`），且 `test/web/api.test.ts:865` 明确断言 409。§9 V9 要求既有测试全绿，两条互斥 —— **采纳 D3 的裁决：沿用 409**，`?db=` 场景复用同一个 `mapStoreError` 映射。
理由（D3 给，我认同）：`invalid_db` 的语义是「资源当前状态不可读」，与 `conflict` 同属 409 一族；而 500 在本 API 里被前端归类为「服务器内部错误（可重试的环境故障）」，与「库被删了」性质不同。

## 5. 安全模型（冻结，**本节是评审重点**）

### 5.1 威胁模型不因多库而变，但**攻击面变宽**

现状（`00` §5）：无认证的本地 HTTP 服务，靠三条规则挡住 CSRF 与 DNS rebinding。
多库把"能读**这一个**库"放宽为"能读**注册表里任意**库" —— 一旦注册表能被远端操控，就等于**任意 SQLite 文件的读写**。

### 5.2 ⭐ 规则 R1：注册的前置条件是**只读探测通过**

任何路径进入注册表之前，MUST 依次通过：

1. **归一化（仅用于「库 id」）**：`path.resolve()`，防 `..`、防相对路径歧义。
   ⚠️ 注意与第 2 步的区别：**库 id 仍是词法 `path.resolve` 产物**（D2 确认，§4.2 的 id 规则不变，`/api/meta` 的 `db_path` 比对不受影响）；`realpath` **只用在第 2 步的判定**上。两者不可混用 —— 混用在第 2 步就会产生下面那个逃逸。
2. ⭐⭐ **roots 包含性检查（**逐段真实解析**，不是词法）**：
   ⚠️⚠️ **我的初版写法（`path.resolve` + `realpathSync` 双重包含）是错的 —— D2 实测出一次真实逃逸，我已独立复现。**

   反例（`/tmp/esc`）：
   ```
   roots/           为 roots
   outside/secret.db 在 roots 外（有数据）
   roots/link -> /tmp/esc/outside      ← roots 内的 symlink
   候选串: roots/link/../outside/secret.db
   ```
   `path.resolve` **词法折叠** `..` → `/tmp/esc/roots/outside/secret.db` → 看着在 roots 内 → **词法检查放行**；
   而内核**先走 symlink 再回退** → 实际打开 `/tmp/esc/outside/secret.db`。实测 `DatabaseSync` 读到了 roots 外的 `secret` 数据。
   → **这不是理论风险，是实测读到了不该读的文件。**

   **正确形态（D2 三版迭代后 26/26 通过）**：
   - (a) **逐段真实解析**：逐段拼路径，对每一段做**真实解析**（`..` 在**已解析结果**上回退，而不是词法折叠）；
   - (b) **一致性断言**：原始串与归一化串 MUST 解析到**同一个真实文件**。
   - ⚠️ **`realpathWalk` 内部 MUST NOT 用 `path.resolve` / `path.join` 取绝对串**（它们词法折叠 `..`）—— D2 在同一个坑栽了两次，这条 MUST 进 review checklist。
   - 仍 MUST NOT 用 `startsWith` 判包含（兄弟目录会骗过它，`00` §16 先例）。
   ⚠️ **反向约束（MUST NOT 误拒）**：无歧义的 `..`（不跨 symlink）**必须放行**、roots 自身是 symlink **必须放行**、悬空 symlink **必须拒绝**。D5 的 V10 必须**成对**测这四条（B12/B13/B14/B15），缺一条就会放过一个错实现。
3. ⭐ **存在性 + 文件类型**：已存在的目标 MUST 用 **`stat()`**（**跟随 symlink**）判定为**普通文件**，且**必须排在只读打开之前**。
   ⚠️⚠️ **硬危害（D2 报告，我已复核）**：`new DatabaseSync(<FIFO>, { readOnly: true })` 会**永久阻塞**（不抛错、不超时）。实测：对 `mkfifo` 的管道文件只读打开，8 秒无返回、被 `timeout` 杀掉。
   → 这不是"探测失败"，是**把整个 web 进程挂死**（同步 sqlite 调用占住事件循环）。故类型检查是**必需**，不是可选优化。
   **同族特殊文件实测（我逐个跑，比推理准）**：
   | 文件 | `stat.isFile()` | 只读打开 | 探测 `memory_kv` |
   |---|---|---|---|
   | FIFO（`mkfifo`） | false | ⚠️ **永久挂死**（4s 超时未返回） | 到不了 |
   | `/dev/zero`、`/dev/null`、`/dev/urandom` | false（character device） | **open+query 成功**（~180ms） | ✅ `no such table: memory_kv` 被拒 |
   | 0 字节普通文件 | **true** | open 成功 | ✅ 被拒（无表） |
   | 文本文件 | **true** | open 成功 | ✅ 被拒（`file is not a database`） |
   → ⚠️ 字符设备**能被 open 成功**（不抛错），只靠 `openMemoryStore` 的建表前检查挡不住 —— **`isFile()` 是必需的**；同时探测（读 `memory_kv`）是**第二道**，两道都在才安全（`00` §12 纪律 2 的「同一下游多道防线」）。
   ⭐⭐ **修正（D2 报告，我已实测复核）**：初版写 `lstat().isFile()` 是**错的** —— `lstat` 对 symlink 返回 `isFile=false`，会把**合法的 symlink 库误拒**（实测：`link.db -> 真实库` 时 `lstat.isFile=false` 但 `stat.isFile=true`）。
   **正确口径**：用 **`stat`**（跟随链接）判类型 —— symlink→普通文件 = 放行；symlink→FIFO = `stat.isFIFO=true` **拒绝**；直接 FIFO = 拒绝。实测三例全部符合。
4. **只读探测**（§4.4）：必须能读到 `memory_kv.schema_version`。
   - 探测失败 → `bad_request`，**MUST NOT 注册**。
   - 探测通过但版本不兼容（`schema.ts:133` 的语义）→ 单独报错，**MUST NOT 注册**。

⭐ **修正（安全评审 SEC-01，我已复核）**：上表「同族风险」的枚举**不完整，且「`isFile()` 一次挡掉全部」是错的**。实测：
```
/proc/version、/proc/self/cmdline、/proc/self/environ     stat.isFile() === **true**、只读 open **成功**
/sys/kernel/notes                                          stat.isFile() === **true**、open 成功
```
→ procfs/sysfs 伪文件**会被 `isFile()` 放行**。它们的危害低于 FIFO（不挂死；探测读 `memory_kv` 会拒），故**探测是必需的第二道**（这印证了「两道都在才安全」，而不是「`isFile()` 足够」）。
**正确口径**：类型检查挡的是「非普通文件」，**不挡** procfs/sysfs 伪文件；后者由探测挡。

⚠️ **硬链接绕过 roots（安全评审 SEC-03，我复核确认）**：`realpathSync` 对硬链接返回它**自己那个（roots 内的）名字**（硬链接没有「目标」）→ `checkPathAllowed` 返回 `ok:true`、inode 与受害者相同，`openMemoryStore` 会污染 roots 外的同一 inode。

⚠️⚠️ **`nlink > 1` 检查：我一度采纳，随后被评审推翻 —— MUST NOT 无条件使用（我两次实测确认）**

- **误伤①（日常备份）**：`cp -al` / `rsync --link-dest` / borg / Time Machine 只要做过**一次**硬链接式备份，**用户自己正常使用的那个库**的 `nlink` 就变 2（实测：备份前 1 → 备份后源库 2，同 inode）。⇒ 无条件 `nlink>1` 拒绝会把正常用户的库**拒掉**。「合法记忆库 nlink 恒为 1」**不成立**。
- **误伤②（与 §5.4 冲突）**：`resolve` 正是 `?db=<进程库>` 走的路。把检查放进 `resolve` ⇒ 进程库 `nlink=2` 时 `?db=<进程库>` 报错，而**不带** `?db=` 仍 200（缺省分支不查注册表）—— 同一个库两种结果。而 §5.4 明定**进程库不受 roots 约束**；且 D4 对**每个**请求都附 `?db=` ⇒ 选中进程库后整个 UI 报错（"默认打开即白屏"，正是 D3 §10.3 花笔墨避免的事）。

✅ **最终裁定（采纳评审的落点建议）**：
1. `nlink > 1` 检查 **MUST 只加在注册路径**，**MUST NOT 加在 `resolve` 的命中分支**。
   ⭐ **实现归属（D2 报，已裁定）**：函数 `admitForRegistration` 住在 **D2 的 `db-path-policy.ts`**（§8.1 导出面 **+1 行**），**唯一调用者是 D1 的 `register()`**。
   ⚠️ **MUST NOT 放在 `/api/databases/open` 的 handler 里** —— handler 只是 `register()` 的**一个**调用方；放那里就是「每个调用方都要记得调」，正是 §7.6 否过的「纪律性防线，漏一处就污染」。**守卫下沉到唯一入口**（与本轮 R6 →`openDatabaseReadonly`、归一化 →`key()` 同一判据）。
   ⚠️ **MUST NOT 进 `checkPathAllowed` / `resolve` 热路径**（否则误伤 `cp -al` 备份过的库 + `?db=<进程库>` 全站 409）。D2 的 B21 把「`checkPathAllowed` 对 nlink=2 **必须放行**」钉成断言。
   ⭐⭐ **「首次登记」的判据是 `!reg`（不在 `dbs` 里），MUST NOT 是 `!reg?.entry`**（D1 发现、D2 采纳、我复核）。
   理由：`evictBeyondLimit` **保留 `dbs` 条目而把 `entry` 置 `null`** ⇒「已登记、仅连接被驱逐」是**独立状态**。用 `!reg?.entry` 会产生**驱逐后**才触发的误伤：
   ```
   登记 → 夜间 cp -al 备份（nlink=2）→ 被 LRU 驱逐（entry=null）→ 用户再点一次「打开」
     ⇒ !reg?.entry 为真 ⇒ 重跑 nlink 检查 ⇒ 被拒   ← 正是要避免的误伤，且更难复现
   ```
   ⇒ 硬链接的准入判据属于**注册时刻**，与「连接是否还活着」无关。D2 的 B25 钉住这条。
   依据：roots 逃逸**必须由注册路径引入** —— 只有注册那一刻才需要证明「这个路径指向 roots 内」。已注册库的 `nlink` 从 1 变 2，只可能是**本机硬链接**（§8.1 已认领的攻击者类别），不构成新的 roots 逃逸。
   ⚠️ **`DbUnavailableError.reason` 可扩 `"hardlink"` 并映射 400 `bad_request`**（区别于 `path-escalated` 的 409）：依据 §4.6「手动路径不在允许 roots 内 → 400」，它是**准入阶段的路径形式拒绝**，不是「已注册资源事后漂移」。
2. **`adopt` 路径豁免**（与 §5.4「进程库不受 roots 约束」一致；`11` 亦明令 adopt MUST NOT 调 `checkPathAllowed`）。
3. R5（重开路径）重跑的是 **`checkPathAllowed`**，保持不动；**`nlink` MUST NOT 跟着进 `resolve`**，否则上面两条误伤都成立。
4. **注册后**才被外部建硬链接的情形 → 归 §8.1 类别，写进**已知限制**即可（建硬链接者已有该目录写权限）。

⭐ **这段的教训（已进 §12）**：**「加了检查」不等于「更安全」** —— 一个听起来零成本的前置条件，可能误伤正常用户，而误伤会**逼用户绕过整个防线**（比不检查更糟）。安全判据 MUST 先问「合法用户会不会被它挡住」。



⚠️⚠️ **R5 的实现必须是 fail-closed，`policy` MUST 必填**（安全评审发现，我已核实 `grep`）：
D1 的守卫写成 `if (this.policy && !this.policyCheck(path))`，且字段注释写「`null`/省略 = **不检查**」。而 `grep -n "new StoreRegistry(" plan/memory-web/*.md` 显示**三个生产构造点一个都没传 policy**（`11:1223`、`13:830`、`13:850`），**只有测试传了**（`11:1620`/`1621`）⇒ **C16/C17 会绿，生产里 R5 永远不生效**。

⚠️ 这与 D3 §4.5 为 `bindHost` 花整段警告的**是同一个失败模式**（测试绿、生产死代码），只是换成了 `policy`。

**裁定**：
1. `policy` 从 optional 改为 **必填**（`policy: PathPolicy`，去掉 `?` 与 `| null`）⇒ **忘记传 = 编译错误**，而不是静默关掉 roots 检查。**MUST NOT 保留 optional**。
2. 删除「省略 = 不检查」的措辞。`--allow-any-path` **只能**由 `PathPolicy.allowAnyPath` 表达（`checkPathAllowed` 已短路处理）—— `policy: null` 若也算「不检查」，等于给它造**第二个真相源**，且是 fail-open，违反仓库「禁第二约定」纪律。
3. 三个构造点同步补上 `policy: { roots, allowAnyPath }`。
4. ⭐ **验收必须加对照**：**不传 policy 的 registry，构造即报错**（把「忘传」变成不可能静默通过）。D5 的 C17 请加这条。
1b. ⚠️ **连带要求（D5 发现，我已核实）：`constructor(opts?: …)` 的 `?` MUST 一并去掉。**
   只把 `policy` 设必填、却让 `opts` 保持可选，会把 fail-closed **从外层绕回来**：`new StoreRegistry()` 在 `opts?` 下**合法**（编译期不报），运行时 `opts` 为 `undefined` ⇒ 读 `.policy` 抛（实测 `Cannot read properties of undefined`）或静默跳过检查。
   ⇒ `constructor(opts: StoreRegistryOptions)`。理由：**必填字段的「必填」会被外层可选性抵消** —— 这是 fail-closed 的常见漏法。
   ⭐ 判据：D5 的 `V6d`（`@ts-expect-error` + `new StoreRegistry({})`）**只有在这条也修了**才测得到它想测的东西。


⭐⭐ **R5 的守卫 MUST 豁免进程库（`pinned`）**（可行性评审发现，我已实测复核）：
D1 落的 R5 写成 `if (!this.policyCheck(path)) throw …`，**无 `pinned` 豁免** ⇒ 与 §5.4「进程库**不受** roots 约束」**直接冲突**：
```
--db /outside/process.db --roots /inside      ← §5.4 与 D1 §8.6 都明说此配置合法
R5 守卫：checkPathAllowed → {ok:false} → 抛 path-escalated → 409
而 §5.4 / D1 §8.6 / C13 / D3 §13#12 都要求 ?db=<进程库> MUST 200
```
**可达性很高，不是边角**：D4 在**首屏**（localStorage 空）就把 `selectedDb` 设为进程库路径（非 null）⇒ `withDbParam` 对**每个**请求都附 `?db=<进程库>` ⇒ 带 `--db` 在 roots 外的用户**一开页面就全站 409**，而**不带** `?db=` 仍 200（同一个库两种结果）。

⚠️ **这正是本节上文（§5.2 末）早已裁定过的形态** —— 那里说「放进 `resolve` ⇒ 进程库报错…且 D4 对每个请求都附 `?db=` ⇒ 整个 UI 报错」，并明确「**`adopt` 路径豁免**」。R5 犯了同一个错。

**修正**：`if (!this.pinned.has(path) && !this.policyCheck(path)) throw …`（`pinned` = 由 `adopt` 登记的进程库，只有 `cli.ts` 一处调用）。
**立意不受损**：SEC-02 的攻击面**全部**来自 `register` 的库（roots 内 symlink 被重定向），`pinned` 只有进程库。
⭐ **验收 MUST 加对照**：`--db` 在 roots 外时，`?db=<进程库>` MUST 200（C13 的对照）。⚠️ C16/C17 都无此例，**测不出来** —— 又一处「测试绿、生产红」。

⭐ **两条合并的通用判据（写进 §12）**：
> **一个守卫新增时，MUST 逐一检查它是否覆盖了「已明文支持的特例」。** 本次两处同型缺陷（nlink 误伤备份用户、R5 误伤 roots 外的进程库）都是**新守卫忘了给它早已裁定的例外留豁免** —— 而两处都表现为「合法配置下整个 UI 报错」，且**两处的测试都测不出来**。

⭐⭐ **`create` 的 store 归属：两处修法 MUST 合起来（可行性评审发现，我已实测）**
把步 7 从 `adopt` 改 `register` 解决了 `pin`，但**步 5 的 store 因此失去归宿**：
```
步5  openMemoryStore(resolved)   ← 契约 §5.3 明令建库必须走它
步7  registry.register(resolved) ← D1 的 register 内部走 resolve → openInto → **再调一次** openMemoryStore
```
两个调用都在**同一个同步 handler** 内 ⇒ `inflight` 去重**无效**（第一次的 Promise 已 settle，不是并发窗）。实测确认：两次 `openMemoryStore` 返回**不同对象**。
⇒ 同一路径两个 `MemoryStore`/两条连接，步 5 那个**既没被 close 也没交给任何人**（`register` 只收 `raw: string`，收 store 的是 `adopt`）。
**危害**：违反 §3.2#2「同一路径在进程内 MUST 只有一个 StoreEntry」，进而破坏它支撑的 §2.2/§7.4 —— 两个 detector 各读各的 `data_version` ⇒ `/api/events` 的 `changed` 失真（D5 的 V3c 正是断这个）+ fd 泄漏。

**裁定（二选一，MUST 明确写进文档）**：
- **(a)** 步 5 建库后**立即 `close()`**，步 7 由 `register` 重开（干净，多一次开/关）；**或**
- **(b)** 给 `register` 加一个收 store 的重载（内部 `dbs.set` 但**不 pin**），复用步 5 的连接。
⚠️ **MUST NOT 只做其中一半** —— 两个修法各解决一半，漏一个就回到「双连接」或「永久 pin」。

**另**：`DatabaseOpenedDTO` 要求 `node_count`/`world_time`，而 `create` 的步骤表**未规定它们的来源**（`/open` 的 §4.3 步 4 写了「用 `entry.store` 填」）⇒ MUST 与 §4.3 同款补一句。

⭐ **这是本轮第三次「修 A 引入 B」**（nlink 落点、R5 豁免、本处）—— 已进 §12：
> **修一个"调用点"缺陷时，MUST 重新检查被改动那个调用点的全部契约义务**（所有权、去重、幂等），而不只是被报告的那一条。
本次三次的共同形态：**修好被指出的那条，破坏了它旁边没人提的那条。**
⭐ **通用判据（写进 §12）**：**安全开关的缺省值 MUST 是「最严」，且缺省路径 MUST 能被编译期或测试抓住。** 一个「忘了就静默关掉」的安全检查，比没有检查更危险 —— 它给出虚假的安全感。
⚠️ **R6 的落地位置（安全评审补充）**：`openDatabaseReadonly` **同时**是 `probeMemoryDb` 的入口 → 守卫 MUST 做在 **`openDatabaseReadonly` 内部**，**MUST NOT** 只在 `readMemoryDbStats` 里补一句（那会漏掉另一条入口）。
⚠️ **第二条可达链（评审补充）**：D1 §6.2.4 的候选过滤**只依赖「`Dirent.isFile()` 已给类型」、以性能为由不 stat** —— 这是**实现措辞里的隐式依赖**。若实现者顺手改成按文件名过滤（`e.name === "memory.db"`，一个完全符合文档措辞的写法），FIFO 就会进候选 → `readMemoryDbStats` 立刻挂死。⇒ 该处 MUST 写成硬要求：候选收进 `paths` 前 MUST 判 `Dirent.isFile()`（FIFO 的 `Dirent.isFile()` 为 false，实测）。

⚠️ **已登记的 DoS（评审补充，低危但如实记录）**：`discoverMemoryDbs` 是**同步 `readdirSync`**。实测 `~/projects`（11345 目录）一次扫描**同步阻塞事件循环 2699 ms**（`hackathon` 为 71 ms）。5s TTL 只摊薄**频率**，不消除**单次阻塞**；在 `--roots ~` 这类配置下，任意一个跨源 GET（S3 不查 GET 的 Origin）都能拉到 `/api/databases` 触发它。
→ 本期**不改异步**（改动面大），但 MUST 写进 `15` 的已知限制与 README；若 `roots` 宽泛，用户应知道首次列库会卡一下。
⚠️ **`create`（不存在的目标）不适用第 3 步**：目标路径**尚不存在**，`stat` 必然 ENOENT。`create` MUST 走第 2 步的**逐段真实解析**（`realpathWalk` 逐段走到不存在处即停；目标不是 dangling link 时 `uncertain === false`，判定落在**已存在的最深祖先的真实路径**上）；**MUST NOT** 因"文件不存在"而拒绝新建 —— 否则全部 create 都被误拒。
⚠️ **更正（安全评审指出，我核实）**：此处初版写「双重包含性（对最深已存在祖先 realpath）」—— 那**正是被实测证伪的 v1 形态**（`12:104`/`12:877` 记录的真实逃逸），且与本节上文（§5.2#2 定稿为「逐段真实解析 + 一致性断言」）**自相矛盾**。`create` 恰恰是最需要谨慎的路径（它会灌表）。语义不变，仅措辞归正。

⚠️ **诚实登记的残留（D2 报告，我认可）**：第 2 步通过后、`openMemoryStore` 打开前存在 **TOCTOU 窗口**（该窗口内把文件换成 symlink）。彻底防护需 `O_NOFOLLOW`，而 `node:sqlite` 不暴露该选项 → **本设计防不住**，风险与代价如实记录（§11 U5）。

⭐ **判据（可机械核验）**：对任意普通 SQLite 文件调用注册入口，该文件的**表集合与 md5/mtime MUST 不变**（§9 反证用例）。

### 5.3 规则 R2：新建库必须显式确认

`POST /api/databases/create` 的 body MUST 含 `confirm: true`，否则 `bad_request`。
理由：路径不存在时**静默新建**会把用户的笔误变成一个莫名其妙的文件；`confirm` 让前端必须弹一个说明"将新建空记忆库"的确认框。
新建库 MUST 走 `openMemoryStore`（它建表，这是期望行为），**MUST NOT** 走只读探测。

### 5.4 规则 R3：可选路径受 roots 约束

- roots 来源：CLI **`--roots <dir>`（可重复）**；缺省 `[process.cwd()]`。
- 缺省**不含** `$HOME` 或 `/`：防止"默认就能读整机"。
- 逃生舱：**`--allow-any-path`**（显式开启后跳过 §5.2#2 的包含性检查）。开启时 CLI MUST 在 stderr 打印醒目警告（沿用 `warnIfNonLoopback` 的风格，`server.ts:53`）。

⭐⭐ **实现必须显式化（安全评审 SEC-05）**：§5.5 本条要求「`?db=` 只接受进程库」，但 D3 的 `resolveTargetContext` **只对管理路由**判 `multiDbEnabled(ctx.bindHost)`，`?db=` 分支**无此判断**。
它在非回环下之所以仍返回 404，是因为「管理路由全 403 ⇒ 发现不跑 ⇒ 注册表只有进程库」—— **偶然成立，不是机制保证**。一旦将来新增任何注册入口（如 U3 的 settings roots），非回环部署会**静默恢复成「局域网任何人可读写任意已注册库」**。
→ **MUST** 在目标库解析处显式加：`if (!multiDbEnabled(bindHost) && candidate !== 进程库路径) return 404`。
→ ⚠️ **D5 的 V5c 会因此假绿**（它断言的 404 来自「未注册」而非闸门）—— 须改为断言「闸门本身拒绝」。

⚠️ **连接所有权（安全评审 SEC-06）**：`create` 由 handler `openMemoryStore` 后用 `registry.adopt` 登记，而 `adopt` **无条件 pin**、`closeEntry` 对 pinned **只解引用不 close** → 每个经 create 新建的库**永不被驱逐、也永不被关闭**（进程退出时 `closeAll` 也跳过）。
→ **MUST** 让 create 走 registry 自开连接的路径（`register`/`openInto`），或让 registry 拥有该连接。否则 D5 的 V6（`openCount <= limit`）在做过 create 的会话里无法成立。

⭐ **本节原则（本轮最重要的血教训）**：
> **安全属性不只在算法里，还在调用点上。**

安全评审以内核真值做 oracle、跑了 **4 万例 fuzz**，结论是 `checkPathAllowed` **本身攻不破（零真实逃逸）**；而三条高危/中危洞（SEC-02/03/04）**全部在「算法之外、别的调用点」** —— 守卫只跑一次、守卫漏装一个调用点、守卫对硬链接无效。
⇒ **写安全代码时，审查对象 MUST 包含「这个检查被调用了几次、被哪些路径绕过」，而不只是「这个检查对不对」。**
- `--roots` 与 `--db` 的关系：进程库**不受** roots 约束（它是用户显式指定的，可信）。

### 5.5 ⭐ 规则 R4：非回环绑定 ⇒ 多库**整体禁用**

若 `--host` 不是回环（`isLocalBind(host) === false`，`security.ts:28`）：

- `/api/databases`、`/api/databases/open`、`/api/databases/create` **MUST 全部返回 403**（`forbidden_origin`）。
- 发现扫描 **MUST NOT 执行**（列出路径本身是信息泄漏）。
- 全部数据路由的 `?db=` **MUST 只接受进程库**；其他值一律 404。
- **只有**进程库仍可读写（即退化为当前单库行为）。

理由：非回环时服务对网络可达，而无认证 + 可注册任意路径 = **网络上的任何人都能读写你机器上任意 SQLite 文件**。这是不可接受的权限提升，故整体禁用。

### 5.5b ⭐⭐ 规则 R5：**懒打开（重开）必须重跑路径策略**（安全评审 SEC-02 发现，我已复现）

⚠️ **这是本设计最严重的一处缺口**，且它不在算法里、在**调用点**上：
§5.2 的 R1 原本只在**注册**时执行一次，而 D1 的 registry **懒打开**路径（`resolve` → `openInto` → `openMemoryStore`）只做 `statSync(path).isFile()`。于是：

```
① 注册时：roots/linkin -> roots/real（roots 内，合法，必须放行）
② 攻击/漂移：把 roots/linkin 重指向 /tmp/out/lib.db（roots 外，普通 SQLite 文件）
③ 下次懒打开（LRU 驱逐后必然发生）：
     statSync(id).isFile() === true        ← registry 的守卫，通过（实测）
     realpathSync(id) === /tmp/out/lib.db  ← 已在 roots 外（实测）
     checkPathAllowed(id) → 会拒，但 **重开路径不调它**
   ⇒ openMemoryStore 把 roots 外的文件从 1 张表灌到 24 张
```

⚠️ **与已登记的 TOCTOU（§11 U5）不是同一件事**：U5 是「`checkPathAllowed` 之后、`openMemoryStore` 之前」的**单次系统调用窗口**；本条是**守卫完全不覆盖的生命周期** —— 注册与打开在时间上分离，检查只做一次，**且不需要赢任何竞态**（LRU 驱逐后的下一次请求就自动重开）。

**规则 R5（MUST 实现）**：registry 的懒打开分支 MUST 在 `openMemoryStore` **之前**重跑 `checkPathAllowed(policy, path)`。
- 拒绝 → `DbUnavailableError("path-escalated")` → **409**（沿用 §4.6，不新增码），且 **MUST NOT 从注册表移除**（沿用 §3.2#5「不静默」）。
- ⭐ **判据（可机械核验）**：注册一个 roots 内的 symlink 库 → 重定向该 symlink 到 roots 外 → 发请求 → MUST 被拒，且**受害文件的表集合与 md5 不变**。
- ⭐ **更省的等价做法**：注册时刻记录 `realpath`，重开时比对；不一致即拒。二者择一，MUST 二选一，MUST NOT 都不做。

⚠️ **由此得出的通用原则（本轮血教训，写入 §12）**：**安全属性不只在算法里，还在调用点上。**
`checkPathAllowed` 本身通过了 4 万例 fuzz（评审以内核真值做 oracle，零真实逃逸）—— **算法是对的，洞在"谁调用它、调用几次"**。

### 5.5c ⭐ 规则 R6：类型检查 MUST 下沉到**唯一的只读打开点**（安全评审 SEC-04 发现）

§5.2#3 原本把 `stat().isFile()` 写成「注册的硬前置」，D1 把它装在 `probeMemoryDb` 与 `registry.resolve` 两处。但 registry 里还有**第三个只读打开点**：`readMemoryDbStats`（`/api/databases` 的未打开库走它）—— **没有守卫**，直接 `openDatabaseReadonly`。

可达链：已注册库被 LRU 驱逐（8 上限下**必然**发生）→ 列库时走它 → 若该路径上的文件已变成 FIFO → ⚠️ **整个 web 进程挂死**（`DatabaseSync` 是同步 API，占住事件循环）。这正是 §5.2#3 称为「硬危害」的那件事。

**规则 R6（MUST 实现）**：`openDatabaseReadonly` **内部** MUST 自己做 `statSync(path).isFile()` 守卫，**MUST NOT 依赖调用方**。
理由：约定「调用方记得检查」在三个调用点就漏了一个；把守卫下沉到唯一的只读打开点，才不可能漏。
⭐ **判据**：对 FIFO 调 `readMemoryDbStats` MUST 快速返回（不得挂死）；测试 MUST 用 `timeout` 包裹（否则测试自己挂死）。

### 5.6 沿用不变的部分

- S2 `Host` 检查、S3 `Origin` 检查（`security.ts`）**不改**。
- 不引入 token / session / 登录（M5）。
- 写路径仍 MUST 走 `MemoryStore` 方法（`00` §9.1 纪律 2），本功能**不新增任何直接 SQL 写**。

### 7.6 ⭐ 前端缓存的「库身份」判定（D4 报，我核实后裁定）

**判据（通用，可机械核验）**：`grep -n "Cache\|new Map" src/web/assets/views/*.js src/web/assets/app.js` ——
任何缓存若**值来自某个库的查询结果**、**键里却没有库路径/库标识**，切库后就会**读 A 写 B**。

**已核实的违规**：`tree.js:15` `treeCache` 键 = `${domain}|${parentUri ?? ""}`（`tree.js:104/112/117/159/183/392/398/411` 共 8+ 处读写），值是该 domain 的子树 → **不含库标识**。它同时服务 `#/tree` 与常驻侧栏 ⇒ 切库后侧栏/树页可能显示**上一个库的行**，而写操作打在新库上。

**裁定（两道防线，互补）**：
1. ⭐ **强修法（D2 认领，改 `tree.js`）**：在 `mountSidebar` / `mountTree` **入口**比对本模块记录的「缓存所属库」与「当前库」，不一致则整体失效。
   理由：改键要覆盖 8+ 处 `get/set`，**漏一处在切库后就出脏读**；入口比对是**单点**，更难漏。
   （D3 给的判据我认同：`ChangeDetector` 之所以不会读 A 写 B，是因为库身份**挂在 store 实例上、不是调用方传的**（`runtime.ts:15`）—— 同构修法就是把库身份作为缓存自身的一部分。）
2. **第二道（D4，`app.js`）**：`switchDatabase()` 先 `treeCache.clear()`（复用 `reloadAll()` 既有动作，`app.js:443-449`）。
   ⚠️ **MUST NOT 只靠这一道**：它是纪律性的，任何新切库路径漏掉就会污染。

**D4 另认领**：`renderSidebar`（`app.js:368-392`）缺 `mountSeq`（`app.js:310/344`）那样的序号守卫 → 切库时两次并发 renderSidebar 会让慢的**后落地**覆盖新库侧栏 → 补 `sidebarSeq`。

**D1 自查结论（记录在案，无需改）**：其 `statsCache` 键 = 绝对路径（= 库 id，天然含身份）；`scanCache` 值 = 路径列表（不含库状态）。二者**都不是**此类缺陷。

### 7.7 `?db=` 是**惰性**参数，MUST NOT 当全局状态注入

D3 提出（我认同）：`?db=` 在 `GET /`、`/assets/*` 与 3 条库管理路由上是**惰性**的（§3.4、§4.1）。
前端 MUST 在**两个具体注入点**（`app.js` 的 `get`/`post`）附加它，**MUST NOT** 把它做成"全局状态"再统一注入（如从 `location.search` 取）—— 那会把惰性参数变成到处都有的噪声。
⚠️ 实测接缝：`app.js:111-124` 的 `post(path, body)` **当前没有 query 槽** → D4 MUST 显式加一个参数（例如 `post(path, body, query)`）。

⭐⭐ **拼接顺序 MUST 是「先拼完整 URL（`path + buildQuery(query)`），再交给 `withDbParam` 判分隔符」**（D4 实测发现，我复核）：
若反过来先给裸 path 套 `withDbParam`、再后拼 query，分隔符判定看到**没有 `?` 的 path** 于是插入 `?db=…`，接着后拼的 query 又自带 `?` → 产出**第二个 `?`**，后续参数被吞进 `db` 的值里。
坏产物（D4 实测）：`/api/tree?db=%2F…memory.db?domain=core` —— `domain` 进了 `db` 的值 ⇒ **切库后所有带 query 的请求全部打到错库或 400**。
正确产物：`/api/tree?db=%2F…&domain=core`。
判据：D4 用拟实现纯函数跑 15 条（含 `&` 分隔符、含 `&`/`?`/空格 的怪路径 roundtrip、3 条库管理路由不带参数），修后 15/15。
D3 的接缝描述（§10.4）若写成 `withDbParam(path) + query` 会复现同一 bug —— 已提醒。

⭐⭐ **`db` 值的编码：MUST 用 `URLSearchParams` 的 `.set()` / 对象构造（推荐），或等价的 `encodeURIComponent`；MUST NOT 把库路径拼进 query 字符串再交给 `URLSearchParams` 解析。**（D4 报，安全评审纠正，我已实测四种形态）

⚠️ **更正（安全评审，我已逐字复现）**：初版写「MUST NOT 用 `URLSearchParams`」**机制说错了，且修法会引入更严重的 bug**。实测：
```
path = "/a+b/x.db"                      服务端 searchParams.get('db') 读回
  A new URLSearchParams({ db: p })      → "db=%2Fa%2Bb%2Fx.db"  → "/a+b/x.db"  ✅ 无损
  B q = new URLSearchParams(); q.set()  → "db=%2Fa%2Bb%2Fx.db"  → "/a+b/x.db"  ✅ 无损
  C encodeURIComponent                  → "db=%2Fa%2Bb%2Fx.db"  → "/a+b/x.db"  ✅ 无损
  D 手写不编码（反例）                    → "db=/a+b/x.db"         → "/a b/x.db"  ❌
  E new URLSearchParams("db=/a+b/x.db") ← **把路径当 query 字符串解析** → "/a b/x.db" ❌ 唯一会坏的形态
```
⭐ **`+`→空格 只在「把路径当 query 字符串解析」（形态 E）时发生**；对象构造与 `.set()` 都正确编码 `+`。真正该禁的是**字符串解析形态**，不是 `URLSearchParams` 本身。
⚠️ **措辞更正（D4 实测，我复核）**：A/B/C 三种产物**并非逐字节相同** —— 差别在**空格**与**加号**的编码选择：
```
path = "/tmp/a b+x.db"
  对象构造 / .set()  →  db=%2Ftmp%2Fa+b%2Bx.db    （空格→'+'、加号→%2B）
  encodeURIComponent →  db=%2Ftmp%2Fa%20b%2Bx.db  （空格→%20、加号→%2B）
```
⇒ 正确表述是「**三者都能正确 roundtrip**」，而非「产物等同」。**口径落在「不要用字符串拼/解析 query」**，而不是「等价编码」。
⭐ 两侧只需**语义一致**：服务端用同一套 `URLSearchParams` 解码（`new URL(req.url).searchParams`）即可 —— 它把值里的 `+` 解回空格、`%2B` 解回 `+`，与编码侧对偶。

⭐⭐ **为什么推荐 `.set()` 而不是手拼（这条更关键）**：`.`set()` 会**替换**同名键，手拼会产出**重复 `db=`**：
```
base = "/api/meta?db=%2Fold.db"
  URLSearchParams.set       → "/api/meta?db=%2Fa%2Bb%2Fx.db"                     读回 "/a+b/x.db" ✅
  encodeURIComponent 手拼    → "/api/meta?db=%2Fold.db&db=%2Fa%2Bb%2Fx.db"         读回 "/old.db"   ❌ 打到**旧库**
```
⇒ 按初版「MUST NOT `URLSearchParams`」实现，会**逼实现者手拼**，反而引入「重复 `db=` ⇒ 打到错库」这个**比原 bug 更严重**的问题。

**冻结口径**：
- `db` 值 MUST 经 `.set()` / 对象构造（推荐）或等价的 `encodeURIComponent` 编码；
- **MUST NOT** 把库路径拼进 query 字符串再交给 `URLSearchParams` **解析**；
- **MUST NOT** 手拼追加 `db=`（会产生重复键）；
- 服务端用 `new URL(req.url).searchParams` 解即可（它不解析 `+` 为空格的问题在于**收到什么就是什么**）。
判据：D4 的 15 条纯函数用例（覆盖 `+`/空格/`&`/`?`/`#` 五种怪路径 roundtrip）保持有效，**另加**一条「base 已有 `db=` 时 MUST 替换而非追加」。

## 12. 纪律

1. **契约一改立刻广播**：本文件改动 MUST 通知全部在跑的文档子代理（`hub send`）。
   ⚠️ 教训（`00` §16.11）：`send to:"all"` **只覆盖当时 active 的 peer**；收工的 peer 收不到。缓解：逐个核对文档 mtime ≥ 本文件 mtime，并要求 `file:line` 回执。
2. **跳过全量测试**：子代理 MUST NOT 跑 `npm run check` / 全量 vitest / 全量 lint。主 agent 统一在验收阶段跑。
3. **发现重大冲突立刻用 `hub` 报**，不要憋到 yield。
4. **事实与推断**：沿用 `00` §15 —— 实测标"实测"，推理标 `[INFERENCE]`。
5. ⭐⭐ **安全属性不只在算法里，还在调用点上**（安全评审血教训）：评审以内核真值做 oracle、跑 4 万例 fuzz，结论是 `checkPathAllowed` **算法本身攻不破**；而三个高危/中危洞（SEC-02/03/04）**全在「算法之外、别的调用点」**。
   ⇒ 审安全代码时，审查对象 MUST 包含「**这个检查被调用了几次、被哪些路径绕过**」，而不只是「这个检查对不对」。
6. ⭐⭐ **「加了检查」不等于「更安全」**（同上，我本人犯错）：我曾采纳「`nlink > 1` 就拒绝」，理由「合法库 nlink 恒为 1、零成本」。评审推翻 —— `cp -al` 备份后**用户自己在用的库** nlink 就是 2（我复现确认）。
   ⇒ 听起来零成本的前置条件可能**误伤正常用户**；误伤会**逼用户绕过整个防线**，比不检查更糟。安全判据 MUST 先问「**合法用户会不会被它挡住**」，再问「攻击者能不能绕过」。
7. ⭐ **主 agent 的裁定 MUST 可被下游用证据推翻，推翻后立刻改正并广播**。本轮主 agent 被下游顶翻 **14 次**（含 3 次安全结论、`scanned` 语义、`lstat`、NUL、库数口径、路由数……），每次都改进了设计。**这是流程在起作用，不是流程失败。**
