## §1 一句话定位

**把「版本不匹配就抛错拒绝启动」改成「v2 就地升级到 v3、不丢一行数据、可回滚、跑两遍结果一致」**：迁移器装在 `createSchema` 内（唯一收口点），结构变更与版本号在**一个事务**里原子提交，被 DROP 的 `node_fts` 内容由 **store 的 `reindexNode` 重算**，并用一个持久 marker 让「结构已提交、重算未完成就崩溃」可自愈。

## §3 行为契约逐步（每步写「漏了会怎样」）

### 步 1 — 读版本（`readSchemaVersion` 不动）

`createSchema` 第一件事仍是 `readSchemaVersion(db)`（`schema.ts:150-161`，吞异常返回 `null`）。

- `null` = 全新库 / `memory_kv` 缺失 / 陌生 SQLite 文件 → **走建库分支，行为与今天逐位一致**。
- `"3"` = 已是最新 → 只 `exec(STATEMENTS)`（全 `IF NOT EXISTS`，空操作）。
- `"2"` = 走迁移（步 3 起）。
- **其他任何值**（含 `"1"`、`"99"`、`"abc"`）→ **保留今天的抛错分支**（步 2）。

**漏了会怎样**：若把「非 v3」一律当可迁移，遇到未来版本或损坏的版本号会拿旧代码去改新库 —— 静默破坏。

### 步 2 — 版本裁决（三个分支，不是两个）

```ts
const stored = readSchemaVersion(db);
const needsMigration = stored !== null && stored !== SCHEMA_VERSION;

if (needsMigration && !MIGRATABLE_FROM.includes(stored)) {
    throw new Error(
        `memory database schema v${stored} is incompatible with this build (v${SCHEMA_VERSION}). ` +
        `There is no in-place migration from v${stored}: back up the file and cold-start a fresh database ` +
        `(point memory.dbPath / --memory-db elsewhere), or use a build that can migrate it.`,

}
```

**「`incompatible with this build`」前缀逐字保留**：`src/web/routes.ts:128` 用 `msg.includes("incompatible with this build")` 映射成 409 `invalid_db`；`test/web/api.test.ts:866-873, 965-968` 依赖该映射。**改前缀 → 409 静默退化成 500 `internal`**（T5 型）。

**只改第二句**：原文「There is no in-place migration: delete the file …」在 v2 上**变成假话**。新文案把「无就地迁移」限定到 `from v${stored}`，并保留 `--memory-db` 逃生口的指引（`packages/coding-agent/src/cli/args.ts:239-240` 是该 flag 的真实定义处）。

**漏了会怎样**：① 前缀被改 → 409 映射静默失守；② 文案不改 → 用户按提示删库，而库本来能救。

### 步 3 — 结构迁移（幂等性的真正来源）

```ts
function migrateV2(db: MemoryDatabase): void {
    // ⚠️ 判据是「列在不在」，不是「版本号是多少」。见 §11-C1 的实测反例。
    if (!hasColumn(db, "aliases", "disclosure"))
        db.exec("ALTER TABLE aliases ADD COLUMN disclosure TEXT");
    if (!hasColumn(db, "edges", "disclosure"))
        db.exec("ALTER TABLE edges ADD COLUMN disclosure TEXT");

    // ⚠️ FTS5 不能 ALTER；且 `CREATE ... IF NOT EXISTS` 撞同名旧表是**静默空操作**（实测）。
    //    必须显式 DROP。DROP TABLE 会连带删掉全部 5 张 shadow 表（实测）。
    if (!hasColumn(db, "node_fts", "disclosure")) {
        db.exec("DROP TABLE IF EXISTS node_fts");
        db.exec(NODE_FTS_DDL);
    }

    db.prepare("INSERT OR REPLACE INTO memory_kv (key, value, updated_at) VALUES (?, ?, ?)")
        .run(SCHEMA_VERSION_KEY, SCHEMA_VERSION, new Date().toISOString());
    db.prepare("INSERT OR REPLACE INTO memory_kv (key, value, updated_at) VALUES (?, ?, ?)")
        .run(FTS_REBUILD_KEY, "1", new Date().toISOString());
}
```

三条实测支撑（`probes-d3/{probe6,probe7,migrate-timing}.mjs`）：

1. **`CREATE VIRTUAL TABLE IF NOT EXISTS node_fts ...(三列)` 撞上已存在的两列 `node_fts` 会静默保留两列**（`PRAGMA table_info` 返回 `['node_id','text']`）。⇒「把 STATEMENTS 那行 DDL 改成三列就完事」是**错的**，必须 DROP。这是契约 §8 **T9** 的具体形态，也是本轮最容易踩的坑。
2. `DROP TABLE node_fts` 连带删除 `node_fts_data/_idx/_content/_docsize/_config`（实测：DROP 前 6 个对象、后 0 个）。无需手工清 shadow 表。
3. `ALTER TABLE ... ADD COLUMN` 重复执行抛 `duplicate column name`（实测）。⇒ **必须 `hasColumn` 门控**。

**`node_fts` 的内容不在这里重建**，是**空的**。两个理由：
- 重算是 `reindexNode` 的职责（唯一 tokenizer 真相源，`tokenize.ts:59` 要求写入侧与查询侧同一 token 空间），在 `schema.ts` 复制一份 token 化公式 = D2 明确否决的双真相源。
- 旧 `text` 列里的 disclosure 是**混在正文里的**（`reindexNode` 今天就是 `[uri, disclosure, content].join(" ")`，`store.ts:1429`）。旧内容原样留在 `text`、新 `disclosure` 列为空 → 「纯 disclosure 命中」双重计分（D2 论据）。

**旧 `text` 可完整重建**（不丢信息）：`reindexNode` 只读 `nodes.uri / nodes.disclosure / nodes.content`（`store.ts:1420-1429`）与 `glossary.keyword`（`store.ts:1424-1428`）。两张表都不在迁移改动范围内 ⇒ DROP 掉旧索引**不损失任何可重建信息**。

**漏了会怎样**：① 不用 `hasColumn` 门控 → 第二次打开抛 `duplicate column name`，**开库直接失败**；② 不 DROP 直接跑新 DDL → 列还是两列，D2 的 `bm25(node_fts, 0.0, 1.0, 1.0)` **报错或静默错列**；③ 在 schema.ts 重算 → 双 tokenizer 真相源。

### 步 4 — 迁移前自动备份

```ts
function backupBeforeMigration(db, fromVersion) {
    const file = databaseFilePath(db);           // PRAGMA database_list 的 main.file
    if (!file) return { skipped: "in-memory database" };
    const stamp = new Date().toISOString().replace(/[-:]/g, "").replace(/\..+/, ""); // YYYYMMDDTHHMMSS
    // ⚠️ 时间戳只到秒 ⇒ MUST 处理撞名，否则同一秒内第二次迁移被 VACUUM INTO 拒绝（§11-C10）。
    let target = `${file}.pre-v${fromVersion}-${stamp}.bak`;
    for (let i = 2; existsSync(target); i++) target = `${file}.pre-v${fromVersion}-${stamp}-${i}.bak`;
    // ↑ `existsSync` 来自 `node:fs` —— schema.ts 目前不 import 它，需新增该 import。
    try {
        db.prepare("VACUUM INTO ?").run(target);  // ⚠️ 绑定参数形式可用（实测）
        return { path: target };
    } catch (error) {
        return { skipped: (error as Error).message };
    }
}
```

- **备份放在 `BEGIN` 之前**：`VACUUM INTO` 在事务内抛 `cannot VACUUM from within a transaction`（实测）。
- **用 `VACUUM INTO` 而不是 `cp`**：`VACUUM INTO` 读的是**连接视角**，因此**包含 WAL 里未 checkpoint 的数据**。可复现对照见 `probes-d3/wal-vs-cp.mjs`（合成库，危害必现：裸 `cp` 丢 1 行 nodes + 1 行 raw_log，`VACUUM INTO` 与 live 一致）；§10.4 有完整输出。
  > ⚠️ **顺序不能反**（RevHonesty 指出、主 agent 已改契约 §7 门槛 9）：**先对源库 checkpoint，`cp` 才可能正确**；事后对**副本** checkpoint **无效** —— 副本读到的已是主库文件的旧快照，缺的 WAL 数据根本不在副本里。契约定稿的写法是「**先对源库 `wal_checkpoint` 再 `cp`，或一律 `VACUUM INTO`**」。本设计的备份实现**选后者**（单条语句、无时序依赖）。
  > ⚠️ **真库引用纪律**：MUST 写**全路径**，MUST 复跑一致。本机有 9 个 `elias/memory.db`，同一 `.pi/` 下 3 个版本并存 —— 漏路径或漏 WAL 都会得到「同一脚本两次跑出不同数字」。
- **失败不阻断迁移**。理由：`nodes` / `aliases` / `edges` / `raw_log` / `node_revisions` **一个字节都不改**（步 3 只 ALTER 加列 + DROP 派生索引）；DDL 全在一个事务里，失败即整体回滚（实测见 §10.4 门槛 4 段：事务内抛错后 `node_fts` 列与 `nodes` 行数**完整回到事务前**，marker 不存在）。⇒ 备份是**针对未知问题的冗余**，不是原子性的必需品。备份失败时**大声报告**（§5），不静默（契约 §9.1）。
- **命名先例**：本机已有 `~/.pi/settings.json.bak`、`world/magnolia/elias/.pi/memory.db.pre-elias-migration-20260914` ——「迁移前留一份同名旁支文件」是本仓既有习惯。
- **成本**：真库（125 节点）`VACUUM INTO` = **24.3 ms / 11,501,568 bytes**。
- ⚠️ **备份路径 MUST 处理撞名**（见 §11-C10）：时间戳只到秒，同一秒内两次迁移会撞名，而 `VACUUM INTO` 对已存在目标抛 `output file already exists`。原设计只靠时间戳**不够**。

**漏了会怎样**：① 用 `cp` → 静默丢最近事务；② 放进事务 → SQLite 直接报错，迁移整条路径失败；③ 备份失败就中止 → 为一个冗余步骤把记忆系统整个关掉（比今天更差）；④ 备份失败静默 → 用户以为有备份，实际没有。

### 步 5 — 结构迁移与版本号在同一事务内提交

```ts
if (needsMigration) {
    const backup = backupBeforeMigration(db, stored!);       // 事务外
    db.transaction(() => migrateV2(db));                      // 一个事务：ALTER + DROP + CREATE + 版本号 + marker
    process.stderr.write(`[memory] schema v${stored} → v${SCHEMA_VERSION} migrated in place` +
        ("path" in backup ? `; backup: ${backup.path}` : `; backup skipped: ${backup.skipped}`) + "\n");
    // ⚠️ 这是 stderr，**不是** audit_log —— 见 §5.1 的裁定（迁移器不写 audit 事件）。
}
for (const sql of STATEMENTS) db.exec(sql);                   // 全是 IF NOT EXISTS
```

**事务边界**：`db.transaction`（`driver.ts:57-67`）用 `BEGIN` / `COMMIT` / `ROLLBACK`。DDL 原子性已实测（`probes-d3/verify.mjs` 门槛 4 段：事务内 ALTER + DROP + CREATE + marker 后抛错，`node_fts` 列与 `nodes` 行数**完整回到事务前**，marker 不存在）。

**为什么新版号必须和 DDL 同一事务**：见 §11-C1 —— 若版本号先提交、DDL 后失败，库里就是「声称 v3、实际两列」的自相矛盾状态，且迁移器不会再被触发。

**`STATEMENTS` 顺序**：改造后 `exec(STATEMENTS)` 在迁移之后跑；因为全 `IF NOT EXISTS`，对已迁移的表是空操作。**`schema.ts:78` 那条 `node_fts` 必须替换为 `NODE_FTS_DDL` 常量引用**，否则 DDL 有两份副本，将来改一处漏一处。

**漏了会怎样**：① 版本号与 DDL 分两个事务 → 崩溃点产生「谎报版本的库」（§11-C1）；② `STATEMENTS` 里留旧的两列 DDL → 新库建出来仍是两列，D2 全盘失效；③ 迁移放在 `exec(STATEMENTS)` 之后 → `CREATE INDEX IF NOT EXISTS` 等语句在旧表上先跑，可能抛 `no such column`（`schema.ts:124-129` 的注释正是这个历史教训）。

### 步 6 — 持久 marker：让「结构已提交、重算未完成」可自愈

`migrateV2` 写 `memory_kv.fts_rebuild_pending = "1"`，并在**成功重算之后**删除。

`MemoryStore` 构造器末尾：

```ts
private _healPendingFtsRebuild(): void {
    let pending: string | null = null;
    try { pending = this.getKv(FTS_REBUILD_KEY); } catch { return; }  // 表不存在 = 不是我们的库
    if (pending === null) return;
    this.reindexAll();                                                // D2 的批量入口
    this.db.prepare("DELETE FROM memory_kv WHERE key = ?").run(FTS_REBUILD_KEY);
}
```

**为什么落在构造器而不是 `openMemoryStore`**（`index.ts:123-127`）：

| 入口 | 是否经过 `openMemoryStore` |
|---|---|
| 生产：`cli.ts:197`、`registry.openInto`（`registry.ts:384`）、`agent-session.ts:231`、`extensions/memories/index.ts:36` | ✅ |
| 测试：`test/*.test.ts` 的 7 处直调、`coding-agent/test/memory-module.test.ts:47-49` | ❌ 直接 `createSchema` + `new MemoryStore(db)` |

`new MemoryStore(db)` 是**所有**路径都经过的那一步。把自愈放在那里，「必须记得调 reindexAll」这条**调用方纪律就不存在了** —— 这正是 `openDatabaseReadonly` 把类型守卫下沉到单点（`driver.ts:90-98`）与 `registry.openInto` 声明自己是唯一开库点（`registry.ts:379-382`）的同一套做法。

**成本**：每次 `new MemoryStore` 多一次 `SELECT value FROM memory_kv WHERE key='fts_rebuild_pending'`（走主键，亚微秒级）；只有 marker 存在时才付重算代价。

**顺序**：`reindexAll` 必须先于清 marker。若反过来（先清后算），崩溃窗口 = 「无 marker + 空 FTS」= **永久静默失效**（召回恒 0 命中）。这是本设计里**唯一**会把「可自愈」变成「不可自愈」的次序错误，§10 T-5 有专门断言。

**重算成本实测**（真库，`probes-d3/migrate-timing.mjs` / `timing3.mjs`）：

| 规模 | 耗时 |
|---|---|
| 120 节点（首次冷启动，含 jieba 初始化） | **391.6 ms** |
| 120 节点（jieba 已热） | **195.3 ms** |
| 5000 节点合成库 | 5,105.8 ms（**1.02 ms/节点**） |

⇒ 单次开库多 ~0.4 s 上限，一次性，可接受。**不做增量/分批**（§12-Q4 记录该判断）。

**漏了会怎样**：静默空召回；且用户与后续开发者都无从判断（`/api/meta` 计数仍正常、`nodes` 完好）。

### 步 7 — 版本号写入路径

今天只有 `stored === null` 时才写版本号（`schema.ts:140-146`）。改造后 `migrateV2` 自己写，建库分支照旧。**`seed()` 不动**（`store.ts:1340-1354`）—— 但它用 `setKv(SCHEMA_VERSION_KEY, SCHEMA_VERSION)` **无条件重盖**版本号，意味着**任何先 `createSchema` 再 `seed()` 的流程都会把版本号写成当前构建的版本**，即使结构没迁移。这是 §11-C1 的第二个来源。

### 步 8 — 存量 `nodes.disclosure` 的处置（契约 §3.1 回退规则 × 全部数据情形）

**总原则：迁移不改写任何 `disclosure` 值。** `nodes.disclosure` 原样保留（真库逐条不变，实测见 §10.1 的 `JSON.stringify` 全行快照比对：**125 行逐条相同、90 条非空值不变**）；两个新列一律 `NULL`。

**为什么新列一律 NULL 就是「行为逐位不变」**：D1 已定稿回退链为 `aliases.disclosure ?? nodes.disclosure`（`??` 语义，NULL = 继承节点级）。⇒ 迁移后 `effectiveDisclosure(任一新老别名) === 迁移前的 nodes.disclosure`。

### 步 9 — 幂等性（跑两遍结果一致）

三层保证，缺一不可：

1. **版本门**：`stored === SCHEMA_VERSION` 时 `needsMigration = false`，`migrateV2` 根本不进。实测第二遍 `migratedFrom === null` 且 `rebuild === false`、`node_fts` 行数不变（`probes-d3/verify.mjs` 门槛 3 段）。
2. **列存在性门**（`hasColumn`）：即使版本号被污染成 `"2"`（§11-C1），`ALTER` 也不会因 `duplicate column name` 崩。实测：纯版本号判据的迁移器在污染库上**直接抛错**；列判据版成功收口（`pollute.mjs`）。
3. **marker 清理由重算成功驱动**：重算幂等（`reindexNode` 先 `DELETE FROM node_fts WHERE node_id = ?` 再插，`store.ts:1422`），重复执行 marker 分支结果一致。

**漏了会怎样**：只靠版本号 → 一次 `import()` 就能造出「v3 结构 + v2 版本号」的库，下次开库抛 `duplicate column name`（**开库失败**，比今天还糟）。§11-C1。

### 步 10 — 回滚

**回滚 = 用备份文件替换现库**，不是「跑一个反向迁移」。

- **自动备份点在步 4**，覆盖所有需要迁移的情形。
- **不需要反向迁移代码**：v3 → v2 是减列（SQLite `DROP COLUMN` 需 ≥ 3.35，本机 3.53.4 支持），但把索引降回两列要再 `reindexAll` 一次，且**没有任何调用方会要求降级**（§12-Q3：不保持向后兼容）。加反向代码 = 加永不执行的死代码。
- **迁移失败时不需要回滚**：DDL 在事务内，失败即 `ROLLBACK`，库**自动回到 v2**（实测）。此时 `createSchema` 抛错，用户看到 §7 的文案。
- **文档要求**：错误文案与 CLI 输出 MUST 提到备份文件路径（步 4 生成），否则备份等于不存在。

**漏了会怎样**：迁移卡在「结构已改、版本号未写」的中间态且无备份 → 只能冷启动重建（今天的行为），而这正是本次要消灭的。

### §5.1 是否需要 audit 事件 → **明确不做**（有意决策，非疏漏）

`test/web/audit.test.ts:236-250` 强制：`AUDIT_EVENTS`（16 个冻结名，区间 **`:20-37`**，`:20` 起于 `const AUDIT_EVENTS = [`、`:37` 终于 `] as const;`）必须与**下列六个文件**中 `logAudit("<name>")` 字面量的集合**双向相等**（`:239` 的文件清单、`:249` 的断言）：`store.ts, tools.ts, module.ts, autoretain.ts, temp-notify.ts, slots.ts`。

- 门禁**扫不到**该文件 → 测试**照样绿**；

**D3 裁定：迁移器不写 audit 事件。** 理由：

1. **迁移不是「对记忆的操作」**，是「对库结构的升级」；`audit_log` 的语义（`docs/memory-system.md:191` 决策 23）是「记忆系统每次**对外动作**（写入/编辑/删除/召回/注入/autoretain）」。
2. 登记新事件名要**改冻结契约**（`00-共同上下文.md` §6.5 的 16 名清单）＋ 同步 `AUDIT_EVENTS` / `AUDIT_EVENT_LOOKUP` / `:239` 文件清单 / `audit.js` 的 `EVENT_CLASS` —— **四份清单**。收益不抵成本。
3. `schema.ts` 目前**不 import `MemoryStore`**，要在那里 `logAudit` 就得先构造一个 store（迁移器只有 `MemoryDatabase`），循环依赖风险。

**替代的留痕方式**（可诊断性不降级）：

- 迁移动作写入 `memory_kv`（`schema_version` 变更是天然记录）；备份文件名含 `pre-v2-<timestamp>`。
- **向 stderr 写一行**（§3 步 5 的 `process.stderr.write`）—— 这**不是** `logAudit`、不进 `audit_log`、不占冻结的 16 事件名，只是让 CLI/日志可见（`cli.ts:196-204` 的 stderr 风格是现成先例）。
- `SchemaOpenResult.backup`（§2.1）把备份路径**回报给调用方** —— §7.1 要求迁移失败消息带备份路径，无此字段则无法兑现。
- `agent-session` 侧见 §7.1。

> ⚠️ **`schema.ts` 里 MUST NOT 出现 `logAudit` 调用**，否则会落进「门禁看不见」的盲区（契约 §8 T5）。

### §5.2 审计流的既有内容不受影响

`audit_log` 是 append-only 且迁移不写它；`test/web/audit.test.ts` 的计数/顺序断言不受影响。

## §7 错误边界与降级

### §7.1 错误分档（这是本次必须补的）

| 情形 | 现状 | 迁移后 MUST |
|---|---|---|
| 全新/陌生文件 | 建库（`stored === null`） | 不变 |

| **迁移中途失败**（磁盘满/锁冲突/权限） | 不存在 | **抛出一个与「版本不兼容」可区分的错误** |

`packages/coding-agent/src/core/agent-session.ts:4310-4320` 把 `_setupMemoryModule` 的一切异常吞成：

```
error: `Memory module unavailable: ${message}`
```

⇒ **半迁移的库与「功能未配置」在用户视角完全一样。** D3 要求：

1. 迁移失败的错误消息 MUST 带**可区分的稳定词根**（建议 `migration failed`），使 `agent-session` 的这条消息能被人与日志立即分辨；
2. 该消息 MUST 带上备份文件路径（若已生成），否则用户不知道从哪恢复；
3. **MUST NOT** 在 `agent-session` 里新增分支（越界，且新增改动面）—— 只保证「消息可区分」这一条就够定位。

### §7.2 数据库被锁

迁移走 `db.transaction`（`BEGIN`，deferred）。若另一进程持写锁：`BEGIN` 成功、第一条写语句时撞 `SQLITE_BUSY` → 回滚 → 抛错。`openDatabase` 已设 `PRAGMA busy_timeout = 5000`（`driver.ts:53`），5 s 后放弃。

**MUST NOT** 把 `BEGIN` 换成 `BEGIN IMMEDIATE`：`driver.ts` 的 `transaction` 是所有写路径共用的（`store.ts` 全篇），改它超出本文范围（§12-Q5）。

### §7.3 只读探测绝不迁移

`probeMemoryDb`（`discovery.ts:133-205`）打开的是 `openDatabaseReadonly`（`driver.ts:89`），**任何写语句都会抛 `attempt to write a readonly database`**。迁移器 MUST NOT 被它调用。见 §11-C2。

### §7.4 marker 自愈的半失败降级

若 `reindexAll` 抛错（OOM/磁盘满），marker **不被清除**（代码顺序保证），`MemoryStore` 构造器抛错 → 开库失败。下次开库**重试**。⇒ **不产生「无 marker + 空 FTS」的永久静默态。**

```ts
// packages/memory/src/schema.ts
export function createSchema(db: MemoryDatabase): SchemaOpenResult {
    const stored = readSchemaVersion(db);                       // 既有，:150
    const needsMigration = stored !== null && stored !== SCHEMA_VERSION;
    if (needsMigration && !MIGRATABLE_FROM.includes(stored)) {  // MIGRATABLE_FROM = ["2"]
        throw new Error(/* 前缀逐字保留 */ "…incompatible with this build…");
    }
    let backup: SchemaOpenResult["backup"] = null;
    if (needsMigration) {
        const b = backupBeforeMigration(db, stored!);           // 事务外，VACUUM INTO
        backup = b;
        db.transaction(() => migrateV2(db));                    // driver.ts:57
        process.stderr.write(`[memory] migrated v${stored} → v${SCHEMA_VERSION}` +
            ("path" in b ? `; backup: ${b.path}` : `; backup skipped: ${b.skipped}`) + "\n");
    }
    for (const sql of STATEMENTS) db.exec(sql);                 // :139
    return { migratedFrom: needsMigration ? stored : null, ftsRebuildPending: needsMigration, backup };
}
```

任务明确要求。结论：**旧快照能导入，但必须与「版本号污染」一起处理**。

#### (a) 形状兼容 —— 旧快照（无 `disclosure` 键的 aliases/edges）能导入新版

实测（`probes-d3/import-probe.mjs`）：把快照里 `aliases[i].disclosure` / `edges[i].disclosure` 键**删掉**，再 `import()` 进新库 → **成功**，无抛错。原因是 D1 定稿的 `import()` 只需尾部追加 `disclosure?: string | null`，三态语义下 `undefined` = 保留现有值（新库该列为 NULL，结果就是 NULL）。

⇒ **旧快照（v2 时代 `export()` 的产物）可以导入 v3 库。** 但注意：

- 若 `import()` 仍用 `INSERT OR REPLACE INTO aliases (alias_uri, target_node_id)`（`store.ts:1307-1309`，**只列两列**），加列后 `OR REPLACE`（先删后插）会把该别名的 `disclosure` **静默重置为 NULL** —— 即使快照里带了值也白带。**这是 D1 §11-C7 同型的 runtime 缺陷，D3 MUST NOT 依赖 `OR REPLACE` 语义**（D1 已定：改 `ON CONFLICT ... DO UPDATE` 显式列 `disclosure`）。
- 同一缺陷也在 `store.ts:1316-1318`（edges 的 import 路径，`INSERT OR REPLACE INTO edges (node_id, target_uri, kind)`）与 `store.ts:756-761`（`addEdge`）。归属 D1，本文只登记。

#### (b) **版本号污染** —— 这是实测发现的真问题（T5 型静默失效）

实测（`probes-d3/{pollute,import-probe}.mjs`）：

```
v3 库 . import(v2 时代快照)          → kv.schema_version 变成 '2'
  ↳ 该库结构已是三列，但版本号自称 v2
  ↳ 下次 openMemoryStore：
      纯版本号判据的迁移器 → 抛 "duplicate column name: disclosure"（开库失败）
      列存在性判据的迁移器 → 正常收口
```

机制：`import()` 无条件把快照的整个 `kv` 表逐键 `setKv`（`store.ts:1298-1300`），而 `export()` 导出的是**整个 `memory_kv` 表**（`store.ts:1235-1237`），其中就含 `schema_version`。⇒ **一份旧快照能把新库的版本号改回旧值。**

**两条处置（D3 均要求）**：

1. **迁移器 MUST 用列存在性判据，MUST NOT 只用版本号**（步 3 已写死、§11-C1）。这样污染库能自愈而非崩。
2. **`import()` MUST NOT 把 `schema_version` 写回库**（D1 归属，本文登记）：kv 里的 `schema_version` 是**库自身结构**的属性，不是用户数据。建议 `import()` 对 `SCHEMA_VERSION_KEY` 做**白名单跳过**（或导入后无条件 `setKv(SCHEMA_VERSION_KEY, SCHEMA_VERSION)`）。**不修则**：任何一次「旧快照导入」都会把库打回「版本号与结构不符」的状态，依赖第 1 条兜底 —— 而第 1 条只是容错，不该常态化。
   > ⚠️ 该行为**今天就已存在**（`import()` 现在也会写回旧版本号），只是今天「版本号不匹配 = 拒绝启动」把它的后果表达成了明确报错。迁移落地后若不修，后果从「响亮的拒绝」退化成「静默容错」—— 正好是契约 §8 T5 的方向。**D1 请在本轮一并修。**

#### (c) 快照里的既有 `disclosure` 值

`ExportSnapshot.nodes` 是 `MemoryNode[]`（`store.ts:96`），自带 `disclosure` 字段，**今天就能导出导入**，与本次改动无关。新增的 `aliases` / `edges` 的 `disclosure` 字段（D1 §9 第 8 行）按同规则工作。

### §9.2 向后兼容：**旧版 pi-rp 不能读 v3 库 —— 默认裁定「不保持」（U5）**

**结论：不保持。** 理由逐条：

1. **仓库纪律**（契约 §11-U5 默认）：不做 backward compat 除非用户要求。用户裁定的原始诉求是「恢复 nocturne 的边级 disclosure」，**没有**要求旧二进制继续可读新库。
2. **技术上是「响亮失败」，不是静默破坏**：旧版 `createSchema`（`schema.ts:133-138`）看到 `stored = "3"` 会抛 `memory database schema v3 is incompatible with this build (v2)` 并拒绝启动。**明确报错，无数据损坏** —— 这是可接受的失败形态。
3. **真要做也不需要改代码**：旧库的 `nodes` / `aliases` / `edges` 数据**完全原样**在 v3 库里（§3 步 8，实测逐字段相同）。用户想回退，把 §3 步 4 的备份文件拿回来、或用 `export()`/`import()` 走一遍即可（§9.1 已证明跨版本快照可导入）。
4. **保持兼容的成本**：要让旧版读 v3，要么让旧版容忍未知列（它是 `SELECT *` + 显式列名读 —— `store.ts:112-132` 的 `NodeRow` 逐列读取，**多出的列不会被读**，但 `node_fts` 的两列 `INSERT`（`store.ts:1435`）会往三列表里插两列，实测**成功且 `disclosure` 为 NULL** —— 所以旧版其实「几乎」能读 v3 库！），要么改旧版代码。**但这属于「让历史版本学会未来」**，代码永远无法预期未来。
   > 附实测（SQLite 语义探针；等价断言已并入归档的 `probes-d3/nulltest.mjs`）：三列 FTS 表 `INSERT INTO node_fts (node_id, text) VALUES (?,?)` **成功**，`disclosure` 落 NULL；`bm25(node_fts)` 不带权重也能跑。⇒ **[推断]** 旧版对 v3 库的实际失败点**只是 `createSchema` 的版本号守卫**，不是 schema 形状本身。这加强了「不保持」的判断：真需要时把守卫放宽即可，无需任何数据转换。
5. **谁受影响**：本机唯一的 v2 生产者是本仓自身。真实用户的库（elias 等）都是**被动消费**的，不存在「用户自己编译的旧版 pi-rp」这一说（若有，那是 vendored 副本，如 `hackathon/vendor/pi-rp/`）。

**因此本设计不做**：不写「旧版兼容读 v3」的代码，不加双版本分支，不加降级开关。**唯一要做的**是把这条裁定写进文档（**回写 `docs/memory-system.md:13` 等四处历史政策**，见 §11-C4）。

### §9.3 与 `relocate` 的交叉（任务明确要求「两者都要」之一）

用户裁定的「迁移」包含两件事：存量库 schema 迁移（本文主体）+ `relocate` 与 disclosure 的关系。**后者语义归 D1**（`21-数据模型与语义核心.md` §3 / §11-C8/C9 已定稿），D3 的职责只有一条：

> **迁移器不为存量 alias 补 `aliases.disclosure`。** 存量 alias 一律留 NULL（步 8 情形 4）。`relocate` 的新写入路径（`store.ts:676-679`）由 D1 改用 `ON CONFLICT ... DO UPDATE` 并显式写 `disclosure`（= 移动前的 `effectiveDisclosure(旧uri)`），**只对新 relocate 生效**。

**为什么迁移不补**：补了就等于「编造一个用户从未表达过的入口条件」，且会**破坏**「存量留 NULL = 行为逐位不变」这条地基（D1 与主 agent 均已确认；主 agent 广播原话：「这正是你要的『逐位不变』」）。NULL 在 `??` 语义下天然等价于继承节点级 ⇒ 不补即等价。

> ⚠️ 迁移器也 **MUST NOT** 把 `store.ts:677-679` 的 `INSERT OR REPLACE ... (alias_uri, target_node_id)` 当成模板抄 —— 详见 §9.1(a)，那是 runtime 缺陷且归 D1。

```
PASS  FTS 行数两遍相等  — 5 / 5
PASS  第三遍后 nodes 逐行不变
PASS  版本号污染（结构已 v3）下迁移器不崩
```

**三层保证**见 §3 步 9。第 5 条 PASS 就是**列存在性判据**的价值：版本号被人为改回 `"2"`（结构已是三列）时，纯版本号判据的迁移器会抛 `duplicate column name`（见 `probes-d3/pollute.mjs` 的对照输出），列判据版正常收口。

### §10.4 回滚（契约 §7 门槛 4）

### C1 ⚠️ **幂等性判据 MUST 是「列存在性」，不是「版本号」**（实测反例，本次最重要的发现）

**反例链**（全部实测）：

### C10 ⚠️ **备份文件名只靠秒级时间戳会撞名**（实测发现，非理论担忧）

**发现经过**：我在归档 `probes-d3/verify.mjs` 后连跑它，**第 4 次失败**（flaky）。定位到：

```
FAIL  备份已生成  — output file already exists
```

机制：`stamp` 来自 `toISOString()` 且被裁到**秒**（跟本仓既有的 `memory.db.pre-elias-migration-20260914` 命名习惯一致）。同一秒内的第二次迁移生成的备份路径与第一次**完全相同**，而 `VACUUM INTO` 对已存在的目标**直接抛错**（实测：`VACUUM INTO existing -> output file already exists`）。

**为什么这不只是测试脚本的问题**：
- 生产路径上「同一秒两次迁移」可达：`openMemoryStore` 有 **5 个生产调用点**（主 agent 独立复核，我复跑 `grep -rn "openMemoryStore(" packages --include=*.ts | grep -v dist` 确认：排除测试与注释后**恰好 5 处**）——`agent-session.ts:231`、`extensions/memories/index.ts:36`、`web/cli.ts:197`、`web/registry.ts:384`、`web/routes.ts:1187`。前两个在同一进程内是**各自独立的开库入口**（各自的 Map），后三个在 web 侧（含子进程）—— 多入口并发首次打开同一个 v2 库时，迁移可能在同一秒内被触发多次。
- 此时**第二次的备份失败**。按本文 §3 步 4 的裁定「备份失败**不阻断**迁移」，后果是：**迁移照常进行，但这次没有任何备份** —— 而用户以为有。这正是本批次反复出现的「静默失效」形态。

**处置（已写入 §3 步 4 的伪码）**：备份路径 MUST 在撞名时加序号后缀（`…-2.bak`、`…-3.bak`）。**不引入随机数/临时文件规避**：备份是**用户要能一眼找到并手动恢复**的产物，可预测的命名优先。

**核验**：`probes-d3/verify.mjs` 加后缀后连跑 6 次 → `0 0 0 0 0 0`（全绿）；加之前是 3 连跑 1 败。
> ⚠️ **表述更正（主 agent 复核指出，我采纳）**：这不是「约 25% 概率」的随机抖动，而是**确定性缺陷**——**同秒即挂**（`stamp` 只到秒，同秒生成同名路径，`VACUUM INTO` 必拒）。它看起来像概率问题，只是因为**触发它需要「连跑跨秒」这个巧合**。这个区分重要：随机抖动可以「多跑几次碰运气」，确定性缺陷则**必然在某些调用序列下发生**——生产里多入口并发首开正是那种序列。

> 附带教训（与本批次门槛 10 同源）：**「脚本能跑通一次」不等于「可复跑」**。我把 17 个归档脚本各连跑两遍做体检，发现 **3 个不可复跑**（`verify`/`probe7`/`timing3` 都因「上一轮产物未清理」或「撞名」而失败）—— 而它们正是复核者要拿去复跑的证据。**归档脚本 MUST 自清理、可任意次数重跑。**
