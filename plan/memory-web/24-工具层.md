## §3 行为契约逐步（每步写「漏了会怎样」）

### §3.1 `memorize({uri, when})` → `nodes.disclosure`

1. `executeMemorize`（`tools.ts:452`）先 `resolveUri(uri)`；若命中非 stub 节点 → 报错「URI 已存在」（`:456-458`）。
2. 其余情况（全新节点，或 stub 原地转正）经 `store.put({..., disclosure: <归一后的 when>, ...})`（`:463`）。
   - **`when` 三态归一（与 `revise`/E7 同一纪律；D1 `21` §3-M1 步骤 2 定稿）**：
     ```ts
     store.put({ …, disclosure: params.when === "" ? null : params.when });
     //  注：新建节点场景下 undefined 与 null 等价（无条件），故只需特判 ""。
     ```
   - ⚠️ **MUST NOT 写 `params.when ?? null`**（评审 P1-1）：`""` 非 nullish ⇒ 该式求值为 **`""`**，会把字面空串写进 `nodes.disclosure` ⇒ 该节点**永久不再继承节点级**（`??` 回退被空串切断），且前端 `discBadge("")` 返回 null ⇒ **用户无法识别**（静默失效）。
3. 语义：新建节点没有「入口」，它的 uri 就是**规范入口**，条件属于 `nodes.disclosure`（契约 §3.1 裁定 1）。

> **漏了会怎样**：若把 `memorize` 的 `when` 也改成写别名/边，就无处可写（新建节点尚无别名、无边），要么抛错要么静默丢弃。

### §3.2 `associate({new_uri, when})` → `aliases.disclosure`（**修 §2.9 bug**）

**修前**（`tools.ts:767-789` 逐行复核，**函数体内零次 `params.when`**）：
- 别名模式：`store.addAlias(params.new_uri, node.node_id)`（`:787`）——`when` 被丢弃，磁盘无任何变化、无报错。
- 边模式：`store.addEdge(node.node_id, related.uri, params.kind)`（`:780`）——`when` 同样被丢弃。

**修后**（D1 `21` §3-M2/M3 定稿；**`""` 归一为 `null`**，其余原样传）：
1. 前置校验不变（`target_uri` 存在 `:768-769`；两者互斥 `:770-774`；边模式自关联拒绝 `:778`；别名模式目标未占用 `:786`）。
2. 统一归一：`const when = params.when === "" ? null : params.when;`
3. 边模式：`store.addEdge(node.node_id, related.uri, params.kind, when)`。
4. 别名模式：`store.addAlias(params.new_uri as string, node.node_id, when)`。
5. 结果文案回显写入的 `when`（§6.2）：无 `when` 时保持现状文案。

> ⚠️ **MUST NOT 写 `params.when ?? null`**（D1 明确）：`undefined`=保留现有值 / `null`=清除；`?? null` 会把「调用方省略」变成「清除」（§7 E2）。

> **漏了会怎样（修前的真实症状）**：模型调用 `associate({new_uri:"自己", when:"当被叫名字"})`，用户以为入口条件已设，前端 `effectiveDisclosure("自己")` 却返回 `nodes.disclosure`——**静默的数据丢失**，正是契约 §8 T5 那类。

### §3.3 `associate({related_uri, when})` → `edges.disclosure`

1. 边是**方向性**的：`node_id = target_uri 解析出的节点`，`target_uri = related.uri`（`:780` 现状）。`when` 属于这条**边**，不传给节点。
2. `edges.disclosure` **不进** `effectiveDisclosure` 回退链（契约 §3.1 冻结）。它只在 `retrieve` 沿边一跳扩散时作为该跳的说明展示（读取者裁定归 D1，契约 §3.1 边界情形）。
3. 文档/注释口径 MUST NOT 说成「恢复 nocturne 语义」——`edges`（联想边）是 pi-rp 独有的扩展（契约 §3.1 裁定 3）。

> **漏了会怎样**：若把边模式的 `when` 写进 `nodes.disclosure`，会**污染节点自身**的入口条件——同一节点被其它入口引用时全部被改。

### §3.4 `revise({when})` → `setEntryDisclosure`（**主 agent 裁定 ③：写路径镜像 `resolveUri`**）

**最终裁定（取代本文件早先的「别名优先」写法）**：`revise(uri=X, when=Y)` 写 **X 命中 `nodes.uri` 的那一层**——与读路径同优先级（一致性原理：**写路径与读路径 MUST 同一优先级**）。
- X 命中 `nodes.uri`（规范） → 写 **`nodes.disclosure`**
- 否则 X 是别名 → 写 **`aliases.disclosure`**（`aliases.disclosure = null` 表示继承节点级，`??` 语义）

**统一走 D1 的唯一写入口**（D1 `21` §3 M4，不自行判定）。**写法以 §8.2 为准**：

```ts
// ✅ 正确：三态用守卫，undefined 分支完全不调用（与 §8.2 同一条代码）
if (mod.when !== undefined) {
    store.setEntryDisclosure(mod.uri, mod.when === "" ? null : mod.when);
}
//  内部即镜像 resolveUri：byUri 命中 → _updateNode(disclosure)；否则 aliasEntryStmt → setAliasDisclosure
//  返回 { layer: "alias" | "node", node_id }
```

> 🚫 **MUST NOT 用单个三元表达式统一三态**（评审 R5 实测的静默数据丢失）：
> ```ts
> // ❌ 错：mod.when === undefined 时也求值成 null ⇒ 每次「只改正文/只改重要性」的 revise
> //        都会 setEntryDisclosure(uri, null) = 清除该入口条件（用户没要求改，却被清空）
> store.setEntryDisclosure(mod.uri, mod.when === "" ? null : (mod.when ?? null));
> ```
> **形态根因**：`undefined` 必须走「**不调用**」分支，三元表达式做不到「不调用」——它只能产出一个值。故 `undefined` 分支 MUST 是 `if` 守卫，不是表达式的分支。
>
> ⚠️ **`when` 三态（D4 归一，D1 `21` §11-C1 第 5 条）**：`undefined` → **不调用** `setEntryDisclosure`（不改）；`""` → `setEntryDisclosure(uri, null)`（**清除**，与 `revise` 的 `time: ""` 惯例对齐 `tools.ts:485,556`）；其它 string → 原样写入。
> ⚠️ **行为变更**：现状 `revise(when: "")` 会写入字面空串（`store.ts:353-356` 无空串特判）。改后 `""` = 清除。登记 §9.1。

**为什么不是「别名优先」**：早先版本按 `isAliasEntry`（直接查 `aliases` 表）分流，会让『死别名』（`alias_uri` 同时是 `nodes.uri`）**写别名层而读节点层**——写读分裂（§7 E9）。裁定 ③ 消除了这个分裂。

**内容/时间/重要性编辑照旧**：仍走 `store.updateNode(node.node_id, {...})`（`tools.ts:559`）——别名与规范节点共享 `node_id`。

> **漏了会怎样**：若沿用现状 `store.updateNode(node.node_id, {disclosure})`（`tools.ts:559-566`），则**从别名 revise 永远改不到入口条件**，别名层成为只写不读的死数据（D1 `21` §3 M4 同结论）。

### §3.5 `consolidate({when})` → 新主题节点的 `nodes.disclosure`（**不需改**）

`executeConsolidate`（`tools.ts:826`）四条 resolution 路径中 `when` 的现状落点（已复核）——**三处都是 `disclosure: params.when ?? null`**：

| resolution | 落点 | 行 |
|---|---|---|
| `merge` | `store.put({... disclosure: params.when ?? null ...})` | `:842` |
| `group` | `store.consolidateGroup({... disclosure: params.when ?? null ...})` | `:895` |
| `link` / `keep` | `store.put({... disclosure: params.when ?? null ...})` | `:910` |

⚠️ **P1-1 同类残留（D4 全文档扫描发现，非上一轮点名）**：这三处的 `params.when ?? null` 与 `memorize` 的 bug **同型**——`when: ""` 非 nullish ⇒ 写入字面空串。**MUST 一并归一**：
```ts
// 三处统一（与 memorize/revise 同纪律；D1 `21` §7.5「工具层归一」）
const disc = params.when === "" ? null : params.when;   // undefined 保持 undefined → put 视为无条件
```
> 注：`consolidate` 建的是**新主题节点**，没有「节点级回退」可被切断；但空串仍会（a）让未来挂在它下面的别名 `aliases.disclosure ?? nodes.disclosure` 落回 `""`，（b）令 `discBadge("")` 返回 null ⇒ **用户看不见**。**归一理由与 P1-1 相同**。
> **D1 `21` 的 T-4b 未列 `consolidate`**（其清单是 memorize/revise/associate 两模式/route）——这是 D1 覆盖面的一个缺口，D4 在此登记（§11 C11）。

语义 = **新建主题节点自身的想起条件**（规范入口），与契约 §3.1 裁定 1 一致 ⇒ 除上述归一外**不改**。

> ⚠️ **`link` 路径的死别名 —— D1 裁定归 D4，MUST 修**（D1 `21` 文档 §11-C8 第 2 条）：
> `tools.ts:918` 的 `store.addAlias(src.uri, theme.node_id)` **在 `src.uri` 仍是 `nodes` 存活行时建别名** ⇒ `resolveUri`（`store.ts:181-189`，nodes 优先）永远命中节点，**别名不可达**。`link` 的工具描述（`tools.ts:817`）承诺「保留原位」，而该意图在当前数据模型下**不可表示**（只要 `nodes.uri` 占着这个字符串）。这是 §8 T1 的教训：「加了别名」≠「入口生效」。
>
> **修法（D1 给定论，D4 落）**——只在别名真正可达时才建：
> ```ts
> if (resolution === "link") {
>     if (!store.resolveUri(src.uri)) {
>         store.addAlias(src.uri, theme.node_id);
>     }
>     // 若 src.uri 仍存活：不建别名（本就不可达），并返回可见提示（§7 E10）

> ```
> **反方证据已被 D1 评估并否决**：若 `src` 日后被删，该别名会「复活」为可达——但无任何文档承诺此行为，且 `deleteCascade`（`store.ts:566-569`）只清 `aliases WHERE target_node_id = nodeId`，**不会**清这条（其 target 是 theme）⇒「复活」纯属意外。**不作保留理由。**
>
> 存量死别名**不静默删**（归 D3 探针 + 主 agent 拍板，D1 `21` §12-Q1）。

### §3.6 `autoretain`（`src/autoretain.ts`）的 disclosure —— **改任务书里的一个误名**

**任务书问「`autoretain` 的 `remember` 也带 disclosure，怎么处理？」**：复核后**不存在 `remember` 函数**（全仓 grep 无命中）。真实落点：

- `runAutoretainTask`（`autoretain.ts:193`）→ `store.put({..., disclosure: parsed.disclosure ?? null, ...})`（`:227`）。
- 契约 §2.4 的「`remember`（autoretain 用）描述含「<想起条件，可省略>」」指的是 **JSON 契约字符串**：`AUTORETAIN_JSON_CONTRACT`（`autoretain.ts:67-68`）的字面文本 `"disclosure": "<想起条件，可省略>"`，以及 `parseAutoretainJson` 的返回字段 `disclosure`（`:109-133`）。

**处理**：**不改**。理由：
1. 产物是**新建节点**（`landingUri` 决定的新 uri，`autoretain.ts:213`），无入口 ⇒ `nodes.disclosure` 正确。
2. JSON 契约字段名是 `disclosure`（不是工具参数 `when`），不受「工具参数名冻结」约束；改它要同步 `AUTORETAIN_JSON_CONTRACT` + `parseAutoretainJson` + 默认任务 prompt，**收益为零**（它是机器对机器的契约，不是外部可见 API）。

> ⚠️ **既有行为观察（登记，不修）**：`parsed.disclosure ?? null` 在模型省略 disclosure 时传 **`null`**。若 landing 落在**已存在**节点（`replaceStale` / `underParent` 命中既有 uri），`_put` 会转 `_updateNode`，而 `applyPatchColumns`（`store.ts:353-356`）把 `null` 视为**显式清除** ⇒ **重新生成会静默抹掉该节点原有的 disclosure**。这是既有的 `?? null` 语义，与本次改动无关；但 D1 若定「undefined = 保留」的 upsert 纪律，此处是应当对齐的候选点。见 §11 C4。

### §3.7 `relocate` 暴露 `when`（**D1 已定稿：暴露**）

主 agent 2026-09-16 传达 D1 定稿：`relocateMany` 新增可选 `when` 覆盖；不传则继承「移动前 `effectiveDisclosure(旧uri)`」。⇒ D4 在 `relocate` 工具加**可选 `when` 参数**。

1. `relocateParams`（`tools.ts:718-728`）加 `when: Type.Optional(Type.String(...))`。
2. `executeRelocate`（`tools.ts:730`）把 `params.when` 透传进 moves：`moves: Array<{from, to, when?: string | null}>`（D1 `21` §8.2 `:383`）。
3. 语义（契约 §3.5 + D1 `21` §3-M5）：显式 `when` → 用它；缺省 → 别名继承**移动前**的生效条件（`prior = effectiveDisclosure(member.node.uri)` 于 UPDATE 之前取）。

> ⚠️ **与 `when` 三态的一致性**：沿用 `revise` 的归一——`""` → `null`（清除，不继承）；`undefined` → 走继承。**这是 `relocate` 与 `revise` 的语义差别**：`revise` 的 `undefined` = 不改；`relocate` 的 `undefined` = 继承 prior（D1 `21` §11-C1 第 3 条：prior 取不到 = `null`，**不得**跳过别名插入）。

> **漏了会怎样**：D1 `21` §3-M5 已指出——若不显式写 `disclosure` 列，`_relocateMany` 的 `INSERT OR REPLACE`（`store.ts:677-679`）会把已有别名的 disclosure **静默重置为 NULL**（契约 §8 T5 类）。
