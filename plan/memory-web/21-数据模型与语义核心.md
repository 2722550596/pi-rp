## §2 签名与参数（精确）

### §2.1 新增（`NEW`）

```ts
// packages/memory/src/store.ts — MemoryStore 方法，落点见 §8.1
/** NEW. 生效想起条件：全仓唯一入口。纯 SELECT，无副作用，不抛错。 */
effectiveDisclosure(uri: string): string | null;

/**
 * NEW. 「这个 uri 代表哪个入口、指向哪个节点」——**读写两条路径的共同地基**（M4b）。
 * 优先级：`nodes.uri` 命中 → kind:"canonical"；否则 `aliases.alias_uri` → kind:"alias"；都不命中 → null。
 * `aliasDisclosure` 仅在 kind === "alias" 时有意义（该别名自己写的条件；NULL 表示「继承节点级」）。
 * 定稿形态**一次查两表**，故 `effectiveDisclosure` / `setEntryDisclosure` 都只需 1–2 次 SQL。
 * ⚠️ 死别名（`alias_uri` 撞存活 `nodes.uri`）下返回 `kind:"canonical"`——见 M4b。
 */
resolveEntry(uri: string): {
    kind: "canonical" | "alias";
    node_id: string;
    alias_uri: string | null;
    aliasDisclosure: string | null;
} | null;

/** NEW. 唯一写入口：按「结构层」把 when 写到该 uri 代表的那一层。写路径，记审计。 */
setEntryDisclosure(uri: string, disclosure: string | null): { layer: "alias" | "node"; node_id: string };

/** NEW. 别名的 per-entry 写入（`setEntryDisclosure` 的别名专用内核）。 */
setAliasDisclosure(aliasUri: string, disclosure: string | null): void;

/**
 * NEW. 该 uri 在 `aliases` 表里**是否有行**（含被 `nodes.uri` 遮蔽的死别名——见 M4b）。
 * `EXISTS(SELECT 1 FROM aliases WHERE alias_uri = ?)`，1 条 SQL，纯 SELECT、不抛错。
 * **与 `resolveEntry` 正交**：后者回答「这个 uri 解析成谁」，本函数回答「aliases 表里有没有这行」。

/** NEW. 一个节点的全部别名入口 + 每个入口的**生效**条件（1 条 SQL）。 */
listAliasEntries(targetNodeId: string): Array<{
    alias_uri: string;
    target_node_id: string;

     * ⚠️ 但 `dead === true` 时该值 **不来自** `aliases.disclosure` —— 见 `dead` 字段。

    /**
     * NEW（2026-09-16，主 agent 批准 + 本文 §11-C8）：该别名是「死别名」——
     * 谓词 `EXISTS(SELECT 1 FROM nodes WHERE uri = alias_uri)`，即 `resolveUri(alias_uri)`
```

**`disclosure` 参数的三态语义（冻结，三处一致）**：

| 传入 | 行为 |
|---|---|
| `undefined` | **保留现有值**（不清除）。这是「只改 kind / 只改 target」的常规路径。 |
| `null` | **清除**（写 NULL）。 |
| `string`（含 `""`） | 写入该串；`""` 由工具层归一为 `null`（见 §3.2）。 |

⚠️ **MUST NOT 用 `INSERT OR REPLACE` 实现 upsert**——它先删后插，未列出的列会被重置为默认值（`NULL`），这正是契约 §3.5 登记的静默丢失。已实测本机 SQLite（`3.53.4`）支持 `ON CONFLICT ... DO UPDATE`：

```text
# 实测（node:sqlite，2026-09-16）
INSERT OR REPLACE INTO aliases (alias_uri,target_node_id) VALUES ('a','n2')   → disclosure 由 'D1' 变 null   ← 静默丢失
INSERT INTO aliases ... ON CONFLICT(alias_uri) DO UPDATE SET target_node_id=excluded.target_node_id
                                                                              → disclosure 保持 'D1'          ← 正确
```

## §3 行为契约逐步

> 每个模式写「漏了会怎样」。模式编号 M1–M8 对应契约 §3.3/§3.4/§3.5 与用户要求的落点。

### M1 `memorize({uri, when})` → `nodes.disclosure`

1. `executeMemorize`（`tools.ts:452-472`）已 `existing && !existing.is_stub` 早退（`:456`），故只对「新建 / stub 转正」写入。
2. 写 `store.put({…, disclosure: params.when === "" ? null : params.when})`（`:463`）——⚠️ **两点 MUST**：① **`""` 归一为 `null`**（§7.5 全局规则，与 `revise` 的 `time: ""` 对齐）——**MUST NOT 把 `""` 写进 `nodes.disclosure`**：`effectiveDisclosure` 的 `??` 会把它当**非 null**（有值但空）⇒ 该节点**永久不再继承节点级条件**，且前端 `discBadge("")` 返回 null ⇒ **用户无法识别**（RevHonesty P1-1 点名的静默失效）；② 其余**原样传**（`string` 或 `undefined`），`undefined` = 不改（`_put` 对既有节点透传，`store.ts:262-272`）。
3. **不变**。规范入口的想起条件就是 `nodes.disclosure`（契约 §3.1 裁定 1）。

**漏了会怎样**：若 `""` 不归一，写入字面空串 ⇒ 该入口条件**永不继承节点级**（`??` 被空串截断）且 UI 无法显示 ⇒ **静默失效**（RevHonesty P1-1）。

### M2 `associate({target_uri, new_uri, when})` → `aliases.disclosure`

1. `tools.ts:786` 的 `store.resolveUri(new_uri)` 判重保持。
2. 调用点改为 `store.addAlias(new_uri, node.node_id, params.when === "" ? null : params.when)`（签名见 §2.2）——⚠️ **两点 MUST**：① **`""` 归一为 `null`**（§7.5 全局规则，全入口一致）；② 其余**原样传**（`string` 或 `undefined`）——`undefined`=保留现有值、`null`=清除；**MUST NOT 写 `?? null`**（会把「省略」变成「清除」＝静默数据丢失，§11-C7b）。
3. `addAlias` 内部：
   - `disclosure === undefined` → `ON CONFLICT(alias_uri) DO UPDATE SET target_node_id=excluded.target_node_id`（**不碰 disclosure**）。
   - 否则 `… DO UPDATE SET target_node_id=excluded.target_node_id, disclosure=excluded.disclosure`。
4. 记审计（§5）。

**漏了会怎样**：契约 §2.9 的既有 bug ——`when` 被静默丢弃（`executeAssociate` `tools.ts:767-789` 从不读 `params.when`），用户传了参数磁盘无变化且无报错。**D4 修**，D1 提供承载签名。

### M3 `associate({target_uri, related_uri, when})` → `edges.disclosure`

1. 调用点改为 `store.addEdge(node.node_id, related.uri, params.kind, params.when === "" ? null : params.when)`（`tools.ts:780`）——⚠️ 同 M2：**`""` 归一 `null`，其余原样传**，MUST NOT 用 `?? null`。
2. `addEdge` 用 `ON CONFLICT(node_id, target_uri) DO UPDATE SET kind=excluded.kind [, disclosure=excluded.disclosure]`（PK 是 `(node_id,target_uri)`，`schema.ts:49`）。
3. **`edges.disclosure` 不进生效回退链**（契约 §3.1）——它是「沿这条联想边扩散时的条件」，不是「解析某个 uri 得到的入口条件」。

**漏了会怎样**：`edges.disclosure` 永远无法写入；且若沿用 `INSERT OR REPLACE`（`store.ts:757-759`），重复 `associate` 同一条边（kind 覆盖，`:779` 注释明示幂等）会把已有 disclosure 静默清空。

### M4 `revise({uri, when})` → **结构层**（契约 §3.4，D1 裁定）

**裁定**：`revise(uri=X, when=Y)` 写入 **X 结构上表示的那一层**——由 `resolveEntry(X)` 判定（§M4b），**与之同优先级**：
- `resolveEntry(X).kind === "canonical"`（X 是规范 `nodes.uri`）→ `nodes.disclosure`
- `kind === "alias"`（X 是别名入口）→ `aliases.disclosure`
- `null`（X 不存在）→ 抛错

**MUST NOT 写「回退链命中的那一层」。** 理由（D1 提出、主 agent 采纳并已并入契约 §3.4）：

> 回退链是 `aliases.disclosure ?? nodes.disclosure`。若按「命中层」写，则当某别名的 `aliases.disclosure` 为 NULL（= 继承节点级）时，从该别名 `revise` 会**命中 `nodes.disclosure` 并覆盖它** —— 而 `nodes.disclosure` 是**规范入口与所有其它别名共享**的值。这是**跨入口副作用**：改一个别名的条件，静默改掉整个节点及其余入口的条件。
> 结构层写入则把副作用限制在「用户从哪进来就改哪」的范围内。

**回退链只用于读，不用于写。**

**实现（唯一写入口 `setEntryDisclosure`，建立在 `resolveEntry` 之上）**：

```ts
setEntryDisclosure(uri: string, disclosure: string | null): { layer: "alias" | "node"; node_id: string } {
    const entry = this.resolveEntry(uri);
    if (!entry) throw new Error(`setEntryDisclosure: unknown uri ${uri}`);
    if (entry.kind === "canonical") {
        this._updateNode(entry.node_id, { disclosure });   // 走既有补丁路径（含 reindex）
        return { layer: "node", node_id: entry.node_id };
    }
    this.setAliasDisclosure(uri, disclosure);
    return { layer: "alias", node_id: entry.node_id };
}
```

### M4b `resolveEntry(uri)` 的行为契约（NEW，读写两条路径的**共同地基**）

**唯一职责**：回答「这个 uri 代表哪个入口、指向哪个节点」——**读（`effectiveDisclosure`）与写（`setEntryDisclosure`）MUST 都由它派生**，从而**强制两者同优先级**（这正是评审 T-7 发现矛盾的根因）。

```ts
resolveEntry(uri: string): { kind: "canonical" | "alias"; node_id: string; alias_uri: string | null; aliasDisclosure: string | null } | null {
    const node = this.byUriStmt.get(uri) as NodeRow | undefined;
    if (node) return { kind: "canonical", node_id: node.node_id, alias_uri: null, aliasDisclosure: null };   // ① nodes.uri 优先
    const alias = this.aliasEntryStmt.get(uri) as { target_node_id: string; disclosure: string | null } | undefined;
    if (!alias) return null;                                                                                  // ② 都不命中 → null
    return { kind: "alias", node_id: alias.target_node_id, alias_uri: uri, aliasDisclosure: alias.disclosure };  // ③ 别名入口
}
```

⚠️ **关键推论（D4 核出）**：`resolveEntry` 的规范分支硬编码 `alias_uri: null` ⇒ **死别名下 `resolveEntry(X).alias_uri === null`**，且 `kind === "canonical"`。因此 **`alias_uri !== null` 不能当「有别名行」的判据**。
**「被遮蔽（死别名）」的精确判据（冻结）**：
```ts
const shadowed = store.hasAliasRow(uri) && store.resolveEntry(uri)?.kind === "canonical";
```
**MUST NOT** 用 `resolveUri(uri) !== null` 代替——**普通别名也非 null**（它解析到目标节点），会**假阳性**。
**三个判据用途不同，MUST NOT 混用**：①「有没有别名行」= `hasAliasRow(uri)`（§2.1）；②「是否走别名解析」= `resolveEntry(uri)?.kind === "alias"`；③「该 uri 是否被遮蔽」= 上面那条 `hasAliasRow && kind === "canonical"`。

**优先级语义（冻结）**：**`nodes.uri` 命中即 `kind:"canonical"`**（镜像 `resolveUri:181-189`）——与 `effectiveDisclosure`（§3 M8）**完全同源**。
**死别名下 `kind` 取什么（主 agent 明确要求）**：**取 `"canonical"`**。被遮蔽的别名行虽在 `aliases` 表里，但 `resolveEntry(该 uri)` 返回撞名节点的 `kind:"canonical"` ⇒ **读返回节点条件、写落 `nodes.disclosure`——一致，且都不触碰那条永不生效的别名行**。

**与 `effectiveDisclosure` 的关系（MUST 保持的等价）**：
- `kind:"canonical"` → `effectiveDisclosure(uri) === nodes.disclosure`
- `kind:"alias"` → `effectiveDisclosure(uri) === aliases.disclosure ?? nodes.disclosure`（通过 `node_id` 取目标节点）
- `null` → `effectiveDisclosure(uri) === null`

> `effectiveDisclosure` 的内部实现**MAY**直接内联这两个查询（避免多一层调用），但**其行为 MUST 与 `resolveEntry` 的分支完全一致**；建议实现为 `effectiveDisclosure` 调用 `resolveEntry` 后按 `kind` 取列（一次 `resolveEntry` + 最多一次取列），牺牲极小性能换取**语义不可能漂移**。

**漏了会怎样**：读/写优先级分叉 ⇒ 同一 uri 的 `effectiveDisclosure(X)` 与 `setEntryDisclosure(X)` 作用于不同对象（T-7 型静默错乱）。

**全部情形逐个给行为**（契约 §3.1 边界情形）：

| 情形 | `effectiveDisclosure(X)`（读） | `revise(X, when)`（写） |
|---|---|---|
| X 是规范 uri，无别名 | `nodes.disclosure` | `nodes.disclosure` |
| X 是规范 uri，且另有别名 Y 指向它 | `nodes.disclosure` | `nodes.disclosure`（仅影响规范入口） |
| X 是别名（Y），Y 的 disclosure 非空 | `aliases.disclosure` | `aliases.disclosure` |
| X 是别名（Y），Y 的 disclosure 为 NULL | `nodes.disclosure`（继承） | `aliases.disclosure`（**写结构层 = 给 Y 一个自己的值**） |
| X 同时是 `nodes.uri` 又是某 `aliases.alias_uri` | `nodes.disclosure`（规范优先，镜像 `resolveUri`） | `nodes.disclosure` |
| X 是联想边的 target（但既非规范 uri 也非别名） | `null` | 抛错 `unknown uri` |
| X 不存在 | `null` | 抛错 `unknown uri` |

> ⚠️ 第 5 行（`nodes.uri` 与 `aliases.alias_uri` 撞名 = 死别名，§11-C8）**依赖不变量 `aliases.alias_uri ∉ nodes.uri` 才无分歧**。工具层有守卫（`tools.ts:786` `associate` 拒绝已存在的 `new_uri`；`relocate` 的 target-occupancy 检查 `store.ts:647-655`），但 `store.addAlias` 本身无守卫。**撞名时以第 5 行为准（规范优先，读写一致）**——本文 §11-C8 已按主 agent 裁定修正，并建议 `addAlias` 加守卫（(b) 方案）。

**`when` 三态（工具层归一，D4 执行）**：`undefined` → 不调用 `setEntryDisclosure`（不改）；`""` → `setEntryDisclosure(uri, null)`（清除，与 `revise` 的 `time: ""` 语义对齐，`tools.ts:485,556`）；其它 string → 写入。

**漏了会怎样**：若按「命中层」写，出现 §11-C2 的跨入口副作用；若直接沿用 `store.updateNode(node.node_id, {disclosure})`（现状 `tools.ts:559-566`；`web/routes.ts:684`），则**从别名 revise 永远改不到入口条件**，别名层成为只写不读的死数据。

### M5 `relocate(moves)` → 别名继承「移动前的生效条件」

**冻结语义（契约 §3.5，D1 复核确认）**：不是「继承 target edge」，而是**把移动前的生效条件保留到新别名上**。

```ts
// store.ts:664-681 的 member 循环内
for (const member of plan.members) {
    const isRoot = member.rel === "";
    const newUri = this._rewriteUri(plan.toRoot, member.rel);
    const prior = this.effectiveDisclosure(member.node.uri);   // NEW：移动前（此时 member.node.uri 仍是旧 uri）
    const explicit = plan.when;                                 // moves[i].when，见 §2.2
    const carried = explicit === undefined ? prior : explicit;  // 显式传入则覆盖
    // …UPDATE nodes…
    this.db.prepare(
        `INSERT INTO aliases (alias_uri, target_node_id, disclosure) VALUES (?, ?, ?)
         ON CONFLICT(alias_uri) DO UPDATE SET
             target_node_id = excluded.target_node_id,
             disclosure     = excluded.disclosure`,
    ).run(member.node.uri, member.node.node_id, carried);
    this.reindexNode(member.node.node_id);
}
```

1. **`prior` MUST 在 `UPDATE nodes SET uri=…` 之前取**。反例：先改 uri 再算 `effectiveDisclosure(member.node.uri)` 会查不到旧 uri（旧 uri 此时还不是别名）→ 返回 `null` → **静默丢失条件**。
2. **`INSERT` 显式列出 `disclosure` 列**（修 `store.ts:677-679` 的 `OR REPLACE` 遗漏列缺陷）。
3. `plan` 结构需承载 `when`：`plans.push({ fromUri, toRoot, when: m.when, members })`（`store.ts:605-623` 处扩展）。
4. **根与后代一视同仁**：每个 member 的旧 uri 都成为别名（现状即如此，`:677-679`），故每个 member 都获得「它的移动前条件」。子节点若不继承，`effectiveDisclosure(旧子uri)` 会从移动前的值退化为 `null`（旧子 uri 原来不是别名，解析路径从「规范 uri」变成「无」）——**行为回归**。
5. **显式 `when`**：`relocateMany` 的 `moves[i].when` 为 `string | null` 时覆盖继承（`null` = 显式清除）。`undefined` = 继承。

**子节点随根移动时怎么办**（任务第 3 项）：**每个 member 独立继承自己的 `prior`**，不做「整棵子树共用根的条件」。理由：移动前各子节点各自有（或没有）条件，逐 member 继承才使 `effectiveDisclosure(旧uri) === effectiveDisclosure(新uri)` 对**每个** member 成立。

**漏了会怎样**：
- 不带 `disclosure` 列 → 已有别名的条件被 `OR REPLACE` 静默清空（契约 §3.5 已登记，**实测复现**：见 §2.2）。

### M8 读取路径的精确伪码（与 `resolveEntry` 同源）

```ts
effectiveDisclosure(uri: string): string | null {
    const entry = this.resolveEntry(uri);          // ← 与 setEntryDisclosure 同优先级（M4b）
    if (!entry) return null;                        // 未知 uri → null（不抛错）
    if (entry.kind === "canonical") {
        return (this.getStmt.get(entry.node_id) as NodeRow | undefined)?.disclosure ?? null;
    }
    // kind === "alias"：自己的条件，为 NULL 则继承目标节点级（`??`，非「命中即止」）
    const alias = this.aliasEntryStmt.get(uri) as { disclosure: string | null } | undefined;
    if (alias?.disclosure != null) return alias.disclosure;
    return (this.getStmt.get(entry.node_id) as NodeRow | undefined)?.disclosure ?? null;  // 悬空 target → null
}
```

> **MUST 与 `resolveEntry` 的分支一一对应**（M4b 的三条等价）。实现可内联优化，但**分支语义 MUST 一致**——任一方的优先级改动必须同批改另一方（这是 T-7 的教训）。

**「一个 uri 同时是别名又是边 target」怎么办**：**取别名的**（边不参与，契约 §3.1）。本函数根本不查 `edges`，故天然满足。

**性能 / SQL 次数**：

| 情形 | `resolveEntry` | `effectiveDisclosure` 总计 |
|---|---|---|
| uri 是规范 `nodes.uri` | **1**（`byUriStmt`） | **2**（`resolveEntry` + 取节点列；若实现为直接返回 `node.disclosure` 则 **1**） |
| uri 是别名，其 disclosure 非空 | **2**（nodes + aliases） | **3**（别名分支再多一次 `aliasEntryStmt`；可缓存同一行 → **2**） |
| uri 是别名，disclosure 为 NULL | **2** | **4**（alias 行 + 目标节点行；同上，复用已取行 → **3**） |
| uri 不存在 | **2** | **2** |

> ⚠️ 上表是**天真实现**的上界。**推荐实现（性能与语义都最优）**：`resolveEntry` **一次查两表**并把 alias 行**一并返回**（`{kind, node_id, alias_uri, aliasDisclosure}`），则 `effectiveDisclosure` 恒为 **1–2 次**、且与 `setEntryDisclosure` 分支**完全同源**。**这是定稿形态**——代价是 `resolveEntry` 的返回类型多一个字段（见 §2.1 的最终签名）。

**缓存**：**不做值缓存**。理由：写入面太广（`_updateNode` / `setAliasDisclosure` / `addEdge` / `relocateMany` / `deleteCascade` / `import` / `restoreDeleted` 都可能改变结果），缓存失效点比调用点还多，是契约 §8 T5 型静默错误的温床。**语句**（`MemoryStatement`）在构造期 prepare 一次并缓存为私有字段（与 `getStmt`/`byUriStmt` 同法，`store.ts:166-168`），避免每次调用重复 `prepare`——顺带指出 `resolveUri:184` 每调用一次就 `prepare` 一次，**这是既有低效**，登记 §11-C5。
