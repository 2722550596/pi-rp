| 被探测的文件 | 主文件 md5 | 留下 `-wal`/`-shm` | 证据 |
|---|---|---|---|
| 非 WAL 普通库 | 不变 | 否 | 实测 `probe-plain.db` 探测前后 `readdir` 只有它自己 |
| WAL 库 | **不变** | **是** | 实测 `waldb.db`：连接关闭后 `waldb.db-shm`(32KB) + `waldb.db-wal`(0B) 仍在 |

## 4. `openDatabaseReadonly`（`src/driver.ts` 新增）

### 4.1 签名与归属

```ts
/**
 * 只读打开，供多库探测使用。
 *
 * 存在的唯一理由：`openDatabase` 不可用于探测 —— 它在 :29 执行
 * `PRAGMA journal_mode = WAL`，而 WAL 转换需要写文件头；在一个 readOnly
 * 连接上这会直接抛 `attempt to write a readonly database`（实测），在一个
 * 可写连接上则会**改写被探测文件的头部**。探测 MUST NOT 有后者这种效果。
 *
 * 返回的 `MemoryDatabase` 与 `openDatabase` 同型：`exec`/`prepare` 可用，
 * `transaction` 可用（SQLite 允许只读连接 BEGIN/COMMIT，实测），
 * 任何写语句抛 `attempt to write a readonly database`（实测）。
 * 调用方 MUST 在 finally 里 `close()` —— 本函数不持有全局引用，泄漏即 fd 泄漏。
 */
export async function openDatabaseReadonly(path: string): Promise<MemoryDatabase>;
```

**放在 `driver.ts` 而不是 `discovery.ts`**：`DatabaseSync` 的构造参数形状与 `openDatabase` 逐字同源（`driver.ts:16-22` 的类型字面量），把「如何打开一个连接」的知识集中在一处是现状的既有切法（`driver.ts:26` 的 `node:sqlite` 提示也在这）。`discovery.ts` 只消费。

### 4.2 实现的形状（关键点）

```ts
export async function openDatabaseReadonly(path: string): Promise<MemoryDatabase> {
  // ⭐⭐ R6（契约 §5.5c，安全评审 SEC-04）：类型守卫 MUST 在这一层，
  //      MUST NOT 依赖调用方 —— "调用方记得检查"在第三个调用点就漏了一个，
  //      而漏掉的后果是**整进程挂死**（见下）。
  let st: Stats;
  try {
    st = statSync(path);
  } catch (error) {
    const code = (error as NodeJS.ErrnoException).code;
    throw new ReadonlyOpenError(
      code === "ENOENT" || code === "ENOTDIR" ? "missing" : "unreadable",
      path,
      `无法访问 ${path}：${code ?? String(error)}`,
    );
  }
  if (!st.isFile()) {
    // ⚠️ 这一步是**防挂死**，不是防读错文件：
    //    FIFO（mkfifo）上 `new DatabaseSync(p, {readOnly:true})` 会**永久阻塞**
    //    —— 实测 `timeout 5 node -e ...` 退出码 **124**（同步 API 占住事件循环）。
    //    目录/字符设备同样在这里被挡掉。
    throw new ReadonlyOpenError("not-a-file", path, `不是普通文件：${path}`);
  }

  let DatabaseSync: new (
    path: string,
    options?: { readOnly?: boolean },
  ) => { exec(sql: string): void; prepare(sql: string): MemoryStatement; close(): void };
  try {
    ({ DatabaseSync } = await import("node:sqlite"));
  } catch (error) {
    throw new Error(`Failed to load node:sqlite driver (requires Node >= 22.5): ${String(error)}`);
  }
  let db: { exec(sql: string): void; prepare(sql: string): MemoryStatement; close(): void };
  try {
    db = new DatabaseSync(path, { readOnly: true });
  } catch (error) {
    // chmod 000 → 与 missing **同一句** SQLite 错误，此时只能归 unreadable（§4.3）。
    throw new ReadonlyOpenError("unreadable", path, (error as Error).message);
  }
  // ⚠️ 只设 busy_timeout。MUST NOT 设 journal_mode —— 见 §4.1。
  db.exec("PRAGMA busy_timeout = 5000");
  return {
    exec: (sql) => db.exec(sql),
    prepare: (sql) => db.prepare(sql),
    transaction<T>(fn: () => T): T { /* 与 openDatabase:34-44 逐字同构 */ },
    close: () => db.close(),
  };
}
```

#### 4.2.1 ⭐⭐ 为什么守卫必须在这里（R6）而不是调用方

契约 §5.5c 的通用原则（评审给的教训，我认同并复述）：**约定「调用方记得检查」在三个调用点就漏了一个。**

| 只读打开点 | 有 `isFile()` 守卫吗（改前） |
|---|---|
| `probeMemoryDb`（§7.2 第 ① 步） | ✅ |
| `registry.resolve`（§5.3 第 ① 步） | ✅ |
| ⚠️ `readMemoryDbStats`（§6.5） | ❌ **没有** |

可达链（评审实测，我复核）：已注册库被 LRU 驱逐（上限 8 下**必然**发生）→ `/api/databases` 对未打开库走 `readMemoryDbStats` → 该路径上的文件已变成 FIFO → **`DatabaseSync` 同步构造永久阻塞 ⇒ 整个 web 进程挂死**。实测 `timeout 5 node -e "new DatabaseSync('/tmp/fifo-test.db',{readOnly:true})"` → **EXIT=124（挂死）**，而 `statSync(fifo).isFile() === false`（实测）。

⭐ 把守卫下沉到**唯一的只读打开点**（本函数）之后：`probeMemoryDb` 与 `registry.resolve` 的守卫变成**冗余的第二道**（保留，因为它们要给不同的 `reason` 文案），而 `readMemoryDbStats` **不需要任何改动**就自动安全。这就是「下沉到唯一打开点」的价值。

⚠️ **落地位置 MUST 是 `openDatabaseReadonly` 内部，MUST NOT 只在 `readMemoryDbStats` 里补一句**（安全评审补充）：本函数同时是 **`probeMemoryDb`** 的入口 —— 在 `readMemoryDbStats` 里补守卫只能挡住**一条**入口，`probeMemoryDb` 那条仍然裸奔。这正是「唯一打开点」的意义：**一个下沉点覆盖全部只读入口**。

⚠️ **第二条可达链（评审补充）**：除了「已注册库被驱逐后经 `/api/databases` 走 `readMemoryDbStats`」，还有「**FIFO 被扫描收进 `paths`**」这条 —— 见 §6.2.4 的硬要求（候选 MUST 判 `Dirent.isFile()`，MUST NOT 改成按文件名过滤）。两条链都要堵。

⚠️ **这**不是**说 `isFile()` 能挡下一切**：`/proc/version`、`/sys/kernel/notes` 实测 `statSync(...).isFile() === true` 且 `new DatabaseSync(p,{readOnly:true})` **能打开**（实测，SEC-01）。类型检查挡的是**非普通文件**（FIFO / 目录 / 字符设备 / socket），**不挡** procfs/sysfs 伪文件 —— 后者靠**探测**（`memory_kv` 不存在 ⇒ `not-memory-db`）挡。两层各挡一类，MUST NOT 把任一层说成「一次挡掉全部」（契约 §5.2#3 的初版断言已因此更正）。

- ⚠️ **MUST NOT** 写 `:memory:` 特判（`openDatabase:15` 有）：探测的是磁盘上的真实库。传 `""` 会被 `DatabaseSync("", {readOnly:true})` 拒绝（`[INFERENCE]`，未实测；但 `probeMemoryDb` 在更早的 `stat` 就返回 `not-a-file`，走不到这里）。
- ⚠️ **MUST NOT** 复用 `openDatabase` 再补 pragma，也 **MUST NOT** 给它加 `readOnly?: boolean` 可选参数 —— 后者会改动既有函数签名（牵动 `index.ts:124` 与全部调用点），且契约 §4.4 要求「**不破坏** `openDatabase` 现有语义」。

### 4.3 错误的形状

```ts
/** 只读打开失败。`reason` 与 `ProbeOutcome.reason` 同词表，便于 discovery 直接映射。 */
export class ReadonlyOpenError extends Error {
  readonly reason: "missing" | "not-a-file" | "unreadable";
  readonly path: string;
  constructor(reason: ReadonlyOpenError["reason"], path: string, detail: string) {
    super(detail);
    this.name = "ReadonlyOpenError";
    this.reason = reason;
    this.path = path;
  }
}
```

判据顺序（**这是把 SQLite 的含糊错误拆开的关键**，实测支撑见右列）：

| 步骤 | 判定 | 实测证据（Node v26.8.1） |
|---|---|---|
| 1. `fs.statSync(path)` 抛 `ENOENT`/`ENOTDIR` | `missing` | 不存在文件 → SQLite 只说 `unable to open database file`（errcode 14），**且不创建文件** |
| 2. `stat.isFile() === false`（目录、fifo、socket） | `not-a-file` | 目录 → `disk I/O error`（errcode 266），与 missing **不是同一句**，但仍不可依赖 |
| 3. `new DatabaseSync(path, {readOnly:true})` 抛（`EACCES` 等） | `unreadable` | `chmod 000` → `unable to open database file` ⚠️ **与 missing 同句** → 这就是必须前置 stat 的原因 |

⭐ 若无第 1/2 步，`missing` 与 `EACCES` 会**都**落进 `unreadable`，「文件不见了」就退化成人话说不清的 `unreadable` —— 而契约 §3.2#5 明确要求「文件消失报错而非静默移除」，用户需要看到「文件不见了」而不是「打不开」。

⚠️ 但 `openDatabaseReadonly` 的 stat **不负责**「是不是记忆库」——那是 `prepare` 阶段的事（实测：文本文件 open **成功**，`prepare` 才抛 `file is not a database`）。分层：`openDatabaseReadonly` 只管「能不能拿到连接」，`probeMemoryDb` 管「这个连接里有没有 `memory_kv.schema_version`」。

### 4.4 `close()` 契约（调用方 MUST）

- `openDatabaseReadonly` **不注册任何全局清理**（没有 `process.on("exit")` 兜底）。理由：探测是短命连接，把它塞进 registry 会破坏「注册表 = 可读写库」的语义。
- 调用方 MUST 用 `try/finally`：

```ts
const db = await openDatabaseReadonly(p);
try { /* 读 schema_version */ } finally { db.close(); }
```

- 重复 `close()` **会抛** `database is not open`（`ERR_INVALID_STATE`，实测）。所以探测/registry 的 `close` 只允许调一次；需要幂等的调用点（如 `closeAll()` 被调两次）在 registry 侧自行包一层（§5.8）。
- `[INFERENCE]` `close()` 抛错不影响 fd 释放（`database is not open` 意味着已经关了）。这条只影响「谁先关」的记账。

## 5. `StoreRegistry`（`src/web/registry.ts` 新增）

### 5.1 数据结构（与契约 §3.2 逐字一致的部分用 ⭐ 标）

```ts
import type { MemoryStore } from "../store.ts";

⭐/** 契约 §3.2 冻结形状。 */
export interface RegisteredDb {
  /** 绝对路径，同时是库 id（契约 §4.2）。MUST 是 `path.resolve` 的结果，MUST NOT 是 realpath。 */
  path: string;
  /** 已打开的库；未打开为 null（懒加载）。 */
  entry: StoreEntry | null;
}

⭐/** 契约 §3.2 冻结形状 + 本文新增的 `inFlight`（§5.6）。 */
export interface StoreEntry {
  store: MemoryStore;
  /** 与 store 一一对应的连接。供 `/api/databases` 显示，**不是**逻辑依据。 */
  openedAt: string;
  /** 供 LRU 排序。 */
  lastUsedAt: number;
  /** ⭐ 本文新增：进行中的请求数。> 0 的 entry MUST NOT 被驱逐（§5.6）。 */
  inFlight: number;
}

⭐/** 契约 §3.2#5：已注册但文件消失 → 请求报错，MUST NOT 静默移除。
 *  ⭐ `path-escalated` 是契约 §5.5b R5（SEC-02）新增的一个 reason —— 见 §5.13。 */
export class DbUnavailableError extends Error {
  readonly reason: "missing" | "not-a-file" | "path-escalated";
  readonly path: string;
  constructor(reason: DbUnavailableError["reason"], path: string, detail: string) {
    super(detail);
    this.name = "DbUnavailableError";
    this.reason = reason;
    this.path = path;
  }
}

export interface StoreRegistryOptions {
  /** 同时打开的库数上限。默认 8（契约 §3.2#3）。可注入 —— D5 的 V6 要把它调小才好断言。 */
  limit?: number;
  /** ⭐⭐ R5（§5.13）：路径策略。**必填**（见下）。 */
  policy: PathPolicy;
  onLog?: (line: string) => void;
}

export class StoreRegistry {
  private readonly dbs = new Map<string, RegisteredDb>();             // 路径 → 注册项（含未打开）
  private readonly inflight = new Map<string, Promise<StoreEntry>>(); // 路径 → 进行中的打开（§5.4）
  private readonly pinned = new Set<string>();                        // ⭐ 永不驱逐（§5.5）
  private readonly limitValue: number;
  private readonly onLog: (line: string) => void;
  /** ⭐ R5（§5.13）：构造时传入的路径策略。**必填、非 null**（fail-closed，§5.13.3）。 */
  private readonly policy: PathPolicy;   // ⭐ 必填、非 null（fail-closed，见 §5.13.3）
  private closed = false;

  constructor(opts: StoreRegistryOptions);   // ⭐ `opts` **必填**：容器可选会抵消字段必填（§5.13.3）

  /** ⭐ R5：`checkPathAllowed(policy, p)` 的薄封装（**两参数**，见 §5.13.2）。 */
  private policyCheck(p: string): boolean;

  entryOf(raw: string): StoreEntry | null; // 纯查表：过 key()，不 stat、不打开、不抛（`":memory:"` 除外）
  get openCount(): number;                  // 已打开 entry 数（含 pinned）
  get limit(): number;
  has(raw: string): boolean;                // ≡ entryOf(raw) !== null
  list(): RegisteredDb[];                   // 快照（含未打开的），顺序 = 插入序

  resolve(raw: string): Promise<StoreEntry | null>;      // ⭐ 唯一解析入口（§5.3）；内部过 key() + R5
  register(raw: string): Promise<StoreEntry>;            // 探测已过的路径：登记 + 打开；内部过 key()
  adopt(raw: string, store: MemoryStore): StoreEntry;    // ⭐ 仅用于**不由 registry 打开**的进程库（SEC-06，见 §5.5）
  release(entry: StoreEntry): void;                      // 请求结束：inFlight--（§5.6；⭐ 收 entry 而非 path）
  evictBeyondLimit(keepPath: string): void;              // 导出供测试；resolve 内部也会调
  closeAll(): void;                                      // server close 用；幂等
}
```
⚠️ **注**：`PathPolicy` 与 `checkPathAllowed` 的**类型与实现都归 D2**（`src/web/db-path-policy.ts`，契约 §8.1）。`registry.ts` 只 `import` 它们（这是 D1→D2 的唯一依赖方向，D2 不 import registry）。

### 5.2 五条冻结语义的落地对照

| 契约 §3.2 | 我的实现 |
|---|---|
| **#1 懒打开** | `register` 只写 `dbs.set(path, { path, entry: null })`；连接只在 `resolve` 命中且 `entry === null` 时建立。启动时**只有进程库一个连接**（`adopt`）。33 个发现库不会在启动时被打开。 |
| **#2 同库同连接** | 唯一连接来源是 `resolve` 的懒打开分支，且该分支被 `inflight` Map 去重（§5.4）；`dbs` 的 key 是绝对路径 ⇒ 一个路径最多一个 entry。**没有任何其它路径能 `openMemoryStore`**（`register` 也走同一个内核）。 |
| **#3 LRU 上限 8** | `evictBeyondLimit`：按 `lastUsedAt` 升序挑「非 pinned、非 inFlight、非 keepPath」的 entry 关闭；**在打开新连接之前**调用（§5.7）；关闭后把 `entry` 置 `null`（**保留注册项**）。detector 的 WeakMap 自然失效（§5.9）。 |
| **#4 关闭失败不致命** | `close` 包在 `try/catch`，失败只 `onLog("⚠️ 关闭 <path> 失败：<msg>")`，然后**照常**把 `entry` 置 `null`。 |
| **#5 文件消失不静默** | `resolve` 命中已注册路径时**先 stat**；失败抛 `DbUnavailableError`（→ D3 映射 `invalid_db` 409）。**绝不**从 `dbs` 里 `delete`。 |

### 5.3 `resolve` 的精确算法（唯一入口）

```ts
async resolve(raw: string): Promise<StoreEntry | null> {
  if (this.closed) throw new Error("registry is closed");
  const path = StoreRegistry.key(raw);     // ⭐ §5.10.1：入口归一（statSync 也用这个值）
  const reg = this.dbs.get(path);          // 调用方可传任意形状，归一由入口负责
  if (!reg) return null;                   // ⭐ 未注册 → null，D3 映射 404。
                                           //    MUST NOT 顺手注册（契约 §4.2#3）

  // ① 文件必须在（§5.2#5）。已打开的 entry 也要查 —— POSIX 下 fd 仍有效，
  //    但"服务一份已消失的库的快照"正是契约 §3.2#5 要防的。
  let st: Stats;
  try {
    st = statSync(path);
  } catch {
    throw new DbUnavailableError("missing", path, `记忆库文件不存在：${path}`);
  }
  if (!st.isFile()) {
    throw new DbUnavailableError("not-a-file", path, `记忆库路径不是普通文件：${path}`);
  }

  // ② ⭐⭐ R5（契约 §5.5b，SEC-02）：**懒打开必须重跑路径策略**。
  //    注册与打开在时间上是分离的：一个 roots 内的 symlink 在「注册时合法」，
  //    可以被事后重指向 roots 外，而 LRU 驱逐后的下一次请求会自动重开 ⇒
  //    没有这一步就会把 roots 外的文件灌表（评审复现：1 → 24 张表）。
  //    ⚠️ 这不是 TOCTOU 竞态窗口，是**整个注册→重开生命周期**都缺守卫，
  //       且**不需要赢任何竞态**。
  //  ⭐⭐ `pinned` 豁免（契约 §5.2 末 / §5.4）：**进程库不受 roots 约束**
  //    （`--db /outside/x.db --roots /inside` 是明文合法的配置）。缺了豁免：
  //    D4 首屏把 selectedDb 设为进程库路径 ⇒ 每个请求都带 ?db=<进程库>
  //    ⇒ 该配置下**全站 409**，而不带 ?db= 仍 200（同一个库两种结果）。
  //    见 §5.13.4。
  if (!this.pinned.has(path) && !this.policyCheck(path)) {
    throw new DbUnavailableError(
      "path-escalated",
      path,
      `记忆库路径已超出允许范围（roots 内的符号链接被重定向？）：${path}`,
    );
  }

  if (reg.entry) {
    reg.entry.lastUsedAt = Date.now();
    reg.entry.inFlight++;
    return reg.entry;
  }

  // ② 懒打开（去重）。
  const existing = this.inflight.get(path);
  if (existing) {
    const entry = await existing;
    entry.lastUsedAt = Date.now();
    entry.inFlight++;
    return entry;
  }

  // ③ ⭐ 先腾位，再打开 —— 保证峰值连接数不超过 limit（§5.7）。
  this.evictBeyondLimit(path);
  const opening = this.openInto(path);
  this.inflight.set(path, opening);
  try {
    return await opening;
  } finally {
    // ⭐ MUST 清理，否则一次失败会把永久 rejected 的 Promise 钉在这条路径上，
    //    之后每个请求都以同一句错误失败（"in-flight Promise 中毒"，§10.4）。
    this.inflight.delete(path);
  }
}
```

⭐ **`inFlight++` 出现在三条返回路径**（命中已打开、命中 in-flight、自己打开）：任何一条都要让「这次请求占用了这个 entry」被记账，否则驱逐可能在请求走到一半时把连接关掉。`dispatch` 侧 MUST 在 `finally` 里 `registry.release(entry)`（§5.6）。**这是 D1↔D3 的一个接线点**（已 IRC 冻结签名）。

### 5.4 并发安全（本文最需要说清的一节）

**问题**：同一个路径两个并发请求同时触发懒打开 → MUST 只建一个连接（契约 §3.2#2）。

**方案：in-flight Promise 去重（不是锁、不是队列）。**

- 为什么**不需要**互斥锁：`resolve` 从入口到 `this.inflight.get(path)` 之间**没有 `await`**（`statSync` 同步、`Map` 同步），所以「查 `inflight`」与「写 `inflight`」之间**不可能**被另一个请求插入 —— JS 单线程 run-to-completion 保证。真正的交错窗口只存在于 `await this.openInto(...)` 那一段，而那一段已被 `inflight` 覆盖。
  `[INFERENCE]`：这一点没有实测必要（是 V8 语义，不是 SQLite 行为），但它是我不用锁的**唯一**理由，故在此显式声明。
- 为什么 `inflight` 存 `Promise<StoreEntry>` 而不是在回调里直接放 `entry`：`resolve` 必须在返回前 `inFlight++`，而 `inFlight++` 是**每个请求各一次**的副作用，不能放进共享的 Promise 里。共享的是「打开结果」，`++` 在各自的 `await` 之后做。
- **失败传播**：`opening` 的 rejection 由**第一个**调用者抛出，第二个调用者 `await existing` 也抛**同一个** Error 对象。这是期望行为（同一原因同一错误）。`finally` 清理保证**后续**请求会重新尝试（例如用户先创建目录再重试）。
- **`closeAll` 竞态**：`closeAll` 期间正在 `openMemoryStore` 的路径，靠 `this.closed` 标志在 `openInto` 的 `.then` 里兜底（关掉刚建好的连接并抛 `registry is closed`）。`[INFERENCE]` 这是罕见路径（关服务瞬间），但不处理就是 fd 泄漏。

**明确否决的备选**：

- 每路径一个 `AsyncLock`：代码量 3 倍，收益为 0（窗口已被 Promise 覆盖）。
- 队列串行化全部打开：会把 N 个库的懒打开变成串行，且无必要（`resolve` 的同步段已保证不同路径互不干扰）。

### 5.5 `pinned`：进程库 MUST NOT 被驱逐（契约没写，但必须做）

契约 §3.2#3 只说「关闭最久未用的且不是当前请求目标的」。这留了一个洞：

**场景**：`limit = 8`，8 个库已开，其中一个是**进程库**（`ctx.store`）。用户请求第 9 个库 → LRU 恰好选中进程库 → 关掉它。后果三连：

1. `/api/meta`（不带 `?db=`）走 `ctx.store`（契约 §3.3 的缺省分支），拿到**一个已关闭的连接** → `database is not open` → `mapStoreError` 的 `routes.ts:138` 把它映射成 **500 internal**。用户看到「服务器内部错误」，实际是「你访问了太多库」。
2. launcher 的 `probePort`（`web-launcher.ts:67-69`）拿到的 `db_path` 比对仍对（路径没变），但请求本身炸了 → 判定成 `occupied`，让路换端口 → **`/memories web` 会在一个已经健康的实例旁边另起一个**。
3. `server.ts:130` 在关服务时会对已关闭的 handle 再 `close()` → 抛 `database is not open`（实测重复 close 抛 `ERR_INVALID_STATE`），关服务流程被异常打断。

**设计**：注册表持有 `pinned: Set<string>`；`adopt(path, store)` **无条件**把 `path` 加进 `pinned`；`evictBeyondLimit` 的候选集 = `!pinned && inFlight === 0 && path !== keepPath`。

- `register`（手动/发现库）**不** pin —— 它们可被驱逐后重开（重开很廉价：`createSchema` 对已建表的库是一串幂等的 `CREATE … IF NOT EXISTS`，`schema.ts:139`）。
- **`limit` 与 `pinned` 的冲突**：`openCount` 计**全部**已打开 entry（含 pinned）。若 `pinnedCount >= limit`（例如测试把 `limit` 设成 1 又 `adopt` 了进程库），`evictBeyondLimit` 一个也关不掉 —— 此时 `onLog("⚠️ 注册表超出上限（…）：候选都在使用中或已固定")` 并**允许超出**。理由：**正确性优先于上限**（关掉在用/固定连接会造成 500，比多开几个 fd 严重得多）。
  → D5 的 V6 判据建议写成 `openCount <= Math.max(limit, pinnedCount)`；用 `limit: 2` + **不 adopt 进程库**（测试若用 `:memory:` 进程库就不 adopt，见 §5.10）时退化为 `openCount <= 2`。

### 5.6 引用计数：驱逐 MUST NOT 关掉「正在被另一个请求使用」的连接

**场景**：库 A 的 entry `lastUsedAt` 很旧（用户很久没访问），但**此刻**有一个请求正拿着它执行 `getSearch`（`routes.ts:275-283` 里 `await search(...)` 是唯一会真正让出 event loop 的 handler 路径）。与此同时另一个请求要开第 9 个库 → LRU 选中 A → 关掉 → 前一个请求在 `await` 回来后对已关闭的连接 `prepare()` → `database is not open` → **500**。

**设计**：`StoreEntry.inFlight` 计数。

- `resolve` 的每条返回路径都 `inFlight++`；
- `dispatch`（D3）MUST 在 `finally` 里 `registry.release(entry)`（`inFlight--`，下限 0，并 `lastUsedAt = Date.now()`）；
- `evictBeyondLimit` 跳过 `inFlight > 0` 的 entry。

⭐ 这条同时**取代**了契约 §3.2#3 的「不是当前请求目标」：当前请求的 entry 必然 `inFlight >= 1`，天然不在候选集里。`keepPath` 参数保留（D3 已按这个签名写过对接），但它的语义降级为「额外的保险」——我在代码注释与本文都要写清，避免后人以为它是唯一机制。

⭐ 由此**还**取消了「驱逐必须在 `dispatch` 拿到目标库之前」的必要性：即使驱逐发生在之后，引用计数也不会让在用连接被关。但我**仍然**在 `resolve` 内部、打开之前驱逐（§5.7），因为那是唯一能保证**峰值连接数不超上限**的位置。

```ts
/**
 * 请求结束，归还租约。幂等；对已被驱逐的 entry 也安全。
 * ⭐ 参数是 `entry` 而非 `path`：`path` 版在
 *   「A 持 entry → 该 entry 被驱逐 → B 重开同一 path → A release(path)」
 *   的序列里会扣**新** entry 的计数（而 B 的 `inFlight++` 还没发生），引用计数就漏了一次。
 *   用 entry 引用则永远扣在它当初抬的那一个上，且无需查注册表。
 */
release(entry: StoreEntry): void {
  entry.inFlight = Math.max(0, entry.inFlight - 1);
  entry.lastUsedAt = Date.now();
}
```

### 5.7 驱逐时机与算法

```ts
evictBeyondLimit(keepPath: string): void {
  // 目标：为"即将打开的这一个"腾位置 ⇒ 已打开数要降到 limit - 1。
  const target = Math.max(0, this.limit - 1);
  const candidates = [...this.dbs.values()]
    .filter((r) => r.entry !== null && r.path !== keepPath && !this.pinned.has(r.path) && r.entry.inFlight === 0)
    .sort((a, b) => (a.entry as StoreEntry).lastUsedAt - (b.entry as StoreEntry).lastUsedAt); // 最久未用在前
  let open = this.openCount;
  for (const reg of candidates) {
    if (open <= target) break;
    this.closeEntry(reg);      // 内部 try/catch，失败仅 onLog（§5.2#4）
    open--;
  }
  if (open > this.limit) this.onLog(`⚠️ 注册表超出上限（${open}/${this.limit}）：候选都在使用中或已固定。`);
}

private closeEntry(reg: RegisteredDb): void {
  const entry = reg.entry;
  if (!entry) return;
  // ⭐ pinned = 所有权不在 registry（adopt 进来的进程库）：只解引用，MUST NOT 关。
  //    见 §5.8「谁打开，谁关闭」。`server.ts:130` 会关它。
  if (this.pinned.has(reg.path)) {
    reg.entry = null;
    return;
  }
  try {
    entry.store.db.close();
  } catch (error) {
    // 契约 §3.2#4：关闭失败不致命。
    this.onLog(`⚠️ 关闭记忆库失败（${reg.path}）：${(error as Error).message}`);
  }
  reg.entry = null;   // ⭐ 注册项保留：库还在，只是连接没了（契约 §3.2#5 的"不静默移除"同样适用）
}
```

- **`target = limit - 1` 而不是 `limit`**：调用点是「打开之前」，打开动作会让计数 +1；用 `limit - 1` 使峰值**恰好**等于 `limit`。用 `limit` 的话峰值会是 `limit + 1`。实测逻辑模拟：顺序打开 12 个库、`limit = 8` → 最终 8 个（`db4…db11`），序列中从未出现 9。
- **复杂度**：O(打开数 · log 打开数)，打开数 ≤ 8 ⇒ 可忽略。**MUST NOT** 引入更花哨的结构（LRU 链表）：单用户本地工具，8 个元素的排序是零成本。
- **幂等**：重复调用不关任何东西（`open <= target` 立即 break）。
- ⭐ **`pinned` 的 entry 被计入 `open`（所以它占名额）但永不在候选集里**。⇒ 若 `pinnedCount >= limit`，`open` 会停在上限之上并打日志（§5.5 的「正确性优先于上限」）。实测逻辑模拟：`limit = 3` + `pinned = {/db0}` + 顺序打开 6 个 → 峰值 3，从不超。

### 5.8 `openInto` / `adopt` / `register` / `closeAll`

```ts
/** ⭐ 唯一的连接建立点（全文件仅此一处 `openMemoryStore`）。`resolve` 是唯一调用者；
 *  `register` 也经 `resolve`，所以不存在第二条打开路径 —— 那是"同库同连接"最容易破的地方。 */
private openInto(path: string): Promise<StoreEntry> {
  return openMemoryStore(path).then((store) => {
    const entry: StoreEntry = { store, openedAt: new Date().toISOString(), lastUsedAt: Date.now(), inFlight: 1 };
    // 打开期间可能已被 closeAll（关服务竞态）；此时立即收掉，避免泄漏 fd。
    if (this.closed) {
      try { store.db.close(); } catch { /* 忽略 */ }
      throw new Error("registry is closed");
    }
    // ⭐ 这个库即将被写入 ⇒ §6.4 的 stats 缓存立刻陈旧。这是 registry → discovery
    //    的唯一 import 方向（discovery 不 import registry，无环）。
    invalidateStats(path);
    const reg = this.dbs.get(path);
    if (reg) reg.entry = entry;
    return entry;
  });
}

adopt(raw: string, store: MemoryStore): StoreEntry {
  const path = StoreRegistry.key(raw);          // ⭐ §5.10.1：入口归一，幂等
  const entry: StoreEntry = { store, openedAt: new Date().toISOString(), lastUsedAt: Date.now(), inFlight: 0 };
  this.dbs.set(path, { path, entry });
  this.pinned.add(path);                   // ⭐ 进程库永不被驱逐（§5.5）
  return entry;
}

/**
 * ⭐⭐ SEC-06（安全评审）：`adopt` MUST 只用于**不由 registry 打开**的连接。
 *
 * `adopt` 无条件 pin（§5.5）+ `closeEntry` 对 pinned 只解引用不 close（§5.8）⇒
 * 一个经 `adopt` 进来的连接**永不被驱逐、也永不关闭**。
 * 对**进程库**这是对的（`server.ts:130` 负责关它，§5.11 的「谁打开谁关闭」）。
 * 但若把 `/api/databases/create` 新建出来的连接也 `adopt` 进来，就得到一个
 * **永不回收的 fd + 永不释放的 store**（保留到进程退出）。
 *
 * ⇒ **新建/手动打开一律走 `register(path)`**（它走 `resolve` → `openInto`，
 *    连接所有权在 registry，可被 LRU 驱逐并正常 close）。
 *    `adopt` 的**唯一合法调用点**是 `cli.ts` 启动时的 `registry.adopt(opts.dbPath, store)`。
 *    验收 C16 用 `grep` 钉死这一点（§12）。
 */

async register(raw: string): Promise<StoreEntry> {
  const path = StoreRegistry.key(raw);          // ⭐ 同上
  const reg = this.dbs.get(path);
  if (reg?.entry) { reg.entry.lastUsedAt = Date.now(); return reg.entry; }   // 幂等
  if (!reg) this.dbs.set(path, { path, entry: null });                      // 登记（≠ 打开）
  // ⭐ 必须走 resolve 的同一条去重路径 —— 直接调 openInto 会与并发的 resolve 各建一个连接（F3）。
  //    resolve 返回 null 只可能是"刚被 closeAll 清掉了"，此时重登记一次。
  const entry = (await this.resolve(path)) ?? (await this.resolve(this.ensureRegistered(path)));
  if (entry) this.release(entry);   // register 不持请求：抬过的引用计数立刻归还
  return entry as StoreEntry;
}

/** `closeAll` 与 `register` 的极小竞态兜底：重新登记并返回 path（供再次 resolve）。 */
private ensureRegistered(path: string): string {
  if (!this.dbs.has(path)) this.dbs.set(path, { path, entry: null });
  return path;
}

/** ⭐ 唯一 key 归一（§5.10.1）。`path.resolve` 幂等；`:memory:` 一律拒。 */
private static key(raw: string): string {
  if (raw === ":memory:") throw new Error("StoreRegistry 不接受 :memory:");
  return path.resolve(raw);          // 相对路径按 cwd 解析，`..` 折平
}

closeAll(): void {
  this.closed = true;
  for (const reg of this.dbs.values()) this.closeEntry(reg);
  this.dbs.clear();
  this.pinned.clear();
  this.inflight.clear();
}
```

- **`closeAll` 幂等**：第二次调用时 `dbs` 已空 ⇒ 无操作。
- ⚠️ **它 MUST NOT 关 `ctx.store`**：进程库的关闭归 `server.ts:130` 所有（既有语义，本功能不动）。所以**不需要** `owner: "external"` 之类的标记 —— 规则是「**谁打开，谁关闭**」，`adopt` 进来的连接所有权不在 registry。
  - ⚠️ 严格说 `closeAll` 的循环会**碰到** pinned 的进程库（它也在 `dbs` 里）并调 `close()`。两种解法：(a) `closeEntry` 里加 `if (this.pinned.has(reg.path)) { reg.entry = null; return; }`（只解引用，不关）；(b) 让 `closeAll` 跳过 pinned。
    **定：选 (a)** —— 语义更直白（「pinned = 所有权不在我」），且 `closeEntry` 是唯一的关闭点，规则集中在一处。
    → `closeEntry` 的完整版：先判 pinned（置 `null` 直接返回），再 try/catch close，再置 `null`。
- ⚠️ **若 `closeAll` 在 `server.close` 之后再跑**：进程库那条被 (a) 跳过 ⇒ 根本不会重复 close。顺序无关。
- **`register` 与 `resolve` 共用 `openInto`** ⇒ 不存在第二条打开路径。

### 5.9 与 `runtime.ts` 的 detector WeakMap 的合作（契约 §3.2#3 的「一并失效」）

契约要求驱逐时 `WeakMap.delete(store)`。**我的实现不做这件事，且必须解释为什么**：

- `runtime.ts:15` 的 `detectors` 是 `WeakMap<MemoryStore, ChangeDetector>`，且**模块私有**（没有 `delete` 的导出）。
- 驱逐后 `reg.entry = null`，那个 `MemoryStore` **不再被注册表强引用**；若无其它强引用（请求已 `release`），它会被 GC 回收，WeakMap 的键随之**自动消失** —— 这正是 WeakMap 的语义。**显式 `delete` 与 GC 等价，但显式 delete 需要把 `deleteDetector` 导出到 `runtime.ts` 的公共面**，为一个自动发生的效果引入一个跨模块的写入口（且 `runtime.ts` 不在我的文件边界内）。
- ⚠️ **但有一个必须处理的隐患**：驱逐后**同一路径重开**会创建**新的 `MemoryStore`**（新连接）⇒ WeakMap 里是**新键**，被关掉的旧键自然失效。所以「同一路径的两个 store 同时活着」不可能发生（§5.2#2），`changed` 语义不被破坏。
  ⭐ **重开时 `changed` 会是什么？** `ChangeDetector.last` 从 `null` 开始 ⇒ 第一次 `read()` 返回 `changed: false`（`change-detect.ts:41`）。与「首次访问一个库」的表现一致。**这是正确且诚实的**：连接换了，基线就该重建。登记为「已知行为」而非缺陷（§10.8）。
- ⚠️ **若将来有人给 `runtime.ts` 加了强引用缓存**（例如把 `WeakMap` 换成 `Map<store, detector>`），本条立刻变成真缺陷（旧 store 永远不回收 ⇒ 驱逐只省 fd 不省内存）。故**写进验收清单**：`runtime.ts` MUST 保持 `WeakMap`（§12 C11）。

**这与契约的字面要求（`weakMap.delete(store)`）有差异，已登记为待拍板 T1（§13）。** 我的立场：字面执行需要新增 `runtime.ts` 导出（不归我），而效果由 GC 免费提供。

### 5.10 路径归一化、`realpath` 与 `:memory:`

`dbs` 的 key MUST 是 `path.resolve` 的结果（契约 §5.2#1、§4.2#1）。⚠️ 但**归一化是 registry 的入口职责，不是调用方的纪律** —— 这一条是 D3 在 04:0x 报了一处真实风险后改定的，见 §5.10.1。

#### 5.10.1 ⭐ 统一入口归一（否则会出现**隐性 404**）

**问题**（D3 报，我核实成立）：若 `adopt(opts.dbPath, store)` 用**未归一**的 `opts.dbPath`，而 handler 侧 `resolve(path.resolve(raw))` 用归一值，那么当两者字面不等时（例：`--db "<cwd>/.pi/../.pi/memory.db"`）**`?db=<进程库路径>` 会 404**。
⭐ 危险在于**症状是隐性的**：不带 `?db=` 的 `/api/meta` 照常返回（走缺省分支），所以契约 V4 仍绿 —— 红的是「显式指定进程库」这一条。缺陷只在用户显式指定时才暴露。
⭐ **不是理论担忧**：`web-launcher.ts:125` 自己就写了 `const dbPath = path.resolve(opts.dbPath)` —— 上游确实传过未归一的值。

**设计（单点，四处统一）**：

```ts
/** ⭐ 唯一 key 归一：`path.resolve` 幂等；`:memory:` 一律拒。 */
private static key(raw: string): string {
  if (raw === ":memory:") throw new Error("StoreRegistry 不接受 :memory:");
  return path.resolve(raw);          // 相对路径按 cwd 解析，`..` 折平；幂等
}
```

- `adopt` / `register` / `resolve` / `entryOf`（`has` 同）**四处入口全部先过 `key()`**。
  ⇒ **`entryOf(p)` 与 `resolve(p)` 对同一逻辑路径必然给同一结果**（两者都先归一再查 `Map`）。这是 D3 要求的「一致性保证」，也是我这边可机械核验的断言（§12 C15）。
- ⭐ **为什么不靠调用方**：归一化散在调用方 = `cli.ts` / `/api/databases/open` 的 handler / 未来第三处**各自都要记得**，漏一处就出一个隐性 404。放 registry 入口是**单点**，且对已归一值是幂等的（零成本）。
- ⚠️ `resolve` 的 `statSync` 用**归一后的 abs**（不是 raw）：否则带 `..` 的路径会 stat 到一个语义相同但字面不同的位置 —— 结果一样，但错误信息里的路径会难看。
- ⚠️ `key()` **不做 realpath**（理由见下）。所以 `~/.pi/../.pi/x.db` → `/home/u/.pi/x.db`（对），而 `/a/link.db` 与 `/b/real.db` 仍是两个 key（F9，已登记 T2）。
- `list()` 返回的 `RegisteredDb.path` 也是**归一后的**值 ⇒ `/api/databases` 的 `databases[].path` 一定是绝对路径（契约 §4.2 的「库 id = 绝对路径」由此成立）。

⭐ 对 `cli.ts` 的连带要求：`adopt` 前 MUST 判 `opts.dbPath !== ":memory:"`（`key()` 会抛），但**不需要**自己 `path.resolve`（registry 会做）—— `CliOptions.roots` 仍在 CLI 侧 resolve（那是扫描用的路径，不是注册表 key）。

#### 5.10.2 **MUST NOT 做 `realpath`**。理由（三条）：

1. 契约 §5.2#1 已把「`path.resolve()`」冻结为唯一归一化；
2. 若规范化为 realpath，则「前端回传的值 == 注册表 key」不再成立（前端只会拿到 `/api/databases` 给它的那个字符串 —— 那已经是 realpath 了，所以这条 `[INFERENCE]` 影响小）；
3. ⭐ 真正的问题在 launcher：`web-launcher.ts:67-69` 比较 `db_path === dbPath`，而 `dbPath` 来自 CLI 的 `resolveMemoryDbPath`（**不做 realpath** —— `config.ts:44-45`：`isAbsolute(declared) ? declared : resolve(cwd, declared)`，只有 `resolve`，没有 `realpath`）。若 `adopt` 时把 key 换成 realpath，那么**带 `?db=<用户输入的路径>`** 与**不带 `?db=`** 会解析到两个不同的 key（一个 realpath、一个原样）⇒ 同一物理库两个连接 ⇒ `data_version` 语义损坏。**这是硬约束。**
- `:memory:` 经 `path.resolve(":memory:")` 会变成 `<cwd>/:memory:` —— 一个**假的绝对路径**，注册进去会 `stat` 失败或（更糟）命中一个真叫 `:memory:` 的文件。故 `key()` 显式拒绝 `":memory:"`（§5.10.1）。
- `cli.ts` 只在 `opts.dbPath !== ":memory:"` 时 `adopt`。`[INFERENCE]` `:memory:` 不会来自 CLI（`resolveMemoryDbPath` 返回磁盘路径）；它只出现在测试里。
- 测试用 `:memory:` 作进程库时，`ServerContext.store` 照旧（契约 §3.3 的缺省分支不查注册表），**不带 `?db=`** 的请求一切如常（V4 不受影响）。⚠️ 但**带 `?db=:memory:`** 会抛（`key()`）—— 这是期望行为，`:memory:` 不是可寻址的库 id。
#### 5.10.3 ⚠️ `?db=` 值的编码是**上游责任**，但后果落在注册表（契约 §7.7）

H1 的 `key()` 只做 `path.resolve`，**不做 URL 解码**（那是 `new URL(req.url)` 的活，在 D3）。所以「值被编码坏」的两种后果都表现为**注册表 miss 或命中错库**，值得在这里点名：

| 编码形态 | 读回的值 | 注册表行为 |
|---|---|---|
| `.set("db", p)` / 对象构造 / `encodeURIComponent` | 逐字节原样 | ✅ 命中正确的库 |
| 手写不编码（路径含 `+`/`&`/`?`） | `+`→空格、`&` 截断 | ❌ `key()` 得到一个不存在的路径 → `entryOf` miss → **404**（fail-closed，安全但不友好） |
| 把 `db=` **手拼追加**到一个**已有** `db=` 的 query 上 | `searchParams.get("db")` 取**第一个** | ⚠️ **命中另一个已注册库 ⇒ 读 A 写 B**（这才是危险的那个） |

⭐ **对 D1 的结论**：注册表**无法**从错误的 key 上分辨「用户选错了库」与「值被编码坏了」—— 两者都是「一个已注册或未注册的路径字符串」。所以这条防线**必须在 D4 的注入点**（契约 §7.7 已冻结：`db` 值 MUST 经 `.set()`／对象构造或等价 `encodeURIComponent`；MUST NOT 手拼追加）。D1 侧能做的是**保证 `key()` 幂等且忠实**（已做，§5.10.1），不去「猜测性地修复」一个看起来像路径的字符串。
⚠️ **MUST NOT** 在 `key()` 里对值做 `decodeURIComponent`／`+`→空格 之类的**猜测性反变换** —— 那会把「404」变成「静默打开另一个库」，正是 §4.2#1 全等判据要防的。

### 5.11 注册项的生命周期总表

| 事件 | `dbs` | `entry` | 连接 | `pinned` |
|---|---|---|---|---|
| `adopt(path, store)` | set | 已给 | 借用（所有权在 server/cli） | **+path** |
| `register(path)` | set | null | — | — |
| `resolve` 命中未打开 | — | 新 entry | `openMemoryStore` 新建（**所有权在 registry**） | — |
| `evictBeyondLimit` | 保留 | `null` | `close()`（失败仅日志） | — |
| 文件消失（resolve） | 保留 | 不动 | 不动 | — |
| `closeAll` | clear | — | registry 打开的全部 `close()`；pinned 只解引用 | clear |
| `release` | — | 不动 | 不动 | — |

⭐ **所有权规则（一句话）**：**谁打开，谁关闭。** registry 只关它自己 `openMemoryStore` 出来的连接；`adopt` 进来的由 `server.ts:130`（进程库）关。

### 5.12 与 D3 的接线（已 IRC 冻结，逐字一致）

三个 MUST：

1. `dispatch` 在 `?db=` 非空时 MUST `await registry.resolve(abs)`；返回 `null` → `not_found`(404)。
2. `dispatch` 拿到 entry 后 MUST `try { … } finally { registry.release(entry) }` —— 否则 §5.6 的引用计数失效。**注意传 `entry` 不是 `abs`。**
3. `DbUnavailableError` 的映射：MUST `instanceof` 判定，MUST NOT 匹配 message（`routes.ts:112-141` 那套字符串匹配是既有代码的风味，但新错误有具名类型，没理由退回去）。

**启动接线**：`cli.ts` MUST 在 `startServer` 前 `registry.adopt(opts.dbPath, store)`，否则 `?db=<进程库路径>` 会 404（契约 §4.5 只要求**不带** `?db=` 的 `/api/meta` 语义不变，但**带**进程库路径也必须解析回同一个 store）。

### 5.13 ⭐⭐ R5：懒打开 MUST 重跑路径策略（契约 §5.5b，SEC-02）

**这条是我这一版最严重的缺口，评审的复现我逐条复核过。**

**问题形状**（调用点缺陷，不是算法缺陷）：

```
① 注册：roots/linkin -> roots/real     （realpath 在 roots 内 → checkPathAllowed 通过，注册成功）
② 漂移：root/linkin 被重指向 /tmp/out/lib.db（roots 外）
③ 下次懒打开（LRU 驱逐后**必然**发生）：
     statSync(id).isFile() === true     ← 我 §5.3 第 ① 步的守卫，通过
     realpathSync(id) === /tmp/out/...  ← 已在 roots 外
     checkPathAllowed(id) 会拒 —— 但**重开路径不调它**
   ⇒ openMemoryStore 把 roots 外的文件从 1 张表灌到 24 张
```

⚠️ **与已登记的 TOCTOU（契约 §11 U5）不是同一件事**：U5 是「`checkPathAllowed` 之后、`openMemoryStore` 之前」的**单次系统调用窗口**；本条是**整个「注册 → 重开」生命周期都缺守卫**，且**不需要赢任何竞态** —— 只要 LRU 驱逐过一次，下一次请求就自动走进这个洞。

**我的实现（§5.3 第 ② 步，贴在 `if (!reg.entry)` 之前）**：

```ts
if (!this.pinned.has(path) && !this.policyCheck(path)) {   // ⭐ pinned 豁免（§5.13.4）
  throw new DbUnavailableError("path-escalated", path, `记忆库路径已超出允许范围（…）：${path}`);
}
```

- ⭐ **放在「已打开 entry 命中」之前**（不是只在懒打开分支里）：这样即使 entry 还活着，也会在**每次 resolve** 时重验一次。
- **拒绝 → `DbUnavailableError("path-escalated")` → 409**（沿用 §4.6 的 `invalid_db`，**不新增码**），且 **MUST NOT 从注册表移除**（沿用 §3.2#5「不静默」）。用户能在 `/api/databases` 里看到这个库并得到人话原因。
- **错误的 reason 词表**从 `"missing" | "not-a-file"` 扩到 `+ "path-escalated"`（§5.1 已改）。D3 侧只需 `instanceof` + `reason` 映射到同一个 409 分支，**不需要新逻辑**。

#### 5.13.1 为什么选「重跑检查」而不是「注册时记 realpath 再比对」

契约允许二选一（§5.5b）。我选**重跑检查**，理由三条：

1. **`checkPathAllowed` 已经是权威**（4 万例 fuzz 零逃逸，契约 §5.5b 的评审结论）。记 realpath 是**我自造的第二套判据**，一旦它与 D2 的算法对「什么算越界」有分歧（symlink 链、相对片段、大小写），就出现「两套规则打架」。
2. **记 realpath 会在注册时刻固化一个可能过期的值**：若 realpath 变了但仍在 roots 内（合理迁移），记 realpath 的做法会**误拒**；重跑检查则正确放行。
3. **单点**：重跑检查只有一处代码，而「记 realpath」要在注册处存、打开处比，且要给 `RegisteredDb` 加字段（**会动契约 §3.2 的冻结形状**）。

⚠️ **代价（诚实登记）**：每次 `resolve` 多一次 `checkPathAllowed`（**同步**，含 `realpathSync`），给每个带 `?db=` 的请求加一点点同步时间。`[INFERENCE]` 微秒级；若将来实测有问题，退化方案是「只在 `entry === null` 的分支里跑」—— 那**仍然堵住 SEC-02 的洞**，只是少一层保险。

#### 5.13.2 与 D2 的接口（冻结）

```ts
// src/web/db-path-policy.ts（D2 提供，契约 §8.1）
export interface PathPolicy { roots: string[]; allowAnyPath: boolean; }
export function checkPathAllowed(
  policy: PathPolicy,
  candidate: string,
): { ok: true; path: string } | { ok: false; detail: string };
```

`registry.ts` 的 `policyCheck` 是它的**薄封装**：

```ts
private policyCheck(p: string): boolean {
  return checkPathAllowed(this.policy, p).ok;   // ⭐ 两参数（契约 §8.1 冻结签名）
}
```

⚠️ **`registry.ts` 只读 `.ok`，不用返回的 `.path`**：路径归一化仍由 `key()`（§5.10.1）负责，两个归一化概念 **MUST NOT 混用**（`checkPathAllowed` 的 `.path` 是「归一化后的允许路径」，`key()` 是「注册表 key」，契约 §4.2#1 要求 key = `path.resolve` 的结果）。

#### 5.13.3 ⭐⭐ `policy` MUST 是**必填**参数（fail-closed，评审 P0）

**第一版是 fail-open 的，且是同一个失败模式的第二次犯**：字段写成 `policy?: PathPolicy | null`，注释写「省略/`null` = 不检查」。后果：`grep -n "new StoreRegistry(" plan/memory-web/*.md` → **三个生产构造点（`11`/`13:830`/`13:850`）一个都没传 policy**，只有测试传了 ⇒ **C16/C17 会绿，生产里 R5 永远不生效**。判定与 D3 §4.5 为 `bindHost` 警告的是**同一个失败模式**：测试绿、生产死代码。

**裁定（契约 §5.2 末尾）**：

```ts
export interface StoreRegistryOptions {
  limit?: number;
  policy: PathPolicy;        // ⭐ 必填：去掉 `?` 与 `| null`
  onLog?: (line: string) => void;
}
```

- ⭐ **忘传 = 编译错误**（`tsgo` 的 `strict` 下缺必填属性直接报错）。这是「把纪律变成类型」的做法 —— 比任何注释或测试都可靠。
- ⭐ **删掉「省略 = 不检查」这条口径**。`--allow-any-path` **只能**由 `PathPolicy.allowAnyPath` 表达（D2 的 `checkPathAllowed` 内部分支）。若允许 `policy: null` 也等于「不检查」，就造出了**第二个 fail-open 真相源** —— 与 §5.10.1「归一化只有一个入口」是同一类教训。
- **`--allow-any-path` 时的写法**：`new StoreRegistry({ policy: { roots: [], allowAnyPath: true } })`（roots 内容被 `allowAnyPath` 短路，D2 决定其语义），**不是** `policy: null`。
- **三个生产构造点 MUST 补 `policy`**（`cli.ts` 一处、D3 的 `routes.ts` 两处）—— 见 §8.3 与验收 C20。
- **D5 的 C17 加对照**：不传 policy 的 registry，**构造即报错**（用 `// @ts-expect-error` 或运行时构造断言）。
- ⭐⭐ **`constructor(opts: StoreRegistryOptions)` —— `opts` 也 MUST 必填（去掉 `?`）**（D5 抓到的外层漏洞，主 agent 核实）。
  ```
  constructor(opts?: StoreRegistryOptions)   // ❌ 让 fail-closed 从外层绕回来
  new StoreRegistry()   // 编译期**不报**（opts? 合法）⇒ 运行时 opts === undefined
                        // ⇒ 读 .policy 抛 “Cannot read properties of undefined (reading 'policy')”
  ⇒ 「忘传 policy = 编译错误」这个保证是**假的**
  ```
  ⭐ 连带后果：这让 D5 的 `V6d`（`@ts-expect-error` + `new StoreRegistry({})`）**测不到它想测的东西** —— 该报错的形式是 `new StoreRegistry({})`（漏了**字段**），而真正危险的 `new StoreRegistry()`（**完全忘传容器**）反而不报。
  ⇒ **规则**：**必填字段的「必填」会被它的外层可选性抵消**；只要容器里有一个必填字段，容器本身 MUST 必填。（已写进 §12.0 的 D-2 自检清单。）

#### 5.13.4 ⭐⭐ `pinned` 豁免：R5 MUST NOT 误伤 roots 外的**进程库**（评审发现的回归）

**这是我落 R5 时引入的回归**（可行性评审发现，主 agent 实测复核；我确认成立）。

**回归的形状**：

```
--db /outside/process.db  --roots /inside        ← 契约 §5.4 与本文 §8.6 都明说此配置**合法**
R5（无豁免版）：checkPathAllowed(policy, "/outside/process.db") → { ok: false }
                ⇒ 抛 DbUnavailableError("path-escalated") → 409
但契约 §5.4 / 本文 §8.6 / C13 / D3 §13#12 都要求 `?db=<进程库>` MUST **200**
```

**可达性很高，不是边角**：D4 在**首屏**（`localStorage` 空）就把 `selectedDb` 设为**进程库路径**（非 `null`）⇒ `withDbParam` 给**每个**请求都附 `?db=<进程库>` ⇒ 带 `--db` 且在 roots 外的用户**一开页面全站 409**；而**不带 `?db=`** 的请求走缺省分支（契约 §3.3）仍 **200** —— **同一个库两种结果**。

⭐ **这正是契约 §5.2 末尾早已裁定过的形态**：那里说「把检查放进 `resolve` ⇒ 进程库报错…且 D4 对每个请求都附 `?db=` ⇒ 整个 UI 报错」，并明确「**`adopt` 路径豁免**」。**我的 R5 犯了同一个错**——我拿到的是更早一版的口径，没看到那条豁免裁定。

**修正（一行）**：

```ts
if (!this.pinned.has(path) && !this.policyCheck(path)) { throw … }
```

**立意不受损**：SEC-02 的攻击面**全部**来自 `register` 的库（roots 内 symlink 被重定向）；`pinned` 只可能有**进程库**（唯一调用点 = `cli.ts` 的 `adopt`，C19 已钉死）。

⭐ **为什么「豁免 pinned」不等于「给 R5 开后门」**：`pinned` 不是「用户可选的白名单」，而是「**所有权不在 registry 的连接**」这一结构性标记（§5.11）。它不可能被网页请求经 `?db=` 创造出来 —— 唯一的写入点是 `cli.ts` 启动路径。所以豁免它**不扩大任何攻击面**。

⚠️ **一条必须的对照（已加进 C13b）**：`--db` 在 roots 外时，`?db=<进程库>` MUST **200**。**C16 / C17 都不覆盖这个例子**（它们的库全在 roots 内或在 `allowAnyPath` 下）⇒ 这条回归靠那两条测试**测不出来**。

#### 5.13.5 ⭐ 通用判据（本条与 nlink 那条同型，写进 §12 纪律）

> **一个守卫新增时，MUST 逐一检查它是否覆盖了「已明文支持的特例」。**

本次评审门两处同型缺陷——`nlink`（误伤备份用户）与 R5（误伤 roots 外的进程库）——都是**新守卫忘了给它早已裁定的例外留豁免**；两处都表现为「合法配置下整个 UI 报错」，且**两处的测试都测不出来**。
⭐ 具体做法：新增 `if (!cond) reject` 之前，先 grep 一遍**本设计里所有类似的允许关系**（roots 根与外、`allowAnyPath`、进程库与 roots、`:memory:`），逐个问「这一条会不会命中它」。

### 5.14 R6 在本模块的落点（与 §4.2.1 呼应）

`registry.resolve` 的第 ① 步 `statSync().isFile()` **保留**（它给的是注册表语义的 `DbUnavailableError("not-a-file")`，不是打开错误）。它是**冗余的第二道**：

- `openInto` → `openMemoryStore` → `openDatabase`（可写，**不经** `openDatabaseReadonly`）⇒ **R6 的守卫不覆盖只读那条以外的路径**。⚠️ 所以 `resolve` 的守卫对**可写打开**仍是**唯一**的一道（FIFO 上 `new DatabaseSync(p)` 同样挂死 —— `[INFERENCE]`，因为它是同一个同步构造；本案在 `resolve` 已被 `isFile()` 拦下）。
- 只读那条（`readMemoryDbStats` / `probeMemoryDb`）已被 §4.2 的 R6 守卫覆盖，故它们的 `isFile()` 是**双保险**。
**结论**：三处守卫的**关系**必须写清（本段就是），否则后人删掉 `resolve` 的 `isFile()` 时会以为「R6 已经管了」——**R6 只管只读打开点**。

### 6.2 扫描：深度上限、跳过目录、符号链接

#### 6.2.1 定：`maxDepth = 6`（契约 §11 U2 的建议，本文给理由并确认）

实测（`~/projects/hackathon`、跳过 `.git`/`node_modules`）：

| depth | 耗时 | 访问目录数 | 找到库数 |
|---|---|---|---|
| 4 | 55ms | 1009 | 25 |
| **6** | **72ms** | **1824** | **33** |
| 8 | 70ms | 2045 | 33 |
| 10 | 64ms | 2050 | 33 |

- **depth 4 会漏库**（25 < 33）：`worlds/<world>/characters/<char>/.pi/memory.db` 需要 `worlds(1)/world(2)/characters(3)/char(4)/.pi(5)/memory.db(6)` —— 文件在第 5 层目录里，**depth 必须 ≥ 5 才够**，取 6 留一层余量（例如将来 `worlds/<world>/scenes/<x>/...`）。
  ⭐ **这是「取 6 而不是 4」的硬依据，不是感觉。**
- 6 → 8/10 的收益为 0（都是 33）：说明真实布局的深度 < 6，**上限取 6 不牺牲完整性**。
- 耗时 72ms 与 55ms 同级（目录数 1824 vs 1009，成本主要在 `readdir` 系统调用，线性于目录数）。

#### 6.2.2 定：跳过 `.git` / `node_modules`（+ 可注入追加）

- `.git/objects` 有几千个目录，扫它纯浪费（本机实测 `~/projects` 全扫 826ms、11205 目录；跳过后 `hackathon` 只 72ms、1824 目录）。
- `node_modules` 里不会有我们的 `memory.db`，但它可能被别的包塞进去（`[INFERENCE]`），跳过是**成本-收益**最优。
- **MUST NOT** 跳过 `.pi`（那是库的**必经**目录，`characters/<char>/.pi/memory.db`）。
- 跳过判据用**目录名全等**（`e.name === ".git"`），**MUST NOT** 用 `startsWith` / 大小写不敏感匹配（Linux 上 `Node_Modules` 是不同的目录，不是我们要跳的）。

#### 6.2.3 定：**不跟随符号链接**（本文的明确取舍，给出理由与代价）

实现上这是**自动的**，不需要额外判断：`readdirSync(dir, { withFileTypes: true })` 返回的 `Dirent` 的 `isDirectory()` / `isFile()` **不跟随**符号链接（实测：`lstatSync` 对符号链接给 `isSymbolicLink() === true`、`isFile() === false`；`statSync` 才给 `isFile() === true`）。

**选「不跟随」的理由（三条，按重要性）**：

1. **环**。符号链接可以成环（`a/link -> a`）。跟随它必须引入 visited-inode 集合（要额外 `stat` 每个目录 + 维护 Set）—— 这是一个**本地单用户工具**不值得的复杂度；不跟随时，遍历深度天然被 `maxDepth` 兜住，**不可能死循环**。
2. **越界**。一个 `link -> /` 会让扫描跑出 CLI 声明的 `--roots` 范围。虽然「发现」只是列路径（不打开、不读文件），但**越界列表本身就是信息泄漏**（契约 §5.5 把「列出路径」明确列为需要防范的信息泄漏）。
3. **库 id 的语义**。库 id 是「绝对路径」（契约 §4.2）。如果扫描给出 `/root/link/memory.db`，而用户打开它时 `path.resolve` 得到同一个字符串，**注册表会持有那个符号链接路径**，而 `server.ts`/launcher 的比对可能给出 realpath ⇒ 同一物理库两个 key ⇒ §5.10 第 3 条那个 `data_version` 损坏场景。

**代价（诚实登记）**：
- ⭐ 若用户的 world 是通过符号链接组织的（例如 `worlds/current -> worlds/2026-09`），发现会**看不到**那个库。**缓解**：手动输入兜底（M1 已定）；且 `/api/databases/open` 走 `checkPathAllowed` + `probeMemoryDb`，**它 `stat` 会跟随符号链接**（`fs.statSync` 跟随，实测）⇒ **手动输入一个符号链接路径是可用的**。这个「扫描不跟随、手动可跟随」的不对称是**有意的**（自动的必须保守，手动的必须听用户的）。
- 该不对称 MUST 写进 README（D5 的活），否则用户会困惑「为什么我链接过来的库不出现」。

#### 6.2.4 定：扫描失败如何上报

| 情形 | 处理 |
| root 路径不存在（`ENOENT`） | ⚠️ **不记 error**，静默跳过。理由：CLI 缺省 roots = `[process.cwd()]`，而很多目录下没有 `.pi/`；把「没有库」报成错误会在每次启动时制造噪声。 |
| root 不是目录（`ENOTDIR`）或 `--roots` 指向一个文件 | 静默跳过（同上）。`[INFERENCE]` 未来可考虑 CLI 启动时警告，但那是 CLI 的事（§8.5 登记）。 |
| **已存在**的目录 `readdir` 抛 `EACCES` / `EIO` / `ELOOP` | **记 error**（人话字符串，含 errno），**继续**扫其它分支。一个不可读的子目录 MUST NOT 让整次扫描失败。 |
| ⭐ **候选进 `paths` 前的硬要求（契约 §5.5c 第二条可达链）** | **MUST** 判 `Dirent.isFile()`（`withFileTypes: true` 下的 `e.isFile()`，**无需额外 `stat` 系统调用**）。⚠️ 若实现者改成「按文件名过滤」（`e.name === "memory.db"`，一个完全符合本文措辞的写法），**FIFO 就会进候选** → `readMemoryDbStats` 立刻**挂死整进程**（§4.2.1 实测 EXIT=124）。⇒ 这一条是**硬要求**，不是「性能优化顺便」。实测 `Dirent.isFile()` 对 FIFO 为 `false`。 |
| 库数超过硬上限 | 见 §6.3。 |

error 字符串的**形状**（D3 直接塞进 `discovery.errors`）：
```
`${dir}：${errno 名}${中文说明}`     例："/home/u/x/private：EACCES 无读取权限"
```
⭐ **MUST NOT 把 error 塞进 `paths`**（两者都是 `string[]`，类型上分得开，但语义上必须分开 —— `paths` 是「可注册的候选」）。

### 6.3 扫描上限（防御性，但必要）

`discoverMemoryDbs` 在 `paths.length` 达到 `MAX_DISCOVERED = 512` 时**停止遍历**（提前 return），并追加一条 error：
```
"发现结果已达上限 512 个记忆库，后续目录未遍历。请用 --roots 收窄范围。"
```

- 理由：`--allow-any-path` + `--roots /` 的组合下，一次扫描可能找到任意多的 `memory.db`；`/api/databases` 的响应体没有分页（契约 §4.3 冻结形状没有 `total`/`offset`），所以上限必须在**生产端**。512 的取值：真机 41 个，两个数量级余量。

### 6.4 性能：为什么必须缓存（以及缓存什么）

实测（本机）：

| 操作 | 成本 |
|---|---|
| 扫描 `~/projects/hackathon` depth≤6 | **72–80ms**（1824 目录） |
| 扫描 `~/projects` depth≤6 | **826ms**（11205 目录） |
| 对 33 个库各做一次只读连接 + 读 `schema_version` + `COUNT(*)` | **32ms**（≈1ms/库） |
| D3 实测（26 库） | 20.9ms（≈0.8ms/库） |
| 一次正常 API 请求（同一进程内查询） | `[INFERENCE]` 亚毫秒 |

**结论**：一次 `/api/databases` 若每次全量重扫 + 全量重探，在 `--roots ~/projects` 下是 **~860ms** —— 比任何其它端点慢 3 个数量级，而它会被前端在**每次切库、每次重载**时调用（契约 §6.4 要求切库后重载侧栏，D4 很可能顺带重拉列表）。**必须缓存。**

**两层缓存（都在 `discovery.ts` 的模块作用域，不在 registry）**：

```ts
interface CacheEntry<T> { value: T; at: number }
let scanCache: (CacheEntry<DiscoveryResult> & { key: string }) | null = null;
const statsCache = new Map<string, CacheEntry<MemoryDbStats | null>>();
const DEFAULT_TTL_MS = 5000;
```

| 缓存 | key | TTL | 失效 |
|---|---|---|---|
| 扫描结果 | `roots.join("\u0000")`（+ `maxDepth` + `skip` 的指纹） | 5s | TTL 到期；roots 变了自然 miss |
| 单库统计 | 绝对路径 | 5s | TTL 到期；**且** `invalidateStats(path)` 被显式调用 |

⭐ **不做「永久缓存 + 文件监听」的理由**：`fs.watch` 在 Linux 上对**深层目录树**不可靠（inotify 上限、`recursive` 在旧内核不支持），而且我们真正需要的是「用户新建了一个库之后能看到它」—— 5s TTL 足够（人手速 ~1s，5s 的陈旧窗口可以接受），而且**零 API 复杂度**。若 5s 太钝，用户在址栏刷新一下即可（`[INFERENCE]` 未与用户确认；登记为 T6）。

⭐ **为什么 5s 而不是 30s**：TTL 的代价是「新建/删除的库最多 5s 才反映出来」，收益是「连点 10 次刷新只扫一次」。**5s 是在「人手速」与「连点」之间的折中**，且远大于一次扫描（72ms）× 前端轮询间隔。

⚠️ **`readMemoryDbStats` 的缓存必须与 `registry` 打开事件协作**：库被**打开**（`registry.resolve` 成功）后，它即将被**写入** ⇒ 缓存的 `node_count` 会立刻变旧。所以：
- `registry.ts` 在 `openInto` 成功后 MUST 调 `invalidateStats(path)`（⭐ **这是 `registry.ts` → `discovery.ts` 的唯一 import 方向**，不构成循环：`discovery.ts` 不 import `registry.ts`）。
- `discovery.ts` MUST NOT import `registry.ts`（保持单向依赖）。

`[INFERENCE]` 反向（registry import discovery）是否会让 D2 的 `db-path-policy.ts` 也 import discovery 而产生更大的依赖网？不会：`db-path-policy.ts` 只 import `probeMemoryDb`（一个叶子函数），没有反向边。

#### 6.4.1 本文两处缓存**不是**「读 A 写 B」缺陷（契约 §7.6 自查，已记录在案）

契约 §7.6 的通用判据：**值来自某个库的查询结果、键里却没有库标识 ⇒ 该缓存切库后会读 A 写 B**（已核实违规：`tree.js:15` 的 `treeCache`，键 = `domain|parentUri`，不含库标识）。

| 本文的缓存 | 值 | 键 | 判定 |
|---|---|---|---|
| `statsCache` | 单个库的统计（`nodeCount`/`worldTime`）——**值确实是库内数据** | **绝对路径 = 库 id 本身**（契约 §4.2） | ✅ 键已含身份 ⇒ 切库不会串 |
| `scanCache` | **一组路径**（`DiscoveryResult.paths` + `scanned` + `errors`）——**不是任何库的查询结果** | roots 指纹 | ✅ 值与库状态无关 ⇒ 陈旧也只会「列表里少/多一个路径」，不会把 A 库的数值显示在 B 库上 |

⭐ 与 `treeCache` 的**本质区别**：`treeCache` 存的是**库内数据**（某个 `domain` 的子树），键却只有 `domain|parentUri` ⇒ 必须补库身份（契约 §7.6 裁定由 D2 在 `tree.js` 入口比对）。本文两处：一个键即身份，一个值与库无关 —— **两者都不需要改**。这是契约 §7.6 已收录的 D1 自查结论。

⚠️ **但这不豁免未来的新增缓存**：若将来有人在 `discovery.ts` 里加「某库的节点摘要」之类缓存且用 domain 作键，就立刻落进 §7.6 的违规形状。⇒ 写进验收：C14（§12）。

### 6.5 `readMemoryDbStats` 的实现要点

```ts
export async function readMemoryDbStats(candidate: string): Promise<MemoryDbStats | null> {
  const now = Date.now();
  const hit = statsCache.get(candidate);
  if (hit && now - hit.at < ttl) return hit.value;

  let db: MemoryDatabase | null = null;
  let value: MemoryDbStats | null = null;
  try {
    db = await openDatabaseReadonly(candidate);                     // 可能抛 ReadonlyOpenError
    const version = db.prepare("SELECT value FROM memory_kv WHERE key = ?").get("schema_version");
    const nodeRow = db.prepare("SELECT COUNT(*) AS c FROM nodes").get();
    const timeRow = db.prepare("SELECT value FROM memory_kv WHERE key = ?").get("world_time");
    value = {
      schemaVersion: String((version as { value: string }).value),
      nodeCount: Number((nodeRow as { c: number }).c ?? 0),
      worldTime: timeRow ? String((timeRow as { value: string }).value) : null,
    };
  } catch {
    value = null;          // 不可达 / 不是记忆库 —— 探测语义由 probeMemoryDb 负责，这里只给 null
  } finally {
    // ⭐ MUST：契约 §4.4 "探测函数 MUST 自己 close()，不得泄漏连接"。
    //    注意 close() 会抛（实测 ERR_INVALID_STATE 只在重复 close 时），这里再包一层。
    try { db?.close(); } catch { /* 已关闭：忽略 */ }
  }
  statsCache.set(candidate, { value, at: now });
  return value;
}
```

⚠️ **`COUNT(*) FROM nodes` 在「不是记忆库」时会抛 `no such table: nodes`**（实测 `no such table` 的 message 形状），被 catch 成 `null` → 与 `not-memory-db` 同结果。这是**可接受的**：`readMemoryDbStats` 的契约是「给不出统计就 null」，判定语义由 `probeMemoryDb` 承担。
⭐ **但也意味着 `/api/databases` 对不可达库给 `node_count: null` 而 reason 由 `reachable`/`error` 字段表达**（契约 §4.3 已冻结此形状：`node_count` 不可达时为 `null`）。
⚠️ **world_time 读法**：契约 §6.7 说它存 `memory_kv` 的 `world_time` 键（`store.ts:154` `const WORLD_TIME_KEY = "world_time";`，读路径 `store.ts:1112`）。用**直接 SQL** 读而不是 `store.getWorldTime()`，因为这里只有只读连接、没有 `MemoryStore`（构造 `MemoryStore` 会 `prepare` 三条语句，虽无害但没必要）。
  `[INFERENCE]` `/api/databases` 的 `world_time` 形状（契约 §4.3 例给 `"2020-09-28"`）是**日期**而非 `getWorldTime()` 的原样返回。**这是 D3 的字段映射责任**，我只给原始值。已 IRC 提醒。

## 7. `probeMemoryDb`（`src/web/discovery.ts` 新增）

### 7.1 签名与冻结（契约 §8.1，逐字）

```ts
export type ProbeOutcome =
  | { ok: true; schemaVersion: string }
  | { ok: false; reason: "missing" | "not-a-file" | "not-memory-db" | "incompatible" | "unreadable"; detail: string };
export function probeMemoryDb(candidate: string): Promise<ProbeOutcome>;
```

**为什么是 `async`（返回 `Promise`）**：它 MUST 用 `openDatabaseReadonly`，而那是 `async`（`node:sqlite` 是动态 `import`，`driver.ts:24`）。`[INFERENCE]` 不能改成同步：那会失去 `driver.ts:26` 那条「Node 版本不够」的诊断。

**为什么输入是 `candidate: string` 而不是归一化后的路径**：契约 §5.2 的判据顺序把「归一化」（#1）排在「探测」（#4）**之前**，由调用方（`/api/databases/open` 的 handler，走 `checkPathAllowed`）负责。`probeMemoryDb` **不做** `path.resolve`（它只探「这个字符串指向的东西是不是记忆库」），但**也不拒绝**相对路径 —— `[INFERENCE]` 调用方总会传绝对路径；若传相对路径，`statSync`/`DatabaseSync` 按 cwd 解析，结果与调用方预期一致（`statSync(相对)` 和 `DatabaseSync(相对)` 用同一个 cwd）。这点 MUST 在函数注释里写明。

### 7.2 五种 reason 的判定路径（**MUST NOT 建表、MUST NOT 改文件**）

```ts
export async function probeMemoryDb(candidate: string): Promise<ProbeOutcome> {
  // ── ① 前置存在性/类型检查：把 SQLite 那句含糊的 "unable to open database file" 拆开 ──
  let st: Stats;
  try {
    st = statSync(candidate);                       // ⭐ 同步；跟随符号链接（§6.2.3）
  } catch (error) {
    const code = (error as NodeJS.ErrnoException).code;
    if (code === "ENOENT" || code === "ENOTDIR") {
      return { ok: false, reason: "missing", detail: `路径不存在：${candidate}` };
    }
    return { ok: false, reason: "unreadable", detail: `无法访问 ${candidate}：${code ?? String(error)}` };
  }
  if (!st.isFile()) {
    return { ok: false, reason: "not-a-file", detail: `不是普通文件（目录/管道/设备）：${candidate}` };
  }

  // ── ② 只读打开（唯一副作用：WAL 库会留下 -wal/-shm，见 §2.2） ─────────
  let db: MemoryDatabase;
  try {
    db = await openDatabaseReadonly(candidate);
  } catch (error) {
    // ReadonlyOpenError 带 reason（§4.3），直接映射
    if (error instanceof ReadonlyOpenError) {
      return { ok: false, reason: error.reason, detail: error.message };
    }
    return { ok: false, reason: "unreadable", detail: (error as Error).message };
  }

  try {
    // ── ③ 读 schema_version：NOT 复用 readSchemaVersion（它 catch 掉一切） ──
    let row: { value: string } | undefined;
    try {
      row = db.prepare("SELECT value FROM memory_kv WHERE key = ?").get("schema_version") as
        | { value: string }
        | undefined;
    } catch (error) {
      // "no such table: memory_kv" / "file is not a database" / "no such column: value"
      const message = (error as Error).message;
      return {
        ok: false,
        reason: "not-memory-db",
        detail: `不是记忆库（读 memory_kv.schema_version 失败）：${message}`,
      };
    }
    if (!row || typeof row.value !== "string") {
      // ⭐ 表在但行不在：不是我们认识的库。不同于"陌生 SQLite 文件"，
      //    但同样 MUST NOT 注册，否则 createSchema 会给它灌表（index.ts:125）。
      return {
        ok: false,
        reason: "not-memory-db",
        detail: `不是记忆库（memory_kv 里没有 schema_version 行）：${candidate}`,
      };
    }
    // ── ④ 版本比对：与 schema.ts:133 同一判据（stored !== SCHEMA_VERSION） ──
    if (row.value !== SCHEMA_VERSION) {
      return {
        ok: false,
        reason: "incompatible",
        detail: `记忆库 schema v${row.value} 与本版本 v${SCHEMA_VERSION} 不兼容（无就地迁移）。`,
      };
    }
    return { ok: true, schemaVersion: row.value };
  } finally {
    // ⭐ 契约 §4.4：探测函数 MUST 自己 close()。异常路径也走这里。
    try { db.close(); } catch { /* 重复 close 抛 ERR_INVALID_STATE（实测）；忽略 */ }
  }
}
```

**逐 reason 的判定表（可机械核验）**：

| reason | 触发条件 | 实测的底层事实 | 是否注册 |
|---|---|---|---|
| `missing` | `statSync` 抛 `ENOENT` / `ENOTDIR` | 不存在文件：SQLite 只给 `unable to open database file`（errcode 14），**且不创建文件** | ❌ |
| `not-a-file` | `stat.isFile() === false` | 目录：SQLite 给 `disk I/O error`（errcode 266）—— 与 missing 不同句，但**同样不可依赖**（EACCES 会伪装成 missing 那句） | ❌ |
| `not-memory-db` | 读 `memory_kv.schema_version` 抛，或行不存在 | 普通 SQLite 库：`no such table: memory_kv`（errno 1）；文本文件：open **成功**、`prepare` 抛 `file is not a database`（errno 26） | ❌ |
| `incompatible` | 行存在但 `value !== SCHEMA_VERSION` | `schema.ts:133` 的既有判据，逐字对齐 | ❌ |
| `unreadable` | 前两类都不匹配的 `stat`/open 失败（`EACCES`/`EIO`） | `chmod 000` → `unable to open database file` ⚠️ **与 missing 同句** ⇒ 必须靠第 ① 步的 `stat` 区分 | ❌ |

⭐ **`unreadable` 是兜底而非主要路径**：若没有第 ① 步的 `statSync`，`EACCES` 会掉进 `unreadable`（正确）但 `missing` 也会 —— 那样「文件不见了」（契约 §3.2#5 要求用户可见）就会退化成人话说不清的 `unreadable`。

### 7.3 ⭐ MUST NOT 建表 / MUST NOT 改文件的**机械证据**

三层保证，缺一不可：

1. **只用 `openDatabaseReadonly`**：它传 `{ readOnly: true }`（§4.2）。实测在该连接上 `CREATE TABLE` / `INSERT` **抛 `attempt to write a readonly database`** —— 即使将来有人误在探测里加一句建表，也会立刻炸而不是静默污染。
2. **不调 `createSchema` / `openMemoryStore`**：探测路径**没有**任何指向 `index.ts`/`schema.ts` 写函数的 import。验收清单里的 `grep` 断言（§12 C6）就是钉死这一点。
3. **不 `realpath` 后再打开**（§5.10）：避免「探测了 A、打开了 B 的 realpath」这种绕道。

**判据（契约 §9 V2，D5 实现）**：对任意普通 SQLite 文件 `P`，`probeMemoryDb(P)` 前后
- `md5(P)` 不变（实测：真实 memory 库探测前后 md5 逐字节相同）
- 表集合不变（`SELECT name FROM sqlite_master WHERE type='table'` 排序后相同）

⚠️ **MUST NOT 断言「文件列表不变」**（契约 §2.4b 更正 + 我的复核）：WAL 库探测后**会**留下 `-wal`/`-shm`。

### 7.4 探测的成本（实测）

单库一次 `probeMemoryDb` ≈ **0.8–1ms**（我测 33 库 32ms；D3 测 26 库 20.9ms）。
- **不在探测里做 `COUNT(*)`**：探测只读 `schema_version`（1 次 `prepare` + 1 次 `get`）。统计走 `readMemoryDbStats`（§6.5），它有缓存。
- ⚠️ 这意味 `/api/databases/open` 一次请求最多 **~1ms** 的探测成本，可忽略。

### 7.5 探测的错误文案（人话，给用户看）

`detail` MUST 是人话（D3 直接进 `error` 字段或响应 message）。**MUST NOT** 把 SQLite 的英文原句当成 `detail` 的唯一内容 —— 但**可以**附加它（我的实现是把原文缀在中文后面，见 §7.2 的模板）。理由：`routes.ts:107-111` 的既有立场是「原始 SQLite 文本不进响应体」（`mapStoreError` 会换成中文）；但**探测发生在 handler 之前**，是 HTTP 400 的「请求参数不合法」路径，D3 会自己决定展示哪一段。我的职责是**给出两者**：中文 + 原文。

| `路径逃逸舱已开启（--allow-any-path）` | `opts.allowAnyPath === true` | 契约 §5.4：MUST 打**醒目**警告。 |

⭐ **`--allow-any-path` 的警告样式**：沿用 `server.ts:53-59` 的反显（`\u001b[7m…\u001b[0m`），文案：
```ts
/*** --allow-any-path 的可见警告：沿用 warnIfNonLoopback 的风格（server.ts:53-59）。 */
export function warnIfAllowAnyPath(allow: boolean): string | null {
  if (!allow) return null;
  return (
    "\u001b[7m⚠️  警告：已开启 --allow-any-path —— 本服务可以打开本机任意路径下的记忆库。\u001b[0m\n" +
    "    只在完全信任本机浏览器环境时这样做；否则请用 --roots 限定范围。"
  );
}
```
放在 `cli.ts` 而不是 `server.ts`：它不是绑定层的属性，而是 CLI 选项；且 `server.ts` 的 `warnIfNonLoopback` 已有测试锚点（`security.test.ts` 的 `boot()`），我不想动它。
⚠️ **打的位置（去掉前面那句自相矛盾的"或…也行"）**：定**在 `startServer` 之前**，紧接在 `openMemoryStore` 成功之后。理由：(1)「多库禁用」（非回环）需要**提前**告知，而 `startServer` 内的 `warnIfNonLoopback` 在监听成功后才打（`server.ts:108-109`）——两者相邻会让「多库为何没开」的答案跑到后面；(2) warning 越早出现越不容易被后续输出淹没。⇒ **顺序：`多库: …` → `--allow-any-path` 警告 → `startServer`（含它自己的非回环警告）**。

### 8.5 `USAGE` 增量（`cli.ts:19-29`）

```diff
   --temp-threshold <n>     TEMP 动态区阈值（默认 10，仅影响展示）
+  --roots <dir>            发现记忆库的根目录（可重复；默认当前目录）
+                          仅回环绑定下生效；缺省不含 $HOME 或 /
+  --allow-any-path         允许打开任意绝对路径的记忆库（危险，跳过 roots 检查）
   --help, -h               显示本帮助
```

⚠️ **`--roots` 的「可重复」MUST 在帮助里写出来** —— 否则用户会以为后一个覆盖前一个。

### 8.6 ⚠️ `--roots` 与 `--db` 的关系（契约 §5.4 已冻结，此处只复述判据）

- **进程库不受 roots 约束**（用户显式指定，可信）。⇒ `cli.ts` 的 `adopt` **MUST NOT** 调 `checkPathAllowed`。
- 若用户 `--db /outside/roots/x.db` + `--roots /inside`，则：进程库可用；`?db=<那个进程库路径>` 也 MUST 可用（它已注册）；**发现扫描**看不到它（不在 roots 内）；前端选不到它（除非手动输入，而那会被 `checkPathAllowed` 拒）。
  ⭐ **这是自洽的**，但值得在 README 里说一句（D5 的活）。**已登记为 T5。**
`[INFERENCE]` 是否该把 `dbPath` 自动并入 `roots` 以便被发现？**答案：不。** 理由：`/api/databases` 的 `databases` 是「注册库 ∪ 发现库」，进程库**已在注册库里**（`adopt`）⇒ 它一定会出现在列表中，无需进 roots。而进 roots 的副作用是「它的兄弟目录也被扫」，那会扩大范围（与 §5.4 的意图相悖）。

## 9. 失败分析（≥5 条：这个设计会在什么情况下出错，以及我如何防住）

每条格式：**场景 → 后果 → 我防在哪（可核验的代码位置或断言）→ 残余风险**。

### F1 ⭐ 选错路径 ⇒ 污染用户的文件（本功能最严重的风险）

- **场景**：用户在 `/api/databases/open` 里手输 `/home/u/notes.db`（笔记/别的应用的 SQLite 文件）。若它进了注册表，`resolve` 会调 `openMemoryStore` ⇒ `createSchema` 给它灌 22 张 `memory_*` 表（契约 §2.3，实测）。
- **后果**：**用户的文件被改**。数据未丢，但表被污染；若那个应用对自己的 schema 敏感，可能损坏。
- **防在哪**：
  1. `probeMemoryDb` 是注册的**唯一闸门**（契约 §5.2#1）。它对 `/home/u/notes.db` 读 `memory_kv.schema_version` → `no such table: memory_kv` → `not-memory-db` → **不注册**。
  2. `openDatabaseReadonly` 的 `{readOnly:true}` 使「即使探测代码写错想建表」也会 `attempt to write a readonly database`（实测）——**第二道锁**。
  3. 验收断言 C1/C2（§12）：对普通 SQLite 文件调 `probeMemoryDb`，前后 `md5` 与表集合不变。
- **残余风险**：用户**先**把文件改成合法记忆库布局再打开 —— 那是他的意图，不是我们的错。
- ⚠️ 另有一条**实测发现**的旁路：`resolve` 的懒打开用 `openMemoryStore`，它对**路径不存在且父目录存在**的情况会**静默造出一个空记忆库**（实测：`openMemoryStore('/tmp/existingdir/nope.db')` 成功、文件出现、`nodes = 0`、4096 字节）。**已注册的库被外部删除**正是这个形状 ⇒ 必须由 §5.3 第 ① 步的 `statSync` 拦掉（`missing` → `DbUnavailableError`）。**这是本条最容易被漏的一处，也是我把 `stat` 放进 `resolve` 的主因。**

### F2 未注册的 `?db=` ⇒ 任意文件读取（CSRF / DNS rebinding 面）

- **场景**：用户打开了一个恶意页面，页面对 `http://127.0.0.1:8788/api/node?uri=…&db=/etc/passwd` 发请求。
- **后果**：若 `?db=` 被直接当路径 `openMemoryStore`，攻击者就得到「对任意文件建表/读取」的能力。
- **防在哪**：`resolve` 对未注册路径**返回 `null`**（`dbs.get` miss）→ 404。**`resolve` 内部没有任何 `register`**（§5.3）。唯一注册入口是 `/api/databases/open`（带探测 + D2 的 roots 检查）。
- **残余风险**：若 D3 在 handler 里「顺手注册」（契约 §4.2#3 明文禁止），本防御失效。⇒ 验收断言 C4 用 `grep` 钉死。

### F3 并发懒打开 ⇒ 同库两个连接 ⇒ `data_version` 语义损坏

- **场景**：前端切库后连发 `/api/meta?db=X` 与 `/api/tree?db=X`（或用户连点两次），两个请求同时 miss `entry`。
- **后果**：两个 `MemoryStore`、两个 `ChangeDetector`、两个 `data_version` 计数器 ⇒ `/api/events` 的 `changed` 恒 false（契约 §2.2 点名的失效模式）。
- **防在哪**：§5.3 第 ② 步的 `inflight` Map 去重。断言 C7：`Promise.all([resolve(X), resolve(X)])` 两个结果 `toBe` 同一对象。
- **残余风险**：若有人把 `openInto` 的调用从 `resolve` 里搬出去（绕过去重），立刻回到本状态。⇒ 验收钉死「唯一打开点」：`grep -c "openMemoryStore" src/web/registry.ts` == 1。

### F4 驱逐误关「在用连接」或「进程库」⇒ 500

- **场景**：见 §5.5（进程库）与 §5.6（在途请求）。
- **后果**：`database is not open` → `mapStoreError` 的 `routes.ts:138` → **500**；进程库那条还会连带让 `/memories web` 的 launcher 误判 `occupied` 并另起端口（§5.5 第 2 点）。
- **防在哪**：(a) `pinned` + `closeEntry` 的 pinned 短路；(b) `inFlight` 引用计数 + `resolve` 抬 / `release` 放；(c) 两个机制都没能腾出位置时**允许超出上限并打日志**（§5.5）—— 宁可多开 fd，不可关掉在用的。
- **残余风险**：若 D3 忘记 `finally release`，`inFlight` 只增不减 ⇒ 库**永不**被驱逐 ⇒ fd 缓慢泄漏。这是**退化而非错误**。⇒ 断言 C8 用「resolve 后不 release」的对照把 D3 的遗漏变成可观测现象。

### F5 `probeMemoryDb` 泄漏连接 ⇒ fd 耗尽

- **场景**：`/api/databases/open` 被反复调用（或探测的 `try/finally` 写错），每次泄漏一个只读连接。
- **后果**：进程 fd 逐次增长；到 ulimit 后所有请求开始失败。
- **防在哪**：§7.2 的 `finally { try { db.close(); } catch {} }` 覆盖 `ok` / `not-memory-db` / `incompatible` **三条**返回路径（`missing` / `not-a-file` 在打开之前返回，无需 close）。断言 C5。
- **残余风险**：`[INFERENCE]` 若 `DatabaseSync.close()` 不释放底层 fd（无证据，未观察到），本防御无效 —— 那是 Node 的契约，我不重复实现。

### F6 扫描遇到不可读目录 ⇒ 整次发现失败或死循环

- **场景**：roots 下有一个 `0700` 的别人目录、一个自指的符号链接，或一个巨大的目录树。
- **后果**：`/api/databases` 500（异常外溢），或扫描挂住。
- **防在哪**：§6.2.4 每个 `readdirSync` 各自 `try/catch` → 记 error 继续；§6.2.3 不跟随符号链接 ⇒ 结构上不可能成环；§6.3 的 `MAX_DISCOVERED = 512` 硬上限。断言 C9 / C10。
- **残余风险**：一个 depth ≤ 6 但每层几万目录的树会让一次扫描到秒级 —— 由 5s 缓存摊薄，且只影响 `/api/databases` 这一个端点。

### F7 `-wal` / `-shm` 被当成「污染」而误判（对我们自己的库）

- **场景**：D5/Main 写 V2 断言时用 `readdir` 比较探测前后的文件列表。
- **后果**：**对这个功能自己的库**（真实 memory 库是 WAL，实测）断言变红 ⇒ 要么误改断言、要么误删「污染」。
- **防在哪**：契约 §2.4b 已更正；本文 §7.3 明确「断言用 md5 + 表集合，MUST NOT 用文件列表」。断言 C2 照此写。
- **残余风险**：无（文档纪律问题，已钉死）。

### F8 `--roots` 看起来生效但其实没有（相对路径 / 空树）

- **场景**：用户 `--roots ./worlds`（相对路径）而 cwd 不是他想的地方；或 root 存在但整棵树下无 `memory.db`。
- **后果**：空列表，用户以为功能坏了。
- **防在哪**：(a) `parseCliArgs` 立即 `path.resolve`（§8.2）⇒ 日志里打绝对路径，一眼看出解析到哪；(b) §8.4 启动日志把 roots 打出来。
- **残余风险**：用户不看日志 ⇒ 前端空列表。**登记为 T4**（是否该在「扫描成功但 0 结果」时给前端提示，属 D3/D4）。

### F9 库 id 在「符号链接 / 硬链接 / bind mount」下分裂

- **场景**：`/a/link.db -> /b/real.db`。用户一次用 `/a/link.db`（手动输入），一次用 `/b/real.db`（发现）。
- **后果**：两个 key ⇒ 同一物理库两个连接 ⇒ `data_version` 分裂（同 F3）。
- **防在哪**：**部分防住，部分不防**：
  - 发现扫描**不跟随**符号链接 ⇒ 不会主动产出两个 key（§6.2.3）。
  - 手动输入一个符号链接路径**可用**（`statSync` 跟随）⇒ 用户可能造出第二份。**设计上接受**（M5 单用户本地工具；硬链接 / bind mount 在 `path.resolve` 层面无解）。
  - `[INFERENCE]` 若要彻底防需 realpath 作 key —— 但那会破坏 §5.10 第 3 条的 launcher 兼容。**有意的取舍，登记为 T2。**
- **残余风险**：用户自造的分裂。**可观测**：`/api/databases` 会列出两条不同 `path` 的记录（同 `node_count`），用户能看出来。

### F10 库文件在「打开后」被外部替换（换 inode，不是删除）

- **场景**：`pi` 在别处重建了库（删 + 建，或 `import` 写新文件后 `rename` 覆盖）。
- **后果**：我们的连接仍指向**已 unlink 的旧 inode**，读到旧快照；路径上已是一个新文件。`stat` 检查**防不住**（路径存在且是普通文件）。
- **防在哪**：**不防**。这是「连接语义」的固有边界；「谁打开谁关闭」意味着我们不监听替换。
- **残余风险**：用户看到陈旧数据。**缓解（不是修复）**：重开该库 —— 但 `/api/databases/open` 幂等，已打开的 entry 会被直接返回 ⇒ **其实也不刷新**。`[INFERENCE]` 真修复是「打开前比对 mtime/inode 并重开」，代价是每请求一次 stat + 可能的原子重开，且与 LRU 交互复杂。**登记为 T3。**

### F11 ⭐⭐ 注册后符号链接被重指向 ⇒ 懒打开把 roots 外的文件灌表（SEC-02 / R5）

- **场景**：① `roots/linkin -> roots/real` 注册成功（realpath 在 roots 内）；② 攻击/漂移把它重指向 `roots` 外的普通 SQLite 文件；③ 该 entry 被 LRU 驱逐后的下一次请求**自动**懒打开它。我的 §5.3 第 ① 步只查 `statSync(id).isFile()` ⇒ **通过**；而 `checkPathAllowed` 只在**注册**时跑过一次 ⇒ **roots 外的文件被 `createSchema` 从 1 张表灌到 24 张**。
- **后果**：**污染 roots 外的任意普通 SQLite 文件**（本功能最严重的危害类别，同 F1）。
- **为什么我第一版漏掉**：我把「路径策略」当成**注册时的一次性准入**，而没意识到**注册与打开在时间上分离** —— 懒打开是一条**独立的**、可能晚几天才走到的路径。
- **防在哪**：§5.13 的 R5 —— `resolve` 在**每次**调用（不限懒打开分支）里重跑 `checkPathAllowed(policy, path)`，拒绝 → `DbUnavailableError("path-escalated")` → 409 且不从注册表移除。验收 **C16**（重定向 symlink 后断言被拒 + 受害文件 md5/表集合不变）+ **C17**（注入假 policy 证明接线存在）。
- **残余风险**：⚠️ R5 与 `openMemoryStore` 之间仍有**一个** TOCTOU 单次窗口（`checkPathAllowed` 通过后、`openMemoryStore` 打开前，symlink 被再次重指向）—— 那是契约 §11 U5，**本设计的已知边界**，不宣称已解决（同步 API 下无法完全消除；见 §10.11）。

### F12 ⭐⭐ FIFO 让整进程挂死（SEC-04 / R6）

- **场景**：已注册库被 LRU 驱逐（上限 8 下**必然**）→ `/api/databases` 对未打开库调 `readMemoryDbStats` → 该路径上的文件已变成 **FIFO**。我的 `readMemoryDbStats`（§6.5）**没有** `isFile()` 守卫，直接 `openDatabaseReadonly`。
- **后果**：`new DatabaseSync(p, {readOnly:true})` 在 FIFO 上**永久阻塞**（同步 API 占住事件循环）⇒ **整个 web 进程挂死**，所有请求不再响应。实测：`timeout 5 node -e "new DatabaseSync('/tmp/fifo-test.db',{readOnly:true})"` → **EXIT=124**。
- **防在哪**：§4.2 的 R6 —— 守卫**下沉到唯一的只读打开点** `openDatabaseReadonly` 内部，**MUST NOT 依赖调用方**。验收 **C18**（FIFO 上三个入口都必须快速返回，且用 `timeout` 包裹测试）。
- **残余风险**：⚠️ **`resolve` 走的是可写路径**（`openMemoryStore` → `openDatabase`），R6 **不覆盖它**——`resolve` 的 `statSync().isFile()` 对 FIFO 仍是**唯一**一道（§5.14 已写清这个关系）。
- **教训（通用）**：约定「调用方记得检查」在三个调用点就漏一个。**守卫必须下沉到唯一的打开点。**

### F13 ⭐ `adopt` 进来的连接永不回收（SEC-06）

- **场景**：`/api/databases/create` 新建库后，若把新连接也 `adopt` 进来（而不是 `register`）。`adopt` 无条件 pin（§5.5）+ `closeEntry` 对 pinned 只解引用不 close（§5.8）。
- **后果**：该连接**永不驱逐、永不关闭** —— 永久 fd + 永久 store，保留到进程退出。反复 create 就线性泄漏。
- **防在哪**：§5.8 的 SEC-06 注释把 `adopt` 的语义收紧为「**仅**用于不由 registry 打开的连接」，唯一合法调用点是 `cli.ts` 的进程库。验收 **C19**（`grep .adopt(` 只出现在 `cli.ts`；`routes.ts` 零处）。
- **残余风险**：`[INFERENCE]` 若将来有第二个「外部已打开的连接」需求（例如未来某个复用入口），需要重新审视这条规则 —— 但那时应当**显式**给 `adopt` 加 `{ pinned: false }` 之类的参数，而不是默默放宽。

### F14 ⭐⭐ R5 误伤 roots 外的进程库（**我自己引入的回归**，§5.13.4）

- **场景**：`--db /outside/process.db --roots /inside`（契约 §5.4 与本文 §8.6 都明说**合法**）。我的 R5 第一版写 `if (!this.policyCheck(path)) throw` —— **没有 `pinned` 豁免** ⇒ `checkPathAllowed` 对 `/outside/process.db` 返回 `{ok: false}` ⇒ **抛 `path-escalated` → 409**。
- **后果（可达性高）**：D4 在**首屏**把 `selectedDb` 设为进程库路径（非 `null`）⇒ `withDbParam` 给**每个**请求附 `?db=<进程库>` ⇒ 该配置下**一开页面全站 409**；而**不带 `?db=`** 仍 200（走缺省分支）—— **同一个库两种结果**。
- **为什么是回归而不是设计缺陷**：**修 R5 之前没有这个问题**（那时根本没有路径策略检查）。新增守卫时我只想「堵住越界」，**没有回头检查「已明文支持的特例」**（此处：进程库不受 roots 约束）。
- **防在哪**：守卫加 `!this.pinned.has(path) &&`（§5.13.4）。验收 **C13b** —— 它是**唯一**能抓住这条的断言（C16/C17 的库全在 roots 内或 `allowAnyPath` 下 ⇒ 测不出来）。
- **残余风险**：无（`pinned` 的唯一写入点是 `cli.ts` 的 `adopt`，C19 钉死 ⇒ 它不可能被网页请求创造出来，豁免它不扩大攻击面）。
- ⭐ **教训（与 D2 的 `nlink` 误伤备份用户同型，已写进 §5.13.5 与 §12）**：**一个守卫新增时，MUST 逐一检查它是否覆盖了「已明文支持的特例」。**

## 10. 边界与已知行为（诚实登记，不是缺陷）

### 10.1 「注册」与「打开」是两个时刻

`/api/databases` 的 `registered: true` 表示「这个路径被接受过（探测通过）」，**不**表示连接活着。契约 §4.3 的 `registered` 语义就是这个（D3 的字段）。用户可能在列表里看到一个库，但它此刻是「已注册未打开」—— 这正是 §3.2#1 懒打开的表现，**不是 bug**。

### 10.2 驱逐会「忘记」一个库的连接，但不会忘记这个库

驱逐后 `entry = null`、注册项保留（§5.11）。下一次请求它会重新打开并**重新跑一遍 `createSchema`**（`index.ts:125`，对已建表的库是一串 `IF NOT EXISTS`，幂等且 `<1ms`）。`[INFERENCE]` 成本可忽略。

### 10.3 进程库被关 ⇒ `mapStoreError` 判定成 500（不是 409）

`routes.ts:138` 把 `database is not open` 映射成 **500 internal**。我的设计**经过 §5.5 / §5.6 保证进程库不被关**，所以这条路径理论不可达。但**若**它发生（例如 D3 漏了 `release` 且同时驱逐了 pinned —— 两处同时失效），用户看到的将是 500 而非 409。**这是既有错误映射的性质，不是我的设计缺陷**；我不改 `mapStoreError`（它归 D3/既有代码）。

### 10.4 「in-flight Promise 中毒」

若 §5.3 的 `finally { this.inflight.delete(path) }` 被漏掉，一次打开失败会留下一个永久 rejected 的 Promise ⇒ 之后每次请求都以同一句旧错误失败，直到进程重启。**我在实现里用 `finally` 钉死它**，并写进验收 C7b。

### 10.5 探测对 WAL 库留下 `-wal`/`-shm`，且**不清理**

见 §2.2、§7.3。**如实登记**：这是我们唯一的可观测副作用。不清理的理由是「清理需要额外的写操作判断」，且删除它们是任何只读客户端的正常行为。

### 10.6 不做 `realpath` 的代价

见 §5.10、F9。`[INFERENCE]` 若用户用「同一物理库的两个不同路径字符串」打开它，会得到两个连接。**可观测**（`/api/databases` 两条记录），**不阻断**。

### 10.7 扫描结果的顺序是「遍历序」，不是排序序

契约 §4.3 要求 `databases` 按「registered 优先 → node_count 降序 → path 升序」排 —— 那是 **D3 的排序责任**（在合并注册表与发现结果后）。我的 `paths` 只保证**确定性**（同一目录树的 `readdirSync` 顺序稳定），不保证「好看」。

### 10.8 驱逐后重开 ⇒ `/api/events` 的第一拍是 `changed: false`

见 §5.9。与「首次访问」一致，**诚实**。用户若依赖 `changed` 检测外部写入，在驱逐边界上会丢一拍。`[INFERENCE]` 影响：一个库必须在「被驱逐的瞬间」被外部写过才会漏 —— 概率极低且下一拍会补上（`data_version` 是单调的，只是 `last` 基线被重置）。

### 10.9 stats 缓存的 5s 陈旧窗口

见 §6.4。用户新建节点后 `/api/databases` 的 `node_count` 最多陈旧 5s，**除非**该库被打开过（`openInto` 会 `invalidateStats`）。切到这个库会打开它 ⇒ 立刻失效 ⇒ 诚实。

### 10.10 `MAX_DISCOVERED = 512` 是一个**静默截断**

会在 `errors` 里留一条记录，但**列表本身不标"被截断"**（契约 §4.3 的形状没有这个字段）。`[INFERENCE]` 若真机出现，那是用户该收窄 roots 的信号；登记为 T7（是否要在 §4.3 加字段 —— 那会改冻结形状，需主 agent 裁决）。

### 10.11 ⚠️ R5 之后仍存在的 TOCTOU 单次窗口（契约 §11 U5，**已知且未解决**）

R5（§5.13）把「注册 → 重开」的**生命周期**缺口堵住了，但**不消除**这个更窄的窗口：

```
checkPathAllowed(policy, path) 通过
   ↓  ← ⚠️ 在这里把 symlink 重指向 roots 外（同一进程外的攻击者）
openMemoryStore(path) / openDatabaseReadonly(path)
```

- **为什么不修**：`checkPathAllowed` 与 `openMemoryStore` 是两次独立系统调用（前者在 policy 层，后者在 driver 层）；要消除它需要 **`O_NOFOLLOW` 语义**或「打开后 fstat 校验再 fsync 前放弃」——前者要求 `DatabaseSync` 暴露 open flags（**它不暴露**），后者需要一个「已打开但未使用」的中间态（`openMemoryStore` 一打开就 `createSchema`，没有这个态）。
- ⭐ **性质区分（重要）**：F11/SEC-02 是「**压根没有守卫**，不需要赢竞态」（已修）；本条是「**有守卫，但守卫与使用之间有窗口**」（U5，未修）。契约 §5.5b 明确把两者分开。
- **残余风险**：本机单用户工具（M5），攻击者若已能在你机器上原子替换 symlink，他能做的远不止这个。**登记为已知边界，不是「已解决」。**

### 10.12 R6 只覆盖只读打开点（可写那条靠调用方守卫）

`openDatabaseReadonly` 内的 `isFile()` 守卫（R6）**不覆盖** `resolve` 走的那条**可写**路径（`openMemoryStore` → `openDatabase`）。FIFO 上 `new DatabaseSync(p)`（可写）**同样会挂死**（`[INFERENCE]`，同一个同步构造；本案在 `resolve` 第 ① 步已被 `isFile()` 拦下）。
⇒ **`registry.resolve` 的 `statSync().isFile()` 是那条路径上唯一的一道**（§5.14 已写清三处守卫的层次）。


### 10.13 ⚠️ 扫描是**同步**的 ⇒ 单次阻塞事件循环（已知 DoS，低危，如实登记）

`discoverMemoryDbs` 用**同步 `readdirSync`**（§6.2 的设计）。实测：`~/projects`（11345 个目录）一次扫描**同步阻塞事件循环 2699 ms**（`~/projects/hackathon` 为 71 ms）。

- **5s TTL 只摊薄频率，不消除单次阻塞**：TTL 之内没有第二次扫描，但**触发的那一次**仍然是一次 2.7 秒的同步停顿（整个进程在此期间不响应任何请求）。
- **触发面**：`/api/databases` 是 **GET**，而 S3 的 `Origin` 检查**只作用于非 GET/HEAD**（`security.ts:53-54`、契约 §5.6）⇒ 任意一个跨源页面都能发一个 GET 触发它（`[INFERENCE]` 前端不会自动跨源带凭据，但 GET 本身不拦）。在 `--roots ~` 这类宽 roots 下值得知道。
- **为什么不本期改**：改异步（`fs.promises` 或 `opendir` 流式）会改动 `discoverMemoryDbs` 的**整个实现形态**与它的「同步、可预测」的确定性（`readdirSync` 的稳定顺序是 §10.7 的前提），换来的是「宽 roots 下首次列库卡一下」这一个症状。
- **缓解（已做）**：`MAX_DISCOVERED = 512`（§6.3）限制了**找到的库数**但**不限制遍历的目录数** —— 所以这条缓解**不足**，我不假装它够。
- **必须告知用户（D5 的活）**：写进 `15` 的已知限制与 README —— **若 `roots` 宽泛，首次打开库列表会卡一下（可到秒级）**；建议用 `--roots` 收窄到实际放 world 的目录。
- ⭐ **登记为已知限制，MUST NOT 说成「已缓解」**。若将来要修，最小改动是给扫描加一个**目录数上限**（例如 20000 个目录后停止并记一条 error，与 `MAX_DISCOVERED` 同形）。

## 11. 分层的各自职责（防越界）

| 层 | 职责 | MUST NOT |
|---|---|---|
| `driver.ts` | 「怎么打开一个连接」（可写 / 只读） | 知道探测、注册表、库语义 |
| `discovery.ts` | 「这个路径是不是记忆库」「子树里有哪些库」「只读统计」 | 打开可写连接、持长命连接、知道 HTTP |
| `registry.ts` | 「已注册的库在进程里的连接生命周期」 | 探测、路径策略（roots）、路由 |
| `db-path-policy.ts`（D2） | 「这个路径允许被注册吗」「多库在这个绑定位下开着吗」 | 探测实现、注册表内部 |
| `routes.ts`（D3） | 「`?db=` → 目标库 → handler」，3 条库管理路由 | 打开连接、探测、驱逐（只调 `resolve` + `release`） |
| 前端（D4） | 选择状态、`?db=` 注入 | 直连 SQLite、直接注册 |

⭐ **探测的调用者只有两个**：`/api/databases/open`（D3，注册前）与 `readMemoryDbStats` 的失败路径（内部）。**没有第三个**。这是防「探测被绕过」的结构性保证。
⭐ **R5/R6 的落点（安全评审后新增，§5.13 / §4.2.1 / §5.14）**：路径策略的**重验**在 `registry.resolve`（D1）；类型守卫的**唯一下沉点**在 `openDatabaseReadonly`（D1 的 driver 层）。两者都**不**放在 D3 的调用点 —— 这是「安全属性在调用点上」这条教训的落法。

## 12. 实现完成后的验收清单（每条可机械核验）

前置：`cd packages/memory`；所有 `grep` 用仓库的 `grep` 工具（禁 shell `grep`）；测试用 `npx vitest --run test/web/<file>`（**MUST NOT** 跑全量，那由主 agent 统一跑）。

#### 12.0 三条从本轮评审门换来的纪律（**先读这节，再写守卫**）

> **D-1（新守卫必查特例）**：**一个守卫新增时，MUST 逐一检查它是否覆盖了「已明文支持的特例」。**
> 本轮两处同型缺陷 —— `nlink`（误伤备份用户）与 R5（误伤 roots 外的进程库，F14）—— 都是**新守卫忘了给它早已裁定的例外留豁免**；两处都表现为「合法配置下整个 UI 报错」，且**两处的测试都测不出来**。
> 做法：写 `if (!cond) reject` 之前先 grep 一遍本设计里**所有类似的允许关系**（roots 内/外、`allowAnyPath`、进程库与 roots、`:memory:`），逐个问「这一条会不会命中它」。

> **D-2（安全开关缺省最严）**：**安全开关的缺省值 MUST 是「最严」，且缺省路径 MUST 能被编译期或测试抓住。**
> 一个「忘了就静默关掉」的安全检查，比没有检查更危险 —— 它给出虚假的安全感。落地：`policy` 必填（§5.13.3，忘传 = 编译错误；C20）。
> ⭐⭐ **D-2 推论（D5 抓到）**：**必填字段的「必填」会被它的外层可选性抵消** —— 只要容器（options 对象）里有一个必填字段，**容器本身也 MUST 必填**。`constructor(opts?)` 会让 `new StoreRegistry()` 在编译期合法、运行时撞 undefined ⇒ 「忘传 = 编译错误」的保证是**假的**（§5.13.3 / C20b）。


> **D-3（下沉到唯一入口）**：约定「调用方记得检查」在 N 个调用点就会漏一个。**守卫 MUST 下沉到唯一的打开/入口点**（R6 落 `openDatabaseReadonly`，覆盖 `probeMemoryDb` 与 `readMemoryDbStats` 两条入口；§5.10.1 归一化落 `key()`，覆盖四个入口）。

⭐ **本节三条都是「测试绿、生产红」的形态** —— 新增验收项时 MUST 问一句：**这条断言在「守卫被误改/漏接」时会变红吗？** C13b（R5 豁免）、C20（policy 必填）、C20b（容器必填）就是为此而加的。
