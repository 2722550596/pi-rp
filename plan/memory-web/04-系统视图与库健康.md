## 1. 一句话定位

`views.ts` 是**七个 `MEM://` 视图的第二实现**：它把 `memory-views.ts` 里那七个「给人看 markdown」的 `render*` 函数，翻译成「给程序看的结构化 DTO」；`views-parity.test.ts` 用一条**双向相等的可机械核验不变量**把两份真相钉在一起，防止它们悄悄漂移。

它不发明语义。它**只搬运**语义 —— 每一个 `filter` / `sort` / `slice` 都必须在 `memory-views.ts` 里找到一一对应的那一行。

### 2.0 公共片段

```ts
// src/web/views.ts — NEW
import type { MemoryNode, MemoryStore, VisibilityPredicate } from "./../store.ts";

/** 每个视图共用的条目外壳。uri 是 UI 路由主键（契约 §6.1），node_id 只做内部传递。 */
export interface ViewItemBase {
  /** 节点内码。契约 §10.1：唯一叫法 node_id，禁用 id / node_uuid。 */
  node_id: string;
  /** 人类可读地址，UI 显示与寻址主键。 */
  uri: string;
  /** UI 路由用的域名，来自 node.domain（契约 §6.1）。 */
  domain: string;
  /** 重要度，数值越大越重要（契约 §6.1 ⚠️ 与 nocturne priority 极性相反）。 */
  importance: number;
  /** 已遮蔽（原分支已回滚）。契约 §6.6 + Main 广播 #2 的冻结文案。 */
  shadowed: boolean;
}

/** MEM://timeline 的条目：维度是 raw_id，不是 node（见本文 §4.3）。 */
export interface TimelineItem {
  raw_id: number;            // 契约 §6.2 / §10.1
  world_ts: string | null;   // 《世界时间》主轴口径（契约 §10.2）
  role: string;              // 可能是 customType（契约 §12-P5）→ 前端必须容错
  text: string;              // 已折叠空白 + 截断至 200 字符，与 renderTimelineView 同口径
  session_id: string;        // render* 没渲染，但 D3 的 session 分组要用；见 §8 冲突#6
}

export interface ForgottenItem extends ViewItemBase {
  /** 沉睡天数 = nowDays - epochDays(last_accessed_at ?? created_at)。与 render* 同口径。 */
  days_asleep: number;
  /** render* 的第二行（snippet(node)，上限 80）。 */
  snippet: string;
}

export interface RecentItem extends ViewItemBase {
  /** node.updated_ts 原文（ISO）。render* 只取前 16 字符，DTO 给全量让 UI 自己决定。 */
  updated_ts: string;
  /** node.disclosure，可为 null。 */
  disclosure: string | null;
}

export interface IndexDomainGroup {
  domain: string;
  /** 该 domain 下 !is_stub && parent_id === null && isVisible 的根节点。 */
  roots: Array<ViewItemBase & { snippet: string }>;
}

export interface WakeupChild {
  node_id: string;
  uri: string;
  domain: string;
  importance: number;
  shadowed: boolean;
  /** child.disclosure，渲染成 (当…)。render* 用**未截断**的 disclosure。 */
  disclosure: string | null;
  /** child.content 折叠空白后截断 100 字符；render* 在空时**整段省略**。 */
  snippet: string;
}

export interface WakeupFocus {
  node_id: string;
  uri: string;
  domain: string;
  importance: number;
  shadowed: boolean;         // 恒为 false —— 被遮蔽的焦点在 render* 里被 continue 掉了
  world_ts: string | null;
  /** formatRelativeWorldTime(node.world_ts, worldTime)，recall.ts:98。空串 = 无相对量。 */
  world_ts_relative: string;
  disclosure: string | null;
  /** 全文，不截断（render* 在此处也不截断）。 */
  content: string;
  children: WakeupChild[];
}

export interface GlossaryItem {
  keyword: string;
  node_id: string;
  uri: string;               // 经 store.getNode(node_id) 反查；节点不存在时该条目**整条不出现**
}

/**
 * MEM://wakeup —— 三段式。
 * ⚠️ 结构不是扁平 items[]：它有三个**语义不同**的集合，parity 必须分开核（见本文 §4.4）。
 */
export interface WakeupViewDTO {
  world_time: string | null;
  focuses: WakeupFocus[];
  /** 被 render* 剔除、但仍留在 awaken 清单里的条目 —— UI 必须能显示「为什么没出现」。 */
  skipped: Array<{ uri: string; reason: "missing" | "stub" | "shadowed" }>;
  /** 最近动态：render* 只渲染 snippet，**不带 uri**（见本文 §4.4 与 §12-SPIKE-E）。 */
  recent: Array<{ node_id: string; uri: string; snippet: string }>;
}

export interface DiagnosticCategories {
  stale: Array<ViewItemBase & { days_asleep: number; snippet: string }>;
  crowded: Array<ViewItemBase & { child_count: number }>;
  placeholder: Array<ViewItemBase & { child_count: number; created_at: string }>;
}

export interface DiagnosticViewDTO {
  domain: string | null;
  /** 三分类**各自**为空时不出现（render* 用 if (x.length > 0) 决定是否打印小节）。 */
  categories: DiagnosticCategories;
  /** ⚠️ render* 在三分类全空时返回**英文常量串**而非分类骨架，见 §2.7 与 §6。 */
  healthy: boolean;
}

/** /api/view 的响应信封（契约 §7.2：列表端点返回 { items, total }）。 */
export type ViewDTO =
  | { name: "timeline";   items: TimelineItem[];   total: number }
  | { name: "forgotten";  items: ForgottenItem[];  total: number; domain: string | null }
  | { name: "recent";     items: RecentItem[];     total: number }
  | { name: "index";      items: IndexDomainGroup[]; total: number; domain: string | null }
  | { name: "glossary";   items: GlossaryItem[];   total: number }
  | { name: "wakeup";     items: WakeupViewDTO;    total: number }
  | { name: "diagnostic"; items: DiagnosticViewDTO; total: number; domain: string | null };
```

> `total` 的语义冻结为「主集合的长度」。`index` 的 `items` 是分组数组，`total` = **分组数**；根节点总数在 `IndexDomainGroup[].roots.length`。
> `wakeup` / `diagnostic` 的 `items` 不是数组 —— 它们的「集合维度」见 §4.4 / §4.5；`total` 分别给 `focuses.length` 与三分类条目数之和。

② 由此产生一个**既有缺陷**：`listed` 只在子节点处 `add`，而焦点处与子节点比对的是 `child.uri`（解析后），所以清单里写 alias 时 `fullUris.has("core://new/place")` 为 false → 该节点在「最近动态」里**又出现一次**。SPIKE-F 实测：同一节点内容在输出里出现 **2 次**，用规范地址写清单时只 1 次。结构化版 MUST **照抄**该行为（parity 要求），UI 层 MUST 去重显示（§7.4）。这是本文登记的最重要一条既有缺陷。

③ **同一根因的另一半**：`listed` 初始是**清单原文**（alias 串），而比对用 **`child.uri`（解析后）**，所以 alias 场景下这个「已在清单里」的判定同样会漏 —— 子节点会被重复渲染。SPIKE-M 实测清单含重复项时同一块渲染两次（`### core://dup` × 2）。结构化版照抄，parity 侧靠 `Set` 收敛（§4.6）。

④ ⭐ **决定性发现**：`## 最近动态` 区块**不渲染任何 uri**（`:124` 只有 `snippet(n)`）。SPIKE-E 原文：

```
## 最近动态
别的节点乙
别的节点甲

contains '://' ? true          ← 唯一的 :// 来自焦点区的 ### core://focus
listRecentNodes(5) minus listed -> [ 'core://other/b', 'core://other/a' ]
```

即这一段携带的**节点身份在文本里根本不存在**。它不是「提取正则写得好不好」，是**信息在渲染时就被丢弃了**。因此 §8.3 原公式对 wakeup 的 `recent` 子集**不可机械核验**。方案见 §4.4 —— 这是本文对契约 §8.3 的**正式偏离申请**。

## 3. 每个视图的取数算法

`src/web/views.ts` 的**唯一入口**：

```ts
// NEW — src/web/views.ts
export interface ViewRequest {
  name: "timeline" | "forgotten" | "wakeup" | "glossary" | "recent" | "index" | "diagnostic";
  /** 与 MEM:// URI 里的 domain 段同义；timeline 忽略它。 */
  domain?: string;
  /** 与 MEM:// URI 的 <N> 段同义。缺省值按视图各自的口径。 */
  limit?: number;
  /** 分支可见性谓词，由 visibility.ts 构造（契约 §6.6）。 */
  isVisible: VisibilityPredicate;
  /** 用于计算 shadowed。契约 §6.6 第一步。 */
  isShadowed: (node: MemoryNode) => boolean;
}

export function buildView(store: MemoryStore, req: ViewRequest): ViewDTO;
```

**默认 limit 的冻结值**（下表）。⚠️ 这些值是 `tools.ts` 的 `parseViewSegments(uri, view, fallbackLimit)`（`tools.ts:180-199`）传给各视图的 **fallback 参数** —— 本文**只对齐这些数值**，**MUST NOT** 复现或调用该 URI 解析函数（`/api/view` 收显式参数，见下）：

| 视图 | 默认 limit | 依据 |
|---|---|---|
| `timeline` | 20 | `tools.ts:238` `parseViewSegments(uri, "timeline", 20)` |
| `forgotten` | 5 | `tools.ts:245` `parseViewSegments(uri, "forgotten", 5)` |

## 4. ⭐ §8.3 不变量：为什么必须双向相等，以及怎么才真的成立

### 4.1 为什么不能用「包含关系」

契约 §8.3 已定：**双向相等，多一个少一个都要 fail**。补三条理由（这是本文最该被评审的一段）：

「包含关系」有**两种朝向**，两种都错得不一样：

- **UI ⊆ 文本**（只断言 UI 不漏）→ 放行「UI **多**渲染了节点」。多出来的典型是：忘了 `!is_stub`、忘了 `isVisible`、忘了去重。这三类恰恰是本模块**最可能**引入的 bug（契约 §8.3 点名要求 fixture 覆盖 stub / shadowed）。
- **文本 ⊆ UI**（只断言 UI 不多）→ 放行「UI 漏渲染」。典型是 `.slice()` 差一位、`listed` 集合语义抄错。

更关键：**包含关系在空集上恒真**（`∅ ⊆ 任何集合`）。所以「UI 崩了返回空数组」这种最严重的失败，用包含关系**永远测不出来**。双向相等在空集上仍要求文本侧也为空，所以能抓住它 —— 这正是 §11「非空性用例」要证明的东西（SPIKE-N 矩阵里 `G2 全空库` 那一列就是活证）。

**一句话**：这条不变量的目的不是「检查 UI 对不对」，是「检查**两份实现是否还一致**」。而「一致」是**等价关系**，只能由相等断言，不能由包含断言近似。

### 4.2 两侧集合的**可精确定义**

| 侧 | 定义 | 为什么「可精确」 |
|---|---|---|
| 结构化侧 | `items[].node_id` 去重后的集合（`index` 取 `roots[]` 扁平，`wakeup` 取三段，见 §4.3） | DTO 由本文定义、字段名冻结，取值无歧义 |
| 文本侧 | 从 `render*` 输出里**按视图专用锚点**提取 uri → `store.resolveUri(uri)?.node_id` → 去重 | 见 §5 |

⭐ **关键前提**：文本侧的「精确」**不是免费的**。它要求「文本里渲染的每个节点都带 `uri`」且「`uri` 处在可判别的结构位置」。**契约 §8.3 原文默认了这两条成立，但实跑证明它们在 `wakeup` 上不成立**（§2.6 ④）。见 §4.4。

| `wakeup` | `focuses[].node_id` ∪ `focuses[].children[].node_id` | §5.3 **结构解析** | `node_id`（分段，见 §4.4） |
| `diagnostic` | 三分类 `node_id` 并集 | §5.2 锚点⑤（三条） | `node_id` + **分类名集合** |

⚠️ **`timeline` 的维度是 `raw_id`**，文本侧提取**必须**用 `^- \[(\d+)\] ` 这个行锚点，不能用「任意数字」。`raw_id` 与 `node_id` 是两套 ID 空间，混用会在「恰好有个节点 id 等于 raw_id」时假绿。契约 §8.3 修正版已明确（Main 广播 #3）。

### 4.3.1 ⭐ `timeline` 升级为**双端点互验**（契约变更 #6，2026-09-15）

契约 §8.3 的 timeline 断言**已升级**（由 D3 提议、主 agent 采纳并回写）：

```
主防线（timeline 专用）：Set(/api/raw?activeOnly=1&limit=N 的 raw_id)
                     === Set(/api/view?name=timeline&limit=N 的 raw_id)
附加断言（保留）：        === Set(renderTimelineView(store, N) 文本提取的 raw_id)
```

**为什么这条更强，以及为什么本文接受它。** 原公式是「D4 的结构化输出 vs 引擎的 `render*`」—— 它只能证明 **D4 与引擎一致**，完全**看不到 D1 的 `/api/raw` 自己实现偏差**（比如 D1 忘了传 `activeOnly`、或把 `limit` 语义写成了「跳过」）。新公式把两个**独立端点**对撞，任一侧偏差都会红。这是把本模块的不变量从「与引擎对齐」提升到「**消费者所见即所断言**」，本文完全拥护。

**但本文对这条升级加一个限定条件**（这是 D4 对契约的**唯一补正**）：`activeOnly=1` 只是 D1 的**入参**，断言必须同时核 **`active=0` 的行确实被两侧都排除**，否则两个端点**可能一起错**（例如 D1 与 D4 都忘了 `activeOnly`，`/api/raw` 返回全部行、`/api/view` 只在渲染时过滤 → 两个端点集合仍相等，但**都不等于引擎口径**）。因此 §11.3 的 T9 拆成三条：**T9a 双端点互验**（主防线）+ **T9b 与 `render*` 文本互验**（附加防线，专门抓「一起错」）+ **T9c 回滚夹层**（抓「先取尾再过滤」）。契约说附加断言「不是主防线」——本文同意它不是主防线，但它**是唯一能抓共同偏斜的防线**，MUST 保留，**不得**因为升级为主防线而删掉。

**我自己复跑的象限**（主 agent 建议「双人各测一个象限」，D3 已测 N=5/20/100 + 四个要素）。我测的象限是**跨 session × 同 entry_id 复合键 × 回滚夹层**，N ∈ {1,2,3,5,20,100}，六档全绿。原始输出见 §12.14-SPIKE-P。

⭐ **本次复跑额外暴露的一条 fixture 要求**：`raw_id=1`（活跃）与 `raw_id=4/5`（活跃）之间**夹着两条 `active=0`**（raw_id=2,3）。这使 `N=3` 成为**唯一能区分「先过滤再取尾」与「先取尾再过滤」的档位** —— 若实现写成后者，`N=3` 会给出 `[5,4,3]`（含一条 inactive），而正确实现给 `[5,4,1]`。**§11.2 的 timeline fixture（G8）MUST 含「活跃行在中间被 inactive 隔开」的形态**，且断言 MUST 至少覆盖 `N=3`（§11.3 T9c）。这是本文对 fixture 清单的**新增硬要求**（D3 的四要素清单里没有这一条）。

### 4.4 ⭐ `wakeup`：必须放弃「整体相等」，改「逐段相等」

**这是本文对契约 §8.3 的正式偏离申请，理由是可复现的实测事实。**

`renderWakeupView` 的 `## 最近动态` 段（`memory-views.ts:124`）渲染的是 `snippet(n)`，**不含 uri**。SPIKE-E 原文（§12）：

```
## 最近动态
别的节点乙
别的节点甲
```

而结构化侧要表达的是 `listRecentNodes(5).filter(n => !listed.has(n.uri) && isVisible(n))` 那**两个**节点。文本里**零个**可提取的 uri。

因此：**「文本侧 node_id 集合」对 wakeup 是不完备的，任何提取正则都救不了**（信息不在文本里）。强推「整体双向相等」只有两条路，都不可接受：

- 让结构化侧**也丢掉** `recent` → 等于「为迎合一条错误公式，把一个真实语义删掉」。这违背契约 §8.2（Web UI MUST 输出结构化 JSON 以便排序/过滤/跳转）—— `recent` 正是 UI 要跳转的节点。
- 放宽成包含关系 → 回到 §4.1 的全部问题，且**更糟**：`recent` 段完全不受约束。

**采用方案（三段分别核，每段都是双向相等）：**

```
wakeup 的 parity = 以下三条同时成立：
  ① Set(focuses[].node_id)             === 文本「### 」块的 uri 集合（经 resolveUri 反查）
  ② Set(focuses[].children[].node_id)  === 文本中焦点块之后「- 」子列表的 uri 集合
  ③ focuses[].length + recent[].length  === 文本「### 」块数 + 「## 最近动态」行数
```

- ① ② 是**双向相等**，且用**结构解析**（§5.3）而非行正则 —— 因为 `renderWakeupView` 会把 `node.content` **原样打印**（`:105`），内容里可出现 `### core://x` 或 `- core://x` 形状的行。SPIKE-K 复现：内容含 `### core://real/target` 的节点会让**行正则**多提取一个**真实存在**的 uri（`resolveUri` 成功），而**结构解析**正确地只认出 1 个焦点。
- ③ 是**对 `recent` 的间接约束**（用「行数」这个可数事实，而非「身份」这个已丢失的事实）。它把「UI 漏一个 recent 节点」与「多一个」都变红，**同时不强求信息不在文本里的身份**。这是 §4.1「不变量必须方向对」的具体体现：**在这里追求「逐节点身份相等」是方向错，比没有更贵**（拿一个不可能成立的条件，会把测试逼成 `skip` 或恒绿）。

> ⚠️ ③ 是**弱化**。要让 `recent` 的身份也被真正核验，只有一条路：**改 `renderWakeupView`**，在 `## 最近动态` 行里带上 uri（如 `- ${n.uri}: ${snippet(n)}`）。那是**引擎侧改动**，不在本期（契约 §12「本期不修引擎」）。**已登记为 §9-U1 待拍板** —— 若主 agent 批准，③ 立刻可升级成逐身份双向相等，公式更干净。

### 4.5 `diagnostic`：不是节点集合，是「分类 + 节点」的积

三分类**各自可能不出现**（`:204/:211/:216` 各有一个 `if (x.length > 0)`）。所以它的 parity 是**两层**：

```
① Set(diagnostic.categories 里值非空的键名)
     === 文本里 `## \d+\. ` 小节的分类名集合      ← 用名字，不用序号（会跳号，§2.7-3）
② Set(stale ∪ crowded ∪ placeholder 的 node_id)
     === 文本里三类条目行的 uri 提取集合
```

并且**必须**有一条断言覆盖 `healthy` 分支：三分类全空时，文本 === `"No issues found. Memory system is healthy."`，结构化 === `{healthy: true, categories:{stale:[],crowded:[],placeholder:[]}}`。SPIKE-B 实测该字符串**没有任何 uri**，所以此时②自动退化成「两侧都是空集」——仍要断言，因为它是**空视图**这一类 fixture 的唯一入口。

### 4.6 去重必须在**两侧都做**

- 结构化侧：`wakeup` 在 **alias 清单**场景下会让同一 `node_id` 出现两次（§2.6 ②，SPIKE-F 实测）。
- 文本侧：`glossary` 里同一 `node_id` 可被多个 `keyword` 指向（表是 `(keyword, node_id)`）。

**裁定**：两侧都取 `Set`，并**另行**断言「结构化侧去重前长度 === 文本侧去重前 uri 出现次数」作为**软**检查（不进 fail 集，只 `console.warn`）。[推断] 若主 agent 认为回显次数也算契约，应升级为硬断言 —— 但那会要求 UI 也照抄重复，与「UI 应按 uri 去重显示」（§7.3）冲突，故本文定为软检查。

### 4.7 有序 vs 无序

实跑 SPIKE-I 证明两侧顺序都确定（§5.4）。所以**主断言用有序相等**（`items` 与文本行天然都有序），比集合相等更强；数组相等失败时再打印两侧的差集辅助定位。契约 §8.3 写的「集合」不禁止更强的有序断言 —— 有序相等成立 ⇒ 集合相等成立。

**原始输出见 §12。** 下面每条结论都对应 §12 的一段实录。

### 5.2 结论一：`uri` 的**四种形态 + 三条 diagnostic 锚点**（对五个非 wakeup 视图有效）

必须**按行锚点分别写正则**，不能用一个通用 uri 正则扫全文：

| # | 出现位置 | 实测原文 | 锚点正则 |
|---|---|---|---|
| ① | `forgotten` 主行 | `- 1 天没想起 \| index:// [★5]` | `^- \d+ 天没想起 \| (\S+) \[★-?\d+\]$` |
| ② | `recent` 主行 | `- core://identity/habits [★8] (修改时间: 2026-09-14 23:51)` | `^- (\S+) \[★-?\d+\] \(修改时间: \d{4}-\d{2}-\d{2} \d{2}:\d{2}\)$` |
| ③ | `index` 条目 | `  history://: Scene summary domain`（uri 后**紧跟冒号**） | `^ {2}(\S+?): ` |
| ④ | `glossary` 指向行 | `  -> core://scenes/tavern`（**不取** keyword 行） | `^ {2}-> (\S+)$` |
| ⑤a | `diagnostic` stale | `- core://identity [★10] — 沉睡约 257 天` | `^- (\S+) \[★-?\d+\] — 沉睡约 \d+ 天$` |
| ⑤b | `diagnostic` crowded | `- history://scenes (12 children)` | `^- (\S+) \(\d+ children\)$` |
| ⑤c | `diagnostic` placeholder | `- core://identity — 1 条记忆挂在下面 \| Created: 2026-09-14` | `^- (\S+) — \d+ 条记忆挂在下面 \| Created: \d{4}-\d{2}-\d{2}$` |

**⭐ 为什么必须是「按行锚点」，而不是 Main 广播里建议的通用式 `/[a-z][a-z0-9+.-]*:\/\/[^\s)（），,、—]*/`**：SPIKE-J 用**真实会出现的 fixture** 打穿了通用式 —— 节点 `core://carrier` 的**正文内容**里写了 `- core://real/target [★5]`、`### core://real/target`、`-> core://real/target`、`  core://real/target: x` 四种形状。因为 `forgotten`/`index` 会把正文摘要拼进**同一行**、`wakeup` 会把正文**原样打印**，通用式会把这些**正文里提到的真实节点**也提取出来，产生**假阳性**。SPIKE-J 原始输出：

```
--- forgotten ---
- 1 天没想起 | core://notes/a [★5]
  第一行 - core://phantom/from-content [★5] ### core://phantom/heading -> core://phan…
  looseExtract -> ["core://notes/a","core://phantom/from-content","core://phantom/heading","core://phan…"]
```

后三个是**正文内容**，不是视图条目。

**「解析失败就丢弃」这条兜底不够。** 上例的假阳性指向**真实存在**的节点（建库时真建了 `core://phantom/*`），所以「`resolveUri` 失败就丢」救不了它 —— 它只会丢掉碰巧不存在的那些（`…` 截断尾巴）。**唯一的解是按行锚点。**

### 5.3 结论二：`wakeup` 必须用**结构解析**，不能用行正则

`renderWakeupView` 的 `### ` / `- ` 行可被 `node.content` 伪造。SPIKE-K 的对抗 fixture：

```typescript
store.insertNode({ uri: "core://real/target", content: "真实目标", importance: 5 });
store.insertNode({ uri: "core://carrier",
  content: "第一行\n### core://real/target\n- core://real/target [★5]\n第二行", importance: 5 });
store.setKv("awaken_uris", JSON.stringify(["core://carrier"]));
```

实测输出：

```
### core://carrier
> (发生于: 2026-09-15T00:00:00Z，今天)
第一行
### core://real/target
- core://real/target [★5]
第二行
```

| 提取器 | 结果 | 判定 |
|---|---|---|
| 行正则 `^(?:### \|- )(\S+?)…$` | `["core://carrier","core://real/target"]` | ❌ **假阳性**（`core://real/target` 是正文内容，且 `resolveUri` 成功） |
| 结构解析 | `{focuses:["core://carrier"], children:[]}` | ✅ 精确 |

**结构解析规则**（`renderWakeupView` 语法，逐行对齐 `memory-views.ts:89-126`）：

1. 按 `"\n\n---\n\n"` 切块（`:126` 的 join 分隔符）。
2. 块以 `"### "` 开头 → **焦点块**：第一行 = `### <uri>`；其后**第一个空行之后的连续 `- ` 行**（且必须延伸到块尾）才是子节点列表。
   - ⚠️ 若正文自己以 `\n\n- …` 结尾，规则 2 仍会误认。SPIKE-L 复现：正文 `"正文\n\n- core://fake/one\n- core://fake/two"` 被认成 2 个子节点 —— 但这两个 uri **`resolveUri` 为 null**，所以「解析 → `resolveUri` 过滤」两步合起来仍精确。**两步缺一不可。**
   - 若正文里写的是**真实存在**的 uri，该歧义无法从文本侧消除。[推断] 概率极低（需正文恰好以空行 + `- 真实uri` 结尾，且该节点恰为「最近动态」候补）。登记为 §9-U2。
3. 块以 `"## 最近动态\n"` 开头 → 剩余**非空行数**即 `recent` 长度（身份已丢失，见 §4.4 ③）。
4. 其余块（`> 当前世界时间: …`）忽略。

### 5.4 结论三：排序确定性 = 不需要二级排序键

把 20 个节点的 `updated_ts` 全改成同一值，`renderRecentView(s,10)` 连跑 12 次，输出序列**逐项相同**（SPIKE-I）。`forgotten` 同法测过也稳定。
依据：基集 `listRecentNodes` 有 `ORDER BY updated_ts DESC LIMIT ?`（SQLite 对全同键的返回序由 rowid 决定，稳定）+ V8 稳定排序。

### 5.5 结论四：最终采用的正则/解析器（24/24 PASS）

契约 §8.3 说的「同一组 URI 正则」在实现上**不是一组，而是按视图五组 + wakeup 一个结构解析器**。这是对契约表述的补正，登记为 §8 冲突#3。

## 6. `diagnostic` 与契约 §1.3 红线的关系

### 6.1 红线原文与边界

契约 §1.3 第 3 条：

> **不做审计观测面板的"扩展"。** `docs/memory-system.md:190` 决策 23 原文："默认开、可关、**不设观测面板**"。本期只提供**只读的审计流列表页**（对账用），**不得**新增任何对审计流的聚合分析 / 图表 / 告警。

**边界两侧对照：**

| | 审计流（`audit_log`） | 库健康（`diagnostic`） |
|---|---|---|
| 数据源 | `audit_log` 表，**append-only 事件流**（契约 §6.5，16 个事件名） | `nodes` 表，**当前状态快照** |
| 回答的问题 | 「**发生过什么**」（谁在何时写了什么） | 「**现在怎么样**」（哪些记忆睡太久 / 哪些父节点太挤） |
| 时间性 | 时间序列 | 无时间轴（只有一个 `nowDays` 基准） |
| 权威实现 | 无（本期新写的只读列表，D1/D5） | `renderDiagnosticView`（**引擎既有**；`tools.ts:229-232` 已作为 `MEM://diagnostic` 暴露给模型，`tools.ts:161` 白纸黑字列在工具描述里） |
| 红线 | ⛔ **不得**聚合 / 图表 / 告警 | ✅ **可以**分类展示，因为它**本来就分类** |

### 6.2 本文的裁定：`diagnostic` **不在** §1.3 红线内

两条理由，都可核验：

1. **它是引擎既有的模型可见视图，不是本期新造的观测面。** `tools.ts:161` 的 `recall` 工具 URI 描述里已列 `MEM://diagnostic/<domain>`，`tools.ts:229-232` 是它的执行分支。本期做的是「把同一份内容以结构化形式搬到 Web」——契约 §8.2 明确要求这件事。**移除它会制造新的 parity 缺口**（六个视图有 Web 版、一个没有），反而更糟。
2. **决策 23 的「不设观测面板」针对 `audit_log` 的聚合分析**（`docs/memory-system.md:190` 上下文是「审计留痕」条目）。`diagnostic` 的分类（stale/crowded/placeholder）是 `nodes` 表上的**状态判据**，与审计流无数据关系。

### 6.3 但仍要守的**自律线**（对 `views.js` 的硬约束）

`diagnostic` 是**唯一**一个天然诱导人加图表的地方（它已经分类了，「加个饼图吧」是本能）。所以：

- 呈现形式 **MUST 是三个列表**。**MUST NOT** 出现饼图 / 折线 / 趋势线 / 计数器仪表盘 / 「健康分」。
- **MUST NOT** 出现任何「随时间变化的诊断」（那会需要 `audit_log`，直接踩红线）。
- **MUST NOT** 产生告警 / 通知 / 徽章红点。
- 允许的增强只有一条：**每条结果可点击跳转到节点页**（这是「浏览」，不是「观测」）。
- `healthy === true` 时显示 `No issues found...` 的**中文对照**（例：`未发现问题，记忆系统健康。`），**不**做成绿色的「全绿通过」徽章。

⭐ 给主 agent 的判断依据：**「这个界面在回答『库现在是什么样』还是『库曾经发生了什么』？」** 前者是 `diagnostic`，可以；后者是审计面板，§1.3 禁止。

## 7. 视图页的交互（`src/web/assets/views/views.js`）

### 7.1 模块契约（D2 已批准，本文遵守）

```js
// src/web/assets/views/views.js  — 纯 ESM JS（契约 §2.1：不得写 .ts）
export async function mount(el, params, ctx) {
  // …
  return function dispose() { /* 解绑全部监听 */ };
}
```

- `el`：`#mw-main`（已清空）。
- `params`：`URLSearchParams`。本页认 `name`（七个之一，缺省 `recent`）、`domain`、`limit`。
- `ctx`：`{ api, toast, navigate, on, off, route }`（D2 §2.5）。本页**只用** `ctx.api.view` / `ctx.api.meta`、`ctx.navigate`、`ctx.on/off`。
- **零 POST**（契约 §9.1 纪律 1：读路径不写库，且 §6.2 红线禁止新增写语义）。本页 MUST NOT 出现 `method: "POST"`。
- **零裸模块说明符 import**（契约 §2.1 零构建）：只用相对路径与浏览器原生 API。

### 7.2 导航（域内切换 + 视图切换）

路由形态（hash，D2 的壳负责解析）：

```
#/view?name=recent
#/view?name=forgotten&domain=core&limit=10
#/view?name=diagnostic
#/view?name=wakeup&limit=5
```

- 顶部一条 **tab 条**，七个视图各一个 `<a role="tab">`。点击 → `ctx.navigate("#/view?name=<n>")`。**切视图时 `domain` 与 `limit` MUST 重置为默认**（不同视图的合法 domain 集合不同，`wakeup`/`glossary`/`recent` 根本没有 domain 概念）。
- `index` / `forgotten` / `diagnostic` 三个视图**显示 domain 下拉**：选项来自 `ctx.api.meta()` 的 domain 列表（D2 §4.1 已把它定为 `listDomains` 的来源）。选「全部」→ 去掉 `domain` 参数。
- **`timeline` 不显示 domain 下拉**，改显示一句说明：`原文日志不分领域（raw_log 无 domain 概念）`。依据 `memory-views.ts:23-24` 的注释与 `tools.ts:213-214`。

### 7.3 limit 调整

- limit 控件是 `<input type="number" min="1" max="200">`，默认值取**该视图的默认 limit**（§3 表格：timeline 20 / forgotten 5 / wakeup 5 / recent 10）。
- **`glossary` / `index` / `diagnostic` 不显示 limit 控件**（它们的 render* 没有 limit 语义；`index`/`diagnostic` 的 render* 参数里也没有 limit）。给它们一个假的 limit 会造出**第二套语义**，违反契约 §8.2 精神。
- 提交 → `ctx.navigate` 带上 `limit`；`views.js` 把 `limit` 原样透传给 `ctx.api.view({name, domain, limit})`，**不在客户端做任何截断**（截断是服务端语义，客户端截断会让 parity 断在客户端）。
- **`wakeup` 的 limit 提示文案必须写清**：`最近动态条数`（不是「焦点条数」）。依据 §3.6：`limit` 只作用于 `recent`。

### 7.4 渲染要点（逐视图，全部由 DTO 驱动）

| 视图 | 渲染 |
|---|---|
| `timeline` | 每行 `[raw_id] world_ts role: text`。`world_ts === null` 时显示 `—`（**不要**照抄 render* 的空串，那会渲染出连续两空格）。`role` 直接输出（可能是不认识的 customType，契约 §12-P5）→ **必须容错**，不加白名单。 |
| `forgotten` | 卡片：`days_asleep` 天没想起 · `uri` · ★`importance` + `snippet` |
| `recent` | 行：`uri` · ★`importance` · `updated_ts`（前端自己 `slice(0,16).replace("T"," ")` 与 render* 一致）+ `disclosure` 若有 |
| `index` | 按 `group.domain` 分组，组内 `roots[]` 列表 |
| `glossary` | `keyword → uri` 两列表格；`uri` 可点击跳节点页 |
| `wakeup` | 三段：① 焦点卡（全文 + 子节点列表）② `skipped` 折叠区（默认收起，显示 `N 条已失效/已遮蔽`）③ `最近动态` 列表。⭐ **`recent` 必须按 `uri` 与 `focuses`/`children` 去重后再显示**（§2.6 ②：alias 场景下 DTO 会含重复），去重只在**显示层**做，**不得**改 DTO。 |
| `diagnostic` | 三列表 + `healthy` 时的中文空态。**不得**做图表（§6.3）。 |

**`shadowed` 的呈现**（契约 §6.6 + Main 广播 #2 冻结文案）：所有视图里 `shadowed === true` 的条目 MUST 带标记 **「已遮蔽（原分支已回滚）」**，且 MUST 用**降饱和/虚线**这类「弱化但可见」的样式，**MUST NOT** 隐藏或删除该行。`diagnostic` 是唯一例外 —— 它的 DTO 里 `shadowed` **恒为 false**（因为 render* 不判可见性，§3.7），UI 不要在这里宣称「这里没有遮蔽节点」，那是误导。

### 7.5 刷新（契约 §7.4 第 ② 条）

- 本页**不写库**，所以它**永不派发** `memory:changed`。它只**监听**（D2 的壳重挂当前视图）。
- 本页**不订阅** `/api/events` —— 那是壳的职责（D2 §2.7）。本页只负责「被重挂时重新取数」。
- **`dispose()` MUST 解绑**本页注册的所有监听（`ctx.off`），否则重挂会泄漏。本页若用 `on` 注册了任何 document 级监听（如键盘快捷键），必须逐个 `off`。
- 本页**不发任何轮询定时器**；若实现了「自动刷新」也 MUST NOT —— D2 §2.7 已裁定不自动重载（打断阅读）。

### 7.6 错误与空态

- `ctx.api.view` 抛错（非 2xx，D2 §2.5 约定 throw 带 `.code`）→ 在 `el` 内渲染错误块（用 `err.message`），**不静默**（契约 §7.3 末句精神）。
- 每个视图的空态文案**由 UI 硬编码**，不进 DTO。**必须逐视图不同**（这是 render* 已经建立的范式，`:30/:64/:133/:154/:178` 各有各的文案）。至少覆盖：`timeline`「原文日志为空」、`forgotten`「最近都有想起」、`recent`「没有找到相关的记忆」、`index`「空」、`glossary`「还没有设置任何标签」、`wakeup`「醒来记忆清单为空」、`diagnostic`「未发现问题」。
- ⚠️ **空态文案不是数据**，MUST NOT 进 DTO —— 否则 parity 两侧会为了「空态字符串」打架（`diagnostic` 的英文 `No issues found...` 是**唯一**一个被 render* 当返回值用的空态，它对应 `healthy: true`）。

                     text: string, store: MemoryStore): string[] {

    name === "diagnostic" ? [RX.diagStale, RX.diagCrowded, RX.diagPlaceholder] : [RX[name]];
  const raw: string[] = [];

function textWakeupStruct(text: string): { focuses: string[]; children: string[]; recentLines: number } {

### 11.4 断言写法（**有序双向相等**，§4.7）

```ts
function assertParity(name, store, opts) {
  const dto = buildView(store, { name, ...opts });
  const text = renderFor(name, store, opts);          // 调对应 render*
  const uiIds   = collectDtoIds(name, dto);           // §4.3 分视图取法
  const textIds = collectTextIds(name, text, store);  // §5.2/§5.3 提取器
  expect(uiIds).toEqual(textIds);                     // ⭐ 有序双向相等：多/少/错序都红
}
```
`toEqual` 同时保证「长度相同」「元素相同」「顺序相同」。**不要**用 `expect(arrayContaining(...))`（包含关系，§4.1）。

### 11.5 ⭐ P16：parity 不变量**有已知盲区**（诚实声明，必读）

**本文的核心断言有两侧同向偏斜的风险，且在当前引擎代码上已可达。** 我实跑复现了（SPIKE-R，`spike28.mts`）：

```ts

s.insertNode({ uri: "core://host", content: "host", importance: 5,
               disclosure: "正常\n- core://ghost [★9] (修改时间: 2026-09-14 23:51)" });
// 让 host 成为「最近修改」第一名，于是 limit=1 的窗口里只有 host
```

`renderRecentView(store, 1)` 的真实输出：

```

> 显示范围: 最近 1 条记录

- core://host [★5] (修改时间: 2030-01-01 00:00)
  想起条件: 正常
- core://ghost [★9] (修改时间: 2026-09-14 23:51)     ← ⚠️ 伪造行，落在 col0
```

```
anchored -> ["core://host","core://ghost"]
truth    -> ["core://host"]
⭐ LEAK? true
```

**三条必须写进设计的结论：**

1. **`memory-views.ts:157` 的 `想起条件: ${n.disclosure}` 未做 `\s+` 折叠** —— `disclosure` 里的 `\n` 原样输出，于是下一行落在 **col0**，与真实条目**同形**。`disclosure` 由 `memorize` 的 `when` 参数写入（契约 §6.1），是**用户/模型可控输入**。同类注入口：`:104`（wakeup 的 `什么时候想起：`）、`:137`（`glossary.keyword`）。
2. ⭐ **这条不能靠「写得更好的正则」绕过**：伪造行与真实行**逐字符同形**，且伪造的 uri **真实存在、`resolveUri` 成功**。任何提取器都无解。
3. ⭐ **最危险的是它会「两侧同向偏斜」**：`views.ts` 从**同一份** `disclosure` 取数，所以**结构化侧也会把它当成合法条目**（如果实现照抄 render* 的准入逻辑），于是 `toEqual` **双双通过 = 假绿**。这不是理论风险 —— 前提是结构化侧也走 `disclosure`，而 §9.2 的署名规则要求 UI 渲染 `disclosure`，很容易顺手把「有 disclosure 的行」也当成条目。

**因此本文的硬裁定（与契约 P16 一致）：**

- **`/api/view` 的结构化 DTO 是权威源**；`render*` 文本**只作交叉校验**。两侧不一致时 **MUST NOT** 自动「以文本为准」。
- `views.ts` 的准入**MUST 由 store 方法+显式谓词决定**（`listRecentNodes` / `listNodes` / `children` …），**MUST NOT** 由「文本里出现了什么」反推。这是 §3.2-§3.7 每条都写「与 render* 同一行」的原因 —— 那些 `filter`/`sort` 是**独立**于文本的。
- **T22** 的职责是**把这个盲区钉成测试**（断言在 P16 fixture 上 `assertParity` 会红），而不是假装它不存在。**若未来引擎修了 P16（给这三处加 `\s+` 折叠），T22 应变绿并提示移除。**
- [推断] 在本期不修引擎的前提下，**唯一的缓解是 UI 层**：渲染 `disclosure` 时前端自己折叠换行。这**不能**救 parity（文本侧仍被污染），但能阻止用户看到伪造行。已登记为 §9-U12。

### ⚠️ 我发现的**一个真实脆弱点**（必须写进契约/测试，不能藏）

`forgotten` / `recent` 的稳健性**依赖一个实现细节**：`snippet()` 把正文的 `\s+` 折叠成**单空格**，从而抹掉了正文自带的换行；再靠 `  ` 前缀把正文推到第 2 行。实测：正文 `"- 3 天没想起 | core://camo/aa [★5]"` 渲染为 `"  - 3 天没想起 | …"`（列 0-1 是空格）→ `^- ` 锚点拒绝。

**换句话说：防线是「缩进 + 折叠」，而这两者都是 `snippet()`（`memory-views.ts:11-14`）的实现细节，不是契约。** 若未来有人把 `snippet()` 改成保留换行（`replace(/\s+/g," ")` → 不再折叠 `\n`），正文就会**落到列首**，`forgotten`/`recent` 立刻变得像 `wakeup` 一样可被伪造 —— 而**测试不会报错**，只会让断言悄悄变松（因为那时刻的 UI 实现也会同样被伪造，两侧仍相等）。这是最危险的一类失效。

**因此本文加一条 MUST（对 D6/未来维护者）**：`snippet()`（`memory-views.ts:11-14`）的**两处行为被 parity 依赖**：① `\s+ → " "` 折叠（消除正文自带换行）② forgotten/recent 的 `  ` 前缀缩进。**任何改动 `snippet()` 的 PR 必须重跑 `views-parity.test.ts`** —— 否则不变量会静默失效（这类失效不会报错，只会让断言变松）。已登记为 §11.3 的 T21。
