## 1. 一句话定位

**D5 是这套系统里唯一"能让用户把库写坏"的模块。**

前四个模块（D1–D4）错了，用户看到错的信息；D5 错了，用户的记忆**没了**——而且是不可逆地没了，因为这个库的设计里 `deleteCascade` 会**真的物理删除节点行**（`store.ts:577`），只把正文归档进 `node_revisions` 作为唯一找回路径（`store.ts:571-576`，决策 10 v5.4）。

因此在"独立 HTTP 服务直接接受写请求"（契约 §1.2 路线决策）这个前提下，D5 的定位是**三重约束的收敛点**：

| 约束 | 来源 | 本模块的落地 |
|---|---|---|
| **不可绕过的写入通道** | §9.1 纪律 2 | 所有写操作 MUST 经 `MemoryStore` 方法；`edit.js` 只发 HTTP，绝不持有数据库 |
| **不可伪装的署名** | §9.1 纪律 3 + §9.2 | 人类编辑恒为 `source='manual'` / `editor_source='manual'` / `editor_model=null`；UI 渲染为"用户（Web UI）" |
| **不可省的确认** | §9.3 | forget / restore / relocate / world-time 四类操作各有强制的界面约束 |

一句话：**D5 交付的不是"能编辑"，是"能安全地编辑"。** 用户按下删除之前，界面必须已经告诉过他"这东西还能不能找回来、怎么找回来"。

## 2. 编辑入口与信息架构

### 2.1 写入动作 → 入口页面 → 归属

| 写操作 | 入口（用户看到的） | 页面归属 | D5 的交付 |
|---|---|---|---|
| 新建节点 | 树页/节点页的"新建"按钮；**待回填占位节点**（D4 diagnostic 的 Placeholder 分类）上的"回填"按钮 | D2 | `createNode()` 原语 + 表单校验 |
| 改正文 | 节点页"编辑正文" | D2（页面）/ D5（面板行为） | `edit.js` 的编辑面板 |
| 改重要度 | 节点页重要度控件（就地改，无需进编辑态） | D2 | `reviseNode({importance})` |
| 改想起条件（`disclosure`） | 节点页"想起条件"字段 | D2 | `reviseNode({disclosure})` |
| 改节点世界时间（`world_ts`） | 节点页详情里的世界时间字段（与"世界钟"**不是一回事**，见 §4.8） | D2 | `reviseNode({world_ts})` |

| 恢复历史版本 | 节点页"修订史"面板的"恢复此版" | D2（面板）/ D5（动作） | `restore()` + diff 组件 |
| 移动/改名 | 节点页"移动"；批量移动 | D2 | `relocate()` + 前警告 |

### 2.2 模块边界（与 D2/D3/D4 的接缝）

**D5 不拥有任何页面。** D5 拥有的是：

1. `assets/views/edit.js` —— 一个**可被路由挂载**的编辑面板（满足 D2 广播的视图模块契约 `mount(el, params, ctx) → dispose()`）；
2. 同一文件导出的**写操作原语**（`reviseNode` / `forgetNode` / `restore` / `relocate` / `addGlossary` / `removeGlossary` / `awaken*` / `setWorldTime` / `createNode` / `addEdge`）与**危险动作组件**（`confirmForget` / `showDiff`）。

**为什么原语放在 `edit.js` 而不是新开 `assets/write.js`**：契约 §3 的文件布局是**冻结**的，`assets/` 下只有 `index.html` / `app.js` / `views/*.js` / `app.css` / `vendor/`。新开文件要回契约 §7.1 同级流程广播。而 ESM 允许 `views/temp.js` 写 `import { reviseNode, forgetNode } from "./edit.js"`——**零布局变更**。故本设计采用**跨视图模块 import**，不新增文件。（若主 agent 更倾向独立 `assets/write.js`，D6 的 `copy-assets` 配方 `shx cp -r src/web/assets/. dist/web/assets/`（D6 §4.2）天然覆盖平级文件，切换成本为零。）

**编入 D2 的 `ROUTES` 表**：D2 维护该表（主 agent 广播 #5）。D5 申请的条目为：

```js
edit: { module: "./views/edit.js", params: ["uri", "mode"] }
```

`mode` ∈ `"create" | "revise"`。**在没有 D2 的 shell 时，`edit.js` 也 MUST 能独立 `mount`**（便于冒烟）——这不额外要求，因为 `mount(el, params, ctx)` 本身就不依赖 shell。

### 2.3 写后刷新契约（⭐ 落实契约 §7.4 第②条）

契约 §7.4 已修正：`PRAGMA data_version` 是**每连接**计数器，**服务端自己的写入自己看不见**。因此：

- **每一个写操作成功后，`edit.js` MUST 广播**：
  ```js
  document.dispatchEvent(new CustomEvent("memory:changed", { detail: { route, uri } }));
  ```
- **MUST NOT** 依赖 `/api/events` 轮询来发现本次写入。`/api/events` 的职责被契约限定为"发现**外部**改动"。
- 广播前，写客户端 MUST 已经拿到服务端返回的对象（或已重新拉取），**不得**用本地乐观状态冒充服务端状态。
- D2 的 shell 收到事件后重挂当前视图。因此编辑面板的"是否处于编辑态"这一状态 **MUST 能从路由参数推断**（`#/node?uri=...&edit=1`），这样重挂后用户不会被弹回只读态。

### 3.2 副作用对表（D1 实现时的机械核验项）

以下四条**可机械核验的不变量**，D1 的 `test/web/api.test.ts` MUST 直接断言（我已实跑确认全部成立）：

**I1（内容写必然产修订 + 审计）**：对任意非 stub 节点，`updateNode(id, {content: X})` 且 `X !== 当前正文` ⟺ 恰好多 **1** 条 revision、恰好多 **1** 条 `update_node`。
（实跑 D：`update_node` 1 条，revDelta 1。⚠️ 例外：stub 升格走 `promote_stub` 且 revDelta = 0。）

**I2（非内容写必然零副作用）**：`updateNode(id, {importance|disclosure|world_ts})` ⟹ revDelta = 0 **且** 审计行数 = 0。
（实跑 21 号：`disclosure only` / `world_ts only` / `importance only` 三行均为 `audits: 0, revDelta: 0`。）

**I3（删除的审计条数 = 被删节点数）**：`deleteCascade(id)` 返回 `n` ⟺ 新增 `n` 条 `delete_node` 审计。
（实跑 S：count 2，审计 2 条。实跑 AB 显示顺序是**子先父后**。）

**I4（relocate 的 alias 集合 = 被移动的旧 URI 集合）**：`relocateMany([{from,to}])` 成功后，`aliases` 表中新增的 `alias_uri` 集合 === `{from}`（多成员子树时 === 每个成员的旧 URI）。
（实跑 I：`aliases = [{"alias_uri":"core://a",...}]`。）

### 3.3 三条「前端 MUST 知道」的行为（否则会做出错误的界面反馈）

**(a) `put` 与 `updateNode` 的成功返回不同**：`put` 返回 `MemoryNode`（`:273`/`:277`），`updateNode` 返回 `number`（版本号，`:391-393`）。D1 的 `POST /api/node/revise` **MUST** 在响应里同时给出 `{ node: <DTO>, version: number }`，否则前端无法判断"这次到底有没有产生新版本"（W2b 会返回旧版号）。

**(b) 「保存成功」不等于「产生了修订」**：用户把正文原样保存（W2b/W1d）时 store 完全静默。界面 MUST 区分三种成功文案（**含 `version === 0`，见下**）：

```text
version >= 1          → "已保存，归档为 v{N}"
version === 0 且原为 stub → "已保存：占位节点已提升为正式记忆"   ← 合法成功，不是错误
version === 0 且原非 stub 且正文未变 → "内容未变化，未产生新版本"
```

这一条直接源于 I2 与 W1c/W2c，且是用户能亲眼验证的（点开修订史看不到新版）。

⭐ **`version === 0` 不是错误**（契约 §16.10b，主 agent 复现）：`updateNode` 对 **stub 提升**（`is_stub=1` 且写 `content`）走**独立分支**（`store.ts:316-324`）——覆盖空正文、**不产 revision**、记 `promote_stub` 审计、**`return 0`**（`:323`）。复现：`put("core://x/y/z")` 造出 stub 父链 → `updateNode(stub, {content})` 返回 **`0`**、`is_stub` 变 `0`、`currentVersion` **仍为 0**。

⇒ **D5 MUST**：编辑面板只在 `conflict`(409) / `bad_request`(400) 时报错（§4.0）；**`version === 0` MUST 走成功分支**。把 0 当失败会把**合法的 stub 回填误判为错误**——而 stub 回填正是 D4 diagnostic `Placeholder` 分类的主推动作（§4.1）。

**(c) 一次 `put` 可能产生多条审计**：新建 `a://b/c/d` 会先补 stub 祖先（W1e），审计里出现 3 条 `insert_node`。UI 的 toast **MUST NOT** 说"已创建 1 条记忆"——只能说"已保存：a://b/c/d"。审计条数不是用户语义单位。

## 4. 各写操作的前端交互契约

> 本节是 `edit.js` 的实现规格。所有请求经 D1 的 `fetch` 封装；错误响应形状为契约 §7.3 的 `{error:{code,message}}`。
> 通用状态机（所有写操作共享）：

```text
idle ──submit──▶ submitting ──ok──▶ refresh + toast ──▶ idle
                     │
                     └──err──▶ error（保留表单输入） ──retry──▶ submitting
```

**MUST**：`submitting` 期间禁用提交按钮并阻止重复提交（防止双击产生两次 `forget`）。**MUST NOT**：`submitting` 期间清空表单——用户输入是唯一的真相，丢了它等于丢了用户的编辑。

#### 4.0 ⭐ 错误码分流：`bad_request` vs `conflict`（契约 §7.3，7 码集）

契约 §7.3 的错误码集为 **7 个**（广播 #8 新增 `conflict` / HTTP 409）。D5 的**所有写操作** MUST 按下表分流，**MUST NOT** 把"地址被占用"当成"表单填写有误"：

| code | 触发（本模块相关） | 原始错误文本 | 证据 | UI 文案与引导 |
|---|---|---|---|---|
| `bad_request` | 参数缺失/非法、时间格式错 | — | 实跑 MA/MB | 表单内联错误 |
| ⭐ `conflict` (409) | `insertNode` 同 uri | `UNIQUE constraint failed: nodes.uri` | 主 agent 实测复现 | "该地址已被占用，请换一个 URI 或先处理原节点" |
| ⭐ `conflict` (409) | `relocateMany` 目标被占 | `relocate: target occupied by <uri>` | `store.ts:652` | "目标地址已被 **{占用者}** 使用，请换目标或先处理它" |
| ⭐ `conflict` (409) | `restoreDeleted` 目标存活 | `restoreDeleted: <uri> still exists` | `store.ts:511` | "该地址仍在使用中，无法从归档恢复；请换地址或先删除现有节点" |
| ⭐ `conflict` (409) | 恢复时 `node_id` 已被复活（P14） | `UNIQUE constraint failed: nodes.node_id` | 实跑 SC/W4d | "该记忆已在另一地址下恢复过" |

**产品含义（MUST 体现到文案）**："地址被占用" ≠ "参数有误"。前者用户**能自己解决**（改地址 / 先删），后者只能改输入。把 409 显示成"表单填写有误"会让用户在错误的输入框里反复挠头。

⚠️ **`put` 不是 conflict**：`POST /api/node` 对同 uri 是 **upsert 覆盖**（`store.ts:258-274`；实跑 MG 返回新正文 `OVERWRITE`、不报错）。**D1 的实现 MUST NOT 写成"先查再抛 conflict"**——那会把 W1b 的覆盖语义变成拒绝，破坏 `createNode()` 的"覆盖保护"设计（§4.1，前端靠自己的确认框处理，不靠服务端报错）。`UNIQUE constraint failed: nodes.uri` 只可能来自 **`insertNode` 被直接调用**的路径（例如恢复时重建），常规 `POST /api/node` 到不了这里。

### 4.1 `createNode()` — 新建 / 回填占位节点

| 项 | 规格 |
|---|---|
| 路由 | `POST /api/node` |
| 请求体 | `{ uri, content, parent_uri?, importance?, disclosure?, world_ts? }` |
| 前端校验 | `uri` 非空、含 `://`、无空白字符 |
| ⭐ 覆盖保护 | 提交前 MUST 先 `GET /api/node?uri=`；**若命中且 `is_stub === 0`**，弹确认："`{uri}` 已存在，继续将覆盖其正文（旧正文会归档为修订）。" —— 因为 store 层的 `put` 是 upsert（`:258-274`），**不会拒绝**覆盖（实跑 MG：`b` → `OVERWRITE` 无阻力）。这是唯一防线。 |
| 成功 | 广播 `memory:changed`（`detail.uri` = 新 URI），跳转 `#/node?uri={uri}`，toast "已创建：{uri}" |

### 4.6 加关联边（`addEdge()`）

| 项 | 规格 |
|---|---|
| 路由 | `POST /api/edge` |

| ⭐ 目标不校验 | store 不检查 `target_uri` 是否存在（P4；`schema.ts:45-50` 无 FK；实跑 DC：`core://ghost` 写入成功）。前端 MUST 先 `GET /api/node?uri={target}`，悬空则弹确认："目标 `{target_uri}` 不存在，边将悬空显示。" |

⭐ **MUST 先分清两个概念**（用户最容易混淆处）：

|---|---|---|---|

### 4.9 删节点（`forgetNode()`）— ⭐ 最高危

| 项 | 规格 |
|---|---|
| 路由 | `POST /api/node/forget`，体 `{ uri }` |
| ⭐ 二次确认（契约 §9.3） | MUST 弹模态确认，内容 MUST 包含三要素：<br>① 将要删除的 URI 与**子树规模**（"将删除 N 条记忆"，N 由 `GET /api/node` 的 children 递归估算或由 `GET /api/tree` 数）；<br>② 明确文案"**修订史会保留**"；<br>③ 明确给出找回路径"可从『恢复已删记忆』页（`/api/revisions?deleted=1`）恢复"。 |
| ⭐ 不可逆性如实告知 | 语气 MUST NOT 软化。库的语义是**真删**（`store.ts:577` 物理删行；决策 10 v5.4），恢复**只靠修订史**，且恢复**只恢复正文**——`importance` / `disclosure` / `world_ts` 都不在 revision 里（`node_revisions` 只存 content，`schema.ts:34-43`；实跑 TA：恢复后 importance 回 5、disclosure 回 null）。确认框 MUST 写明这一点。 |

### 4.10 恢复（`restore()`）— 本设计新增的写操作页

契约 §7.1 的 `POST /api/node/restore` 承载**两种**语义，前端 MUST 用不同入口、不同确认：

#### 4.10.1 恢复已删记忆（`restoreDeleted`）

| 项 | 规格 |
|---|---|
| 路由 | `POST /api/node/restore`，体 `{ uri, version? }` |
| 列表来源 | `GET /api/revisions?deleted=1` → `listDeletedUris()`（`store.ts:488-498`），字段 `{uri, versions, last_seen}` |
| ⭐ 恢复的是"那一版正文"，不是"那条记忆" | 恢复**只带回 content**：`importance`/`disclosure`/`world_ts` 全部回落默认/当前世界钟（`restoreDeleted` 的 `_insertNode({uri, content, source:"import"})`，`:534`；实跑 TA）。确认框 MUST 写明。 |
| ⭐ 恢复后的 `source` 变成 `"import"` | `:534` 硬编码 `source: "import"`。UI 详情页的署名会显示 "import" —— 这是**真实的**（"这条记忆是从归档里重建的"），D5 MUST 在成功 toast 里解释："已从修订史恢复（来源标为 import）。" |
| ⭐ 同名多行陷阱 | 一个 URI 如果在 relocate 后又被删，`listDeletedUris` 会**同时**出现旧 URI 与新 URI 两行，且两行背后是**同一个 `node_id`**（`node_revisions.uri` 逐行不同，`schema.ts:37`；实跑 OA：两行同 id）。UI MUST 把这种情况标注为"同一记忆的多个历史地址"，否则用户会以为有两份。 |
| ⭐⭐ 恢复顺序陷阱 | 级联删除的子树若**子先恢复**，`restoreDeleted` 会为该子的父 URI **自动补一个 stub 祖先**（`:535`），从而**阻塞父的恢复**——因为父的 URI 已被 stub 占用，`restoreDeleted` 抛 `still exists`（实跑 QC）。**UI MUST 强制"父先子后"**：恢复列表按 URI 段数（深度）升序排列，且对"父尚未恢复的子"禁用恢复按钮并提示"请先恢复其父 `{parentUri}`"。这是本设计里最容易让用户"点错顺序就把自己堵死"的地方。 |
| 父先子后验证 | 实跑 RA/RB：按浅→深顺序恢复，`node_id` 全部保留、树边正确重连。 |
| 恢复孤儿子 | 子先恢复虽然会补 stub 父（实跑 QA：`is_stub=1`，`node_id` 是**新的**），随后父恢复被拒；此时唯一的出路是恢复**父的父 URI**（如果存在）或先 `forget` 那个自动 stub。D5 MUST 在确认框里警告这一点，**不提供**"自动修复"按钮（那会引入新的隐式删除风险）。 |
| 成功 | 广播 `memory:changed`；跳转 `#/node?uri={uri}`；toast 见上 |
| 错误 | `conflict`（409）→ "该地址仍在使用中，无法从归档恢复；请换地址或先删除现有节点"（`still exists`，`store.ts:511`）；`conflict`（409）→ "该记忆已在另一地址下恢复过"（`UNIQUE constraint failed: nodes.node_id`）；**两者都 MUST NOT 透出原始 SQLite 英文文本**（D1 映射，见 §4.0 与 §7.3 第 4 条） |

#### 4.10.2 恢复历史版本（`restoreRevision`）

| 项 | 规格 |

| ⭐ diff 前置（契约 §9.3） | MUST 显示"将被覆盖的当前内容 diff"：`GET /api/revisions?uri=`（需含 `content`）与 `GET /api/node` 的当前 `content` 做行级 diff。确认文案："恢复 v{N} 会**覆盖当前正文**（当前正文将归档为新版本，仍可回退）。" |
| ⭐ 不是删除 | 恢复旧版**不丢**当前版——`_updateNode` 把当前正文归档为新 revision（`:330-336`；实跑 AA/H：revs 变 [1,2]，v2 是恢复前的内容）。文案 MUST 让用户安心："旧版本会保留。" |

| 错误 | `no version N for X`（实跑 BF）→ 内联错误 + 刷新修订史（版本可能已被 retention 裁掉，`store.ts:425-434`） |

### 4.11 移动 / 改名（`relocate()`）

| 项 | 规格 |
|---|---|
| 路由 | `POST /api/node/relocate`，体 `{ moves: [{ from, to }] }` |
| ⭐ alias 提示（契约 §9.3） | MUST 在提交前提示"旧 URI `{from}` 会保留为 alias，旧地址仍可解析"。这不是缺陷，是设计（`store.ts:677-679`）。 |
| ⭐ 断边警告（P1，**已裁定：阻塞式**，见 §8.1 / 契约 §12-P15） | MUST 弹**阻塞式确认**（用户勾选后才可提交），文案含两点：① 指向该节点的关联边将不再显示（引擎缺陷，已知）；② 修复办法 = 移动后对受影响目标重新「保存关联」（`addEdge` 会 upsert 覆盖）。 |
| 冲突预检 | store 的冲突检查是**原子且先于写入**的（`:625-655`），一次冲突整批回滚、零变更（实跑 ME/MF）。UI **MUST** 把后端冲突错误翻成用户可读文案，逐类映射：<br>`unknown uri` → "源地址不存在：{X}"<br>`target occupied by` → "目标地址已被占用：{X}"<br>`nested inside source` → "不能把节点移进它自己的子树"<br>`sources overlap` → "两个源互相包含，无法同时移动"<br>`targets collide` → "两次移动的目标冲突：{X}" |

| 批量语义 | 一次请求 = 一个事务（`:600`）。UI MUST 支持多行编辑（每行 from→to），并**在提交前**做前端侧的"源重叠 / 目标重复"预检，避免必然失败的整批提交 |
| 子树规模提示 | 移动会改写整个子树（`:664-675`）。确认框 MUST 显示"将移动 N 个节点（含子树）"——N 由 `GET /api/tree?parentUri={from}` 数出 |
| 成功 | 广播 `memory:changed`（D4 的 wakeup 页因前缀 remap 会变，实跑 ED）；跳转 `#/node?uri={to}`；toast "已移动 N 个节点：`{from}` → `{to}`" |
| 错误 | `conflict`（409，目标被占 `store.ts:652`）→ "目标地址已被 {占用者} 使用，请换目标或先处理它"；`bad_request` → 上表逐类文案；**无部分成功的可能**（事务，`:600`）。⚠️ 冲突**不是** `bad_request`（见 §4.0） |

### 4.12 整理 TEMP（D3 页面的写动作）

TEMP 页的"整理"**没有专属端点**——契约 §7.1 里没有 `/api/temp/*` 写路由。它由 D3 的页面用**已有的写原语**组合而成，目标 = **清到零**（契约 §10.1「动态区」）：

| 用户动作 | 实际调用 | D5 交付 |
|---|---|---|
| 把草稿归位 | `reviseNode({uri, content})` 改正文 + `relocate({from, to})` 移到正式域 | 两个原语，D3 组合 |
| 丢弃草稿 | `forgetNode({uri})` | 原语 + 高危确认 |
| 合并多条草稿 | **无端点** | 见 §12（D5 不做 consolidate） |

⭐ **D3 的责任边界**：D3 渲染列表与触发按钮，**D5 提供动作原语与确认流程**。D3 MUST NOT 自己拼 HTTP 请求。若 D3 发现需要新端点（如批量 forget），**回到契约 §7.1 流程**，不要私自在页面里循环调 N 次 `forget`——那会产生 N 次部分失败的可能，而 store 的 `deleteCascade` 是**每节点一个事务**（`:555`），没有跨节点的原子性。

## 6. 并发与竞态

### 6.1 三类并发源

| # | 源 | 机制 | 应对 |
|---|---|---|---|
| C1 | 同一用户的**两个标签页** | 各自持有 `current_version` | 版本号乐观锁（§6.2） |
| C2 | **agent 会话**正在写同一个库 | pi 进程持有**另一个** `DatabaseSync` 连接 | `/api/events` 轮询（D1）+ 版本复核（§6.2）+ 写后广播 |
| C3 | 同一页面**双击/重复提交** | `submitting` 未拦住 | 禁用按钮 + `AbortController` |

⚠️ **WAL 让 C2 变得隐蔽**：`driver.ts:29-30` 显式开 `PRAGMA journal_mode = WAL` 与 `busy_timeout = 5000`，两连接可并发读、写串行化。所以 C2 的典型表现**不是报错**，而是**静默覆盖**——agent 在你打开编辑面板的 30 秒里改了这条记忆，你点保存就把它盖掉了。这是 §6.2 存在的唯一理由。

### 6.2 版本号乐观锁（D5 的核心防覆盖机制）

**为什么必须做**：`updateNode`/`put` 都是**无条件写**（`store.ts:310-344`、`:257-278` 无任何版本校验）。store 层**不提供**乐观锁。

```text
1. 打开编辑面板 → GET /api/node?uri=X → 记 node.current_version = V0
2. 用户编辑（可能耗时很久）
3. 提交 → GET /api/node?uri=X → 得 V1
4. V1 === V0 → POST /api/node/revise（正常）
   V1 !== V0 → 阻断，弹三选
```

| 选项 | 行为 |
|---|---|
| 放弃我的修改 | 丢弃本地编辑，面板重载为 V1 内容 |
| 覆盖 | 提交我的版本。**确认框 MUST 说明"对方的 v{V1} 会归档为修订，可回退"** |
| 看差异 | diff（服务端 V1 正文 vs 我的本地正文），再决定 |

**两次 GET 之间的窗口仍在**（V1 之后理论上又可能变）。这是**故意接受**的：窗口从"整个编辑时长"缩到"两次 GET 之间的毫秒级"，成本/收益最优。完全消除需要服务端事务内版本比对（改 store），**违反"本期不修引擎"**。

**`current_version` 来源**：`store.currentVersion(nodeId)`（`store.ts:436-441`）。⚠️ `insertNode` 不产 revision，**新节点 `currentVersion` = 0**（实跑 CD）。D1 的 `/api/node` MUST 暴露 `current_version`（含 0）。D5 不实现乐观锁的**服务端**一半——它只是"先读后写"的客户端协议。

### 6.3 ⭐ 写请求必须串行化（服务端硬约束，本设计向 D1 提要求）

`MemoryStore` 是**单连接**（`driver.ts:28` 只 `new DatabaseSync(resolved)` 一次），而独立 HTTP 服务可能并发处理多个请求。`driver.ts` 的 `transaction()` 是**手写 `BEGIN`/`COMMIT`**（`:34-44`），**不是 savepoint，不可重入、不可嵌套**。

**实测**：事务内再开事务 → `cannot start a transaction within a transaction`。因此向 D1 提两条硬约束：

> **① D1 MUST 串行化所有写请求**（内部队列，一次一个）。
> **② store 的事务是单层，MUST NOT 嵌套**——D1 自己 MUST NOT 调 `store.db.transaction()`（即使 `store.db` 是 `readonly` 公开的，`store.ts:157`），也 MUST NOT 在事务内调 `await`。

⭐ **精确的失败条件**（不要写成笼统的"并发不安全"）：store 的每个写方法都**同步**且各自恰好包一层 `db.transaction()`（`put:253`、`updateNode:392`、`deleteCascade:555`、`relocateMany:600`、`restoreDeleted:510`）。JS 单线程 ⇒ 只要 (a) D1 不自己开事务、(b) 事务内不 `await`，两笔并发写就**不会**在事务内交错。**危险的不是"并发"，是"嵌套"或"带着事务 await"**。`search()` 是异步的（`recall.ts:350`），若有人把它塞进写事务就会炸——`/api/search` 是只读端点，别让它进写路径。

**为什么仍要串行化（即便交错不会发生）**：`busy_timeout=5000` 下，agent 进程与 web 进程抢写锁时，web 侧要**等最多 5 秒再抛 `SQLITE_BUSY`**。串行化 + 合理快速失败，比让用户等 5 秒后看到一个未翻译的英文错误好。D1 MUST 把 `SQLITE_BUSY` / `database is locked` 映射成契约 §7.3 的错误码（建议 `internal` + 中文 message，或新增无冲突的专用码时回契约 §7.3 流程）。

### 6.4 就地控件（重要度）的竞态

重要度是**防抖 + 就地提交**，与正文编辑不同：不做 V0/V1 复核（否则每次拨滑块都要两次 GET）。取而代之：`AbortController` 保证同一节点同时只有一个在途写；服务端返回值只有一个 `version`，**I2 保证它不变**（不产修订），故不需要版本比对；失败时从服务端重拉 `importance`（不信任本地值）。

⭐ 快速拨动会被防抖折叠成**最后一次**。这是**正确行为**（`importance` 是可覆盖标量），MUST NOT 为它做"操作队列"。

### 6.5 TEMP 整理的并发（D3 + D5）

TEMP 页可能显示 N 条草稿，用户逐条处理；期间 agent 可能也在写（`autoretain` 产物落进 TEMP）。⭐ **`deleteCascade` 是每节点一个事务，没有跨节点的原子性**（`:555`）。所以 D5 **MUST NOT** 为"整理"做"批量删除 N 条"的按钮——那会产生"删了 3 条、第 4 条失败"的半成品状态，而 TEMP 的目标是"清到零"（契约 §10.1），半成品比不做更糟。D3 的列表 MUST 逐条处理，D5 逐条确认。

## 7. 不可逆操作的兜底：误删恢复路径的完整走法

### 7.1 用户在页面上走的路

```text
节点页「删除」
   └─▶ 二次确认（§4.9）→ POST /api/node/forget → 节点行物理消失
          └─▶ toast:「已删除 N 条记忆，可在『恢复已删』页找回」
                 └─▶ 用户点 toast 里的链接 / 打开恢复页
                        └─▶ GET /api/revisions?deleted=1  → listDeletedUris()
                               └─▶ 选一条 → POST /api/node/restore { uri }
                                      └─▶ restoreDeleted() 重建节点
```

### 7.2 恢复路径的**硬保证**与**硬限制**（MUST 全部写进 UI 文案）

| 保证 | 证据 |
|---|---|
| 删掉的**正文**一定找得回（最后归档的那一版） | `deleteCascade` 调 `archiveRevision(node.content, ...)`（`:575`）并把 `uri` 补进该行（`:576`） |
| 找回后 **`node_id` 不变**，修订史重新接上 | `_insertNode(..., forceId = rev.node_id)`（`:534`；实跑 BG/HF） |
| 找回后树位置自动重挂 | `ensureStubAncestors` + 隐含父 relink（`:535-538`；实跑 RB） |

| 限制 | 证据 |
|---|---|
| **重要性 / 想起条件 / world_ts 找不回** | revision 只存 content（`schema.ts:34-43`）；实跑 TA：恢复后 importance 5、disclosure null |
| **`source` 变成 `import`** | `:534` 硬编码；实跑 TA/HF |
| **级联删除的子树要逐条恢复** | `restoreDeleted` 只重建单节点；实跑 JD/JE：父恢复后子仍在 deleted 列表 |
| ⭐ **必须父先子后** | 子先恢复会补 stub 父、**堵死**父的恢复（实跑 QA/QC） |
| **relocate 过的节点有两个「已删 URI」** | `node_revisions.uri` 逐行携带（`schema.ts:37`）；实跑 OA：两行同 `node_id` |
| ⭐⭐ **从旧 URI 恢复会拿回旧正文**（**静默数据错误**，不报错） | 实跑 NB/NC：从 `core://old` 恢复得 `V1-CONTENT`，从 `core://new` 恢复得 `V2-CONTENT` |

### 7.3 ⭐⭐ 本模块发现的**第二高危陷阱**：relocate → delete → restore

**完整复现**（`/tmp/d5/probe16.mjs`、`probe22.mjs`）：

```text
1. insertNode({uri:"core://old", content:"V1"})        → 节点 n，v 无 revision
2. updateNode(n, {content:"V2"})                       → 归档 v1(content=V1, uri=old)
3. relocateMany([{from:"core://old", to:"core://new"}])→ 节点 uri=new；alias old→n
4. deleteCascade(resolveUri("core://new").node_id)     → 归档 v2(content=V2, uri=new)
   结果：listDeletedUris() = [{uri:"core://new",...}, {uri:"core://old",...}]  ← 两行，同一个 node_id
5. restoreDeleted("core://old")  → 成功，但 content = "V1"（旧正文！）url = core://old
   此后 listDeletedUris() = []（node_id 已复活），「core://new」这一行也消失了
6. restoreDeleted("core://new")  → 抛 UNIQUE constraint failed: nodes.node_id
```

**为什么危险**：用户在恢复页看到的是两个看起来无关的 URI（一个是他的删除目标 `core://new`，一个是历史地址 `core://old`）。如果他点了那个"看起来也能点的"旧行，会：

1. **拿到一份旧正文**（他的编辑成果 V2 看起来"丢了"）。⭐ 这是**静默数据错误**——不报错、界面还显示"恢复成功"，比抛错更危险；用户无从察觉自己拿回的是改名前的版本。
2. **把 `node_id` 占住**，导致从正确 URI 恢复时报一句**未包装的英文 SQLite 错误**。

⭐ **复现的前置条件（主 agent 复核时专门标注）**：本陷阱**依赖"该节点被编辑过"**。若 `put()` 之后从未 `updateNode`，`node_revisions` 为空，`listDeletedUris()` 不会冒出旧 URI 那一行（`deleteCascade` 归档的那一版带的就是当前 URI）。**写验收测试（§11-T7b）时 MUST 先编辑一次再 relocate**，否则复现不出来。

**D5 的处置（四条 MUST）**：

1. **恢复页 MUST 按 `node_id` 把同源行分组**（D1 的 `/api/revisions?deleted=1` MUST 暴露每行的 `node_id`），显示为"`core://new`（另有历史地址 `core://old`）"。
2. ⭐ **每组默认只对「最新 URI」那行开放恢复按钮**（最新 = 该 `node_id` 的 revision 中版本号最大的那一行的 `uri`）；旧 URI 行 MUST 加警示文案"**历史地址：从此处恢复会拿回改名前的旧正文**"，并默认折叠为只读。**这是本陷阱唯一的产品级防线**——顺序/文案错了，用户就会踩中静默错误。
3. **降级方案**（若 D1 未暴露 `node_id`）：只对每个分组里 `last_seen` 最大的那行开放恢复，其余折叠。
4. **D1 MUST** 把 `UNIQUE constraint failed: nodes.node_id` 与 `restoreDeleted: ... still exists` 都映射成契约 §7.3 的 **`conflict`（409）** + 中文 message（**MUST NOT** 透出原始 SQLite 英文文本；契约 §7.3 "MUST NOT 静默降级"）。D5 只提出**必需的字段**（`node_id`）与**必需的文案**。⇒ 与 §4.0 的错误码分流表一致。

### 7.4 兜底的兜底（当恢复路径本身失效时）

| 场景 | 出路 | D5 的 UI |
|---|---|---|
| 修订史被 retention 裁光（`store.ts:425-434`） | **无**（数据真没了） | 恢复页在 `versions === 0` 时不可能出现（`listDeletedUris` 基于 revision 表）；但**改 `maxVersionsPerNode` 后**旧版本的消失要在恢复页如实反映——`versions` 字段来自 `listDeletedUris` 的 `COUNT(*)`（`:491`），已经很诚实 |
| URI 被 stub 占住（父先子后违规） | 恢复**更外层的父 URI**，或先 `forget` 那个 stub | 确认框警告 + 提示父 URI；**不提供自动修复**（§4.10.1） |

## 8. 与现状差异 / 发现的冲突

### 8.1 ⭐ P1（`relocateMany` 不重写 `edges.target_uri`）—— **本模块必须回答的产品问题**

**契约 §12-P1 的事实**：`relocateMany` 从不重写 `edges.target_uri`（`store.ts:604-689` 无 edges 处理；对比 `deleteCascade` 有，`:568`）。

**我实跑确认了比 P1 原文更严重的一层**（`/tmp/d5/probe13.mjs`）：

```text
KA. incoming before relocate: [{direction:"incoming", node_id:src, target_uri:"core://target", kind:"refs"}]
    relocateMany([{from:"core://target", to:"meta://target"}])
KB. incoming AFTER relocate : []        ← 边"消失"了
KC. edges 表原始行还在      : [{node_id:src, target_uri:"core://target", kind:"refs"}]
```

即：`edges` 行**没被删**，但 `listRelated(target)` 是按 `edges.target_uri` 等值匹配节点的**当前 `uri`** 来查 incoming 的（`store.ts:772-779`）。节点已改名，所以**再也匹配不上**——incoming 边**静默消失**，而 `edges` 表里留着一条指向旧地址的僵尸行。`relocate` 的审计也只记 `rename_node / "moved N nodes"`（`:683-687`），**完全没提边**（`/tmp/d5/probe13.mjs` KD）。

**这不是"显示旧地址"（契约 §12-P1 的措辞），是"显示不出来"。**

✅ **已裁定（主 agent，2026-09-15，契约 §12-P15）：采纳本建议，且升级为阻塞式确认。** relocate 确认框 MUST 要求用户**勾选后才能提交**，文案含两点：① 指向该节点的关联边将不再显示；② 修复办法 = 对每个受影响目标重新 `addEdge`（会 upsert 覆盖，`store.ts:758`）。

```
⚠️ 移动后，其它记忆指向 "{from}" 的关联边将不再显示。
   （已知引擎缺陷：relocate 不更新边的目标地址。数据不会丢，但界面上看不到。）
   受影响：{N} 条边（由 GET /api/node 的 edges incoming 数出）
   [ ] 我明白，并会在移动后重新保存这些关联
```

⭐ **以上计数 N 的取数口径（契约 §16.1）**：`GET /api/node?uri={from}` 的 `edges[]` 里筛 `direction === "incoming"`，取 `.length` 即 N。**不能用** `target_uri` 匹配 —— `EdgeDTO` 的 `node_id`（边的源）才是可用字段，`target_uri` 是裸值（P1/P15）。若 `dangling === true` 的 incoming 边被算进 N，务必在文案里区分（"其中 K 条已是悬空边"）。

**理由**（三条，按重要性）：
1. **不说 = 用户以为边丢了**。边是用户手动建立的关系（`docs/memory-system.md:234` 决策 30："edges 只用于显式 retrieve 的一跳扩散"），是用户的劳动成果。
2. **本期不修引擎**（契约 §12 前言），所以唯一能做的就是**告知**。
3. **修复成本低**：用户重新 `addEdge` 一次即可（同一 `(nodeId, targetUri)` 会被 upsert 覆盖，`store.ts:758`）。所以警告里 MUST 给出"怎么办"，而不只是"出事了"。

**反方论点（我考虑过但否决）**：警告太吵、用户会习惯性点确定。**否决理由**：relocate 是低频操作（改名/整理），不是日常动作；而后果是静默的、用户自己发现不了的。低频 + 静默 + 不可自察 = 必须提醒。**阻塞式勾选**正面回应了这个反方论点——习惯性点"确定"被挡住，用户必须读。

| **T4** | 级联删除的审计条数（I3） | 建 `p` + `p/c1` + `p/c2`，`deleteCascade(p.node_id)` | 返回 `3`；`audit_log` 新增恰好 3 行 `event='delete_node'`，其 `object` 集合 === `{p, p/c1, p/c2}`；每个 `node_id` 各多 1 条 revision |

| **T7** | ⭐ P1 断边（引擎行为，**不是 UI 断言**） | 建 `t`、`s`；`addEdge(s.node_id, t.uri, "refs")` → 断言 `listRelated(t.node_id).length === 1` → `relocateMany([{from:t.uri,to:"meta://t"}])` | `listRelated(renamed.node_id).length === 0`（incoming 消失）**且** `edges` 表行数仍为 1（行未删）**且** 该行的 `target_uri` 仍是旧 URI。→ 这条用例是 §8.1 契约 §12-P15 裁定的证据基础 |
| **T7b** | ⭐⭐ relocate→delete→restore 陷阱链（§7.3 / 契约 §12-P14） | ⚠️ **前置：MUST 先 `updateNode` 编辑一次**（否则 `node_revisions` 为空、复现不出来）→ 然后 `insertNode(uri:"core://p/orig")` → `updateNode(content:"V2")` → `relocateMany([{from:"core://p/orig",to:"core://p/new"}])` → `deleteCascade(...)` | ① `listDeletedUris()` 含**两行**（`p/new` 与 `p/orig`）且它们的 `node_id` **相等**；② `node_revisions` 里 v1 的 `uri='core://p/orig'`、v2 的 `uri='core://p/new'`（relocate 不改 revision.uri）；③ `restoreDeleted("core://p/orig")` 成功但 `content === "V1-CONTENT"`（★**静默数据错误**）；④ 随后 `restoreDeleted("core://p/new")` **抛错**且 message 含 `UNIQUE constraint failed` |
| **T8** | relocate 的 alias + awaken remap（I4） | `setAwakenUris(store, ["core://d", "core://d/kid"])` → `relocateMany([{from:"core://d",to:"core://e"}])` | `listAliases(node_id)` 含 `core://d`；`getAwakenUris(store)` === `["core://e","core://e/kid"]` |
