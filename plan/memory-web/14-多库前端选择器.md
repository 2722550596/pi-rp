### 3.2 新增：唯一的 `?db=` 注入点

```js
/**
 * ⭐ 全站唯一的 `?db=` 注入点（契约 §2.5 的两个注入口收敛于此 / 契约 §7.7）。
 * 参数 MUST 是**已拼好的完整 URL**（path + query）—— 先给裸 path 注入、后拼 query 会产出
 * **第二个 `?`**（实测坏产物 `/api/tree?db=%2F…memory.db?domain=core`，`domain` 被吞进 db 的值里）。
 *
 * ⭐⭐ 写入方式 MUST 是 **`.set()` 替换**，MUST NOT 手拼追加（`url + sep + "db=" + …`）。
 * 手拼追加在「URL 里**本来就有** `db=`」时会产出**重复键**：
 *   输入 `/api/node?db=%2Fold.db` → 产出 `/api/node?db=%2Fold.db&db=%2Ftmp%2Fnew.db`
 *   → 服务端 `searchParams.get("db")` 读到**第一个**值 `/old.db` ⇒ **打到旧库**（而 `.getAll()` 是 2 个）。
 * ⚠️ 该输入**必然可达**：§3.3 的 `buildQuery` 只能挡「query **对象**里的 `db`」，
 *    挡不住**已经串进 path 字符串**的 `db=`（任何粘进 hash 的 URL 都可能带它）。
 * `.set()` 同时解决两件事：**替换同名键**（不重复）+ 正确编码。
 */
export function withDbParam(url) {
  if (!selectedDb) return url; // 未选库 ⇒ 不加参数 ⇒ 服务端用进程库（契约 §4.1 缺省语义）
  const hashIdx = url.indexOf("#");
  const hash = hashIdx >= 0 ? url.slice(hashIdx) : "";
  const noHash = hashIdx >= 0 ? url.slice(0, hashIdx) : url;
  const qi = noHash.indexOf("?");
  const path = qi >= 0 ? noHash.slice(0, qi) : noHash;
  if (path === DB_ADMIN || path.startsWith(`${DB_ADMIN}/`)) return url; // 契约 §3.4 库管理路由无 ?db=
  if (!path.startsWith("/api/")) return url; // 契约 §7.2 静态资源与 ?db= 无关
  // 解析**其它**已有参数（对象构造：把整串当 query 解析 —— 这是唯一会坏编码的路径，故不用于库路径）
  const usp = new URLSearchParams(qi >= 0 ? noHash.slice(qi + 1) : "");
  usp.set(DB_PARAM, selectedDb); // ⭐ set = 替换，天然去重（契约 §7.7）
  return `${path}?${usp.toString()}${hash}`;
}
```

⭐ **编码口径（修正我初版的错误说法）**：坏的不是 `URLSearchParams` 本身，而是**用字符串解析**它 ——
`new URLSearchParams("db=" + "/tmp/a+b.db").get("db")` → `"/tmp/a b.db"`（`+` 被当空格，**不可逆**）。
而 `.set()` / **对象构造** / `encodeURIComponent` **都能正确 roundtrip**（实测三者都解回原值）。
但**三者的字节产物不相同**：`+` 在 `.set()`/对象构造下编成 `%2B` 但空格编成 `+`；
`encodeURIComponent` 下空格编成 `%20`（实测 `db=%2Ftmp%2Fa+b…` vs `db=%2Ftmp%2Fa%20b…`）。
⇒ 结论：**服务端的解码方式**决定哪个安全 —— 两边用**同一套** `URLSearchParams` 语义即可（HTTP query 本就如此）。
⚠️ **MUST NOT 把库路径拼进 query 串再解析**（那正是唯一会坏的那条路）。

**实测基线（25 条，`/tmp` 真跑，全通过）** —— ⭐ 复核方式：从**本文档逐字提取** `withDbParam`/`buildQuery` 的实现拼成 .mjs 再跑，不是另写一份。：

| `/api/tree?domain=core`，同上 | `/api/tree?domain=core&db=%2Ftmp%2Fnew.db` |
| **B11** ⭐ `/api/node?db=%2Fold.db`，同上 | `/api/node?db=%2Ftmp%2Fnew.db`（**`db` 恰一次且为新值**） |

### 3.3 改动：`buildQuery` / `get` / `post`（`app.js:71-124`）

`buildQuery` 加 1 行（`db` 归 HTTP 层唯一所有）：
```js
// ⚠️ MUST 导出：D5 的 §12.4 用 `buildQuery` 组装"其它参数"再验 `withDbParam` 的替换语义。
export function buildQuery(query) {
  const usp = new URLSearchParams();
  for (const [k, v] of Object.entries(query ?? {})) {
    if (k === DB_PARAM) continue; // ⭐ db 是保留键：调用方传 db 一律忽略
    if (v === undefined || v === null || v === "") continue;
    usp.set(k, v === true ? "1" : v === false ? "0" : String(v));
  }
  const qs = usp.toString();
  return qs ? `?${qs}` : "";
}
```

`get`/`post` 各改 **1 行** `fetch` 实参；`post` 加第三槽（契约 §7.7 + D3 §10.4 的接缝）：

```js
// app.js:101 签名加第三槽（可选，缺省无超时 ⇒ 既有调用逐字不变）：get(path, query, opts)
export async function get(path, query, opts) {
  let res;
  try {
    // ⭐ 超时（契约 §5.2#3 的前端对应物）：AbortSignal.timeout 是平台原生能力，零依赖。
    //    只有 /api/databases 会传它（见 §3.7）—— 因为只有那条路径可能在服务端
    //    「只读打开一个 FIFO」上永不返回（契约 §5.2#3）。其余数据路由沿用无超时（不改既有语义）。
    //    ⚠️ 成因不是 --allow-any-path（它只跳过 roots 检查，不跳过 isFile 类型检查）——
    //    而是契约 §5.2 末尾**自认防不住**的 TOCTOU 窗口，以及实现漏掉类型检查时的漂移。详见 §9.11。
    const signal = opts && opts.timeoutMs ? AbortSignal.timeout(opts.timeoutMs) : undefined;
    res = await fetch(withDbParam(path + buildQuery(query)), { headers: { Accept: "application/json" }, signal });
  } catch (cause) {
    // ⚠️ 超时也走这里：`AbortSignal.timeout` 触发时 fetch 抛 `TimeoutError` 的 DOMException。
    //    换成可识别的码（`timeout`），让 §3.7 把它与"连不上"区分开（两者都保留 selectedDb）。
    if (cause && cause.name === "TimeoutError") throw httpError("timeout", "请求超时。");
    throw httpError("internal", "无法连接记忆服务。", { cause });
  }
  return unwrap(res);
}

// app.js:111 签名加第三槽：post(path, body) → post(path, body, query)；超时同理（此处不必用，留对称）
export async function post(path, body, query, opts) {
  let res;
  try {
    // ⚠️ 不手工设置 Origin（浏览器负责）；带 Origin 的非 GET 由服务端契约 §5 S3 校验。
    const signal = opts && opts.timeoutMs ? AbortSignal.timeout(opts.timeoutMs) : undefined;
    res = await fetch(withDbParam(path + buildQuery(query)), {
      method: "POST",
      headers: { "Content-Type": "application/json", Accept: "application/json" },
      body: JSON.stringify(body ?? {}),
      signal,
    });
  } catch (cause) {
    if (cause && cause.name === "TimeoutError") throw httpError("timeout", "请求超时。");
    throw httpError("internal", "无法连接记忆服务。", { cause });
  }
  return unwrap(res);
}
```

⚠️ `timeout` 是**前端自造的码**，不在契约 §4.6 的七码闭集里 —— 它**永远不会**从服务端来，只出现在这三处（`get`/`post` 的 catch）。因此 §3.6 的 `renderError` **不需要**为它加 `ERROR_TEXT` 分支：`dbUnreachable` 不会因它被置位（它不带 404/409 的 `code`），落到 `ERROR_TEXT.internal` 的兜底文案即可。

**为什么 `post` 必须加 query 槽**：`?db=` 必须出现在**全部 21 条数据路由**（11 GET + 10 POST，契约 §4.1）。旧 `post(path, body)` 拿不到 `?db=` → 写操作落进程库、读操作落选中库 = **读 A 写 B**。这是本任务里除 `edit.js` 之外**第二个**必须堵的同族缺陷（F12）。

export async function refreshDatabases(opts) {
  try {
    // ⚠️ 必须带超时（契约 §5.2#3）：若某库路径实际是 FIFO，
    //    服务端只读打开会**永不返回**（单线程+同步 sqlite ⇒ 整进程所有请求都停）⇒ 本请求无限挂起。
    //    没有超时的话 `dbMode` 永远停在 "unknown" ⇒ `#mw-db` 永远 hidden ⇒ 多库静默消失。
    const body = await get(DB_ADMIN, null, { timeoutMs: opts && opts.timeoutMs });
    dbSnapshot = body && typeof body === "object" ? body : null;
    processDbPath = dbSnapshot && typeof dbSnapshot.current === "string" ? dbSnapshot.current : null;
    dbMode = "ok";
  } catch (err) {
    const code = err && err.code;
    // 403 forbidden_origin ⇒ 非回环绑定，多库整体禁用（契约 §5.5）
    // 404 not_found       ⇒ 端口上跑着**旧版本**实例（无这 3 条路由）。web-launcher 会复用端口，
    //                        所以这不是假想：必须优雅退化，MUST NOT 白屏、MUST NOT 卡在 ?db= 上。
    // timeout（非前两者）   ⇒ dbMode = "error"：与"网络抖一下"同一档，**保留** selectedDb（§5.2）。
    //                        理由：库可能只是被一个 FIFO 卡住，服务端修好（换掉那个路径）后照常可用；
    //                        而把用户的库选择清掉是不可逆的（§5.2 已立此原则）。
    dbMode = code === "forbidden_origin" || code === "not_found" ? "off" : "error";
    if (dbMode === "off") {
      selectedDb = null; // 多库不可用 ⇒ 清本地选择，全部请求退回进程库

## 5. 首次加载的判定顺序（契约 §6.3 冻结）

### 5.1 顺序（`resolveInitialDb()`，boot 内调用，唯一一次）

```js
async function resolveInitialDb() {
  const stored = readStoredDb();                       // ① localStorage 的 mw:db
  // ② 取库列表，**带超时并真的中止**（不是 Promise.race 后放着不管 —— 那样在途请求
  //    仍会在稍后写 dbMode/dbSnapshot，把已经渲染好的选择器**覆盖**一次）。
  await refreshDatabases({ timeoutMs: DB_INIT_TIMEOUT_MS });

  if (dbMode === "off") {                              // 多库被禁 / 旧实例
    selectedDb = null; persistDb(null); mountDbSelector(); return;
  }
  if (dbMode !== "ok" || !dbSnapshot) {                 // 列表拿不到（超时/网络抖）⇒ 按"暂时失败"处理
    selectedDb = stored;                               // ⚠️ 仍尊重本地选择：不因一次网络抖动丢用户状态
    mountDbSelector(); return;
  }

  const cur = dbSnapshot.current;
  const list = Array.isArray(dbSnapshot.databases) ? dbSnapshot.databases : [];
  const hit = stored ? list.find((d) => d.path === stored) : null;

  if (!stored)       { selectedDb = cur; }              // ③-a 没存过 → 进程库
  else if (!hit)     { selectedDb = cur;                // ③-b 存过但不在列表 → 进程库 + 说明
                       toast("上次选择的记忆库已不在列表中，已回到进程库。"); }
  else               { selectedDb = stored; }           // ③-c 在列表 → 用它（**含 reachable:false**）

  mountDbSelector();
}
```

| 判定 | 依据 |
|---|---|
| ① 先读 localStorage | 契约 §6.3「localStorage 有值且该库在列表中 → 用它」 |
| ② 再取列表（含 4s 上限） | 不在列表里的值 MUST NOT 被使用（否则第一个请求就 404，用户看到"库不见了"却不知为何） |
| ③-a 没存过 → `current` | 契约 §6.3 后半句 |
| ③-b 存过但不在列表 → `current` + 可见说明 | 契约没规定这一支。选"回进程库 + **说明**"而非静默：与契约 §6.5 的"不静默回退"同族 —— 静默回退会让人以为在看 A 其实是 B |
| ③-c 在列表**但不 reachable** → **仍选它** | ⭐ 契约 §6.5 明文：`MUST NOT` 静默回退到 `current`。此时 `mountDbSelector` 显示「· 不可达」，第一个请求会 404/409 → 由 §3.4 的 `dbUnreachable` 出专属错误卡（含"切回进程库"） |
| 4s 超时 | `/api/databases` 可能触发一次全盘扫描（D1 侧，几十个目录），不能让首屏无限等。**更硬的理由**：契约 §5.2#3 记录了 FIFO 会让服务端只读打开**永不返回** ⇒ 不设超时则 `#mw-db` 永远 hidden、多库功能静默消失。超时后**仍尊重本地选择**（§5.2） |
| 超时为何要"真的中止"而非 `Promise.race` | race 只让**等待**结束，在途请求稍后仍会写 `dbMode`/`dbSnapshot`，把已渲染的选择器覆盖一次。`refreshDatabases` 是唯一写这两处的地方，故超时必须由它自己带（§3.1） |

### 5.2 为什么超时后**不**清 `selectedDb`

反例：`selectedDb` 被清 ⇒ 请求落到进程库 ⇒ 页面显示进程库的树，而用户以为在看自己的库。这与契约 §6.5 禁的"静默回退"是同一个错误，只是触发条件从"库被删"变成"列表请求慢"。**宁可 404（有 `dbUnreachable` 错误卡），不可静默换库。**

### 5.3 与 `/api/meta` 的 launcher 兼容（契约 §4.5）

未选库（`selectedDb === null`）⇒ `withDbParam` 不加参数 ⇒ `GET /api/meta` **逐字**等于旧请求 ⇒ `web-launcher.ts` 的 `db_path === dbPath` 比较不受影响。这是"进程库在 `<option>` 里 value 为空串"的理由（§3.7）。

⚠️ 超时/失败时也**不**加参数（`selectedDb` 可能非 null 却库不可达 —— 那时带 `?db=` 是对的，会得到 404 → §3.6 的错误卡；而 `selectedDb === null` 才是"用进程库"）。

## 6. 切换行为（契约 §6.4 冻结）

### 6.1 三步与落点

| 契约 §6.4 要求 | 落点 | 说明 |
|---|---|---|
| ① 重载侧栏（域树变了） | `reloadAll()` → `renderSidebar()`（`app.js:447`） | 复用既有函数，不新写 |
| ② 重挂当前路由 | `reloadAll()` → `remount()`（`app.js:448`） | `remount` 读 `currentPath`/`currentParams`（`app.js:297-300`）⇒ **留在当前视图**，不跳首页 |
| ③ 清空上一层选中 | `clearSelectionParams()`（§3.7） | 只删 `#/node?uri=` 与 `#/tree?...&uri=` 的 `uri`，保留 `domain` |

**顺序不能换**：先 `treeCache.clear()` + `sidebarSeq++`，再 `renderSidebar()`，再 `remount()`。反序会让"盯着旧缓存的侧栏"先渲染一次。

### 6.2 为什么复用 `reloadAll` 而不是另写一套

`reloadAll`（`app.js:443-449`，F9）已经**恰好**是 `treeCache.clear()` + `renderSidebar()` + `remount()`（⚠️ 它现在 import 的是 `views/tree.js` 取 `treeCache` —— 抽到 `tree-cache.js` 后 D2 应把这一处也改指向新模块，见 §11.1） —— 切库需要的全部三步。另写一套会产生**第二个**"刷新整站"约定（仓库纪律禁止）。切库与"重新载入按钮"（`app.js:502`）的**唯一**差别是清 `uri`，这一条在 `switchDatabase` 里补。

### 6.3 与 `mountRoute` 的 `mountSeq` 配合（`app.js:307-363`）

`remount()` → `mountRoute(currentPath, currentParams)` → `const seq = ++mountSeq`（`app.js:310`）。
若切库前有一次旧库的 `mountRoute` 在途，它的 `seq` 会失配（`app.js:344/354/359`）→ 自动废弃，**不会**把旧库内容写进新库页面。所以路由层**不需要**改；缺守卫的只有 `renderSidebar`（§3.10）。

## 7. 不可达库（契约 §6.5 冻结）

### 7.1 三层防线

| 层 | 机制 | 覆盖的失败 |
|---|---|---|
| L1 选择器 | `dbOptionText` 出「`<label>` · 不可达」，`<select>` 仍选中它，**不**改 `selectedDb` | 用户在点之前就看得见 |
| L2 取数 | `unwrap`（§3.4）把 `not_found`/`invalid_db` 记进 `dbUnreachable` | 库在页面加载后消失（外部 `rm`） |
| L3 渲染 | `renderError` 前置分支（§3.6）出专属错误卡 + **「切回进程库」**按钮 | 用户有明确出路 |

### 7.2 为什么**不**能落进既有的 `ERROR_TEXT`

| 既有文案 | 用户会读出 | 真相 |
|---|---|---|
| `invalid_db`：`app.js:278`「数据库 schema 版本不匹配，请先升级 / 迁移记忆库」 | 我的库坏了、要迁移 | 可能只是文件被删了 |
| `not_found`：`app.js:271`「该地址在记忆库里不存在」 | 节点被删了 | 库本身不在注册表里 |
| 两者共有的按钮「回到树」：`app.js:288` | 点了能恢复 | 点了重挂同一个坏库 → 同一个错 → **死循环卡死** |

### 7.3 「可切回」的两条出路（都必须存在）

1. 错误卡上的「切回进程库」→ `switchDatabase(null)`。
2. 顶部 `#mw-db` **仍然可见可用**（`dbUnreachable` 只影响主区渲染，不动 `#mw-db`）→ 选另一个库。

### 7.4 明确**不做**的事

- **不**自动 `switchDatabase(current)`：这正是契约 §6.5 禁的静默回退。
- **不**在 `localStorage` 里清掉那个坏库：它可能只是**暂时**不可达（网络盘挂载中）。用户下次启动还能选它；只有 `dbMode === "off"` 时才清（§3.7，因为那时多库整个不可用）。
- **不**把错误卡做成"占满整页"：`#mw-db` 是 nav 的子元素，物理上不可能被主区覆盖。

## 9. 前端失败分析（11 条）

> 每条给：触发条件 → 现象 → 处置 → **为何这样处置**。

### 9.1 `/api/databases` 失败（网络层：服务没起 / 端口被别的进程占）

**触发**：`refreshDatabases` 抛 `internal`（`app.js:280` 文案），`dbMode = "error"`。
**现象**：`mountDbSelector` 因 `!isMultiDbAvailable()` 把 `#mw-db` **隐藏**；主区/侧栏正常（它们各自还有 `/api/meta`、`/api/tree` 的错误路径）。
**处置**：**保留** `selectedDb`（§5.2）；请求继续带 `?db=`；若服务其实活着只是 `/api/databases` 单点抖，用户切不了库但**当前库照常用**。
**为何**：把"库列表暂时取不到"降级成"用户的库被忘了"是**不可逆的用户状态损失**，而 `?db=` 正确性只依赖服务端注册表，不依赖前端这张列表。

### 9.2 `/api/databases` 返回 403（非回环绑定，契约 §5.5）

**触发**：`dbMode = "off"`。
**现象**：`#mw-db` 隐藏；`selectedDb = null` + `localStorage` 删除；请求不带 `?db=` ⇒ 退化为**单库**行为（正是契约 §5.5 末条）。
**处置**：`#/databases` 路由仍可导航，但页面显示「多库功能在当前绑定下不可用（服务只绑回环时才启用）」—— **不**显示空表。
**为何**：不能把 403 显示成"没有找到任何库"，那会引导用户去手输路径，而手输端点同样 403。

### 9.3 `/api/databases` 返回 404（**旧版本**实例，端口复用）

**触发**：`web-launcher.ts` 判定"端口上已有服务本库的实例"就**复用**它（契约 §4.5）→ 那个实例可能是多库功能之前构建的，没有 `/api/databases` → 404。
**现象**：与 9.2 **同判** `dbMode = "off"`，但文案不同：「服务端版本不支持多库（缺少 /api/databases）。请在 pi 中重新启动 web 服务」。
**为何**：404 与 403 的**用户动作**相同（都用不了），但**原因**不同 —— 混用一句文案会把"升级版本"误报成"改了绑定地址"，让人白折腾。

### 9.4 选中的库在别处被删（外部 `rm`，库已打开）

**触发**：库已注册（服务端 `StoreEntry` 在内存里），文件被 `rm`。后续请求 → `invalid_db`(409) 或 `not_found`(404)（取决于连接是否还活着）。
**现象**：L2 记 `dbUnreachable` → L3 出错误卡（§7）；`#mw-db` 里该库的选项**仍在**（列表来自 `/api/databases`，它按「注册库 ∪ 发现库」给，注册表**不**因文件消失而移除 —— 契约 §3.2 的第 5 条「文件消失不静默」）。
**处置**：错误卡给「切回进程库」；同时 `refreshDatabases()` 会让该库的 `reachable` 变 `false` → 下次打开选择器显示「· 不可达」。
**为何**：这正是契约 §3.2 第 5 条「已注册库文件消失 → 报错，MUST NOT 静默从注册表移除」的**前端对应物**：服务端不静默移除，前端就必须能显示"它还在列表里但不可读"。

### 9.5 几十个库的 `<select>` 可用性与长路径截断

**触发**：真机实测几十个 `memory.db`（数字口径见契约 §7.9，**不作断言**），绝大多数 `node_count === 0`。
**现象 a（可辨认性）**：只发 `label` 无法区分 → **契约 §6.2 强制**每个选项缀 ` · N 条`，空库显示 `0 条`、不可达显示 `不可达`（契约 §4.3 的三个语义各有字面）。
**现象 b（列表长度）**：`<select>` 的展开浮层由**操作系统**渲染，不受 `max-width` 限制 —— 长路径会横向撑开很长一列。**这是浏览器层限制，本项目无法修**。
**处置**：`label` 取短名（D3 的生成规则，如 `worlds/` 之后剥离 `.pi`/`characters`）；全路径只出现在 `title` 与 `#/databases` 页。选项**不按节点数过滤**（U4：空库可选但标注 —— 用户可能就是要去填它）。
**为何不**加"只看有内容的库"开关：那会让"我要去填那个空库"变得不可达；而 `node_count` 已经让辨认问题解决。

### 9.6 中文 / 长路径在错误卡与表格里的截断

**触发**：`renderNotice`（`app.css:130-134`）= `.mw-empty` 里的 `<p>`，**无** `word-break`（不像 `.mw-kv dd`，`app.css:84` 有 `word-break: break-word`）。一个 120 字符的中文+ASCII 混合路径在窄屏会横向溢出。
**处置**：`#/databases` 页的路径单元格用 `.mw-db-path`（§8：`word-break: break-all` + 等宽）。
错误卡**不新增 CSS**：把路径行包一层既有 `.mw-content`（`app.css:85`：`white-space: pre-wrap; word-break: break-word;`）即可。
**为何错误卡不省掉全路径**：路径是这类失败唯一有诊断价值的信息（是哪一个库不可达）；省掉它，用户就只能去管理页猜。用既有 class 而非新 class 是 §8 行数预算内的取舍，不是可读性妥协。

### 9.7 `localStorage` 不可用（隐私模式 / 禁用第三方存储）

**触发**：`localStorage.getItem` 抛错（Safari 隐私模式历史行为）。
**处置**：`readStoredDb`/`persistDb` 各有一个 `try/catch`（§3.1），降级为"不持久化"；本次会话内切换仍然生效（`selectedDb` 是内存变量）。
**为何**：沿用 `app.js:493-497` 对主题键的既有处置方式（**同一条约定**，不新造）。

### 9.8 选择器里出现**重复 label**

**触发**：D3 报告 `label` 理论上可能重复（`path` 才是 id）。
**处置**：`<option value>` 用 `path`（唯一），文案用 `label`。重复 label 只影响**视觉**辨认，不影响选择正确性；配合 ` · N 条` 与 `title` 里的全路径，可分辨。
**为何不**去重：合并两条不同路径的选项会造成**两个库都选不到**，比 label 撞脸严重得多。

### 9.9 切库期间连点（快速 A→B→A）

**触发**：用户连续改 `<select>`。
**处置**：`switchDatabase` 首行 `if (path === selectedDb) return;` 吞掉重复；`renderSidebar` 的 `sidebarSeq`（§3.10）与 `mountRoute` 的 `mountSeq`（`app.js:310`）各自废弃过期渲染；`treeCache.clear()` 由 `reloadAll` 每次都做。
**残余**：若 A→B→A 期间三次 `refreshDatabases` 并发，`dbSnapshot` 可能是旧的一次（后写的胜）。影响仅为**短暂的节点数陈旧**，非正确性 —— D1 侧有 5s TTL 缓存，重拉结果一致。

### 9.10 `?db=` 被中间层改坏（编码）

**触发**：库路径含 `+` / 空格 / `&` / `?` / `#`（Linux 允许除 `/` 与 `\0` 之外全部字符）。
**处置**：`db` 的写入 MUST 走 `URLSearchParams.set()`（§3.2）—— 替换式、编码正确。**MUST NOT** 把库路径**拼进 query 字符串再交给 `URLSearchParams` 解析**（`new URLSearchParams("db=" + 路径)` 把 `+` 当空格，不可逆）。
**为何**：这是 Main 实测定位的机制（契约 §7.7）：`new URLSearchParams('db=/a+b/x.db')` 读出 `/a b/x.db` ⇒ 请求打到**另一个路径** ⇒ 轻则 404、重则（若那路径恰好是另一个库）**读错库**。
⚠️ **精确归因（我初版说反了）**：`.set()` / **对象构造** / `encodeURIComponent` 三者**都能正确 roundtrip**；唯一会坏的是**字符串解析**那条路。所以口径不是"禁用 `URLSearchParams`"，而是"**不要用字符串拼 query**"。
**判据**：① 选中 `/tmp/a+b.db` 时，URL 里 `db` 键**恰一次**且服务端读回 `/tmp/a+b.db`；
② ⭐ 输入**已带** `db=` 时 MUST **替换**：`withDbParam("/api/node?db=%2Fold.db")` → `db` **恰一次**且为**新值**（追加会产出两个键，服务端 `.get()` 读**第一个** ⇒ 打到旧库）。

⭐ **同源的第二个实例（与 D2 §3.4#9 互引）**：D2 的 `realpathWalk` **MUST NOT** 用 `path.resolve` / `path.join`
取绝对串 —— 它们**保证**词法折叠 `..`（`path.resolve("/r/link/../out/x")` → `"/r/out/x"`，实测），
在那边放行 roots 外的**真实文件**（路径逃逸，安全漏洞），在这边把 `+` 变成空格（静默的错误值）。
**同一条根因：规范化 API 默认"帮你修好"输入，而安全/寻址代码恰恰不能接受未经请求的修复。**
两处判据都落在同一句上 —— **判据/寻址所用的值 MUST 与用户提供的值逐字同源，不得经过会改写的规范化**。

### 9.11 服务端被 FIFO 卡住（超时是**可用性**防线，不是安全防线）

**触发**（契约 §5.2#3 记录的硬危害）：某 `memory.db` 实际是 FIFO ⇒ `new DatabaseSync(<FIFO>, { readOnly: true })` 的 `open(2)` **永久阻塞**（等一个永不出现的写端；不抛错、不超时，实测 4–8 秒无返回、被 `timeout` 杀掉）。服务端是**单线程 + 同步 sqlite**（`server.ts:70` 的 `createServer` + `driver.ts:28` 的 `DatabaseSync`）⇒ 阻塞期间**进程内没有任何请求能得到处理**（不只 `/api/databases`，`/api/tree` 也一样）。

⚠️ **可达性的准确口径（我第一版写错了，此处更正）**：
1. **契约设计下不可达** —— §5.2#3 的 `stat().isFile()` 类型检查会先拒掉 FIFO，且该检查**与 `--allow-any-path` 无关**（逃生舱只跳过 §5.2#2 的 roots 包含性，**不**跳过类型检查）。我初版把成因写成「`--allow-any-path` 下若某库被换成 FIFO」是**错的**。
2. **但仍有两条真实可达路径**：
   - **TOCTOU 窗口**：契约 §5.2 末尾**自己登记**了这个残留 ——「第 2 步通过后、`openMemoryStore` 打开前存在 TOCTOU 窗口⋯**本设计防不住**，风险与代价如实记录（§11 U5）」。此窗口内把文件换成 FIFO，类型检查已经过了。
   - **实现漂移**：§5.2#3 的地位是"前两版实现都被证伪"换来的。任何一版把类型检查**漏掉或排到 open 之后**，症状就是"整个服务静默挂死"而不是"一个请求报错"。
3. ⚠️ **前端超时治不了服务端**：它只把「前端**永远**转圈、且 `#mw-db` 永远 hidden（§下方现象）」变成「4s 后给出可见错误」。**服务端那个进程仍然卡着**，需要重启。这一点 MUST 如实标注 —— 不要把前端超时当成 §5.2#3 的替代品，它是**第二道可用性防线**，不是安全控制。

**现象（若前端不设超时）**：`/api/databases` 永不 resolve ⇒ `dbMode` 永远停在 `"unknown"` ⇒ `isMultiDbAvailable()` 恒 false ⇒ `#mw-db` **永远 hidden**。用户看到的是「多库功能没了」，而且**没有任何错误提示** —— 因为一次失败都没发生。
**处置**：§3.3 给 `get` 加可选 `timeoutMs`（`AbortSignal.timeout`，平台原生、零依赖），§3.7 的 `refreshDatabases` 带 4s → 超时抛 `timeout` 码 → `dbMode = "error"` → `#mw-db` 仍 hidden **但** `selectedDb` 保留，且后续用户手动重试（`reloadAll`）能恢复。
**为何不改判 `"off"`**：`"off"` 会**清掉** `localStorage` 里的库选择（§3.7 的 `persistDb(null)`）。而这是**环境问题**（服务端侧删掉那个路径就好了），不是"此绑定不支持多库"。把用户的选择清掉是不可逆损失 —— 与 §5.2 同一条原则。
**为何超时必须由 `get` 自带、而不是外层 `Promise.race`**：race 只结束**等待**；在途 fetch 稍后仍会 resolve 并写 `dbMode`/`dbSnapshot`，把已渲染的选择器**覆盖**一次（且第二次会带着真数据，看起来像"自己好了"，极难排查）。中止必须真的落到 fetch 上。
**另一条我不做的处置**：超时后**不**自动重试（会反复把已挂死的服务端再敲一遍，无益）、**不**把库标成 `reachable:false`（那是服务端 DTO 的字段，前端无权就地改写 —— 会在下一次 `refreshDatabases` 后被覆盖，制造不一致）。

## 10. `views/edit.js` 的 `fetch` 收敛（契约 §7.1，Q3）

### 10.1 问题

`edit.js:23-53` 的 `requestJSON` 里 `edit.js:38` 是裸 `fetch`，**绕过** `app.js` 的 HTTP 层 ⇒ **不会**带 `?db=` ⇒ 切库后：

| 操作 | 实际落到 | 用户以为 |
|---|---|---|
| 读 `GET /api/node`（`edit.js:108/530/636/856`） | 进程库 | 选中的库 |
| 写 `POST /api/node/revise` 等 10 处 | 进程库 | 选中的库 |

⇒ **读 A 写 B**，且**写**是静默的（服务端 200，前端 toast「已保存」），**最严重的一类**。

### 10.2 方案：收敛到 `app.js` 的 HTTP 层（不是"在 fetch 处补注入"）

契约 §7.1 给了两条路（"收敛到 `ctx.api.post`" 或 "在其 `fetch` 处补同样的注入"）。**选收敛**：

```js
// edit.js 顶部新增**唯一**一条 import（本文件此前零 import，F4）
import { get, post } from "../app.js";

// 原 requestJSON（edit.js:23-53）整段删除，替换为两个薄适配：
//   getJSON(path, query)  → app.js 的 get(path, query)
//   postJSON(path, body)  → app.js 的 post(path, body)
// 二者都已被 app.js 的 withDbParam 注入 ?db=，且 unwrap 的错误形状与旧 requestJSON 一致
// （都是带 .code 的 Error，edit.js:461 describeWriteError 只读 .code/.message ⇒ 无需改）。
export function getJSON(path, query) { return get(path, query); }
export function postJSON(path, body) { return post(path, body); }
```

**为什么不是"在 `edit.js:38` 的 fetch 上补 `?db=`"**：
1. `?db=` 的**唯一**真相源是 `app.js` 的模块级 `selectedDb`。在 `edit.js` 再读一次（无论 import 还是读 `localStorage`）就是**第二个真相源**，两者漂移时静默写错库。
2. 契约 §2.5 已经声明 `app.js:104`/`:115` 是"仅有的两个注入口"。在 `edit.js` 补第三个，就把这条契约改成"三个"。
3. `edit.js` 的 `requestJSON` 与 `app.js` 的 `unwrap` 是**同一件事的两份实现**（都是"fetch + 解析 `{error:{code,message}}` + 抛带 `.code` 的 Error"）。收敛后这份重复消失，仓库纪律（"第二个约定禁止"）直接命中。

### 10.3 为什么**不**引入循环依赖（逐条核验）

**关键事实（F4，实测）**：`edit.js` 当前**零 import**；全仓**没有任何文件** import `edit.js` 的 `getJSON`/`postJSON`。

```
app.js  ──(动态 import，app.js:136-137)──▶  edit.js
app.js  ◀──(新的静态 import: get/post)────  edit.js
```

1. **ESM 允许循环依赖**（Live Binding），只有"在模块求值期使用尚未初始化的绑定"才报 `ReferenceError: Cannot access 'x' before initialization`。
2. `edit.js` 的 import 只**读** `get`/`post` 两个**函数声明**（hoisted，在 `app.js` 的任何语句执行前就已初始化）；`edit.js` 里**没有任何模块顶层语句调用它们** —— 全部调用都在函数体内，即挂载之后。⇒ 求值期不会访问未初始化绑定。
3. `app.js:136-137` 的 `import("./views/edit.js")` 是**动态**的（在 `ROUTES` 的箭头函数里，`:136`），**不是**模块顶层 import ⇒ `app.js` 求值时**不会**触发 `edit.js`。⇒ 依赖图虽成环，但**求值顺序无环**。
4. 反向也不可能出现"`edit.js` 先求值"：唯一的入口是 `app.js:562` 的 `boot()`，它先于任何 `ROUTES[path]()` 调用。
5. 已实测：`node --check` 对两个文件都通过（ESM 语法合法）。

⚠️ **实施约束（防止把安全变成不安全）**：`edit.js` MUST NOT 在**模块顶层**调用 `get/post`，也 MUST NOT 新增任何顶层副作用语句。这是"环是安全的"唯一前提。

### 10.4 不要收敛的部分（边界）

`edit.js` 的其余部分**不动**：导出面（D5 §10.2 冻结）、`notifyChanged`（`edit.js:64-66`，DOM 事件，与库无关）、`describeWriteError`（`edit.js:461`，只读 `.code`/`.message`，新旧错误形状同构）、`confirmForget`/`confirmSimple`/`showDiff`（纯 DOM）。这是"最小侵入"的具体含义。
