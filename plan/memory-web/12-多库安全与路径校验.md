## 2. 本轮向契约报回、且已被采纳的更正（四类）

前三条由我的实测触发，主 agent 已复核并写入契约（§2.1–§2.3）；第四条是我按 §9.2 自测时**证伪了本文初稿**（§2.4）。**记录在此，因为它们证明「纸面直觉」在安全问题上不可信**。

### 2.1 ⚠️ FIFO：「只读打开」不失败，而是**永不返回**

契约 §5.2#3 的硬危害，我实测（Node v26.8.1 / WSL2）：

```
$ mkfifo /tmp/fifo-XXXX/pipe.db
$ timeout 10 node -e 'new (require("node:sqlite").DatabaseSync)(fifo, { readOnly: true })'
EXIT CODE: 124          ← 被 timeout 杀掉，10 秒无返回
```

对照实验（同一台机器）：不存在的文件 → 抛 `unable to open database file`；目录 → 抛 `disk I/O error`；**文本文件 → 打开成功**、`prepare` 才抛 `file is not a database`。
**只有 FIFO/管道不抛错、不返回**。而 `DatabaseSync` 是**同步** API → 它占住 Node 事件循环 ⇒ **整个 web 进程挂死**，除 Ctrl-C 之外任何请求都不再被处理。

同族（**被 `stat().isFile()` 挡掉**）：块设备、字符设备、socket、`/dev/*`（实测 `/dev/null`、`/dev/zero` 均 `isFile=false`）。
⚠️⚠️ **但 `isFile()` 挡不住 procfs/sysfs 伪文件（SEC-01，评审实测，我已复核）**：
```
/proc/version         stat.isFile() === true    open 成功、prepare 抛出
/proc/self/cmdline    stat.isFile() === true    open 成功、prepare 抛出
/proc/self/environ    stat.isFile() === true    open 成功、prepare 抛出
/sys/kernel/notes     stat.isFile() === true    open 成功、prepare 抛出
```
⇒ **必须把 T16 的归因从「类型检查」改成「只读探测」**：`isFile()` 是**第一道**（挡 FIFO/设备/socket 这一族**挂死**风险），procfs/sysfs 由**探测**兜住（读不到 `memory_kv` → `not-memory-db`）。两道**都**必需，且顺序（类型检查在前）不能换 —— 否则 FIFO 仍会先挂死进程。

### 2.2 ⚠️ `lstat` 是错的 —— 会误拒合法 symlink 库

契约初版（主 agent 第一版指令，也是本文 §5.2 第一稿）写 `lstat().isFile()`。我实测三例：

| 文件 | `lstat().isFile()` | `stat().isFile()` | 该拒还是该放 |
|---|---|---|---|
| `link.db`（symlink → 真实记忆库） | **false** | **true** | **该放**（用 symlink 组织库是合法用法） |
| `pipe.db`（直接 `mkfifo`） | false | false（`isFIFO=true`） | 该拒 |
| `link-to-fifo.db`（symlink → FIFO） | false | false（`isFIFO=true`） | 该拒 |

⇒ **判类型 MUST 用 `stat`（跟随链接）**：`stat().isFile()` 同时满足「放行 symlink→普通文件」与「拒绝 symlink→FIFO」。主 agent 已复核并改契约 §5.2#3。

⭐ 这是本设计里「保守 ≠ 更严」的教科书例子：`lstat` 看着更严，实际只是**更错** —— 它把一个合法输入堵死，而对真正的危害（FIFO）两者的结论一样。

### 2.3 ⚠️ symlink 逃逸：词法包含性会被骗过（`..` 之外的第二条口子）

D5 报、我复核、契约 §5.2#2 已采纳为**双重口径**：

```
roots = /tmp/sym/roots
roots/link -> /tmp/sym/outside        （目录 symlink）

候选 = roots/link/secret.db
  path.relative(roots, path.resolve(候选))  =  "link/secret.db"       → 词法判定「通过」❌ 错
  realpathSync(候选)                         =  /tmp/sym/outside/secret.db
  path.relative(roots, 上面那个)             =  "../outside/secret.db" → 真实判定「拒绝」✅ 对
```

**危害是实的，不是理论的**：`create` 走 `openMemoryStore`，它会**灌表**（§5.1）。
我实测（roots 内放 `new.db -> roots 外/一张 users 表的库`）：

```
outside tables before: 1
outside tables AFTER create-through-symlink: 24    ← roots 外的文件被污染
```

→ `realpath` 是**唯一**能看穿它的手段。

### 2.4 ⭐ `..` 与 symlink 的组合：`path.resolve` 会掩盖真实的逃逸目标（本文自我更正）

**这一条不是向契约报回，而是我按 §9.2 自己跑测试时，把自己写的第一版实现证伪了**（§12.3 记录了完整迭代）。

```
roots/esc -> /outside        （esc 是指向 roots 外的 symlink）
候选 = "roots/esc/../outside/secret.db"

path.resolve(候选)          = roots/outside/secret.db     ← 词法折叠，落在 roots 内 ✅ 看起来安全
内核逐段走                  = esc 解析为 /outside，其父 = /   ← 真正打开的是 roots 外的文件 ⚠️
```

⇒ 「归一化后在 roots 内」**不等于**「内核会打开 roots 内的文件」。只做一次 `path.resolve` + 包含性检查（契约 §5.2#2 的字面写法）在这条输入上**放行**了一次真实逃逸。
**修法**（§3.2 的核心）：逐段真实解析（`..` 在**已解析**基础上回退）+ 断言「原始串与归一化串解析到同一个真实文件」。
⚠️ 反向的幼稚修法同样错：一刀切「含 `..` 就拒」会把 `roots/sub/../real/good.db`（无歧义）也拒掉 —— 实测过，误拒率不可接受（§9.2 B14）。
**契约影响（已闭环）**：契约 §5.2#2 的初版字面表述（「词法包含」+「对最深已存在祖先 realpath」）**不足以**覆盖本条。主 agent 已**独立复现该逃逸**（实测 `DatabaseSync` 读到 roots 外的 `secret` 数据）并把 §5.2#2 改写成正确形态（逐段真实解析 + 一致性断言 + `realpathWalk` 禁用 `path.resolve`），同时给 §5.2#1 加了「id 用法 vs 判定用法不可混用」的注。本文 §3.2 与契约 §5.2 现**逐字一致**。

## 3. `src/web/db-path-policy.ts`（冻结文件）

### 3.1 签名（形状冻结，逐字实现契约 §8.1）

```ts
export interface PathPolicy {
  /** 允许的根目录。调用方可给相对路径；本函数会 resolve。 */
  roots: string[];
  /** 逃生舱：跳过包含性检查（契约 §5.4）。开启时 CLI MUST 打醒目警告。 */
  allowAnyPath: boolean;
}

export function checkPathAllowed(
  policy: PathPolicy,
  candidate: string,
): { ok: true; path: string } | { ok: false; detail: string };

export function multiDbEnabled(host: string): boolean;
```

**为什么是 `{ ok, detail }` 而不是 `null` / 抛错**：`detail` 是**给用户看的中文**，D3 直接塞进 `bad_request` 的 `message`（契约 §4.6：手动路径不在 roots 内 → 400 `bad_request`）。
**`ok` 分支返回 `path`**：归一化结果（`path.resolve` 产物），D3 MUST 用它而不是原始 input —— 否则注册表 key 与 `?db=` 的比较会漂（契约 §4.2#1 要求全等；`web-launcher.ts:68-69` 的 `db_path` 比对也依赖同一口径）。

### 3.2 实现（真代码）

```ts
/**
 * 纯路径策略。除 `isLocalBind`（security.ts 的纯函数）外零项目内 import ——
 * 结构上不可能与 D1 的 discovery.ts / registry.ts 形成循环依赖（C1）。
 *
 * 本文件**不做**：类型检查（D1 的 probeMemoryDb 用 stat 判 isFile）、
 * 打开数据库（D1）、schema 校验（D1）。
 * 本文件**做**：归一化 + 逐段真实解析 / 一致性判定 —— 两者都只看路径。
 */
import { lstatSync, realpathSync, statSync } from "node:fs";
import path from "node:path";
import { isLocalBind } from "./security.ts";

const NUL = String.fromCharCode(0);

/**
 * ⭐ 内核语义的真实路径解析：**逐段**走，`..` 在**已解析**的基础上回退。
 *
 * 为什么不能直接用 `realpathSync(候选)`：它对**不存在**的路径抛 ENOENT，
 * 而 create 必须接受尚不存在的路径（契约 §5.3）。
 * 为什么不能"逐级上溯到最深已存在祖先再 realpath"（本文初稿的写法，已被实测证伪）：
 * 那样会把 `roots/esc/../out/x.db`（esc 是 → 外的 symlink）**整体**交给一次 realpath，
 * 于是 `..` 在**词法**层面先被折叠掉，内核真正会打开的文件被掩盖（见 §3.4#7）。
 *
 * 返回 `uncertain`：遇到「说不准」的情况（悬空 symlink / 自环 / EACCES）置真 → 调用方拒绝。
 */
function realpathWalk(input: string): { real: string; uncertain: boolean } {
  // ⚠️ MUST NOT 用 path.resolve / path.join 来取绝对串 —— 它们**词法折叠** `..`，
  // 会把本函数存在的意义（逐段看穿 symlink）当场抹掉。只能手工拼前缀。
  const abs = path.isAbsolute(input) ? input : `${process.cwd()}${path.sep}${input}`;
  const root = path.parse(abs).root;
  let real = root;
  let uncertain = false;
  for (const comp of abs.slice(root.length).split(path.sep)) {
    if (comp === "") continue;
    if (comp === "..") {
      real = path.dirname(real); // ⭐ 在「已解析」的基础上回退（内核语义）
      continue;
    }
    const next = path.join(real, comp);
    try {
      real = realpathSync.native(next);
    } catch (error) {
      let isLink = false;
      try {
        isLink = lstatSync(next).isSymbolicLink();
      } catch {
        isLink = false;
      }
      const missing = (error as NodeJS.ErrnoException).code === "ENOENT"
        || (error as NodeJS.ErrnoException).code === "ENOTDIR";
      // 悬空/自环 symlink，或 EACCES 等 → 说不准；普通的不存在 → 合法（create 的目标）。
      if (isLink || !missing) uncertain = true;
      real = next;
    }
  }
  return { real, uncertain };
}

/** 词法包含。用 path.relative 而非 startsWith（兄弟目录会骗过 startsWith，契约 §5.2#2a）。 */
function inside(root: string, candidate: string): boolean {
  const rel = path.relative(root, candidate);
  return !(rel === "" || rel.startsWith("..") || path.isAbsolute(rel));
}

export function checkPathAllowed(
  policy: PathPolicy,
  candidate: string,
): { ok: true; path: string } | { ok: false; detail: string } {
  if (typeof candidate !== "string" || candidate === "") {
    return { ok: false, detail: "路径不能为空。" };
  }
  // NUL MUST 显式拒绝。⚠️ 理由**不是**「path.resolve 会静默吞掉它」—— 那是错的（实测：
  // path.resolve("/tmp/a\0b") 长度 8、含 NUL、与输入逐字节相同，**不折叠**）。
  // 真实理由是：含 NUL 的路径在 open(2) 层**语义未定义**，且它必然是畸形输入。
  // ⭐ 副作用（也是好消息）：既然不折叠，`?db=<注册路径>%00` 归一后与注册路径**不全等**
  //   ⇒ 走 404，**不会**打到错库（契约 §4.2#1 的全等比较天然挡住）。
  if (candidate.includes(NUL)) {
    return { ok: false, detail: "路径不能包含 NUL 字节。" };
  }

  // ⚠️⚠️ 硬链接检查**不在这里**（本文初稿曾放这里，**被评审推翻**，见 §8.2c）。
  // 原因：`checkPathAllowed` 同时服务**注册路径**与 R5 的**每次重开路径**（D1 的 `resolve`）。
  // 放进本函数 ⇒ `cp -al` 备份过的**用户自己的库**（nlink 变 2）会在 `?db=` 命中分支被拒，
  // 而**不带** `?db=` 仍 200 —— 同一个库两种结果，且 D4 对每个请求都附 `?db=` ⇒ 整个 UI 报错。
  // 硬链接的准入判据在 `admitForRegistration`（独立导出，**MUST NOT** 被 `resolve` 调用）。

  const resolved = path.resolve(candidate);

  if (policy.allowAnyPath) return { ok: true, path: resolved };

  const roots = Array.isArray(policy.roots) ? policy.roots : [];
  // 空 roots = 什么都不允许（保守缺省，不是「允许一切」）。
  if (roots.length === 0) return { ok: false, detail: "未配置任何允许的根目录（--roots）。" };

  // ⭐ 一致性判定（本节的核心，实测见 §3.3 R6）：
  // 内核按**原始串**逐段走，我们返回的 id 按**归一化串**走。
  // 若不校验两者指向同一文件，`roots/esc/../out/x.db`（esc → 外）会出现
  // 「判定通过、id 落在 roots 内的一个不存在的路径、而内核打开的是 roots 外的文件」。
  const raw = realpathWalk(candidate);
  const norm = realpathWalk(resolved);
  if (raw.uncertain || norm.uncertain) {
    return { ok: false, detail: `无法确认真实路径（权限、悬空或循环符号链接）：${candidate}` };
  }
  if (raw.real !== norm.real) {
    return {
      ok: false,
      detail: `路径含歧义（symlink 与 ".." 组合会让内核打开的文件与你看到的 id 不是同一个）：${candidate}`,
    };
  }

  for (const root of roots) {
    const realRoot = realpathWalk(path.resolve(root));
    if (realRoot.uncertain) continue; // root 都说不准 → 不能用它做判据
    if (!inside(realRoot.real, raw.real)) continue;
    return { ok: true, path: resolved };
  }
  return {
    ok: false,
    detail: `路径不在允许范围内：${resolved}（允许的根：${roots.map((r) => path.resolve(r)).join(", ")}）`,
  };
}

/**
 * ⭐ **仅注册路径**使用的准入判据：硬链接守卫（契约 §5.2 末段、§8.2c）。
 *
 * 硬链接**绕过** roots 包含性：`realpathSync` 对硬链接返回它**自己那个（roots 内的）名字**
 * （硬链接没有「目标」）⇒ §3 的逐段真实解析对它**无感**。实测：
 *   roots 外 victim.db 与 roots 内 hard.db 同一 inode；realpath 判「在 roots 内」；
 *   openMemoryStore(hard.db) 把 victim.db 从 1 张表灌到 24 张。
 *
 * ⚠️⚠️ 本函数 **MUST NOT** 被 `registry.resolve`（R5 的每次重开路径）调用 —— 只给
 * `register` / `/api/databases/open` 用。理由（评审实测推翻了我的初版落点）：
 *   `cp -al` / `rsync --link-dest` 做过一次硬链接式备份后，**用户自己正常使用的库**
 *   `nlink` 就是 2（实测：备份前 1 → 备份后源库 2）。若把它放进每次解析的路径，
 *   `?db=<那个库>` 会被拒而不带 `?db=` 仍 200 ⇒ 同一个库两种结果，且 D4 对每个请求都附
 *   `?db=` ⇒ 选中该库后**整个 UI 报错**（"默认打开即白屏"）。
 *
 * 为什么放在注册口是**足够**的：roots 逃逸**只能由注册引入**（只有那一刻需要证明
 * 「这个路径指向 roots 内」）。已注册库的 nlink 从 1 变 2 只可能是本机硬链接
 * ⇒ 归 §8.1 已认领的攻击者类别，不构成**新的** roots 逃逸。
 *
 * 代价：一次 `statSync`（非热点路径：每次「打开」一次，不在 resolve 热路径上）。
 *
 * ⭐⭐ **调用点已被裁决（Main，2026-09-16）：唯一调用者是 D1 的 `registry.register()`。**
 *   - **MUST NOT** 由 D3 的 `/api/databases/open` handler 调 —— handler 只是 `register()` 的**一个**
 *     调用方；放 handler 里就是「每个调用方都要记得调」，正是契约 §7.6 拒绝过的「纪律性防线」。
 *     下沉到 `register()` = **单点**（与 R6 → `openDatabaseReadonly`、归一化 → `key()` 同一条判据：
 *     **守卫要下沉到唯一入口**）。
 *   - **MUST NOT** 进 `checkPathAllowed`：D1 的 `register()` 委托 `resolve()`，而 `resolve` 对
 *     **非 pinned** 路径会跑 `policyCheck`（= `checkPathAllowed`）⇒ 塞进去就等于落在 resolve
 *     热路径上，两条误伤立刻成立（§8.2c）。
 *   - ⭐ **为什么这里不需要 `pinned` 豁免**（Main 指出，我复核确认）：`pinned` 的**唯一写入点**是
 *     `cli.ts` 的 `adopt`（D1 §5.5 / §5.11）⇒ **`register()` 结构上不可能遇到 pinned 路径**。
 *     这不是「忘了加豁免」，而是「豁免问题在此不存在」—— 恰好证明落点正确。
 *     （对比：`resolve` 的 R5 守卫**必须**有 `pinned` 豁免 —— D1 已落 C13b 正反两条对照。）
 *   - 契约 §8.1 的 D2 导出面已由 Main 批准 **+1 行**（本函数即第四个导出）。
 *   - ⭐⭐ **只在「首次登记」跑，条件 MUST 是 `if (!reg)`（路径不在 `dbs` 里）** ——
 *     **不是**「`reg?.entry` 早退之后」。两者**不等价**：D1 §5.11 的生命周期表明写
 *     `evictBeyondLimit` 保留 `dbs` 而把 `entry` 置 `null` ⇒ 「reg 存在但 entry 为 null」
 *     是**已登记、只是连接被驱逐**。若在那里跑守卫，「登记 → 夜间 `cp -al` 备份 →
 *     被驱逐 → 用户再点一次 `/open`」会被拒 —— 正是要避免的误伤，且**发生在驱逐之后**（更难复现）。
 *     rationale：守卫的存在理由是「证明这个路径指向 roots 内」，那只在**首次登记**时是个问题；
 *     symlink 漂移归 R5（`resolve` 每次重跑 `checkPathAllowed`），硬链接在**登记之后**才被建
 *     ⇒ 契约 §5.2末 裁定 #4 已定「归 §8.1 类别、写进已知限制」。
 */
export function admitForRegistration(
  candidate: string,
): { ok: true } | { ok: false; detail: string } {
  let nlink: number;
  try {
    nlink = statSync(path.resolve(candidate)).nlink;
  } catch {
    return { ok: true }; // 不存在 → create 的合法目标（§5.3）；类型/探测在后续步骤兜
  }
  if (nlink > 1) {
    return {
      ok: false,
      detail:
        `该文件有多个硬链接（nlink=${nlink}），无法确认它就是允许范围内的那个文件。` +
        `如果你用 cp -al / rsync --link-dest 做过硬链接式备份，请改用 --allow-any-path 或把它加进 --roots。`,
    };
  }
  return { ok: true };
}

/** R4（契约 §5.5）：非回环绑定 ⇒ 多库整体禁用。唯一依据是**绑定地址**，不是请求头。 */
export function multiDbEnabled(host: string): boolean {
  return isLocalBind(host);
}
```

⚠️ **本节代码是本轮实测迭代的产物，不是一次成稿**：我按 §9.2 的验收清单逐条跑，**前两版都被自己的测试证伪**（见 §3.3 #7/#11、§12.3b）。结论：`checkPathAllowed` 是**唯一**必须做「内核语义模拟」的地方，任何试图用一次 `realpathSync` 搞定它的写法都会有反例。

**实现要点逐条**：

1. **先 `path.resolve` 再判**：防相对路径歧义（契约 §5.2#1）。⚠️ 但 `..` 的**语义**不能靠 `path.resolve` —— 见第 3 点。
2. **`roots` 也要 resolve**：CLI `--roots ./foo` 是相对路径，不 resolve 则词法比较无意义。
3. ⭐ **`..` 是内核语义，不是字符串操作**：`path.resolve("roots/esc/../out/x.db")` **词法折叠**为 `roots/out/x.db`，而内核先走 `esc` 再 `..` 回到 `roots/..`＝**父目录** → 打开的是 `roots` **外**的文件。**两者不是同一个文件**（§3.3 R6 实测）。所以：`realpathWalk` 逐段解析（`..` 在**已解析**基础上回退），并**额外**要求「原始串的真实路径 == 归一化串的真实路径」，否则拒绝。这一条是本函数存在的全部理由。
4. **`allowAnyPath` 短路在 NUL 检查之后**：NUL 是**输入畸形**，与「放宽范围」无关，逃生舱也不该接受畸形输入。
5. **`uncertain` 一律拒**：`EACCES`（无权限的中间目录）、`ELOOP`（自环）、**悬空 symlink**（`lstat().isSymbolicLink() === true` 但 `realpathSync` 抛 ENOENT）都是「说不准」→ 保守选**拒**。⚠️ 悬空 symlink 这一条是 §3.3 R9 实测逼出来的：`realpathWalk` 若把「不存在」与「悬空链接」混为一谈，`roots/dangling/x.db` 会被判**放行**（而它指向一个可能被任意创建的位置）。
6. **`isLocalBind` 从 `security.ts` import**（唯一项目内 import，纯函数、无副作用）：MUST NOT 复制一份 `LOOPBACK` 常量 —— 第二份真相源正是 S1/S2/S3 最不该发生的事。
7. **不缓存 realpath 结果**：`checkPathAllowed` 是**非热点路径**（每次「打开/新建」一次），而缓存会把 TOCTOU 窗口从「一次系统调用间」放大到「进程生命周期」。**用系统调用换安全**，这里买对了。
8. ⚠️ **返回值仍是词法 id（`path.resolve` 产物），不是 `raw.real`**：库 id MUST 与 launcher 的 `db_path` 比对口径一致（契约 §4.2#1、`web-launcher.ts:68-69`）。`real` 只用于**判定**，不参与 id 生成。

### 3.4 边界裁定

1. **Windows 大小写**：`path.win32.relative` **大小写不敏感**（实测：`C:\roots` ⊇ `C:\ROOTS\x.db` → `rel="x.db"`）。第 1 条就能放行大小写不同的同一目录，不需额外 lowercase 处理。⚠️ 但**库 id（`?db=` 的值）仍是大小写敏感的字符串比较**（契约 §4.2#1 的全等）→ Windows 上同一库可能有两个 id。**接受**：本设计只在 Linux/WSL2 真机验证（§12.1）；Windows 大小写一致性属 `[INFERENCE]`，登记 U7。
2. **反斜杠**：`path.relative` 在 win32 下返回**反斜杠**分隔。若判定写成 `rel.startsWith("../")`，会在 Windows 上**永远为假**（漏判逃逸）。契约与 `routes.ts:813` 用的都是无分隔符的 `rel.startsWith("..")` → 恰好跨平台正确。**MUST 沿用无分隔符写法**，MUST NOT 手写 `"../"`。
3. **symlink 逃逸的立场（明确）**：**拒**。理由：roots 的**全部意义**就是限定可读范围，放行一个指向范围外的 link 等于把 roots 变成装饰。**代价**：用户若用 `ln -s` 把库组织在 roots 外的树里，会看到 400 —— 缓解是 `--allow-any-path`，或把**真实**目录加进 `--roots`。
   ⭐ **同样的立场适用于硬链接**（硬链接也没有「范围外/内」的概念，它只是同一个 inode 的第二个名字）—— 但**落点不同**：symlink 由 `checkPathAllowed` 在**每次判定**时拦（因为它有「目标」可解析），硬链接由 `admitForRegistration` 在**注册时**拦（因为重开路径必须放行，见 §8.2c 的两条误伤）。**两者的判据相同，调用点必须不同。**
4. **roots 自身是 symlink**：MUST 对 root 也走 `realpathWalk`（§3.2 已实现），否则「root 是 link、候选是真实路径」会误拒（§3.3 #11 实测）。
5. **`..foo` 目录会被误拒**（§3.3 #12）：因为 `rel.startsWith("..")` 对 `"..foo/x"` 也为真 —— 这正是 `routes.ts:813` 的既有形状。**沿用而非「修正」**：(a) 仓库纪律明令复用既有约定、禁在旁另立第二套；(b) 保守方向正确（多拒一个目录名，不可能多放行一个逃逸）；(c) 以 `..` 开头的真实目录名近乎不存在，且失败信息会报出是哪个路径。**代价**：把库放进 `..archive/` 会得到 400 —— 那时再改成 `rel === ".." || rel.startsWith(".." + path.sep)`（我已实测该精确式对全部用例给出相同结论，仅该行不同）。登记 U8。

6. ⭐ **`realpathWalk` 的 `..` 语义（本节最容易做错的一处）**：`..` MUST 在**已解析**的路径上回退，不是在词法串上折叠。举例（§3.3 #7）：
   ```
   roots/esc -> /outside       （esc 是指向 roots 外的 symlink）
   候选 = "roots/esc/../outside/secret.db"
     词法折叠（path.resolve） : roots/outside/secret.db      ← 在 roots 内，看起来安全
     内核语义（逐段走）        : esc 已解析为 /outside，其父 = /   ← 实际打开的是 roots 外的文件
   ```
   ⇒ 只判「归一化后的路径在不在 roots 内」会**放行**一次真实的逃逸。**MUST** 额外断言「原始串与归一化串解析到同一个真实文件」（§3.2 第 3 点）。
   **代价**：极少数「路径里带 `..` 且中间有 symlink」的合法输入会被 400 拒（错误信息会给出归一化后的绝对路径，用户复制重发即可）。本设计选**更严的那一侧**。
7. ⭐ **「拒绝一切 `..`」的取舍**：我试过「输入含 `..` 段就拒」（最简单），实测正确，但会把 `roots/sub/../real/good.db` 这种**无歧义**的输入也拒掉（§3.3 #8）。用户从编辑器/终端粘贴路径时 `..` 很常见 → 误拒率不可接受。采纳信息更全的一致性判定，而非一刀切。
8. **悬空 symlink MUST 拒**：`realpathSync` 对悬空链接抛 `ENOENT`，与「普通的不存在」同码。若不额外用 `lstat().isSymbolicLink()` 区分，`roots/dangling/x.db` 会被判放行（§3.3 #10 实测）—— 而该位置可由任何能在 roots 内建文件的人随时创建。**代价**：用户若预置了指向「以后才创建的库」的悬空链接，会看到 400（应改为先建库再建链接）。
9. ⭐ **`realpathWalk` MUST NOT 用 `path.resolve` / `path.join` 取绝对串**：两者都会**词法折叠** `..`（实测：`path.resolve("/r/link/../out/x")` → `"/r/out/x"`），从而抹掉本函数存在的意义。只能用 `path.isAbsolute(input) ? input : cwd + path.sep + input` 手工拼。**本文在同一处栽了两次**（初稿在 `checkPathAllowed` 里先 `path.resolve`、修好后又把它重新引进 `realpathWalk` 内部）—— 记录在此，因为这是本设计最容易被「顺手优化」破坏的一行。
   ⭐ **同源的第二个实例（与 D4 `14` §9.10 互引）**：D4 的「`?db=` 值 MUST 经 **`.set()` / 对象构造**（推荐）或 `encodeURIComponent` 编码；**MUST NOT 把库路径拼进 query 串再交给 `URLSearchParams` 解析**；**MUST NOT 手拼追加 `db=`**」。两处判据落在同一句上：
   **判据/寻址所用的值 MUST 与用户提供的值逐字同源，不得经过会改写的规范化。**
   注意强度差异：我这里不是「可能改写」而是**保证改写**，且被改写的值**就是判据本身** ⇒ 直接构成路径逃逸（CWE-22）；D4 那边是静默产生错误值。
   ⚠️ **口径更正（安全评审 B，我已复核）**：D4 那条**初版**写的是「MUST NOT 用 `URLSearchParams`」—— **机制说错了**。实测 `+`→空格 **只发生在「把整串 query 交给 `URLSearchParams` 构造」这一种形态**；对象构造与 `.set()` 都无损。按初版口径会**逼实现者手拼**，而手拼在「base 已有 `db=`」时会**追加**成重复参数 ⇒ 服务端读回**旧库** —— 比原 bug 更严重。契约 §7.7 已改。**两个坑的根因仍然同一句**（规范化/拼接 API 悄悄改写值），但**禁的是具体形态，不是整个 API**。
10. **win32 的 drive 与 `..`**：`realpathWalk` 用 `path.parse(abs).root` 取根、`path.sep` 切分 —— `[INFERENCE]` 真机未验，属 §3.4#1 的同一限制。

|---|---|---|---|

### 4.2 ⭐ 为什么 R4 是**唯一**还站得住的闸门（本节是全文最重要的一节）

直觉是「S2 已经保证请求来自回环，所以 R4 只是纵深防御」。**这个直觉是错的**：

- S2 的 `HOST_RE`（`security.ts:22`）只校验 `Host` **头的字面值**。实测：`evil.com`、`127.0.0.1.evil.com`、`0.0.0.0:8788`、`192.168.1.5:8788`、`LOCALHOST` 全部被拒 ✅；
- **但它拦不住一个伪造头**。局域网主机对 `http://192.168.1.5:8788/` 发原始 HTTP、写 `Host: 127.0.0.1` —— 这个请求**通过 S2**。`test/web/security.test.ts:49-54` 的工具注释已点明此事（「forging Host IS the test」—— 测试工具必须能对 `Host` 撒谎，否则测不到安全规则）；
- S3（`security.ts:53-59`）对非 GET 要求 `Origin` 匹配，**但 `Origin` 缺失直接放行**（`security.ts:54`；实测：无 `Origin` 的 `POST /api/world-time` → 200）。而伪造 `Host` 的攻击者**当然也不会附 `Origin`**。

⇒ **在 `--host 0.0.0.0` 下，S2 + S3 对「会伪造头的网络主机」等于不存在。**
⇒ 因此 R4 **不是纵深防御，是主控制**。它 MUST：

1. **判绑定地址（`ctx.bindHost`），不是请求头**。D3 已在 `13` §4.5 独立裁定同一件事（并指出「用请求头会得到永假分支，测试假绿」）。我从安全侧独立确认：**用请求头 = 生产永不生效**。
2. **在 `ROUTES.find` 之前判**（D3 §4.4）：否则 `DELETE /api/databases` 会先撞 405，既泄漏「该路径存在」，又让整体禁用落空。
3. **发现扫描随之不执行**（契约 §5.5）：`/api/databases` 403 就不扫。MUST NOT 在 `startServer` 里预扫描 —— 那会在非回环启动的**那一瞬间**把路径列表算出来（哪怕没人请求）。
4. **`?db=` 只接受进程库**，其余一律 404（契约 §4.6 表）。这里用 404 而非 403：**不泄漏「路径存在但我拒绝」与「路径根本不存在」的区别**。

### 4.3 为什么「列出路径本身就是信息泄漏」

`/api/databases` 的响应（契约 §4.3）不用读到库内容就已泄漏：

| 字段 | 泄漏了什么 |
|---|---|
| `path` | 用户主目录名、项目名、world 名、角色名（真实形态：`…/worlds/<world>/characters/<char>/.pi/memory.db`，契约 §2.6） |
| `node_count` | **哪个角色有多少条记忆** —— 直接反映用户的创作活跃度与兴趣分布 |
| `world_time` | 故事内时间线 |
| `roots` | 允许范围的完整列表（= 把 §3.4 的边界直接告诉对方） |

即使「只是路径」，它也已是一份**目录结构指纹**，可独立用于进一步的路径猜测。所以契约 §5.5 把「扫描不执行」与「端点 403」并列不是啰嗦：**少扫一次 = 少一次把这份指纹算出来的机会**。

## 5. 核心威胁：`openMemoryStore` 灌表

### 5.1 危险（实测复现）

`openMemoryStore`（`src/index.ts:123-127`）= `openDatabase` + `createSchema` + `new MemoryStore`。
`createSchema`（`src/schema.ts:131-147`）只在 `memory_kv.schema_version` **存在且与 `SCHEMA_VERSION` 不匹配**时才拒绝（`schema.ts:133`）；而 `readSchemaVersion`（`schema.ts:150-161`）读不到就 `catch` 返回 `null`（「表不存在」与「行不存在」共用同一个 `null`）→ **一路 `CREATE TABLE IF NOT EXISTS`**（`schema.ts:139`）。

实测（`/tmp/poll-XXXX/victim.db`，一张 `users` 表）：

```
before tables: [ 'users' ]               md5: 4053d9902bea
after  tables: 24 tables                 md5: 4cd500655b5c    ← 20+ 张 memory_* 表被创建
users data survived: [ { id: 1, name: 'bob' } ]                ← 数据没丢，但文件被污染
```

⇒ **选错一个路径就会污染用户的文件**。这是本功能最严重的风险。

### 5.2 为什么必须在**注册入口**拦，而不是改 `openMemoryStore`

`openMemoryStore` 是**引擎公共 API**（`src/index.ts:123` 导出；`web/cli.ts:163` 与 pi 主流程都在用）。在它里面加校验会：

1. 改动 pi 主流程的行为契约（引擎立场是「显式指定的路径 = 可信」，见 §5.4 对进程库的同类裁定）；
2. 与 `00` §12 的登记 Q1「⚠️ **不修**」直接冲突；
3. **且它修不了本功能的问题** —— 风险来自「**未经校验的路径也能走到它**」，而不是「它自己的行为错」。校验必须发生在**调用者能拦下的那一层**。

⇒ 契约 §10 Q1 的裁定（**不修引擎，在注册入口拦**）正确，我确认。
⇒ **代价（如实记录）**：任何绕过本功能的调用者仍然会灌表。本设计只保护「经 web UI 注册」这一条路径。§8.1 会再说一次。

### 5.3 「先验后开」的时序保证

注册入口（`POST /api/databases/open`）的顺序**本身是安全属性**，MUST NOT 调换：

```
0. body 里取 path（非空字符串）                    → 否则 400
1. checkPathAllowed(policy, raw)                  → 否则 400（本文件 §3）
2. probeMemoryDb(allowed.path)   ← 只读！        → 否则 400（D1）
3. registry.register(allowed.path)                ← 这一刻才可能有写
```

`create` 的顺序（D3 §4.4 表，我复核认可）：

```
0. confirm === true                                → 否则 400
1. checkPathAllowed(policy, raw)                   → 否则 400
2. stat(dirname) 父目录存在                         → 否则 400（MUST NOT mkdir -p）
3. stat(resolved) 已存在（任意类型）                 → 409 conflict
4. writeFileSync(resolved, "", { flag: "wx" }) 原子占位 → EEXIST ⇒ 409
5. openMemoryStore(resolved)   ← 期望它建表
```

**第 4 步的 `wx` 是本设计里唯一一处原子性**，我实测它对 symlink 也是对的行为：

```
A dangling-symlink target: wx -> EEXIST      ← 目标是指向不存在文件的 link
B existing-target symlink: wx -> EEXIST      ← 目标是指向已存在文件的 link
```

⇒ **`create` 不可能经由「目标位置被预先放了 symlink」写到 roots 外**（`O_EXCL` 不跟随符号链接）。
⚠️ 但 `wx` **挡不住父目录里是 symlink**（`roots/escapedir/new.db`，`escapedir`→外）：那种情况**只能**由 §3 的真实层包含性检查挡住。两者互补，缺一不可。

### 5.4 「零副作用」的准确边界（区分「改主文件」与「留 WAL 附属文件」）

契约 §2.4b 的更正，我实测复核确认：

| 被探测的文件 | 主文件 md5 | 主文件 mtime | 新建 `-wal`/`-shm` |
|---|---|---|---|
| 非 WAL 的普通 SQLite（`journal_mode=delete`） | 不变 | **不变** | 否 |
| **真实记忆库**（WAL） | **不变**（实测 `d6f70660b5b9` 前后逐字节相同） | **不变**（逐位相同） | ⚠️ **是** |

实测（真实 `openMemoryStore` 建出的库）：

```
before: d6f70660b5b9 1789502166569.1665
probe  schema_version: { value: '2' }
after : d6f70660b5b9 1789502166569.1665
md5 identical: true | mtime identical: true
files after probe: [ 'm.db', 'm.db-shm', 'm.db-wal' ]       ← 附属文件确实留下了
```

**三条结论**（与契约 §2.4b 一致）：

1. ⭐ **主库文件本体永不被改**（逐字节）—— 这才是「先验后开」安全的**真正依据**。
2. ⚠️ **会留下 `-wal`/`-shm` 附属文件**。这是任何只读客户端读 WAL 库的正常行为，删除安全（下次打开重建），`close()` 之后仍在磁盘上。
3. ⭐ 因此安全判据 MUST 表述为「**主库文件的表集合 + md5/mtime 不变**」，MUST NOT 断言「文件列表不变」—— 后者对本功能自己的库都**不成立**（会假红，D5 的 V2 已按此改）。

**另一条硬边界（D3 报告、契约 §5.2 已收）**：`openDatabase`（`driver.ts:14`）在 `driver.ts:29` 执行 `PRAGMA journal_mode = WAL`。实测：**这才是改 mtime 的那一步**（单独一次普通 open 不改 mtime；加 WAL pragma 才改）。所以 `openDatabaseReadonly`（D1）MUST NOT 复用 `openDatabase`，MUST NOT 设 `journal_mode`。
最强的证据不是「改写文件头」而是：**只读连接上执行 `PRAGMA journal_mode = WAL` 直接抛 `attempt to write a readonly database`**（D1 实测）。我独立实测到一条更细的：**WAL 库 + 目录只读**时，连只读打开也抛同一句（`attempt to write a readonly database`）—— 即真实记忆库的只读探测**有前提**：目录需可写（要能建 `-wal`/`-shm`）。这解释了为什么「零副作用」的说法必须限定。登记 U10。

### 5.5 「先验后开」**不保证**的事（诚实登记）

- **不含内容安全**：探测只证明「`memory_kv.schema_version` 读得到且版本匹配」。一个**恶意构造**的 `memory.db` 可塞任意内容（超长 `content`、海量 `raw_log`）→ 打开后 Web UI 会渲染它。这是「读不可信内容」（XSS 面）而非路径安全；`00` §10 已冻结文本一律 `textContent`，本功能**不改变**该口径，也**不新增**任何 `innerHTML`。
- **不含 TOCTOU**：见 §8.2。

## 6. CSRF / DNS rebinding 面：多库下 S2/S3 是否仍足够？

### 6.1 前提：本服务不**发**任何 CORS 头

实测：`grep -rn "Access-Control\|OPTIONS" src/web/` **零命中**，且真服务器任何响应都不含 `Access-Control-Allow-Origin`（我逐响应打印过头）。
⇒ 恶意网页对 `http://127.0.0.1:8788/…` 发的跨源 `GET`：**请求会到达服务器**、**副作用会发生**，但**浏览器不会把响应体交给该页面的 JS**。

### 6.2 逐项实测（真服务器，命令见 §12.3）

| 请求 | 结果 | 结论 |
|---|---|---|
| `OPTIONS /api/world-time`（预检，`Origin: http://evil.com`） | **403** `forbidden_origin`，无 `Allow`/ACAO 头 | 恶意页**无法**发起需要预检的跨源写（`application/json` 就是要预检的那种） |
| `POST` 无 `Origin`（curl 式） | **200** | `security.ts:54` 的放行路径，见 §6.4 |
| `POST` `Origin: null` | **403** | sandboxed iframe / `file://` / 跨源重定向后的 `null` 源**被拒** ✅ |
| `POST` `Origin: http://evil.com` | **403** | ✅ |
| `POST` `Content-Type: text/plain`、body `value=…` | **400**（`请求体不是合法 JSON`） | 见 §6.5 |
| `GET /api/meta` 带 `Origin: http://evil.com` | **200** | 与 `test/web/security.test.ts:177` 既有断言一致（S3 只管非 GET）；**但无 ACAO → 页面读不到** |

### 6.3 恶意网页能否诱导浏览器调 `POST /api/databases/open`？

**结论：不能。** 三条独立理由，任一条单独成立即足以挡住：

1. **需要预检**：`app.js:115-119` 的 `post` 带 `Content-Type: application/json` → 跨源即触发预检 → 预检实测 403（§6.2 第 1 行）。**本服务不回应预检 → 浏览器根本不发真正的 POST。**
2. **即使绕过预检，`Origin` 也会被拒**：跨源 POST 的 `Origin` 必是攻击者的源，而 `checkOrigin`（`security.ts:53-59`）要求它**恰等于**本服务的 host:port，实测 403。
3. **读不到结果**：即便前两条失效，响应没有 ACAO → 页面拿不到 body。

### 6.4 ⭐ 无 `Origin` 的请求直接放行（`security.ts:54`）是否构成**新**风险？

**结论：不构成新风险，但它是全设计里最脆弱的一条假设，MUST 被显式记录。**

- **为什么不是新风险**：S3 的「无 Origin 放行」是**为 curl / 脚本 / 非浏览器客户端**留的，与多库无关 —— 单库时代它就已让「任何能发原始 HTTP 的本地进程」直通全部写路由。多库**不改变**这条，只改变「直通之后能干多少」（§5.1），而那个放大由 R4（§4.2）与 §3 的 roots 处理。
- **它依赖浏览器保证，不是我们的保证**：`security.ts:54` 的安全性等价于断言「浏览器对**每一个**非 GET 请求都会附 `Origin`」。这是 Fetch 规范的行为，**不是本服务能核验的事实**。任何浏览器缺陷、扩展、非浏览器客户端都会让它失效。
- **对多库的具体后果（万一失效）**：恶意页若能无 `Origin` 发 POST，就能调 `/api/databases/open` →
  - **仍然**过不去 roots（§3）；
  - **仍然**过不去只读探测（D1）—— 只能注册**真记忆库**；
  - 但**可以**注册 roots 内任何真记忆库，并随后 `?db=` 对它做**读写**（含 `POST /api/node/forget` 硬删）。
  ⇒ 所以「万一失效」的后果是**严重**的，只是**不影响本设计的正确性**（因为它同时需要浏览器违约）。
- **我们**不做**的加固**（契约 M5 明示）：token / session / 登录。若哪天 M5 被推翻，最便宜的替代是「首请求签发一个 `SameSite=Strict` cookie，所有非 GET 要求它存在」——**本期不做**，仅登记为 U11（不是建议，是「如果未来要不要做」的锚）。

### 6.5 为什么「简单表单 POST」不是绕过路径

跨源 POST 有三种「简单请求」形态可绕预检：`Content-Type` ∈ `{application/x-www-form-urlencoded, multipart/form-data, text/plain}`。
但本 API 的**每一个** POST 都走 `readJsonBody`（`routes.ts:859-875`）→ `JSON.parse`：

```
POST /api/world-time   Content-Type: text/plain   body: value=2020-01-02
→ 400 {"error":{"code":"bad_request","message":"请求体不是合法 JSON"}}    ← 实测
```

⇒ 简单表单能**到达** handler，但**过不了 body 解析**。⚠️ 这在多库下**不变**，因为 3 条库管理路由同样只吃 JSON（D3 已定）。
⚠️ 诚实补充：这不是一层**独立**的防线 —— 它是 `create` 的 `confirm: true` 之外的巧合（`text/plain` 里也可以塞合法 JSON 字符串…… 但 `text/plain` 的合法 JSON **可以是** `{"path":"…","confirm":true}`，**能过**）。
⇒ **正确结论**：简单表单 POST **能**打到 `/api/databases/create`（带合法 JSON body）。真正挡住它的是 §6.2 的 **`Origin` 检查**与 §6.3 的**读不到响应**，**不是** body 解析。MUST NOT 把 body 解析当防线（它的报错恰恰证明请求已到达 handler —— 若那里有副作用就晚了）。

### 6.6 DNS rebinding

| 攻击 | 是否有效 | 被谁挡 |
|---|---|---|
| 恶意域解析到 `127.0.0.1`，页面 JS 调 API | 否 | **S2**：浏览器发的 `Host` 是攻击者域名（如 `evil.com:8788`）→ 实测正则拒绝 ✅ |
| 同上，但攻击者用 `localhost`/`127.0.0.1` 之类作为域名前缀规避正则 | 否 | 正则**锚定** `^…$` 且大小写敏感（`security.ts:22`）→ `127.0.0.1.evil.com`、`LOCALHOST` 均拒（实测） |
| 攻击者域解析到 `127.0.0.1` **且**用户浏览器允许改 `Host` | 否（浏览器不改 Host） | 浏览器规范 |
| **局域网主机直连 + 伪造 `Host: 127.0.0.1`** | **是**（若 `--host` 非回环） | **只有 R4**（§4.2） |

⇒ 最后一行是全表唯一成功的攻击，也是 §4.2 把 R4 定性为「主控制」的原因。

## 7. ⭐ 威胁矩阵

**读法**：`--host` 只影响「谁能把包送到本服务」，不改变「送到之后能干什么」——后者由 roots（§3）、探测（D1）、R4（§4）决定。
「能达成什么」一列假设**攻击者已完成前置**（如已能把包送到服务）。凡本设计挡不住的，写「—（防不住）」并在 §8 展开。
| # | 攻击者能力 | `--host 127.0.0.1` 时 | `--host 0.0.0.0` 时能达成什么 | 被哪条规则挡住 |
|---|---|---|---|---|
| T1 | **本机同 uid 进程**（能读 `~`、能执行 curl） | 全部：读任意库、写、删节点、读任何文件（它本来就能） | 同左 | **—（防不住，且多库不提升权限）**。见 §8.1 |
| T2 | 本机同 uid 进程，但只想**污染**一个陌生 SQLite 文件 | 只能污染**它自己**手里的文件 | 同左 | **—（防不住）**。它不需要本服务 |
| T3 | 本机**其他 uid** 进程 | 包到不了端口（回环 + 端口归属） | 若端口可达：**与前一行同**（若无认证） | **—**。`[INFERENCE]`：本设计的 roots 对它能起**部分**作用（它不能用 UI 注册 roots 外的库），但**不**是本设计的承诺 |
| T4 | **局域网主机**（能连端口、不会伪造头） | 包到不了 | 数据路由可用（读+写**进程库**）；管理路由 **403** | **R4**（§4）+ **S2**（`Host` 非回环 → 403） |
| T5 | 局域网主机，**会伪造 `Host: 127.0.0.1`** | 包到不了 | 数据路由可用（读写**进程库**）；管理路由 **403**；`?db=` 非进程库 **404** | **只有 R4**（§4.2）。S2/S3 对它**无效** |
| T6 | 局域网主机，会伪造 `Host`，且想读**任意** SQLite 文件 | 包到不了 | **不能**：无法注册（403），`?db=` 只认进程库 | **R4**（§4）+ §4.2 的「判绑定地址而非请求头」 |
| T7 | 恶意网页（同浏览器，`fetch` 跨源） | 跨源 GET 请求会到达 → 副作用可发生；响应读不到 | 同左（多库已 403，且 `?db=` 只认进程库） | **S3**（预检/Origin 403）+ **无 ACAO** + **R4**。见 §6.3 |
| T8 | 恶意网页，想调 `POST /api/databases/open` 让用户机器读任意文件 | **不能**（预检 403 → 请求根本不发） | 同左（且管理路由 403） | **S3 + 无 ACAO + R4**（§6.3） |
| T9 | 恶意网页，用**简单表单** POST（绕预检） | 能到达 handler，但 `Origin` 非本服务 → **403** | 同左 | **S3**（§6.5）。body 解析**不是**防线 |
| T10 | 恶意网页，`Origin: null`（sandboxed iframe） | **403**（实测） | 同左 | **S3** |
| T11 | 恶意域做 **DNS rebinding** | **不能**：`Host` 是攻击者域名 → S2 403（实测） | 同 T4/T5 | **S2**；非回环时退化为 T5 |
| T12 | 恶意网页诱导用户**手**粘贴路径并点确认 | 能注册 roots 内任意**真记忆库**，随后可读写/硬删 | 管理路由 403 → 不能 | **只有用户自己**。roots 缩窄范围，`confirm` 拦误点，**挡不住社工**。见 §8.3 |
| T13 | 恶意网页靠**误伤**（用户点错库） | 不需要攻击者：用户自己就能删掉另一个角色的记忆 | 同左 | **—（产品面风险，非入侵）**。见 §8.4 |
| T14 | 恶意 `memory.db`（内容层：超长字段/巨量行） | 打开后渲染 → 资源消耗 / 渲染异常 | 同左 | **—（本设计不检查内容）**。见 §5.5 |
| T15 | **TOCTOU**：roots 内路径在 `checkPathAllowed` 后、`openMemoryStore` 前被换成 symlink | 能写到 roots 外 | 同左 | **—（防不住，`node:sqlite` 不暴露 `O_NOFOLLOW`）**。见 §8.2 / 契约 U5 |
| T16 | FIFO / 设备文件 / socket 被当作候选路径 | **不挂死**（类型检查前置） | 同左（管理路由 403 更早） | **D1 的 `stat().isFile()`**（契约 §5.2#3）。⚠️ 靠的是**类型检查**，不是 §3 |
| T17 | 兄弟目录名（`roots-evil`）伪装成 roots | 拒 | 拒 | **§3 词法层**（`path.relative`，非 `startsWith`） |
| T18 | roots 内 symlink 指向 roots 外 | 拒 | 拒 | **§3 真实层**（`realpath`，§2.3） |
| T19 | roots **内**的合法 symlink 库 | **放行**（不误拒） | 管理路由 403 → 只能进程库 | **§3 #6** ——「不误拒」也是验收项 |
| T20 | `--allow-any-path` 已开启 | 任意路径可注册（仍需类型 + 探测） | 管理路由 403，故仅本机有效 | **无**（用户显式放弃），CLI MUST 警告 |
| T16 | FIFO / 块设备 / 字符设备 / socket / `/dev/*` 被当作候选路径 | **不挂死**（类型检查前置） | 同左（管理路由 403 更早） | **D1 的 `stat().isFile()`**（契约 §5.2#3）。⚠️ 靠的是**类型检查**，不是 §3 |
| T16b | **procfs/sysfs 伪文件**（`/proc/version`、`/proc/self/environ`、`/sys/kernel/notes`） | 可被注册为候选 | 同左 | ⚠️ **`isFile()` 放行**（实测 `true`）→ **由只读探测挡**（读不到 `memory_kv`）。见 §2.1 |
| T21 | ⭐ **硬链接**（roots 外的 inode，硬链进 roots **注册**） | **拒**（注册口 `nlink > 1`） | 拒 | **`admitForRegistration`**（§3.2、§8.2c）；`realpath` 对它**无感**。⚠️ **仅注册口**，`resolve` 故意不查（否则误伤 `cp -al` 备份过的正常库） |
| T22 | ⭐ **注册后重定向 symlink**（SEC-02，无需赢竞态） | 后续任何**重开**都会打开 roots 外文件 | 同左 | 缓解 = **R5 每次重开重跑 `checkPathAllowed`**（契约 R5、D1 §5.13）；**仍有判定-打开之间的窄窗口**（§8.2a） |

**矩阵读出来的三件事**：

1. **T5/T6 是 R4 存在的唯一理由**。删掉 R4，非回环部署立刻退化为「网络上的任何人可读写你机器上任意记忆库」。
2. **R1（roots 包含性，§3）+ 只读探测（D1）+ 类型检查（契约 §5.2#3）是「本机」防线的全部** —— 它们对 T1/T2 无效，因为那类攻击者不需要本服务。**不要**误以为 roots 在防本机进程。
3. **T12/T13 是「用户自己」的风险面**，且 T13（误伤）比 T12（社工）更可能发生。安全文档 MUST 把它算进来（§8.4 给出了唯一可行的缓解：`confirm` 的文案必须**回显库路径**）。

## 8. ⭐ 本设计**防不住**什么（诚实清单，10 条）

> 安全文档的纪律：把「不设防的地方」写在显眼处，而不是让读者从威胁矩阵里自己推断。以下每条都给**代价**与**可行缓解**。

### 8.1 本机同 uid 进程 —— 完全防不住，但多库**不提升**它

- 攻击者能读 `~`、能 `curl`、能直接 `new DatabaseSync(path)`。它需要本服务的唯一理由已经不存在。
- **多库不提升它的权限**：它能读的文件、它本来就能读。
- **但多库扩大了「本服务的表面」**：一个能 `curl` 的本机进程现在可以通过 `POST /api/databases/open` **让 web 进程持有 8 个并发连接**（契约 §3.2#3 的 LRU 上限）—— 这是**资源消耗**面，不是权限面。
- **代价/缓解**：M5 明示不做认证。缓解只在 OS 层（多用户机器上别用同一个 uid 跑别人的 web）。
- **判据**：本设计**不声称**对 T1/T2 有任何防护。任何把它算作「已防护」的复核都是误读。

### 8.2 ⚠️⚠️ 守卫的**调用点**：注册只跑一次，而打开会发生很多次（SEC-02，契约 R5）

> ⚠️ **本文初稿把这一节写成「TOCTOU：`checkPathAllowed` 与 `openMemoryStore` 之间的单次系统调用窗口」，口径过窄 —— 安全评审指出了，我复核认同。** 保留原窄窗口描述（8.2a）外，**必须**加上 8.2b 的**生命周期**口径，因为后者才是主要风险，且它**不需要赢竞态**。

#### 8.2a 窄窗口（原口径，仍然存在）

```
t0  checkPathAllowed 通过（径直文件）
t1  ← 攻击者把该路径替换成 symlink → roots 外
t2  openMemoryStore(path)  → 灌表打在 roots 外
```

- **为什么防不住**：彻底防护需要 `open(2)` 的 `O_NOFOLLOW`（或 `openat` + `dirfd`），而 `node:sqlite` 的 `DatabaseSync` **不暴露任何 fd/flag 选项**（实测：构造参数只接受 `{readOnly}`）。Node 的 `fs.openSync` 支持 `O_NOFOLLOW`，但**拿不到它的 fd 交给 SQLite**。
- **代价**：登记为契约 §11 **U5**；`create` 路径**额外**受 §5.3 的 `wx` 原子性保护（目标位置被预放 symlink 会被 `EEXIST` 挡掉）。

#### 8.2b ⭐⭐ 真正的问题：守卫在**注册**时跑一次，而**重开**没有守卫（口径修正）

```
t0  roots/swap.db -> roots 内合法库     → 注册通过（含 realpath、nlink，全部通过）
t1  攻击者 unlink + 重新 symlink        → roots/swap.db -> roots 外目标
t2  任何**后续**重开（LRU 驱逐后的下一次请求、或重启进程再注册同一路径）
    → openMemoryStore(roots swap.db) 打开的是 roots 外的文件
```

**实测（我复核）**：
```
注册时：realpath(roots/swap.db) = /tmp/…/roots/real.db      in roots? true   ✅ 判定通过
重定向后：realpath(roots/swap.db) = /tmp/…/outside/victim.db  in roots? false  ⚠️
⇒ 后续任何一次重开都会打开 roots 外的文件。
```

- **为什么比 8.2a 严重**：**不需要赢任何竞态**。攻击者只要在被注册**之后**任意时刻改一次链接，然后**等**（LRU 驱逐、用户切库、进程重启）—— 下一次打开就是逃逸。8.2a 要求「在两次系统调用之间精确命中」，8.2b 只要求「在某个时间点做过一次修改」。
- ⚠️ **本文初稿的「不提供新能力」论证在此口径下不成立**：初稿说「攻击者必须已经能在 roots 内建文件 = 本机同 uid 进程 = 本来就能直接污染目标文件」。但 8.2b 的**触发者是 web 进程自己**（用户切库就触发），且它把「roots」这个边界**在时间维度上**抹掉了 —— 用户在 t0 批准的路径，t2 打开的可能完全是另一个文件，而**UI 上显示的仍是同一个路径**。
- **为什么本设计修不了**：守卫是「对路径的判定」，而攻击改变的是「路径的含义」。要修必须在**每次打开时重跑守卫**（D1 的 `registry` 打开路径）**或**用 `O_NOFOLLOW`（不可行，见 8.2a）。
- **可行的缓解（登记为契约 R5，实现归 D1）**：**每次懒打开/重开都重跑 `checkPathAllowed`**，而不是只在 `register` 时跑。代价是每次重开多几次 `stat`/`realpath`（非热点，可接受）。这**同时关掉** 8.2a 的窗口（判定与打开紧邻）与 8.2b 的生命周期问题，但不关掉「判定与打开之间的那一瞬」。
- **代价**：如实登记；**本设计不声称**已关闭此窗口。

### 8.2c ⭐ 硬链接绕过 roots（**注册时拦；重开路径故意不拦**）

`realpathSync` 对硬链接返回它**自己那个（roots 内的）名字** —— 硬链接没有「目标」，所以 §3 的逐段真实解析对它是**无感**的。

**实测（我复核）**：
```
roots 外 victim.db 与 roots 内 hardlink.db 同一 inode（ino 2378327 === 2378327）
realpathSync(hardlink.db) = /tmp/…/roots/hardlink.db     → 判定「在 roots 内」✅
openMemoryStore(hardlink.db) → victim.db 表数 1 → 24     → **roots 外的文件被污染**
```

**修法**：`admitForRegistration`（§3.2，**独立导出**，`statSync(path).nlink > 1` → 拒）。

⚠️⚠️ **落点是本节的关键，我初版放错了位置，被评审推翻（我逐条复核认同）**：

| 落点 | 后果 |
|---|---|
| ❌ 放进 `checkPathAllowed`（初版） | 它同时服务 `resolve` ⇒ **误伤①**：`cp -al` / `rsync --link-dest` 备份过的**用户自己的库** nlink 就是 2（实测：备份前 1 → 备份后源库 2）；**误伤②**：`?db=<那种库>` 被拒而不带 `?db=` 仍 200（缺省分支不查注册表）⇒ 同一库两种结果，且 D4 对**每个**请求都附 `?db=` ⇒ **选中该库后整个 UI 报错** |
| ✅ 只放注册口（`admitForRegistration`） | 只在「需要证明这个路径指向 roots 内」的那一刻跑；`resolve` 完全不碰它 |

**为什么放注册口就够**：roots 逃逸**只能由注册引入**。已注册库的 nlink 从 1 变 2 只可能是**本机硬链接** ⇒ 归 §8.1 已认领的攻击者类别，**不构成新的 roots 逃逸**。

- **`adopt`（进程库）豁免** —— 与契约 §5.4「进程库不受 roots 约束」一致。
- **R5（重开重跑 `checkPathAllowed`）保持不动**，`nlink` MUST NOT 跟着进 `resolve`。

**注册口专用的硬链接判据（`admitForRegistration`，§8.2c）**——与 B1–B16 分开列，因为它们是**另一次调用的**契约：

| # | 断言 | 输入 | 期望 |
|---|---|---|---|
| B17 | ⭐ **注册口拒硬链接** | roots 外 inode 在 roots 内的硬链接 | `ok: false` |
| B18 | 注册口放行普通文件 | nlink=1 的常规文件 | `ok: true` |
| B19 | 注册口放行**不存在**的 create 目标 | `R/new.db` | `ok: true`（`stat` 抛 ENOENT → 放行，§5.3 的 `wx` 兜底） |
| B20 | 注册口放行 roots 内 symlink（目标 nlink=1） | `R/sym.db -> R/plain.db` | `ok: true` |
| B21 | ⭐ **`checkPathAllowed` 对 nlink=2 仍放行（反误伤）** | `cp -al` 备份过的库（nlink=2），走 `resolve` 路径 | **`ok: true`** —— 这条与 B17 **同等重要**：只测 B17 会得到一个把检查塞进 `resolve` 的错实现（❌ 两条误伤） |

⚠️ **B17 与 B21 必须成对**（与 B13/B14 同理）：B17 保证硬链接被拦，B21 保证**只用注册口拦**。缺 B21 就会写出「`nlink>1` 塞进 `checkPathAllowed`」的版本 —— 它会拒掉用 `cp -al` 备份过的**用户自己的库**，并让 `?db=<那个库>` 整个 UI 报错（§8.2c）。

| # | 断言 | 判定方式 |
|---|---|---|
| B22 | ⭐ **调用点归属** | `grep -n "admitForRegistration" src/web/` → **恰 2 处**：`db-path-policy.ts`（定义）+ `registry.ts` 的 `register()`（唯一调用）。**MUST NOT** 出现在 `routes.ts`（handler）里 |
| B23 | ⭐ **`admitForRegistration` MUST NOT 进 `checkPathAllowed`** | `grep -n "admitForRegistration" src/web/db-path-policy.ts` → 只在**定义行**与 docblock 注释里；`checkPathAllowed` 函数体内**零调用**（否则立即落在 `resolve` 热路径上，B21 会红） |
| B24 | **`register()` 不可能遇到 pinned 路径**（结构性断言） | `grep -n "pinned.add" src/web/registry.ts` → **恰 1 处**，且在 `adopt()` 内。⇒ 无需为 `admitForRegistration` 加 `pinned` 豁免 |
| B25 | ⭐ **只在首次登记跑**（不是「早退之后」） | 行为断言：`register(P)` 成功 → 对 P 建硬链接（nlink=2）→ **`register(P)` 再调一次 MUST 成功（幂等，不跑守卫）**；反例断言：把它放进 `resolve` 的每次路径 ⇒ 该调用会 409（B21 已覆盖）。⚠️ 条件 MUST 是 `!reg`（不在 `dbs`），**不是** `!reg?.entry` —— 后者会被 `evictBeyondLimit`（保留 `dbs`、`entry=null`）命中 |

⭐ **教训（本文最值得记的一条）**：**「加了检查」不等于「更安全」**。`nlink > 1` 听起来是零成本的前置条件（`statSync` 本来就要调），但无条件加它会**误伤正常用户**，而误伤会**逼用户绕过整个防线**（用 `--allow-any-path` 关掉 roots），**比不检查更糟**。
⇒ 安全判据 MUST 先问「**合法用户会不会被它挡住**」，再问「攻击者能不能绕过」。

### 8.3 用户被社工：把恶意路径粘进「打开」框并点确认

- **能达成**：注册 roots 内**任意合法记忆库**，随后完整读写（含硬删）。
- **roots 的作用**：把可达范围从「整机」缩到「roots」。这是本设计**唯一**的收窄机制，也是它值得存在的理由。
- **`confirm: true` 的作用**：拦**误点**（笔误路径），**不拦**社工 —— 用户看着一个确认框点「确定」就是社工成功。
- **防不住的理由**：M5 不做认证 ⇒ 服务无法区分「用户本人的意图」与「被诱导的意图」。
- **代价**：这是无认证本地工具的固有属性（`00` §1.3 非目标已认领）。

### 8.4 ⭐ SEC-04：`readMemoryDbStats` 若缺同样的守卫，FIFO 挂死仍可达

/api/databases（D3）要对**每个发现到的库**填 `node_count`/`world_time` → 它会开只读连接（D1 的 `readMemoryDbStats`）。
⚠️ **这条路径与注册路径是两套代码**：§5.2 的类型检查（`stat().isFile()`）只写在**注册**入口上。
⇒ 若 `readMemoryDbStats` 忘了同样的前置检查，`roots` 里一个 **FIFO** 就能在**列举库时**挂死整个进程（不需要用户点「打开」）。

- **为什么是独立风险**：发现扫描会遍历 roots 下的**所有** `memory.db` 候选（契约 §4.3 的 `databases` 是「注册库 ∪ 发现库」）→ 攻击者只需在 roots 里放一个 FIFO 文件（**不需要**任何注册动作）。
- **归 D1 的契约 R6**（主 agent 已写入 §5.5c）。**验收**：C4 的哨兵扩展为「FIFO 哨兵」—— 在 roots 内放 FIFO，断言 `/api/databases` 仍在有限时间内返回。
- **代价**：本条**不是**「防不住」，而是「**待实现**的防线」；登记在此以免被当成已修。

### 8.5 ⭐ SEC-01：procfs/sysfs 伪文件绕不过 `isFile()`（见 §2.1 实测）

`/proc/version`、`/proc/self/cmdline`、`/proc/self/environ`、`/sys/kernel/notes` 的 `stat().isFile()` 都是 **`true`** 且 SQLite **能 open 成功**（`prepare` 才抛）。
- **不是安全漏洞**：它们读不到 `memory_kv` → 只读探测返回 `not-memory-db` → 400。**可被注册的结论不成立**。
- **但归因必须正确**：这一步是**探测**挡的，**不是**类型检查挡的。本文 §2.1 与 T16b 已按此改写。
- **代价**：`--allow-any-path` 下这些路径会被反复探测（每次一次 open），但对 `/proc` 无写风险。

### 8.6 ⭐ SEC-05：非回环下「`?db=` 只接受进程库」**要求**与**实现**的落差

契约 §5.5 要求非回环时 `?db=` 只接受进程库（其余 404）。实测 D3 的解析分支**没有 `bindHost` 判断** —— 那个 404 是**偶然**（注册表里恰好只有进程库，所以其他值自然 404）。
⇒ 一旦有人在回环下注册了库然后**重启为非回环**（或未来注册表实现变化），这条要求就**不再自动成立**。

- **归 D3**：加显式闸门（`multiDbEnabled(ctx.bindHost)` 为假时 `?db=` 只比对进程库路径）。
- **本设计的责任**：`multiDbEnabled`（§3.2）已提供判据，**MUST** 被用在**数据路由的解析**上，而不只是 3 条管理路由。登记，防「测出来是绿的但理由是错的」。

### 8.7 ⭐ DoS：发现扫描是**同步**递归，会阻塞事件循环

`discoverMemoryDbs`（D1）用同步 `readdirSync` 递归。实测（我本机复跑）：
```
同步扫描 ~/projects（depth≤6，跳过 .git/node_modules）：14871 个目录 / 331ms
评审实测：~/projects 11345 个目录 / 2699ms（机器负载不同）
```
期间**事件循环完全被占住** → 所有请求排队。契约 §4.3 的 5s TTL 缓存（D1）把它降到「每 5s 一次」，但**单次**仍是一次百毫秒到秒级的卡顿。

- **为什么算安全问题**：同一进程上的任何未认证请求都能**触发**它（`GET /api/databases`）→ 低成本的**可用性**攻击面。
- **缓解（归 D1）**：TTL 缓存（已有）+ 扫描深度上限（已有）+ 必要时 `--roots` 收窄。**不做**异步化（会引入并发扫描的新状态）。
- **代价**：如实登记；非回环下管理路由 403 ⇒ 只有本机可触发。

### 8.8 ⭐ 最大的实际风险不是入侵，而是**误伤**（含产品面）

多库把「一进程一库」放宽为「一进程 N 库」，于是**每一个写路由都作用在一个可变的库上**：

| 操作 | 打在错库上的后果 |
|---|---|
| `POST /api/node/forget` | **硬删**该节点的记忆（`store.ts` 的 forget 是硬删 + revision 留底） |
| `POST /api/node/relocate` | 改变另一个角色的地址结构 |
| `POST /api/node`（upsert） | 覆盖另一个角色的同名 URI |
| `POST /api/awaken` / `/api/world-time` | 改动另一个角色的世界钟 / 唤醒集 |

- **触发条件极低**：39 个库里只有 4 个有内容（契约 §2.6）→ 用户极易在空库/相似库之间选错。
- **本设计的缓解（建议，归 D3/D4 的产品决策，此处只给安全立场）**：
  1. `confirm` 类确认框 MUST **回显库路径**（只写「将新建空记忆库」不够 —— 用户要能看出是**哪个**）；
  2. 库选择器 MUST 显示 `node_count`（契约 §6.2 已强制）—— 它同时也是「我是不是选错了」的唯一线索；
  3. 破坏性操作（forget / restore）的现有二次确认（`00` §9.3）MUST 在文案里带上**当前库的短名**。
- **代价**：多一次文案工作，换掉一类**必然会发生**的数据损失。**强烈建议采纳**，但它是 D3/D4 的范围，本文只登记（U15）。

### 8.9 内容层：恶意/畸形 `memory.db`

- 探测只看 `memory_kv.schema_version`（D1），**完全不看内容**。一个 4 GB 的 `raw_log` 或 1 MB 的单行 `content` 都算「合法记忆库」。
- 后果：打开后渲染慢 / 内存涨 / 浏览器卡。**不是**安全漏洞（`00` §10 冻结 `textContent`，无 XSS）。
- **不做**的加固：大小/行数上限（会引入「多大算太大」的争议，且与本功能目标无关）。登记 U13。

### 8.10 敏感信息**必然**在响应里（无遮蔽层）

`/api/databases` 的 `roots` 与每个 `path` 会原样返回给**任何能调它的客户端**（本机）。`/api/meta` 的 `db_path` 同理（且这是 launcher 兼容性所必需，契约 §4.5）。
- **不做**的加固：路径遮蔽/脱敏。理由：本工具的目标就是「让人看清哪个库是哪个」（契约 §6.2）—— 脱敏会直接摧毁可用性，且它对本机攻击者毫无意义。
- **代价**：截图/分享浏览器页面时会连带泄漏路径。登记 U14（文档警告即可）。

**文件 A：`src/web/assets/views/tree-cache.js`（新，零 DOM、零 import 副作用）**

```js
// ── 缓存 + 库身份（契约 §7.6 D2 强修法；§7.10 要求本文件可被 node 直接 import） ──
// ⚠️ 本文件 MUST NOT import 任何 DOM 相关模块（含 ../app.js）—— 否则测试无法 import 它。
// ⭐ 本文件的**全部理由**：treeCache 的值来自某个库，而键里没有库标识。
//    这个模块把「这些条目属于哪个库」与缓存放在一起，做到**单点**失效。

export const treeCache = new Map();

// undefined = 尚未认领（首次挂载认领但不 clear —— 否则每次 mount 都白掉缓存）
let cacheOwner;
let cacheGen = 0;

/** mount / mountSidebar 的第一句 MUST 调用它（唯一失效点）。 */
export function ensureCacheFor(currentDb) {
  const owner = typeof currentDb === "string" && currentDb !== "" ? currentDb : null;
  if (cacheOwner === undefined) {
    cacheOwner = owner;
    return;
  }
  if (cacheOwner !== owner) {
    treeCache.clear();
    cacheOwner = owner;
    cacheGen++; // 让在途响应失效（loadLayer 用）
  }
}

/** `loadLayer` 在 await 前后各取一次：不同 ⇒ 这次响应属于旧库，MUST 丢弃。 */
export function currentGen() {
  return cacheGen;
}

/**
 * 精确失效：只删该 uri 的祖先层与自身层，不整树重拉（既有语义，从 `tree.js` 搬来）。
 * ⚠️ 搬进来的理由：它是**缓存的所有者操作**，必须与 `treeCache` **同处一个模块** ——
 * 否则 `app.js` 的 `memory:changed` handler 得 `import("./views/tree.js")` 才能用它，
 * 那会把 DOM 副作用拖进一个纯逻辑路径（§10.0）。`parentOf` 是纯字符串函数，一并搬。
 */
export function invalidateTreeFor(uri) {
  if (!uri) {
    treeCache.clear();
    return;
  }
  const parent = parentOf(uri);
  for (const key of [...treeCache.keys()]) {
    const i = key.indexOf("|");
    const prefix = i === -1 ? "" : key.slice(i + 1);
    if (prefix === "" || prefix === uri || prefix === parent || uri.startsWith(`${prefix}/`)) treeCache.delete(key);
  }
}

/** 纯字符串：`core://` 是根，再往上没有父层（既有语义，从 `tree.js` 搬来，逐字不变）。 */
export function parentOf(uri) {
  const s = String(uri ?? "");
  const i = s.lastIndexOf("/");
  if (i === -1) return "";
  const head = s.slice(0, i);
  return head.endsWith("://") ? "" : head; // `core://` 是根，再往上没有父层
}
```

⚠️ **搬运时实测到的一处既有瑕疵（如实登记，本次**不**改）**：`parentOf("core://a")` 返回 **`"core:/"`**（不是 `""`，也不是 `"core://"`）—— 因为 `lastIndexOf("/")` 落在 `core://` 的第二个斜杠上，`slice(0, 6)` = `"core:/"`，而它不以 `"://"` 结尾。
⇒ 注释写的「`core://` 是根」**只在 `core://` 自身**成立；**第一级节点**（`core://a`）的「父」是一个**不存在的畸形 URI**。
**影响**：`invalidateTreeFor("core://a")` 里 `prefix === parent` 这一支**永不命中**（没有哪个 key 的 prefix 是 `"core:/"`）⇒ 该节点的**父层缓存不会被精确失效**（根层 `""` 与自身层仍会被删）。属**既有**行为，与多库无关。
**本次处置**：**逐字搬运，不改**（改它会动既有缓存失效语义、可能影响既有测试，且超出 §7.6 的范围）。登记 **U17**。

⚠️ **`cacheGen` 通过 `currentGen()` 只读暴露**，不导出可变绑定 —— 否则调用方可能自己 `++`，绕开 `ensureCacheFor` 这个**唯一失效点**。

```js
  const items = Array.isArray(res && res.items) ? res.items : [];

  const prev = offset === 0 ? { items: [] } : treeCache.get(key) ?? { items: [] };
  const merged = {
    items: prev.items.concat(items),
    total: Number.isFinite(total) ? total : prev.items.length + items.length,
  };
  treeCache.set(key, merged);
  return merged;
}
```
