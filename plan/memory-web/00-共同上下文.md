## 1. 目标与非目标

### 1.1 预期效果（明月 2026-09-15 定）

一个**面向使用者**的本地 Web 界面，用来浏览、检索、编辑一套 `memory.db`：

- 看得见**一棵树**（nodes）、**一份原文日志**（raw_log）、**一个动态区**（TEMP）、**七个系统视图**（MEM://）。
- 能读懂**记忆现在是什么状态**：谁写的、什么时候、重要度、有没有被回滚遮蔽、修订过几次。
- 能安全地做少量写作（改正文、改重要度、整理 TEMP、挂触发词、调世界钟）。
- 不需要懂 SQL，不需要开 TUI，不需要起 pi 进程。

### 1.2 三条路线决策（已拍板，MUST NOT 重新论证）

| 维度 | 决定 | 理由 |
|---|---|---|
| **使用者** | 面向使用者（像 nocturne 那样），非运维控制台 | 明月 2026-09-15 选 |
| **数据通道** | 独立 HTTP 服务**直接打开 `MemoryStore`**，不经过 pi 进程 | 明月选；`MemoryStore` 本就设计为可脱离 pi 运行时（README §3），只依赖 `node:sqlite` |
| **代码位置** | **不开新包**；落在 `packages/memory` 内的 `src/web/` + `test/web/` | 明月 2026-09-15 修正 |

### 1.3 非目标（MUST NOT 出现在本期实现里）

- **不做实时协作 / 多用户 / 权限系统。** 单机、单人、只绑 localhost。
- **不做 pi 会话联动。** 不读 session 文件、不订阅 AgentEvent、不驱动模型。前端是**只读 DB + 少量直写**。
- **不做审计观测面板的"扩展"。** `docs/memory-system.md:190` 决策 23 原文："默认开、可关、**不设观测面板**"。本期只提供**只读的审计流列表页**（对账用），**不得**新增任何对审计流的聚合分析 / 图表 / 告警。这一条若被推翻，必须在「发现的冲突」登记。
- **不引入任何 npm 依赖。** 见 §2。
- **不引入任何构建步骤。** 见 §2。

## 2. 技术栈（冻结）

### 2.1 硬约束

| 项 | 决定 |
|---|---|
| 服务端语言 | TypeScript（`src/web/*.ts`），被 root `tsgo` 与 biome 正常检查 |
| 服务端依赖 | **仅 node 内置**：`node:http`、`node:fs`、`node:path`、`node:url`。**零 npm 依赖** |
| 客户端语言 | **纯 ES Module JavaScript**（`src/web/assets/*.js`），**无 TS、无 JSX、无打包** |
| 客户端样式 | **Pico CSS v2.1.1**（**默认构建，含 utility class**），vendored 到 `src/web/assets/vendor/pico.min.css` |
| 构建 | `tsgo` 编译 TS + `shx cp` 拷静态资源。**无 bundler / 无 vite / 无 postcss** |

### 2.2 为什么这样切（先例与理由）

**先例（决定性）**：`packages/coding-agent/src/core/export-html/` 已经是"包内静态资源前端"的成熟范式：

- `template.html` + `template.css` + `template.js`（76KB 纯 JS）+ `vendor/marked.min.js` + `vendor/highlight.min.js`
- 靠 `copy-assets` 脚本进 dist：`packages/coding-agent/package.json:39`
- 服务端 `readFileSync` 读模板再内联：`src/core/export-html/index.ts:151-155`
- **不被 biome / tsgo 检查**（biome includes 只有 `packages/*/src/**/*.ts`，见 `biome.json:27-39`）

也就是说，"在 pi-rp 包里塞一个无构建前端"**不是新发明，是本仓既有做法**。

**客户端为什么用纯 JS 而不是 TS**：root `tsconfig.base.json:4` 的 `lib` 是 `["ES2022","ES2024"]`，**没有 DOM**。root `tsconfig.json:39` 的 include 是 `packages/*/src/**/*`，会扫到 `src/web/**/*.ts`。若把浏览器代码写成 `.ts`，就必须给 root config 加 `DOM` lib 或给 memory 加 exclude —— 那正是上游 2026-05-20 删除 `packages/web-ui` 时踩的坑（见 §2.3）。**写成 `.js` 即零配置。**

### 2.3 反例警示：被删除的 `@earendil-works/pi-web-ui`

commit `b141e1fa2`（2026-05-20）删除了 `packages/web-ui`。它当时用 Lit + Tailwind + Vite，代价是**四条全局配置被污染**：root `package-lock`、`tsconfig` 需 exclude、`biome.json` 需 include、root `check` 需 `cd` 进去。

**本设计 MUST NOT 重蹈**：任何"要给 root tsconfig / biome.json / package.json check 脚本加例外"的方案都是**错的**，必须在设计阶段改掉。

### 2.4 Pico CSS vendoring 规则

- 文件：`src/web/assets/vendor/pico.min.css`（v2.1.1，MIT，83,319 字节，已核验）。
  - ⭐ 实测（主 agent 复现）：字节数 83,319、**sha256 = `fbc9a63fc9fc9f72d12fd7fc9806e11fa9f77ae4f9cad146b27003a1119ba3db`**、gzip 约 11,627 字节。

## 5. 安全模型（冻结）

本地 HTTP 服务器接受写请求 = 可被任意网页 CSRF + DNS rebinding 打。三条 MUST：

| # | 规则 | 实现点 |
|---|---|---|
| S1 | 默认只绑 `127.0.0.1`。`--host` 可覆盖，但启动时 MUST 打印醒目警告 | `server.ts` |
| S2 | 每个请求校验 `Host` 头 ∈ `{localhost, 127.0.0.1, [::1]}`（可带端口）。不匹配 → 403 | `security.ts` |
| S3 | 非 GET/HEAD 请求，若带 `Origin` 头则 MUST 等于 `http://<host>:<port>`；不带 Origin（curl/脚本）放行。不匹配 → 403 | `security.ts` |

错误码 `forbidden_origin` 见 §7.3。**不引入 token / 登录 / session**（§1.3 非目标）。

### 6.6 分支可见性（⭐ 本设计最容易做错的一处）

引擎侧可见性：`isVisible(node, anchorActive)`（`store.ts:1175-1179`）—— `auto` 节点仅当 `anchor_entry_id` 存在**且**该 anchor 在**当前活跃分支**上才可见。引擎用内存里的 `hiddenAutoNodeIds` 集合（`module.ts:334-348`）。

引擎的真实判据（`module.ts:334-348` `recomputeAnchorVisibility`，逐行读出的口径）：

```
对每个 source='auto' 的节点 n：
    若 n.anchor_session_id 或 n.anchor_entry_id 缺失            → hidden
    否则若 n.anchor_session_id !== 当前会话                      → 跳过（既不加 hidden，也不算可见）
    否则若 n.anchor_entry_id 不在当前分支的 entryIds 里          → hidden
    否则                                                         → 可见
```

**独立服务器拿不到"当前会话"这个上下文，但可以从 DB 推导分支状态 —— 且必须推导，否则 UI 会展示已被回滚的幻觉记忆。**

⭐ **实测确认的一处语义分歧（2026-09-15，已复现）**：引擎对**别的会话**产生的 auto 节点是**跳过**（`continue`，`module.ts:344`），而不是判为 hidden。所以"该节点所属会话被回滚了"**不**等于"当前视角下它被遮蔽"。

冻结算法（`visibility.ts`），按会话是否已知分两步：

```
# 第一步：无条件推导，得到节点自身的分支状态（与"当前会话"无关）
对每个 source != 'auto' 的节点：
    n.shadowed = false
对每个 source == 'auto' 且 (anchor_entry_id 缺失 或 anchor_session_id 缺失) 的节点：
    n.shadowed = true                      # 对齐 module.ts:340-342
对每个 source == 'auto' 且两个 anchor 都在的节点 n：
    查 raw_log WHERE entry_id = n.anchor_entry_id AND session_id = n.anchor_session_id
    n.shadowed = (该行为空) OR (该行 active = 0)

# 第二步（可选）：仅当用户显式选定"角色视角 = 某个 session"时才做
若指定了视角 session S，则对 source=='auto' 且 anchor_session_id !== S 的节点：
    该节点在两个方向上都**不参与**可见性判定（MUST NOT 标 shadowed，MUST NOT 当作可见）
    → DTO 用单独字段表达，或前端标注"来自其它会话"
```

- **默认（未指定视角 session）时 MUST 采用第一步的无条件口径**，即把"所属会话已回滚"的节点标为 `shadowed` —— 这是**保守但有据**的：翻 `active` 的机制本身只由该会话的 `syncRawBranch` 触发（`store.ts:887-901`），所以 `active=0` 确实意味着"这条路已经不在了"。
- ⚠️ 但 MUST NOT 把它渲染成"当前角色看不到" —— 因为引擎在别的会话里会**跳过**它。UI 文案冻结为 **"已遮蔽（原分支已回滚）"**，而非"已隐藏"。
- `shadowed` **不是** `isVisible()` 的替代品，只是无会话上下文的保守近似。
- DTO 字段名冻结为 `shadowed: boolean`；若实现第二步，另加 `foreignSession: boolean`（默认 false）。

### 6.7 世界钟

### 7.4 变更检测（`/api/events`）

⭐ **实测结论（2026-09-15，node 22 + 本机 SQLite，见下方"实测记录"）**——语义比我最初写的更细，D1 MUST 按这个实现：

`PRAGMA data_version` 是**每连接**的计数器，规则是：

| 情形 | `data_version` |
|---|---|
| 本连接**自己**写入 | **不变** ⚠️ |
| **别的连接**（同进程或跨进程）写入并提交 | **递增** |
| 只读、无写入 | 不变 |

返回值是整数，语义只有"变没变"，**不是**全局版本号（不同连接的值不可比大小）。

**由此产生的两条硬约束**：

1. `/api/events` MUST 由**同一条连接**读取 `data_version`，且该连接与处理写请求的连接可以是同一条 —— 但此时**服务端自己的写入不会被自己看见**。
2. 因此客户端在**自己发起写请求后** MUST **主动刷新**，不得依赖 `/api/events` 轮询发现该次写入（否则会"写完界面不变"）。
   `/api/events` 的职责被限定为：发现**外部**（agent 会话、另一个工具）对本库的改动。

返回：

```jsonc
{ "version": 42, "changed": true }
```

- `version` = 本次读到的 `data_version` 原始值；`changed` = 与上一次本连接读到的值是否不同。
- 首次调用时 `changed` MUST 为 `false`（无基线，不谎报变更）。
- 进程内 MUST 缓存"上次读到的值"（每连接一份，或单连接单值 —— 由 D1 定并说明）。

**这是刷新机制的唯一依据**，不做 WebSocket（§1.3 非目标）。

#### 实测记录（可复现）

```text
A before B's write: 2
A after  B's write: 3      ← 别的连接提交 → 递增
A again (no write): 3      ← 不变
A after  A's own write: 3  ← ⭐ 自己写入不变
B after  A's write: 3      ← B 看到 A 的写入 → 递增到 3
cross-process: 2 -> 3 INCREMENTS   ← 跨进程同样成立
```

复现方式：两条 `DatabaseSync` 连接打开同一 WAL 库，一条写、另一条读 `PRAGMA data_version`；再用 `execFileSync` 起子进程写，验证跨进程同样递增。

## 8. 视图语义（冻结）

### 8.1 七个 MEM:// 视图（`memory-views.ts:22-...`）

### 8.2 结构化而非文本（冻结）

现有 `render*` 函数**输出 markdown-ish 文本**，是给 TUI / 工具用的。
**Web UI MUST 输出结构化 JSON**，不直接吐 `render*` 的字符串（否则无法排序、过滤、跳转）。

即 `src/web/views.ts` 是**第二实现**。为防两份真相漂移，见 §8.3。

### 8.3 ⭐ 可机械核验的不变量（本设计的核心约束）

> 教训来源：`design-first-feature-workflow` —— 「冻结契约若不能被机械核验，就等于没冻结」，且「用双向相等，不用并集」。

`test/web/views-parity.test.ts` MUST 断言，对每个视图与同一 fixture，**UI 结构化输出的 id 集合 === `render*` 文本输出的 id 集合**。

⭐ **集合的维度因视图而异，不可统一用 `node_id`（原稿在此处写错，已按实测修正）**：

| 视图 | 集合维度 | 依据 |
|---|---|---|
| `timeline` | **`raw_id`** | 实测：`renderTimelineView` 输出 `- [2] 2020-01-02 assistant: …`，**完全没有节点 URI**（`memory-views.ts:28-31` 的 SELECT 只取 raw_log 列） |
| `forgotten` / `recent` / `wakeup` | `node_id` | 输出里每个节点都带 `uri` |
| `glossary` | `node_id`（**关键词 → 节点**，集合取被指向的节点集合） | 输出 `- 薇拉\n  -> core://scenes/tavern` |
| `index` | `node_id`（domain 根节点集合） | 输出 `  history://: Scene summary domain` |
| `diagnostic` | **不是节点集合**，而是"问题分类"清单（Placeholder / stale / crowded） | 实测：输出的是分类段落（`## 3. 待回填占位节点 (Placeholder)`），与其它六个维度不同 |

对 `diagnostic`：parity MUST 改为**逐分类相等**（结构化 `categories[].name` 集合 === 文本中 `##` 小节的集合），或由 D4 给出并 spike 验证的等价公式。

**提取规则（⭐ 原稿的通用正则方案已被 D4 实测推翻，见下）**：MUST **按视图的行锚点/结构解析**，**MUST NOT** 用"全文匹配 uri 正则"。

⭐ **推翻记录（D4 报、主 agent 复现）**：通用正则会被**节点正文伪造**。实测：节点 `core://notes/a` 的正文写了 `见 core://notes/target 那一条`，渲染后提取得到
`["index://","history://","meta://","core://notes/a","core://notes/target","core://notes/target"]`
—— `core://notes/target` **既作为标签出现、又作为正文内容出现**，且 `resolveUri()` **成功**。所以"解析失败就丢弃"这条兜底**无效**。

冻结的两条修正：
1. **必须按视图结构/行锚点提取**（例如 forgotten/recent 的行形态是 `- N 天没想起 | <uri> [★k]`），不得全文扫正则。
2. ⭐ **`wakeup` 的 `## 最近动态` 段不可机械核验**：`memory-views.ts:124` 只渲染 `snippet(n)`，即**正文**（函数体见 `memory-views.ts:11-14`：仅 `node.content`，**不含 uri**）——节点身份在渲染时就被丢弃。→ 该段 parity MUST 降级为**行数约束**（或改为直接比对有序 `node_id` 列表，由 D4 定），MUST NOT 声称能双向相等。
   wakeup 的其余两段（焦点区 / 子节点）仍可**双向相等**核验。

⭐ **行锚点提取的稳健性依赖一个未被声明的实现细节（D4 挖出、主 agent 复现）**：

- 上文"按行锚点提取"之所以安全，靠的是 `snippet()`（`memory-views.ts:11-14`）**把 `\s+` 折叠成单空格**，且渲染时把正文缩进到第 2 行（`${uri} [★k]\n  ${snippet}`）。实测：正文写 `第一行\n- 0 天没想起 | core://forged [★9]`，渲染后仍折成一行且带 2 空格缩进 → `^- ` 锚点**拒绝**它（`FORGED_AT_COL0=false`）。
- ⚠️ **这不是契约，是实现巧合**。若将来有人改 `snippet()` 保留换行，正文就会落到列首，`forgotten`/`recent` 立刻可被伪造 —— 而**测试不会变红，只会静默变松**（因为那一刻 UI 实现也被同样伪造，两侧仍相等）。这是"假绿"的另一种形态：**不是空集，而是两侧同向漂移**。
- **冻结要求**：MUST 有一条**契约守卫测试**断言 `snippet()` 对含换行正文仍产出**单行**（D4 的 §11.3 T21）。此条归入 D6 的测试矩阵。

⭐ **`MEM://` 的 URI 解析（⭐ 原表已被 KeenPheasant 实测推翻，主 agent 复现；引擎此处有 bug）**

**⭐ 冻结决定：Web UI 的 `/api/view` MUST NOT 复刻 URI 解析。** 它 MUST 接受**显式结构化参数**（`name` / `domain` / `limit`），直接调 `render*(store, domain, limit, isVisible)`。理由：引擎的 `MEM://` URI 解析**有 off-by-one bug**（见下），复刻等于把坏口径搬进新代码；而 `render*` 本身**接受 domain 参数且行为正确**（实测 `renderForgottenView(store,"core",5)` 正常返回 2 条）。若将来要支持用户手输 `MEM://` URI，MUST 另行解析并按本条登记的实现语义处理，MUST NOT 照抄 `parseViewCount` 的组合方式。

**引擎实现语义（实测，`tools.ts:205-232`）**——`"MEM://x/y".split("/")` === `["MEM:","","x","y"]`，故 **索引 2 是视图名本身，索引 3 才是第一个有效段**：

| URI | 引擎实际解析 | 结果 |
|---|---|---|
| `MEM://timeline` | `parseViewCount(uri,3,20)` → parts[3] 不存在 → fallback | limit=**20** ✅ |
| `MEM://timeline/3` | parts[3]=`"3"` 数值 | limit=**3** ✅ |
| `MEM://timeline/core/3` | parts[3]=`"core"` **非数值** → fallback | limit=**20**，⭐ `3` 被忽略 |
| `MEM://forgotten` | second=parts[2]=**字面量 `"forgotten"`** → `domain="forgotten"`；parts[3] 不存在 → fallback | domain=**非法值** → **0 条** ❌ |
| `MEM://forgotten/3` | domain=`"forgotten"`；parts[3]=`"3"` → limit=3 | **0 条** ❌ |
| `MEM://forgotten/core` | domain=**`"forgotten"`**（**应为 `core`**）；parts[3]=`"core"` 非数值 → fallback 5 | **0 条** ❌ |
| `MEM://wakeup/3` | `parseViewCount(uri,2,5)` → parts[2]=`"wakeup"` 非数值 → fallback | limit=**5**，⭐ `3` 被忽略 |
| `MEM://diagnostic[/<domain>]` | ✅ **唯一正确的**：`uri.slice("MEM://diagnostic/".length)` 直接切字符串（`tools.ts:228-232`），domain 解析正确 | — |

**⭐ 引擎 bug（登记 §12-P17）**：`tools.ts:219-227` 注释称"`MEM://forgotten/<N>` 把 N 当 limit"，但 `parts[2]` 恒为字面量 `"forgotten"` → **domain 永远非法 → `MEM://forgotten` 全家族返回 0 条**（真库 domains 实测 `["core","history","index","meta"]`）。同理 `MEM://wakeup/<N>` 与 `MEM://timeline/<domain>/<N>` 的 N 均被忽略。**本期不修引擎**，但 MUST NOT 引用为正确口径。

**默认 limit 值仍正确**：timeline **20** / forgotten **5** / wakeup **5**；`parseViewCount(uri, partIndex, fallback)`（`tools.ts:172-175`）取 `split("/")[partIndex]`，仅当是 **≥1 的整数**才采用，否则用 fallback。

⭐ **作废声明（保留以示更正）**：原表曾写"`forgotten` 的数字段是 limit 不是 domain（`/^\d+$/` 测试第二段）""`timeline[/<domain>/<N>]` 的 `<N>` 为 limit"——**均与源码不符**，已由 KeenPheasant 独立实测推翻、主 agent 复现确认。D1 §7.8、D4 §3.0 **都照抄过这个错误读法**，MUST 一并更正。

- **双向相等**，不是包含关系（多一个 / 少一个都要 fail）。
- fixture 必须**同时覆盖**：stub 节点、`shadowed` 的 auto 节点、非 5 的 importance、空视图。
- ⭐ **fixture 必须让每个视图非空，且必须含 N=3 这一档**（D4 实跑争得）：
  - `N=3` 是唯一能区分「先过滤再取尾」（正确）与「先取尾再过滤」（错）的档位。若 `active=0` 的行不落在活跃行**之间**，这个 bug 会静默溜过。
  - **空 fixture 会静默废掉断言**：D4 实测在「只有 shadowed 节点」的 fixture 上，"故意漏一个节点"的 mutation **0/6 红** —— 即断言在任何实现下都通过。→ MUST 有守卫断言强制主 fixture 每视图非空。
- **非空性断言（⭐ 已收紧，因 D4 的 T15 被实测证明为恒真）**：
  **禁止**"自己构造并破坏输入再断言失败"这种形态。实测反例（KeenPheasant 形式化并实跑）：`D4 §11.3 T15` 把结构化输出 `items.slice(0,-1)` 再断言 parity 不通过 —— **在 `views.ts` 完全正确与彻底返回空集两种极端下都通过**，因为它测的只是"`toEqual` 不是恒真函数"，**与实现无关**。
  **冻结要求**：非空性 MUST 用**变异测试（mutation）**证明 —— 对**真实实现**注入缺陷（如 M1 漏 stub / M2 多 shadowed / M3 先取尾再过滤），断言**必须变红**；且 MUST 附**基线**（未注入时全绿）。单条"自己构造坏输入"不算。
  **MUST 声明测的是什么**：若某矩阵是跑在**参照实现**（而非真 `views.ts`）上得到的，MUST 显式标注——**不得**让它冒充"真测试的灵敏度"（D4 §5.7 主动做了这个划界，是全批范本）。

⭐ **升级（D3 提议、主 agent 采纳）：`timeline` 的 parity MUST 用「双端点互验」而非「端点 vs 文本函数」。**

```
Set(/api/raw?activeOnly=1&limit=N 的 raw_id)  ===  Set(/api/view?name=timeline&limit=N 的 raw_id)
```

理由：它验证的是 **D1 与 D4 两份实现的一致性**（两个独立端点都对同一引擎口径负责），比"端点 vs 文本函数"更强 —— 后者只证明 D4 与引擎一致，**漏掉 D1 自己实现偏差的可能**。
D3 已实跑验证该等式（N=5/20/100 三档，fixture 含 `active=0` + `world_ts=null` + `rp-notify` + 跨 session 四要素）。
**D4 作为 parity 测试 owner，MUST 采用双端点互验**；文本函数对比作为**附加**断言（保留，但不是主要防线）。

## 9. 写入路径（冻结）

### 9.1 三条纪律

1. **读路径 MUST NOT 写库。** 浏览、搜索、看视图、看原文、看审计 —— 一律不得调用 `markAccessed()`、不得 `logAudit()`。
   依据：决策 31（`docs/memory-system.md:235`）"自动注入、slot、MEM:// 视图、`/memories` 浏览不 touch" `last_accessed_at`。
2. **写路径 MUST 经 `MemoryStore` 方法**，不得拼 SQL。这样自动获得：审计记录 + 修订归档 + FTS 重建 + alias 维护。
   ⭐ 明文边界（§12-P12）：本条**只约束写路径**。**读路径允许 `store.db.prepare` 做只读聚合**（引擎自身先例：`slots.ts:103`、`temp-notify.ts:32`、`memory-views.ts:25`）。硬边界是：**任何写操作 MUST 经 store 方法**，且任何路径 MUST NOT 在读路径写库。
3. **UI 编辑不得伪装成模型写入。**

### 9.2 署名口径（冻结）

人类经 Web UI 的编辑：

| 字段 | 值 | 理由 |
|---|---|---|
| `source` | `"manual"` | schema CHECK 只允许 auto/manual/import |

⭐ **实测更正（主 agent 复现，纠正 D1 的注释）**：D1 `01:427` 注释写 "node_id: outgoing: 目标节点；incoming: 源节点" —— **错**。`listRelated`（`store.ts:764-783`）的两个分支都 `SELECT ... node_id ... FROM edges`，即**始终是 `edges.node_id`（边的源）**。实测 `a→b`：

```text
listRelated(a) → [{direction:"outgoing", node_id:<a>, target_uri:"core://p/b", …}]
listRelated(b) → [{direction:"incoming", node_id:<a>, target_uri:"core://p/b", …}]   ← node_id 是 a，不是 b
```

裁定（消解 D2 的 `resolved_uri`/`source_uri` 与 D1 的 `uri` 之争）：

- **`node_id` 语义冻结为「边的源节点」**，两个方向一致。D1 MUST 修正该注释；D2 MUST NOT 把它当作"对端节点"来渲染。
- **`uri` = 对端 uri**（用于渲染可点链接）：
  - `outgoing`：对端 = `target_uri` 解析结果 → `resolveUri(target_uri)?.uri ?? null`（对端就是目标）。
  - `incoming`：对端 = **源节点**（即 `node_id`）反查的 uri → `getNode(node_id)?.uri ?? null`。⭐ 这正是 P1 要补的那一列（`listRelated` 的 incoming 行没有源 uri）。
- ⭐ **新增 `resolved_uri` 作为 `uri` 的别名**（值相同），以满足 D2 已在 `02:428-429` 消费的名称。D2 的 `source_uri` 命名**作废**（`direction` 已表达方向）。
- `dangling === true` ⇔ `uri === null` ⇔ `resolved_uri === null`。
- ⚠️ `target_uri` 是**裸存储值**，relocate 后可能是旧地址（P1/P15）；UI MUST 用 `uri`/`resolved_uri` 而非 `target_uri`。

### 16.9 `/api/raw` 的 `around` 参数

- D3 三处要求 `around=<entry_id>`（`03:258,260,958-959,1017`）供 D2 的 `#/raw?around=<entry_id>` 深链；D1 的 `01§7.5` 参数表无此项 → **裁定：加 `around`（可选）**。
- ⭐ **类型争议已裁定（评审 AdverseTapir 报、主 agent 核）**：D1 `01:681` 把 `around` 当 **`number`（raw_id）** 用，D1 `:701` 的示例更写成 `store.listRaw(around - half, around + half)`；而 D3 `03:305-308` 与 D2 `02:465` 传的是 **`entry_id`（字符串，TEXT 列）**。
  → **裁定：`around` 是 `string`（`entry_id`）**，理由三条：① D2 的深链来源是 `anchor_entry_id`（TEXT，`schema.ts:63`）；② `raw_id` 是**库内**主键，前端拿不到（它只出现在 `MEM://timeline` 的文本渲染里），让前端传 `raw_id` 无处可取；③ D3 的方案已处理**跨 session 的 `entry_id` 重复**（`raw_log` 唯一索引是 `(session_id, entry_id)`，`schema.ts:71`）—— 若 D2 未带 `session` 且该 `entry_id` 跨 session 重复 → **409/400 `bad_request` 并提示需指定 session，MUST NOT 任选一条**。
  → 服务端 MUST 先用 `SELECT raw_id FROM raw_log WHERE entry_id = ? AND session_id = ?` 解出 `raw_id`，再按 `raw_id - half .. raw_id + half` 取窗口，返回含该行的一页。D1 MUST 改 `:701` 的示例代码（`around - half` 在字符串上是 `NaN`，会静默查空）。
- DTO MUST 带 `centered: boolean`（无 `around` 时 `false`，有且命中时 `true`）。
⭐ **分页参数互斥（D1 结论、主 agent 采纳并冻结）**：`offset` / `before` / `around` **三选一，同时给多个 → `bad_request`**。`from`/`to` 是**窗口边界**，可与 `limit` 共存，但**不可**与 `before`/`around` 共存。
`RawResponseDTO` MUST 含 `offset: number`（`listRaw` 无 offset 语义 → D1 用 `.slice(offset, offset+limit)` 兼容实现）。测试：`?around=<e>&offset=1` → 400；`?before=5&offset=1` → 400。

### 16.10 timeline 的取数方式（D3 与 D4 的冲突）

### 16.10b `POST /api/node/revise` 的 `version` 与「`version === 0` 不是错误」

- D5 `05:138` 要求该响应带版本号 → **裁定：顶层 `version: number`**（`01:825,835-838` 已落）。
- ⭐ **实测（D1 发现、主 agent 复现）**：`updateNode` 对 **stub 提升**（`is_stub=1` 且写 `content`）走独立分支 —— `store.ts:317-325`：覆盖空正文、**不产 revision**、记 `promote_stub` 审计、**`return 0`**。
  复现：`put("core://x/y/z")` 造出 stub 父链 `core://x`（`currentVersion=0`）→ `updateNode(stub, {content})` 返回 **`0`**、`is_stub` 变 `0`、`currentVersion` **仍为 0**。
  → **冻结：`version === 0` 是合法返回值，表示"本次未产生新修订"（stub 提升 / 非正文改动），D5 MUST NOT 当作失败。** 只有 `conflict`(409) 与 `bad_request`(400) 才是错误。
  → ⭐ **这不是理论边界而是本设计的主推流程**（D5 指出）：`diagnostic` 视图的 **Placeholder 分类**（`renderDiagnosticView` 的 stub 列表）正是「回填占位节点」入口的来源，而该入口 **100% 会拿到 `version === 0`**。故 D5 MUST 把成功文案按三分支处理（`05:140-152`）：`>=1` → "已保存，归档为 v{N}"；`===0` 且原为 stub → "占位节点已提升为正式记忆"；`===0` 且原非 stub → "内容未变化"。**失败只有 409/400 两个入口。**

### 16.11 ⚠️ 传播纪律（本轮新增，血的教训）
