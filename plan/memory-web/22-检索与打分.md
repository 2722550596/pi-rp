## §1 一句话定位

把 `node_fts` 从单列 `fts5(node_id UNINDEXED, text)` 改成**双内容列** `fts5(node_id UNINDEXED, text, disclosure)`，让 disclosure 成为**可独立加权的检索列**；`text` 不再混入 disclosure。**检索候选粒度保持「每节点一行」**，入口（别名/联想边）级的 disclosure **不进 FTS**（§5.4 给出论证与两个备选方案）。

## §3 行为契约逐步

### §3.1 `reindexNode(nodeId)` — 写入侧

```
1. node = getNode(nodeId); 若 null → return            （store.ts:1420-1421 不变）
2. DELETE FROM node_fts WHERE node_id = ?              （store.ts:1422 不变）
3. 若 node.is_stub → return                            （store.ts:1423 不变：stub 永不进 FTS）
4. keywords = SELECT keyword FROM glossary WHERE node_id = ?   （store.ts:1424-1428 不变）
5. text := tokenizeForSearch([node.uri, node.content].join(" "))
      ← ⚠️ 相比现状 store.ts:1429 **移除了 node.disclosure**
6. 若 keywords 非空 → text += " " + keywords.join(" ")  （store.ts:1430-1433 不变）
7. disclosureText := tokenizeForSearch(node.disclosure ?? "")
8. 若 text 与 disclosureText **都为空** → return        （见下，与现状 store.ts:1434 略不同）
9. INSERT INTO node_fts (node_id, text, disclosure) VALUES (?, ?, ?)
```

**为什么第 5 步必须把 disclosure 从 text 里拿掉**：否则 disclosure 同时存在于 `text`（被权重加权）与 `disclosure`（再被加权）→ **同一批词被双重计分**，且新列形同虚设。遗漏后果：`§10 A2/A3` 断言失败。

**为什么第 7 步要用 `tokenizeForSearch` 而不是原样塞**：新增列与 `text` 列**必须活在同一个 token 空间**——`tokenize.ts:7-12` 的纪律要求写入侧与查询侧同源；若 disclosure 列塞原文而 text 列塞分词结果，两者的词元粒度会不同（例如 CJK 原文未切分 → 只有整串成为一个词）。实测（`probes-d2/d2-evidence-isolate.mjs`（seam 段））：`tok(join(uri,disc,content))` 与 `tok(uri+content) ∪ tok(disc)` 在两库 **120/120、73/73 节点上 token 集合完全相同**，故拆列不改变任何命中——这是「拆列是安全的」的形式证明。遗漏后果：disclosure 列的 CJK 词粒度与 text 列不一致，部分 disclosure 词搜不到。

**为什么第 8 步要把空判改成「两列独立」**：现状 `if (!text) return`（`store.ts:1434`）在 text 为空时**整行不建**。改后 text 与 disclosure 是两列，若仍用 `if (!text) return`，则「正文为空但有想起条件」的节点整行不建，其 disclosure 词永远搜不到。**诚实说明**：由于 `text` 里含 `node.uri`（恒非空），真实的非 stub 节点 `text` 几乎不可能为空——**这一步主要是防御性的**（保证「两列各自为空判空」的语义自洽），不是热路径上的关键修复。**改法**：`if (!text && !disclosureText) return;`。

> 副作用提示：FTS5 的 `bm25` 对**空列**（零词）的文档给 0（实测 `probes-d2/d2-evidence-isolate.mjs`（arity 段）/ §7）。空 disclosure 列会**削弱**该节点在 bm25 tiebreak 上的得分（bm=0 比 -x 差）。由于 bm25 只是第 4 级 tiebreak、且现状（v2）里空 disclosure 根本不占列，这会让「无想起条件」的节点在**完全同分**时略微靠后——三段隔离 (a) 实测两库 86/86、73/73 排序不变，故接受。

### §3.2 `searchNodeFts(queries)` — 查询侧

现状（`store.ts:1009`）：
```sql
SELECT node_id, bm25(node_fts) AS bm FROM node_fts WHERE node_fts MATCH ? ORDER BY rank
```
改为：
```sql
SELECT node_id, bm25(node_fts, ${NODE_FTS_BM25_WEIGHTS}) AS bm
FROM node_fts WHERE node_fts MATCH ? ORDER BY rank
```

**关于是否显式带权重（主 agent 复核后订正，本文原说法有误）**：实测（`probes-d2/d2-evidence-isolate.mjs`（bare 段））证明 **`bm25(node_fts)` ≡ `bm25(node_fts, 1.0, 1.0)` ≡ `bm25(node_fts, 0.0, 1.0, 1.0)`**（三者数值逐位相同，包括「doc 长度差异」被正确计入）。⇒ **在本文推荐的 `1.0/1.0` 下，显式写权重与 bare 完全等价，纯属行为保持**（这正是推荐值「最小惊讶」的理由之一）。
> **那还需要显式写吗？需要。** 价值不在「改变数值」，而在**把口径钉成契约**：显式常量让 §10 A6 能锁「权重串元数 == 列数」（防 E2 静默陷阱），且在将来有人改推荐值（如改回 2.5）时**一眼可见**。bare 写法会把这个决策藏进 FTS5 的默认值里。

**`ORDER BY rank` 的真相（实测，可跑证据见下）**：`rank` 是 FTS5 内建列，**用默认权重（全 1.0）** 计算，**忽略** SELECT 里 `bm25(...)` 给的自定义权重；而 SELECT 出来的 `bm` 用自定义权重。两者可以不一致。
```
$ SRC=/tmp/d2exp/cur.db node --experimental-strip-types plan/memory-web/probes-d2/d2-evidence-isolate.mjs
# …（等其余段）
rank-vs-custom: ORDER BY rank=AB  bm25(1.0,1.0)=AB  bm25(0,2.5,1.0)=BA
rank ignores custom weights: true
```
构造：节点 A 的查询词只在 `disclosure` 列，节点 B 的只在 `text` 列。`ORDER BY rank` 与 `ORDER BY bm25(t,1.0,1.0)` **同序**（证明 rank ≡ 全默认权重），而与 `ORDER BY bm25(t,0.0,2.5,1.0)` **反序**（证明自定义权重**不**影响 `rank`）。
> 📌 该段落在 `probes-d2/d2-evidence-isolate.mjs` 末尾「(iv)」，无真库也能跑（用 `:memory:` 自建表）。

**但 `searchNodeFts` 没有 LIMIT**（`store.ts:1007-1012`），全部命中行都进 `hits` Map，且只有「每节点最小值」被保留（`store.ts:1013-1016`）→ **`ORDER BY rank` 对本函数是可观测性为零的遗留物**。本文**保留它**（无成本、无风险），但明确记录：它不参与打分，**不要**据此认为权重生效了。

**权重真正生效的位置**：`rank()` 的 tiebreak（`recall.ts:257-259`）——`a.bm25 ?? +∞`。即：只有当 `score`、`kw`、`vec` 三项**全相等**时，bm25 排序才被使用。

> ⚠️ **列限定语法在本函数里不可用**：FTS5 支持 `disclosure:"X"` / `text:"X"` 按列过滤（原生 SQL 下可分辨；见 §10 A3 附注），但 `searchNodeFts` **先把 query 过 `tokenizeForSearch`**（`store.ts:1000`），`disclosure:"X"` 会被切成 `disclosure : " X "`（实测：`tokenizeForSearch('disclosure:"晚香玉"') === 'disclosure : " 晚香玉 "'`）→ 列限定语法被破坏。**这是既有设计（查询侧与索引侧同一 token 空间）的必然结果，本次不引入该语法。** 若将来要支持按列过滤，需在 `searchNodeFts` 外层单独解析，不能复用该 tokenizer。

### §3.3 `reindexAll()` — 新增

```ts
/** 全量重建非 stub 节点的 FTS 行。迁移入口（D3）。 */
reindexAll(): void {
  this.db.transaction(() => {
    const rows = this.db.prepare("SELECT node_id FROM nodes WHERE is_stub = 0").all();

}
```

### §5.2 bm25 权重：**实测推翻契约建议的 2.5**（任务第 2 问，契约 §11 U2）

#### 事实先摆

1. **pi-rp 的 bm25 不是打分项**：`recall.ts:231-235` 的 score 完全由 `vec/kw/importance/recency` 决定；bm25 只在 `rank()` 的 tiebreak 第 4 位（`:257-259`）。契约 §1.3 说 pi-rp「无 bm25 权重表」——准确说，是**bm25 从未在 pi-rp 打分里出现过**。
2. **权重不影响候选选择**（MATCH 是布尔的）。实测（`d2-evidence-isolate.mjs` 的 (b) 段与 §5.2 事实 2）：把 disclosure 列权重设为 `0.0`，`MATCH` 命中数**完全相同**。⇒ **权重 0 不等于「不进索引」**，只等于「命中它不加分」。
3. **nocturne 权重串的 2.5 位是 `path`，不是 `content`**。契约建议「text 给 2.5（对应 nocturne 的 path 权重位）」——**该对应关系在 pi-rp 不成立**：pi-rp **没有** `path` 列。pi-rp 的 `text` = `uri + content + glossary`（`store.ts:1429-1433`），是 nocturne 的 `uri`(2.0) + `content`(1.0) + `search_terms`(0.75) **三者合并**，找不到单一的对应权重位。更诚实的读法：nocturne 串里紧邻 `disclosure`(1.0) 的是 `content`(1.0) 与 `search_terms`(0.75)——**pi-rp 的 `text` 与 `disclosure` 最贴近的权重都是 `1.0`**，故 `1.0/1.0` 比 `2.5/1.0` 更有依据。（`[推断]`：这属于「相似度打分」而非可证明的恒等式，故本文只用它**支持**而非**决定**推荐值；决定性的仍是下面的实测。）

#### ⚠️ 第一轮数字全部作废（方法学事故，必须记录）

本文初稿的「73 节点 / `2.5` 扰动 13/73」**是错的**，两处硬伤：

1. **真库引用未连路径**（主 agent 的纪律）：本机有 9 个 `elias/memory.db`。我最初取的是 `hackathon-video/templates/fpal/characters/elias/.pi/memory.db`（**模板/旧副本**，73 节点），而**现库**是 `world/magnolia/elias/.pi/memory.db`（**120 节点 / 86 带 disclosure / 3 别名 / 49 glossary**）。
2. **未 checkpoint 的 WAL 被丢失**：真库是 `journal_mode=wal` 且带 4 MB 未合并的 `-wal`。`cp memory.db out.db` **不带 `-wal`** ⇒ 我读到的是一份**更旧的快照**，且随原库写入而变。这解释了「同一脚本两次跑出不同数字」。

**修正后的纪律**（详见 §10.0，含实证）：**快照 MUST「先固化源库」——首选 `VACUUM INTO`，或「先对源库 `wal_checkpoint` 再 `cp`」；MUST NOT「先 cp 再对副本 checkpoint」**（该顺序补救不了已经复制走的旧快照——本文初稿正是踩了这个）。且 MUST 记录真库完整路径。下面的数字全部来自 `VACUUM INTO` 快照 `cur.db` 与 `tmpl.db`，且已复跑两次一致。

#### 实测（契约 §7 门槛 1 三段隔离，`probes-d2/d2-evidence-isolate.mjs`）

**关键前提**：`bm25` 只做 tiebreak，**所以「权重」这一变量只能在「score/kw/vec 三者全等」的邻居之间产生差异**。三段对照把它们拆开：

| 对照 | 固定 | 变动 | 现库 cur(120/86 查询) | 模板 tmpl(73/73 查询) | 归因 |
|---|---|---|---|---|---|
| **(a) DDL/列布局** | 同一 token 多重集、无权重 | 2 列(disclosure 并入 text) vs 3 列(独立列) | **86/86** | **73/73** | ✅ **列布局本身零语义差**（充分必要条件） |
| **(b) 权重** | 同一文本、3 列 | bare ≡ `1.0,1.0` → `0.0, 2.5, 1.0` | 73/86 | 60/73 | 权重差异，**仅 tiebreak** |
| **(b') 恒等校验** | 同一文本、3 列 | bare vs `0.0, 1.0, 1.0` | **86/86** | **73/73** | ⚠️ **这是同义反复校验**（见下） |
| **(c) 文本修复** | 3 列 + `0.0, 1.0, 1.0` | 存量(陈旧) text vs 重算 text | 69/86 | 73/73 | 迁移的**期望行为**（陈旧修复） |

**top-1 在所有档位、两个库上全同**（86/86、73/73）——权重与文本修复**都不改变第一条召回**，只动同分邻居。

> ⚠️ **(b') 不是「零扰动的新方案」，是「同义反复的行为保持校验」**：主 agent 已实测 `bm25(t) ≡ bm25(t,1.0,1.0)`（FTS5 默认权重即全 1.0），本文 `probes-d2/d2-evidence-isolate.mjs`（bare 段） 独立复现（逐位相同）。⇒ (b') 的对照双方**本就是同一个函数取值**，`86/86` 必然成立。**它的价值不是「证明改动无回归」（没改动），而是「证明推荐值 == 现状默认」**——即本次推荐**不引入任何行为变化**。这正是「最小惊讶」的判据。**不要把 (b') 的 86/86 当成「实测验证了 1.0/1.0 更优」**——本文的正面证据是 **(b) 显示 2.5 会引入噪声**。

**(a) 的意义**：这是唯一能证明「拆列没改语义」的对照。它不是 100%（初版我给错构造，曾得 37/86）——**只有当 2 列把 disclosure 折进 `text`、3 列把它拆出，且两者 token 多重集相同时**，(a) 才应为 0 差异。本文的 `86/86` 就是这个构造下的结果。

**(c) 的意义**：现库**存量 FTS 文本陈旧**。实测（`probes-d2/d2-evidence-isolate.mjs`（staleness 段），两个判据都给）：
```
cur(现库) : n=49  glossary 词不在 node_fts.text 中：字面子串缺 30 / 整 token 缺 33
tmpl(模板): n=17  glossary 词不在 node_fts.text 中：字面子串缺  9 / 整 token 缺  9
样本: 问好 / p4告警 / 老板观察力挺强的 / 卢卡斯 / 枯萎 / 蒜苗回锅肉 …
```
⇒ 与主 agent/D3 复核的结论**同向**（数量口径不同：我用「字面子串」得 30，与主 agent 的 30/49 一致；用「整 token」得 33）。**同源于上一轮 §17 的 glossary reindex 时序 bug**——当时只修了 `import()`，**存量库仍带陈旧**。迁移全量 reindex 会修好它们 → (c) 的 17/86 差异**是期望行为**。

### §5.4 边级 disclosure 能否进 FTS（任务第 3 问，**核心难题**）

**约束**：`node_fts` 的稳定列是 `node_id`（`UNINDEXED`），本质是**一节点一行**；而入口（`aliases`/`edges`）可以有 N 条。二者基数不匹配。

#### 方案 1（**裁定：采用**）——FTS disclosure 列 = `nodes.disclosure`（节点级），入口条件不进 FTS

- 语义：FTS 承载「该节点自身的想起条件」，与 `rank()`/`keywordScore()` 读的 `MemoryNode.disclosure` 同源。
- **与新版 `effectiveDisclosure` 的关系**：主 agent 已裁定 `effectiveDisclosure` **镜像 `resolveUri`（`nodes.uri` 优先）**（IRC 2026-09-16）。⇒ 在**非死别名**场景，`effectiveDisclosure(node.uri) ≡ node.disclosure`。**FTS 列与 effective 值在规范 uri 上恒等**，故 `reindexNode` 直接读 `node.disclosure` 即可，**无需调 `effectiveDisclosure`**（省一次查询；且 `reindexNode` 是热路径）。
- **代价（必须承认）**：**只在入口条件里出现的词，keyword 模式搜不到**。实测（`probes-d2/d2-evidence-entry.mjs`）：给节点挂一个别名，别名 disclosure = 「当我经过离心机时」，而「离心机」在该节点 uri/content/disclosure 中**一次都不出现** → 方案 1 查 `离心机` 得 **0 命中**；方案 2 得 **1 命中**。
- **为何仍采用**：见方案 2 的反证。

#### 方案 2（**否决**）——把入口条件合并进该节点的 FTS disclosure 列

实测（`probes-d2/d2-evidence-entry.mjs`，完全相同的合成别名）：
```
Option A（方案 1）: 查 "离心机" -> 0 row(s);  查 "示波器" -> 0 row(s)
Option B（方案 2）: 查 "离心机" -> 1 row(s);  查 "示波器" -> 1 row(s)
```
**否决理由——归因说谎**：用户搜的是「别名入口 `core://entries/bench` 的条件」，返回的是 **target 节点**（`core://identity/habits`）。随后 UI / 注入会展示该**节点**的条件（或另一个入口的条件）——**与用户搜的词毫无关系**。这正是契约 §8 T5「静默缺陷」。**FTS 行无法承载入口身份，硬塞必然错配。**

#### 方案 3（**否决**）——每入口一行 FTS

- 破坏不变量：`searchNodeFts` 返回 `Map<node_id, number>`（`store.ts:993`）；`buildPool`（`recall.ts:185-197`）与 `rank()`（`:214`）全是**节点级**。每入口一行会让同一 node_id 出现多行 → Map 语义需重定义 → 调用链全改。
- 收益（「命中入口可归因」）当前**无消费者**：`RecalledItem`（`recall.ts:45-57`）没有 entry 维度。
- 成本/收益严重不成比例 → 本轮不做。

#### 边界：向量通道的补偿（记为待办，不实现）

若将来要覆盖方案 1 的代价，最轻的路径是**只补进 vector 打分文本**：D1 已提供 `listAliasEntries(targetNodeId): Array<{alias_uri, target_node_id, disclosure, dead}>`（D1 `21-数据模型与语义核心.md:53-72` 定稿**四字段**；`disclosure` 已是 effective 值，`dead` 标注死别名——D5 的 `toAliasEntryDTOs` 消费同形）。把入口条件 join 进 `embedDocText` 的第三参（`embeddings.ts:101`）即可——**但这会改变 embed 输入文本 → 改变 md5 缓存键（`embeddings.ts:96`）→ 全库重新嵌入一次**。故本轮不做，登记为 §12 待办。

### §5.6 `SearchItemDTO.disclosure` 的口径（主 agent 指派 D2 裁定）

**事实**：`src/web/serialize.ts:175-178` 有 `SearchItemDTO.disclosure: string | null`，由 `routes.ts:351`（`disclosure: item.disclosure`）填充，**来源是 `recall.ts` 搜索结果的节点级 `item.disclosure`**（`recall.ts:239`）。

**裁定：选项 (b) —— 改 `effectiveDisclosure(node.uri)` 口径。**

理由（三点，逐条可核）：
1. **数值上等于现状**：搜索结果只有 uri、没有「从哪个入口进来的」语义；命中的是节点。`effectiveDisclosure(node.uri)` 在规范 uri 上**恒等于** `node.disclosure`（主 agent 镜像裁定，§5.5/§11 C4）。⇒ **改口径不改变任何搜索结果的显示值**，零 UI 回归。

3. **不选 (a) 的理由**：(a)（保持裸 `nodes.disclosure`）与 (2) 冲突——它把「唯一的例外」留在最显眼的搜索页。(c)（UI 特殊标注「这是节点条件」）**不必要**：既然 (b) 与 (a) 数值相同、且是唯一正确读法，标注会制造一个不存在的不一致。

**追问：`rank()` 自身要不要改（`recall.ts:236-248` 构造 `RecalledItem.disclosure`）？**

> **D2 的答案：不改 `rank()`，改喂给它的输入。** `rank()` 是**纯函数**（`recall.ts:213` 注释：「Pure: no I/O」）——它不能持有 store，改它会破坏这条性质。而 `recall.ts:239` 直接透传 `doc.disclosure`。**正确落点**：在 `search()`（`recall.ts:362`）/ `store.recall()`（`store.ts:1146`）组装 pool 时，把每个 `MemoryNode.disclosure` 替换为 `store.effectiveDisclosure(node.uri)`。但这些路径的候选是 `buildPool` 节点级（`recall.ts:185-197`），逐节点调 `effectiveDisclosure` 是 O(n) 次查询。
>
> ⇒ **务实结论：本轮 `rank()`/`search()` 不动**（因为数值恒等、且 O(n) 查询会伤热路径），**只要求 `serialize.ts` 的 DTO 组装点用 `store.effectiveDisclosure(item.uri)` 覆盖 `item.disclosure`**（单点、O(topK)）。**这样 UI 口径统一、搜索语义不变、热路径不受影响。** 若将来别名语义改变使二者不再恒等，UI 侧已经是对的，打分侧再单独立项。

> 📌 **这在 `serialize.ts`/`routes.ts` 落点，属 D5 地盘**（D2 只给裁定）。D5 MUST 在 `SearchItemDTO` 组装处调用 `effectiveDisclosure`，**MUST NOT** 直接透传 `item.disclosure`。

> 📌 **诚实结论**：本改动自身的**排序效果为零**（(a) 86/86、73/73 证明布局中立；`1.0/1.0` 亦零扰动）。它的价值不在排序，而在 **(a) disclosure 成为可独立加权的列**（为将来 `W_DISCLOSURE` 打分项铺路，对齐 nocturne 的独立列结构）、**(b) 移除「disclosure 混在 text 里被 content 权重放大」的口径污染**、**(c) 修复 R1 缺陷**、**(d) 迁移时顺带修好存量陈旧 FTS 文本**。**不应把本改动宣传成「改善检索质量」**——实测不支持。这是契约 §8 T6「断言症状=把 bug 奉为规范」的反面纪律。

### §9.2 迁移影响

- **FTS 表必须 DROP + 重建**（FTS5 不能 ALTER，契约 §8 T9）。全量重建走 `reindexAll()`（§3.3）。

- **重建次数**：D3 一次全量；此后的增量全部经 `reindexNode`。

### §10.0 排序验收 MUST 是三段隔离（契约 §7 门槛 1，主 agent 修订后）

**MUST NOT** 只给单一的「改动前 vs 改动后 top-N 逐位对比」——那会把三个原因混成一团（§7 门槛 8「失败 MUST 归因到错误类型」同源）。**MUST 给三段，每段：命令 + 输出 + 归因**：

|---|---|---|---|
| **(a) DDL/列布局** | 同一 token 多重集 + 旧权重（无） | 2 列（disclosure 并入 text）vs 3 列（独立列） | **差异 = 0**（否则是 bug，(b)(c) 不可信） |
| **(b) 权重** | 3 列 + 同一文本 | 无权重 → `0.0, 2.5, 1.0`（或建议的 `1.0, 1.0`） | 差异可量化（应仅 tiebreak 级） |

本文 §5.2/§5.3 已给三段实测（`probes-d2/d2-evidence-isolate.mjs`，两个真库）。**D3 的迁移验收 MUST 引本表**，并把 (c) 的差异解释为「存量陈旧被修好」而非回归。

**真库纪律（本文方法学事故的教训）**：

1. **引用真库 MUST 连完整路径**（本机 9 个 `elias/memory.db`）。
2. **快照 MUST「先固化源库」**：首选 `VACUUM INTO`，或「先对**源库** `wal_checkpoint`、再拷贝」。**MUST NOT「先拷贝、再对副本 checkpoint」**。
3. **harness MUST 先与真 `store.recall()` 对拍**（10 条查询逐位一致），再用于对比。
4. **跑完清理 /tmp 大文件**（tmpfs 曾 100% 满）。

**为什么第 2 条的「拷贝后再 checkpoint 副本」是错的（本文事故根因，实证）**：
- 不带 `-wal` 的 `cp memory.db out.db` **当场就复制了旧快照**（WAL 里的新数据没进去）；
- 事后对**副本**跑 `PRAGMA wal_checkpoint(TRUNCATE)` 只作用于**副本自己的** `-wal`（通常为空）——**补救不了**。

**实测**（`/tmp/d2exp`，让写者持锁 + `wal_autocheckpoint=0` 造出 222 KB 未合并 WAL，随后建表写 50 行）：
```
源库真相（读到 WAL）              : 50 rows
A 裸 cp（不带 -wal）             : no such table: walprobe   ← 新表整张丢
B cp 后对【副本】checkpoint      : no such table: walprobe   ← 同样丢（顺序错了无效）
C VACUUM INTO                    : 50 rows                   ← ✅ 正确
D 先对【源库】checkpoint 再 cp   : 50 rows                   ← ✅ 正确
```
⇒ 正确写法：`sqlite3 "file:<源库>?mode=ro" "VACUUM INTO '<快照路径>'"`（首选），或 `sqlite3 <源库> "PRAGMA wal_checkpoint(TRUNCATE)"` **之后**再 `cp`。
