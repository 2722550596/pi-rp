## 3. 三个模板的解剖：为什么抄 `grep` 而不是抄 `write`

`write` 的**骨架**可抄，`write` 的**高亮**不可抄。

| 维度 | `write.ts:234-268` | `grep.ts:375-384` | 本设计采用 |
|---|---|---|---|
| `lastComponent` 复用 | ✅ `?? new WriteCallRenderComponent()` | ✅ `?? new Text("",0,0)` | **抄 grep 的极简式** |
| 高亮 | `highlightCode(code, getLanguageFromPath(path))`（`:152-155`） | 无 | **不抄**（§10.7 实测有害） |
| 增量缓存 | `updateWriteHighlightCacheIncremental`（`:96-127`） | 无 | **不抄**（无高亮则无缓存） |
| 行截断 | `maxLines = expanded ? all : 10` + keyHint（`:158-164`） | 无（result 侧 `:106-112` 有 15 行 + keyHint） | **抄**（调用侧 `MAX_CALL_LINES`，结果侧 `MAX_RESULT_LINES`） |
| 失败路径 | `formatWriteResult` 只在 `isError` 时吐字（`:170-185`） | 直接渲染全文 | **抄 grep**（见 §5.4：本场景软失败无 `isError`） |
| 空结果 | 返回**空 `Container`**（`:258-263`） | 返回可能为空的 `Text` | **抄 write 的 return 空组件，不 return undefined** |

结论：**渲染器 = `grep` 的三行式 + `write` 的「复用 lastComponent / 截断 / keyHint / 空组件」四条骨架，砍掉全部高亮。**

### 5.3 裁定 J5：`revise` 的 renderCall **不复用 `renderDiff`**

三条独立理由，每条都有 `file:line` 或实测：

1. **没有 diff 的输入。** `renderDiff(diffText)`（`diff.ts:79`）吃的是 `generateDiffString` 产出的 `-N old / +N new /  N ctx` 格式（`edit-diff.ts:380-431`）。`edit` 能拿到是因为有 `details.diff`（`edit.ts:356-365`）。memory **没有** before-body：`revise` 的三种编辑模式里，`append` 与 `line` 连「被替换的原文」都不存在；`old_text→new_text` 只有**片段**，不是文件，凑不出带行号的 diff。
2. **格式敏感、静默退化。** 实测（probeH）：`renderDiff("-b\n+X")` 的**两行都被涂成 `toolDiffContext`（灰）**，因为 `parseDiffLine` 的正则 `/^([+-\s])(\s*\d*)\s(.*)$/`（`diff.ts:9`）要求 `+`/`-` 后紧跟空白。⇒ 手搓 diff 得到「一堆灰字」，不报错、不红测，**看起来像坏了但没人知道**。对照：`renderDiff("- b\n+ X")` 正常红/绿。
3. **批量语义不同。** `revise` 的 `batch`（`tools.ts:504`）是 N 条**异构**操作（改重要性 / 追加 / 替换混在一起），把它们拼成一个「文件 diff」在语义上是错的。

**替代方案（采用）**：call 侧渲染成「**逐条操作摘要**」：

```
修订记忆
  core://a  ★重要度 → 2
  core://b  ＋追加「（补）」
```

### 5.4 裁定 J4：`renderResult` 显示 1 行确认，**不显示空白**

`renderResult` 对 memorize/revise **共用同一个实现**（§4.2）：**原样渲染 result 文本**（`getTextOutput`，`render-utils.ts:39-64`），只做行截断与着色。

```
memorize 成功   → | 已记下 core://identity @ 2026-06-05        |
revise  成功   → | 已修订：core://a                               |
memorize 软失败 → | URI 已存在：core://x（改写请用 revise）          |
```

**为什么不显示空白**（前两条实测）：

1. **空白在 export 里会退化成 JSON dump。** 实测（probeE）：`renderResult` 返回空 `Container` → `createToolHtmlRenderer` 产出 `{expanded: ""}`；`template.js:1029` 的守卫是 `if (rendered?.callHtml || rendered?.resultHtmlCollapsed || rendered?.resultHtmlExpanded)` —— 空串**是 falsy** ⇒ 掉进 `else` 分支（`template.js:1054-1058`）**打印 `JSON.stringify(args, null, 2)`**。⇒ 「空白」在导出 HTML 里反而是**最啰嗦**的那一种。
2. **空白挡不住软失败。** 若渲染器写「成功就渲染空、失败就渲染文本」，它需要知道成功 —— 而 `isError` 全是 `false`（§1.4a）。要靠 `details.ok` 硬编码判断，多一处可漏的分支。
3. **1 行确认是「写成功」的唯一 UI 事实。** 用户看不到别的反馈，`memorize` 没有其它 UI 出口。

**空白没有收益（实测）**：`renderResult` 返回空 `Container` 时**不增加任何可视行**（probeL：结果前后都是 7 行），但 `hasContent` 仍被置真（`tool-execution.ts:315`），所以 `hideComponent` 不会被设（`:367-369`）—— 除非 `renderShell: "self"`。想「整行消失」只能靠 `self` shell，而本期**不用** `self`（§2.2），所以空白**并不能**换来更紧凑的界面，只换来 export 的 JSON dump。

## 6. 裁定 J3：改动顺序（任何中间态都不是净丢失）

```
S1  注入 renderCall + renderResult（§4.2 + agent-session 的 1 行）      ← 纯增益：UI 多出流式视图，content 一字未动
S2  返回值加结构化字段（memorize 的 ok/uri；revise 的 failed_uris），文案不动   ← 纯增益：无消费者改变
S3  删掉 startsWith("已修订")，failed 读结构体（§5.2）        ← 等价替换：failed 数值与文案全不变
S4  收窄 memorize result content：nodeRow → nodeLine（§5.1）  ← 唯一「变少」的一步
```

**为什么 S4 不是净丢失**（前两条可 grep 验证）：

- 被删的是**正文回显**，而正文在**同一条 assistant 消息的 tool_use 参数**里，模型看得到（`anthropic-messages.ts:1237-1243` `input: block.arguments ?? {}`；`openai-completions.ts:1264-1268`）—— **实测**（probeM）流式参数逐字到达。
- compaction 摘要同时吃 tool calls 段（`compaction/utils.ts:127-133` 拼 `name(k=v)`）与 tool result 段（`:141-145`），**删后者不丢信息**。
- UI 侧同时**多**了一个 renderCall（S1 已落地），正文从 tool result 搬到 tool call，**可见性只增不减**。

**S4 之前必须先做完 S1**：否则收窄 content 会让「TUI 没有正文 + result 也没有正文」= **真的什么都看不见**。这是本设计的**硬序约束**。

**回滚粒度**：S4 是唯一影响 LLM 上下文的改动 ⇒ 若事后发现模型因缺正文回显而行为退化，**只回滚 S4**（还原 `nodeLine` → `nodeRow`），S1–S3 全部保留。

```ts
/**
 * Renderers for the memory tools (memorize / revise).
 *
 * Injected by name from agent-session's memory-module host: the memory package
 * stays headless (packages/memory must not depend on coding-agent, slots.ts:17),
 * so render — a pure TUI concern — lives here.
 *
 * Deliberately does NOT reuse write's highlighter: memory bodies are prose, and
 * getLanguageFromPath() misreads a memory URI as a language
 * (getLanguageFromPath("core://a/b.json") === "json", measured).
 */
import { Text } from "@earendil-works/pi-tui";
import { keyHint } from "../../modes/interactive/components/keybinding-hints.ts";
import type { Theme } from "../../modes/interactive/theme/theme.ts";
import type { ToolDefinition, ToolRenderResultOptions } from "../extensions/types.ts";
import { getTextOutput, str } from "./render-utils.ts";

type Args = Record<string, unknown> | undefined;

/** Collapsed body cap for the call side, mirroring write.ts:158. */
const MAX_CALL_LINES = 10;
/** Collapsed result cap, mirroring grep.ts:106. */
const MAX_RESULT_LINES = 15;

/** memorize args: the body the user wants to see streaming. */
function bodyOf(args: Args): string | null {
	return str(args?.content);
}

function truncate(theme: Theme, lines: string[], max: number, expanded: boolean): string {
	const shown = expanded ? lines : lines.slice(0, max);
	let text = shown.map((l) => theme.fg("toolOutput", l)).join("\n");
	const remaining = lines.length - shown.length;
	if (remaining > 0) {
		text += `${theme.fg("muted", `\n... (${remaining} more lines, ${lines.length} total,`)} ${keyHint(
			"app.tools.expand",
			"to expand",
		)}${theme.fg("muted", ")")}`;
	}
	return text;
}

/**
 * memorize ≈ write: header + streaming body.
 * Never throws: any malformed arg degrades to a placeholder (an exception here
 * falls back to the bare-name renderer but poisons `lastComponent`; see §10.5).
 */
export function renderMemorizeCall(args: Args, theme: Theme, context: ToolRenderContextLike): Text {
	const component = (context.lastComponent as Text | undefined) ?? new Text("", 0, 0);
	const uri = str(args?.uri);
	const body = bodyOf(args);
	const head = `${theme.fg("toolTitle", theme.bold("铭刻记忆"))} ${theme.fg(
		"accent",
		uri === null || uri === "" ? "…" : uri,
	)}`;
	// req() guards the pre-stream window: the first message_update can fire with
	// args === {} (or undefined) before any field has arrived (measured, probeB/K).
	let text = head;
	if (body) {
		text += `\n\n${truncate(theme, body.replace(/\r/g, "").split("\n"), MAX_CALL_LINES, context.expanded)}`;
	} else if (!context.argsComplete) {
		text += theme.fg("muted", "\n(写入中…)");
	}
	component.setText(text);
	return component;
}

/** revise ≈ edit: a per-mod summary, NOT a diff (J5 — see §5.3). */
export function renderReviseCall(args: Args, theme: Theme, context: ToolRenderContextLike): Text {
	const component = (context.lastComponent as Text | undefined) ?? new Text("", 0, 0);
	const single = str(args?.uri) ? [{ uri: str(args?.uri), ...(args ?? {}) }] : [];
	const batch = Array.isArray(args?.batch) ? (args.batch as Array<Record<string, unknown>>) : single;
	const lines = batch.map((m) => {
		const uri = typeof m.uri === "string" && m.uri ? m.uri : "…";
		return `${theme.fg("accent", uri)}  ${describeMod(m, theme)}`;
	});
	let text = theme.fg("toolTitle", theme.bold("修订记忆"));
	if (lines.length > 0) {
		text += `\n${truncate(theme, lines, MAX_CALL_LINES, context.expanded)}`;
	}
	component.setText(text);
	return component;
}

function describeMod(m: Record<string, unknown>, theme: Theme): string {
	if (typeof m.old_text === "string") {
		// "->" not U+21C4: Ambiguous width (see 7.4).
		return theme.fg("toolOutput", `替换「${m.old_text}」->「${m.new_text ?? ""}」`);
	}
	if (typeof m.append === "string") return theme.fg("toolOutput", `＋追加「${m.append}」`);
	if (typeof m.line === "number") return theme.fg("toolOutput", `行 ${m.line} ← 「${m.line_content ?? ""}」`);
	if (typeof m.importance === "number") return theme.fg("toolOutput", `★重要度 → ${m.importance}`);
	if (typeof m.when === "string") return theme.fg("toolOutput", `想起条件 → 「${m.when}」`);
	if (typeof m.time === "string") return theme.fg("toolOutput", `世界时间 → ${m.time || "(清除)"}`);
	return theme.fg("muted", "（无内容改动）");
}

/**
 * Shared result renderer: echo the tool's own confirmation text.
 *
 * MUST return a Component, never undefined: `undefined` is addChild'ed and then
 * thrown on by the next render() with no catch in the TUI pipeline (§10.4).
 * Empty `Container` (write.ts:258-263) is the escape hatch when there is truly
 * nothing to say — but export-html then falls back to a JSON dump (§5.4).
 */
export function renderMemoryResult(
	result: { content: Array<{ type: string; text?: string; data?: string; mimeType?: string }> },
	options: ToolRenderResultOptions,
	theme: Theme,
	context: ToolRenderContextLike,
): Text {
	const component = (context.lastComponent as Text | undefined) ?? new Text("", 0, 0);
	const raw = getTextOutput(result, false).trim();
	if (!raw) {
		component.setText("");
		return component;
	}
	const lines = raw.split("\n");
	const body = truncate(theme, lines, MAX_RESULT_LINES, options.expanded);
	component.setText("\n" + (context.isError ? theme.fg("error", body) : body));
	return component;
}

/** Structural slice of ToolRenderContext this module needs (avoids a wide import). */
interface ToolRenderContextLike {
	lastComponent: unknown;
	expanded: boolean;
	argsComplete: boolean;
	isError: boolean;
}
```

## 9. 失败分析（10 条，含父任务点名的 3 条）

> 每条格式：**触发条件 → 表现 → 证据 → 防线**。凡「实测」均为本机探针输出。

### F1 ⭐ 流式期 args 是半截的（父任务点名）

- **触发**：`message_update` 每次到达都调 `updateArgs`（`interactive-mode.ts:3155-3186`），`content` 字段可能刚到一半；首帧甚至 `args === undefined` 或 `{}`。
- **表现**：整体崩裂（`args.content.split` → TypeError）、或显示 `undefined` 字样、或**首帧就闪出一个空白行**。
- **实测**（probeB）：`new ToolExecutionComponent(..., undefined, ...)` → 渲染器拿到 `args === undefined`；渲染出 `{"a":"UNDEF","partial":true}`（我的探针原样打印）。
  **实测**（probeM）：`parseStreamingJson` 在半截 JSON 上返回**前缀有效字段** —— `cut=20` → `{"uri":"core://ident"}`；`cut=40` → `{"uri":"core://identity","content":"伊莱在酒"}`。⇒ **半截 `content` 是常态，不是边界情况**。
- **防线**：所有字段读一次 `str()`（`render-utils.ts:25-29`，非字符串返回 `null`，`null` 与 `""` 都走 placeholder）；**永不**对 `args.content` 做 `.split` 后再判类型；`!context.argsComplete` 时打「(写入中…)」而不是猜。

### F2 ⭐ export 静默吞异常 → 导出 HTML 掉进 JSON dump（父任务点名）

- **触发**：渲染器内部抛异常（或返回 `undefined`）。
- **表现（export）**：`createToolHtmlRenderer` 的 `try{...}catch{ return undefined }`（`tool-renderer.ts:115-118`、`:166-169`）**吃掉异常**；`template.js:1029` 的守卫因 `undefined` 全假 ⇒ 走 `:1054-1058` 的 `JSON.stringify(args, null, 2)` 回退。
  **实测**（probeE）：`renderResult` 返回 `undefined` → `r.renderResult(...) === undefined`；返回空 `Container` → `{expanded: ""}`（空串也 falsy，同样回退）。
  **实测**（probeE）：OSC-8 超链接**原样泄进 HTML** —— `"\u001b]8;;file:///tmp/x\u001b\\core://x\u001b]8;;\u001b\\"`。根因：`ansi-to-html.ts:193` 的 `ANSI_REGEX = /\x1b\[([\d;]*)m/g` **只匹配 SGR**（`ESC[ … m`），`ESC]…` 根本不在集合里。
- **防线**：(a) 渲染器**内部绝不抛**（所有取值经 `str()`，无 `JSON.parse`、无数组下标假设）；(b) **不用 `hyperlink()`**（`tui/src/terminal-image.ts:626-628`）也不用 `linkPath()`（`render-utils.ts:19-23`，它在 `getCapabilities().hyperlinks` 为真时内部调 `hyperlink`）→ memory URI 不是文件路径，本来也不该给 `file://` 链接；(c) 只有 `theme.fg/bold` 这类 SGR 输出。

### F3 ⭐ `lastComponent` 原型错（父任务点名）

- **触发**：跨 `updateDisplay`（`tool-execution.ts:278` `renderContainer.clear()` 后重建子组件）复用了**上一次返回的不同类型组件**。
- **实测（关键：call/result 是独立槽位）**（probeO）：`log = "call:undef | call:Text | result:undef"` —— **result 槽位的 `lastComponent` 是 `undefined`**，与 call 槽位（`tool-execution.ts:20-21` 两个独立字段）**互不污染**。
  **实测（原型错会静默失效，不是崩溃）**（probeD A2）：第一趟返回 `Text`、第二趟把它当 `Box` 用（`(last as Box).clear()`）→ **不抛异常**，因为 `updateDisplay` 的 `catch`（`tool-execution.ts:290-294`）吞掉并把 `lastComponent` 重置为 `undefined`，**回退到裸名**。所以：**类型搞错 = 悄悄退化**，比崩溃更难发现。
- **防线**：call 与 result 各自 `?? new Text("", 0, 0)`（照抄 `grep.ts:376`/`:381`），**两个渲染器只认 `Text`**；不用 `Box`/`Container` 做 call 组件（`Box.clear()` 与 `Text.setText` 二选一，混用必踩）。

### F4 ⭐⭐ 渲染器返回 `undefined` → **崩掉整个进程**（父任务描述与实测不符）

- **触发**：渲染器某个分支 `return undefined`（TS 会拦，但 `as any`、`?? undefined`、`.find()` 结果都能绕过）。
- **表现**：`undefined` 被 `renderContainer.addChild(component)`（`tool-execution.ts:288`/`:302`/`:314`）接受（`Container.addChild` 只 push，无类型检查，`tui/src/tui.ts:214-216`）；**下一次 `render()`** 在 `for (const child of this.children) child.render(width)`（`tui/src/tui.ts:236-240`）抛 `TypeError: Cannot read properties of undefined (reading 'render')`。
- **证据（实测）**（probeA «THREW», probeD (E), probeF）：
  ```
  (E) updateResult ok; rows: THREW: Cannot read properties of undefined (reading 'render')
  THREW: Cannot read properties of undefined (reading 'render')   ← renderCall undefined
  THREW: Cannot read properties of undefined (reading 'render')   ← renderResult undefined
  ```
  且 `doRender`（`tui-main-screen.ts:180-205`）**没有任何 try/catch**（`grep -n "try\|catch" tui-main-screen.ts` → 空），异常一路到 `process.prependListener("uncaughtException", ...)`（`interactive-mode.ts:3983-3985`）→ `uncaughtCrash`（`:3934-3937`）→ **`process.exit(1)`**。
  ⇒ **父任务写的「否则走 fallback 又把 result 渲染出来」在 TUI 里不成立**：进程直接死。
- **防线**：返回类型**声明为非可选**（`(…) => Text` 而非 `| undefined`，见 §7.1 签名）；空 = `component.setText("")`（`Text` 对空串返回 `[]`，`text.ts:52-58`）；真要「整行消失」用 `Container`（`write.ts:261-263`），**永不用 `undefined`**。
  **必须加的测试**：§8.3 第二条（空 `content` 时不抛）。

### F5 首帧 `args === undefined` 之外的「空 uri」

- **防线**：`uri === "" || uri === null` → 统一 placeholder `…`（§7.1 的 `renderMemorizeCall`），**不留裸空格**。

### F6 `revise` 批量里混入空 `uri`

- **触发**：模型调 `revise({batch:[{importance:2}]})` 而漏了 `uri`（schema 里 `reviseModSchema.uri` 是**必填** `Type.String()`，`tools.ts:474`，但 `executeRevise` 的**单条**路径会 `params.uri ?? ""`（`:637`）→ 空串进 `applyReviseMod`）。
- **表现**：call 渲染出 `   ★重要度 → 2`（空 uri + 缩进），看不出改的是谁；result 是 `未找到：`。
- **防线**：渲染时 `uri || "…"`；**不改 schema**（改 `Type.Optional` 会让 `failed` 语义漂移，超出本期）。

### F7 超长 / 超多行正文撑爆一次渲染

- **触发**：`memorize` 正文 200+ 行（模型写长场景纪要是常态）。

### F8 `lastComponent` 复用与「累积式」组件的组合陷阱

- **触发**：渲染器写 `const c = (ctx.lastComponent as Container) ?? new Container(); c.addChild(...)`（看似无害的「累加」写法）。

- **防线**：`Text.setText()` 是**替换**不是追加（`text.ts:25-30` 清缓存并整体替换）⇒ 选 `Text` 天然免疫；**禁止**在渲染器里 `addChild` 到 `lastComponent`。

### F9 `details` 新字段无人消费 → 死代码

- **触发**：M5/M8 加了 `ok`/`uri`/`failed_uris`，但若渲染器/**没有**任何消费者，它们就是死字段。
- **表现**：无运行时现象，但「加它是为了机器可读成功信号」的**设计目的落空**（§1.4a）。
- **防线**：**本期明确消费点只有两处** —— (a) §8.1 的 `failed_uris` 断言；(b) 未来若做「失败行标红」需要 `ok`。⇒ **§12.5 U2 已列为待拍板**：要么本期就用 `ok` 给 renderResult 上色（让字段不空转），要么承认它是**为后续留的接口**并如实登记。**MUST NOT 假装它是已接线功能。**

### F10（附）`revise` 的 `history`/`restore` 会走 memorize 的渲染器

- **触发**：`revise` 一个工具三个 action（`tools.ts:486-493`），`renderReviseCall` 只认 `uri`/`batch`/编辑字段。
- **表现**：`revise({action:"history", uri:"core://x"})` 的 call 渲染成 `修订记忆\ncore://x  （无内容改动）`，**略有误导**（它其实是查询）。

## 10. 对父任务事实的更正（4 条，前 3 条有实测证据）

### 10.1 更正：return `undefined` 不是「走 fallback」，是**崩进程**

见 F4。父任务原文：「什么都不显示」必须 return 空组件，不能 return undefined（**否则走 fallback 又把 result 渲染出来**）。
**实测**：TUI 路径上 `undefined` 会被 `addChild` 收下，然后在 `tui/src/tui.ts:236-240` 抛 `TypeError`，`doRender` 无 catch，最终 `uncaughtCrash` → `exit(1)`。
⇒ **结论（必须 return 空组件）不变，但严重度被低估了**：这不是「格式不对」，是**进程崩溃**。这条应当作为**实现期硬门**（§8.3 的测试）。

### 10.2 更正：`isPartial` 在 export 里恒 `true`，但 `argsComplete` 恒 `true`

父任务只说 `isPartial` 恒定。**实测**（probeE）补全：`createRenderContext(..., isPartial=true, ...)`（`tool-renderer.ts:110`）同时硬编码 `argsComplete: true`（`:90`）。
⇒ 渲染器**不能**用 `!argsComplete` 来打「(写入中…)」—— 在 export 里 `argsComplete` 永远真，那段分支只会出现在 TUI。**这不影响正确性**（export 的 args 本来就是完整的），但实现者若把它当「加载态」跨两种介质复用会困惑。

### 10.3 更正：依赖返回值的测试是 **7 处**，不是 6 处

父任务列 `:42,76,89,117,125,484`（6 处）。**实际 grep**（`已记下|已修订|details.failed`）命中 **7 处**，遗漏 `tools.test.ts:57` 与 `:100`。补全后见 §8.1（两条都安全）。

### 10.4 更正：`tool-execution.ts:273` 的判定不是「有没有 renderer」，而是「**有没有 tool definition**」

父任务说「`:273` `hasRendererDefinition()`」。**实测读码**：`hasRendererDefinition()`（`tool-execution.ts:104-106`）的返回是 `this.builtInToolDefinition !== undefined || this.toolDefinition !== undefined` —— 它判的是**定义存在性**，不是「有 renderCall」。
⇒ 关键推论：**只要 memory 工具进了 `_toolDefinitions`（它们确实进了），`hasRendererDefinition()` 就恒真**，`renderCall` 缺失时走的是 `:281-283` 的 `createCallFallback()`，而**不是** `:326-330` 的 `contentText` 全量 dump 分支。
⇒ 这解释了 §1.2 的实测（裸工具名，4 行），也意味着：**在 S1 之前，memory 工具的 result 已经不会走 JSON dump**（它走 `:299-304` 的 `createResultFallback()`）。
